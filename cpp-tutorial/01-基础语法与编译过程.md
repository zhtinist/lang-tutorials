# 基础语法与编译过程

本章是整套速查手册的起点,覆盖"跑起来一个 C++ 程序"所需的全部基础机制:编译器如何把 `.cpp` 变成可执行文件、头文件与 include 机制、命名空间、标准输入输出流,以及新手最容易踩的两个坑——声明与定义的区别、ODR(一次定义规则)。目标是把知识点列全,每点给一个可编译验证的最小例子。

## 一、最小程序与编译器

```cpp
#include <iostream>

int main() {
    std::cout << "Hello, C++!" << std::endl;
    return 0;
}
```

```
$ g++ -std=c++20 -Wall hello.cpp -o hello && ./hello
Hello, C++!
```

macOS 上 `g++` 实际是 Apple Clang 的别名(`g++ --version` 会看到 `Apple clang`)。常用编译选项:

| 选项 | 作用 |
|---|---|
| `-std=c++20` | 指定语言标准(还可以是 `c++11/14/17/23`) |
| `-Wall -Wextra` | 打开常用警告 |
| `-O2` | 优化等级 |
| `-g` | 生成调试信息 |
| `-o <file>` | 指定输出文件名 |

## 二、编译的四个阶段:预处理 → 编译 → 汇编 → 链接

一次 `g++ hello.cpp -o hello` 背后实际做了四件事,可以用 `-E`/`-S`/`-c` 逐阶段拆开看:

**1. 预处理(Preprocessing)**:展开宏、`#include`、条件编译,产出纯文本的翻译单元。

```cpp
#define SQUARE(x) ((x) * (x))
int gVal = SQUARE(5);
int main() { return 0; }
```

```
$ g++ -E stages.cpp | tail -3
int gVal = ((5) * (5));
int main() { return 0; }
```

宏 `SQUARE(5)` 被原样替换成 `((5) * (5))`,预处理阶段不理解 C++ 语法,只做文本替换。

**2. 编译(Compilation)**:把预处理后的代码翻译成汇编代码(`-S`,产出 `.s` 文件),这一步做语法检查、类型检查、生成中间代码并优化。

```
$ g++ -S -std=c++20 hello.cpp -o hello.s && head -8 hello.s
	.build_version macos, 26, 0	sdk_version 26, 5
	.section	__TEXT,__text,regular,pure_instructions
	.globl	_main
	.p2align	2
_main:
	.cfi_startproc
```

**3. 汇编(Assembly)**:汇编器把 `.s` 翻译成机器码,产出目标文件(`.o`,`-c`),此时函数/变量以"符号"形式存在,尚未确定最终地址。

```
$ g++ -c -std=c++20 hello.cpp -o hello.o && file hello.o
hello.o: Mach-O 64-bit object arm64
```

**4. 链接(Linking)**:链接器把多个目标文件、静态/动态库粘合成一个可执行文件,解析符号引用,分配最终地址。

```
$ g++ hello.o -o hello_linked && ./hello_linked
Hello, C++!
```

一个 C++ 工程通常由多个 `.cpp` 文件(翻译单元)组成:每个 `.cpp` 独立走完预处理→编译→汇编,得到各自的 `.o`,最后统一链接。

## 三、头文件、include guard 与 `#pragma once`

头文件(`.h`)通常只放**声明**(函数原型、类定义、`extern` 变量),`.cpp` 放**实现**,通过 `#include` 把声明"抄"进使用者的翻译单元。

```cpp
// math_utils.h
#ifndef MATH_UTILS_H
#define MATH_UTILS_H

int add(int a, int b);   // 只有声明,没有定义

#endif // MATH_UTILS_H
```

```cpp
// math_utils.cpp
#include "math_utils.h"

int add(int a, int b) {
    return a + b;
}
```

```cpp
// main.cpp
#include <iostream>
#include "math_utils.h"

int main() {
    std::cout << "1 + 2 = " << add(1, 2) << std::endl;
    return 0;
}
```

```
$ g++ -c math_utils.cpp -o math_utils.o
$ g++ -c main.cpp -o main.o
$ g++ math_utils.o main.o -o multifile_out && ./multifile_out
1 + 2 = 3
```

`#ifndef/#define/#endif` 这套写法叫 **include guard**:防止同一个头文件在同一个翻译单元里被 `#include` 两次导致重复定义。现代编译器普遍支持更简洁的 `#pragma once`(非标准但事实标准,几乎所有编译器都支持),效果相同:

```cpp
// point.h
#pragma once

struct Point {
    int x;
    int y;
};
```

```cpp
// a.cpp
#include "point.h"
#include "point.h"   // 重复 include,#pragma once 保证只展开一次
int main() {
    Point p{1, 2};
    return p.x + p.y;
}
```

```
$ g++ -std=c++20 -Wall a.cpp -o pragma_out && ./pragma_out; echo $?
3
```

## 四、命名空间 `namespace`

命名空间用来避免不同模块之间的命名冲突,可以嵌套,可以用 `using` 引入。

```cpp
#include <iostream>

namespace math {
    int square(int x) { return x * x; }
    namespace detail {
        int helper_value = 100;
    }
}

namespace phys {
    int square(int x) { return x * x * 2; } // 同名函数,不同命名空间不冲突
}

int main() {
    std::cout << math::square(4) << std::endl;            // 16
    std::cout << phys::square(4) << std::endl;             // 32
    std::cout << math::detail::helper_value << std::endl;  // 100

    using namespace math;
    std::cout << square(5) << std::endl; // 25,using 后可省略前缀

    return 0;
}
```

```
$ g++ -std=c++20 -Wall ns.cpp -o ns_out && ./ns_out
16
32
100
25
```

要点清单:

- `using namespace X;` 会把 `X` 里所有名字引入当前作用域,**头文件里应避免使用**(会污染所有 include 它的文件)。
- 匿名命名空间 `namespace { ... }` 让符号只在当前翻译单元可见,是 C 里 `static` 全局变量/函数的现代替代。
- `std` 是标准库的命名空间,`std::cout`、`std::string`、`std::vector` 等都在其中。

## 五、输入输出流 `cin`/`cout`

```cpp
#include <iostream>

int main() {
    int age;
    std::cout << "请输入年龄: ";
    std::cin >> age;                 // 从标准输入读取一个 int
    std::cout << "你输入的年龄是 " << age << std::endl;
    return 0;
}
```

常用要点:

- `<<` 是输出流的插入运算符,`>>` 是输入流的提取运算符,两者都可以连续链式调用(`cout << a << b << c;`),因为返回的是流对象的引用。
- `std::endl` 输出换行并**刷新缓冲区**;只换行不强制刷新用 `"\n"`,大量输出时后者性能更好。
- `std::cin >> x` 遇到类型不匹配(比如给 `int` 输入字母)会让流进入失败状态,需要 `cin.clear()` + `cin.ignore()` 才能恢复。
- `std::cerr`(标准错误,无缓冲)用于输出错误信息,`std::clog`(有缓冲)同样输出到标准错误。
- 整行读取用 `std::getline(std::cin, line)`,而不是 `>>`(后者遇空白就停)。

## 六、编译期常见坑

**1. 声明(declaration)vs 定义(definition)**:声明只是告诉编译器"这个名字存在,类型是什么",定义则真正分配存储/给出函数体。一个实体可以被声明多次,但**只能定义一次**。只声明不定义,编译能通过(编译器信任你后面会有定义),但链接阶段会报错:

```cpp
int notDefined(int x); // 只声明
int main() { return notDefined(3); }
```

```
$ g++ -std=c++20 -Wall decl_only.cpp -o decl_out
Undefined symbols for architecture arm64:
  "notDefined(int)", referenced from:
      _main in decl_only-xxx.o
ld: symbol(s) not found for architecture arm64
```

**2. ODR(One Definition Rule,一次定义规则)**:同一个实体(非 inline 函数、全局变量等)在整个程序中只能有一份定义。如果头文件里直接写函数体(没有 `inline`),被多个 `.cpp` 包含就会在链接时重复定义:

```cpp
// bad.h —— 违反 ODR 的写法
int helper() {
    return 42;
}
```

```
$ g++ -c a.cpp -o a.o   # a.cpp 包含 bad.h
$ g++ -c b.cpp -o b.o   # b.cpp 也包含 bad.h
$ g++ a.o b.o main.o -o odr_out
duplicate symbol 'helper()' in:
    a.o
    b.o
ld: 1 duplicate symbols
```

修复方式是给函数加 `inline`(允许多个翻译单元中出现相同定义,链接器负责去重合并),或者把定义挪到唯一的 `.cpp` 里、头文件只留声明:

```cpp
// good.h
inline int helper() {    // inline 允许多个翻译单元中出现相同定义
    return 42;
}
```

```
$ g++ a2.o b2.o main2.o -o odr_good && ./odr_good
84
```

`class`/`struct` 定义、模板定义、`constexpr` 变量本身就隐含 `inline` 语义,因此可以放心写在头文件里被多次包含而不违反 ODR。

## 七、struct 与 class、struct 与 union 的边界

`struct` 和 `class` 在语法能力上完全等价——都可以有构造/析构函数、虚函数、继承、模板参数、访问控制修饰符;[第 4 章](04-面向对象编程.md#一类的定义与访问控制)已经指出两者在语言层面**唯一**的区别是两处默认行为:成员默认访问权限(struct 是 public,class 是 private)和默认继承权限(`struct Derived : Base` 默认 public 继承,`class Derived : Base` 默认 private 继承)。

此外还有一处容易忽略的纯语法规定:模板参数声明只能写 `template<class T>` 或 `template<typename T>`,写成 `template<struct T>` 编译器不会理解成"声明一个模板类型参数",而是按"先前向声明一个 struct 类型 T,再拿它当非类型模板参数"解析,进而报出令人费解的错误——这条限制和 struct/class 的语义无关,纯粹是语言语法的历史遗留:

```
$ g++ -std=c++20 -c bad_template.cpp
error: non-type template parameter has incomplete type 'struct T'
note: forward declaration of 'T'
```

工程惯例上(编译器不强制):struct 用于纯数据聚合——没有不变量需要维护、所有成员天然 public,典型场景是配置项、坐标点、网络协议包头;class 用于有封装需求的类型,内部状态需要通过接口维护不变量。struct 里写 private 成员和虚函数完全合法,编译器不会阻止,但这会让读者困惑——语义上"纯数据"和"多态/行为扩展"是冲突的,实际项目里很少见到 struct 参与继承体系。

顺带一提 **POD(Plain Old Data)** 的判定标准:没有虚函数、没有用户定义的构造/析构、所有成员 public、可以用 `memcpy` 安全拷贝,内存布局与 C 完全兼容。这与关键字本身无关——struct 因为默认 public、语义上暗示"纯数据",天然容易写成 POD,但 class 只要满足同样的条件一样是 POD。用 `extern "C"` 做混合编程时(见下一节),共享的结构体定义必须保持 C 兼容——只能有成员变量,不能有成员函数和继承,这也是为什么跨语言公共头文件里的结构体几乎总是"纯数据" struct。

**struct 与 union 的差异** 不只是"内存共享 vs 独立存储"这一层。struct 本质上就是 class(只是默认 public),拥有完整的面向对象能力;union 的能力被语法明确限制死了——不能作为基类被继承,也不能继承别的类或 struct,不能有虚函数:

```cpp
union UV { virtual void f() {} };   // 不允许
struct Base {};
union UB : Base {};                  // 不允许
union UC { int a; };
struct D : UC {};                    // 不允许
```

```
error: unions cannot have virtual functions
error: unions cannot have base classes
error: unions cannot be base classes
```

根源在于 union 的核心语义是"所有成员共享同一段内存,同一时刻只有一个成员有效"——虚函数依赖的 vptr、继承依赖的基类子对象,都要求对象内部有稳定的、按类型区分的独立布局,这和"共享同一段内存"直接矛盾。但 union 仍然可以有构造函数、析构函数和普通成员函数,访问控制 `private`/`protected` 也和 struct/class 一样正常起作用(这点常被误传为"union 成员强制 public",实测并非如此——union 默认成员是 public,但显式声明 private 完全合法,外部访问会被正确拒绝)。

C++11 之前 union 只能存放 POD 类型;C++11 放开限制,允许存放 `std::string` 这类非 POD 类型,但编译器不会自动为它调用构造/析构——因为 union 并不知道当前哪个成员是"活跃"的。开发者必须自己用 placement new 显式构造、手动调用析构函数:

```cpp
union U {
    int i;
    std::string s;
    U() : i(0) {}
    ~U() {}                          // 不知道当前活跃的是 i 还是 s,不能在这里自动析构 s
};

U u;
new (&u.s) std::string("hello");     // placement new 显式构造
std::cout << u.s << "\n";
u.s.~basic_string();                  // 用完必须手动析构,否则内存泄漏
```

```
hello
```

漏掉手动析构就是内存泄漏(活跃成员是 string 却没调用它的析构函数),析构了不该析构的成员则是未定义行为。现代 C++ 更推荐用 **`std::variant`(C++17)** 替代原生 union:内部维护一个 tag 跟踪当前活跃的类型,自动管理构造/析构,访问了错误的类型会抛异常而不是产生未定义行为。原生 union 仍然保留的场景是二进制协议解析(把一块 buffer 按不同字段类型解释,比如网络包头、硬件寄存器)和极致的内存节省(嵌入式场景)。

## 八、静态存储:static 关键字与变量的作用域、生命周期

`static` 修饰不同实体时,解决的都是同一个问题的不同侧面——"这份存储活多久、谁能看见它",与 `const` 控制"能不能被修改"完全正交,两者可以同时使用:`static const int X = 42;` 既是类范围内共享的一份,又是只读的。

**static 的四种用法**:

1. **局部静态变量**:生命周期延长到程序结束,但作用域仍限于函数内部;只在第一次执行到该定义语句时初始化一次,之后的调用跳过初始化、沿用上次的值。
2. **文件作用域 static**:把符号限制为内部链接,其他翻译单元无法通过 `extern` 访问,实现"文件级私有"。
3. **类的静态成员变量**:属于类本身而非任何一个对象,所有对象共享同一份存储,必须在类外定义一次(C++17 起可以用 `inline static` 在类内直接定义)。
4. **类的静态成员函数**:没有隐式的 `this` 参数,不能访问非静态成员,可以直接用 `类名::函数名()` 调用而无需实例。

```cpp
void counter() {
    static int n = 0;   // 只在第一次执行到这里时初始化
    ++n;
    std::cout << "n=" << n << "\n";
}
int main() { counter(); counter(); counter(); }
```

```
n=1
n=2
n=3
```

**局部变量、全局变量、静态局部变量的差异** 要从作用域和链接性两个维度理解(存储位置和四大内存分区已在[第 2 章](02-变量类型与内存布局.md#六四大内存分区栈-堆-全局静态区-常量区)讲过,这里不重复):

| 维度 | 局部变量 | 全局变量 | 静态局部变量 |
|---|---|---|---|
| 作用域 | 定义它的代码块内 | 整个翻译单元(加 `extern` 可跨文件) | 定义它的函数内部,外部完全不可见 |
| 生命周期 | 跟随栈帧创建/销毁 | 贯穿整个程序运行期 | 贯穿整个程序运行期 |
| 链接性 | 无(每次调用都是新对象) | 默认外部链接;加 `static` 后变成内部链接 | 无链接性,只能通过函数内部访问 |
| 初始化时机 | 每次执行到定义语句 | 程序启动时 | 仅第一次执行到定义语句 |

**static 修饰全局变量改变的是链接性,和 static 修饰局部变量改变生命周期是两回事**,不要混为一谈:不加 `static` 的全局变量具有外部链接,可以被其他翻译单元 `extern` 访问;加了 `static` 后只在当前文件内可见,用于避免跨文件命名冲突。局部变量与全局变量同名时,函数内部的局部变量会遮蔽同名全局变量,可以用 `::globalVar` 显式访问被遮蔽的全局变量,但更好的做法是从一开始就避免同名。

**跨翻译单元的初始化顺序**是一个经典陷阱:同一翻译单元内,全局/静态变量按定义顺序初始化;不同 `.cpp` 文件之间的初始化顺序未定义(Static Initialization Order Fiasco)。如果 A 文件的全局对象初始化依赖 B 文件的全局对象,可能在 B 还未初始化时就被使用,而这类 bug 只在特定链接顺序下才会复现,非常难排查。规避方法是用函数内局部 `static` 变量替代跨文件的全局对象(Construct On First Use 惯用法)——谁先调用谁触发初始化,顺序由调用链天然决定,不再依赖不确定的静态初始化顺序。

**静态局部变量初始化的线程安全性**:C++11 标准保证静态局部变量的初始化过程是线程安全的("magic statics")——如果多个线程同时第一次执行到该定义语句,编译器插入的同步逻辑保证只有一个线程真正执行初始化,其余线程阻塞等待。这是 Meyers 单例(函数内 `static` 局部变量)在 C++11 之后天然线程安全的理论基础(详见[第 4 章单例模式](04-面向对象编程.md))。初始化完成之后的读写不受这层保护,并发修改仍需要额外同步。

## 九、extern "C" 与语言链接

`extern "C"` 告诉 C++ 编译器:对被它包裹的函数声明不做**名称修饰(Name Mangling)**,链接时直接用原始函数名作为符号。

根源在于 C++ 支持函数重载,同一个函数名可以对应多个参数不同的版本,编译器必须把参数类型编码进符号名才能让链接器区分它们:

```cpp
void foo(int) {}
void foo(double) {}
```

```
$ g++ -std=c++20 -c mangle.cpp -o mangle.o && nm mangle.o | grep foo
0000000000000010 T __Z3food
0000000000000000 T __Z3fooi
```

`_Z3fooi`/`_Z3food` 是 Itanium C++ ABI 编码后的符号名(macOS 上符号前还会多加一个下划线),参数类型被编码进了符号本身。C 语言没有重载,一个函数名只对应一个函数,符号名就是函数名本身,不需要这层编码——这也解释了 C 为什么不支持重载:没有名称修饰机制去区分同名函数。

问题出在混合编程时:C++ 代码调用 C 库函数,C++ 编译器会对调用做名称修饰、去找修饰后的符号,但 C 库导出的符号是未修饰的原始名,两边对不上,链接器报 "undefined reference"。`extern "C"` 的作用就是让编译器对这些声明按 C 的规则处理,这样 C++ 里生成的符号引用能和 C 库里的符号匹配上。除了名称修饰,`extern "C"` 通常也意味着采用 C 的调用约定,确保参数压栈方式、栈清理责任等二进制层面的细节完全兼容。

写跨语言通用头文件的标准写法是用 `__cplusplus` 宏保护:

```cpp
// extc.h
#ifdef __cplusplus
extern "C" {
#endif
int add_c(int a, int b);
#ifdef __cplusplus
}
#endif
```

```cpp
// extc.c
#include "extc.h"
int add_c(int a, int b) { return a + b; }
```

```cpp
// extc_main.cpp
#include <iostream>
#include "extc.h"
int main() { std::cout << add_c(2, 3) << "\n"; }
```

```
$ gcc -c extc.c -o extc.o
$ g++ -std=c++20 -c extc_main.cpp -o extc_main.o
$ g++ extc.o extc_main.o -o extc_out && ./extc_out
5
```

C 编译器看不到 `__cplusplus`(未定义),直接跳过 `extern "C"` 部分,按普通声明处理;C++ 编译器能看到并正确地按 C 链接规则处理这些声明——这就是 `extc.c` 用 `gcc` 编译、`extc_main.cpp` 用 `g++` 编译,两个目标文件却能正常链接到一起的原因。

几个边界问题:`extern "C"` **不能**修饰类的成员函数——成员函数隐含 `this` 参数、依赖 C++ 对象模型,没法套用 C 的调用约定;想让 C 代码调用 C++ 类的功能,通常做法是写一层 `extern "C"` 的包装函数,内部创建对象、调用成员函数,对外只暴露纯 C 接口。`extern "C"` 的函数也**不能重载**——不做名称修饰意味着符号名就是函数名本身,两个同名的 `extern "C"` 函数即使参数不同,链接器也会报重复定义。典型应用场景有三类:C++ 调用 C 库(glibc、SQLite、libpng 等)时在其头文件声明前加 `extern "C"`;C++ 库需要被 C 程序调用时用它导出接口;Python/Lua 等语言的 FFI 通常是 C 风格接口,C++ 写扩展模块时必须用它导出入口函数。

## 十、inline 函数与 #define 宏的区别

`inline` 在 [第 3 章](03-函数与引用.md#三内联函数-inline) 和本章第六节都已出现,但两处讨论的都是"函数调用开销"和"ODR"这两个角度。`inline` 函数和 `#define` 宏真正的本质区别在于**处理阶段**:宏在**预处理阶段**做纯文本替换,编译器还未介入,因此不做类型检查、不遵守作用域规则、无法调试;`inline` 函数是在**编译阶段**处理的真正函数,有完整的类型检查,遵守命名空间和类的作用域,参数按正常的函数调用规则只求值一次。

宏最经典的坑是**多次求值**——因为宏只是文本替换,参数在展开后的文本里出现几次就被求值几次:

```cpp
#define SQUARE(x) ((x) * (x))
int a = 5;
int r = SQUARE(a++);   // 展开为 ((a++) * (a++)),a 的自增发生了两次
```

```
r=30 a=7
```

`a` 从 5 开始,两次 `a++` 各自先取值再自增,`r` 拿到的是两次不同求值结果的乘积而非 `5*5`,`a` 也被自增了两次而非一次——这是未定义行为(标准并不保证具体的求值顺序和次数造成的结果),不同编译器/优化级别可能得到不同数值,不能依赖任何具体表现。`inline` 函数不会有这个问题,因为参数在传入函数体之前就已经求值完毕,函数体内只使用求值结果一次。

宏没有类型概念,也不受作用域约束——一旦 `#define` 就全局生效,容易和其他代码里的同名标识符冲突。`inline` 函数遵守正常的语义分析流程:类型检查、重载决议、模板实例化,处在声明它的命名空间/类作用域内,不会污染全局命名空间。

但宏有三项 `inline` 函数做不到的能力,只有预处理器才能提供:**条件编译**(`#ifdef`/`#ifndef`)、**字符串化**(`#` 运算符把参数原样转成字符串字面量,如 `#define STR(x) #x`,`STR(hello)` 得到 `"hello"`)、**记号拼接**(`##` 运算符把两个记号拼接成一个新标识符,如 `#define CONCAT(a,b) a##b`,`CONCAT(var,1)` 得到 `var1`)。这些能力在日志宏、断言宏、代码生成场景仍然常用,是宏在现代 C++ 里没有被完全淘汰的原因。现代 C++ 用 `constexpr` 替代宏定义的编译期常量,用 `inline` 函数或模板替代宏函数,但条件编译、平台适配、依赖 `__FILE__`/`__LINE__` 的日志宏这几类场景,宏仍然不可替代。

## 十一、sizeof 与 strlen 的区别

`sizeof` 是**编译期运算符**,依据的是类型信息,返回一个类型或变量占用的字节数(对 C 风格字符串而言,`sizeof` 数组包含末尾的 `'\0'`)。`strlen`(声明于 `<cstring>`)是**运行时函数**,依据的是内存内容,从起始地址逐字节扫描,直到遇到第一个 `'\0'` 为止,返回的字符个数不包含这个结尾符。

```cpp
char arr[] = "hello";
char* ptr  = arr;
std::cout << sizeof(arr) << " " << strlen(arr) << "\n";   // 6 5:数组类型 char[6] 含 '\0',内容扫描不含
std::cout << sizeof(ptr) << " " << strlen(ptr) << "\n";    // 8 5:sizeof 只看指针类型,与内容无关

char s[] = {'a', '\0', 'b', 'c'};
std::cout << sizeof(s) << " " << strlen(s) << "\n";        // 4 1:strlen 碰到第一个 '\0' 就停
```

```
sizeof(arr)=6 strlen(arr)=5
sizeof(ptr)=8 strlen(ptr)=5
sizeof(s)=4 strlen(s)=1
```

数组作为函数参数传递时会退化为指针(见[第 2 章数组与指针的关系](02-变量类型与内存布局.md#五数组与指针的关系)),函数内部对形参调用 `sizeof` 得到的是指针大小而非数组大小,如果需要在函数内知道数组长度,必须额外传参数,或者用模板对数组引用做推导以在编译期取得长度。

`strlen` 的 O(n) 复杂度有一个容易被忽视的实际影响:如果在循环条件里直接写 `i < strlen(s)`,每轮迭代都会重新扫描整个字符串,一个本应是 O(n) 的循环会退化成 O(n²);正确做法是提前把长度缓存到局部变量里。C++ 标准里 `sizeof` 的结果始终是编译期常量,可以用于模板参数和数组声明这类要求常量表达式的位置——C++ 不支持 C99 引入的变长数组(VLA),因此 C++ 里 `sizeof` 永远是编译期可求值的。如果用 `std::string`,`.size()`/`.length()` 是 O(1)——string 内部维护了长度字段,只有处理 C 风格字符串(`char*`)时才真正需要 `strlen`。

## 十二、浮点数比较的陷阱

浮点数不能直接用 `==` 比较,根源在 IEEE 754 的**表示方式**,而不是"计算出了误差"这么简单:二进制浮点数无法精确表示所有十进制小数。`0.1` 转成二进制是 `0.0001100110011...`(`0011` 无限循环),存储时必须在有效位处截断——这就是误差的来源:不是运算算错了,而是这个数字本身就没法用有限的二进制位精确表示。

```cpp
double a = 0.1 + 0.2;
std::cout << std::setprecision(20) << a << "\n";
std::cout << (a == 0.3) << "\n";
```

```
0.30000000000000004441
false
```

正确的比较方式是设定一个误差容忍度(epsilon),判断两数之差是否落在容忍范围内,常见的有三种策略:

- **绝对误差**:`|a - b| < epsilon`。简单直接,但 epsilon 是固定值——对数值很大的场景不够精确,对接近零的数又显得过于宽松。适合数值范围已知且相对固定的场景。
- **相对误差**:`|a - b| / max(|a|, |b|) < epsilon`。按比例衡量误差,对大数和小数都相对公平,但当 a、b 都接近 0 时,除以一个接近 0 的分母会让结果失真。适合数值跨度大的科学计算场景。
- **混合方法**:先用绝对误差处理接近 0 的边界情况,再对一般情况用相对误差,实际项目里最常见。

epsilon 该取多大没有万能答案:`float` 大约 7 位有效数字,绝对误差通常取 `1e-5` 到 `1e-6`;`double` 大约 15 位有效数字,取 `1e-9` 到 `1e-12`;若采用相对误差,一般取 `std::numeric_limits<float>::epsilon()`(约 `1.19e-7`)的若干倍作为起点,具体值要结合业务对精度的实际要求来定。

另一处经过实测确认的陷阱是"大数吸收小数":

```cpp
double huge = 1e20;
std::cout << ((huge + 1.0) == huge) << "\n";   // true,尾数精度不够表示这个差值
```

```
true
```

其余常见坑还包括:循环中反复累加一个小数,误差会随迭代次数逐渐累积;两个相近的大数相减,有效数字会急剧减少(抵消现象);浮点加法不满足结合律,`(a + b) + c` 不一定等于 `a + (b + c)`。极少数场景下可以直接用 `==` 比较浮点数:比较能被精确表示的整数值(如 `3.0 == 3.0`)、检查是否等于字面量赋值的特定值、或两个值来自同一次赋值且未经过任何运算——一旦经过加减乘除,就不应再用 `==`。

`NaN`(Not a Number,表示无效运算结果,如 `0.0/0.0`、`sqrt(-1)`)有一条特殊规则:它与任何值比较(包括自身)都返回 `false`:

```cpp
double nanv = std::nan("");
std::cout << (nanv == nanv) << " " << (nanv != nanv) << "\n";
```

```
false true
```

可以用 `x != x` 判断一个值是否为 NaN,但更推荐使用语义明确的 `std::isnan(x)`。

## 十三、C++ 四种类型转换

C++ 用四个具名转换运算符替代 C 风格的 `(type)value`,核心目的是让**转换意图在代码里显式化**,让编译器有机会在编译期检查出错误用法。C 风格转换是一把功能不受限的工具,它实际执行的可能是这四种转换里的任意一种,读代码的人和编译器都无法从记号本身判断意图,出错也难以定位。

- **`static_cast`**:编译期完成,用途最广,不做任何运行时检查。
- **`dynamic_cast`**:运行期完成,专用于含虚函数的继承体系中的安全向下转换,失败时指针转换返回 `nullptr`、引用转换抛 `std::bad_cast`。
- **`const_cast`**:功能单一,只用于增减 `const`/`volatile` 属性。
- **`reinterpret_cast`**:最危险,对一段内存的比特位做重新解释,不做任何检查或转换计算。

`static_cast` 能处理基础类型间的转换、`void*` 转具体指针类型、继承体系中的向上转换(基类指针指向派生类对象,这个方向总是安全的)以及向下转换(这个方向不做运行时检查,如果实际对象类型不匹配是未定义行为)。

`dynamic_cast` 依赖 RTTI(运行时类型信息)在运行期检查对象的实际类型:

```cpp
struct Base { virtual ~Base() = default; };
struct Derived : Base { int x = 42; };
struct Other : Base {};

Base* b1 = new Derived();
Derived* d1 = dynamic_cast<Derived*>(b1);   // 类型匹配,转换成功
Base* b2 = new Other();
Derived* d2 = dynamic_cast<Derived*>(b2);   // 类型不匹配,返回 nullptr
```

```
dynamic_cast success: true x=42
dynamic_cast wrong type (nullptr): true
```

代价是运行时开销以及要求目标类含有虚函数(需要 vtable 才能查询 RTTI)。

`const_cast` 的合法用途是去掉"底层 const"——一个本身不是 const 的对象被一个 const 引用/指针指着,需要把它传给参数类型是非 const 的旧接口时,可以用 `const_cast` 去掉这层修饰后再修改,这种情况下修改是安全的:

```cpp
int v = 10;
const int& cref = v;
int& ref2 = const_cast<int&>(cref);
ref2 = 99;
```

```
v after const_cast modify=99
```

但如果被去 const 的对象本身就是以 `const` 声明的,再通过它修改就是未定义行为——编译器可能已经把这个值当作编译期常量折叠处理,修改不会生效甚至导致更隐蔽的问题。

`reinterpret_cast` 是四种里最底层的,纯粹把一块内存的比特位当作另一种类型来解释,不做任何转换计算,常见于指针与整数的相互转换、不相关指针类型之间的强制转换。绝大多数应用层代码用不到它,只有驱动开发、序列化、底层内存管理这类场景才需要。

一处容易被忽略的区别:`static_cast` 在**多重继承**场景下会调整指针的实际数值——因为基类子对象在派生类对象内的偏移可能不为零,`static_cast` 知道这层布局关系并做相应调整:

```cpp
struct A { int a = 1; };
struct B { int b = 2; };
struct C : A, B { int c = 3; };

C obj;
C* pc = &obj;
B* pb = static_cast<B*>(pc);   // 转换后地址发生了偏移
```

```
pc=0x16f102e30 pb=0x16f102e34   // pb 比 pc 多 4 字节,B 子对象紧接在 A 子对象之后
```

`reinterpret_cast` 不做任何这样的调整,纯粹把原指针的比特位原样当新类型使用,不保证结果指向有效对象——这也是为什么继承体系内的指针转换应该用 `static_cast`/`dynamic_cast` 而非 `reinterpret_cast`。
