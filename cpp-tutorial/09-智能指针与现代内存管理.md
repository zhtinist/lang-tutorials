# 智能指针与现代内存管理

本章覆盖现代 C++ 内存管理的核心知识点:三种智能指针(`unique_ptr`/`shared_ptr`/`weak_ptr`)的用法、适用场景与选型原则、`make_unique`/`make_shared`(含 `shared_ptr` 控制块的内部结构)、循环引用问题、自定义删除器、RAII 思想、智能指针的线程安全边界,以及 `new`/`delete` 与 `malloc`/`free` 的区别。现代 C++ 代码里几乎不应该出现裸 `new`/`delete`。

## 一、`unique_ptr`:独占所有权

`std::unique_ptr` 是最轻量的智能指针,同一时刻只能有一个 `unique_ptr` 拥有资源,**不可拷贝、只能移动**(所有权转移),没有引用计数开销,几乎等价于裸指针的性能。

```cpp
#include <iostream>
#include <memory>

struct Widget {
    int id;
    Widget(int id) : id(id) { std::cout << "构造 Widget " << id << "\n"; }
    ~Widget() { std::cout << "析构 Widget " << id << "\n"; }
};

std::unique_ptr<Widget> makeWidget(int id) {
    return std::make_unique<Widget>(id);  // make_unique(C++14):异常安全,且比 new + 构造 unique_ptr 更简洁
}

int main() {
    auto w1 = makeWidget(1);
    std::cout << "w1->id=" << w1->id << "\n";

    auto w2 = std::move(w1);        // unique_ptr 不可拷贝,只能移动(所有权转移)
    std::cout << "w1 is " << (w1 ? "valid" : "null") << "\n"; // null,所有权已转移
    std::cout << "w2->id=" << w2->id << "\n";

    {
        auto w3 = std::make_unique<Widget>(3);
    } // 离开作用域,w3 自动析构 —— RAII
}
```

```
构造 Widget 1
w1->id=1
w1 is null
w2->id=1
构造 Widget 3
析构 Widget 3
析构 Widget 1
```

**适用场景**:资源只有唯一所有者的绝大多数情况——函数内创建、返回给调用者;类的成员,表示"我独占这个资源";工厂函数的返回值。应作为默认首选的智能指针。

**"独占"是怎么在编译期强制出来的**:`unique_ptr` 内部没有引用计数,本质就是对一个裸指针的 RAII 包装,析构函数里调一次 `delete`(或自定义 deleter)。真正保证"同一时刻只有一份所有权"的不是运行期检查,而是编译期直接堵死拷贝路径——一旦类里声明了移动构造/移动赋值,拷贝构造和拷贝赋值的隐式生成就会被抑制,等价于显式 `= delete`,任何试图拷贝的代码根本无法通过编译:

```cpp
std::unique_ptr<int> a(new int(1));
std::unique_ptr<int> b = a;   // 编译错误
```

```
error: call to implicitly-deleted copy constructor of 'std::unique_ptr<int>'
note: copy constructor is implicitly deleted because 'unique_ptr<int>'
      has a user-declared move constructor
```

这是"把一类运行期才会暴露的所有权错误,转移到编译期直接堵死"的典型设计:不需要任何运行时开销(没有标志位、没有检查),类型系统本身就保证了独占语义。

**选型的决策顺序**:默认用 `unique_ptr`;确认资源需要被多处真正共享时才升级为 `shared_ptr`;出现循环引用或需要非拥有性的观察语义时,把其中一个方向换成 `weak_ptr`。`shared_ptr` 往往是"没理清楚所有权关系"时的妥协方案——如果能把创建者、拥有者、销毁者的责任划分清楚,绝大多数情况只用 `unique_ptr` 就够了。`unique_ptr` 可以单向转换成 `shared_ptr`(`std::shared_ptr<T> sp = std::move(up);`),反过来不行,这是所有权从"独占"放大为"共享"的单向操作,语义上不可逆。

## 二、`shared_ptr` 与 `weak_ptr`:共享所有权

`std::shared_ptr` 通过**引用计数**支持多个所有者共享同一个对象,计数归零时自动释放。`std::weak_ptr` 不参与计数,只"观察"对象是否还存活,用来打破循环引用。

```cpp
#include <iostream>
#include <memory>

struct Node {
    int id;
    Node(int id) : id(id) { std::cout << "构造 Node " << id << "\n"; }
    ~Node() { std::cout << "析构 Node " << id << "\n"; }
};

int main() {
    auto a = std::make_shared<Node>(1);   // make_shared:一次分配同时容纳对象和控制块,比 shared_ptr(new T) 更高效
    std::cout << "use_count(a)=" << a.use_count() << "\n"; // 1

    {
        auto b = a;                          // 拷贝 shared_ptr,引用计数 +1
        std::cout << "use_count(a)=" << a.use_count() << "\n"; // 2
    } // b 离开作用域,引用计数 -1

    std::cout << "use_count(a) after scope=" << a.use_count() << "\n"; // 1

    std::weak_ptr<Node> weakRef = a;   // weak_ptr 不增加引用计数,只是“观察”
    std::cout << "use_count via weak still=" << a.use_count() << "\n"; // 1

    if (auto locked = weakRef.lock()) { // lock() 尝试提升为 shared_ptr,对象存活则成功
        std::cout << "locked id=" << locked->id << "\n";
    }

    a.reset();                           // 显式释放
    std::cout << "expired=" << weakRef.expired() << "\n"; // 1(true),对象已销毁
}
```

```
构造 Node 1
use_count(a)=1
use_count(a)=2
use_count(a) after scope=1
use_count via weak still=1
locked id=1
析构 Node 1
expired=1
```

`make_shared` 比 `std::shared_ptr<T>(new T(...))` 更推荐:后者要分配两次(对象一次、控制块一次),前者一次分配同时放下对象和控制块,更快且异常安全性更好。**适用场景**:多个地方需要共同拥有、生命周期不确定谁最后释放的资源(比如观察者模式里的观察者列表、图/树结构中共享的节点)。

**`shared_ptr` 内部的控制块长什么样**:`shared_ptr` 除了一个指向被管理对象的裸指针,还持有一个指向控制块(control block)的指针。控制块是一块独立分配的内存,至少包含两个原子计数器——`shared_count`(强引用计数):每拷贝一次 `shared_ptr` 原子加一,每析构一次原子减一,减到 0 时被管理对象立即销毁;`weak_count`(弱引用计数):每创建一个指向同一控制块的 `weak_ptr` 原子加一,`weak_ptr` 析构原子减一。**控制块本身要等 `shared_count` 和 `weak_count` 都归零才会被释放**——这意味着只要还有存活的 `weak_ptr`,控制块占用的内存就不会被回收,即便对象本身早已析构。这也是为什么 `weak_ptr::lock()` 之后可能安全地返回一个空 `shared_ptr`,而不是访问到一块已经被完全释放的内存:控制块还在,只是里面记录的"对象已死"这条状态被查询到了。

`make_shared` 把对象和控制块安排在同一块连续内存里一次分配完成,用重载 `operator new` 计数分配次数可以直接验证这个差异:

```cpp
{
    std::shared_ptr<Big> p(new Big());   // 2 次 operator new:对象一次,控制块一次
}
{
    auto p = std::make_shared<Big>();    // 1 次 operator new
}
```

这个优化也带来一个容易被忽视的代价:既然对象和控制块共享同一块内存,只要有任何一个 `weak_ptr` 还存活,这整块内存(包括对象本身占用的部分)就不能释放——`make_shared` 出来的对象,其内存的实际释放时机会被"最后一个 `weak_ptr` 析构"这个更晚的事件拖住;而 `new` + `shared_ptr` 的写法里,对象内存在 `shared_count` 归零时就能立即释放,控制块内存可以晚一点单独释放。对于对象本身占用内存较大、又存在长期持有的 `weak_ptr` 的场景,这个差异值得权衡,不能无条件认为 `make_shared` 总是更优。

## 三、循环引用问题与 `weak_ptr` 解决方案

如果两个对象互相持有对方的 `shared_ptr`,会形成引用环,双方引用计数永远不会归零,导致内存泄漏:

```cpp
#include <iostream>
#include <memory>

struct Node {
    int id;
    std::shared_ptr<Node> next;   // 两边都用 shared_ptr 会形成循环引用
    Node(int id) : id(id) { std::cout << "构造 Node " << id << "\n"; }
    ~Node() { std::cout << "析构 Node " << id << "\n"; }
};

void demoLeak() {
    auto a = std::make_shared<Node>(1);
    auto b = std::make_shared<Node>(2);
    a->next = b;    // a 持有 b 的 shared_ptr
    b->next = a;      // b 也持有 a 的 shared_ptr —— 循环引用!
    std::cout << "use_count(a)=" << a.use_count() << " use_count(b)=" << b.use_count() << "\n"; // 都是 2
} // a, b 局部变量析构,但各自引用计数只减到 1(对方还拿着),对象永远不会被析构 —— 内存泄漏
```

```
构造 Node 1
构造 Node 2
use_count(a)=2 use_count(b)=2
(demoLeak 结束,但没有看到 Node 的析构输出 —— 说明发生了内存泄漏)
```

解决方案是把其中一个方向的引用(通常是"反向指针"、"父指针"这类逻辑上不应该拥有所有权的一边)改成 `weak_ptr`:

```cpp
struct NodeFixed {
    int id;
    std::shared_ptr<NodeFixed> next;
    std::weak_ptr<NodeFixed> prev;    // 用 weak_ptr 打破环,不增加引用计数
    NodeFixed(int id) : id(id) { std::cout << "构造 NodeFixed " << id << "\n"; }
    ~NodeFixed() { std::cout << "析构 NodeFixed " << id << "\n"; }
};

void demoFixed() {
    auto a = std::make_shared<NodeFixed>(1);
    auto b = std::make_shared<NodeFixed>(2);
    a->next = b;
    b->prev = a;      // weak_ptr,不增加 a 的引用计数
    std::cout << "use_count(a)=" << a.use_count() << " use_count(b)=" << b.use_count() << "\n"; // a=1, b=2
} // 离开作用域后正常释放
```

```
构造 NodeFixed 1
构造 NodeFixed 2
use_count(a)=1 use_count(b)=2
析构 NodeFixed 1
析构 NodeFixed 2
(demoFixed 结束,两个 NodeFixed 都被正确析构)
```

判断原则:两个对象的"拥有"关系如果是双向的,至少要有一个方向不算作真正的所有权(只是引用/观察),就应该用 `weak_ptr`。典型场景:双向链表/树的父指针、观察者模式里被观察者持有观察者列表、缓存里指向"拥有者"的反向指针。

上面 `demoFixed` 里两个对象的析构不是同时发生的,而是**级联触发**的:局部变量按声明逆序析构,局部变量 `b`(那个 `shared_ptr` 本身)先析构,但它只是把 `NodeFixed 2` 的强引用计数从 2(局部 `b` 加上 `a->next`)减到 1,对象还被 `a->next` 那份强引用拽着,不会被销毁;接着局部变量 `a` 析构,`NodeFixed 1` 的强引用计数(只有局部 `a` 这一份,因为 `b->prev` 是 `weak_ptr` 不计入)归零,`a` 对象被销毁——销毁过程中它的成员 `next`(那个指向 `b` 的 `shared_ptr`)也随之析构,这才把 `NodeFixed 2` 的计数从 1 减到 0,级联触发 `b` 对象的销毁。所以实际打印顺序是 `NodeFixed 1` 先析构、`NodeFixed 2` 紧随其后被级联析构,而不是按局部变量声明的字面顺序。理解这条级联链,是排查"打破循环引用之后析构顺序为什么和预期不一样"这类问题的关键。

## 四、自定义删除器

智能指针默认用 `delete`/`delete[]` 释放资源,但很多资源(C API 返回的句柄、文件指针、系统对象)需要专门的释放函数,这时可以提供自定义删除器:

```cpp
#include <iostream>
#include <memory>
#include <cstdio>

struct FileCloser {
    void operator()(FILE* f) const {
        if (f) {
            std::cout << "关闭文件\n";
            std::fclose(f);
        }
    }
};

int main() {
    // unique_ptr 的删除器类型是模板参数的一部分
    std::unique_ptr<FILE, FileCloser> file(std::fopen("/tmp/cpp_tutorial_test.txt", "w"));
    if (file) {
        std::fputs("hello\n", file.get());
    }
    // 离开作用域自动调用 FileCloser::operator(),而不是默认的 delete

    // shared_ptr 的删除器是运行期存储的(类型擦除),可以直接传 lambda
    std::shared_ptr<int> arr(new int[5], [](int* p) {
        std::cout << "自定义删除数组\n";
        delete[] p;
    });
}
```

```
自定义删除数组
关闭文件
```

`unique_ptr<T, Deleter>` 的删除器类型是模板参数,不同删除器 = 不同类型;`shared_ptr<T>` 的删除器在构造时传入、类型被擦除,同一个 `shared_ptr<T>` 类型可以持有带不同删除器的对象。

## 五、RAII 思想

**RAII**(Resource Acquisition Is Initialization,资源获取即初始化)是 C++ 资源管理的核心哲学:把资源的生命周期绑定到一个对象的生命周期上——构造函数里获取资源,析构函数里释放资源。由于 C++ 保证局部对象在离开作用域时(无论是正常返回还是异常导致的栈展开)一定会调用析构函数,资源就一定会被释放,不需要 `try/finally` 这类语法来保证清理。

```cpp
#include <iostream>
#include <stdexcept>

class FileGuard {              // RAII:构造时获取资源,析构时自动释放,保证异常安全
public:
    FileGuard(const std::string& name) : name_(name) {
        std::cout << "打开资源: " << name_ << "\n";
    }
    ~FileGuard() {
        std::cout << "释放资源: " << name_ << "\n";
    }
private:
    std::string name_;
};

void mayThrow(bool doThrow) {
    FileGuard guard("data.txt");    // 资源获取即初始化
    if (doThrow) {
        throw std::runtime_error("出错了");
    }
    std::cout << "正常使用资源\n";
} // 无论正常返回还是异常抛出,guard 的析构函数都会被调用,资源不会泄漏

int main() {
    try {
        mayThrow(false);
        mayThrow(true);
    } catch (const std::exception& e) {
        std::cout << "捕获异常: " << e.what() << "\n";
    }
}
```

```
打开资源: data.txt
正常使用资源
释放资源: data.txt
打开资源: data.txt
释放资源: data.txt
捕获异常: 出错了
```

智能指针、`std::lock_guard`、标准库容器本身都是 RAII 的具体实现——这是理解"为什么现代 C++ 几乎不需要手写 `try/finally` 式清理代码"的关键。

## 六、`new`/`delete` 与 `malloc`/`free` 对比

```cpp
#include <iostream>
#include <cstdlib>

struct Point {
    int x, y;
    Point() : x(0), y(0) { std::cout << "Point 构造函数被调用\n"; }
};

int main() {
    // malloc/free:只分配/释放原始内存,不调用构造/析构函数
    Point* p1 = (Point*)std::malloc(sizeof(Point));
    std::cout << "malloc 之后 x=" << p1->x << " (未初始化,值不确定)\n";
    std::free(p1);

    // new/delete:分配内存 + 调用构造函数;delete 调用析构函数 + 释放内存
    Point* p2 = new Point();        // 会打印 "Point 构造函数被调用"
    std::cout << "new 之后 x=" << p2->x << "\n"; // 保证是 0,因为构造函数初始化了
    delete p2;

    // new[]/delete[] 用于数组
    int* arr = new int[5]{1,2,3,4,5};
    std::cout << arr[4] << "\n";
    delete[] arr;
}
```

```
malloc 之后 x=0 (未初始化,值不确定,这里恰好是0也可能是垃圾值)
Point 构造函数被调用
new 之后 x=0
5
```

| | `malloc`/`free` | `new`/`delete` |
|---|---|---|
| 来源 | C 标准库函数 | C++ 运算符(可被类重载) |
| 是否调用构造/析构函数 | 否,只管理原始内存 | 是 |
| 失败时的行为 | 返回 `nullptr` | 抛出 `std::bad_alloc` 异常(可用 `new(std::nothrow)` 改为返回 `nullptr`) |
| 是否知道类型大小 | 需要手动 `sizeof(T)` | 编译器自动计算 |
| 数组 | 需要手动算总字节数 | `new T[n]` / 配对 `delete[]` |
| 能否重载 | 不能 | 可以重载 `operator new`/`operator delete` 自定义分配策略 |

必须记住的配对规则:`new` 配 `delete`,`new[]` 配 `delete[]`,`malloc` 配 `free`——混用(比如 `new` 分配的对象用 `free` 释放,或 `new[]` 分配的数组用 `delete` 而非 `delete[]` 释放)是未定义行为。现代 C++ 代码应优先用智能指针 + 容器,把裸 `new`/`delete`/`malloc`/`free` 限制在极少数手写底层数据结构或与 C API 交互的场景。

## 七、智能指针的线程安全性

"`shared_ptr` 是不是线程安全的"不能用一个"是"或"否"打发,必须拆成三个层面分别回答:

**第一层:控制块(引用计数)—— 线程安全**。标准保证控制块内部的引用计数用原子操作实现,多个线程各自持有 `shared_ptr` 的副本、并发地拷贝或析构,引用计数的加减不会出现丢失更新或数据竞争。

**第二层:`shared_ptr` 实例本身(这个变量的读写)—— 不安全**。多个线程同时**只读**访问同一个 `shared_ptr` 变量是安全的,标准明确规定这不构成数据竞争。但只要有一个线程在**写**这个变量(`reset`、赋值、移动),就必须额外加锁——写操作需要同时修改内部的裸指针和调整引用计数,这不是一个原子步骤,并发写、或者一读一写,都需要 `mutex` 保护。

**第三层:被管理的对象本身 —— 不安全**。智能指针只负责生命周期,完全不管对象内部数据的并发访问。多个线程通过各自的 `shared_ptr` 副本读写同一个底层对象的成员,仍然需要 `mutex` 或其他同步手段保护,和智能指针没有关系。

`unique_ptr` 因为是独占语义,不存在"共享"这个场景;所有权转移(移动)本身不是线程安全操作,必须保证同一时刻只有一个线程在操作同一个 `unique_ptr`。

多线程并发拷贝同一个 `shared_ptr` 是安全用法的典型例子——每个线程按值捕获一份副本,强引用计数原子加一,线程内部操作的是自己的独立副本,互不干扰:

```cpp
auto sp = std::make_shared<int>(0);
std::vector<std::thread> threads;
for (int i = 0; i < 8; ++i) {
    threads.emplace_back([sp]() mutable {
        for (int j = 0; j < 10000; ++j) {
            std::shared_ptr<int> local = sp;   // 拷贝:原子 +1
        }                                        // 局部变量析构:原子 -1
    });
}
for (auto& t : threads) t.join();
printf("%ld\n", sp.use_count());   // 1,8 * 10000 次原子增减没有丢计数
```

而修改同一个 `shared_ptr` **变量**(不是它管理的对象)则必须显式加锁:

```cpp
std::shared_ptr<int> guarded = std::make_shared<int>(1);
std::mutex m;
std::vector<std::thread> writers;
for (int i = 0; i < 4; ++i) {
    writers.emplace_back([&guarded, &m, i]() {
        std::lock_guard<std::mutex> lk(m);      // 写操作必须加锁
        guarded = std::make_shared<int>(i);
    });
}
for (auto& t : writers) t.join();
```

原子性还有一层细节:引用计数增加时用 `memory_order_relaxed` 就够,因为增加计数不需要和其他数据建立同步关系;但减少计数到需要判断是否归零时要用更强的内存序(如 `memory_order_acq_rel`)——一旦计数减到 0 触发对象销毁,必须保证之前所有线程对该对象的写入,在执行销毁的这个线程上都已经可见,否则析构函数可能读到还没写完的数据。

C++20 定义了 `std::atomic<std::shared_ptr<T>>` 特化,用来整体原子地替换一个共享的 `shared_ptr` 变量而不需要额外的 `mutex`,但这是一个"标准规定、库实现程度不一"的特性——在确认目标标准库版本已经支持之前,用 `mutex` 保护跨线程共享的 `shared_ptr` 变量的读写仍然是更可靠、可移植性更好的做法。
