# 面向对象与类型系统

这是全书里 OOP 概念最集中的一章,涉及类、继承、多态、泛型、record、sealed、enum、lambda 十来个话题:对象在堆上到底摆了什么、虚方法怎么分派、泛型运行时还剩下什么。

## 一、类的基本形态:定义、继承、泛型、lambda

### 面向过程与面向对象:范式取舍

C 是**面向过程**语言:程序被组织成一系列函数(过程),数据(`struct`)和操作数据的函数是分离的两套东西——一个 `struct Point` 只是数据,`distance(Point a, Point b)` 单独定义在别处,`struct` 本身不知道有哪些函数在操作它。Java 是**面向对象**:把数据和操作数据的方法捆在同一个类型定义里,`Point` 自己"知道"能对自己做什么。

**为什么要把数据和函数捆在一起,而不是像 C 那样分开**:面向过程的问题在于,一个 `struct` 一旦定义,操作它的函数可以在代码库任何地方冒出来,新增一个函数不需要经过 `struct` 定义者同意、也不需要遵守任何契约——数据"能做什么"分散在整个程序里,没有单一位置能回答"这个类型到底支持哪些操作"。面向对象把方法和数据放进同一个类体,首先给了"这个类型能做什么"一个唯一、可枚举的位置(类定义本身);其次,方法访问字段不必再作为显式参数传入(`this` 隐式绑定,见下文),调用点写起来更接近自然语言("`point.distance(other)`" 而非 "`distance(point, other)`");最后也是最关键的一点——只有把数据和方法绑在一起,才能谈**封装**(数据能不能被外部直接改,由这个类自己决定)、**继承**(子类型复用父类型的数据+方法)、**多态**(同一方法调用,不同类型给出不同实现)这三件事,它们都以"方法从属于类型"为前提,面向过程的世界里没有"从属"关系可言。

代价也很直接:面向对象为每个对象背上了额外的运行时结构(对象头,见下文)和一层间接寻址(方法查找),不像面向过程那样"数据就是数据、函数就是函数",没有任何隐藏的分派机制。C 选择的是"你要什么行为,自己显式传数据调函数",Java 选择的是"类型自带行为,调用时由运行时决定具体走哪段代码"——这也是本章接下来要拆解的**动态分派(多态)**机制存在的根本原因。

Java 并不是纯粹的面向对象语言:8 种基本类型(`int`/`boolean`/...)不是对象,没有方法、不能被继承([「变量与内存模型」](03-变量与内存模型.md)讨论过这是性能与一致性之间的取舍),这点和 Smalltalk"一切皆对象"不同,但不妨碍 Java 的类型系统整体上以对象为中心组织。

Java 的类和 C 的 `struct` 最大的不同:类里可以直接放函数(叫"方法"),`new` 出来的对象永远在堆上,变量里存的是指向它的引用(细节见[「变量与内存模型」](03-变量与内存模型.md))。

```java
class Point {
    int x, y;                          // 字段(成员变量)
    Point(int x, int y) {              // 构造器:和类同名,没有返回类型
        this.x = x;                    // this 指当前对象,区分字段和参数
        this.y = y;
    }
    int sum() {                        // 方法
        return x + y;
    }
}

public class PointBasics {
    public static void main(String[] args) {
        Point p = new Point(3, 4);     // new 出一个实例
        System.out.println(p.sum());  // 调用方法:7
        System.out.println(p.x);      // 直接访问字段:3
    }
}
```

```
7
3
```

`class Point { ... }` 只是"图纸";`new Point(3, 4)` 才真正在堆上造出一个对象,`p` 里存的是这个对象的引用。同一张图纸能 `new` 出无数个对象,彼此字段互不影响。

### 最简单的继承与接口

`extends` 表示"继承一个类"(单继承,只能写一个),`implements` 表示"实现一个或多个接口":

```java
interface Greeter {
    String greet();                    // 接口方法:只有签名,没有实现
}

class Animal {
    String name = "animal";
    String speak() {
        return name + " makes a sound";
    }
}

class Dog extends Animal implements Greeter {
    Dog() { name = "dog"; }
    @Override public String greet() { return "woof from " + name; }
}

public class InheritBasics {
    public static void main(String[] args) {
        Dog d = new Dog();
        System.out.println(d.speak());   // 继承来的方法:dog makes a sound
        System.out.println(d.greet());   // 实现接口的方法:woof from dog
    }
}
```

```
dog makes a sound
woof from dog
```

`Dog` 既拿到了 `Animal` 的字段和方法(继承),又必须把 `Greeter` 承诺的 `greet()` 写出来(实现接口)——`@Override` 是给编译器和读者的标记,表示"这是在覆盖父类/接口的方法",拼错方法名编译器会立刻报错。

### 最简单的泛型:`Box<T>`

类名后面的 `<T>` 表示"这个类可以装任意类型,具体装什么由使用者决定":

```java
class Box<T> {
    T value;
    Box(T value) { this.value = value; }
    T get() { return value; }
}

public class BoxBasics {
    public static void main(String[] args) {
        Box<String> b = new Box<>("hello");
        System.out.println(b.get());       // hello

        Box<Integer> n = new Box<>(42);
        System.out.println(n.get());       // 42
    }
}
```

```
hello
42
```

`Box<String>` 和 `Box<Integer>` 是同一份代码,`T` 在使用处被替换成具体类型;编译器负责检查类型对不对,你不需要为每种类型各写一个 `Box`。

### 最简单的 lambda

`Runnable` 是一个只有一个方法 `run()` 的接口(这类接口叫"函数式接口");lambda `() -> ...` 就是给这个方法直接写一段实现,不用专门定义一个类:

```java
public class LambdaBasics {
    public static void main(String[] args) {
        Runnable r = () -> System.out.println("running!");
        r.run();                          // 像调用普通方法一样调用
    }
}
```

```
running!
```

**Java 对象一律在堆上分配**,对象开头有一个隐藏的"对象头",其中一部分指向它所属的类描述结构(HotSpot 里叫 `klass`)——这个指针的作用和 C++ 里的 vptr 很像:决定了调用虚方法时该跳到哪段代码。变量本身不存对象,只存这个引用(值/引用语义的细节见[「变量与内存模型」](03-变量与内存模型.md);对象头的具体字节布局见[「数据类型」](04-数据类型.md))。

带着这个模型,下面逐一拆开:初始化顺序、封装、继承、多态(vtable)、抽象类 vs 接口、`Object`、泛型擦除、record、sealed、enum、内部类与 lambda。

## 二、初始化顺序

构造器可以用 `this(...)` 委托本类的另一个构造器,也可以用 `super(...)` 显式调用父类构造器(不写的话编译器会自动插入无参 `super()`):

```java
class Person {
    String name;
    int age;
    Person(String name) { this(name, 0); }          // this(...):委托本类另一个构造器
    Person(String name, int age) { this.name = name; this.age = age; }
}
class Student extends Person {
    String school;
    Student(String name, int age, String school) {
        super(name, age);                            // super(...):调用父类构造器
        this.school = school;
    }
}
public class ConstructorBasics {
    public static void main(String[] args) {
        Student s = new Student("Ann", 20, "MIT");
        System.out.println(s.name + " " + s.age + " " + s.school);  // Ann 20 MIT

        Person p = new Person("Bob");                // 走 this(...) 委托,age 默认 0
        System.out.println(p.name + " " + p.age);     // Bob 0
    }
}
```

```
Ann 20 MIT
Bob 0
```

Java 类的所有实例方法默认是"虚"的(除 `private`/`static`/`final`)。`new` 一个对象时,JVM 按固定顺序执行:

```
1. 类首次使用时:静态字段默认零值 → 静态初始化块 + 静态字段赋值(按源码顺序,仅一次)
2. 实例创建:分配堆内存,所有实例字段置零值
3. 父类实例初始化(递归:父类字段 → 父类实例块 → 父类构造器体)
4. 本类实例字段默认值 → 实例初始化块 + 字段赋值(按源码顺序)
5. 本类构造器体
```

```java
class Base {
    String x = init("Base.x");        // ③
    Base() { System.out.println("Base()"); }
    static String s = init("Base.s");  // ① 类加载时
    static String init(String m){ System.out.println(m); return null; }
}
class Derived extends Base {
    String y = Base.init("Derived.y"); // ④
    Derived() { super(); System.out.println("Derived()"); } // super() 隐式在最前
}
// new Derived() 输出:Base.s(首次) → Base.x → Base() → Derived.y → Derived()
```

```
Base.s
Base.x
Base()
Derived.y
Derived()
```

对比 C++:成员按**声明顺序**在初始化列表构造,基类先于派生类——Java 顺序类似,但没有初始化列表语法,且静态初始化是懒惰的(类首次主动使用时才触发,由类加载器保证线程安全地执行一次)。

构造器第一行必须是 `this(...)` 或 `super(...)`;不写则编译器插入无参 `super()`。**构造期间调用虚方法很危险**:父类构造器里调被子类重写的方法,此时子类字段尚未初始化(还是零值),会读到未初始化状态。C++ 在构造期虚调用会静态绑定到当前类版本;**Java 则动态绑定到子类版本**,更危险。

亲眼看这个坑:父类构造器调用虚方法 `size()`,分派到子类版本,但此时子类字段 `value` 还是零值:

```java
public class CtorVirtual {
    static class Base {
        Base() { System.out.println("Base ctor sees size = " + size()); } // 虚调用
        int size() { return 0; }
    }
    static class Derived extends Base {
        int value = 42;                 // 在 super() 之后才初始化
        @Override int size() { return value; }
    }
    public static void main(String[] args) {
        Derived d = new Derived();
        System.out.println("after ctor  size = " + d.size());
    }
}
```

```
Base ctor sees size = 0    <- 动态分派到 Derived.size(),但 value 尚未赋值(零值)
after ctor  size = 42      <- 构造完成后才是 42
```

## 三、封装

访问修饰符控制"谁能访问这个字段/方法",最常见的用法是把字段设为 `private`,只暴露 getter/setter:

```java
class Account {
    private double balance;   // 外部不可直接访问

    Account(double initial) { balance = initial; }

    public double getBalance() {     // 只能通过方法读取
        return balance;
    }
    public void deposit(double amount) {
        if (amount > 0) balance += amount;  // 借机会做校验
    }
}

public class EncapBasics {
    public static void main(String[] args) {
        Account a = new Account(100);
        a.deposit(50);
        System.out.println(a.getBalance());  // 150.0
        // a.balance = -999;    // 编译错:balance 是 private,外部访问不到
    }
}
```

```
150.0
```

访问修饰符从窄到宽:`private` < 包级(默认,无关键字) < `protected` < `public`。注意 Java 的 `protected` 还允许**同包**访问,语义比 C++ 宽。无 `friend`。模块系统(JPMS)可在更粗粒度上封装整个包。

## 四、继承:单继承 + 多接口

一个类只能 `extends` 一个父类,但可以 `implements` 任意多个接口,用逗号分隔:

```java
abstract class AbstractBase {
    void base() { System.out.println("base"); }
}
class Service extends AbstractBase implements Runnable, AutoCloseable {
    @Override public void run() { System.out.println("running"); }
    @Override public void close() { System.out.println("closed"); }
}
public class ServiceCheck {
    public static void main(String[] args) {
        Service s = new Service();
        s.base();
        s.run();
        s.close();
    }
}
```

```
base
running
closed
```

Java **类只能单继承**(避免 C++ 菱形继承的复杂性与虚继承),但可实现任意多个接口。

接口曾经只能有抽象方法,JDK 8 起可有 **default 方法**(带实现)和 **static 方法**,JDK 9 起可有 `private` 方法。这带来"多继承实现"的能力,但字段仍只有常量(`public static final`),所以没有状态菱形问题。若两个接口有同签名 default 方法,子类必须显式覆盖解决冲突,否则编译错:

```java
interface A2 { default String who() { return "A"; } }
interface B2 { default String who() { return "B"; } }
class C2 implements A2, B2 { }   // 编译错
```

```
error: types A2 and B2 are incompatible
  class C2 inherits unrelated defaults for who() from types A2 and B2
```

用 `接口名.super.方法名()` 显式指明走哪个接口的默认实现来解决冲突:

```java
interface A { default String who() { return "A"; } }
interface B { default String who() { return "B"; } }
class C implements A, B {
    @Override public String who() { return A.super.who() + B.super.who(); } // 显式解决冲突
}
```

```
AB
```

#### 为什么"组合优于继承"

继承是**白盒复用**:子类拿到的不仅是父类的公开接口,还直接暴露在父类的实现细节之上——子类的行为随父类内部实现的变动而变动,哪怕父类只改了一个从未在契约里承诺过的内部细节,也可能让子类的重写方法悄悄错位(经典的"脆弱基类问题",fragile base class problem)。加上 Java 只能单继承,一旦某个类型需要复用两个互不相关的能力,继承体系表达不出来,只能退而求接口默认方法(见上文)。子类也从不继承父类的构造器,也无法直接访问父类的 `private` 成员(只能通过父类暴露的 `public`/`protected` 方法间接访问)——这两点进一步说明继承传递的是"类型层级",而不是"实现细节的自由访问权"。

组合——让一个类把另一个类的实例作为字段持有,通过调用它的公开方法复用功能——是**黑盒复用**:被组合对象的内部实现完全不可见,唯一的耦合面是它的公开接口。这带来三点继承给不了的好处:一是耦合更弱,内部实现随便改,只要接口不变外部毫无感知;二是更灵活,组合关系能在运行时动态替换(把字段指向另一个实现),而继承关系在编译期就写死;三是更容易单元测试,被组合的依赖可以用接口 + mock 替换,不必像继承那样拉出整条父类链。

```java
// 继承版本:强耦合,Logger 的实现细节(格式、目标)焊死在 Service 的类型层级里
class Logger { void log(String m) { System.out.println("[LOG] " + m); } }
class ServiceByInherit extends Logger {
    void doWork() { log("working"); }
}

// 组合版本:Service 只依赖 Logger 暴露的方法,内部实现可随时替换
class ServiceByCompose {
    private final Logger logger;                 // 持有,而非继承
    ServiceByCompose(Logger logger) { this.logger = logger; }
    void doWork() { logger.log("working"); }
}
```

```
[LOG] working
[LOG] working
```

这不是说继承没有用武之地——表达严格的"is-a"层级关系(`Circle is-a Shape`)、需要多态统一调度时,继承(配合接口)仍是最直接的工具;"组合优于继承"是一条经验法则,提醒你在两者都能达到复用目的时优先选耦合更弱的那个,而不是继承的替代品。

## 五、多态与虚方法表(vtable)

子类重写(`@Override`)父类的方法后,即使用父类类型的引用去调用,实际执行的也是子类版本——这就是"动态分派":

```java
class Bird {
    String sound() { return "..."; }
}
class Duck extends Bird {
    @Override String sound() { return "quack"; }
}

public class PolyBasics {
    public static void main(String[] args) {
        Bird b = new Duck();          // 父类型引用指向子类对象
        System.out.println(b.sound()); // quack —— 运行时按实际对象类型分派,而非引用声明类型
    }
}
```

```
quack
```

Java 实例方法默认动态分派。HotSpot 的实现和 C++ 的 vtable 高度相似:

```
每个类在方法区(Metaspace)有一个 klass 结构,内含 vtable:
  Klass(Animal)          Klass(Dog extends Animal)
  vtable:                vtable:
   [0] Object.方法...      [0] Object.方法...(继承)
   [k] Animal::speak ─┐    [k] Dog::speak    ← 覆盖,槽位相同
                      │
对象头的 klass ptr ───┘ 指向自己的 Klass
调用 a.speak():
   1. 取 a 的对象头 klass ptr
   2. 到 vtable 固定槽位取方法地址
   3. 调用   —— 与 C++ 几乎一致
```

差异:

- **接口方法**不能用固定 vtable 槽位(一个类实现多接口,槽位无法统一),用单独的 **itable**(interface method table)+ 运行时查找,比 vtable 稍慢。JIT 用**内联缓存**(inline cache)优化:记住上次调用的实际类型,单态时几乎零开销。
- Java 的 `final`/`private`/`static` 方法是**静态绑定**(invokespecial/invokestatic),无虚分派。
- JIT 还会做**去虚化**(devirtualization):若能证明某调用点只有一个实现(CHA,类层级分析),直接内联,STW 时若加载了新子类再退优化。C++ 需要手动 `final` 或链接期优化才有类似效果。

字节码层面四条调用指令:`invokevirtual`(虚)、`invokeinterface`(接口)、`invokespecial`(构造器/私有/super)、`invokestatic`(静态),外加 `invokedynamic`(lambda、字符串拼接)。详见[「方法与调用栈」](06-函数与调用栈.md)。

#### 字段不参与多态:只有方法是动态分派的

上面的动态分派只对**方法**成立,**字段访问是静态绑定**——按引用的**声明类型**决定,和对象的实际类型无关。这是最容易被面试问倒的一点,因为直觉上字段和方法"看起来都属于对象":

```java
class Base { int x = 1; int getX() { return x; } }
class Derived extends Base {
    int x = 2;                     // 与父类同名字段,不是覆盖,而是"遮蔽"(hiding),各自独立存储
    @Override int getX() { return x; }
}
public class FieldNoPoly {
    public static void main(String[] args) {
        Derived d = new Derived();
        Base b = d;                              // 同一个对象,两个不同声明类型的引用
        System.out.println(b.x + " " + d.x);     // 1 2  —— 字段按引用声明类型取
        System.out.println(b.getX() + " " + d.getX()); // 2 2 —— 方法按对象实际类型走 vtable
    }
}
```

```
1 2
2 2
```

`b.x` 和 `d.x` 明明指向同一个对象,取到的却是两个不同的值——因为子类同名字段不是"覆盖"父类字段,而是在对象内存里独立开辟一份存储、**遮蔽(hiding)**了父类字段的名字,访问哪一份完全由**引用的声明类型**在编译期静态决定,不查 vtable。这与方法形成鲜明对比:`getX()` 不管用 `b` 还是 `d` 调用,永远走 `Derived::getX`。记忆口诀是**"字段编译看左边,方法运行看右边"**(对应"编译看左,运行看右"这句更常见的说法,专指方法):`b.x` 里的 `b` 声明类型是 `Base`,决定了拿 `Base` 的 `x`;`b.getX()` 则要在运行期查 `b` 实际指向的对象(`Derived`)的 vtable。

**为什么字段不能也做成动态分派**:方法调用可以做成一层间接(vtable 查表再跳转),因为方法本身只是一段代码地址,查表的开销可以被 JIT 内联缓存等手段摊平;字段则不同——字段访问要落到"对象内存里第几个偏移量",而这个偏移量在编译期就必须固定下来,才能生成一条简单的"读某个固定偏移量"的字节码指令(`getfield`),不必在每次读字段时先查一次类型再决定去哪个偏移量取值。如果字段也要走动态分派,意味着每次读一个字段都要先做一次虚方法调用那样的间接查找,对"读一个整数字段"这种最高频的操作而言开销完全不成比例。所以 Java 选择让字段在编译期把偏移量焊死(按声明类型决定去哪个类的布局里找),把"运行期决定用哪份实现"这个特权只留给方法。

这也解释了向上转型(upcast,子类引用赋给父类引用,如 `Base b = d;`,自动完成、无需强转)和向下转型(downcast,`(Derived) b`,需要显式强转并可能抛 `ClassCastException`)为什么只影响"编译器看得到哪些成员",不影响对象本身:转型只是换了一个"看待同一个对象的声明类型",对象在堆上的布局和它的实际类型从未改变;`instanceof`(见[「控制流」](05-控制流.md)的模式匹配 switch)则是运行期查询这个"实际类型"的手段,常在向下转型前用来判断转型是否安全。

## 六、抽象类 vs 接口

`abstract class` 可以混合"抽象方法"(没有方法体,子类必须实现)和"具体方法"(有实现,直接继承用);接口在 Java 8 之前只能有抽象方法:

```java
abstract class Shape {
    abstract double area();          // 抽象方法,没有方法体
    void describe() {                // 具体方法,可以有实现
        System.out.println("area = " + area());
    }
}
class Circle extends Shape {
    double r;
    Circle(double r) { this.r = r; }
    @Override double area() { return Math.PI * r * r; }
}

interface Movable {
    void move();                     // 抽象方法
}
class Car implements Movable {
    @Override public void move() { System.out.println("car moves"); }
}

public class AbstractVsInterfaceBasics {
    public static void main(String[] args) {
        new Circle(2).describe();
        new Car().move();
    }
}
```

```
area = 12.566370614359172
car moves
```

| 维度 | 抽象类 | 接口 |
|------|--------|------|
| 实例字段 | 可有(带状态) | 只有 `public static final` 常量 |
| 构造器 | 有 | 无 |
| 继承 | 单继承 | 多实现 |
| 方法 | 抽象 + 具体 | 抽象 + default + static + private |
| 语义 | "是什么"(is-a) | "能做什么"(can-do,能力) |

经验:表达类型层级共享状态用抽象类;表达能力/契约、需要多重组合用接口。JDK 里 `AbstractList` 是抽象类骨架,`List` 是接口。

#### 为什么抽象方法不能是 `private`/`static`/`final`

```java
abstract class Bad {
    private abstract void f();   // 编译错:非法的修饰符组合
}
```

```
error: illegal combination of modifiers: abstract and private
```

这不是任意的语法限制,三个修饰符都从各自的语义上直接和"抽象方法必须被子类重写"矛盾:`private` 方法对子类不可见,子类根本"看不到"这个方法,更谈不上重写;`static` 方法靠**静态绑定**(`invokestatic`),不参与本章反复强调的动态分派,而抽象方法存在的唯一目的就是"留一个由动态分派决定具体实现的槽位";`final` 方法则是显式禁止被重写,和"抽象方法必须被重写"直接对立。三者被编译器一律拒绝,是"抽象"这个概念在类型系统里落地时必须遵守的一致性——如果放行,`abstract` 这个关键字的承诺(留给子类实现)就会被同一个方法声明上的另一个修饰符同时否定掉。

#### 接口的多继承:`extends` 可以带多个父接口

类的 `extends` 只能带一个父类,但**接口的 `extends` 可以带多个父接口**——这是接口和类唯一不对称的地方,因为接口没有字段状态,不存在类多继承时的菱形数据冲突:

```java
interface Flyable { void fly(); }
interface Swimmable { void swim(); }
interface Amphibious extends Flyable, Swimmable { }   // 接口可以多继承接口

class Duck2 implements Amphibious {
    @Override public void fly() { System.out.println("flying"); }
    @Override public void swim() { System.out.println("swimming"); }
}
```

```
flying
swimming
```

## 七、`Object` 的方法与 equals/hashCode 契约

所有类隐式继承 `Object`。最常重写的三个方法是 `equals`(判断"值相等")、`hashCode`(配合 `HashMap`/`HashSet`)、`toString`(打印时看到的文字):

```java
import java.util.Objects;

class Point2 {
    int x, y;
    Point2(int x, int y) { this.x = x; this.y = y; }

    @Override public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof Point2 p)) return false;
        return x == p.x && y == p.y;
    }
    @Override public int hashCode() { return Objects.hash(x, y); }
    @Override public String toString() { return "Point2(" + x + ", " + y + ")"; }
}

public class EqualsBasics {
    public static void main(String[] args) {
        Point2 a = new Point2(1, 2);
        Point2 b = new Point2(1, 2);
        System.out.println(a.equals(b));   // true
        System.out.println(a == b);        // false —— 不同对象
        System.out.println(a);             // Point2(1, 2) —— toString 被调用
    }
}
```

```
true
false
Point2(1, 2)
```

`==` 永远比较的是引用(是不是同一个对象);要比较"内容是否相等",必须重写 `equals`。`System.out.println(a)` 会自动调用 `a.toString()`。

`Object` 类比但强于 C++——C++ 没有统一根。关键方法:`equals`、`hashCode`、`toString`、`getClass`、`clone`、`wait`/`notify`(见[并发](10-并发模型.md))、`finalize`(已弃用,见[GC](09-错误处理与资源管理.md))。

#### equals/hashCode 契约(违反会导致集合行为错乱)

1. `a.equals(b)` 为 true ⟹ `a.hashCode() == b.hashCode()`(**相等必同哈希**)。
2. 反之不要求(哈希相同不必相等,即允许冲突)。
3. `equals` 需自反、对称、传递、一致、非 null。

只重写 `equals` 不重写 `hashCode`,放进 `HashMap`/`HashSet` 就会因散到错误的桶而丢失(见[「集合框架」](07-复合数据结构.md))。默认 `Object.equals` 是引用相等(`==`),默认 `hashCode` 是**标识哈希(identity hash)**——常被误说成"由对象地址派生",但那站不住脚(GC 移动对象后哈希就会变);现代 HotSpot(JDK8+ 默认)用一个**线程本地的 xorshift 伪随机数**生成,首次调用时惰性算出、存进对象头 mark word,此后不变(见[「数据类型」](04-数据类型.md))。

```java
final class Point {
    final int x, y;
    Point(int x, int y){ this.x=x; this.y=y; }
    @Override public boolean equals(Object o){
        if (this == o) return true;
        if (!(o instanceof Point p)) return false; // 模式匹配 instanceof
        return x == p.x && y == p.y;
    }
    @Override public int hashCode(){ return Objects.hash(x, y); }
}
```

用 `record` 可自动生成这些(下文)。

违反契约的代价可直接看到:只重写 `equals`、不重写 `hashCode`,相等对象散到不同桶,`HashSet` 里就找不回来:

```java
import java.util.*;
public class HashContract {
    // 重写了 equals,但没重写 hashCode —— 违反契约
    static class Bad {
        final int id; Bad(int id){ this.id = id; }
        @Override public boolean equals(Object o){ return o instanceof Bad b && b.id == id; }
    }
    // 两个都重写 —— 正确
    static class Good {
        final int id; Good(int id){ this.id = id; }
        @Override public boolean equals(Object o){ return o instanceof Good g && g.id == id; }
        @Override public int hashCode(){ return Integer.hashCode(id); }
    }
    public static void main(String[] args) {
        System.out.println("Bad  equal? " + new Bad(1).equals(new Bad(1)));
        Set<Bad> bad = new HashSet<>(); bad.add(new Bad(1));
        System.out.println("Bad  contains equal obj? " + bad.contains(new Bad(1)));

        Set<Good> good = new HashSet<>(); good.add(new Good(1));
        System.out.println("Good contains equal obj? " + good.contains(new Good(1)));
    }
}
```

```
Bad  equal? true                 <- 两个 Bad(1) 相等
Bad  contains equal obj? false   <- 但默认 hashCode 不同,散到别的桶,找不到!
Good contains equal obj? true    <- 正确重写后才能找回
```

#### `equals` 里用 `getClass()` 还是 `instanceof`:对称性的取舍

上面的例子都用 `instanceof` 判断类型,但还有一种常见写法是 `obj.getClass() != this.getClass()`。两者不是随便选一个的问题,而是对"子类算不算相等"这件事的不同立场,选错会违反 `equals` 契约里的**对称性**(`a.equals(b)` 与 `b.equals(a)` 结果必须一致):

```java
class Point { int x;
    Point(int x){ this.x = x; }
    @Override public boolean equals(Object o){
        if (!(o instanceof Point p)) return false;   // 用 instanceof:子类也能相等
        return x == p.x;
    }
}
class ColorPoint extends Point {
    String color;
    ColorPoint(int x, String color){ super(x); this.color = color; }
    // 未重写 equals,直接继承 Point 的:只比 x,不比 color
}
public class EqualsSymmetry {
    public static void main(String[] args) {
        Point p = new Point(1);
        ColorPoint cp = new ColorPoint(1, "red");
        System.out.println(p.equals(cp));   // true —— instanceof 认为 ColorPoint 是一种 Point
        System.out.println(cp.equals(p));   // true —— 对称,两边一致
    }
}
```

```
true
true
```

用 `instanceof` 换成 `getClass() != o.getClass()` 会让"父类对象与子类对象比较"恒为 `false`(因为 `Class` 对象不同),对称性倒是保住了,但代价是**父类的 `equals` 再也无法认为任何子类实例与自己相等**——如果业务语义就是"只要坐标一样就算相等,颜色只是附加信息",`getClass()` 版本反而比 `instanceof` 版本更不合直觉。真正危险的是**混用**:父类用 `instanceof`、子类又重写 `equals` 加上额外字段比较(比如让 `ColorPoint` 要求 `x` 和 `color` 都相等),就会出现 `p.equals(cp)` 为 `true`(父类看不到 `color`,只比 `x`)而 `cp.equals(p)` 为 `false`(子类要求 `color` 也相等,`p` 没有 `color`)——同一对 `equals` 调用交换顺序结果不同,直接违反契约。**经验法则**:要么把参与 `equals` 比较的类设计成 `final`(杜绝子类化的可能,`record` 天然如此),要么在继承体系里统一使用 `getClass()` 判等(放弃"父类子类可以相等"这个语义,但保住对称性)。

## 八、泛型与类型擦除(与 C++ 模板的根本分野)

声明泛型类用 `class 类名<T>`(上文的 `Box<T>` 已经见过);泛型方法把 `<T>` 写在返回类型前面,类型参数由调用时传入的实参自动推断:

```java
public class GenericMethodBasics {
    static <T> T firstOf(T[] arr) {     // 泛型方法:类型参数写在返回类型前
        return arr[0];
    }
    public static void main(String[] args) {
        String[] names = {"Ann", "Bob"};
        System.out.println(firstOf(names));   // Ann

        Integer[] nums = {10, 20};
        System.out.println(firstOf(nums));    // 10
    }
}
```

```
Ann
10
```

这是 Java 类型系统最"反直觉"的部分,也是与 C++ 差异最大之处,下面展开讲运行时到底发生了什么。

#### 擦除:运行时没有泛型信息

Java 泛型是**编译期**特性。编译后类型参数被"擦除":`List<String>` 和 `List<Integer>` 运行时都是同一个 `List` 类(裸类型 `List`,`T` 擦除为 `Object`,有界则擦到上界)。编译器在需要处插入**强制转换**并做静态类型检查。

```java
List<String> ls = new ArrayList<>();
ls.add("hi");
String s = ls.get(0);   // 编译器插入 (String) 转换
// 运行时:ls.getClass() == ArrayList.class,与 List<Integer> 完全相同
```

对比 C++:模板是**单态化**(monomorphization),`vector<int>` 与 `vector<string>` 编译出两份独立代码,运行时有各自的类型,zero-cost 抽象但代码膨胀。Java 只有一份代码,无膨胀,但运行时丢失了类型,由此产生一系列限制。

**为什么 Java 选择擦除,而不是像 C++ 那样为每个具体类型单态化生成独立代码**:根本原因是**向后兼容一份已经存在多年的字节码生态**。泛型是 JDK 5(2004 年)才加入的特性,而在此之前 `Collection`、`List` 这些接口已经以裸类型的形式被使用了近十年,大量已编译好、正在生产环境跑的 `.class` 文件(以及第三方发布的 jar 包)里全是不带类型参数的 `List`。如果 Java 像 C++ 模板那样对每个具体类型生成一份独立的字节码,`List<String>` 和裸 `List` 就会变成运行时不兼容的两个类,新编译的泛型代码将无法直接传给旧的、按裸类型编写的方法,也无法被旧代码调用——这会立刻打断所有已发布库的二进制兼容性,新旧代码不能混用。擦除的方案反其道而行:`List<String>` 编译后就是普通的 `List`,和 JDK 5 之前编译的 `List` 字节码完全一致,只是编译器在编译期插入了额外的类型检查和强制转换。这样一份泛型化的新代码,可以无缝调用为裸类型编写的旧代码,反之亦然——这被称为"迁移兼容性(migration compatibility)",是 Java 团队在设计泛型时的明确目标,牺牲的是运行时类型信息(导致不能 `new T[]`、`instanceof` 不能带类型参数等一系列限制),换来的是十年积累的字节码资产不必重新编译就能继续工作。这是一个历史包袱驱动、而非纯技术最优的设计——如果 Java 在诞生之初就带泛型,大概率不会选择这条路。

运行时两种泛型实例是**同一个** `Class` 对象;裸类型更能暴露"运行时不再有类型检查":

```java
import java.util.*;
public class Erasure {
    public static void main(String[] args) {
        List<String>  ls = new ArrayList<>();
        List<Integer> li = new ArrayList<>();
        System.out.println(ls.getClass());                 // 都擦除成 ArrayList
        System.out.println(li.getClass());
        System.out.println("same Class object? " + (ls.getClass() == li.getClass()));
        // 运行时不保留类型参数,下面这行能存进去,直到取出来用才会暴露:
        List raw = li;                 // 裸类型
        raw.add("oops");               // 此处不抛 ClassCastException(仅编译告警)
        System.out.println("li now holds: " + li.get(0));  // 尽管声明是 List<Integer>
    }
}
```

```
class java.util.ArrayList
class java.util.ArrayList
same Class object? true
li now holds: oops
```

编译期在 `raw.add("oops")` 处会有一条 unchecked 警告,但不会阻止编译或运行时报错。

#### 擦除带来的四大限制

```java
// 1. 不能 new T[](无法确定运行时类型,协变数组会漏检)
// T[] arr = new T[10];              // 编译错
T[] arr = (T[]) new Object[10];       // 变通:强转,有 unchecked warning

// 2. 不能 new T()(不知道构造哪个类)
// T t = new T();                     // 编译错,需传 Supplier<T> 或 Class<T>

// 3. instanceof 不能带类型参数(运行时无此信息)
// if (x instanceof List<String>)     // 编译错
if (x instanceof List<?>) { }         // 只能用通配符

// 4. 静态字段不能用类型参数;不能 catch 泛型异常
```

#### 擦除还会让"看似不同"的重载在编译期打架

```java
class Overloads {
    void foo(List<String> a) { }
    void foo(List<Integer> b) { }   // 编译错:两个方法擦除后签名相同
}
```

```
error: name clash: foo(List<Integer>) and foo(List<String>) have the same erasure
```

`List<String>` 和 `List<Integer>` 在源码里是不同类型,编译器却直接拒绝——因为擦除后两个方法的字节码签名都是 `foo(List)`,重载决议(见[「函数与调用栈」](06-函数与调用栈.md))发生在编译期看到的是擦除前的类型,但方法本身要生成到 class 文件里,必须有不同的字节码签名才能共存;既然擦除后二者完全一致,JVM 层面根本没有办法区分该调用哪一个,编译器索性提前拦下这个错误,而不是等运行时用某种隐藏机制去猜。这是擦除"运行时只剩一份类型信息"这个根本限制在重载决议这个具体场景下的直接投影。

#### 桥接方法(bridge method)

擦除会破坏协变返回和泛型覆盖,编译器生成**桥接方法**弥合:

```java
class Node<T> { T get(){...} void set(T t){...} }
class StrNode extends Node<String> {
    @Override String get(){...}        // 你写的
    // 编译器还偷偷生成:Object get(){ return get(); }  ← 桥接,匹配父类擦除后签名 Object get()
}
```

否则父类 `Node` 擦除后是 `Object get()`,子类 `String get()` 签名不同,虚分派对不上。桥接方法用 `javap -v` 可见,标记 `ACC_BRIDGE ACC_SYNTHETIC`——实测 `StrNode.class` 里确实能看到两个 `get`:一个 `()Ljava/lang/String;`(你写的),一个 `()Ljava/lang/Object;` 带 `ACC_BRIDGE, ACC_SYNTHETIC` 标志(编译器生成的)。

#### 通配符:PECS 原则

泛型是**不变**的:`List<String>` 不是 `List<Object>`(和数组协变相反,更安全)。要放松用通配符:

- `? extends T`:上界,**生产者**(只能读出 T,不能写入,因为不知道确切子类型)。
- `? super T`:下界,**消费者**(只能写入 T,读出只能当 Object)。
- 口诀 **PECS**:Producer-Extends, Consumer-Super。

```java
// 从 src 读、往 dst 写:src 是生产者用 extends,dst 是消费者用 super
static <T> void copy(List<? super T> dst, List<? extends T> src){
    for (T t : src) dst.add(t);
}
```

C++20 concepts / 老式 SFINAE 解决的是类似"约束类型参数"的问题,但机制完全不同(编译期鸭子类型 vs 名义子类型 + 擦除)。

## 九、record:不可变数据载体

`record` 一行声明字段,编译器自动生成构造器、访问器(名字就是字段名,不加 `get` 前缀)、`equals`/`hashCode`/`toString`:

```java
record Point3(int x, int y) { }

public class RecordBasics {
    public static void main(String[] args) {
        Point3 p = new Point3(3, 4);
        System.out.println(p.x());      // 3   —— 访问器,不叫 getX()
        System.out.println(p.y());      // 4
        System.out.println(p);          // Point3[x=3, y=4] —— 自动生成的 toString
    }
}
```

```
3
4
Point3[x=3, y=4]
```

```java
record Point(int x, int y) { }
// 自动生成:private final 字段、全参构造器、访问器 x()/y()、equals/hashCode/toString
```

`record` 是**隐式 final** 的、字段 final、语义上是"透明的数据聚合"。类比 C++ 的聚合 struct + 自动生成的 `operator==`。可加紧凑构造器做校验:

```java
record Range(int lo, int hi) {
    Range {   // 紧凑构造器,校验后自动赋值
        if (lo > hi) throw new IllegalArgumentException();
    }
}
```

```java
Range r = new Range(1, 5);
System.out.println(r);           // Range[lo=1, hi=5]
new Range(5, 1);                 // 抛 IllegalArgumentException —— 紧凑构造器里的校验生效
```

## 十、sealed:密封类型(受控继承)

`sealed interface ... permits ...` 明确列出"谁能实现它",不在列表里的类无法实现:

```java
sealed interface Vehicle permits Car2, Bike { }
record Car2(int wheels) implements Vehicle { }
record Bike() implements Vehicle { }

public class SealedBasics {
    public static void main(String[] args) {
        Vehicle v = new Car2(4);
        System.out.println(v);   // Car2[wheels=4]
    }
}
```

```
Car2[wheels=4]
```

限制谁能继承/实现,配合模式匹配做穷尽性检查:

```java
sealed interface Shape permits Circle, Square { }
record Circle(double r) implements Shape { }
record Square(double s) implements Shape { }

double area(Shape sh) {
    return switch (sh) {          // 编译器知道只有两种,无需 default
        case Circle c -> Math.PI * c.r() * c.r();
        case Square s -> s.s() * s.s();
    };
}
```

```java
System.out.println(area(new Circle(2)));  // 12.566370614359172
System.out.println(area(new Square(3)));  // 9.0
```

类似 C++ 里用 `std::variant` + `std::visit` 表达封闭的和类型(sum type)。`sealed` 让编译器验证 switch 穷尽——少覆盖一种子类型,`switch` 表达式会编译报错而不是留一个运行时才暴露的漏洞。

## 十一、enum:是完整的类

最简单的枚举就是列一串常量名,像 C 里的 `enum` 但更安全——不能和整数混用,`switch`/`==` 都能直接用:

```java
enum Day { MON, TUE, WED, THU, FRI, SAT, SUN }

public class EnumBasics {
    public static void main(String[] args) {
        Day d = Day.MON;
        System.out.println(d);            // MON
        System.out.println(d == Day.MON); // true —— 枚举常量可以直接用 == 比较

        for (Day day : Day.values()) {    // 遍历所有常量
            System.out.print(day + " ");
        }
        System.out.println();
    }
}
```

```
MON
true
MON TUE WED THU FRI SAT SUN
```

Java 枚举**不是** C/C++ 的整数常量,而是编译成继承 `java.lang.Enum` 的类,每个枚举常量是一个**单例对象**(JVM 保证)。可有字段、方法、构造器,甚至每个常量各自的方法体(常量特定行为):

```java
enum Planet {
    EARTH(5.97e24, 6.37e6), MARS(6.42e23, 3.39e6);  // 调用构造器
    private final double mass, radius;
    Planet(double m, double r){ mass=m; radius=r; }
    double gravity(){ return 6.67e-11 * mass / (radius*radius); }
}
```

```java
for (Planet p : Planet.values()) {
    System.out.println(p + " gravity = " + p.gravity());
}
```

```
EARTH gravity = 9.813440652193735
MARS gravity = 3.726159709713629
```

因是单例,枚举可安全用 `==` 比较,是实现单例模式的最佳方式,`EnumMap`/`EnumSet` 用序号做位图/数组,极高效。

## 十二、内部类、匿名类、lambda 与变量捕获

函数式接口(只有一个抽象方法的接口,如内置的 `Runnable`)可以直接用 lambda 赋值,不需要专门写一个实现类:

```java
Runnable r = () -> System.out.println("running!");
r.run();
```

#### 内部类种类

- **静态嵌套类**(`static class`):无外部实例引用,等价顶层类放里面。
- **成员内部类**:持有隐藏的 `outer this` 引用,能访问外部实例字段——这也是内存泄漏源(内部类实例存活会拖住外部实例)。
- **局部类 / 匿名类**:定义在方法内。

#### 变量捕获必须 effectively final

匿名类/lambda 捕获的**局部变量必须是 final 或 effectively final**(初始化后不再赋值):

```java
int base = 10;                 // effectively final
Runnable r = () -> System.out.println(base + 1);
// base = 20;                  // 若取消注释,上面编译错
```

**为什么?** 局部变量在**栈帧**里,方法返回后栈帧销毁;而 lambda/匿名类对象在**堆**上,可能活得更久。Java 的做法是把捕获的变量**值拷贝**进 lambda 对象(基本类型拷值,引用类型拷引用值),要求其不变以保证"栈上的原变量"和"堆里的拷贝"语义一致,避免二者不同步的困惑。

对比 C++ lambda:显式选择 `[=]` 按值捕获或 `[&]` 按引用捕获,按引用可捕获可变变量,但栈变量失效后就是悬垂引用(UB)——责任在你。Java 用 effectively final 从语言层堵死了这个坑(只能按值,且值不变)。捕获实例字段则不同:lambda 捕获的是 `this`,通过它访问字段,字段可变。

#### lambda 的底层:invokedynamic

lambda **不是**匿名类语法糖。javac 生成 `invokedynamic` 指令,首次执行时由 `LambdaMetafactory` 在运行时动态生成实现函数式接口的类。好处:无捕获的 lambda 可复用同一实例(无状态),避免匿名类那种每处一个 class 文件的膨胀。方法引用(`String::length`)同理。

## 十三、反射:运行时的类型自省

前面几节的泛型擦除留下一个问题:`ArrayList<String>` 在运行时的 `Class` 对象和裸类型完全一样,那"运行时还能查到哪些类型信息"这件事本身是怎么做到的?答案是**反射(reflection)**——不是泛型信息,而是每个类固有的结构信息(有哪些字段、方法、构造器,以及类上的注解),这些从来没有被擦除,反射就是在运行时把这些结构信息读出来并动态调用的机制。

### `Class` 对象:反射的入口

每个已加载的类,JVM 都会在方法区(Metaspace)维护一份**唯一**的 `Class` 对象描述它——这正是本章开头"对象头里的 klass 指针"所指向的那份元数据在 Java API 层面的镜像。拿到一个类的 `Class` 对象有三条路:

```java
Class<?> c1 = String.class;                    // 编译期已知类型:字面量
Class<?> c2 = "hi".getClass();                 // 从对象实例反查
Class<?> c3 = Class.forName("java.lang.String"); // 运行期按字符串名字动态加载
```

`Class.forName` 是三者里最关键的一条:类名可以来自配置文件、注解、命令行参数——**只有它才能在编译期完全不知道具体类名的情况下,让程序在运行时决定要用哪个类**,这是反射"动态性"的根源。

### 通过反射动态创建对象、读写字段、调用方法

```java
import java.lang.reflect.*;

class User {
    private String name;
    private User() {}                          // 私有构造器和私有字段,正常情况下外部访问不到
    private User(String name) { this.name = name; }
    private String greet() { return "hi, " + name; }
}

public class ReflectDemo {
    public static void main(String[] args) throws Exception {
        Class<?> clazz = Class.forName(User.class.getName());

        // 绕过 private,拿到私有构造器并调用
        Constructor<?> ctor = clazz.getDeclaredConstructor(String.class);
        ctor.setAccessible(true);                // 破坏了封装:正常代码这里编译不过
        Object user = ctor.newInstance("Ann");

        // 绕过 private,读写私有字段
        Field nameField = clazz.getDeclaredField("name");
        nameField.setAccessible(true);
        System.out.println("read private field: " + nameField.get(user));
        nameField.set(user, "Bob");

        // 绕过 private,动态调用私有方法(方法名以字符串形式给出,可以来自配置文件)
        Method greet = clazz.getDeclaredMethod("greet");
        greet.setAccessible(true);
        System.out.println(greet.invoke(user));
    }
}
```

```
read private field: Ann
hi, Bob
```

`getDeclaredXxx` 系列方法能拿到**本类声明的、包括 private 在内**的所有成员(`getXxx` 不带 `Declared` 则只返回 `public` 成员,含继承来的);`setAccessible(true)` 关闭 Java 语言层面的访问检查——这一行正是反射"破坏封装"的字面体现:`private` 修饰符本来是编译器帮你把关的契约,反射调用这行代码之后,这个契约在运行时形同虚设。

### 为什么要有反射:框架不知道你的类型,但要操作它

Spring 的依赖注入是最典型的例子:容器启动时,业务代码里到底有哪些类要被管理、每个类的构造器需要哪些依赖、哪个字段标了 `@Autowired`——这些信息**在 Spring 编译的时候根本不存在**,它们全部来自你后来写的业务代码。框架的代码不可能提前 `import` 你的类、`new` 出你的对象,只能在运行时:扫描到一个类名字符串 → `Class.forName` 加载 → 用反射读它的构造器参数类型和字段上的注解 → 决定要注入什么 → 用反射调用构造器/setter 把依赖塞进去。这是一个通用性和具体性的根本矛盾:框架要在完全不知道使用者会定义什么类的前提下,依然能创建、装配、调用这些类——静态类型的方法调用做不到这一点(方法名、参数类型必须在编译期写死),只有反射把"调用哪个方法"这件事从编译期的语法结构,降级成运行期的字符串查找和动态调度,才能实现这种"框架代码与业务代码互不相识,却能协同工作"的解耦。类似地,MyBatis 靠反射把查询结果集的每一列反射地 `set` 进 POJO 的字段,JSON 库(Jackson/Gson)靠反射遍历字段做序列化/反序列化,JUnit 靠反射发现并调用标了 `@Test` 的方法——这些框架的共同特征是:它们要处理的具体类型集合在框架自身编译时是**开放、未知**的,只有反射能在这种开放性下工作。

### 代价:性能、类型安全、封装

反射不是免费的灵活性,三个代价对应三种典型的负面场景:

- **性能开销**:`Method.invoke()` 比直接调用慢,原因有二——一是参数需要装箱成 `Object[]` 传递、返回值需要拆箱,基本类型经过了一次不必要的对象化;二是反射调用要经过一层访问权限检查和方法查找(现代 JVM 会在多次调用后把高频反射调用"膨胀"成动态生成的字节码委托,即 `MethodAccessor` 从 `NativeMethodAccessor` 切换到 `GeneratedMethodAccessor`,削减了大部分差距,但首次调用和低频调用仍然比 `invokevirtual` 慢一截)。密集调用路径(热点循环)应避免用反射。
- **类型安全弱化**:反射调用把本该编译期检查的方法名、参数类型,变成了运行时才校验的字符串和 `Object[]`——方法名拼错、参数类型不匹配,编译器毫无察觉,只有跑到那一行 `invoke()` 才抛 `NoSuchMethodException`/`IllegalArgumentException`。这是本章反复出现的"静态类型检查 vs 运行期灵活性"取舍的又一个实例(与泛型擦除、`instanceof` 判断同源)。
- **破坏封装**:`setAccessible(true)` 能绕过 `private`,意味着"访问权限是设计者的契约"这条假设在反射面前不成立——这既是它能实现依赖注入等机制的原因,也是安全风险的来源(JDK 9+ 模块系统的**强封装**就是为了在模块边界上重新堵住这个口子,未 `open` 的包默认拒绝跨模块的深度反射)。

**经验法则**:业务代码里能用接口/多态解决的问题,不要用反射解决——反射该留给真正需要"处理编译期未知类型"的框架和通用工具代码。

### 与泛型擦除的关系

反射和泛型擦除看似矛盾(一个说"运行时还能查类型信息",一个说"运行时类型信息被擦除"),其实互补:反射能查到的是类**本身**的结构(`ArrayList` 有哪些字段方法),擦除丢掉的是类型**参数**(`ArrayList<String>` 里的 `String`)——`list.getClass()` 永远只能告诉你这是个 `ArrayList`,反射 API 里没有任何方法能让你问出"这个 `ArrayList` 实例当初是拿 `String` 实例化的",因为这个信息在编译期就已经被擦掉,反射查询的是运行时确实存在的元数据,擦除之前就已经不存在的信息,反射也无中生有不出来。

## 小结

- 对象一律在堆上,对象头里的 klass 指针类比 C++ 的 vptr;初始化顺序是"父类静态 → 父类实例 → 父类构造器 → 本类实例 → 本类构造器",构造期调用虚方法会踩到子类字段未初始化的坑。
- `protected` 比 C++ 语义宽,允许同包访问;单继承 + 多接口避免了 C++ 菱形继承的复杂性,接口 default 方法带来"多继承实现"但无状态菱形问题,冲突需显式覆盖解决。
- 多态靠 vtable(类方法)+ itable(接口方法)实现,JIT 用内联缓存和去虚化优化;重写按动态类型运行期分派,与编译期静态决议的重载是两回事(见[「函数与调用栈」](06-函数与调用栈.md))。
- `equals`/`hashCode` 必须成对重写,否则违反契约会让相等的对象在 `HashMap`/`HashSet` 里因散到错误的桶而"找不回来"。
- 泛型在编译期做类型检查,运行时被**擦除**成裸类型——这是为了向后兼容泛型出现前十年积累的字节码资产(迁移兼容性),代价是不能 `new T[]`/`new T()`、`instanceof` 不能带类型参数等限制,编译器还会生成桥接方法弥合擦除导致的签名不一致。
- `record`/`sealed`/`enum` 都是编译器生成大量样板代码的语法糖,`enum` 常量本质是单例对象;lambda 捕获局部变量必须 effectively final(值拷贝语义),底层靠 `invokedynamic` + `LambdaMetafactory` 运行时生成实现类,而非匿名类语法糖。
- 面向对象把数据和方法捆在一起,换来封装/继承/多态三件事有了统一的载体,代价是每个对象多一层间接寻址;继承是白盒复用、组合是黑盒复用,两者都能满足复用需求时优先选耦合更弱的组合。多态只对方法动态分派,字段访问按声明类型静态绑定(遮蔽而非覆盖)。
- 反射在运行时读取类的结构信息(`Class`/`Field`/`Method`/`Constructor`)并动态调用,是 Spring/MyBatis 等框架处理"编译期未知类型"的核心机制,代价是调用变慢、类型检查后移到运行期、且能绕过 `private` 破坏封装。
