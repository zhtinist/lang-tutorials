# 集合框架的内部实现

C++ 里你用 `std::vector`、`std::list`、`std::unordered_map`、`std::map`。Java 的集合框架(Java Collections Framework, JCF)在概念上一一对应,但**内部实现细节、内存布局、扩容策略与迭代器语义**都值得逐一掰开看:每种容器在堆上到底摆了什么,拷贝的是值还是引用,复杂度从哪来。

关于"引用 vs 值"的基础,参见[「变量与内存模型」](03-变量与内存模型.md);对象头布局参见[「数据类型与内存布局」](04-数据类型.md)。

## 一、数组:一切的地基

数组存一组**同类型**的元素,声明时用 `类型[]`,用 `new 类型[长度]` 创建,长度定死后不能再变:

```java
int[] a = new int[4];       // 4 个 int,初值全是 0
a[0] = 100;
a[3] = 400;
System.out.println(a[0]);      // 100
System.out.println(a.length);  // 4(注意是属性,没有括号,不是 a.length()）

String[] s = new String[3]; // 3 个引用槽,初值全是 null
s[0] = "hi";
System.out.println(s[1]);      // null(还没赋值）
```

访问越界会直接抛异常,不会像 C 那样悄悄读写别的内存:

```java
int[] b = new int[2];
System.out.println(b[5]); // 抛 ArrayIndexOutOfBoundsException,程序终止(除非你 catch）
```

也可以在声明时直接给出全部元素:

```java
int[] c = {1, 2, 3};        // 长度自动定为 3
```

Java 数组是**真正的对象**,在堆上分配,不像 C 那样只是一段裸内存 + 指针算术。

```java
int[] a = new int[4];        // 堆上分配:对象头 + length 字段 + 4 个连续 int
String[] s = new String[3];  // 堆上:3 个连续的“引用槽”,初值 null
```

#### 内存布局(HotSpot,64 位,压缩指针)

```
int[4] 在堆上:
┌──────────┬──────────┬────────┬────┬────┬────┬────┐
│ mark word│ klass ptr│ length │ [0]│ [1]│ [2]│ [3]│
│  8 bytes │  4 bytes │ 4 bytes│int │int │int │int │
└──────────┴──────────┴────────┴────┴────┴────┴────┘
             对象头共 16 字节        元素连续存放,cache 友好
```

与 C 的关键区别:

| 特性 | C/C++ 数组 | Java 数组 |
|------|-----------|-----------|
| 本质 | 裸内存,`a[i]` = `*(a+i)` | 堆上对象,含 length 字段 |
| 长度 | 编译期常量或需另存 | `a.length` 随身携带 |
| 边界检查 | 无,越界即 UB | 每次访问检查,越界抛 `ArrayIndexOutOfBoundsException` |
| 存放对象 | 可存对象值(连续) | 只能存引用(`Object[]` 是引用数组) |
| 协变 | 无 | **协变**:`Object[] o = new String[3];` 合法 |

#### 数组协变的坑

Java 数组协变意味着 `String[]` IS-A `Object[]`,这在编译期通过,但运行时每次写入都要做类型检查:

```java
Object[] arr = new String[3];
arr[0] = "ok";           // 正常
arr[1] = Integer.valueOf(1); // 编译通过!运行时抛 ArrayStoreException
```

C++ 的模板是不变(invariant)的,`vector<string>` 与 `vector<Object>` 毫无关系。Java 数组这个设计是历史包袱(泛型出现前为了让 `Arrays.sort(Object[])` 能用),代价是运行时 store check。泛型集合(下文)则是不变的。

#### 边界检查开销与消除

每次 `a[i]` 都插入 `0 <= i < a.length` 判断。JIT 有 **范围检查消除**(Range Check Elimination):在 `for (int i=0;i<a.length;i++)` 这类可证明安全的循环里,C2 会把检查提到循环外或删除,使性能逼近 C。所以规范层面有开销,实现层面常常被优化掉。

Java 把数组之外的容器归到一张继承图里。这张图不需要背,只是查阅用的"地图"——想知道某个容器属于哪一类、有哪些兄弟实现,回来看一眼即可:

## 三、ArrayList vs LinkedList

`ArrayList` 是最常用的"列表",支持按下标取、追加、删除:

```java
List<String> list = new ArrayList<>();
list.add("a");
list.add("b");
list.add("c");
System.out.println(list.get(1));   // b
list.remove("b");                  // 按值删除(也有按下标删除的重载 remove(int)）
System.out.println(list);          // [a, c]
System.out.println(list.size());   // 2
```

`LinkedList` 用法和 `ArrayList` 基本一致(都实现了 `List` 接口),额外提供 `addFirst`/`addLast` 这类操作两端的方法:

```java
LinkedList<String> linked = new LinkedList<>();
linked.add("x");
linked.addFirst("w");
System.out.println(linked);        // [w, x]
```

新手先无脑用 `ArrayList` 就够了,下面会讲为什么。

#### ArrayList:动态数组

内部就是一个 `Object[] elementData` + `int size`:

```java
// 简化的 JDK 源码结构
transient Object[] elementData; // 真正存元素的数组
private int size;               // 逻辑大小(<= elementData.length 容量)
```

内存图:

```
ArrayList 对象(堆)          elementData 数组(堆)
┌───────────────┐          ┌────┬────┬────┬────┬────┬────┐
│ elementData ──┼────────▶ │ e0 │ e1 │ e2 │null│null│null│
│ size = 3      │          └────┴────┴────┴────┴────┴────┘
└───────────────┘           capacity = 6, size = 3
```

注意存的是**引用**(`Object[]`),对象本体散落在堆各处;不像 C++ `vector<Point>` 把 Point 值连续内联。所以 Java 的 `ArrayList<Point>` 遍历时是"数组连续 → 逐个跳到堆各处",cache 局部性不如 C++ 的值语义 vector。要连续存基本类型,得用原生 `int[]` 或第三方原生集合。

**扩容**:默认容量 10,满了按 **1.5 倍** 增长(`newCap = oldCap + (oldCap >> 1)`),`Arrays.copyOf` 分配新数组并拷贝引用(浅拷贝,只拷指针值,不复制对象本体)。

```
size=10 已满,add 第 11 个:
新容量 = 10 + 5 = 15,分配 Object[15],拷贝 10 个引用过去,旧数组待 GC
```

对比 C++ `std::vector` 常见 2 倍扩容(libstdc++ 用 2x,MSVC 用 1.5x)。均摊 O(1) 追加。

**为什么是 1.5 倍而不是 2 倍**:两者都能保证均摊 O(1) 的追加复杂度——只要每次按固定比例(而非固定增量)扩容,总拷贝成本就是几何级数,均摊到每次 `add` 上是常数。真正的差别在**空间浪费**和**旧内存复用**这两件事上。倍数越大,扩容次数越少(总拷贝开销越低),但每次扩容后浪费的空间上限也越大——2 倍扩容在最坏情况下(刚扩容完就不再增长)会有接近 50% 的容量空置,1.5 倍的上限约 33%,这对内存本就比 C++ 值语义容器更"泡沫"的 Java(见前面`ArrayList<Point>`元素散落堆各处的讨论)是更谨慎的选择。另一个常被引用的理由是**旧内存的复用可能性**:如果扩容倍数严格小于**黄金分割比** `(1+√5)/2 ≈ 1.618`,那么从理论上讲,前几次释放掉的旧数组所占的内存空间,有可能被后续某次扩容重新复用(这是一些内存分配器上"倍数增长序列的和小于当前需求"这一数学性质带来的潜在收益,是否真正生效取决于具体分配器实现)。1.5 恰好在这个界限以下,是"扩容次数尽量少"与"峰值浪费尽量小"之间一个经验上表现均衡的取值,而不是任意选择。

用反射窥探底层 `elementData` 数组的真实长度,可直接观察这条 1.5 倍增长曲线(容量是内部实现,反射需加 `--add-opens`):

```java
import java.lang.reflect.*;
import java.util.*;
public class GrowDemo {
    static int cap(ArrayList<?> list) throws Exception {
        Field f = ArrayList.class.getDeclaredField("elementData");
        f.setAccessible(true);
        return ((Object[]) f.get(list)).length;
    }
    public static void main(String[] args) throws Exception {
        ArrayList<Integer> list = new ArrayList<>();
        System.out.println("initial capacity = " + cap(list));
        int last = -1;
        for (int i = 0; i < 40; i++) {
            list.add(i);
            int c = cap(list);
            if (c != last) { System.out.println("size=" + list.size() + " -> capacity=" + c); last = c; }
        }
    }
}
// 运行:java --add-opens java.base/java.util=ALL-UNNAMED GrowDemo.java
// initial capacity = 0     <- 空构造器懒分配,首次 add 才建长度 10 的数组
// size=1  -> capacity=10
// size=11 -> capacity=15   <- 10 + (10>>1) = 15
// size=16 -> capacity=22   <- 15 + (15>>1) = 22
// size=23 -> capacity=33
// size=34 -> capacity=49
```

#### 扩容实现的源码演进:JDK 8 → JDK 9+(含本机 JDK 25)

上面这条 1.5 倍增长曲线在 JDK 8 到当前 JDK(本机 25)之间,底层调用链发生过一次重构,**数值结果不变,但实现方式值得了解**:

- **JDK 8**:`add(E e)` → `ensureCapacityInternal()` → `calculateCapacity()` → `ensureExplicitCapacity()` → `grow()`。`grow()` 内部直接写死计算公式并直接赋值给字段:
  ```java
  int newCapacity = oldCapacity + (oldCapacity >> 1);
  ```
- **JDK 9 及以后**(本机 JDK 25 也是这套):调用链简化为 `add(E e)` → 私有重载 `add(E e, Object[] elementData, int s)` → `grow()`,把 `elementData` 和 `size` 以参数形式传入,而不是在方法内部反复读字段。容量计算被抽到公共工具类 `ArraysSupport`:
  ```java
  int newCapacity = ArraysSupport.newLength(oldCapacity,
              minCapacity - oldCapacity, /* minimum growth,至少要多少 */
              oldCapacity >> 1);         /* preferred growth,最好扩多少 */
  ```
  `ArraysSupport.newLength` 是 JDK 9 引入的共享工具方法,被 `ArrayList`、`HashMap`、`ArrayDeque` 等多个集合类复用,避免各自重复实现同一套"至少要多少、最好扩多少"的边界处理逻辑;把字段访问换成参数传递,也给了 JIT 更多逃逸分析和内联的优化空间。这是一次**纯内部重构**,`newCapacity` 的计算结果、1.5 倍这条曲线本身没有变化——上面的反射代码在 JDK 8 和 JDK 25 上分别跑一遍,打印出来的容量序列是一样的。

带初始容量构造 `new ArrayList<>(3)` 时有个容易被忽略的边界:插入第 4 个元素触发扩容,此时 `minCapacity=4`、`oldCapacity=3`,`oldCapacity>>1` 只有 1,按"取两者较大值"算出新容量是 `3+1=4`,不是直觉上的 `3*1.5→4`(数值凑巧一样,但推导路径不同)。只有当容量长到一定程度、`oldCapacity>>1`(偏好增量)持续大于 `minCapacity-oldCapacity`(最小增量)之后,才会稳定呈现"精确 1.5 倍"的曲线;容量很小的头几次扩容更接近"每次只多一点"的线性增长,不要用小规模测试草率反推比例公式。

#### ArrayList vs Vector

`Vector` 是比 `ArrayList` 更老的实现(JDK 1.0 遗留),两者都基于 `Object[]` 动态数组,区别集中在:

| 维度 | ArrayList | Vector |
|------|-----------|--------|
| 线程安全 | 否 | 是——每个公共方法都加 `synchronized` |
| 扩容倍数 | **1.5 倍**(`oldCapacity + oldCapacity>>1`) | **2 倍**(`newCapacity = oldCapacity * 2`) |
| 遍历方式 | `Iterator` / 增强 for | `Iterator` + 遗留的 `Enumeration`(`elements()`) |
| 现状 | 首选 | 不推荐 |

`Vector` 的 `synchronized` 锁的是整个对象,同一时刻只有一个线程能进入任何一个公共方法,哪怕两个线程都只是读也要互斥排队;`ArrayList` 没有这层开销,单线程场景下明显更快。多线程真要线程安全,应该用 `Collections.synchronizedList()` 或 `CopyOnWriteArrayList`(见后文「线程安全的集合有哪些」),而不是 `Vector` 这种方法级全表锁——这也是"新代码不要用 `Vector`"的直接原因。

#### LinkedList:双向链表

```java
private static class Node<E> {
    E item;
    Node<E> next;
    Node<E> prev;
}
```

每个节点是独立堆对象:对象头 16 字节 + 3 个引用(item/next/prev,压缩指针各 4 字节)≈ 32 字节/节点,存一个元素开销巨大。内存图:

```
first ─▶┌────┬────┬────┐   ┌────┬────┬────┐   ┌────┬────┬────┐◀─ last
        │prev│item│next┼──▶│prev│item│next┼──▶│prev│item│next│
        │null│ e0 │  ●─┘   │ ●  │ e1 │ ●─┘   │ ●  │ e2 │null│
        └────┴────┴────┘◀──┴────┴────┴────┘◀──┴────┴────┴────┘
```

对应 C++ `std::list`。节点散布堆中,遍历 cache-unfriendly。`get(i)` 是 O(n)(从最近的一端走)。**实践中 `ArrayList` 几乎总是更好**,即便频繁头部插入,`ArrayDeque` 也比 `LinkedList` 快。`LinkedList` 唯一优势是持有节点引用时的 O(1) 删除,但集合 API 里你通常拿不到节点。

#### ArrayList vs 普通数组:怎么选

结合第一节对数组内存布局的分析,数组和 `ArrayList` 的取舍可以归纳成一句话:**元素个数固定、追求极致性能(尤其是基本类型)用数组;个数不确定、需要集合 API 用 `ArrayList`**。

| 维度 | 普通数组 | ArrayList |
|------|---------|-----------|
| 长度 | 创建后固定,变长需手动 `Arrays.copyOf` 整体重建 | 自动扩容(1.5 倍),`size()` 随时反映当前元素数 |
| 存储的类型 | 基本类型和引用类型都行,基本类型连续内联(见第一节内存图) | 只能存引用类型,`int` 等基本类型自动装箱成 `Integer`,元素在堆上散落(见前面 `ArrayList<Point>` 的讨论) |
| API | 只有 `[]` 和 `.length`,增删要手写搬移 | `add`/`remove`/`contains`/`indexOf` 等开箱即用 |
| 泛型约束 | 协变但不做元素类型的编译期强约束(`Object[] o = new String[3]` 运行时才报 `ArrayStoreException`,见第一节) | `ArrayList<String>` 编译期就把类型焊死,不存在这类运行时惊喜 |
| 典型场景 | 数值计算、图像/音频缓冲区等大数据量基本类型场景 | 业务代码里绝大多数"一组对象"的场景 |

如果场景就是"存一大堆 `int`/`long` 还要动态增长",`ArrayList<Integer>` 的装箱开销可能成为瓶颈,这时候优先考虑手写一个基于 `int[]` 的动态数组,或引入 Eclipse Collections / fastutil 这类提供 `IntArrayList` 的第三方库(第一节已提过),而不是必须在"数组"和"`ArrayList`"里二选一。

#### 复杂度对照

| 操作 | ArrayList | LinkedList |
|------|-----------|-----------|
| `get(i)` | O(1) | O(n) |
| `add`(尾) | 均摊 O(1) | O(1) |
| `add(i, e)`(中间) | O(n)(搬移) | O(n)(定位)+O(1) |
| 头部插入 | O(n) | O(1) |
| `contains` | O(n) | O(n) |
| 内存/元素 | 1 个引用 + 容量冗余 | ~32 字节节点 |

## 四、HashMap:重头戏

`HashMap` 存"键 -> 值"映射,`put` 写入、`get` 按键查、`containsKey` 判断键是否存在;遍历用 `entrySet()` 拿到键值对:

```java
Map<String, Integer> scores = new HashMap<>();
scores.put("Alice", 90);
scores.put("Bob", 85);
System.out.println(scores.get("Alice"));           // 90
System.out.println(scores.containsKey("Carol"));   // false
for (Map.Entry<String, Integer> e : scores.entrySet()) {
    System.out.println(e.getKey() + " -> " + e.getValue());
}
```

注意:`HashMap` 不保证遍历顺序(下一节会看到实际打印顺序和插入顺序不一致),想要固定顺序看下一节的 `LinkedHashMap`/`TreeMap`。

对应 C++ `std::unordered_map`,但实现细节差别很大。

#### 结构:桶数组 + 链表/红黑树

```java
transient Node<K,V>[] table;  // 桶数组,长度总是 2 的幂
static class Node<K,V> {
    final int hash;   // 缓存的扰动后哈希
    final K key;
    V value;
    Node<K,V> next;   // 链表指针(拉链法解决冲突)
}
```

内存图(冲突时拉链):

```
table (Node[16])
┌────┐
│ 0  │──▶ null
│ 1  │──▶ [h,k1,v1] ──▶ [h,k9,v9] ──▶ null   (bucket 1 有两个键冲突)
│ 2  │──▶ null
│... │
│ 5  │──▶ [h,k5,v5] ──▶ null
└────┘
```

#### 哈希冲突的两种通用解法,以及 HashMap 为什么选链地址法

任何哈希表实现,只要桶数组长度有限,冲突就不可避免,通用解决思路只有两条:

- **开放地址法(Open Addressing)**:所有元素都存在数组本身里,冲突时按某种探测序列找下一个空位——**线性探测**(依次查 `i+1, i+2, ...`,容易产生"堆积"扎堆)、**二次探测**(查 `i±1², i±2², ...`,缓解堆积但可能探测不到全部单元)、**双重哈希**(用第二个哈希函数决定探测步长,分布更均匀)。
- **链地址法(Separate Chaining)**:每个桶挂一个独立的数据结构(通常是链表),把所有落在该桶的元素串起来——这正是 `HashMap` 的选择,也是本节前面 `Node<K,V>.next` 拉链结构的由来。

**为什么 `HashMap` 选链地址法而不是开放地址法**:

1. **删除的复杂度**:开放地址法删除一个元素后不能简单置空,否则会截断后续探测序列,通常要写入"已删除"的墓碑标记(tombstone),既占位又让查找逻辑变复杂;链地址法删除只是普通链表删除,`O(1)` 摘掉一个节点。
2. **负载因子的容忍度**:开放地址法所有元素挤在同一个数组里,一旦负载因子接近 1 探测序列会急剧变长,必须严格控制在较低负载因子(远小于 1)才能保持性能,对空间浪费更敏感;链地址法允许负载因子大于 1(极端情况下退化成一个大链表,只是变慢,不会像开放地址法那样彻底失效),`HashMap` 默认负载因子 0.75 也更从容。
3. **对哈希函数均匀性的要求**:开放地址法一旦哈希函数分布不均,探测序列会大量重叠导致连锁堆积;链地址法即使哈希函数一般,冲突也只局限在单个桶内的链表变长,影响面更可控。
4. **扩容压力**:开放地址法扩容时探测序列的语义会整体改变,几乎必须重新插入所有元素;链地址法扩容(下文 rehash)可以按桶为单位重新分配,JDK 8 甚至做到不重算哈希只判断一个 bit。

`HashMap` 在链地址法的基础上又叠了一层优化——链表长度超过阈值时树化(见下文),这是 JDK 8 才有的增强,链地址法本身的选择从 JDK 1.0 到现在没变过。

#### 哈希扰动函数

桶下标 = `hash & (n-1)`(n 是 2 的幂,等价取模但更快)。若直接用 `key.hashCode()`,高位不参与运算(因为 `& (n-1)` 只保留低位),高位不同、低位相同的键会撞。扰动把高 16 位异或到低位:

```java
static final int hash(Object key) {
    int h;
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
}
```

#### 冲突加剧时 treeify

同一个桶的链表长度 **≥ 8** 且 **table 长度 ≥ 64** 时,链表转为**红黑树**,把该桶最坏查找从 O(n) 降到 O(log n)。树节点数退到 **≤ 6** 时退化回链表(留 6/8 的滞后区间避免频繁转换)。

```
链长 >= 8 且 table.length >= 64:
bucket ──▶ 链表 ─treeify─▶ 红黑树(TreeNode)
若 table 还没到 64,优先扩容而非树化
```

**为什么 JDK 8 要专门为此引入红黑树,而不是保持链表到底**:在正常随机分布下,`HashMap` 的桶几乎不可能积累到 8 个元素——泊松分布告诉我们,负载因子 0.75 下单桶达到 8 个元素的概率低到可以忽略,链表在**正常使用**下从来不是问题。真正促成这次改动的是一类**恶意构造哈希碰撞的拒绝服务攻击**:如果攻击者能控制放入 `HashMap` 的 key(典型场景是 Web 服务器把 HTTP 请求参数名放进一个 `HashMap` 解析),就可以精心构造一批 `hashCode()` 结果故意落在同一个桶里的字符串,让原本期望 O(1) 的操作退化成 O(n) 的链表遍历——这类攻击(2011 年披露的"Hash DoS")曾让多个语言的 Web 框架用极少的畸形请求就能把 CPU 打满。仅靠链表,即使哈希扰动函数已经把高位异或进低位,也无法阻止蓄意构造的碰撞。JDK 8 的方案是给这一最坏情况设一个上限:一旦某个桶的链表长度触及一个"正常分布下几乎不会达到、但攻击下容易达到"的阈值(8),就转换成红黑树,把最坏复杂度兜底在 O(log n),而不再是 O(n)。这是一种"正常路径不变,只加固最坏情况"的设计:平均场景仍是普通链表拉链(实现简单、常数因子小),只有真正退化到病态分布时才承受红黑树更高的实现复杂度和维护成本(节点更大、插入删除要维持平衡)。这也解释了为什么阈值退回链表设在 6 而非 8——避免元素数量在 7/8 之间抖动时反复来回转换结构,6/8 的滞后区间是一种迟滞(hysteresis)设计,用来吸收这种抖动。

#### 负载因子与扩容 rehash

- **负载因子 0.75**:`size > capacity * 0.75` 时扩容为**两倍**。0.75 是空间/时间折中(经泊松分布分析,冲突概率与内存浪费平衡)。
- **扩容 rehash**:分配 2 倍新桶数组,重散列每个元素。因容量是 2 的幂且翻倍,元素新位置只有两种:`原位置` 或 `原位置 + 旧容量`。JDK 8 用这个性质避免重算 hash,只看 `hash & oldCap` 那一位是 0 还是 1,把旧链拆成 lo/hi 两条链,分别放到新表两个位置。O(n) 但常数小。

```
旧 table.length=16,扩到 32:
某桶的链表按 (hash & 16) 拆成两条 →  桶 j 和桶 j+16
```

**JDK 7 的扩容触发条件比 JDK 8 多一个隐藏限制**:JDK 7 `addEntry()` 里判断的是 `(size >= threshold) && (null != table[bucketIndex])`——不仅元素总数要超过阈值,**这次插入恰好落在的那个桶必须已经非空**(即真的发生了一次哈希冲突)才触发扩容;JDK 8 简化为只看 `size > threshold`,不再关心这次插入具体落在哪个桶。这是一个容易被忽略的历史细节,但不影响两者"负载因子 0.75、超阈值翻倍"的大结论。

#### put 方法完整流程

前面几点(桶结构、扰动函数、树化、扩容)都是拼图的一角,串起来看 `putVal` 的完整流程(JDK 8+),正好是"计算 hash → 定位桶 → 处理冲突 → 插入或更新 → 检查扩容"五步:

```java
// 简化版 putVal,保留核心分支,略去泛型通配符等细节
final V putVal(int hash, K key, V value, boolean onlyIfAbsent, boolean evict) {
    Node<K,V>[] tab; Node<K,V> p; int n, i;
    // ① 桶数组还没初始化(第一次 put)就先 resize() 建表
    if ((tab = table) == null || (n = tab.length) == 0)
        n = (tab = resize()).length;
    // ② 用 (n-1) & hash 定位桶;桶为空,直接放新节点,是最快路径
    if ((p = tab[i = (n - 1) & hash]) == null)
        tab[i] = newNode(hash, key, value, null);
    else {
        // ③ 桶非空,处理冲突:先看桶里的第一个节点是不是同一个 key
        Node<K,V> e; K k;
        if (p.hash == hash && ((k = p.key) == key || (key != null && key.equals(k))))
            e = p; // 命中,记下待更新的节点
        else if (p instanceof TreeNode) // 已经树化,走红黑树插入
            e = ((TreeNode<K,V>) p).putTreeVal(this, tab, hash, key, value);
        else {
            // 普通链表:遍历到尾部,找到就记下 e,找不到就尾插新节点
            for (int binCount = 0; ; ++binCount) {
                if ((e = p.next) == null) {
                    p.next = newNode(hash, key, value, null);
                    // 链表长度达到阈值(8),尝试树化(内部还会判断 table 长度是否 >= 64)
                    if (binCount >= TREEIFY_THRESHOLD - 1)
                        treeifyBin(tab, hash);
                    break;
                }
                if (e.hash == hash && ((k = e.key) == key || (key != null && key.equals(k))))
                    break; // 找到同 key 节点,跳出
                p = e;
            }
        }
        // ④ key 已存在:按 onlyIfAbsent 决定是否覆盖 value,返回旧值
        if (e != null) {
            V oldValue = e.value;
            if (!onlyIfAbsent || oldValue == null) e.value = value;
            afterNodeAccess(e); // 钩子方法,LinkedHashMap 借此维护访问序(LRU)
            return oldValue;
        }
    }
    ++modCount; // 结构性修改计数 +1,fail-fast 迭代器靠它检测并发修改
    // ⑤ 插入了新节点,size 超过阈值就扩容
    if (++size > threshold) resize();
    afterNodeInsertion(evict); // 钩子方法,LinkedHashMap 的 LRU 淘汰逻辑挂在这里
    return null;
}
```

几个容易被问到的点:

- **`onlyIfAbsent` 参数**:`put()` 传 `false`(存在就覆盖),`putIfAbsent()` 传 `true`(存在就不覆盖,返回旧值)——两者共用同一套 `putVal`,只是这一个布尔位不同。
- **`afterNodeAccess`/`afterNodeInsertion` 钩子**:`HashMap` 里是空实现,专门留给 `LinkedHashMap` 覆写,用来维护插入序/访问序双向链表(第五节)和实现 LRU 缓存淘汰——设计上典型的模板方法模式,`HashMap` 定骨架,子类填细节。
- **树化和扩容谁先发生**:插入新节点导致链表变长时先判断树化,树化内部如果发现 `table.length < 64` 会优先扩容而不是真正建树(避免小表就大量建红黑树,浪费空间);而插入完成后的整体扩容检查(第⑤步)是另一回事,判断的是全表 `size` 是否超过阈值,和某一个桶的链表长度无关。

#### 关键契约:equals/hashCode

`HashMap` 定位分两步:先按 hash 找桶,再在桶内用 `equals` 逐个比。所以自定义 key **必须**同时正确重写 `equals` 和 `hashCode`,否则相等的对象散到不同桶就找不回来。详见[「面向对象与类型系统」中的 equals/hashCode 契约](08-面向对象与类型系统.md)。C++ 里同理:`unordered_map` 需要 `std::hash` 特化 + `operator==`。

#### 复杂度

| 操作 | 平均 | 最坏(树化后) |
|------|------|--------------|
| `get`/`put`/`remove` | O(1) | O(log n) |
| 遍历 | O(capacity + size) | 同 |

注意:`HashMap` **非线程安全**;并发下扩容 JDK7 会成环死循环(JDK8 修复但仍可能丢数据)。并发用 `ConcurrentHashMap`,见[「并发模型」](10-并发模型.md)。

#### 为什么线程不安全:具体到每一种坏事

"非线程安全"不是一句空话,`HashMap` 在并发下具体会出这几类问题:

**1. JDK 7:扩容死循环(经典面试题)**。JDK 7 的 `transfer()` 用**头插法**把旧链表元素搬到新数组,且是"一边遍历旧链表一边把新节点插到新桶头部"。如果线程 A 扩容到一半被挂起,线程 B 也在并发扩容,两者交替推进 `next` 指针的过程可能让本来是 `a → b` 的单向链接,在两个线程各自认为的"下一个节点"错乱重排后,被拧成 `a → b → a` 的环。之后任何一个线程再 `get()` 该桶,遍历链表 `next` 永远走不到 `null`,CPU 占满,程序假死。

```
正常搬迁:  a -> b -> null
并发交叉后可能变成:  a -> b -> a -> b -> ...(环,遍历永不终止)
```

**2. JDK 8:数据覆盖(丢失更新)**。JDK 8 把 `transfer()` 改成**尾插法**,不再产生环,官方 release note 里也明确是为了修复这个死循环;但这并不等于线程安全。最直接的例子是两个线程同时对**同一个空桶**执行 `putVal()` 的第②步(`tab[i] == null` 就直接放入新节点)——这个"判断桶为空 + 写入新节点"合起来不是原子操作,两个线程都读到"桶是空的",都执行写入,后写入的那个会直接覆盖先写入的引用,先写的那次 `put` 彻底丢失,`size` 也只增加了一次。

**3. `size` 计数丢失**。`++size` 本身就是"读取-加一-写回"三步,多线程并发执行时经典的 race:两个线程同时读到 `size=10`,都算出 `11` 再写回,结果两次 `put` 只让 `size` 变成 `11` 而不是 `12`。下面这段代码可以稳定复现"更新丢失"(把 `HashMap` 换成 `get`+`put` 的读改写模式,不依赖具体哪种内部竞态,只要能证明"非原子的读写组合在并发下会丢更新"就够了):

```java
import java.util.*;
import java.util.concurrent.*;

public class LostUpdateDemo {
    public static void main(String[] args) throws Exception {
        Map<String, Integer> map = new HashMap<>(); // 非线程安全
        map.put("counter", 0);
        int threads = 8, loopsPerThread = 2000;
        ExecutorService pool = Executors.newFixedThreadPool(threads);
        CountDownLatch latch = new CountDownLatch(threads);
        for (int t = 0; t < threads; t++) {
            pool.submit(() -> {
                for (int i = 0; i < loopsPerThread; i++) {
                    int cur = map.get("counter");   // 读
                    map.put("counter", cur + 1);    // 改后写回,读写之间不是原子的
                }
                latch.countDown();
            });
        }
        latch.await();
        pool.shutdown();
        System.out.println("expected = " + (threads * loopsPerThread));
        System.out.println("actual   = " + map.get("counter"));
    }
}
// expected = 16000
// actual   = 2866   <- 实际输出每次不同,但稳定小于期望值,证明更新丢失
```

**4. `modCount` 不是 `volatile`,fail-fast 也不可靠**。`modCount` 只是普通 `int` 字段,一个线程结构性修改了 `Map`,另一个线程的迭代器不一定能立刻"看见"这个变化(可见性问题),`ConcurrentModificationException` 因此是"尽力而为"而非保证触发——这也是第八节强调"fail-fast 不是并发保护"的根本原因。

从并发编程的三个核心视角总结:`put()` 的"判断桶空 + 写入"、`++size` 都破坏了**原子性**;`modCount`/`table` 引用没有用 `volatile` 修饰,破坏了**可见性**;JDK 7 头插法搬迁在指令重排下还牵涉**有序性**。三者叠加,就是"HashMap 非线程安全"这句话背后的全部内容。

#### ConcurrentHashMap 怎么解决线程安全

`ConcurrentHashMap` 在 JDK 7 和 JDK 8 用了两套完全不同的方案:

**JDK 7:分段锁(Segment)**。整个 `ConcurrentHashMap` 被拆成若干个 `Segment`,每个 `Segment` 继承 `ReentrantLock` 并且内部又是一个独立的小 `HashEntry[]` 哈希表。写操作只锁自己所在的 `Segment`,不同 `Segment` 之间可以并发写;并发度上限就是 `Segment` 的个数(默认 16)。读操作大多不加锁,靠 `volatile` 保证可见性。

```
ConcurrentHashMap(JDK7)
┌─────────┬─────────┬─────────┬─────┐
│Segment0 │Segment1 │Segment2 │ ... │  <- 每个 Segment 自带一把 ReentrantLock
│(小Hash表)│(小Hash表)│(小Hash表)│     │     和自己的 HashEntry[]
└─────────┴─────────┴─────────┴─────┘
```

**JDK 8:去掉 Segment,改用 CAS + `synchronized`(锁桶头节点)**。结构变回和 `HashMap` 一样的单一 `Node[] table`(同样支持链表转红黑树),并发控制下沉到"桶"这一级粒度,比 `Segment` 更细:

- 目标桶为空时,用 **CAS**(`compareAndSwapObject`)尝试直接放入首节点,成功就完事,不需要加锁;失败(说明有别的线程抢先了)就自旋重试。
- 目标桶已经非空(有别的线程占用或本来就有链表/树)时,对**该桶的头节点**加 `synchronized`,只在这一个桶的粒度上互斥,不影响其他桶的并发写。
- 扩容时通过一个 `volatile` 的 `sizeCtl`/迁移状态标记多个线程协同"分片搬迁":每个线程认领一段桶区间去迁移,搬完用 CAS 标记该区间"已完成",其他线程可以来"帮忙"迁移还没做完的区间,而不是只能有一个线程独自扩容、其他线程干等。

```
ConcurrentHashMap(JDK8)
Node[] table(和 HashMap 结构一致)
桶为空 → CAS 直接放入(无锁)
桶非空 → synchronized(该桶头节点) → 链表/红黑树插入
```

理论并发度从"Segment 个数"提升到"数组长度",且 JDK 6 之后 `synchronized` 支持锁升级(偏向锁 → 轻量级锁 → 重量级锁),在低竞争场景下和 `ReentrantLock` 性能相当却更轻量,这是 JDK 8 弃用分段锁的直接原因。

**为什么 `ConcurrentHashMap` 不允许 `key`/`value` 为 `null`**:`get(key)` 返回 `null` 有两种可能——"这个 key 不存在"或"这个 key 存在但 value 就是 null",单线程下可以再调一次 `containsKey()` 消除歧义;但在并发场景下,`containsKey()` 和 `get()` 是两次独立调用,中间可能被其他线程插入/删除,查出来的结果已经对不上了,`null` 会带来无法消除的歧义。`Hashtable` 同理禁止 `null`;`HashMap` 单线程下没有这个歧义问题,所以放开了限制。

#### HashMap / Hashtable / HashSet / ConcurrentHashMap 怎么选

| | HashMap | Hashtable | HashSet | ConcurrentHashMap |
|---|---------|-----------|---------|--------------------|
| 线程安全 | 否 | 是(整表 `synchronized`) | 否 | 是(CAS + 桶级 `synchronized`) |
| null key/value | 都允许 | 都不允许 | 允许一个 null 元素 | 都不允许 |
| 底层结构 | 数组+链表/红黑树 | 数组+链表(无树化) | 内部包一个 HashMap,元素当 key | 数组+链表/红黑树 |
| 初始容量 | 16,2 的幂 | 11,扩容 `2n+1` | 同 HashMap | 可自定义,同样 2 的幂 |
| 迭代器 | fail-fast `Iterator` | 遗留的 `Enumeration` + fail-fast `Iterator` | fail-fast `Iterator` | 弱一致迭代器,不抛 `ConcurrentModificationException` |
| 适用场景 | 单线程/已自行同步的键值对存储 | 基本弃用,仅维护老代码 | 单线程去重、成员判断 | 高并发计数器、缓存、共享状态 |

`Hashtable` 容量默认给了一个质数 11(而不是 2 的幂),目的是配合它自己的哈希分布策略减少冲突,但代价是扩容成 `2n+1` 后**必须重新计算所有元素的哈希值**——不像 `HashMap`/`ConcurrentHashMap` 容量总是 2 的幂,可以用位运算代替取模、扩容时也能利用"新位置只差一个 bit"的性质省掉重算哈希,这也是 `Hashtable` 性能明显落后的原因之一,而不仅仅是"加了锁"这么简单。

#### 线程安全的集合有哪些

除了 `ConcurrentHashMap`,`java.util.concurrent` 包和几个遗留类一起构成了 Java 线程安全集合的全貌:

| 集合/工具 | 属于 | 线程安全实现方式 |
|-----------|------|------------------|
| `Vector` | List | 方法级 `synchronized`(遗留,不推荐) |
| `Hashtable` | Map | 方法级 `synchronized`(遗留,不推荐) |
| `Collections.synchronizedList/Map/Set(...)` | 包装器 | 对传入的集合包一层锁,每个方法调用都同步整个集合,粒度粗 |
| `ConcurrentHashMap` | Map | 见上文,CAS + 桶级 `synchronized` |
| `CopyOnWriteArrayList` | List | 写时复制整个数组(写操作重,读操作完全无锁),适合"读多写极少"场景,如监听器列表 |
| `ConcurrentLinkedQueue` | Queue | 无锁(CAS)实现的非阻塞队列 |
| `BlockingQueue` 系列(`ArrayBlockingQueue`/`LinkedBlockingQueue`等) | Queue | 内部用锁+条件变量,支持"队列满/空时阻塞等待",是生产者-消费者模式的标准工具 |

选择原则:优先用 `java.util.concurrent` 包里专门设计的并发集合(`ConcurrentHashMap`、`CopyOnWriteArrayList`、各种 `BlockingQueue`),它们针对并发场景做了细粒度锁或无锁优化;只有历史遗留代码才会看到 `Vector`/`Hashtable`;`Collections.synchronizedXxx()` 是"给现成的非线程安全集合套一层壳"的应急方案,粒度粗、性能一般,复合操作(比如"先判断包含再插入")仍然需要调用方自己在包装后的集合上加锁做整体同步。

## 五、LinkedHashMap / TreeMap

`LinkedHashMap`、`TreeMap` 和 `HashMap` 一样有 `put`/`get`,区别只在**遍历顺序**:

```java
Map<String, Integer> linked = new LinkedHashMap<>();
linked.put("banana", 1);
linked.put("apple", 2);
System.out.println(linked.get("apple")); // 2
System.out.println(linked);              // {banana=1, apple=2}

Map<String, Integer> tree = new TreeMap<>();
tree.put("banana", 1);
tree.put("apple", 2);
System.out.println(tree);                // {apple=2, banana=1}
```

三种 Map 该怎么选:不关心顺序用 `HashMap`(最快);想按插入顺序遍历用 `LinkedHashMap`;想按 key 排序遍历用 `TreeMap`。

#### LinkedHashMap

在 `HashMap` 的 Node 上再加 `before`/`after` 双向链,维护**插入顺序**(或访问顺序 `accessOrder=true`,可实现 LRU 缓存)。哈希查找仍 O(1),额外维护一条贯穿所有节点的链表。

```
HashMap 的桶结构 + 一条横穿所有节点的双向链(记录顺序)
head ──▶ node ──▶ node ──▶ node ──▶ tail
```

#### TreeMap

基于**红黑树**(自平衡 BST),对应 C++ `std::map`。按 key 排序(自然序或 `Comparator`)。所有操作 O(log n),提供 `firstKey`/`lastKey`/`floorKey`/`ceilingKey`/`subMap` 等有序视图。key 需可比较(`Comparable` 或传 `Comparator`),见[「标准库算法」](11-标准库算法.md)。

#### 红黑树在 Java 集合里的分布

容易和"HashMap 会树化"混淆的一点是:**只有 `TreeMap`/`TreeSet` 把红黑树当成唯一核心结构**,任何时候查找、插入、删除都在整棵树上进行,天然保持全局有序;而 `HashMap`/`HashSet`/`LinkedHashMap`/`LinkedHashSet`/`ConcurrentHashMap` 的红黑树只是**某一个桶内部**在冲突严重时的局部退化结构(第四节的树化条件:链长 ≥8 且 table 长度 ≥64),桶与桶之间依然是哈希分布,**整个 Map 并不因此获得全局排序能力**——`HashMap` 遍历顺序仍然是"看着乱"的桶序,不会因为某个桶内部是棵树就变得有序。

红黑树相比追求绝对平衡的 AVL 树,允许"最长路径不超过最短路径两倍"这种更宽松的平衡(通过"黑色节点数相同、红色节点不相连"的规则保证),插入删除时需要的旋转次数更少、维护成本更低,查找复杂度仍稳定在 O(log n)——这是一种用"放弃极致平衡换取更低综合维护成本"的工程取舍,`TreeMap` 直接受益于此,`HashMap` 的树化则是把它当成"最坏情况下的安全网"来用,两者动机并不相同。

三种 Map 的迭代顺序对比一目了然:`HashMap` 由桶位置决定(未指定、看着"乱"),`LinkedHashMap` 保插入序,`TreeMap` 按 key 排序:

```java
import java.util.*;
public class MapOrder {
    static void fill(Map<String,Integer> m) {
        for (String k : new String[]{"banana","apple","cherry","date"}) m.put(k, k.length());
    }
    public static void main(String[] args) {
        Map<String,Integer> hash = new HashMap<>();
        Map<String,Integer> linked = new LinkedHashMap<>();
        Map<String,Integer> tree = new TreeMap<>();
        fill(hash); fill(linked); fill(tree);
        System.out.println("HashMap:       " + hash.keySet());
        System.out.println("LinkedHashMap: " + linked.keySet());
        System.out.println("TreeMap:       " + tree.keySet());
    }
}
// HashMap:       [banana, date, apple, cherry]   <- 桶顺序,未指定(切勿依赖)
// LinkedHashMap: [banana, apple, cherry, date]   <- 插入顺序
// TreeMap:       [apple, banana, cherry, date]   <- 字典序
```

## 六、HashSet / ArrayDeque

`HashSet` 是"只存键、不存值"的集合,`add` 添加、`contains` 判断是否存在,重复元素会被自动忽略:

```java
Set<String> set = new HashSet<>();
set.add("a");
set.add("b");
set.add("a");                          // 重复,忽略
System.out.println(set.size());        // 2
System.out.println(set.contains("a"));  // true
```

`ArrayDeque` 是双端队列,当栈用就 `push`/`pop`(后进先出),当队列用就 `offer`/`poll`(先进先出):

```java
ArrayDeque<Integer> stack = new ArrayDeque<>();
stack.push(1);
stack.push(2);
System.out.println(stack.pop());    // 2 —— 后进先出

ArrayDeque<Integer> queue = new ArrayDeque<>();
queue.offer(1);
queue.offer(2);
System.out.println(queue.poll());   // 1 —— 先进先出
```

- **HashSet**:内部就是一个 `HashMap`,元素当 key,value 是一个共享的 dummy `Object`。所以 `HashSet` 的一切特性等于 `HashMap` 的 keySet。对应 C++ `unordered_set`。
- **LinkedHashSet**:内部 `LinkedHashMap`,保插入序。
- **TreeSet**:内部 `TreeMap`,有序,对应 `std::set`。
- **ArrayDeque**:**循环数组**实现的双端队列,`head`/`tail` 两个索引在环形缓冲上移动,扩容翻倍。作栈或队列都比 `Stack`(过时,继承自 `Vector`,带同步)和 `LinkedList` 快。**首选的栈/队列实现**。不允许 null(用 null 表示空槽)。

```
ArrayDeque 循环数组:
┌───┬───┬───┬───┬───┬───┐
│ e │ e │   │   │ e │ e │   head=4, tail=2 (环绕)
└───┴───┴───┴───┴───┴───┘
```

## 七、泛型集合与类型擦除的影响

集合声明时用尖括号 `<类型>` 指定"只能装什么",编译器帮你在编译期挡住类型错误,取出来也不用强制类型转换:

```java
ArrayList<String> names = new ArrayList<>();
names.add("Alice");
// names.add(42);       // 编译报错:类型不匹配,写 Java 之前的编译器就会拦下
String first = names.get(0); // 不需要强制类型转换
System.out.println(first);   // Alice
```

对比:如果不写尖括号(老式写法 `ArrayList names = new ArrayList();`),`get(0)` 拿到的是 `Object`,还要手动强转,还可能在运行时才炸——所以现在写 Java 永远带上尖括号里的类型。

`ArrayList<String>` 在运行时就是 `ArrayList`,内部 `Object[]`;泛型只在编译期检查并自动插入强制转换。这就是为什么不能 `new T[]`、集合里存的永远是引用(基本类型被自动装箱)。擦除机制详见[「泛型与类型擦除」](08-面向对象与类型系统.md)。

后果:`ArrayList<Integer>` 每个元素是堆上的 `Integer` 对象 + 数组里的引用,内存与拆装箱开销远大于 C++ `vector<int>`。性能敏感场景用原生数组或第三方原生集合(Eclipse Collections、fastutil)。

## 八、迭代器与 fail-fast

用增强 for 循环遍历集合是最常见的写法,底层其实是编译器帮你调用了 `Iterator`:

```java
List<String> list = new ArrayList<>(List.of("a", "b", "c"));
for (String x : list) {
    System.out.println(x);
}
```

**有一条硬性规则**:遍历过程中不要直接调用集合的 `add`/`remove` 去修改它(不管是不是你要删的那个元素),否则大概率会抛异常。想在遍历时删元素,用 `removeIf`,或显式拿到 `Iterator` 调用它自己的 `remove()`。下面的"底层与 C 对比"会解释原因。

集合内部维护 `modCount`(结构性修改计数)。迭代器创建时记下 `expectedModCount`,每次 `next()` 校验;若期间集合被非迭代器途径修改,抛 `ConcurrentModificationException`。

```java
List<Integer> list = new ArrayList<>(List.of(1, 2, 3));
for (Integer x : list) {      // 增强 for 底层用 Iterator
    if (x == 2) list.remove(x); // 结构修改 → modCount 变 → 下次 next() 抛异常
}
// 正确做法:用 iterator.remove() 或 list.removeIf(x -> x == 2)
```

实际跑一遍能看到异常确实抛出,而 `removeIf` 安全无恙:

```java
import java.util.*;
public class FailFast {
    public static void main(String[] args) {
        List<Integer> list = new ArrayList<>(List.of(1, 2, 3, 4));
        try {
            for (Integer x : list) {          // 增强 for 底层用 Iterator
                if (x == 2) list.remove(x);   // 结构性修改,modCount 变化
            }
        } catch (ConcurrentModificationException e) {
            System.out.println("caught: " + e.getClass().getSimpleName());
        }
        list.removeIf(x -> x == 2);           // 正确:内部走迭代器,不抛 CME
        System.out.println("after removeIf: " + list);
    }
}
// caught: ConcurrentModificationException
// after removeIf: [1, 3, 4]
```

fail-fast 是**尽力而为**的错误检测(不保证一定触发),不是并发保护;真正并发用 `CopyOnWriteArrayList`/`ConcurrentHashMap`(弱一致迭代器,不抛此异常)。C++ STL 里对应的是"迭代器失效"——但 STL 是 UB,Java 主动抛异常帮你抓早。

## 九、与 C++ STL 容器速查对照

| Java | C++ STL | 底层 |
|------|---------|------|
| `ArrayList` | `vector` | 动态数组(Java 存引用,C++ 存值) |
| `LinkedList` | `list` | 双向链表 |
| `ArrayDeque` | `deque` | 循环数组(C++ deque 是分段数组) |
| `HashMap` | `unordered_map` | 拉链哈希(Java 会树化) |
| `TreeMap` | `map` | 红黑树 |
| `HashSet` | `unordered_set` | 哈希 |
| `TreeSet` | `set` | 红黑树 |
| `PriorityQueue` | `priority_queue` | 二叉堆 |

## 小结

- 数组是堆上带 length 字段的对象,越界抛异常而非 UB,但协变留了运行时 store check 的坑。
- `ArrayList` 是可扩容的引用数组,按 **1.5 倍**扩容——扩容次数与峰值内存浪费之间的权衡取值;`LinkedList` 是双向链表(单节点开销大,遍历 cache 不友好),复杂度差异明显,实践中 `ArrayList`/`ArrayDeque` 几乎总是更好的选择。
- `HashMap` 是桶数组 + 链表/红黑树,靠哈希扰动、0.75 负载因子扩容、JDK8 的 rehash 优化撑起 O(1) 均摊;JDK 8 引入的**树化**专门针对恶意构造的哈希碰撞攻击,把最坏复杂度从 O(n) 兜底到 O(log n),正常分布下几乎不触发。
- `LinkedHashMap`/`TreeMap` 分别用双向链和红黑树维护顺序;`HashSet`/`TreeSet`/`LinkedHashSet` 本质是套壳的对应 Map;红黑树只在 `TreeMap`/`TreeSet` 里是全局结构,在 `HashMap` 系列里只是单个桶的局部退化。
- `HashMap` 线程不安全体现在原子性(桶判空+写入、`++size`)、可见性(`modCount`/`table` 非 `volatile`)、有序性(JDK7 头插法并发扩容成环)三个层面都有破绽;`ConcurrentHashMap` 用 CAS + 桶级 `synchronized`(JDK8,取代 JDK7 的 Segment 分段锁)把并发控制下沉到单个桶,配合协同扩容解决这些问题。
- 泛型在运行时被擦除,集合里的基本类型全部装箱;迭代器靠 `modCount` 做 fail-fast 检测,是尽力而为而非并发保护。
