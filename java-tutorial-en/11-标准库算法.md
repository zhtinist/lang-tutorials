# Standard Library Algorithms

C++'s `<algorithm>`, `std::sort` (introsort), `std::set` (red-black tree), and `priority_queue` (heap) all live in the STL. Java's counterparts are `java.util.Collections`, `Arrays`, `PriorityQueue`, and `TreeMap`, plus the functional Stream API.

## 1. The Collections Utility Class

`java.util.Collections` is a bunch of static methods that operate on `List`/`Collection`:

```java
List<Integer> list = new ArrayList<>(List.of(3, 1, 2));
Collections.sort(list);                          // in-place sort (internally converts to an array and uses TimSort)
int idx = Collections.binarySearch(list, 2);     // binary search on a sorted List; on a linked list (non-RandomAccess) it's O(n) list traversals + O(log n) comparisons
Collections.reverse(list);
Collections.shuffle(list);
int max = Collections.max(list);

// unmodifiable view: returns a wrapper; any modification throws UnsupportedOperationException (analogous to a const reference, but checked at runtime)
List<Integer> ro = Collections.unmodifiableList(list); // still points to the underlying list; when list changes, it changes too
List<Integer> imm = List.of(1, 2, 3);            // JDK9+ genuinely immutable copy
```

`binarySearch` requires that the premise of binary search — the array is already sorted in the same order — be guaranteed by the caller itself; the standard library will not check it for you. The reason is straightforward: checking "is it already sorted" is itself O(n), and if every call verified it once, it would cancel out the O(log n) meaning of binary search; making this premise a contract handed to the caller is what lets `binarySearch` itself stay O(log n). Violating the contract (passing an unsorted array) does not raise an error, it merely returns a meaningless result. A negative return value `-(insertion point)-1` indicates not found, and can be used to determine the insertion position.

## 2. Arrays.sort: Two Algorithms

`Arrays.sort` uses different algorithms for **primitive types** and for **object arrays**, and this is not arbitrary:

```java
int[] a = {5, 2, 8, 1};
Arrays.sort(a);                    // Dual-Pivot Quicksort

Integer[] b = {5, 2, 8, 1};
Arrays.sort(b);                    // TimSort (a merge-sort variant)
Arrays.sort(b, Comparator.reverseOrder());
```

| Dimension | Primitive int[] | Object Object[] |
|------|--------------|--------------|
| Algorithm | Dual-pivot quicksort | TimSort |
| Stability | Doesn't matter (equal values are completely identical) | Must be stable |
| Comparison cost | Extremely low (a machine instruction) | High (calls compareTo/compare, possibly a virtual method) |
| Focus | Cache locality, comparison count | Reduce comparisons, stability |

**Why primitive types use dual-pivot quicksort**: two `int`s being equal means they are the very same value, and swapping them makes no observable difference, so **stability is meaningless** — this is a precondition for choosing quicksort, not an advantage of quicksort itself; quicksort is equally fast for sorting objects, it's just that its instability, on primitive types, costs nothing at all. Quicksort is in-place and cache-friendly (sequential access has good locality), and comparison is a cheap CPU instruction, which means "comparison count" is not the bottleneck here — "memory-access pattern" is. Dual-pivot quicksort picks two pivots to split the array into three segments, giving about **5% fewer comparisons** than classic single-pivot quicksort and better cache locality — note that its **swap count is actually higher than single-pivot's**, and the advantage comes from "fewer comparisons + memory-access-friendliness," not "less moving."

**Why objects use TimSort**, corresponding directly to the two focus points in the table above:
1. **Stability**: object sorting is often by some field, and the original relative order of equal elements must be preserved (for example, sort by A first, then by B, and when B is equal the A order must be maintained). Quicksort arbitrarily swaps positions of equal-valued elements during partitioning and does not guarantee the original order, which doesn't matter for primitive types but is a wrong result for multi-field object sorting. TimSort (merge-based algorithms are naturally stable) meets this requirement.
2. **Comparison is expensive**: comparing objects is a method call (possibly an interface virtual call, and possibly comparing multiple fields internally), not something a single machine instruction can complete, which means "reducing the comparison count" is more worth optimizing than "reducing the number of data moves." TimSort exploits the local ordering common in real data: it scans out already-ordered segments ("runs") and merges between runs rather than re-comparing every pair of elements, so on already-sorted input the comparison count approaches O(n); quicksort doesn't recognize this structure, and its worst case is still O(n²) comparisons.

TimSort combines merge sort with insertion sort: it scans out increasing/decreasing runs, extends short runs to a minrun length using binary insertion sort, and then merges them according to a stack invariant. Worst case O(n log n), already-sorted O(n). It needs O(n) auxiliary space (for merging), whereas quicksort is in-place — an object array is itself a layer of pointer indirection (the array stores references, not the objects themselves), so its cache locality is naturally worse than a primitive array's, and in that case paying a little extra space for stability and fewer comparisons is a reasonable trade-off.

## 3. Comparable and Comparator

- `Comparable<T>`: **natural ordering**, the class implements `compareTo` itself, and a class has only one. Analogous to C++'s `operator<`.
- `Comparator<T>`: an **external strategy**, of which any number can be defined. Analogous to the functor passed to `std::sort`.

The two coexist rather than only one being kept because they answer two different questions: "does this type itself have a single natural ordering" (such as numeric magnitude or string lexicographic order, which `Comparable` expresses as the type's built-in sorting semantics), versus "what temporary rule do I want to sort by this one time" (the same `Person` type — in some places you want to sort by age, in others by name, and none of these constitutes "the natural ordering of this type," but is merely a one-off need of the caller, which `Comparator` expresses as an independent strategy object that can be swapped out at any time, without intruding into the class definition).

The example below uses two pieces of syntax you may not have seen: `record` is Java 16+ shorthand that declares in one line an immutable class holding only data (analogous to a C++ `struct` that has only fields with auto-generated constructor and getters); `Person::name` is a **method reference**, shorthand for `p -> p.name()`, which you can just read as "a lambda that takes the name field."

```java
record Person(String name, int age) implements Comparable<Person> {
    @Override public int compareTo(Person o) {   // natural ordering: by age
        return Integer.compare(this.age, o.age);  // don't use this.age-o.age, overflow risk
    }
}

// Comparator combinators (JDK8+), declarative, like a chained SQL ORDER BY
Comparator<Person> cmp = Comparator
    .comparing(Person::name)                     // first by name
    .thenComparingInt(Person::age)               // if names are equal, then by age
    .reversed();                                 // reverse the whole thing

Comparator<Person> byAgeNullsFirst = Comparator
    .comparingInt(Person::age)
    .reversed();
List<Person> people = new ArrayList<>();
people.sort(cmp);   // List.sort internally goes through TimSort
```

Contract: `compare` must be reflexive, transitive, and antisymmetric; and consistency with `equals` is recommended (otherwise `TreeMap`/`TreeSet` behavior is counterintuitive). Violating transitivity makes TimSort throw `IllegalArgumentException: Comparison method violates its general contract` — this is not an arbitrarily added check but is because the correctness proof of merge sort itself depends on the comparison relation satisfying transitivity (the algorithm assumes "knowing A ≤ B and B ≤ C lets you deduce A ≤ C," without needing to compare A and C again); once this premise fails, the algorithm's internal consistency detection discovers the contradiction and actively reports an error, rather than silently outputting a wrong but non-crashing sort result.

Runnable: sort by `name` ascending first, and when `name` is the same, by `age` descending — `thenComparing` + `reversed` declarative composition:

```java
import java.util.*;

public class CmpDemo {
    record Person(String name, int age) {}

    public static void main(String[] args) {
        List<Person> people = new ArrayList<>(List.of(
            new Person("Bob", 30), new Person("Ann", 30),
            new Person("Bob", 25), new Person("Ann", 20)));

        // sort by name ascending; when name is the same, by age descending
        people.sort(Comparator.comparing(Person::name)
                              .thenComparing(Comparator.comparingInt(Person::age).reversed()));

        for (Person p : people) System.out.println(p.name() + " " + p.age());
    }
}
// Ann 30
// Ann 20
// Bob 30
// Bob 25
```

## 4. PriorityQueue: The Binary Heap

`PriorityQueue` is an **array-based min binary heap** (by default the smallest element is at the front), analogous to C++'s `priority_queue` (which defaults to a max-heap).

```java
PriorityQueue<Integer> pq = new PriorityQueue<>();      // min-heap
pq.offer(3); pq.offer(1); pq.offer(2);
pq.peek();     // 1, peek at the heap top O(1)
pq.poll();     // 1, pop and sift down to adjust O(log n)

// max-heap / custom
PriorityQueue<Integer> maxHeap = new PriorityQueue<>(Comparator.reverseOrder());
```

**Why use a heap rather than a sorted array or a balanced tree**: the only problem a heap solves is "repeatedly take the extremum, repeatedly insert"; it doesn't need the two capabilities of "arbitrary-position lookup" or "complete in-order traversal," and this narrower requirement lets it be cheaper than a general-purpose ordered structure. A sorted array can take the extremum in O(1), but inserting a new element requires shifting data, O(n); a red-black tree (`TreeMap`/`TreeSet`) does both insertion and extremum-taking in O(log n), which looks the same as a heap, but a red-black tree must maintain the stronger invariant of "the relative order between any two elements" (in order to support in-order traversal yielding a total order and to support floor/ceiling queries for any key), whereas the heap abandons this invariant and maintains only the much weaker property "parent node ≤ child node" (without requiring order between sibling nodes), gaining in exchange that insertion/deletion only needs to sift up or down along a single path, without the recoloring and rotation maintenance of a red-black tree, with a smaller constant factor and a simpler implementation. This is a direct example of "the more specific the requirement, the cheaper the structure that can satisfy it" — if you need complete ordering or arbitrary lookup, you should use `TreeMap`; if you only need to repeatedly take the extremum, choose a heap.

Internally an `Object[] queue`, with the parent-child index relation: the children of node `i` are `2i+1` and `2i+2` (using array-subscript arithmetic to simulate tree pointers, saving the space of storing left/right child pointers in each node, and also laying the nodes out contiguously in memory, which is cache-friendly). `offer` sifts up (siftUp), and `poll` moves the last element to the heap top and sifts it down (siftDown).

```
The heap represented by the array [1,3,2,7,4]:
          1(0)
        /     \
      3(1)     2(2)
      /  \
    7(3) 4(4)
```

**Not thread-safe**, and it also **doesn't guarantee ordered traversal** (only the heap top is ordered — this is the direct consequence of the weak invariant mentioned above, "abandoning the order between any two elements"); to traverse in order you must repeatedly `poll`. For concurrent scenarios use `PriorityBlockingQueue`.

Runnable: use a **min-heap** of size k to find the Top-K largest values — the heap top is exactly the smallest of these k, and anything exceeding it is popped, a single operation being `O(log k)`. This exactly exploits the heap's property of "only needing to know the extremum, not to maintain the overall order," and is cheaper than sorting all the data (O(n log n)):

```java
import java.util.*;

public class HeapTopK {
    public static void main(String[] args) {
        int[] data = {5, 1, 9, 3, 7, 8, 2, 6, 4};
        int k = 3;

        // maintain the k largest values: the top of the min-heap = the smallest among the current top-k
        PriorityQueue<Integer> pq = new PriorityQueue<>();  // min-heap
        for (int x : data) {
            pq.offer(x);
            if (pq.size() > k) pq.poll();                   // pop the smallest, O(log k)
        }

        // poll one by one: a min-heap dequeues in ascending order
        List<Integer> topK = new ArrayList<>();
        while (!pq.isEmpty()) topK.add(pq.poll());
        System.out.println("top-" + k + " ascending = " + topK);
    }
}
// top-3 ascending = [7, 8, 9]
```

## 5. TreeMap / TreeSet: The Red-Black Tree

`TreeMap` is underpinned by a **red-black tree** (a self-balancing BST), and `TreeSet` is its wrapper (the value acts as the key). They correspond to C++'s `std::map`/`std::set`. All operations are O(log n), and they are **ordered by key**.

```java
TreeMap<String, Integer> tm = new TreeMap<>();
tm.put("banana", 2); tm.put("apple", 1); tm.put("cherry", 3);
// ordered views and navigation methods (HashMap doesn't have these)
tm.firstKey();               // "apple"
tm.floorKey("b");            // "apple" (the largest key ≤ "b")
tm.ceilingKey("b");          // "banana" (the smallest key ≥ "b")
tm.headMap("cherry");        // subview of keys less than cherry (a view; changes are reflected back into the original map)
tm.subMap("apple", "cherry");
for (var e : tm.entrySet()) { }  // traverse in ascending key order
```

The five properties of a red-black tree (nodes red/black, root black, children of a red node are black, the black height from any node to its leaves is the same, etc.) guarantee that the longest path ≤ 2× the shortest, approximately balanced without requiring strict balance. **Why choose a red-black tree rather than a more strictly balanced AVL tree**: an AVL tree requires that the height difference between the left and right subtrees of any node be ≤ 1, giving shorter lookup paths and faster lookups, but after an insertion or deletion, maintaining this stricter constraint requires on average more rotations to restore balance; a red-black tree relaxes the constraint (allowing the longest path to reach twice the shortest path), gaining in exchange a lower upper bound on the number of rotations for insertion/deletion (at most two rotations for insertion, at most three for deletion). As a general-purpose associative container, `TreeMap` sees both insertion/deletion and lookup commonly, and the red-black tree, at the compromise point of "lookup is slightly slower but insertion/deletion is cheaper," fits general-purpose scenarios better — this is also the shared reason C++'s `std::map`, the Linux kernel scheduler, and many others choose red-black trees over AVL. Insertion/deletion maintains balance via recoloring + rotation, with each adjustment being O(log n).

| Comparison | HashMap | TreeMap |
|------|---------|---------|
| Underlying | array + linked list/red-black tree | red-black tree |
| Ordered | Unordered | Ordered by key |
| get/put | O(1) amortized | O(log n) |
| Navigation methods | None | floor/ceiling/subMap etc. |
| null key | Allows one | Not allowed (needs comparison) |

`HashMap` trades away ordering for O(1); `TreeMap` trades an O(log n) factor to get back ordering and navigation capability — which one to choose depends on "whether you need to sort by key or do range queries," and if you don't, use the faster `HashMap`, and if you do, pay the log factor in exchange for `TreeMap`'s navigation methods.

## 6. The Stream API

The simplest usage: filter a `List` first, then count:

```java
List<String> names = List.of("Ann", "Bob", "Al", "Ben");
long count = names.stream()               // 1. open a "pipeline" from the collection
    .filter(s -> s.startsWith("A"))        // 2. keep only the elements that meet the condition
    .count();                              // 3. count how many are left
System.out.println(count);                 // 2
```

`collection.stream()` opens the pipeline, in the middle you can chain any number of "processing steps" (here `filter`), and at the end a "result-taking operation" (here `count`) ends the whole chain — this three-part structure of source, intermediate operations, and terminal operation is not an arbitrary API-style choice; below we explain what problem it specifically solves.

A Stream is a **declarative, lazy, parallelizable** data-processing pipeline, analogous to C++20 ranges/views. It is not a container, it stores no data, it is "a description of operations on a data source."

### Laziness and Operation Classification

```java
List<String> words = List.of("apple", "banana", "cherry", "avocado");

long count = words.stream()          // source
    .filter(s -> s.startsWith("a"))  // intermediate operation: lazy, returns a new Stream
    .map(String::toUpperCase)        // intermediate operation
    .peek(System.out::println)       // intermediate operation (for debugging)
    .count();                        // terminal operation: triggers actual execution
```

- **Intermediate operations** (`filter`/`map`/`sorted`/`distinct`/`limit`): lazy, they only record and don't execute. They return a Stream and can be chained.
- **Terminal operations** (`collect`/`forEach`/`count`/`reduce`/`findFirst`): trigger the traversal and execute the whole chain.

**Why split into these two kinds of "lazy intermediate operations" and "eager terminal operations" rather than having every operation execute immediately**: if operations like `filter` and `map` all evaluated immediately, each step would have to produce a complete intermediate collection to hand to the next step — `filter` first collects the elements meeting the condition into a new `List`, then hands it to `map` which generates a second new `List`, then hands it to the next operation... an n-step chained operation would allocate n intermediate collections, each of them O(number of elements) in memory and one full traversal. As the chain gets longer or the data gets larger, the overhead of memory allocation and multiple passes accumulates linearly.

Stream's design flips this around: an intermediate operation merely records "what to do" as a function and doesn't actually traverse the data, until a terminal operation is called, at which point the data is driven **one element at a time** through the whole chain — the same element passes through the `filter` check, `map` transformation, and `peek` print in turn within the same "visit," then the next element is taken and repeats, so the whole chain does **one traversal** of the data source and doesn't need to allocate a collection for any intermediate step (operations such as sorted/distinct that need to see all the data before they can decide are exceptions, and such operations must buffer themselves). This is precisely "operation fusion": multiple logical steps are, at execution time, merged into a series of function calls within one traversal, rather than n traversals + n allocations.

Laziness also brings another direct benefit: **short-circuiting**. Operations like `limit`/`findFirst` can, once they've obtained the result they need, let the whole pipeline stop early without processing the entire data source — if operations were eagerly evaluated, `filter` would already have computed all the elements meeting the condition and put them into a collection, and even if `findFirst` only wants the first one, it would already be too late.

```java
// short-circuit: stop as soon as the first one is found, won't process the whole stream
Optional<Integer> first = Stream.iterate(1, n -> n + 1)  // infinite stream
    .filter(n -> n % 7 == 0)
    .findFirst();   // Optional[7]
```

This example pushes the necessity of laziness to an extreme: the data source is an infinite stream, and if `filter` tried to evaluate eagerly, the program would never terminate — only this laziness mechanism of "do nothing until a terminal operation explicitly demands some result" makes the very act of "making a finite number of queries against an infinite sequence" feasible.

### Collectors

The terminal operation `collect` collects the stream into a result:

```java
import static java.util.stream.Collectors.*;

List<String> list  = words.stream().collect(toList());
Set<String> set    = words.stream().collect(toSet());
Map<Character, List<String>> byFirst =
    words.stream().collect(groupingBy(s -> s.charAt(0)));   // group, like SQL GROUP BY
Map<Boolean, List<String>> parts =
    words.stream().collect(partitioningBy(s -> s.length() > 5));
String joined = words.stream().collect(joining(", ", "[", "]"));
Double avg = words.stream().collect(averagingInt(String::length));
```

**Why does `collect` take a `Collector` object rather than opening a pile of overloaded methods directly on the `Stream` interface like `toList()`/`toSet()`/`groupingBy()`**: `Collector<T,A,R>` essentially packages "how to reduce" into three functions (`supplier` creates a mutable intermediate container, `accumulator` merges one element into the container, `combiner` merges two containers produced by parallel processing into one) plus a finishing step (`finisher`). If we switched to method overloading, the combinations of `toList`, `toSet`, `toMap` (with an overload taking a merge function), and `groupingBy` (which can nest to specify a downstream collector for "how to collect after grouping") would quickly explode into dozens of overloads with similar signatures but different semantics, and there would be no way for the overloaded methods to compose with one another — whereas a `Collector` is a value that can be passed as an argument and can be nested (`groupingBy(classifier, downstream Collector)` is exactly making one `Collector` part of another `Collector`), and `collectingAndThen` can wrap another layer of post-processing around an arbitrary collector. This is the design of "encapsulating behavior as composable objects" rather than "enumerating all combinations as method names" — the number of combinations is the product of several orthogonal dimensions, and after encapsulating them as objects you only need to write one function per dimension, whereas the overloading approach would require writing one method per combination.

The significance of the `combiner` (merging two intermediate containers) doesn't stop there: it is the precondition for parallel streams to work — the data is split into several chunks, each chunk runs `supplier`+`accumulator` on its own to produce a local result, and finally the `combiner` merges these local results pairwise into one. Method overloading has no natural place to put this "merge" step, whereas the `Collector` interface makes it a first-class citizen, so the same `Collector` can support both serial and parallel streams without writing a separate set for the parallel scenario.

Runnable: `peek` observes laziness — `findFirst` short-circuits and stops once it pulls the first match, without traversing the whole stream; `groupingBy` groups by first letter:

```java
import java.util.*;
import java.util.stream.*;
import static java.util.stream.Collectors.*;

public class StreamDemo {
    public static void main(String[] args) {
        List<String> words = List.of("apple", "banana", "cherry", "avocado", "blueberry");

        // lazy + short-circuit: peek only prints the elements that are actually pulled
        System.out.println("--- lazy pipeline (findFirst short-circuits) ---");
        Optional<String> first = words.stream()
            .peek(w -> System.out.println("seen: " + w))   // side effect, used to observe the traversal
            .filter(w -> w.startsWith("b"))
            .findFirst();
        System.out.println("first b-word = " + first.get());

        // groupingBy: group by first letter, using a TreeMap to make the output ordered and stable
        Map<Character, List<String>> byFirst = words.stream()
            .collect(groupingBy(w -> w.charAt(0), TreeMap::new, toList()));
        System.out.println("--- groupingBy ---");
        System.out.println(byFirst);
    }
}
// --- lazy pipeline (findFirst short-circuits) ---
// seen: apple
// seen: banana
// first b-word = banana
// --- groupingBy ---
// {a=[apple, avocado], b=[banana, blueberry], c=[cherry]}
```

The output confirms laziness: `peek` prints only up to `banana` and then stops (`findFirst` short-circuits), and `cherry`, `avocado`, `blueberry` are never accessed at all — if the stream were eagerly evaluated, `filter` would first scan the whole list, and `peek` should print all 5 elements.

### Parallel Streams

`parallelStream()` or `.parallel()` splits the stream and, underneath, uses the **common ForkJoinPool** (`ForkJoinPool.commonPool()`, with a default thread count = number of CPU cores - 1) to process it in a divide-and-conquer manner. ForkJoinPool is chosen over an ordinary thread pool because it uses **work-stealing** scheduling: each worker thread has its own double-ended task queue, and after finishing its own tasks it goes to "steal" tasks from the tail of other threads' queues, without needing a central scheduler to coordinate, which is naturally suited to the divide-and-conquer scenario of "a big task recursively split into a large number of uneven subtasks."

```java
long sum = LongStream.rangeClosed(1, 1_000_000)
    .parallel()
    .sum();
```

Caveats:
- The data source must be **easy to split** (arrays and `ArrayList` are good, supporting fast binary division by index; `LinkedList` is bad, splitting itself requires traversal, cancelling out the parallelism gain).
- Operations must be **stateless and side-effect-free**, otherwise there are data races (don't modify shared variables inside a lambda).
- For small datasets or cheap operations, the splitting/merging/scheduling overhead of parallelism may not pay off — the gain of a parallel stream is only worthwhile when "per-element processing cost × number of elements" is significantly greater than the fixed overhead of "split + schedule + merge."
- All parallel streams share the same commonPool, and one slow task (especially blocking IO) will hold threads and drag down all the other parallel-stream tasks globally; don't use it for IO-intensive scenarios.

## 7. Optional

`Optional<T>` expresses "there may be no value," replacing a bare `null` and forcing the caller to handle absence, reducing NPEs. Analogous to C++17's `std::optional` (but Java's is an object, with heap-allocation overhead).

The specific problem `Optional` solves compared to "returning a T that may be `null`" is: `null` is indistinguishable in the type signature from a normal value (`String getName()` may return a name or may silently return `null`, and the caller can't tell from the signature and can only rely on documentation or experience), and once the caller forgets a null check it's a runtime NPE, and often one that blows up far from where "actually missing a value" occurred. `Optional<String>` writes the fact "there may be no value" into the method signature itself, forcing the caller either to explicitly handle the "empty" branch (`orElse`/`map`/`ifPresent`) or to explicitly choose `get()`/`orElseThrow()` and bear the risk — turning "there may be no value here" from an easily overlooked implicit convention into type information the compiler can see.

The most basic usage: `Optional.of` wraps a value that definitely exists, `Optional.empty()` indicates there definitely is no value, and `isPresent()` tells which case it is:

```java
Optional<String> opt1 = Optional.of("hello");   // definitely has a value
Optional<String> opt2 = Optional.empty();       // definitely has no value
System.out.println(opt1.isPresent());           // true
System.out.println(opt2.isPresent());           // false
```

In actual code, it's more common to use `Optional.ofNullable` to wrap a "value that may be null" (such as the return value of a method that may not find a result), then combine it with the methods below to handle the "present" or "absent" cases without having to explicitly write `if (x != null)`:

```java
Optional<String> opt = Optional.ofNullable(getName());
String s = opt.orElse("default");             // give a default when there's no value
String t = opt.orElseGet(() -> compute());    // lazy default (computed only when there's no value)
opt.ifPresent(System.out::println);
String u = opt.map(String::trim).filter(x -> !x.isEmpty()).orElse("-");
opt.orElseThrow(() -> new IllegalStateException("missing"));
```

Usage convention: use it mainly as a **method return value** to express "there may be no result"; **don't** use it for fields, method parameters, or collection elements — in these scenarios `Optional` itself also takes a heap allocation, and whether a field/parameter can be null is usually expressed by other means (documentation, a `@Nullable` annotation, a direct null check), so wrapping them in an `Optional` merely adds an extra object allocation and a layer of unwrapping without buying any extra clarity in the signature.

## 8. Numeric Utilities

For everyday use, do basic arithmetic with the static methods of `Math`; when the precision or range of `int`/`long`/`double` is not enough (for example, needing an integer beyond 64 bits, or financial calculations that can't have floating-point error), then use `BigInteger`/`BigDecimal`.

```java
Math.max(a, b); Math.floorMod(-1, 3); // 2 (differs from %, the result's sign follows the divisor and is always non-negative)
Math.addExact(a, b);                  // throws ArithmeticException on overflow, rather than silently wrapping around

// BigInteger: arbitrary-precision integer (immutable), analogous to a big-number implementation of your own; operations return new objects
BigInteger big = BigInteger.valueOf(2).pow(1000);
BigInteger f = big.multiply(BigInteger.TEN).mod(BigInteger.valueOf(7));

// BigDecimal: exact decimal, a must for finance (double can't exactly represent 0.1)
BigDecimal price = new BigDecimal("0.10");    // must construct from String; new BigDecimal(0.1) would carry binary error
BigDecimal total = price.multiply(new BigDecimal("3"));  // exactly 0.30
System.out.println(new BigDecimal("0.1").add(new BigDecimal("0.2"))); // 0.3 (double would be 0.30000000000000004)
total = total.setScale(2, RoundingMode.HALF_UP);         // explicitly specify rounding
```

`BigDecimal` must be constructed from a string rather than a `double` literal, and the reason lies in the representation of floating-point numbers themselves: `double` is a binary floating-point number, and a decimal fraction like `0.1` is an infinitely repeating fraction in binary and can only be approximated — `new BigDecimal(0.1)` gets not the mathematical 0.1 but the binary fraction that this `double` approximation itself precisely corresponds to (expanding into a long string of nonzero digits), and `BigDecimal` merely faithfully presents this already-existing error without introducing new error. Constructing from a string, on the other hand, parses precisely by decimal directly, avoiding the step of "first converting to a lossy binary floating-point number, then converting back."

```java
// Random: linear-congruential pseudorandom; for concurrency use ThreadLocalRandom; for security scenarios use SecureRandom
int r = ThreadLocalRandom.current().nextInt(0, 100);
```

> `BigInteger`/`BigDecimal` are immutable, and frequent operations produce a large number of temporary objects, so watch out for GC pressure in loops. They are compared with `compareTo`, and `BigDecimal`'s `equals` also compares the scale (`2.0` != `2.00`), so use `compareTo == 0` to judge numeric equality.

## Summary

- **Usage**:
  - `Collections` is a set of static methods that operate on `List`/`Collection`: `sort`/`binarySearch`/`reverse`/`shuffle`/`max`; for an unmodifiable view use `unmodifiableXxx` (wraps the original collection) or `List.of` (a genuinely immutable copy).
  - `Arrays.sort` is called the same way for a primitive array and an object array, and it automatically selects the algorithm internally.
  - To sort objects: the class implements `Comparable` itself (only one natural ordering), or you pass in an external `Comparator` (of which there can be any number), and in JDK8+ use `Comparator.comparing().thenComparing().reversed()` for declarative composition.
  - `PriorityQueue` is a heap, a min-heap by default, and `offer`/`peek`/`poll` add/remove/inspect the heap top.
  - `TreeMap`/`TreeSet` are naturally ordered by key and add navigation methods that `HashMap` doesn't have, such as `firstKey`/`floorKey`/`ceilingKey`/`headMap`/`subMap`.
  - The skeleton of a Stream is "source `.stream()` → several intermediate operations (`filter`/`map`/`sorted`) → one terminal operation (`collect`/`count`/`forEach`)"; `collect` combined with `Collectors` does grouping, partitioning, joining, and statistics.
  - `Optional<T>` is used to express "there may be no value," used mainly as a method return value, combined with `orElse`/`map`/`ifPresent` for handling, and not used on fields or parameters.
  - For values beyond the range of `long` use `BigInteger`, and for exact decimals (financial scenarios) use `BigDecimal` — `BigDecimal` must be constructed from a string, and to compare numeric equality use `compareTo == 0` rather than `equals`.
- **Principles**:
  - `Arrays.sort`: primitive types use **dual-pivot quicksort** (equal values are inherently indistinguishable, so stability is meaningless; in-place, cache-friendly); objects use **TimSort** (a merge+insertion hybrid that recognizes already-sorted runs, guarantees stability, is worst-case O(n log n) and O(n) on already-sorted data, and needs O(n) auxiliary space) — the two choices correspond respectively to the two utterly different cost structures of "comparison is cheap, memory access dominates" and "comparison is expensive, stability is a hard requirement."
  - The contract of `Comparator`/`Comparable` requires reflexivity, transitivity, and antisymmetry, and violating transitivity makes TimSort throw `IllegalArgumentException` outright, because the correctness proof of merge sort itself depends on the transitivity of the comparison relation.
  - `PriorityQueue` is underpinned by an **array-represented binary heap** (the children of node `i` are `2i+1`/`2i+2`), maintaining only the weak invariant "parent ≤ child," maintaining less information and a smaller constant than a red-black tree, suited to the scenario of "only needing to repeatedly take the extremum"; `offer` sifts up, `poll` sifts down, both O(log n), and it is not thread-safe.
  - `TreeMap` is underpinned by a **red-black tree**, relying on properties like "root black, children of a red node must be black, the black height of any path is the same" to guarantee approximate balance (rather than the strict balance of an AVL), trading a slightly longer lookup path for fewer rotations on insertion/deletion, with all operations O(log n).
  - Stream's intermediate operations are all **lazy** and don't actually execute until a terminal operation: this avoids allocating an intermediate collection at every step (operations can be fused into one traversal), and enables **short-circuiting** (`limit`/`findFirst` end early, which is also the precondition for handling infinite streams); a `Collector` is designed as an object packaging the four functions "supply–accumulate–combine–finish" rather than method overloads, so that grouping and collection strategies can be arbitrarily composed and nested, while naturally supporting the local-result merging of parallel streams. Parallel streams rely on the work-stealing scheduling of the common `ForkJoinPool` for divide-and-conquer, and require the data source to be easy to split and the operations to be stateless and side-effect-free.
  - `BigInteger`/`BigDecimal` are both **immutable** objects, and each operation generates a new object, so watch out for GC pressure with heavy use in loops; `BigDecimal` must be constructed from a string because it needs to avoid the lossy step of a decimal fraction first passing through `double`'s binary approximation.
