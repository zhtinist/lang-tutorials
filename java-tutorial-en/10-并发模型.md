# Concurrency Model

In C/C++, concurrency relies on `std::thread`, `pthread`, atomic types, and manually controlled `memory_order`; the programmer must decide, at every access to a shared variable, which memory ordering to use. Java abstracts this whole stack into the **JMM (Java Memory Model)** and `java.util.concurrent`: the language specification uniformly defines "what read/write orderings are safe under multithreading," and the utility classes package common concurrency patterns (locks, counters, thread pools, asynchronous orchestration) into components you can call directly.

## 1. Thread creation and lifecycle

For the "task" a thread is to run, Java has three ways to write it:

```java
// 1. Extend Thread (not recommended: the single-inheritance slot is used up, and the task is tightly coupled to the thread)
class MyThread extends Thread {
    @Override public void run() { System.out.println("run in " + getName()); }
}

// 2. Runnable: no return value, no checked exceptions, the most commonly used
Runnable r = () -> System.out.println("runnable");

// 3. Callable<V>: has a return value V, may throw checked exceptions, used together with Future (see the java.util.concurrent section)
Callable<Integer> c = () -> 42;

public class ThreadDemo {
    public static void main(String[] args) throws Exception {
        Thread t1 = new MyThread();
        t1.start();            // start() makes the JVM spin up a new thread to run run()
        Thread t2 = new Thread(r);
        t2.start();
        t1.join();             // the current thread blocks until t1 terminates, like pthread_join
        t2.join();
    }
}
// which of the two threads prints first is unspecified, but join() guarantees main waits for both to finish before ending
```

`start()` makes the JVM create a new thread and asynchronously call back into `run()`; if you call `run()` directly, that is just an ordinary method call, the code executes **synchronously** in the current thread, and no new thread is started at all. A `Thread` object can be `start()`-ed only once; calling it a second time throws `IllegalThreadStateException`.

Java's `Thread` on HotSpot defaults to a **1:1 mapping to a kernel thread** (OS thread), just as heavy as C++'s `std::thread`. Calling `start()` triggers a `pthread_create`, and each thread is allocated about 1MB of stack space by default (adjustable with `-Xss`). The system-level cost of `new Thread(...).start()` is the same order of magnitude as hand-writing `pthread_create` in C—a thread is not a free resource, and this is the starting point for the fundamental problem that "virtual threads" at the end of this chapter set out to solve.

The six states of `Thread.State` do not map one-to-one to the OS's thread states:

```
    NEW --start()--> RUNNABLE <----+
                      |  ^          | notify / timeout / lock acquired
    fails to acquire  |  |          |
    lock on entering  |  |          |
    a sync block      v  |          |
                   BLOCKED          |
    wait()/park()   |               |
                      v             |
    WAITING / TIMED_WAITING --------+
                      |
                   TERMINATED (run returns)
```

- `RUNNABLE` covers both "currently running on a CPU" and "ready and waiting to be scheduled"; Java does not distinguish them (only the OS does).
- `BLOCKED`: waiting for a `synchronized` monitor lock.
- `WAITING`: `Object.wait()`, `Thread.join()`, `LockSupport.park()`—waiting indefinitely.
- `TIMED_WAITING`: the above calls with a timeout, and `Thread.sleep(ms)`.

Two threads modifying the same variable at once goes wrong; let's look first at a concrete consequence, then explain the root cause:

```java
public class SimpleSyncDemo {
    static int counter = 0;

    static synchronized void increment() {   // a synchronized method: only one thread can execute it at a time
        counter++;
    }

    public static void main(String[] args) throws InterruptedException {
        Runnable job = () -> {
            for (int i = 0; i < 100_000; i++) increment();
        };
        Thread t1 = new Thread(job);
        Thread t2 = new Thread(job);
        t1.start();
        t2.start();
        t1.join();
        t2.join();
        System.out.println("counter = " + counter); // 200000, the same on every run
    }
}
// counter = 200000
```

Each of the two threads adds to `counter` 100,000 times; with `synchronized` added, the result is always exactly 200,000. Remove `synchronized`, and `counter++` itself is three steps—"read, increment, write back"—and these three steps of the two threads may interleave, so the result will nondeterministically be less than 200,000. The mechanism behind this is the subject of the next several sections.

### The four creation approaches compared in practice

The three forms above only address "how to define the task"; in real projects there is a fourth, more common way to put it into practice—handing the task to a thread pool. Running all four in one piece of code makes the behavioral differences more intuitive than looking at the syntax alone (verified in practice with `javac`/`java` on JDK 25):

```java
import java.util.concurrent.*;

public class ThreadCreateDemo {
    static class MyThread extends Thread {                 // 1. extend Thread
        @Override public void run() { System.out.println("[extends Thread] running"); }
    }
    static class MyRunnable implements Runnable {           // 2. implement Runnable
        @Override public void run() { System.out.println("[implements Runnable] running"); }
    }
    static class MyCallable implements Callable<Integer> {  // 3. implement Callable, with a return value
        @Override public Integer call() { return 42; }
    }

    public static void main(String[] args) throws Exception {
        Thread t1 = new MyThread();
        t1.start(); t1.join();

        Thread t2 = new Thread(new MyRunnable());
        t2.start(); t2.join();

        // FutureTask implements both Runnable and Future<V>; it is the bridge between Callable and Thread
        FutureTask<Integer> futureTask = new FutureTask<>(new MyCallable());
        new Thread(futureTask).start();
        System.out.println("[Callable+FutureTask] result = " + futureTask.get()); // blocks until call() finishes

        // 4. Thread pool: the task definition is unchanged, only the way it is delivered for execution differs
        ExecutorService pool = Executors.newSingleThreadExecutor();
        Future<Integer> future = pool.submit(new MyCallable());
        System.out.println("[thread pool] result = " + future.get());
        pool.shutdown();
    }
}
// [extends Thread] running
// [implements Runnable] running
// [Callable+FutureTask] result = 42
// [thread pool] result = 42
```

| Creation approach | Has a return value? | Can declare checked exceptions? | Uses up the single-inheritance slot? | Typical scenario |
|---|---|---|---|---|
| Extend Thread | No | No (the `run()` signature does not allow `throws`) | Yes | Extremely simple, one-off tasks; rarely used |
| Implement Runnable | No | No | No | The most general form; decouples task from thread |
| Implement Callable + FutureTask | Yes (generic `V`) | Yes (`call()` declares `throws Exception`) | No | Tasks whose result or exception you need to obtain |
| Submit to a thread pool | `submit` returns a `Future` | Depends on Runnable/Callable | No | The default choice in production; see the "Thread pool" section below |

**Why "implement an interface" is recommended more often than "extend Thread"**: the reason is not merely the surface syntactic constraint of "Java's single inheritance," but more fundamentally a separation of concerns: `Thread` is the OS-level concept of "a thread of execution," while `Runnable`/`Callable` is the business-level concept of "the task to be done." Extending `Thread` hard-binds the two together, so the task logic cannot be passed, reused, or dropped into a thread pool independently of `Thread`; implementing `Runnable`/`Callable` lets the same task object be both `new Thread(task)` and submitted as-is to a thread pool without changing any code. `Callable` has two things `Runnable` lacks—"a return value + checked exceptions"—because the signature of `Runnable.run()` was fixed as `void run()` (without `throws`) back in JDK 1.0, whereas `Callable<V>` is an interface added together with `java.util.concurrent` in JDK 5, designed specifically for tasks that need to propagate results and exceptions; `FutureTask` wraps a `Callable` into a `Runnable`, so it can be dropped straight into `new Thread(futureTask).start()`, and you can also obtain `call()`'s return value via `futureTask.get()`—it is the bridge connecting the two worlds of "a task has a return value" and "Thread only understands Runnable."

## 2. The Java Memory Model (JMM)

The JMM is a **specification** (Chapter 17 of the JLS), not a direct description of some particular hardware behavior. It defines, when multiple threads read and write shared variables, what values are legally visible.

**Why a formal specification is needed, rather than letting everyone judge by intuition that "it looks right so it's fine"**: intuition is built on the single-threaded model of sequential execution—"code executes top to bottom, and once a variable is assigned it can be seen." But for a single-threaded program, the compiler and CPU guarantee only **as-if-serial** (the reordered result is consistent with the sequential-execution result), and the scope of this guarantee is limited to "this one thread observing itself." Across threads, one thread's reordered, cached, or delayed-write-back operations may become visible to another thread at any arbitrary moment, and as-if-serial places no constraint whatsoever on this cross-thread visibility—this is space left for hardware and compilers to optimize freely, not an oversight of theirs. Concurrent code written by intuition may "happen" to run correctly every time on x86 (where memory ordering is relatively strong), but may break on ARM (where memory ordering is far weaker and reordering more aggressive) or under a JIT version that inlines/reorders more aggressively—this kind of bug that "runs on your machine" and cannot be stably reproduced by ordinary testing can only be prevented in advance by a specification that precisely states "which orderings are guaranteed and which are not"; testing alone cannot falsify "this code is correct on all platforms." This is exactly the reason the JMM (JSR-133, 2004) exists: before 2004 Java's memory-model definition was internally contradictory (allowing some counterintuitive reorderings that even the spec authors thought should not happen), and the work of JSR-133 was to re-formalize "what may be reordered and what may not," so that compiler implementers and application developers work against the same contract rather than each relying on their own experience.

The JMM abstracts as follows: each thread has a **working memory**, and shared variables live in **main memory**. To operate on a variable, a thread must first copy it from main memory into its working memory, and after modifying it, write it back.

```
   +----------------+        +----------------+
   |   Thread A      |        |   Thread B      |
   | working memory  |        | working memory  |
   | [x=0 copy]      |        | [x=0 copy]      |
   +-------+--------+        +--------+-------+
           |  read/write             |
           v                         v
   +-------------------------------------------+
   |            main memory  x = 0              |
   +-------------------------------------------+
```

This is an **abstract model** and does not represent the real memory layout—in reality "working memory" corresponds to CPU registers, the store buffer, and the various levels of cache; the JMM deliberately does not bind to any concrete hardware implementation, specifying only the observable behavioral contract, so that the specification can constrain, at the same time, hardware with entirely different memory orderings such as x86 and ARM. The core problem: after thread A modifies `x`, thread B does not necessarily see it immediately—the root cause is the objective existence of the cache layer, plus the fact that compilers/CPUs reorder instructions for performance.

The JMM defines three properties that must each be guaranteed separately; note that they are three **different** things, with different causes and different tools to solve them, which is also the direct basis for the later division of labor among `volatile`/`synchronized`/`Atomic`:

| Property | Meaning | Consequence when not guaranteed | Guaranteed by |
|------|------|----------------|-----------|
| Atomicity | The operation is indivisible and cannot have another thread's operation inserted into an intermediate state | A compound operation (e.g. `count++`) is executed interleaved, losing updates | Basic reads/writes (except long/double) are naturally atomic; compound operations need synchronized/CAS |
| Visibility | One thread's write can be read by another thread | One thread writes a new value, another thread reads the old value forever (even spinning in an infinite loop) | volatile, synchronized, final |
| Ordering | Instructions are not reordered in a way that breaks cross-thread observable semantics | Two order-dependent steps are reordered, and another thread sees "the effect before the cause" | volatile, synchronized, happens-before |

The reason the three are independent is straightforward: visibility solves "after a write, can others see it" (a caching problem); ordering solves "can the order of writes be scrambled" (a reordering problem); atomicity solves "can one logical operation be split into several steps whose intermediate state other threads can see" (an operation-granularity problem)—the three problems have different causes, so naturally no single tool can solve all three at the lowest cost simultaneously. This is why the Java concurrency toolbox is not one "universal lock" but is layered: `volatile` solves only visibility and ordering, while `synchronized`/`Atomic` are what solve atomicity (detailed below).

> The `long`/`double` pitfall: the JMM guarantees atomicity only for 32-bit reads and writes; a 64-bit variable may be split into two writes on a 32-bit platform, causing a read of "half a value" (a mismatched combination where the high 32 bits are the new value and the low 32 bits are the old value). Adding `volatile` guarantees the 64-bit read/write is atomic as a whole. HotSpot on mainstream 64-bit JVMs actually treats these atomically in practice, but the specification itself does not make this guarantee, and portable code must not depend on this coincidence of a specific implementation.

## 3. happens-before

The JMM does not require you to reason about implementation details like "when the cache is flushed" or "how instructions are reordered"; instead it provides a higher-level contract: **happens-before**. If operation A happens-before operation B, then A's result is visible to B, and A is semantically ordered before B—this is a contract you can use directly to reason about program correctness, without understanding the CPU cache-coherence protocol. The rules:

1. **Program order**: within the same thread, an earlier operation happens-before a later one.
2. **Monitor lock**: an `unlock` on a lock happens-before a subsequent `lock` on the same lock.
3. **volatile**: a write to a volatile variable happens-before a subsequent read of it.
4. **Transitivity**: A hb B, B hb C ⇒ A hb C.
5. **Thread start**: `t.start()` happens-before any operation within the thread.
6. **Thread termination**: operations within a thread happen-before the return of another thread's `t.join()`.

```java
int a = 0;
volatile boolean flag = false;

// Thread 1
a = 1;              // (1)
flag = true;        // (2) volatile write

// Thread 2
if (flag) {         // (3) volatile read; if it reads true, then (2) hb (3)
    System.out.println(a); // necessarily 1: (1)hb(2)hb(3), by transitivity ⇒ (1)hb(4)
}
```

Without `volatile`, the write to `a` may not be visible to thread 2, or (1)(2) may be reordered, causing thread 2 to see `flag == true` but `a == 0`.

## 4. Instruction reordering and double-checked locking

Compilers and CPUs reorder instructions for performance, on the sole premise that **single-threaded semantics (as-if-serial) are unchanged**—a premise that no longer holds under multithreading, making it one of the most insidious sources of concurrency bugs, because the wrong result caused by reordering "looks completely normal" from a single-threaded viewpoint. The classic example is double-checked locking (DCL):

```java
public class Singleton {
    private static volatile Singleton instance; // volatile cannot be omitted
    public static Singleton getInstance() {
        if (instance == null) {                  // first check (no lock)
            synchronized (Singleton.class) {
                if (instance == null) {          // second check
                    instance = new Singleton();  // see the breakdown below
                }
            }
        }
        return instance;
    }
}
```

Breaking down concretely why `instance = new Singleton()` goes wrong without `volatile`: at the bytecode level this line is not done in one step but in three—(1) allocate a block of memory, (2) call the constructor on this memory to initialize the fields, (3) point the `instance` reference at this memory. As long as the compiler or CPU judges that "within a single thread, the order of these three steps does not affect the final result," it is entitled to reorder them into (1)(3)(2)—i.e. first point `instance` at the memory, then run the constructor. For the thread executing this code, the reordering is indeed unobservable (by the time it finishes (2), `instance` already points to a fully initialized object, the same as the sequential-execution result). But for **another thread**, the intermediate state of the reordering is observable: if thread A is right in the middle of the reordered (1)(3) (`instance` is already non-null, but the object's fields are still default values) while thread B executes the first check `if (instance == null)`, B sees `instance != null` and returns directly—but what it gets is a **half-built object whose constructor has not finished running**, and subsequent access to this object's fields will read default values (e.g. reading all-0/null fields where a business object was expected). This fault occurs only in the window where multiple threads simultaneously contend to "create for the first time"; the window is extremely narrow, unit tests and everyday runs can hardly ever trigger it, it only occurs sporadically under high concurrency in production, and the field state may differ on each reproduction—this is exactly where concurrency bugs are far harder to track down than sequential-execution bugs.

Once `volatile` modifies `instance`, the rule that "operations before a write cannot be reordered after the write" directly forbids (2)(3) from being reordered into (3)(2): the operations before the write to `instance` (step 3)—namely step 2, the constructor's initialization—must complete first. This is exactly why DCL only became correct in JDK 5 (after JSR-133 defined volatile semantics)—before JDK 5, `volatile` guaranteed only visibility and did not forbid reordering, so DCL was unsafe before then even with `volatile` added.

## 5. volatile

The most common use of `volatile` is a "one-writer, many-readers status flag"—one thread writes, other threads read, and reads are guaranteed to see the latest value:

```java
public class VolatileFlagDemo {
    static volatile boolean ready = false;
    static int data = 0;

    public static void main(String[] args) throws InterruptedException {
        Thread writer = new Thread(() -> {
            data = 42;         // write the ordinary variable first
            ready = true;      // then write the volatile, acting as a "publish" signal
        });
        Thread reader = new Thread(() -> {
            while (!ready) {   // busy-wait until it sees the writer's update
                // spin
            }
            System.out.println("data = " + data); // guaranteed to see 42, not 0
        });
        reader.start();
        writer.start();
        writer.join();
        reader.join();
        System.out.println("done");
    }
}
// data = 42
// done
```

Remove `volatile`, and the `reader` thread may in theory never see `ready` turn `true` (the compiler/JIT may optimize `while (!ready)` to read a register only once, because it cannot tell this field will be changed by another thread), or may see `ready == true` but `data` still 0 (reordering). With `volatile` added, neither problem occurs.

What `volatile` provides is precisely the two guarantees of visibility and ordering (analogous to C++'s acquire/release semantics, but not exactly equivalent):

1. **Visibility**: a thread's write to a volatile variable guarantees that any thread subsequently reading it sees the latest value. This is implemented with **memory barriers** (store/load fences) working together with the CPU's cache-coherence protocol, and **not** literally "every read/write bypasses the cache and flushes straight to main memory" (that is an oversimplified statement).
2. **Forbids reordering**: operations before a write cannot be reordered after the write, and operations after a read cannot be reordered before the read.

**Why `volatile` does not guarantee the atomicity of compound operations**, rather than simply being made to "make reads and writes atomic" and solve it in one stroke: `volatile`'s implementation cost is deliberately kept very low—it only inserts memory barriers at read/write points, and involves no mutual-exclusion mechanism (no queuing, no blocking, no OS involvement), which is exactly why it is far lighter than a lock. But for a multi-step operation like "read the old value, compute the new value, write it back," a memory barrier governs "the ordering and visibility of each step when it occurs individually," but cannot govern "the interleaving of these several steps of two threads"—a barrier is not a mutex, and it will not make a second thread wait idly until the first thread finishes the entire read-modify-write sequence:

```java
volatile int count = 0;

void bump() {
    count++;  // the three steps read-modify-write; volatile cannot prevent two threads both reading the same value, each adding 1, and losing updates
}
```

When two threads each call `count++` 100,000 times on the same `volatile int count`, the result is almost certainly less than 200,000—`volatile` guarantees that each read/write is visible when it occurs individually, but cannot stop the interleaving of "thread A reads 100, thread B also reads 100 (A's write has not happened yet, or A has not written yet), both compute 101 based on 100 and each write it back":

```
count = 157682 (expected 200000, usually less)   // across multiple runs, the result differs each time but is always clearly less than 200000
```

**The division of labor among volatile / synchronized / Atomic** is thus determined: `volatile` solves only the visibility + ordering of a single variable, at the lowest cost; to make a compound operation like read-modify-write atomic as a whole, either use `synchronized`/`ReentrantLock` for mutual exclusion (making the entire critical section serial, with only one thread entering at a time, able to cover any number of lines of code and any number of variables), or use a CAS-based atomic class like `AtomicInteger` (making only a single-step operation on a single variable atomic, relying on hardware instructions rather than blocking; see the next section). The three are layered by "the granularity of the problem to solve" and "the cost you are willing to pay," and are not substitutes for one another. `count++` needs `synchronized` or `AtomicInteger` to be guaranteed atomic; `volatile` suits a "one-writer, many-readers status flag," not a "counter that multiple threads all modify."

## 6. synchronized and the object header

Adding `synchronized` to a method allows only one thread to execute it at a time; `synchronized` can also wrap a block of code and specify which object to lock on:

```java
synchronized (lock) {        // the monitorenter bytecode
    // critical section
}                            // the monitorexit bytecode (the exception path also exits)
```

Alongside locking there is also `wait`/`notify`: one thread "waits" until some condition is met, and another thread "wakes it up" after changing the condition. Both must be called inside a `synchronized` block:

```java
public class WaitNotifyDemo {
    static final Object lock = new Object();
    static boolean condition = false;

    public static void main(String[] args) throws InterruptedException {
        Thread waiter = new Thread(() -> {
            synchronized (lock) {
                while (!condition) {                 // use while rather than if, to guard against spurious wakeups
                    try { lock.wait(); } catch (InterruptedException e) { }
                }
                System.out.println("waiter: condition met");
            }
        });
        waiter.start();
        Thread.sleep(100); // let the waiter most likely enter wait first (does not affect correctness, just makes the demo clearer)
        synchronized (lock) {
            condition = true;
            lock.notifyAll();                        // wake the waiters (they still must re-contend for the lock)
        }
        waiter.join();
        System.out.println("main: done");
    }
}
// waiter: condition met
// main: done
```

`lock.wait()` releases the lock and puts the current thread into waiting, until another thread calls `lock.notify()`/`notifyAll()` gives it a chance to be woken and re-contend for the lock—so `wait`/`notify` must be used in pairs on the same lock object.

`synchronized` is a **reentrant monitor lock** (monitor). Every Java object can serve as a lock, and the lock state is recorded in the **mark word of the object header**. The 64-bit HotSpot object-header layout (uncompressed, ordinary object):

```
Object memory layout:
+------------------+------------------+-------------+---------+
| Mark Word (8B)   | Klass Pointer(4/8B)| instance fields | padding |
+------------------+------------------+-------------+---------+
```

The Mark Word reuses the same 8 bytes to store different information (the lock flag bits determine how it is interpreted):

| Lock state | Mark Word content (partial) | Flag bits |
|--------|----------------------|--------|
| Unlocked | hashCode, GC generational age | 01 |
| Biased lock | ID of the owning thread | 01 (biased bit 1) |
| Lightweight lock | pointer to the Lock Record on the stack | 00 |
| Heavyweight lock | pointer to the monitor (ObjectMonitor) | 10 |
| GC mark | — | 11 |

### Lock upgrade

To avoid always going heavyweight (an OS mutex, involving user-mode/kernel-mode switches, expensive), HotSpot introduced a tiered scheme, essentially a direct product of the observation that "the vast majority of locks actually have no real contention"—if you blindly went heavyweight from the start, you would pay the cost of switching into the kernel for contention that does not exist at all:

```
unlocked --first thread enters--> biased lock (records the thread ID; subsequent CAS for the same thread is all skipped)
         --another thread contends--> lightweight lock (spin + CAS, optimistic, suits short critical sections)
         --spin fails / heavy contention--> heavyweight lock (suspends the thread, enters the OS wait queue)
```

- **Biased lock**: assumes the lock is always acquired by the same thread, records the thread ID on the first acquisition, and afterward needs no CAS if there is no contention. Disabled by default and slated for removal from JDK 15 onward (in modern applications, thread pools and concurrency frameworks make the assumption of "the same thread repeatedly locking" no longer generally hold, and the benefit of maintaining this layer of complexity has shrunk).
- **Lightweight lock**: threads execute alternately (not contending simultaneously). A thread builds a Lock Record in its own stack frame and uses CAS to swap the mark word for a pointer to it. If it fails, it spins.
- **Heavyweight lock**: real contention. It inflates into an `ObjectMonitor`, and contending threads are suspended by the OS, analogous to `pthread_mutex`.

### The Monitor structure: what a heavyweight lock actually is

The `wait`/`notify` in the earlier `WaitNotifyDemo` were in fact already using a monitor, without spelling out its internal structure. After inflating into a heavyweight lock, the mark word points to an `ObjectMonitor` (a real C++ structure in the HotSpot source), whose core fields correspond respectively to "who is running," "who is queued," and "who is waiting for notification":

| Field | Meaning |
|------|------|
| `Owner` | The thread currently holding the lock |
| `EntryList` | The queue of threads that failed to acquire the lock and are blocked on `monitorenter` |
| `WaitSet` | The set of threads that called `wait()` and voluntarily gave up the lock to wait |
| `recursions` | The reentrancy count of the current holding thread |

These four fields explain why the behavior of the earlier `wait`/`notify` example must be bound to the same lock: a thread calling `lock.wait()` essentially moves itself out of `Owner` and into the `WaitSet` of the `ObjectMonitor` for this lock, releasing the lock at the same time; another thread's `notify()`/`notifyAll()` moves the thread(s) in the `WaitSet` (one or all) back into the `EntryList`, making them eligible again to contend for `Owner`—"moved into the EntryList" is not "immediately acquires the lock"; a woken thread must still contend along with the other threads in the `EntryList`, which is why the earlier code uses `while` rather than `if` around `wait()` to recheck the condition. `recursions` directly corresponds to the "reentrant" property: when the same thread again enters a `synchronized` block for a lock it already holds, it is not blocked by the `EntryList`, but simply increments `recursions`, decrementing it on `monitorexit`, and only when it drops to 0 is the lock actually released—this is why `synchronized void setA() { setB(); }` (A and B locking the same object) does not lock itself out.

## 7. CAS and Atomic*

Atomic classes like `AtomicInteger` provide a set of operations that "look like ordinary methods but are actually atomic as a whole," with no need to lock yourself:

```java
import java.util.concurrent.atomic.AtomicInteger;

public class AtomicBasicDemo {
    public static void main(String[] args) {
        AtomicInteger ai = new AtomicInteger(0);
        System.out.println(ai.incrementAndGet()); // 1
        System.out.println(ai.incrementAndGet()); // 2
        boolean ok = ai.compareAndSet(2, 100);     // expect the current value to be 2, set it to 100
        System.out.println(ok);                    // true
        System.out.println(ai.get());               // 100
    }
}
// 1
// 2
// true
// 100
```

Multiple threads calling `incrementAndGet()` concurrently will not lose updates the way an ordinary `int`'s `count++` does—behind this is CAS (Compare-And-Swap), the cornerstone of lock-free concurrency, corresponding to x86's `cmpxchg` instruction. Semantics: `if (memory value == expected) { memory value = new value; return true }`, and the whole process is atomic in hardware—it solves the same "atomicity" problem as a lock but takes an entirely different path: a lock relies on mutual exclusion (making the second thread wait), whereas CAS relies on "optimistic retry" (blocking no thread, and on failure re-reading the latest value and trying again), so there is no overhead of suspending/waking threads at all, and it is much faster than a lock when contention is light; under heavy contention, the repeated retries also waste CPU, and this is the boundary of its cost.

```java
ai.incrementAndGet();               // the underlying CAS spin: do { old=get(); } while(!compareAndSet(old, old+1))
boolean ok = ai.compareAndSet(1, 2); // if expected 1, set 2

// JDK8+ high-concurrency counter, striping to reduce CAS contention (the hot spot is spread across multiple Cells)
LongAdder adder = new LongAdder();
adder.increment();
long sum = adder.sum();
```

`Atomic*` implements the CAS of its internal field with `volatile` + `Unsafe`/`VarHandle`—which also explains why `Atomic*` can fill the gap mentioned earlier that "volatile does not guarantee the atomicity of compound operations": it does not make `volatile` stronger, but rather, on top of the visibility `volatile` provides, uses the hardware instruction CAS to merge "compare and swap" into a single indivisible operation, fundamentally eliminating the possibility of the "read old value, compute, write back" steps being interposed by another thread.

**The ABA problem**: a value changes from A to B and back to A, and CAS cannot detect it—because CAS only compares "is the current value equal to the expected value," and does not care whether the value was changed and changed back in between; in structures like lock-free stacks and lock-free linked lists, ABA may cause a node to be wrongly reused or freed. It is solved with `AtomicStampedReference` (binding a version number to the value and comparing both together), analogous to the tagged pointer in a lock-free stack.

A runnable comparison: 8 threads each `count++` 100,000 times. The unprotected `int` **loses updates** because "read-modify-write" is not atomic, while `AtomicInteger` is always correct thanks to CAS:

```java
import java.util.concurrent.atomic.AtomicInteger;

public class LostUpdate {
    static int plain = 0;                       // unprotected
    static final AtomicInteger atomic = new AtomicInteger(0);

    public static void main(String[] args) throws Exception {
        int threads = 8, perThread = 100_000;
        Runnable job = () -> {
            for (int i = 0; i < perThread; i++) {
                plain++;                         // read-modify-write, not atomic: loses updates
                atomic.incrementAndGet();        // CAS: atomic
            }
        };
        Thread[] ts = new Thread[threads];
        for (int i = 0; i < threads; i++) ts[i] = new Thread(job);
        for (Thread t : ts) t.start();
        for (Thread t : ts) t.join();            // wait for all to finish, the result is deterministic

        int expected = threads * perThread;      // 800000
        System.out.println("expected      = " + expected);
        System.out.println("atomic == exp : " + (atomic.get() == expected));
        System.out.println("plain  <  exp : " + (plain < expected));
    }
}
// expected      = 800000
// atomic == exp : true
// plain  <  exp : true    —— plain is almost certainly < 800000 (lost updates), atomic always equals the expected value
```

(This code has been verified in practice: `atomic == exp` is always `true`, `plain < exp` is always `true`, and the phenomenon is stable and reproducible.)

## 8. java.util.concurrent

### ReentrantLock

`ReentrantLock` is the explicit version of `synchronized`: you `lock()` yourself and `unlock()` yourself, and you must put `unlock()` in a `finally`, otherwise the exception path will cause the lock never to be released:

```java
import java.util.concurrent.locks.ReentrantLock;

public class LockBasicDemo {
    static final ReentrantLock lock = new ReentrantLock();
    static int counter = 0;

    static void increment() {
        lock.lock();
        try {
            counter++;
        } finally {
            lock.unlock();
        }
    }

    public static void main(String[] args) throws InterruptedException {
        Runnable job = () -> { for (int i = 0; i < 100_000; i++) increment(); };
        Thread t1 = new Thread(job);
        Thread t2 = new Thread(job);
        t1.start();
        t2.start();
        t1.join();
        t2.join();
        System.out.println("counter = " + counter); // 200000
    }
}
// counter = 200000
```

The extra capability over `synchronized` is being able to try to acquire the lock with a timeout, and take another branch if it cannot be obtained, rather than waiting forever:

```java
if (lock.tryLock(1, TimeUnit.SECONDS)) {   // wait at most 1 second
    try {
        // critical section
    } finally {
        lock.unlock();
    }
} else {
    // did not get the lock, do something else (e.g. give up, retry)
}
```

`ReentrantLock` is more flexible than `synchronized`: interruptible, timeout-capable, fairness-capable, and supports multiple condition variables. It is based on **AQS (AbstractQueuedSynchronizer)**—a `volatile int state` + a CLH-variant wait queue; the visibility of `state` relies on `volatile`, while the queuing and blocking under contention rely on AQS's own wait-queue mechanism. `new ReentrantLock(true)` constructs a fair lock (queued in request order, slightly lower throughput but no thread starves forever).

| Comparison | synchronized | ReentrantLock |
|------|--------------|---------------|
| Acquisition | Implicit (JVM) | Explicit lock/unlock |
| Release | Automatic | Manual (finally) |
| Interruptible | No | lockInterruptibly() |
| Timeout | No | tryLock(timeout) |
| Fair lock | No | Optional |
| Condition variables | Single (wait/notify) | Multiple Conditions |

### What locks are there in Java: a classification table

We have already covered `synchronized` (lock upgrade: biased lock → lightweight lock → heavyweight lock) and `ReentrantLock` (based on AQS) separately, but "what locks are there in Java" asks about a higher-level classification dimension—the same lock often falls into several dimensions at once, and these dimensions describe mutually independent problems, not mutually exclusive options:

| Classification dimension | Type | Meaning | Example |
|---|---|---|---|
| By whether contention is assumed | Pessimistic lock | Assumes there is definitely contention; locks first, then operates | `synchronized`, `ReentrantLock` |
| | Optimistic lock | Assumes there is no contention; operates first, then checks at commit whether it was modified, retrying on conflict | CAS, `AtomicInteger` (see the previous section) |
| By whether jumping the queue is allowed | Fair lock | Acquired strictly in request order; no thread starves forever | `new ReentrantLock(true)` |
| | Unfair lock | Allows a newly arrived thread to grab a just-released lock directly, trading fairness for throughput | `synchronized`, `new ReentrantLock()` (default) |
| By whether it can be acquired again | Reentrant lock | The same thread can repeatedly acquire a lock it already holds without deadlocking, implemented via `recursions`/`state` counting | `synchronized`, `ReentrantLock` |
| | Non-reentrant lock | The same thread acquiring it again locks itself out | A hand-written spinlock that does not record the owner |
| By whether it can be shared | Exclusive lock (mutual-exclusion lock) | Only one thread can hold it at a time | `synchronized`, `ReentrantLock`, the write lock of `ReentrantReadWriteLock` |
| | Shared lock | Multiple threads can hold it at the same time | The read lock of `ReentrantReadWriteLock`, `Semaphore` (allows N to enter simultaneously) |
| By behavior on acquisition failure | Spinlock | On failing to acquire the lock, does not block but loops and retries (with an upper bound, after which it turns to blocking) | The implementation of the lightweight lock; `AtomicInteger`'s internal CAS spin |
| | Blocking lock | On failing to acquire the lock, suspends directly and yields the CPU, waiting to be woken | The heavyweight lock (`ObjectMonitor` suspends threads into the `EntryList`) |
| By lock-granularity design | Segmented lock | Splits one big object into segments, each locked separately; concurrency degree = number of segments | The `Segment` of JDK 7 `ConcurrentHashMap` (JDK 8 changed to locking the bucket's head node; see the next section) |

**Why the same lock spans several rows**: take `synchronized` as an example—it is simultaneously an "unfair lock" (the instant thread A releases the lock, a newly arrived thread B may grab it faster than the already-queued thread C), a "reentrant lock" (the same thread can repeatedly enter a critical section it already holds), and an "exclusive lock" (only one thread executes the critical section at a time)—these three describe three mutually independent problems (whether to queue in order, whether reentry is allowed, whether sharing is allowed), and `synchronized` made a fixed choice on each of these three dimensions; whereas `ReentrantLock` hands the choice on the "fair/unfair" dimension back to the caller (passing `true`/`false` to the constructor), which is precisely one concrete manifestation of why it is more flexible than `synchronized`, rather than a vague claim of "more flexible."

The `optimistic lock`/`pessimistic lock` layer of classification corresponds directly to the earlier "CAS and Atomic*" section in this chapter: a pessimistic lock assumes "not locking will surely cause problems," so it pays the cost of locking first and then operates, and `synchronized`/`ReentrantLock` both follow this line of thinking; an optimistic lock assumes "probably no one is contending with me," so it operates directly without locking, and only at the moment of committing the result uses CAS to check "did anyone modify it first during this period," writing successfully if not and retrying (or re-reading the latest value and recomputing) if so—the earlier `AtomicInteger`/`LongAdder` are the most basic way optimistic locking is realized in Java; the common database-level pattern of "adding a `version` field to a row, `UPDATE ... WHERE version = old version number`" is the same idea reused at another layer of the system.

### ConcurrentHashMap

In concurrent scenarios do not use an ordinary `HashMap` (multiple threads simultaneously triggering a resize may cause a linked list to form a cycle and `get` to loop forever); use `ConcurrentHashMap`, whose API is used the same way as `HashMap`:

```java
import java.util.concurrent.ConcurrentHashMap;

public class CHMBasicDemo {
    public static void main(String[] args) {
        ConcurrentHashMap<String, Integer> map = new ConcurrentHashMap<>();
        map.put("a", 1);
        map.putIfAbsent("a", 99);         // "a" already exists, not overwritten
        map.computeIfAbsent("b", k -> 2); // "b" does not exist, compute and put it in
        System.out.println(map.get("a")); // 1
        System.out.println(map.get("b")); // 2
    }
}
// 1
// 2
```

The JDK 8 rewrite: **array + linked list / red-black tree**, with concurrency control using **CAS + synchronized (locking the bucket's head node)**, rather than the segmented lock (Segment) of JDK 7. Choosing "lock the bucket's head node" rather than locking the whole table is so that the concurrency degree is proportional to the number of buckets rather than being compressed to 1—this is precisely the fundamental reason it has far higher throughput than `Collections.synchronizedMap` (which locks the whole table, so only one thread can operate at any moment):

- Inserting into an empty bucket: CAS puts it directly, lock-free.
- Non-empty bucket: `synchronized` locks that bucket's head node, only one bucket, concurrency degree = number of buckets.
- When a linked list's length ≥ 8 and the table capacity ≥ 64, it converts to a red-black tree, dropping queries from O(n) to O(log n).
- `size()` uses `baseCount` + `CounterCell[]` (similar to LongAdder) to avoid a hot spot.

Reads are basically lock-free (a node's val/next are volatile), writes lock only a single bucket, and throughput is far higher than `Collections.synchronizedMap`.

### The thread pool ThreadPoolExecutor

Rather than `new Thread` for every task, one usually uses a thread pool to reuse threads—creating an OS thread is itself expensive (as discussed earlier, stack allocation, `pthread_create`, and kernel scheduling all have real costs), and the thread pool amortizes this cost across many task executions. The simplest usage is to obtain an `ExecutorService` and `submit` tasks to it repeatedly:

```java
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;

public class PoolBasicDemo {
    public static void main(String[] args) throws Exception {
        ExecutorService es = Executors.newFixedThreadPool(2);
        Future<Integer> f = es.submit(() -> 1 + 1);
        System.out.println("result = " + f.get()); // 2, blocks to get the result
        es.shutdown();                              // remember to shut down the pool when done
    }
}
// result = 2
```

`submit` hands the task to the thread pool for asynchronous execution and returns a `Future` immediately; `f.get()` blocks waiting for the task to finish and obtains the return value; `shutdown()` notifies the pool to accept no new tasks and to exit once it finishes what it has in hand.

More common in production is to `new ThreadPoolExecutor` yourself with the parameters spelled out, rather than using `Executors`' factory methods:

```java
import java.util.concurrent.ArrayBlockingQueue;
import java.util.concurrent.Executors;
import java.util.concurrent.ThreadPoolExecutor;
import java.util.concurrent.TimeUnit;

ThreadPoolExecutor pool = new ThreadPoolExecutor(
    2,                              // corePoolSize: number of core threads, always resident
    4,                              // maximumPoolSize: maximum number of threads
    60L, TimeUnit.SECONDS,          // keepAliveTime: idle survival time for non-core threads
    new ArrayBlockingQueue<>(100),  // workQueue: the task queue
    Executors.defaultThreadFactory(),
    new ThreadPoolExecutor.CallerRunsPolicy() // rejection policy
);
```

Task submission logic (be sure to understand it):

```
submit a task
  ├─ number of running threads < core?   → create a core thread to run it
  ├─ no, queue not full?                  → enqueue and wait
  ├─ no, thread count < max?              → create a non-core thread to run it
  └─ no                                    → trigger the rejection policy
```

Rejection policies: `AbortPolicy` (throws an exception, the default), `CallerRunsPolicy` (the submitter runs it itself, backpressure), `DiscardPolicy`, `DiscardOldestPolicy`.

> In production, avoid `Executors.newFixedThreadPool`/`newCachedThreadPool`: the former has an unbounded queue (piled-up tasks may OOM rather than triggering the rejection policy), and the latter has an unbounded thread count (under a sudden burst of load it may create a huge number of threads and drag down the system). Manually `new ThreadPoolExecutor` with explicit parameters makes the decision "is there a capacity ceiling at all" explicit, rather than relying on the hard-to-notice defaults behind the factory methods.

### Why more threads is not always better

Intuitively "the more threads, the stronger the concurrency," but this intuition holds only on an idealized machine with infinite cores. On a real machine, once the thread count exceeds a certain point, throughput no longer rises and may even fall, because two kinds of invisible cost grow with the thread count:

- **Context-switching overhead**: CPU cores are limited, and once the thread count greatly exceeds the number of cores, the OS scheduler must constantly swap threads on and off the CPU—each switch must save/restore registers, flush the TLB, and destroy the just-established cache locality (the newly swapped-in thread most likely has to reload data from memory rather than hitting what the previous thread left in L1/L2). These switches produce no business result at all and are purely scheduling cost; the more threads, the more switches per unit time, and the lower the proportion of CPU time actually spent on business computation—this is the most direct cause of "more threads is not always better," and is the same mechanism, at a different scale, as "too many platform threads dragging down the scheduler" in the earlier "virtual threads" section.
- **Memory overhead**: as mentioned earlier, each platform thread takes about 1MB of stack by default; 1,000 threads consume nearly 1GB of stack memory alone, not counting the other resources a thread holds (database connections, file handles bound to the thread also grow proportionally).

Hence an empirical formula for estimating "how many threads is appropriate," rather than picking a number arbitrarily:

```
optimal thread count ≈ number of CPU cores × (1 + average wait time / average compute time)
```

The meaning is straightforward: a task that computes the whole time (wait time approaching 0) should have a thread count close to the number of cores—opening more threads just makes them queue for CPU time slices, does not speed up computation, and instead adds switching overhead; a task that spends most of its time waiting on IO (wait time far exceeding compute time) can open far more threads than cores, because during the wait a thread does not occupy the CPU, and this "idle" time can be scheduled for another thread to compute. From this come two commonly used simplified rules of thumb:

- **CPU-intensive tasks** (pure computation, sorting, encryption/decryption): thread count ≈ number of CPU cores + 1. As many threads as cores exactly fill each core, and the extra 1 leaves margin for "a thread occasionally taking a page fault or briefly blocking," avoiding some core idling for that instant.
- **IO-intensive tasks** (database queries, RPC calls, file reads/writes): thread count ≈ number of CPU cores × 2, or even higher. Such tasks spend most of their time with the thread waiting for IO to return and not occupying the CPU, and the extra threads can execute the compute part of other tasks while a "waiting" thread yields the CPU.

These two values are only empirical starting points, not exact solutions—the true optimum depends on the actual ratio of "wait time / compute time" in the formula above, and production usually requires load testing and observing CPU utilization and the number of context switches (`vmstat`/`pidstat` can show the `cs`/`csw` columns) to tune it, rather than applying a fixed multiplier once and for all. This is also why the earlier part of this section stresses using `new ThreadPoolExecutor(...)` with explicit parameters rather than relying on the `Executors` factory methods—the thread-count ceiling ought to be a value computed from the actual load, not a number hidden inside the default implementation that developers will not even look at.

### Future and CompletableFuture

The `Future` returned by `es.submit(...)` in the `PoolBasicDemo` above is the most basic asynchronous-result placeholder—`get()` blocks to obtain the result, and until you have the result you can do nothing; multiple asynchronous steps cannot be chained declaratively, only manually `get()`-blocked layer by layer. `CompletableFuture` solves exactly this composability problem: you can string multiple asynchronous steps together like building blocks, without manually blocking at each step:

```java
import java.util.concurrent.CompletableFuture;

public class CFBasicDemo {
    public static void main(String[] args) {
        CompletableFuture<Integer> cf = CompletableFuture
            .supplyAsync(() -> 10)     // asynchronously produce a value
            .thenApply(x -> x * 2);    // transform the result, chaining to return a new CompletableFuture
        System.out.println(cf.join()); // 20, blocks waiting for the whole chain to finish before taking the value
    }
}
// 20
```

More common chained forms also include consuming the result and handling exceptions:

```java
CompletableFuture
    .supplyAsync(() -> 10)                    // asynchronously produce
    .thenApply(x -> x * 2)                    // transform (chained on the same thread)
    .thenCompose(x -> CompletableFuture.supplyAsync(() -> x + 1)) // flatten a nested future
    .thenAccept(System.out::println)          // consume, prints 21
    .exceptionally(ex -> { ex.printStackTrace(); return null; })
    .join(); // wait for the chain to finish —— the common thread pool uses daemon threads, so if main does not wait it may exit early and miss the print
```

Similar to JS's Promise / C++'s `std::future` + continuation. Runnable: `thenCombine` runs two tasks concurrently and then merges them; `exceptionally` recovers from an exception in the chain, and subsequent steps continue:

```java
import java.util.concurrent.CompletableFuture;

public class CFCompose {
    public static void main(String[] args) throws Exception {
        CompletableFuture<Integer> a = CompletableFuture.supplyAsync(() -> 3);
        CompletableFuture<Integer> b = CompletableFuture.supplyAsync(() -> 4);

        // combine: a and b execute concurrently, and merge when done
        int hypotSq = a.thenCombine(b, (x, y) -> x * x + y * y).join(); // 25

        // chaining + exception recovery
        String r = CompletableFuture.supplyAsync(() -> 10)
            .thenApply(x -> x / 0)                    // throws ArithmeticException
            .exceptionally(ex -> -1)                  // recover to -1
            .thenApply(x -> "result=" + x)
            .join();

        System.out.println("hypotSq = " + hypotSq);
        System.out.println(r);
    }
}
// hypotSq = 25
// result=-1
```

## 9. Deadlock and how to avoid it

The four conditions for deadlock (consistent with OS textbooks): mutual exclusion, hold-and-wait, no preemption, and circular wait. Typical:

```java
// Thread 1: lock A then B; Thread 2: lock B then A → circular wait
synchronized (A) { synchronized (B) { } }  // Thread 1
synchronized (B) { synchronized (A) { } }  // Thread 2
```

Means of avoidance:
- **Lock ordering**: all threads acquire locks in a fixed global order (breaks circular wait).
- **tryLock with timeout**: `ReentrantLock.tryLock` backs off and releases if it cannot acquire.
- **Reduce lock granularity/hold time**, and be lock-free where possible (CAS, immutable objects).
- Detection: `jstack <pid>` can report "Found one Java-level deadlock."

## 10. BIO / NIO / AIO

The problem the next section "virtual threads" sets out to solve—"a blocking IO request occupies an entire kernel thread"—was, before virtual threads appeared, already mitigated by Java from different angles through three generations of different IO models. Understanding the differences among these three is necessary background for understanding why virtual threads are designed the way they are.

The core difference among the three is two independent dimensions: **whether the thread must keep waiting** (blocking/non-blocking), and **who notifies of / completes the IO** (synchronous/asynchronous)—these two dimensions are easily conflated, but describe different problems:

| Model | Full name | Blocking/non-blocking | Synchronous/asynchronous | Core mechanism |
|---|---|---|---|---|
| BIO | Blocking IO | Blocking | Synchronous | One connection one thread; after a `read()` call the thread is suspended until data arrives |
| NIO | Non-blocking IO | Non-blocking | Synchronous | A single thread's `Selector` polls the ready events of many `Channel`s; when ready, the thread does the `read()` itself |
| AIO | Asynchronous IO | Non-blocking | Asynchronous | A `read()` returns immediately; after the OS finishes copying the data it proactively calls back, and the thread never participates in waiting |

**Why "blocking/non-blocking" and "synchronous/asynchronous" are two different things**: blocking is about "whether the thread that made the call can do something else while waiting for the result"—in BIO a thread calling `read()` just waits there dead, whereas in NIO a thread calling non-blocking `read()` immediately gets a result of "no data for now" or "there is data," without waiting foolishly. Synchronous/asynchronous is about "who completes the IO operation itself": in a synchronous model, blocking or not, the step of actually copying the data from the kernel buffer to user space is done by the thread that made the call (an NIO thread still has to call `read()` itself to move the data over, it just can go do something else first before moving, relying on the `Selector` to notify it that "it can move now"); in an asynchronous model, even the copying step is handed to the OS, and the thread is only called back at the very end to be told "the data is already where you wanted it." NIO's "non-blocking" happens in the phase of waiting for data to become ready, and the copying phase is still synchronous; AIO hands both the waiting and the copying phases to the OS, and this is the essential dividing line between NIO and AIO, not the superficial "AIO is just NIO plus a callback."

### BIO: one connection one thread

```java
ServerSocket server = new ServerSocket(8080);
while (true) {
    Socket socket = server.accept();       // blocks: waits here as long as there is no new connection
    new Thread(() -> {
        try (InputStream in = socket.getInputStream()) {
            in.read(buffer);               // blocks: waits here as long as there is no data
            // handle the request...
        } catch (IOException e) { /* ... */ }
    }).start();
}
```

Every incoming connection spins up a thread to serve it; the code is intuitive and easy to debug (the call stack is the real execution path). The drawback has appeared repeatedly above: the thread count is proportional to the connection count, and once connections grow, the thread stacks and context-switching overhead alone crush the machine first—this is the most direct manifestation, in network programming, of the previous section's "in IO-intensive scenarios you cannot add threads without limit," and the fundamental reason NIO was born. It suits scenarios with few and relatively fixed connections, e.g. a small number of long-lived connections between internal services.

### NIO: one thread manages many connections

The trio `Selector` + `Channel` + `Buffer` lets one thread simultaneously "keep an eye on" hundreds or thousands of connections, handling only whoever's data is ready, without opening a thread per connection:

```java
Selector selector = Selector.open();
serverChannel.configureBlocking(false);
serverChannel.register(selector, SelectionKey.OP_ACCEPT);

while (true) {
    selector.select();                      // blocks, but only on "is any event ready"
    for (SelectionKey key : selector.selectedKeys()) {
        if (key.isAcceptable()) { /* handle a new connection */ }
        if (key.isReadable())   { /* this connection's data is ready, read it */ }
    }
}
```

Underneath, `Selector.select()` relies on OS-provided "multiplexing" mechanisms such as **epoll** on Linux and **IOCP** on Windows—it hands "polling hundreds or thousands of fds for data" to the kernel to do with a more efficient data structure (not a foolish application-layer loop asking one by one), and the kernel returns to user space only the list of connections that are actually ready, so the application layer need not dedicate a kernel thread per connection to wait. This is precisely why it can support high-concurrency connections with a small number of threads, and one reason frameworks like Netty choose to build on NIO rather than AIO—not that AIO's philosophy is bad, but that AIO's kernel-level implementation on mainstream operating systems (especially Linux) has long been not mature and efficient enough, whereas NIO is more stable and controllable.

### AIO: the thread does not participate in waiting at all after initiating

```java
AsynchronousServerSocketChannel server =
    AsynchronousServerSocketChannel.open().bind(new InetSocketAddress(8080));
server.accept(null, new CompletionHandler<AsynchronousSocketChannel, Object>() {
    @Override
    public void completed(AsynchronousSocketChannel channel, Object attachment) {
        // the OS has already established the connection before calling back here; this thread did not block waiting at all before
        server.accept(null, this);   // continue to accept the next connection
    }
    @Override
    public void failed(Throwable exc, Object attachment) { /* ... */ }
});
```

After initiating `accept`/`read`, the thread returns immediately to do other things, and the OS proactively calls the `completed` callback after finishing the connection establishment or data copy—this is the concrete meaning of the "asynchronous" column in the table above. The cost is that every IO operation needs a callback object, and the business logic gets fragmented into a pile of callback pieces; this is precisely the concrete example of the readability cost of "asynchronous/callback-style programming" that the next section "virtual threads" will mention at its start. AIO sees little actual use in the Java ecosystem, largely because the performance gain bought by this readability cost is not as stable on Linux as "NIO + a small number of threads."

### How to choose among the three

- Few, relatively fixed connections (calls between internal services): BIO, the simplest code and the lowest debugging cost.
- Many connections with short per-request handling time (typical web servers, gateways): NIO, using a small number of threads to withstand a large number of concurrent connections; the NIO modes of Netty and Tomcat are both this idea.
- Many connections with long per-request handling time, and callback-style programming is acceptable: AIO, in theory the most thread-thrifty, but its ecosystem and OS support are not as mature as NIO's.

These three models can reduce the thread count to varying degrees, but none solves the other half of the tension raised in the next section—NIO/AIO save threads but turn business code into event polling or callback chains, no longer the intuitive "execute top to bottom" form. The idea of virtual threads is the reverse: the problem of thread count is handed to the runtime to solve with M:N scheduling, while business code keeps the synchronous, intuitive BIO-style form—this is also why understanding the trade-offs of BIO/NIO/AIO helps in understanding what problem virtual threads really solve.

## 11. Virtual threads (Loom, JDK 21)

The platform threads seen earlier (`new Thread(...)`) bind 1:1 to a kernel thread, have about a 1MB stack, and are created via `pthread_create`. This is not much of a problem in **CPU-intensive** scenarios (the thread count should be close to the number of cores anyway), but in an **IO-intensive** service (e.g. a typical "one request one thread" web server) it hits a structural contradiction: while handling an HTTP request, the thread spends the vast majority of its time waiting for the database to return and for downstream RPC responses—during these waits the thread does no computation at all, but as long as it is a platform thread, it keeps occupying a precious kernel thread and about 1MB of stack memory until the IO completes.

**Why "enlarging the thread pool" cannot solve it**: doing the arithmetic makes it clear—a thread pool of 100,000 platform threads consumes, for stack memory alone, 100,000 × 1MB = 100GB, which most machines simply cannot bear, not counting each thread's kernel-mode scheduling cost; facing tens of thousands of threads, the OS scheduler's context-switching overhead itself (save/restore registers, TLB flush, cache locality destroyed) grows significantly, and throughput drops instead. This is not a problem of "the parameters were not tuned well," but the resource-consumption ceiling of the model "a waiting request occupies a complete kernel thread"—enlarging the thread pool only pushes this tension out, it does not eliminate it.

Before virtual threads, the industry's solution was **asynchronous/callback-style programming** (Java's NIO + `CompletableFuture`, Netty's Reactor model): rather than letting a thread block waiting on IO, register a callback, and after the IO is ready run the callback on some thread, so the same thread can handle other connections during the wait. This did solve the resource problem (Netty can withstand tens of thousands of concurrent connections with just a few threads), but at the cost of a changed programming model—the business logic gets split into a pile of pieces connected by callback chains, the originally linear logic of "read the database → compute a result → query once more → return" becomes deeply nested or chained `thenCompose`/`thenApply`, an exception must be handled explicitly at each stage, and the debug call stack no longer corresponds to "the call path this request actually went through" but to "in which scheduling of which thread pool this callback was triggered"—the intuition for troubleshooting is broken.

**What virtual threads set out to solve is exactly this contradiction**: to both escape the resource model of "a blocking request occupying a kernel thread" and preserve the simple, intuitive programming model of "write code top to bottom, use ordinary `try/catch`, and the call stack is the real call path." From JDK 21 you can use **virtual threads**, whose syntax is almost the same as platform threads but which are extremely lightweight and can be created in the millions:

```java
import java.util.concurrent.Executors;
import java.util.concurrent.Future;

public class VirtualBasicDemo {
    public static void main(String[] args) throws Exception {
        Thread vt = Thread.ofVirtual().start(() -> System.out.println("hello from virtual thread"));
        vt.join();
        System.out.println("is virtual: " + vt.isVirtual()); // true

        try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
            Future<Integer> f = executor.submit(() -> 1 + 1);
            System.out.println("result = " + f.get()); // 2
        }
    }
}
// hello from virtual thread
// is virtual: true
// result = 2
```

`Thread.ofVirtual().start(...)` starts a virtual thread directly; `Executors.newVirtualThreadPerTaskExecutor()` is a thread pool that "uses a new virtual thread to run each submitted task," and the usage of `submit`/`get` is exactly the same as an ordinary thread pool.

A **virtual thread** is a **user-mode thread** scheduled by the JVM (analogous to a Go goroutine): its stack grows on demand and lives on the heap, its creation and switching do not go through the OS, and it can be created in the millions—something a platform thread bound 1:1 to a kernel thread cannot do.

```java
// one virtual thread per task; on blocking IO it is automatically unmounted, occupying no kernel thread
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (int i = 0; i < 1_000_000; i++) {
        executor.submit(() -> {
            Thread.sleep(Duration.ofSeconds(1)); // blocking does not occupy the carrier thread
            return null;
        });
    }
}
```

Runnable: start 100,000 virtual threads at once, each "blocking" for 10ms. Placed on a few platform threads (carriers), they still finish in tens of milliseconds—the same number of platform threads simply cannot be created. Use `CountDownLatch` to wait for all to check in, and `AtomicInteger` to count:

```java
import java.util.concurrent.CountDownLatch;
import java.util.concurrent.Executors;
import java.util.concurrent.atomic.AtomicInteger;

public class VThreads {
    public static void main(String[] args) throws Exception {
        int n = 100_000;
        AtomicInteger done = new AtomicInteger();
        CountDownLatch latch = new CountDownLatch(n);

        // one virtual thread per task, 100,000 in total, each briefly blocking
        try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
            for (int i = 0; i < n; i++) {
                executor.submit(() -> {
                    Thread.sleep(10);         // blocking unmounts the carrier, rather than occupying a kernel thread
                    done.incrementAndGet();
                    latch.countDown();
                    return null;
                });
            }
            latch.await();                    // wait for all tasks to check in
        }
        System.out.println("tasks done      = " + done.get());
        System.out.println("current is virtual: " + Thread.currentThread().isVirtual());
    }
}
// tasks done      = 100000
// current is virtual: false   —— main is a platform thread; the 100,000 virtual threads are scheduled by a small number of carrier threads
```

(This example has been verified in practice: 100,000 virtual threads + 10ms of blocking each, total elapsed time about 0.15 seconds—if you switched to 100,000 platform threads, the creation overhead and stack memory alone would suffice to crush most machines.)

### Mount and unmount

A running virtual thread is **mounted** onto a platform thread (the **carrier thread**, from a ForkJoinPool). On encountering a blocking operation (such as network IO or `sleep`) it is **unmounted**: the virtual thread's stack (in the form of a continuation) is saved to the heap, and the carrier thread is freed to run other virtual threads. After the blocking ends it is mounted onto some carrier again to continue—this is precisely the mechanistic core of how it simultaneously achieves "resource efficiency" and a "synchronous programming model": the business code is still ordinary sequential blocking calls (`Thread.sleep`, blocking IO APIs), the call stack is still the request's real call path, but the runtime translates "blocking" into "release the underlying resource and resume later," a step completely transparent to the person writing the code.

```
platform thread pool (carriers, ~number of CPU cores)
  Carrier-1: [VT-A running] --VT-A hits IO blocking--> unmount VT-A, mount VT-B
  Carrier-2: [VT-C running]
             heap: [VT-A stack snapshot, awaiting wakeup] [VT-D stack snapshot] ...
```

Comparison: when a platform thread blocks, the entire kernel thread is suspended by the OS (occupied but unusable, and cannot be given to anyone else); when a virtual thread blocks, the kernel thread is freed to do work. Hence the synchronous "one request one thread" form can also achieve asynchronous throughput, without having to sacrifice the programming model for resource efficiency.

| Dimension | Platform thread | Virtual thread |
|------|---------|---------|
| Mapping | 1:1 kernel thread | M:N, scheduled by the JVM onto carriers |
| Order of magnitude | Thousands | Millions |
| Stack | Fixed ~1MB | On demand, growable/shrinkable on the heap |
| Cost of blocking | Occupies a kernel thread | Unmounted, frees the carrier |
| Suitable for | CPU-intensive | IO-intensive, high concurrency |

**The pinning pitfall**: if a virtual thread cannot be unmounted when it blocks, it **pins** the carrier thread, weakening the advantage. The root cause lies in how the monitor lock is implemented—**in JDK 21–23**, the `ObjectMonitor` underlying a `synchronized` block records the lock's holder as the **current operating-system thread**, not the virtual thread itself; if a virtual thread is unmounted while holding the lock and later resumes execution mounted on a different carrier, the lock's holder identity no longer matches the OS thread actually running it, which breaks the underlying assumption the monitor implementation relies on—"the lock holder = some definite OS thread." To avoid this inconsistency, the JVM in JDK 21–23 chose to not unmount a virtual thread when it blocks inside a `synchronized` block, pinning the carrier directly, so the advice at the time was to switch critical sections involving blocking IO to `ReentrantLock` (whose lock state is recorded in a Java object and is not bound to an OS thread's identity). **From JDK 24 (JEP 491), the monitor implementation was rewritten to record the lock holder by tracking the virtual thread itself rather than the underlying OS thread**, eliminating this binding, so pinning caused by `synchronized` basically disappears and there is no longer a need to deliberately replace it with `ReentrantLock`. Calling a native method (JNI) still pins—for a different reason: a native stack frame is memory that genuinely belongs to the current OS thread's call stack, and the JVM has no ability to migrate a piece of executing native code together with its stack frame onto another carrier thread; this is a hard constraint of the OS-level thread model, not a matter of JVM implementation choice, so this class of pinning currently cannot be eliminated.

For the underlying memory barriers of `volatile`/CAS, review [03 Variables and the Memory Model](03-变量与内存模型.md). For tasks submitted to a thread pool and exception propagation, see [09 Error Handling and Resource Management](09-错误处理与资源管理.md).

## Summary

- **Usage**: `new Thread(() -> ...).start()` starts a thread, `join()` waits for it to finish; when two threads modify the same variable, wrap it with `synchronized`, or use `ReentrantLock`/`AtomicInteger`; for batches of tasks use a thread pool's `submit` and obtain results via `Future`/`CompletableFuture`; use `ConcurrentHashMap` instead of `HashMap` in concurrent scenarios; `Thread.ofVirtual()`/`newVirtualThreadPerTaskExecutor()` start virtual threads, with the same syntax as platform threads but creatable in the millions.
- **Principles**: the root cause of multithreading going wrong is that "working memory / main memory" in the JMM abstraction are not synchronized, and this is not an implementation oversight but the inevitable cost of compilers/CPUs only committing to single-threaded as-if-serial semantics—the three independent problems of visibility, ordering, and atomicity are guaranteed respectively by volatile/synchronized/happens-before and CAS, and no single tool can solve all three at the lowest cost simultaneously. `synchronized`'s lock state is recorded in the object header's mark word and goes through the upgrade biased lock → lightweight lock → heavyweight lock; behind the heavyweight lock are the four fields `Owner`/`EntryList`/`WaitSet`/`recursions` of `ObjectMonitor`; CAS is the hardware cornerstone of lock-free concurrency (but has the ABA problem); `ReentrantLock` is based on AQS; `ConcurrentHashMap` raises concurrency to the bucket level via "CAS for empty buckets + locking the head node of a non-empty bucket"; for thread pools, understand the submission flow of core/maximum thread count, queue, and rejection policy, and the context-switching cost behind the rule of thumb "thread count ≈ cores × (1 + wait time / compute time)"; virtual threads use M:N scheduling and the mount/unmount mechanism to solve, while preserving the synchronous programming model, the structural resource problem of "blocking IO occupying an entire kernel thread," but you must avoid the scenarios that cause pinning (pre-JDK 24 `synchronized` blocking, native calls).
- **Classification and selection**: there are four ways to create threads—extend Thread / implement Runnable / implement Callable+FutureTask / submit to a thread pool—differing in whether they have a return value and whether they can declare checked exceptions; "what locks are there in Java" is a cross-dimensional classification table (optimistic/pessimistic, fair/unfair, reentrant/non-reentrant, exclusive/shared, spin/blocking, segmented), and the same lock often falls into several dimensions at once; among IO models, BIO (blocking + synchronous), NIO (non-blocking + synchronous, via epoll/IOCP multiplexing), and AIO (non-blocking + asynchronous, via callbacks) are three generations of solutions to the "IO waiting occupies threads" problem before virtual threads appeared, and virtual threads solve the same problem afresh at the runtime layer while preserving the synchronous programming model.
