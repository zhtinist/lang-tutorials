# Error Handling and Resource Management: Exceptions and Garbage Collection

C++ uses exceptions for error propagation, RAII (destructors) for resource release, and manual `delete`/smart pointers for memory management. Java splits these three concerns into: the exception hierarchy, try-with-resources (an approximation of RAII), and **automatic garbage collection (GC)**.

## 1. Basic try/catch/finally

**Throwing and catching an exception** (dividing by 0 throws `ArithmeticException`):

```java
public class QuickTry {
    public static void main(String[] args) {
        try {
            int x = 10 / 0;          // throws ArithmeticException
            System.out.println("this line is never reached: " + x);
        } catch (ArithmeticException e) {
            System.out.println("caught exception: " + e.getMessage());
        } finally {
            System.out.println("finally always runs");
        }
        System.out.println("the program keeps going");
    }
}
// caught exception: / by zero
// finally always runs
// the program keeps going
```

Key points: `try` wraps the code that might fail; `catch (Type variable)` matches exceptions by type and catches them; the code in `finally` always runs once whether or not an exception occurred (commonly used for cleanup). After an exception occurs, the code in the `try` block from the failure point onward no longer executes (in the example above, the `println` on the `x` line does not run), and control jumps straight to the matching `catch`.

**Closing a resource once** (`try-with-resources`): in C you have to remember to `fclose` a file you opened; in Java, as long as a resource implements `AutoCloseable`, writing `try (...)` guarantees it is automatically closed when you are done, without hand-writing `finally { close(); }`:

```java
public class QuickTWR {
    // The simplest possible closeable resource: just implement AutoCloseable
    static class SimpleResource implements AutoCloseable {
        SimpleResource() { System.out.println("open resource"); }
        void use() { System.out.println("use resource"); }
        @Override public void close() { System.out.println("close resource"); }
    }

    public static void main(String[] args) {
        try (SimpleResource r = new SimpleResource()) {
            r.use();
        }
        System.out.println("close() was automatically called after the try block ended");
    }
}
// open resource
// use resource
// close resource
// close() was automatically called after the try block ended
```

For a resource declared inside the parentheses of `try (SimpleResource r = new SimpleResource())`, `close()` is automatically called once when the `try` block ends (whether it finishes normally or throws an exception) — this is the closest thing Java has to C++'s RAII/destructors.

There are still a few things to clear up: after an exception is thrown, how exactly does the JVM find which `catch` should handle it? Why does `finally` "always run"? When try-with-resources closes multiple resources, in what order does it do so, and what happens if `close()` itself throws? The following sections address these in turn.

## 2. The Exception Hierarchy: Checked vs Unchecked

Java exceptions fall into two broad categories. The practical difference when writing code is: **the compiler forces you to handle checked exceptions but does not force you to handle unchecked exceptions**.

```java
import java.io.*;

public class QuickChecked {
    // Checked exception: the method signature must declare throws, or it won't compile
    static void mightFail(boolean fail) throws IOException {
        if (fail) throw new IOException("simulated IO failure");
        System.out.println("read succeeded");
    }

    // Unchecked exception: no throws declaration required
    static int divide(int a, int b) {
        return a / b; // when b=0 it throws ArithmeticException; the compiler does not force handling
    }

    public static void main(String[] args) {
        try {
            mightFail(true);
        } catch (IOException e) {
            System.out.println("caught checked exception: " + e.getMessage());
        }

        try {
            divide(1, 0);
        } catch (ArithmeticException e) {
            System.out.println("caught unchecked exception: " + e.getMessage());
        }
    }
}
// caught checked exception: simulated IO failure
// caught unchecked exception: / by zero
```

If `mightFail` declares `throws IOException`, code that calls it must either catch it with `try/catch` or itself declare `throws IOException` on its own signature to propagate it outward — otherwise the compiler reports an error directly. The `ArithmeticException` thrown by `divide` has no such constraint; you may choose to catch it or ignore it, and the compiler will not intervene.

Everything throwable inherits from `Throwable`. It has two main branches:

```
                Throwable
               /         \
           Error        Exception
        (severe JVM-level faults)  /       \
     OutOfMemoryError  RuntimeException  others (checked)
     StackOverflowError  (unchecked)       IOException
                          NullPointerException  SQLException
                          IllegalArgumentException ...
```

| Category | Checked? | Semantics | C++ analogy |
|------|----------|------|----------|
| `Error` | No | Unrecoverable at the JVM level (stack overflow, heap exhaustion); **should not be caught** | Roughly system-level things like `std::bad_alloc` |
| `RuntimeException` | No | Programming errors (null pointer, out of bounds, illegal argument); should be prevented by code | Logic errors, similar to what an `assert` should catch |
| Checked `Exception` | Yes | Expected external failures (IO, network); **the compiler forces handling** | No C++ counterpart; the deprecated `throw()` specification is a negative example |

**Checked vs unchecked** is a compile-time constraint unique to Java: a checked exception must be declared in the method's `throws` clause or caught locally with `try/catch`, or the code won't compile. C++'s early dynamic exception specifications (`throw(...)`) were deprecated because they were hard to use; Java kept the concept but it too has been much debated.

The tree above only draws a few of the most common representatives; in practice you encounter far more. Here is a fuller list of common types organized by the three categories:

| Category | Common types | Trigger scenarios |
|------|----------|----------|
| `Error` | `OutOfMemoryError`, `StackOverflowError`, `NoClassDefFoundError` (a class definition can't be found at runtime), `VirtualMachineError` | JVM memory/resource exhaustion, class-loading failure, internal virtual-machine faults |
| Checked `Exception` | `IOException`, `FileNotFoundException`, `SQLException`, `ClassNotFoundException` (loading a nonexistent class by string name), `InterruptedException` (a thread was interrupted) | Failures of external resources such as files/network/databases, or interruption of thread cooperation |
| `RuntimeException` | `NullPointerException`, `ArrayIndexOutOfBoundsException`/`IndexOutOfBoundsException`, `ClassCastException` (a cast failed), `IllegalArgumentException`, `NumberFormatException` (a string-to-number format error), `ArithmeticException` | Null-pointer dereference, out-of-bounds access, illegal cast, argument-validation failure, number-parsing failure, illegal arithmetic (such as integer division by zero) |

```java
import java.io.*;
public class Checked {
    // Checked: must declare throws, otherwise a compile error
    static String readFirst(String path) throws IOException {
        try (BufferedReader r = new BufferedReader(new FileReader(path))) {
            return r.readLine();
        }
    }
    // Unchecked: no declaration needed, the compiler doesn't intervene
    static int div(int a, int b) { return a / b; } // b=0 throws ArithmeticException
}
```

#### Why design a separate `Error` class instead of letting the program crash outright

`Error` and `Exception` both inherit from the same `Throwable`, and this is not an arbitrary class-hierarchy arrangement: even though the problems `Error` represents (stack overflow, heap exhaustion, internal JVM faults) are essentially "unrecoverable" and "should not be caught and handled by business code," Java still wraps them into an object that can carry information, rather than having the JVM silently terminate the process — the reason is that **a unified throwable-object hierarchy brings unified diagnostic capability**: whether the program dies from a business-logic error or from a system-level fault, in the end it all propagates upward through the same stack-unwinding mechanism (detailed in the next section), all of it can print a consistently formatted stack trace (which class, which line, what the call chain was), and all of it can be uniformly logged at the outermost layer. If `Error` were not part of this hierarchy, the JVM would have to terminate in a completely separate, non-programmable way when it hit a stack overflow or memory exhaustion (for example, printing a C-level crash message directly and then exiting), and operators and developers would lose the means of capturing "what exactly did the program die from" through the familiar Java exception-handling mechanism (even if only as a catch-all log like `catch (Throwable t) { log(t); }`). Syntactically you can indeed write `catch (Error e)` or even `catch (Throwable t)`, but this should only be used for catch-all actions such as logging or resource cleanup, and you should not expect the program to keep working normally after catching it — the information an `Error` carries is a diagnostic clue for humans, not a signal for program logic to decide which way to go.

#### Why distinguish checked from unchecked exceptions instead of having just one kind like C++/Python

This is the direct manifestation, in terms of compiler enforcement, of two different error-handling philosophies. For checked exceptions, Java chooses **compile-time fail-fast**: the moment a method declares it may throw `IOException`, all callers must either handle it explicitly or continue to declare it outward, and the compiler forces you to face the fact that "this may fail here" the instant you write the call statement — the upside is that operations destined to fail in certain environments (files/network and the like) won't be accidentally forgotten by developers, and the downside is a large amount of boilerplate `try/catch`/`throws` declarations, plus developers who write empty `catch` blocks that swallow exceptions just to make the code compile, thereby manufacturing a false sense of robustness. Languages like C++ and Python choose **runtime discovery**: exceptions don't appear in method signatures, the compiler doesn't check them at all, the code is more concise, but a call that may fail — if nobody remembers to wrap it in a `try` — pushes the problem off until the program actually runs to that line and actually fails, which may be long after the production release. Java's trade-off is to exchange compile-time verbosity for runtime predictability, applying mandatory checking only to exceptions of the kind "the external environment fails and the program logic cannot avoid it" (IO, network, database), while excluding from mandatory checking those of the kind "programming error, which should be avoided by writing correct code" (null pointer, array out of bounds, illegal argument) — this is precisely the meaning of "should be prevented by code" on the `RuntimeException` row of the [table above](#the-exception-hierarchy-checked-vs-unchecked): checking for this kind of error shouldn't be a runtime matter but something that should be blocked during development by testing and code review, and there is little point in the compiler getting involved.

#### Wrapping a checked exception in an unchecked one and rethrowing it

In practice a common situation arises: a low-level API (such as reflection or serialization) must declare a checked exception in its signature, but the business-logic layer that calls it actually believes this exception "can't possibly happen" or "even if it happens, there's no way to recover at this layer," and forcing `throws` declarations all the way down would pollute a long chain of method signatures. A common approach is to **wrap** the checked exception into an unchecked one at this layer and rethrow it, while using exception chaining to preserve the root cause (echoing the `cause` in Section 5):

```java
static void loadConfig(String name) {
    try {
        Class.forName(name);                 // declares throws ClassNotFoundException (checked)
    } catch (ClassNotFoundException e) {
        throw new IllegalStateException("config class missing: " + name, e);  // convert to unchecked, attach root cause
    }
}
```

The benefit is that the caller's method signatures are no longer forced to declare `throws` layer after layer; the cost is that if the caller really does want to do something special for this specific failure, it needs an extra `instanceof`/`getCause()` check, unlike a checked exception which is directly visible in the signature — this is a deliberate trade-off: it downgrades the "this will almost never fail, and even if it does there's no way to recover gracefully" scenario from compiler-mandated handling to optional handling.

## 3. try/catch/finally and Stack Unwinding

The `finally` block runs once whether the `try` returns normally or throws an exception — the `QuickTry` example in the previous section already demonstrated this: even though `10 / 0` threw an exception, the `println` in `finally` still ran. This makes it well suited for placing cleanup actions that must happen whether or not things succeed, such as logging or releasing resources that are not `AutoCloseable`.

When an exception is thrown, the JVM starts from the current method and looks up its **exception table** — `javac` generates a `[start PC, end PC, handler PC, catch type]` record for each `try` block. If the current frame has no matching handler, that frame is popped (stack unwinding), and control walks back up the call chain until a matching `catch` is found or it reaches the bottom of the thread's stack (at which point the thread terminates and prints a stack trace).

`finally` executes whether things go normally or an exception occurs. At the bytecode level, the compiler **copies** the `finally` code onto every normal/exception exit path (or falls back to the exception table + `athrow`); this is how it achieves "guaranteed execution."

```java
public class Finally {
    static int tricky() {
        try {
            return 1;          // computes the return value 1 and pushes it on the stack first
        } finally {
            return 2;          // the return in finally overrides it -> actually returns 2 (anti-pattern!)
        }
    }
    public static void main(String[] args) {
        System.out.println(tricky()); // 2
    }
}
```

> Pitfall: a `return` or a thrown exception in `finally` swallows the return value/exception from the `try`. Never `return` inside `finally`.

## 4. try-with-resources: Java's RAII

The previous section's `QuickTWR` already showed the most basic usage: a resource class implements `AutoCloseable`, is written inside the `try (...)` parentheses, and `close()` is then automatically called when the `try` block ends — whether the block completes normally or throws an exception partway through.

C++ relies on **destructors** for deterministic resource release when an object leaves scope (RAII). The reclamation timing of a Java object is uncertain (the GC decides), so you can't rely on `finalize` to close a file. JDK 7 introduced **try-with-resources**: any object implementing `AutoCloseable` (`close()`) is **guaranteed** to have `close()` called in the reverse of its declaration order when the try block ends — this is Java's closest form of deterministic resource management to RAII.

```java
import java.io.*;
public class TWR implements AutoCloseable {
    private final String name;
    TWR(String name) { this.name = name; System.out.println("open " + name); }
    @Override public void close() { System.out.println("close " + name); }

    public static void main(String[] args) {
        // reverse-order closing: close b first, then close a (similar to C++ local objects destructing in reverse)
        try (TWR a = new TWR("A"); TWR b = new TWR("B")) {
            System.out.println("body");
            throw new RuntimeException("boom");
        } catch (RuntimeException e) {
            System.out.println("caught: " + e.getMessage());
            // exceptions thrown by close are attached to the primary exception as "suppressed exceptions":
            for (Throwable s : e.getSuppressed()) System.out.println("suppressed: " + s);
        }
    }
    // output: open A / open B / body / close B / close A / caught: boom
}
```

The difference from C++: the call site of `close()` is instrumented by the compiler at the try exit, while the **object's memory itself** is still reclaimed by the GC later. That is, "deterministic release of resources (fd/handle)" and "non-deterministic reclamation of memory" are two separate things.

The `close()` above throws no exception, so `getSuppressed()` is empty. Only when **both the try body and `close()` throw** do you see the "suppressed exception" mechanism: the primary exception is the one thrown by the try body, and the exceptions of the two `close()` calls are attached to the primary exception in reverse order:

```java
public class Suppressed implements AutoCloseable {
    private final String name;
    Suppressed(String name){ this.name = name; }
    @Override public void close() {
        System.out.println("close " + name);
        throw new RuntimeException("close-fail-" + name);   // close() itself also throws
    }
    public static void main(String[] args) {
        try (Suppressed a = new Suppressed("A"); Suppressed b = new Suppressed("B")) {
            throw new RuntimeException("body-fail");         // primary exception
        } catch (RuntimeException e) {
            System.out.println("primary   : " + e.getMessage());
            for (Throwable s : e.getSuppressed())            // exceptions thrown by close are attached here
                System.out.println("suppressed: " + s.getMessage());
        }
    }
}
// close B                   <- reverse-order closing
// close A
// primary   : body-fail     <- the try body's exception wins as the primary exception
// suppressed: close-fail-B  <- close's exceptions are "suppressed," attached in reverse order
// suppressed: close-fail-A
```

## 5. Multi-catch and Exception Chaining

Separating multiple types with `|` in a single `catch` lets you use one piece of handling logic to catch different kinds of exceptions without writing duplicate code:

```java
public class QuickMultiCatch {
    static void parse(String s) {
        if (s == null) s.length();   // calling a method on null triggers NullPointerException directly
        Integer.parseInt(s);         // throws NumberFormatException when the format is wrong
    }

    public static void main(String[] args) {
        String[] inputs = { null, "abc" };
        for (String s : inputs) {
            try {
                parse(s);
            } catch (NumberFormatException | NullPointerException e) {
                // one catch handles both types at once
                System.out.println("parse failed: " + e.getClass().getSimpleName());
            }
        }
    }
}
// parse failed: NullPointerException
// parse failed: NumberFormatException
```

```java
public class MultiCatch {
    static void handle(String s) {
        try {
            Integer.parseInt(s);
        } catch (NumberFormatException | NullPointerException e) {
            // multi-catch: one catch handles several types; e is implicitly final, with the common supertype
            // exception chaining: preserves the "root cause (cause)," making it easy to locate the original fault
            throw new IllegalStateException("handling failed: " + s, e);
        }
    }
    public static void main(String[] args) {
        try { handle(null); }
        catch (IllegalStateException e) {
            System.out.println(e.getMessage());
            System.out.println("root cause: " + e.getCause());
            // root cause: java.lang.NumberFormatException: Cannot parse null string
            // note: in modern JDKs Integer.parseInt(null) already checks for null explicitly and throws
            // NumberFormatException("Cannot parse null string") directly, rather than an NPE --
            // catching both types here still makes sense: switch to another parsing approach (e.g. take s.length() manually first),
            // and the null-pointer path would go down the NullPointerException branch.
        }
    }
}
```

Exception chaining (`initCause` / a constructor taking a cause) lets you translate an exception without losing the original stack trace; when printed, a `Caused by:` section appears.

## 6. IO Streams: The Classic Scenario for Deterministic Resource Management

The `AutoCloseable`, stack unwinding, and suppressed exceptions covered in the previous sections almost always revolve, in real code, around the single concern of "a stream must be closed after use" — files and sockets are the most common non-memory resources that must be closed explicitly (echoing the line in [Runtime Model](01-运行模型.md): "memory is handed to the GC, but handles still need explicit closing"). This section runs through Java's IO type hierarchy while reinforcing try-with-resources once more.

### Byte Streams vs Character Streams: Why Two Type Hierarchies Are Needed

C uses one set of `FILE*` + `fread`/`fwrite` to handle any data source, without distinguishing "is this pile of bytes text or not." Java splits its IO type hierarchy in two from the root:

- **Byte streams**: `InputStream`/`OutputStream` and their subclasses, working in units of bytes (8 bits), oriented toward arbitrary binary data (images, video, serialized objects).
- **Character streams**: `Reader`/`Writer` and their subclasses, working in units of characters, automatically handling byte-to-character encoding conversion internally.

**Why you can't get by with only byte streams and need a whole separate set of character streams**: bytes and characters are not the same thing — the same Chinese character is 3 bytes in UTF-8, 2 bytes in GBK, and 2 bytes in UTF-16; if there were only byte streams, any "read a line of text" operation would require the caller to manually specify the encoding, manually assemble the bytes, and manually judge whether a multi-byte character got cut in the middle (a read-buffer boundary landing exactly in the middle of a multi-byte character is a classic source of garbled text). Java encapsulates this "byte ↔ character" encoding-conversion layer into `Reader`/`Writer` (done via the two bridge classes `InputStreamReader`/`OutputStreamWriter`), so that when you program against a `Reader`, what `readLine()`/`read()` return is already a correctly decoded `char`, and you needn't worry about how many bytes a character is or whether boundaries get cut. The cost is an extra parallel type hierarchy (every byte-stream concept conceptually has a corresponding character-stream version); in exchange, "handling text" and "handling binary" are each type-safe and can't be misused for each other — nobody accidentally hard-decodes a JPEG as UTF-8 text.

### Node Streams vs Processing Streams: The Decorator Pattern

**Node streams** such as `FileInputStream` wrap a real data source directly (a file, socket, or in-memory array); **processing streams (wrapper streams)** such as `BufferedInputStream`, `DataInputStream`, and `ObjectInputStream` don't connect to a data source directly but wrap another stream and layer functionality on top of it:

```java
new BufferedReader(new InputStreamReader(new FileInputStream("a.txt"), StandardCharsets.UTF_8))
```

This line, from inside out: `FileInputStream` opens the file and yields a byte stream → `InputStreamReader` decodes the bytes into a character stream by UTF-8 → `BufferedReader` wraps another buffering layer around the character stream and provides `readLine()`. This is exactly the **decorator pattern** — each layer adds only one capability without changing the wrapped object's interface (all implement the same `Reader`/`InputStream` abstraction), stacking layer upon layer. It is a concrete embodiment of the "composition over inheritance" section in [Object Orientation and the Type System](08-面向对象与类型系统.md): Java doesn't need to write a dedicated class for a "buffered, line-reading, UTF-8-decoding file stream," but composes one from a few single-responsibility classes.

### Reading and Writing Files Correctly with try-with-resources

```java
import java.io.*;
import java.nio.charset.StandardCharsets;

public class IoDemo {
    public static void main(String[] args) throws IOException {
        try (BufferedReader br = new BufferedReader(
                new InputStreamReader(new FileInputStream("input.txt"), StandardCharsets.UTF_8));
             BufferedWriter bw = new BufferedWriter(
                new OutputStreamWriter(new FileOutputStream("output.txt"), StandardCharsets.UTF_8))) {
            String line;
            while ((line = br.readLine()) != null) {
                bw.write(line);
                bw.newLine();
            }
        }
    }
}
```

Multiple resources are written in the same `try (...)` separated by semicolons, and the close order is still the **reverse** of the declaration order (close `bw` first, then `br`) — exactly the same rule as the `TWR` example in Section 4.

### The Relationship Between flush and close

`BufferedWriter`/`BufferedOutputStream` accumulate a buffer internally, so a `write()` call doesn't necessarily reach the underlying file immediately — `flush()` forces the buffer contents down to the underlying layer, and `close()` internally does a `flush()` first and then releases the underlying resource (the file descriptor). If you forget to `flush` and also don't use try-with-resources, the data in the buffer may be lost if the program exits abnormally; this is one more reason try-with-resources is preferred over a hand-written `finally { close(); }` — you don't have to remember the close order and the flush timing, as the compiler's instrumentation handles it all.

### A Brief Note on NIO

`java.nio` provides an alternative `Channel` + `Buffer` model that supports non-blocking IO and more efficient throughput for large files/networks. APIs like `Files.copy()` and `FileChannel.transferTo()` are commonly used for copying large files (and can leverage zero-copy). This model runs in parallel to the traditional `java.io` streams as a separate path; the details are beyond this chapter.

## 7. Garbage Collection (GC)

In C and C++, memory is yours to manage: `malloc`/`free`, `new`/`delete`; forget to `free` and you leak, `free` one extra time and you crash. Java has no `delete` — for the objects you `new`, when they are released and by whom is entirely handed to a background mechanism: the **garbage collector (GC)**. It sweeps the heap at appropriate times and reclaims the memory of objects that "nobody can reach anymore." The cost: you don't know the exact reclamation moment, and reclamation itself may cause the program to stall briefly (a "pause"/STW). Understanding how the GC works is what lets you read the logs and tune the right parameters when problems arise.

The GC runs automatically throughout; there aren't many APIs you can call directly, mainly `WeakReference`/`SoftReference`/`Cleaner`/`System.gc()` — these still follow the "how to use it first, then the internals" order. Purely conceptual content like "the generational hypothesis" and "how collectors evolved" goes straight into the internals discussion.

## 8. The Generational Hypothesis and Heap Layout

This part is purely explanatory — the GC runs on its own and you don't need to write code to trigger it, but understanding how the heap is partitioned is what lets you understand the later "how to choose a collector" and "which tuning parameter to change."

The GC is built on the **weak generational hypothesis**: the vast majority of objects die young; objects that live long rarely point to young objects. So the heap is managed generationally:

```
                Java heap
 +---------------------------------------------------+
 | Young Gen                                         |
 |  +----------+  +----------+  +----------+         |
 |  |  Eden    |  | Survivor |  | Survivor |         |
 |  | (new obj)|  |   S0     |  |   S1     |         |
 |  +----------+  +----------+  +----------+         |
 +---------------------------------------------------+
 | Old Gen (Tenured)  long-lived objects             |
 +---------------------------------------------------+
   (Metaspace lives in native memory, holds class metadata, and is not on the heap)
```

- New objects are allocated in **Eden** (pointer bumping, extremely fast, similar to advancing a stack top).
- When Eden fills up, a **Minor GC** is triggered: surviving objects are copied to one of the Survivors, with age +1; each time an object survives a Minor GC its age grows, and once it exceeds a threshold (default 15, `-XX:MaxTenuringThreshold`) it is promoted to the old generation. The two Survivors take turns being the "copy target," so one is always empty (the copying algorithm, which avoids fragmentation).
- When the old generation fills up, a **Major GC** (old-generation collection) is triggered; a **Full GC** usually means collecting the whole heap + Metaspace, is the slowest, and should be avoided as much as possible. (Note: "Major GC" is a **classic term of generational collectors**; modern collectors such as G1/ZGC use different terminology — G1 distinguishes young / mixed / full, where `Full GC` is its fallback whole-heap collection when it degrades.)

| GC type | Reclamation scope | Trigger | Pause |
|---------|----------|------|------|
| Minor GC | Young gen | Eden full | Short |
| Major GC | Old gen | Old gen full | Long |
| Full GC | Whole heap + Metaspace | Old gen/Metaspace short of space, `System.gc()` | Longest |

### The Three Basic Reclamation Algorithms, and Why the Young and Old Generations Each Use a Different One

The mention above of "the two Survivors take turns being the copy target" is backed by the **copying algorithm**; the Major GC triggered when the old generation fills up uses a different set of algorithms. Placing all three basic algorithms side by side makes it clear how the "generational collection" strategy actually lands as a concrete choice of algorithms:

| Algorithm | Approach | Pros | Cons | Where used |
|------|------|------|------|--------|
| Mark-Sweep | Mark all surviving objects, sweep the unmarked ones | No need to move objects; low overhead when many objects survive | Produces fragmentation; marking and sweeping each scan the heap once, a two-pass cost | Old gen (high survival rate, high cost to move) |
| Copying | Copy surviving objects wholesale to another space, clear the original space entirely | Only one scan, completing compaction along the way, no fragmentation | Needs a spare space of equal size; when many objects survive, copying cost overtakes the savings | Young gen (low survival rate under the weak generational hypothesis, low copying cost) |
| Mark-Compact | After marking surviving objects, move them compactly to one end of memory, then clear the space beyond the boundary | No fragmentation, no double space needed | Moving objects has its own overhead (all references pointing to them must be updated in sync) | Old gen (a compromise between "no double space" and "no fragmentation") |

**Why the young generation uses copying and the old generation uses mark-compact/mark-sweep**: this is precisely the direct corollary of the weak generational hypothesis — in the young generation objects "die young," so a single Minor GC usually has only a few surviving objects, and the cost of the copying algorithm is proportional to the **number of surviving objects** rather than the total heap size, so when the survival rate is low, copying is almost free compaction; the old generation is the reverse, with a high survival rate, and if it still used copying, most of the heap contents would have to be copied over, and the copying algorithm inherently needs to reserve half the space as a "spare area," which is an unacceptable double waste on the large space of the old generation. So the old generation chooses to clean in place directly (mark-sweep) or compact in place (mark-compact) — which one to choose is a trade-off between "sweeping is fast but leaves fragmentation" and "compacting is slow but leaves none," and different collectors give different answers (detailed in the next section).

The **generational collection algorithm** is not a "fourth algorithm" on par with the previous three, but the **strategy** itself of "partition the heap and choose the algorithm best suited to each region" — it is the combined application of the three algorithms above under the premise of the "weak generational hypothesis," and the Eden/Survivor/old-generation layout is the concrete landing of this strategy.

## 9. Reachability Analysis and GC Roots

Java **does not use reference counting** (which can't handle circular references), but uses **reachability analysis**: starting from a set of **GC Roots**, it traverses the reference graph, and any object that is unreachable can be reclaimed.

GC Roots include:

- References in each thread's **stack-frame local-variable table** (objects referenced by methods currently executing);
- Objects referenced by **static fields**;
- Constant-pool references, JNI global references;
- Objects held by synchronization locks, and so on.

```
GC Roots
  | thread-stack local variable  ---> A ---> B      (A, B reachable, alive)
  | static field                 ---> C
                          C <---> D    (C, D reference each other)
                                E ---> F  (E, F reference each other but no Root reaches them => both reclaimed)
```

Note the last group: `E` and `F` reference each other in a cycle; reference counting would wrongly judge them as alive, whereas reachability analysis correctly determines they are garbage. This is precisely why Java doesn't use reference counting.

## 10. Collector Evolution and the STW Trade-off

**STW (stop-the-world)**: certain phases of the GC must pause all application threads (which reach a "safepoint") to obtain a consistent snapshot of the heap. The evolutionary history of collectors is essentially the history of **continually shortening STW**.

| Collector | Characteristics | STW | Suitable for |
|--------|------|-----|------|
| Serial | Single-threaded, simple | Full STW, relatively long | Small heaps, client-side |
| Parallel (throughput-first) | Multi-threaded parallel collection | STW but parallel | Batch processing, throughput-heavy |
| CMS (deprecated in JDK 9, **removed in JDK 14**) | Concurrent mark-sweep, a low-pause pioneer | Partially concurrent | Low-latency old gen (has fragmentation problems) |
| **G1** (default since JDK 9) | Region-partitioned, predictable pause targets | Short STW, mostly concurrent | General-purpose for large heaps |
| ZGC | Colored pointers + read barriers | Pauses <1ms, independent of heap size | Very large heaps, low latency |
| Shenandoah | Concurrent compaction | Extremely short pauses | Low latency |

The core of the trade-off is **throughput vs latency**: Parallel pursues doing the most work per unit time (suitable for background batch processing); ZGC/Shenandoah sacrifice a little throughput for nearly imperceptible pauses (suitable for interactive/online services). There is no "best," only "best matched to the scenario."

Selection: `-XX:+UseG1GC`, `-XX:+UseZGC`, `-XX:+UseParallelGC`.

### Three Easily Confused Terms

- **Throughput** = user-code run time / (user-code run time + GC time) — measures the proportion of time spent "doing real work" per unit time, which the Parallel family of collectors directly optimizes for.
- **Concurrent** = GC threads and user threads run **at the same time** without blocking each other — the marking phases of CMS/G1/ZGC are mostly concurrent.
- **Parallel** = multiple GC threads work **at the same time**, but user threads are still in an STW pause — both Parallel and ParNew are "multi-threaded parallel, but user threads wait." The three are not mutually exclusive: in a single G1 collection, some phases execute in parallel (multiple GC threads mark together) and some phases execute concurrently (running at the same time as user threads).

**ParNew, not listed in the table**: it is the multi-threaded version of Serial (also the copying algorithm), and the only reason it existed is that **it was once the only young-generation collector that could work together with CMS** — CMS only handles the old generation, and the young generation still needs a separate collector to pair with, and ParNew was the "young-generation partner" born to pair with CMS. Now that CMS has been removed in JDK 14, ParNew has lost its reason to exist along with it.

**The four phases of CMS** reveal exactly how "low pause" is bought: initial mark (**STW**, marks only the objects directly associated with GC Roots, fast) → concurrent mark (runs together with user threads, marks all reachable objects, the most time-consuming but non-pausing) → remark (**STW**, corrects the changes produced during concurrent marking because user threads kept running, usually slightly longer than initial mark) → concurrent sweep (runs together with user threads, cleans up unmarked objects). Both STW phases are compressed to the small scope of "doing only incremental correction," while the bulk of marking and sweeping is placed in concurrent phases — this is the core idea behind it being the "low-pause pioneer," at the cost of the fragmentation brought by the mark-sweep algorithm, plus the **Concurrent Mode Failure** that occurs when user threads fill up the old-generation space during concurrent cleanup (at which point it degrades into a full STW collection by Serial Old, whose pause is instead longer than not using CMS at all).

**The four phases of G1** are structurally similar to CMS but have one more step: initial mark (STW) → concurrent mark (concurrent with user threads) → final mark (STW, handling reference changes during concurrent marking) → live-data selection and collection (STW, but because the heap is divided into a large number of Regions, G1 picks a batch of the "highest reclamation-yield" Regions to process first, using the copying algorithm to complete compaction along the way, thereby avoiding CMS's fragmentation problem). G1's most fundamental difference from CMS is its **Region-based heap layout**: no longer a contiguous young/old generation, but sliced into a large number of fixed-size small blocks, each of which can independently play the role of Eden/Survivor/old generation. At GC time it computes a cost-effectiveness account of "garbage ratio / reclamation time" for each Region and reclaims the most worthwhile ones first — this turns "pause time" from "however big the whole old generation is, that's how long you pause" into a target that can be softly controlled via `-XX:MaxGCPauseMillis`.

**The evolution of the JDK's default collector** reveals the shift in the community's attitude toward "latency over throughput": JDK 8's default was the Parallel Scavenge (young gen) + Parallel Old (old gen) combination, throughput-first; from JDK 9 the default changed to G1; and even after ZGC/Shenandoah became officially supported, they still need to be explicitly specified to be enabled and have not become the default in any LTS version.

## 11. finalize Deprecation and Cleaner

To release resources, always prefer the `try-with-resources`/explicit `close()` you already know — it is deterministic and executes immediately when you're done. `Cleaner` is only a safety net for "in case you forget to call `close()`," and should not be treated as the primary means:

```java
import java.lang.ref.Cleaner;

public class QuickCleaner implements AutoCloseable {
    private static final Cleaner CLEANER = Cleaner.create();
    private final Cleaner.Cleanable cleanable;

    QuickCleaner() {
        // register a "fallback cleanup action for when close is forgotten"
        cleanable = CLEANER.register(this, () -> System.out.println("fallback cleanup triggered"));
    }

    @Override
    public void close() {
        System.out.println("explicit close() was called"); // preferred path: deterministic, immediate
        cleanable.clean();                          // manually trigger cleanup; the fallback action won't run again afterward
    }

    public static void main(String[] args) {
        try (QuickCleaner r = new QuickCleaner()) {
            System.out.println("use resource");
        }
        // because try-with-resources already called close(), the fallback Cleaner action prints only once
    }
}
// use resource
// explicit close() was called
// fallback cleanup triggered
```

Actively calling `cleanable.clean()` inside `close()` executes the cleanup action immediately once; if you forgot to write `try-with-resources` and this object eventually becomes unreachable, the background thread inside `Cleaner` will also automatically run the same action once after GC — but that is a "last line of insurance," not the primary path you should depend on.

C++ destructors execute deterministically. Java's `Object.finalize()` once wanted to play this role, but its **execution timing is uncertain, it may never execute, it slows down the GC, and it can even resurrect objects**. It was marked `@Deprecated` in JDK 9 and further deprecated for removal starting in JDK 18.

Alternative: **`java.lang.ref.Cleaner`**, which registers a cleanup action that a background thread executes when the object becomes phantom-reachable. But it is still non-deterministic — **always release critical resources explicitly with try-with-resources**, and use Cleaner only as a last-resort fallback.

```java
import java.lang.ref.Cleaner;
public class CleanerDemo implements AutoCloseable {
    private static final Cleaner CLEANER = Cleaner.create();
    // the cleanup action must be a static/standalone class and must never hold a reference to the outer object, or the object will never be reclaimable
    static class State implements Runnable {
        public void run() { System.out.println("release native resource (fallback)"); }
    }
    private final Cleaner.Cleanable cleanable;
    CleanerDemo() { cleanable = CLEANER.register(this, new State()); }
    @Override public void close() { cleanable.clean(); } // explicit path: deterministic release
}
```

## 12. Reference Strength: Strong/Soft/Weak/Phantom

The `Object o = new Object()` you write day to day is a **strong reference** — as long as it is reachable, the GC will never touch it. If you want the effect of "I still want to use this object, but when memory is tight it can be sacrificed first," wrap it in a `WeakReference`:

```java
import java.lang.ref.WeakReference;

public class QuickWeakRef {
    public static void main(String[] args) {
        Object obj = new Object();
        WeakReference<Object> weak = new WeakReference<>(obj); // wrap in a weak reference
        System.out.println("before get(): " + (weak.get() != null)); // true -- the strong reference obj still exists

        obj = null;      // remove the only strong reference
        System.gc();      // suggest the JVM do a garbage collection (not guaranteed to run immediately)
        System.out.println("after get(): " + weak.get()); // very likely null
    }
}
// before get(): true
// after get(): null
```

What `weak.get()` returns is the referenced object, or `null` (if already reclaimed). As long as the strong reference `obj` is still there, `weak.get()` stays valid; once you set `obj` to null and no other strong reference points to it, the GC has the right to reclaim it, and `weak.get()` becomes `null` accordingly.

`java.lang.ref` provides four reference strengths, which determine an object's "right to survive" in the eyes of the GC:

| Strength | Class | GC behavior | Typical use |
|------|-----|---------|----------|
| Strong reference | plain `Object o = ...` | Never reclaimed while reachable | Default |
| Soft reference | `SoftReference` | Reclaimed only **when memory is insufficient** | Memory-sensitive caches |
| Weak reference | `WeakReference` | Reclaimed at the next GC | `WeakHashMap`, canonicalizing maps |
| Phantom reference | `PhantomReference` | The object can never be retrieved; used only for reclamation notification | Cleanup as a replacement for finalize |

**Soft references: memory-sensitive caches**

The semantics of a soft reference are "keep it if memory isn't tight, sacrifice it first if it is" — which is naturally suited for caching: a cache hit improves performance, but the cache itself is not something that can't be dropped, and when memory is critical it should give way to business logic first rather than leaving an OOM to the user. The example below first confirms that a soft reference lives well when memory is ample, then deliberately blows up the heap toward OOM to observe the soft reference being cleared before `OutOfMemoryError`:

```java
import java.lang.ref.SoftReference;
import java.util.ArrayList;
import java.util.List;

public class SoftCache {
    public static void main(String[] args) {
        SoftReference<byte[]> cache = new SoftReference<>(new byte[1024 * 1024]); // simulate 1MB of cached data
        System.out.println("just created: " + (cache.get() != null));

        System.gc(); // a routine GC with ample memory almost never touches soft references
        System.out.println("after normal GC (ample memory): " + (cache.get() != null));

        try {
            List<byte[]> hog = new ArrayList<>();
            while (true) hog.add(new byte[4 * 1024 * 1024]); // greedily eat memory, approaching OOM
        } catch (OutOfMemoryError e) {
            System.out.println("soft reference already reclaimed when OOM triggers: " + (cache.get() == null));
        }
    }
}
// run with java -Xmx64m SoftCache:
// just created: true
// after normal GC (ample memory): true
// soft reference already reclaimed when OOM triggers: true
```

The JVM guarantees: **before throwing `OutOfMemoryError`, it will always clear all soft references first and retry the allocation** — this is the precise meaning of "insufficient" in the soft reference's "reclaimed only when memory is insufficient": not some percentage threshold, but the last moment where "if we don't clear you, we're about to OOM." So a soft-reference cache will never cause an OOM (it gets sacrificed before the OOM), but it also means that once reclaimed, the cache is cleared **wholesale**, not selectively by a strategy like LRU — if you need a finer eviction policy, use a cache that explicitly manages capacity, such as Guava Cache/Caffeine, rather than relying on soft references.

```java
import java.lang.ref.*;
public class Refs {
    public static void main(String[] args) {
        ReferenceQueue<byte[]> queue = new ReferenceQueue<>();
        byte[] data = new byte[1024];
        // weak reference + reference queue: after the object is reclaimed, ref is enqueued, letting you perceive the reclamation
        WeakReference<byte[]> weak = new WeakReference<>(data, queue);
        data = null;          // remove the only strong reference
        System.gc();          // suggest GC (not guaranteed to run immediately)
        System.out.println("get() after reclamation: " + weak.get()); // very likely null
        Reference<?> polled = queue.poll();                 // the reclaimed reference has been enqueued
        System.out.println("enqueued: " + (polled == weak));
    }
}
```

**ReferenceQueue** is a companion mechanism: when a referenced object is reclaimed, the JVM places the corresponding `Reference` object into the queue, and your cleanup thread performs the follow-up after it `poll`s it out (this is exactly how Cleaner is implemented internally).

**Phantom references: used only to "perceive" reclamation, cannot retrieve the object itself**

The `get()` of a weak/soft reference can at least retrieve the instance before the object is reclaimed; a phantom reference's `get()` **always returns `null`** from the moment it is created — its only purpose is to put itself into a `ReferenceQueue` after the associated object is determined reclaimable, letting your code know "after the fact" that "this object is gone," so as to trigger a cleanup action. This is the meaning of the name "phantom reference":

```java
import java.lang.ref.PhantomReference;
import java.lang.ref.ReferenceQueue;

public class PhantomDemo {
    public static void main(String[] args) throws InterruptedException {
        ReferenceQueue<Object> queue = new ReferenceQueue<>();
        Object target = new Object();
        PhantomReference<Object> phantom = new PhantomReference<>(target, queue);

        System.out.println("phantom.get() is always null: " + (phantom.get() == null));

        target = null;             // remove the only strong reference
        System.gc();
        Thread.sleep(200);         // give the Reference Handler thread a little time to enqueue

        System.out.println("phantom reference enqueued after object reclamation: " + (queue.poll() == phantom));
    }
}
// phantom.get() is always null: true
// phantom reference enqueued after object reclamation: true
```

A typical use is cleaning up **off-heap resources**: the off-heap memory behind a `DirectByteBuffer` is not directly managed by the GC, and internally the JDK uses a phantom-reference-like mechanism to trigger the release of off-heap memory at the same time as the Java object itself is reclaimed — the phantom reference is responsible for "knowing it's time to clean up," while the actual cleanup action (calling a native method to free memory) is done by the cleanup logic you register. This is exactly the underlying principle of the `cleanable.clean()` fallback path in the earlier "finalize Deprecation and Cleaner" section.

The most common concrete use of weak references is `WeakHashMap`: the key is held only by a weak reference, and once there are no more external strong references, the entry disappears automatically after GC — naturally suited for canonicalizing caches, avoiding the "add-only, never-remove" leak:

```java
import java.util.*;
public class WeakMap {
    static void seed(Map<Object,String> m) {          // the keys live only in this stack frame
        m.put(new Object(), "v");
        m.put(new Object(), "v");
    }
    public static void main(String[] args) throws Exception {
        Map<Object,String> weak = new WeakHashMap<>();
        seed(weak);
        System.out.println("before GC  weak.size = " + weak.size());
        System.gc();
        Thread.sleep(100);
        System.out.println("after  GC  weak.size = " + weak.size());
    }
}
// before GC  weak.size = 2
// after  GC  weak.size = 0    <- keys have no strong references, so entries are cleared after GC
// (note: if you keep the keys in a local variable of main, they become GC Roots and are not reclaimed)
```

## 13. What a Memory Leak Looks Like in Java

Having a GC does not mean there are no memory leaks. A leak = **an object is logically no longer useful but is still reachable from GC Roots**, so the GC doesn't reclaim it. Common forms:

- **A long-lived collection that only adds, never removes**: a `static Map`/cache keeps `put`-ing, and keys and values are forever reachable. Use `WeakHashMap` or set a capacity limit (such as a Guava/Caffeine cache).
- **A listener/callback not deregistered**: an observer forgets to `removeListener` after registering, and stays referenced by the subject object.
- **A `ThreadLocal` not `remove`d**: a thread-pool thread lives long, and the `ThreadLocal`'s value stays reachable along with the thread. You must `remove()` when done.
- **An inner class implicitly holding the outer instance**: a non-static inner class/anonymous class holds `Outer.this`, and if its lifetime is longer than the outer object's, the outer object can't be reclaimed (same origin as the caution in the Cleaner section).

### Why Weak References Didn't Fully Prevent ThreadLocal Leaks

A `ThreadLocal`'s value actually lives in each thread's own `ThreadLocalMap`, and this Map's `Entry` is cleverly designed: `Entry extends WeakReference<ThreadLocal<?>>` — **the key (the `ThreadLocal` instance itself) is a weak reference, and the value (the business object you stuffed in) is a strong reference**. The intent of this design is clear: if externally there is no longer any strong reference pointing to this `ThreadLocal` object (for example, it's a local variable of some method that has already returned), the GC can reclaim the key, and it won't leave this `ThreadLocal` object forever unreclaimable just because "the thread is still alive" — this is precisely a typical engineering application of the "reclaimed at the next GC" property of weak references from the previous section "Reference Strength." The following reproduces this structure in a simplified version:

```java
import java.lang.ref.WeakReference;

public class ThreadLocalPattern {
    static class Entry extends WeakReference<Object> { // simulates Entry extends WeakReference<ThreadLocal<?>>
        Object value; // strong reference, not automatically cleared just because the key is reclaimed
        Entry(Object key, Object value) { super(key); this.value = value; }
    }
    public static void main(String[] args) {
        Object threadLocalKey = new Object();      // simulate a ThreadLocal instance
        byte[] bigValue = new byte[1024 * 1024];   // simulate a 1MB business object stuffed in
        Entry entry = new Entry(threadLocalKey, bigValue);

        threadLocalKey = null;  // the user forgot to hold the ThreadLocal reference
        System.gc();

        System.out.println("was the key reclaimed: " + (entry.get() == null));
        System.out.println("is the value still there: " + (entry.value != null));
    }
}
// was the key reclaimed: true
// is the value still there: true
```

The problem lies exactly here: **the key, having lost its strong reference, will be cleared by the GC, but the value is still strongly referenced by the `Entry`** — as long as this `Entry` is still hanging in the thread's `ThreadLocalMap` array, the value keeps occupying memory. And `ThreadLocalMap` only cleans up those "stale entries" whose keys are already null the **next** time this thread itself calls the `ThreadLocal`'s `get()`/`set()`/`remove()` — if the thread is a long-lived thread in a thread pool and happens to no longer access this `ThreadLocal`, this cleanup may never happen naturally. This is the true meaning of the weak-reference design "preventing only half": it prevents the leak of "the `ThreadLocal` object itself," but not the leak of "the value stuffed in" — the latter still requires you to explicitly call `remove()` after use, which is the biggest difference from the automated reclamation of soft/weak/phantom references: the automated mechanism covers only the key, while the value's lifetime must be managed by you.

## 14. Common OOMs and Tuning Parameters

`OutOfMemoryError` is an `Error`, subdivided by different messages:

| Error message | Meaning | Direction |
|----------|------|------|
| `Java heap space` | The heap can't fit it | Increase `-Xmx` or hunt for a leak (heap-dump analysis) |
| `GC overhead limit exceeded` | Spending 98%+ of time in GC yet reclaiming little | Usually a leak or too small a heap |
| `Metaspace` | Class metadata over the limit (dynamically generating many classes) | `-XX:MaxMetaspaceSize`, hunt for a class-loader leak |
| `unable to create new native thread` | Thread count exceeds the system/memory limit | Reduce threads, tune `-Xss` |
| `Direct buffer memory` | Off-heap direct memory exhausted | `-XX:MaxDirectMemorySize` |

Common parameters:

```
-Xms512m -Xmx4g                  # initial/max heap (in production, set both equal to avoid dynamic-resizing jitter)
-Xss1m                           # per-thread stack size
-XX:MaxMetaspaceSize=256m        # Metaspace upper limit
-XX:+UseG1GC -XX:MaxGCPauseMillis=200  # use G1 and set a pause target
-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/tmp/dump.hprof  # export a heap snapshot on OOM
-Xlog:gc*                        # print GC logs (unified logging in JDK 9+), for analysis
```

Diagnostic flow: `-Xlog:gc*` to watch GC frequency and pauses → grab the `.hprof` on OOM → use MAT/VisualVM to analyze the dominator tree and find who's holding a large object.

## Summary

- **At the usage level**: `try/catch` catches exceptions by type, and `finally` guarantees execution always; `try-with-resources` makes a resource implementing `AutoCloseable` `close()` automatically after use; `catch (A | B e)` catches multiple types at once; a checked exception must be declared with `throws` in the method signature or caught locally, while an unchecked exception has no such constraint; the GC runs automatically without your concern, but `WeakReference`/`SoftReference`/`Cleaner` are a few related APIs you can actively use, resource release still prefers an explicit `close()`, and `Cleaner` serves only as a fallback.
- **At the underlying level**: exceptions locate their handler via the exception table the method carries, and if none is found they unwind frame by frame; `finally` achieves "guaranteed execution" via compile-time code copying; try-with-resources calls `close()` in the reverse of declaration order, and an exception thrown by `close()` is attached to the primary exception as suppressed; exception chaining preserves the root cause via `cause`. Putting `Error` in the unified `Throwable` hierarchy is so that system-level faults can also go through the same diagnosable stack trace; the checked/unchecked distinction is a trade-off between the two philosophies of compile-time fail-fast and runtime discovery, and a checked exception from a low-level API is often wrapped into an unchecked one and rethrown, preserving the root cause via cause. IO streams are split into two type hierarchies of byte/character so that "handling text" and "handling binary" are each type-safe, and processing streams layer capabilities like buffering/encoding on top of node streams via the decorator pattern. The GC doesn't use reference counting (which can't handle circular references), and judges liveness via reachability analysis starting from GC Roots; the heap is divided by the weak generational hypothesis into Eden/Survivor/old generation, with the young generation using the copying algorithm and the old generation using mark-sweep/mark-compact, and generational collection is essentially the strategy of "choose the algorithm best suited to each region"; the Minor/Major/Full GC reclamation scopes increase in turn; the evolutionary history of collectors from Serial to G1/ZGC is the history of compressing STW pauses, G1 turns pause time into a tunable target via its Region-based heap layout, and CMS's four-phase concurrent mark-sweep is a pioneer on this road but at the cost of fragmentation and Concurrent Mode Failure; `finalize` is deprecated, and `Cleaner` + `PhantomReference`/`ReferenceQueue` is its replacement mechanism; soft references are cleared only before OOM and are suited for memory-sensitive caches, weak references are reclaimed at the next GC, and `ThreadLocalMap.Entry` uses one as its key precisely to prevent the `ThreadLocal` object itself from leaking, but the value still needs an explicit `remove()`; a memory leak in Java manifests as "logically useless but still reachable." Master all this, and you can confidently command the JVM's heap the way you manage C++ memory.
