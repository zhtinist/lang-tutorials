# 并发模型:goroutine 与 channel

并发是 Go 的招牌。对 C++ 程序员来说,第一件要重新校准的事是忘掉 `std::thread` 那种"一个并发单元 = 一个 OS 线程"的心智模型——goroutine 是运行时在少量 OS 线程上多路复用的用户态协程,便宜到可以开几十万个,这背后是一整套调度器设计,而不只是"更轻的线程"这么简单。

## 一、goroutine:极轻量的协程

`go` 关键字加一个函数调用就启动一个 goroutine:

```go
go f(x, y)        // 启动一个 goroutine 跑 f(x,y), 立即返回, 不等它
go func() {
    fmt.Println("in goroutine")
}()
```

配合 `sync.WaitGroup` 等一组 goroutine 都跑完(下面「sync 包」一节详细介绍):

```go
var wg sync.WaitGroup
results := make([]int, 3)

for i := 0; i < 3; i++ {
	wg.Add(1)
	go func(id int) { // 启动一个 goroutine
		defer wg.Done()
		results[id] = id * id
	}(i)
}
wg.Wait() // 等所有 goroutine 完成

fmt.Println(results) // [0 1 4]
```

goroutine 什么时候结束:函数体返回就结束。`main` 函数返回则整个程序退出,**不等其他 goroutine**——需要等待就用 channel 或 `sync.WaitGroup`。

| | OS 线程(C++ std::thread) | goroutine |
|--|--------------------------|-----------|
| 初始栈 | 固定 1~8 MB(虚拟内存预留) | **2 KB**,按需增长/收缩 |
| 创建/销毁 | 系统调用,微秒级,昂贵 | 用户态,纳秒级,几乎白送 |
| 调度 | 内核调度,切换要陷入内核 | 运行时用户态调度,切换极快 |
| 数量级 | 几千个就吃力 | 几十万、上百万可行 |

**为什么 goroutine 能便宜到这个数量级,而不是直接用 OS 线程或某个简单的协程库**。OS 线程的成本主要来自两处:一是每个线程要预留一块固定大小、通常几 MB 的栈(即便实际只用了几十 KB,虚拟地址空间和物理内存的记账开销依然存在),几千个线程就足以让虚拟内存管理和上下文切换的成本变得可观;二是线程的创建、销毁、调度都要经过内核,每次切换都要陷入内核态、保存恢复完整的寄存器和内核态数据结构,代价是微秒级的。简单的用户态协程库(不涉及运行时调度器,只做"保存/恢复寄存器"式的协作式切换)确实能避开第二个问题,但通常仍需要程序员手动决定何时让出、如何和阻塞式系统调用共存,一旦协程发起阻塞式 I/O,照样会拖住整个承载它的 OS 线程。Go 的方案是同时解决这两个问题:**用户态、按需增长的小栈**(2KB 起步)砍掉了固定大栈的开销;**运行时自带的 M:N 调度器**(下面的 GMP 模型)接管了协程和系统调用/网络 I/O 的交互,让"看起来同步阻塞"的代码底层自动变成非阻塞加调度切换,程序员不需要手写状态机或显式 yield。这两者缺一都不足以把并发单元的成本降到 goroutine 现在这个量级——只做小栈而没有集成调度器,只是省了内存但阻塞问题还在;只做调度器而没有小栈,起始开销依然是线程级的。

**把进程也纳入比较,能看清三者是同一条线上的三个层次**:进程是操作系统分配独立地址空间、文件描述符等资源的基本单位,进程之间没有默认共享的内存,通信要走 IPC(管道、socket、共享内存段);同一进程内的多个线程共享地址空间和文件描述符,但线程的创建、销毁、调度仍然由**内核**负责,每一次调度决策和上下文切换都要陷入内核态。goroutine 则把"调度"这一层也从内核搬到了用户态:Go 运行时自己决定哪个 goroutine 在哪个 M 上跑、什么时候切换,不需要陷入内核就能完成一次切换。这正是本节开头"几十万个 goroutine 可行、几千个线程就吃力"的根本原因——线程切换的成本大头来自内核态陷入本身(要保存/恢复的不只是寄存器,还有内核栈和调度相关的记账数据),而 goroutine 切换只是用户态一次函数调用级别的寄存器换手,两者不是同一个数量级的开销。

**栈增长**:goroutine 栈起始 2KB,不够时运行时分配更大的栈(通常翻倍)、把内容拷过去、并**改写所有指向该栈的指针**([第06章连续栈](06-函数与调用栈.md))。正因为运行时会在栈"搬家"时修正指针,你**照样可以**像平常一样对局部变量取地址(`&local`)、把它返回或传给别处:逃逸分析会把真正逃逸的变量放到堆上,其余留在栈上,你完全无感。这点恰恰和 C 相反——C 里返回/长期持有栈变量地址是悬垂指针 bug,Go 里则安全。检测"够不够用"发生在编译器插入到每个函数序言的栈溢出检查里:比较当前栈指针(SP)和一个叫 `stackguard0` 的阈值,不够就先跳去扩容再继续执行原函数,这一步对写代码的人完全透明。**栈也会收缩,不是只增不减**:GC 期间运行时会检查每个 goroutine 的栈使用率,如果实际使用不到栈容量的 1/4、且当前栈比初始大小(2KB)更大,就会分配一块更小的栈、把数据挪过去——原理和扩容时的"搬家 + 改指针"完全一样,只是方向反过来。这避免了"一个 goroutine 曾经因为深递归临时用过 1MB 栈,之后大部分时间只用几 KB,却一直占着这 1MB 不释放"这种长期浪费。

**逃逸分析实操:用 `go build -gcflags="-m"` 看编译器的判断**。上面"逃逸分析会把真正逃逸的变量放到堆上"不是一句原则性描述,可以让编译器把每个变量的判断过程打印出来。逃逸的常见触发条件:变量的地址被返回给调用者、变量被赋值给 `interface{}`(装箱要求这块内存能被独立寻址,编译器保守地把它放到堆上)、变量被闭包捕获且闭包本身逃逸出了定义它的函数、变量大小编译期无法确定、或者栈帧会因此变得过大。实测:

```go
package main

import "fmt"

type Point struct{ X, Y int }

func newPoint(x, y int) *Point {
	p := Point{x, y} // 地址被 return, 必须逃逸
	return &p
}

func sumLocal(a, b int) int {
	s := a + b // 只在函数内部用, 不逃逸
	return s
}

func toIface(x int) interface{} {
	return x // 装箱进 interface{}, 逃逸
}

func makeCounter() func() int {
	count := 0 // 被下面的闭包捕获, 闭包本身又逃逸出了 makeCounter, count 跟着逃逸
	return func() int {
		count++
		return count
	}
}

func main() {
	p := newPoint(1, 2)
	fmt.Println(*p, sumLocal(3, 4), toIface(5))
	c := makeCounter()
	fmt.Println(c())
}
```

关掉内联跑 `go build -gcflags="-m -l" .`(`-l` 禁用内联,不然编译器会把小函数内联进调用点,干扰对逃逸行为的观察),核心输出:

```
./main.go:8:2: moved to heap: p          // newPoint 里的 p: 地址被返回, 逃逸
./main.go:18:9: x escapes to heap        // toIface 里的 x: 装箱进 interface{}, 逃逸
./main.go:22:2: moved to heap: count     // makeCounter 里的 count: 被逃逸的闭包捕获, 逃逸
./main.go:31:26: sumLocal(3, 4) escapes to heap  // 见下文解释
```

值得注意 `sumLocal` 函数体内的 `s` **完全没有出现在报告里**——`-m` 只报告堆分配、内联等值得关注的判断,一个变量如果哪儿都没提到,就说明它安安静静地留在了栈上。但调用点 `fmt.Println(*p, sumLocal(3, 4), toIface(5))` 里,`sumLocal(3, 4)` 的返回值本身却被标记为逃逸——原因是 `fmt.Println` 的签名是 `...interface{}`,把一个 `int` 传进去必须先装箱成 `interface{}`,这次装箱在调用点单独触发了一次堆分配,和 `sumLocal` 内部 `s` 逃不逃逸是两回事。这说明逃逸分析是**逐个变量、逐个使用点**判断的,不是"整个函数逃逸或不逃逸"这种函数级别的属性——"这段代码看起来都是局部变量,应该没有堆分配"这种直觉未必成立,决定权在每一处具体的使用方式。

**goroutine 数量真的没有上限吗**:便宜不等于没有代价,三类资源迟早会成为硬限制。一是内存——每个 goroutine 起始栈 2KB,64 位系统上单个栈最多可增长到 1GB(32 位系统 250MB),不加节制地开出上百万个 goroutine,光栈占用就可能吃掉几十 GB 内存。二是调度与 GC 开销——goroutine 越多,调度器维护、窃取队列的成本越高,更关键的是每次 GC 的 STW 阶段都要扫描所有存活 goroutine 的栈做根对象标记,goroutine 数量线性增长会直接拖慢每次 GC 的停顿时间(下面「Go 内存分配与垃圾回收」一节详细展开 GC 各阶段)。三是操作系统线程数——goroutine 本身不直接对应线程,但阻塞式系统调用、CGO 调用等会独占一个 M,过多此类阻塞会推高 M 的数量,而 Go 运行时默认给一个进程最多 **10000** 个 OS 线程的硬上限(`runtime/debug.SetMaxThreads` 可调),超过就会直接让整个程序崩溃退出——这和下面「内存泄漏的常见场景」一节的 goroutine 泄漏是很危险的组合:一旦大量 goroutine 卡在阻塞式系统调用上,线程数可能被迅速推高触顶。实践中控制 goroutine 数量的标准手段,就是本章「常见并发模式」一节的 worker pool,或者用一个容量为 N 的带缓冲 channel 当信号量:进入前 `sem <- struct{}{}`,退出时 `<-sem`,把同时活跃的 goroutine 数硬限制在 N。

## 二、channel 与 CSP

Go 奉行 CSP(Communicating Sequential Processes)哲学:

> **不要通过共享内存来通信,而要通过通信来共享内存。**
> Don't communicate by sharing memory; share memory by communicating.

意思是:优先用 channel 在 goroutine 间**传递数据的所有权**,而不是多个 goroutine 抢一块共享内存靠锁保护([第07章](07-复合数据结构.md)已展开这条哲学与共享内存+锁模型的对比)。

```go
ch := make(chan int)        // 无缓冲
ch := make(chan int, 10)    // 缓冲 10

ch <- 42                    // 发送
v := <-ch                   // 接收
v, ok := <-ch               // ok=false 表示已关闭且空
close(ch)                   // 关闭(由发送方关, 别由接收方关)
for v := range ch { }       // 收到 channel 关闭为止
```

常见用法:用 channel 等待一个 goroutine 完成。

```go
done := make(chan struct{})   // struct{} 零大小, 只当信号
go func() {
    work()
    close(done)               // 或 done <- struct{}{}
}()
<-done                        // 阻塞直到 work 完成
```

channel 的底层结构(`hchan`:环形缓冲 + 一把锁 + 等待队列)已经在[第07章](07-复合数据结构.md)详细讲过。这里补充一点运行时行为:**无缓冲 channel 的发送/接收是一次会合(rendezvous),这不是实现上偶然的选择,而是它的语义定义本身**——无缓冲意味着没有任何存储空间供数据暂存,"发送完成"这件事在定义上就等于"接收方已经把值取走",所以发送方和接收方必须在时间轴上重叠于同一点,数据直接从一个 goroutine 的栈拷到另一个的栈,不经过任何中间缓冲。这一点天然构成 happens-before(下面「Go 内存模型」一节详细展开):一次发送发生的时刻,必然早于或等于对应接收完成的时刻,反过来说,只要接收方观察到自己收到了值,就能确信发送方在此之前的所有操作都已完成并对自己可见。这正是上面"等待 goroutine 完成"模式能正确工作的原因——它依赖的不是"channel 大致能同步"这种模糊直觉,而是会合语义提供的精确的可见性保证。

**单向 channel 约束通信方向**:函数参数里把 channel 类型声明为只发送 `chan<- T` 或只接收 `<-chan T`,双向 channel 可以隐式转换为单向、反过来不行。这不只是风格建议——`producer(out chan<- int, ...)` 这种签名把"这个函数只应该往里塞数据、不该从里面读"的意图固化成编译期检查:调用方传一个双向 channel 进去,函数体内一旦手滑写出反向操作,编译直接报错,而不必等到运行时死锁或读到不该读的数据才发现问题。

```go
package main

import "fmt"

// producer 只能向 out 发送(编译期禁止从中接收)
func producer(out chan<- int, n int) {
	for i := 0; i < n; i++ {
		out <- i
	}
	close(out)
}

// consumer 只能从 in 接收(编译期禁止向其发送)
func consumer(in <-chan int) int {
	sum := 0
	for v := range in {
		sum += v
	}
	return sum
}

func main() {
	ch := make(chan int) // 双向 channel, 传参时自动收窄为单向
	go producer(ch, 5)
	fmt.Println(consumer(ch)) // 0+1+2+3+4 = 10
}
```

**向已关闭的 channel 收发,以及为什么"发送 panic、接收不 panic"是故意的不对称设计**:关闭规则只有三条,但组合起来足够精细——向已关闭的 channel 发送会 **panic**(`send on closed channel`),不管这个 channel 有没有缓冲空间,不存在"缓冲还没满所以能再塞一个"的例外;对同一个 channel 重复 `close` 同样 panic(`close of closed channel`),`close` 一个 nil channel 也 panic(`close of nil channel`);但从已关闭的 channel 接收则完全不同——缓冲区里还有剩余值会先正常吐出来,吐完之后再收,不阻塞,直接返回该类型零值和 `ok=false`。实测:

```go
package main

import "fmt"

func main() {
	ch := make(chan int, 1)
	close(ch)

	func() { // 向已关闭 channel 发送: panic
		defer func() { fmt.Println("send panic:", recover()) }()
		ch <- 1
	}()

	v, ok := <-ch // 已关闭且缓冲已空: 不阻塞, 返回零值
	fmt.Println("recv after close:", v, ok)

	func() { // 重复 close: panic
		defer func() { fmt.Println("close panic:", recover()) }()
		close(ch)
	}()
	// send panic: send on closed channel
	// recv after close: 0 false
	// close panic: close of closed channel
}
```

这个不对称不是随意选的,而是两边的语义压根不对等。`close` 在语义上是发送方一次性地宣布"以后不会再有数据了";这个宣布之后如果还有代码往里发送,只有两种可能——要么有多个发送方彼此不知道对方已经替大家关闭了 channel,要么发送方自己对生命周期的管理出了错。这类"谁也不知道 channel 到底还能不能用"的 bug,如果只是安静地丢弃数据,会在生产环境里表现为诡异的数据丢失、难以定位;让它直接 panic,能强迫这类逻辑错误在测试阶段就暴露出来。接收方则完全没有这层矛盾——"这个 channel 已经不会再有新数据了"是一个可以被无限次确认、不会变化的稳定事实,每次查询都得到同样的答案,没有理由为此付出 panic 的代价,所以设计成一直返回零值 + `false`。

**安全关闭的核心原则:只由发送方关闭,且多发送方场景下没有任何一个发送方能独自决定关闭**。原因直接对应上面的 panic 规则:如果由接收方关闭,接收方并不知道发送方是否还打算再发一次,一旦发送方后续真的发送就会 panic;如果多个发送方里随便一个关闭,其余发送方毫不知情,继续发送同样会 panic。这里有一个容易踩的**误解**:以为用 `sync.Once` 包一层 `close` 就能让多发送方场景安全——`sync.Once` 确实能保证 `close` 这个动作本身只执行一次(避免"重复 close"的 panic),但它解决不了另一半问题:其他发送方并不知道 channel 已经被关闭,仍然可能在 `Once` 触发之后继续往里发送,一样会 panic。真正安全的做法是把"决定何时关闭"从发送方那里剥离出来,交给一个独立的协调者:引入一个额外的"停止信号" `stopCh`(或 `context`),协调者关闭 `stopCh` 广播"停止"给所有发送方;发送方在自己的发送逻辑里配合 `select` 监听 `stopCh`,收到信号后不再发送并退出;等 `sync.WaitGroup` 确认所有发送方都已退出,协调者才去关闭真正的数据 channel——这样"关闭"这个动作和"还有没有人可能发送"这件事被同一个协调者统一管理,不再依赖多个发送方之间的默契:

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	data := make(chan int)
	stop := make(chan struct{})
	var wg sync.WaitGroup

	for id := 0; id < 3; id++ { // 3 个并发发送者, 谁都不直接 close(data)
		wg.Add(1)
		go func(id int) {
			defer wg.Done()
			for i := 0; i < 2; i++ {
				select {
				case data <- id*10 + i:
				case <-stop: // 收到停止信号, 不再发送
					return
				}
			}
		}(id)
	}
	go func() { wg.Wait(); close(stop) }() // 唯一的协调者: 所有发送者退出后才广播停止

	sum, count := 0, 0
	for count < 6 { // 3 发送者 * 每个 2 条 = 6 条, 提前知道总数就不需要 close(data)
		select {
		case v := <-data:
			sum += v
			count++
		}
	}
	fmt.Println("count:", count, "sum:", sum)
	// count: 6 sum: 63   —— (0+1)+(10+11)+(20+21)=63, 与到达顺序无关
}
```

**对 nil channel 收发**:`var ch chan int`(声明了但没 `make`)是 nil channel。对 nil channel 收发都会**永久阻塞**,而且这个阻塞连运行时都无法唤醒——不像等一把锁或等一个真实 channel,总有对应的解锁/发送操作能触发唤醒;nil channel 没有底层 `hchan`,没有等待队列也没有缓冲区,goroutine 挂起后根本不存在任何后续事件能把它唤醒。这一点和"已关闭 channel"是两种容易混淆但截然相反的行为:已关闭 channel 的接收操作不阻塞、立即返回零值+false;nil channel 的收发操作则是阻塞且永远等不到,`close` 一个 nil channel 还会直接 panic(上面刚验证过)。

```go
package main

import (
	"fmt"
	"time"
)

func main() {
	var nilCh chan int // 零值 channel, 从未 make, 是 nil
	select {
	case <-nilCh:
		fmt.Println("不可能走到这里: nil channel 的 case 永远不就绪")
	case <-time.After(20 * time.Millisecond):
		fmt.Println("只有 timeout 分支会触发")
	}
	// 只有 timeout 分支会触发
}
```

nil channel 看起来像一个纯粹的坑,但在 `select` 里恰恰是**动态"关掉"某个 case** 的惯用手法(下面「select:多路复用」一节还会再提一句):一个 case 永远不会就绪,等价于把它从这一轮 select 的候选里排除。典型场景是"某个 channel 已经处理完毕,后续几轮 select 都不应该再从它读",与其在 `select` 外面写一堆 `if doneReadingCh1` 的分支判断,不如直接把 `ch1 = nil`,让运行时替你保证"再也不会选中这个 case"。

**channel 死锁的常见场景**:Go 运行时会检测"所有 goroutine 都已经睡死、没有任何一个能被唤醒"这种全局死锁,直接让整个程序崩溃退出并打印 `fatal error: all goroutines are asleep - deadlock!` 外加每个 goroutine 的调用栈——这和下面「data race」一节的 `-race` 是两种不同性质的检测:data race 需要 `-race` 编译插桩才能发现,而这种死锁检测是运行时**默认内置、随时生效**的,因为它不依赖任何采样或插桩,只需要确认"当前所有 goroutine 都在等待、没有一个是 runnable"这一全局状态,这是一个运行时能精确判定的性质,不需要额外插桩成本。常见诱因:

- **无缓冲 channel 发送后没有接收方**:比如 `main` 里 `ch := make(chan int); ch <- 1` 之后没有任何其他 goroutine 去接收,发送方永久阻塞,而且此时只有 main 这一个 goroutine 在跑,运行时能确定性地判断"再没有任何调度希望了"。
- **向一个不会再被消费的 channel 发送,却没人在另一端 `range` 或接收**:比如 worker 往 `results` 里发,但主 goroutine 已经提前 `return` 不再读。
- **`sync.WaitGroup` 的 `Add`/`Done` 数量不匹配**:`Add` 多了(或 `Done` 少调用了一次),`Wait()` 永远等不到计数归零。
- **对同一把非重入的 `sync.Mutex` 重复 `Lock()`**(比如递归函数忘了自己已经持有锁,又调用了一次 `Lock`):自己把自己锁死,这也是下面「sync 包」一节要提到的"`sync.Mutex` 故意不支持重入"的直接后果之一。
- **两个 goroutine 互相等待对方持有的锁/channel**(经典 AB-BA 顺序问题):goroutine 1 先锁 `mu1` 再试图锁 `mu2`,goroutine 2 反过来先锁 `mu2` 再试图锁 `mu1`,两边各自持有对方需要的那把锁,谁都无法前进。

**避免手段,对应上面每一类**:保证多把锁的加锁顺序在所有代码路径里一致(所有地方都先 `mu1` 后 `mu2`,不要在某处反过来);`Add`/`Done` 严格配对,能用下面「常见并发模式」一节里"预分配 slice 按索引写"或 `errgroup` 这类已经把计数管理封装好的工具,就不要手写容易错配的 `Add`/`Done`;需要等待的地方尽量配 `context.WithTimeout` 或 `select` + `time.After` 兜底,把"死等"变成"等不到就放弃并报错",这样即便逻辑有漏洞,也只是超时而不是永久挂起;临界区尽量短,避免在持锁状态下调用可能间接递归回来的函数。**这里有一个容易忽略的区别**:死锁(deadlock)是 goroutine 彻底被阻塞挂起,谁都无法推进;活锁(livelock)则是 goroutine 表面上一直在运行、状态也在变化,但由于重试逻辑设计不当(比如两个 goroutine 都在"发现冲突就退让"),反复相互避让导致谁都无法真正完成工作——数据竞争检测器和上面的死锁检测器都抓不住活锁,因为从运行时视角看这些 goroutine 明明"活着"在跑,通常需要引入随机化的退避时间来打破这种同步的相互避让节奏。

## 三、select:多路复用

`select` 同时等待多个 channel 操作,哪个就绪走哪个(多个就绪则随机选一个,防饥饿):

```go
select {
case v := <-ch1:
    fmt.Println("from ch1", v)
case ch2 <- x:
    fmt.Println("sent to ch2")
case <-time.After(2 * time.Second):
    fmt.Println("超时")            // 超时模式
default:
    fmt.Println("都没就绪, 非阻塞") // 有 default 就不阻塞
}
```

- 无 `default`:阻塞到至少一个 case 就绪。
- 有 `default`:所有 case 都没就绪时立即走 default —— **非阻塞收发**。
- `time.After` 返回一个到点才发数据的 channel —— **超时**惯用法。
- 对 nil channel 的 case 永远不就绪,可用于动态"禁用"某分支。

多个 case 同时就绪时**随机**选择一个执行,而不是按代码里书写的顺序优先——这和 map 遍历顺序随机化是同一类考虑(见[第07章](07-复合数据结构.md)):如果 `select` 按书写顺序确定性地优先某个 case,程序员会不自觉地把这种顺序当成隐含的优先级来用,而这从未是语言承诺的语义;强制随机化让"多个 channel 同时就绪时谁先被处理"从一开始就不可预测,防止某个 case 因为写在前面就长期"饿死"排在后面的 case,也逼着需要真正优先级语义的代码显式实现,而不是依赖巧合的书写顺序。

**`select` 的底层执行机制(运行时 `selectgo`)分三步,随机性只是其中一步,不是全部**:

1. **求值 + 生成两个独立的顺序**:先按书写顺序(自上而下、从左到右)对每个 case 里的 channel 表达式和待发送的值求值一遍——这一步是确定性的,不会被打乱;然后运行时用内部的伪随机数生成器(`fastrand`)生成一个**轮询顺序(poll order)**,把 case 检查的先后打乱,这正是上面"随机选择"的来源。同时还会按 **channel 地址排序**生成一个独立的**加锁顺序(lock order)**——注意这个顺序跟轮询顺序不是同一个:轮询顺序决定"先看哪个 case 是否就绪"(需要随机,防饥饿),加锁顺序决定"以什么固定次序去抢每个 channel 内部的锁"(必须固定,如果两个 goroutine 同时执行涉及同一组 channel 的 `select` 却按不同顺序加锁,就会构成经典的 AB-BA 死锁——这正是上面「channel 死锁的常见场景」一节提到的加锁顺序问题,`select` 内部用"按地址排序"这种确定性规则统一了顺序,避免自己踩自己列的坑)。
2. **按轮询顺序逐个检查是否就绪**:对每个 case,如果对应的 channel 操作可以立即完成(有数据可收/有空位可发/对方已经在等待队列里),就直接执行这个 case 并返回,不再看后面的 case——这就是"多个 case 就绪时随机选一个"的具体实现方式:因为轮询顺序本身是随机打乱过的,"第一个检查到就绪的 case"自然等价于"从所有就绪 case 里随机选一个"。如果遍历完一圈都没有就绪的,且有 `default`,立即走 `default`。
3. **没有 `default` 且都不就绪:等待队列 + 挂起**:当前 goroutine 把自己注册进**每一个** case 对应 channel 的等待队列(发送队列或接收队列),然后 `gopark` 挂起——这一步呼应前面「GMP 调度模型」一节的"只阻塞 G 不阻塞 M":M 不会跟着停摆,会继续去跑别的 G。等某个 channel 真的发生了对应的收发操作,运行时会唤醒这个 goroutine,并且**清理掉它在其余 channel 等待队列里残留的注册**(不然一次唤醒会导致同一个 goroutine 出现在多个等待队列里,后续别的 channel 操作可能误唤醒一个已经在别处忙的 goroutine)。

这也解释了为什么"case 书写顺序不影响结果"不只是文档里的一句承诺,而是实现上根本没有留任何缝隙让顺序产生影响:第 1 步生成的轮询顺序本身就与书写顺序无关,第 2 步严格按这个随机顺序检查,书写顺序至多决定第 1 步"按什么次序求值 case 表达式"(而表达式求值通常没有副作用可观察),不会传导到"选中哪个 case"这个结果上。

可运行示例:两路 channel 多路复用 + `time.After` 超时兜底。两个 goroutine 到点各发一次,`select` 收满两条才退出。到达顺序不定,所以断言**集合**而非精确顺序:

```go
package main

import (
	"fmt"
	"time"
)

func main() {
	nums := make(chan int)
	strs := make(chan string)

	go func() {
		time.Sleep(10 * time.Millisecond)
		nums <- 42
	}()
	go func() {
		time.Sleep(20 * time.Millisecond)
		strs <- "hi"
	}()

	got := map[string]bool{}
	timeout := time.After(100 * time.Millisecond)
	for len(got) < 2 {
		select {
		case n := <-nums:
			got[fmt.Sprintf("num:%d", n)] = true
		case s := <-strs:
			got[fmt.Sprintf("str:%s", s)] = true
		case <-timeout:
			fmt.Println("timed out")
			return
		}
	}
	fmt.Println("got num:", got["num:42"])
	fmt.Println("got str:", got["str:hi"])
	// got num: true
	// got str: true
}
```

## 四、GMP 调度模型

日常写并发代码基本不需要关心调度器,唯一常打交道的旋钮是并行度:

```go
runtime.GOMAXPROCS(4)         // 设置/查询 P 的数量(即并行度上限)
n := runtime.GOMAXPROCS(0)    // 传 0 表示只查询不修改
```

Go 运行时用 **G-M-P** 三元组把 goroutine 多路复用到 OS 线程上。

- **G(goroutine)**:一个协程,含栈、程序计数器、状态。
- **M(machine)**:一个 OS 线程,真正在 CPU 上执行代码。
- **P(processor)**:调度上下文/逻辑处理器,持有一个**本地可运行 G 队列**。P 的数量 = `GOMAXPROCS`(默认 = 可用 CPU 核数;**Go 1.25 起**在容器中会感知 cgroup 的 CPU 限额、按限额取整,不再一律等于物理核数)。**M 必须绑定一个 P 才能执行 G**。

**goroutine 的上下文切换保存在哪**:每个 G 是运行时里一个普通的 Go 结构体,里面有一个 `gobuf` 字段——保存的是这个 goroutine 被换下 CPU 那一刻的寄存器现场(栈指针 SP、程序计数器 PC、BP 等,并不是所有寄存器,而是恢复执行足够用的最小集合),外加一个状态字段(`_Grunnable`/`_Grunning`/`_Gwaiting` 等)和它自己栈的位置信息。调度器要切换 G 时(无论是主动让出、被抢占、还是阻塞挂起),做的事就是把当前寄存器状态存进这个 G 自己的 `gobuf`,再从下一个要跑的 G 的 `gobuf` 里把寄存器恢复出来——全程停留在用户态,数据结构就是运行时里的一个字段,不涉及切换到内核栈、保存页表基址寄存器这些线程上下文切换才要做的事。这也是为什么"goroutine 上下文切换比线程便宜"不只是一句结论:线程切换要保存/恢复的是内核认识的一整套执行环境,goroutine 切换只是把几个寄存器值誊到一个 Go struct 字段里再誊回来。

```
              全局运行队列 GRQ: [G G G ...]
                     │(本地空了来偷/拿)
   ┌─────────────┐   ┌─────────────┐
   │  P0         │   │  P1         │   P 数量 = GOMAXPROCS
   │ 本地队列LRQ │   │ 本地队列LRQ │
   │ [G G G]     │   │ [G G]       │
   └──────┬──────┘   └──────┬──────┘
          │绑定             │绑定
      ┌───▼───┐         ┌───▼───┐
      │  M0   │         │  M1   │   M = OS 线程, 数量按需(可能 > P)
      │(线程) │         │(线程) │
      └───────┘         └───────┘
           实际跑在 CPU 核上
```

**为什么要三层(G-M-P),而不是 goroutine 直接映射线程、或者只有 G 和 M 两层**。只有 G 和 M 两层(goroutine 直接排队等 M 执行)会遇到一个具体问题:当某个 G 发起阻塞式系统调用时,执行它的 M 陷入内核阻塞,如果没有第三个概念把"可以并行执行的名额"和"某一时刻具体绑定哪个线程"分开,要么整个运行时的并行度因为这一次阻塞而减少,要么每次阻塞都要临时决定"还要不要多开一个线程来维持并行度"而缺乏一个清晰的记账单位。P 就是这个"并行度名额"的显式载体:`GOMAXPROCS` 个 P 决定了同一时刻最多有多少个 G 在真正并行执行,M 的数量则可以按需超过 P 的数量(应对阻塞的系统调用)。这让"并行度"和"线程数"成为两个独立可调的量,而不是纠缠在一起。

**本地队列 + work-stealing(工作窃取)**:每个 P 有本地队列(容量 256、环形数组实现,无锁操作),新建的 G 优先放本地(无锁,快)。本地队列放满时,不是每次都去抢全局队列的锁,而是把本地队列**前一半**(连同新建的 G)一次性打包,只加**一次**全局锁批量转移过去——这是一个"用批量操作摊薄锁开销"的设计,如果每次队列快满都单独加锁转移一个 G,锁竞争的频率会高得多。P 本地空了,调度器按固定顺序找活干:先去全局队列拿(需要加锁,但概率上远少于本地无锁操作),全局队列也空就**从别的 P 队列偷一半**(`runqsteal`,用无锁 CAS 实现,不需要额外加锁),这几步都还找不到活干,最后还会去问一次 **netpoller**(下面会讲)有没有 I/O 已经就绪、可以直接转成可运行状态的 G——这是整条"找活干"链路里最后一道兜底,顺序上从最便宜(本地无锁)到最贵(全局加锁、偷取、查询 netpoller)依次尝试。这让负载自动均衡,又把需要全局同步的操作压缩到尽量少的场景。

**如果把 P 这一层去掉,会退化成什么样**:这是一个很有价值的思想实验,能反过来印证 P 存在的必要性。去掉 P 之后,调度模型退化成只有 G 和 M 两层(接近 Go 1.0 之前、以及很多简单协程库的做法)——所有 goroutine 只能放进一个全局队列,所有 M 想拿一个可运行的 G 都得竞争同一把全局锁。具体会摔在四个地方:第一,**全局队列锁竞争**成为瓶颈,核数越多、并发 M 越多,抢这把锁的排队开销越明显,调度延迟不再随核数扩展反而可能变差;第二,**失去本地缓存**——P 除了挂调度用的本地运行队列,还持有 `mcache`(线程本地的小对象内存分配缓存,见下面「内存分配机制」一节),没有 P 就没有天然的"每处理器一份"缓存位置,每次内存分配都要去竞争访问全局的 `mcentral`,分配效率大幅下降;第三,**无法 work-stealing**——工作窃取的前提是"每个调度单元有自己的本地队列,可以被别的单元来偷",只有一个全局队列时不存在"偷"这个概念,负载不均衡时没有自动纠正的机制,可能出现某些 M 在忙、另一些在闲等;第四,**失去精确的并行度控制**——`GOMAXPROCS` 本质上是在设置 P 的数量,去掉 P 之后就没有一个干净的旋钮能精确限定"同一时刻最多几个 G 在并行跑",只能间接通过限制 M 的数量或者操作系统的线程调度来近似达到类似效果,而 M 的数量本身还要应对系统调用阻塞的场景(见下一段),两个目的绞在同一个量上,不像现在这样解耦干净。P 层本质上是"用一层额外的数据结构(每个 P 的本地队列、mcache)换取更少的全局同步"的空间换时间取舍,去掉它不是不能运行,而是显式地放弃了这套优化,回到早期协程库常见的全局锁瓶颈。

**系统调用时 P 与 M 解绑(hand-off)**:某个 G 发起阻塞式系统调用(如读文件),它所在的 M 会陷入内核阻塞。运行时把这个 M 的 P **摘下**,交给另一个(空闲或新建的)M,让 P 上其余的 G 继续在别的核上跑,不被一个阻塞调用拖住。系统调用返回后,原 M 尝试重新获取一个 P,拿不到就把 G 放回队列、自己休眠。这正是上一段"P 与 M 解耦"这个设计带来的直接收益:P 可以在原 M 阻塞期间被摘下转交给别的 M,并行度不因为一次阻塞调用而下降。

**Goroutine 阻塞的完整分类,以及每一类调度器怎么处理**:上面"系统调用时 P 与 M 解绑"只是阻塞里的一种情况,完整看,阻塞大致分两类,处理方式完全不同。

- **只阻塞 G,不阻塞 M(异步阻塞)**:channel 发送/接收未就绪、`sync.Mutex`/`sync.RWMutex` 抢锁失败、`select` 所有 case 都不满足且无 `default`、`sync.WaitGroup.Wait`/`sync.Cond.Wait`、`time.Sleep`(挂进运行时的定时器堆,等到点被唤醒)、网络 I/O(下一段的 netpoller)。这些场景下,goroutine 调用运行时的 `gopark` 把自己挂起、状态切成等待,M **不会**跟着阻塞,而是继续从 P 的本地队列(或全局队列、或从别的 P 偷来的任务)里取下一个可运行的 G 执行;等条件满足(锁被释放、channel 就绪、定时器到点……),运行时调用 `goready` 把等待的 G 重新标记为可运行、塞回某个 P 的队列等待调度。
- **G 和 M 一起阻塞(同步阻塞)**:传统的阻塞式系统调用(本地文件 I/O 等)、CGO 调用。这类操作是直接把控制权交给内核,运行时没法在不阻塞底层线程的前提下悄悄把 G 换下来,所以这时候真正被卡住的是 M 本身。这正是上面"系统调用时 P 与 M 解绑"要解决的问题:运行时的后台监控线程(sysmon)一旦发现某个 M 因系统调用阻塞过久,就把它的 P 摘下转交给别的(空闲或新建的)M,让 P 上其余的 G 不被这一次阻塞拖累。

这两类的本质区别在于:前者阻塞的是"用户态的一个记账单位"(G),M 全程没有停摆;后者阻塞的是"内核认识的执行单元"(M),运行时唯一能做的补救是把 P 转移走、不让并行度因此减少。这也是为什么"用 channel/锁/WaitGroup 这些同步原语"和"直接发起阻塞式系统调用"在 Go 里是两种完全不同的成本模型——前者哪怕同时阻塞几万个 goroutine,消耗的也只是内存和调度器记账;后者阻塞太多则会直接把 M 数量推向上一节提到的 10000 上限。

**网络 I/O 用 netpoller**:网络读写不会真的阻塞 M,而是注册到基于 epoll/kqueue 的 netpoller,goroutine 挂起、M 去跑别的 G,I/O 就绪时再唤醒。所以你能用"每连接一个 goroutine、同步阻塞式写法"却获得 epoll 的伸缩性——这是 Go 网络服务爽点的底层原因:程序员写的是最直观的同步代码,调度器在背后把它转换成事件驱动模型的效果。

**抢占式调度**:早期 Go 是协作式(只在函数调用处让出),一个纯计算死循环会饿死同 P 的其他 G。Go 1.14 起是**基于信号的异步抢占**:运行时可向长时间不让出的 G 发信号,在安全点强制切换。所以现在不用担心 `for {}` 卡死调度器。

**把上面散落各处的"什么时候会发生一次调度"收拢成一张时机清单**:前面几段分别讲了系统调用、channel/锁阻塞、抢占,但完整看,触发一次调度决策(切换正在运行的 G)大致是这几类:

1. **主动让出**:显式调用 `runtime.Gosched()`,或者函数调用时编译器插入的栈溢出检查(`morestack`)顺便发现"该我让出了"的标记。
2. **被动阻塞**:上面详细展开过的"只阻塞 G 不阻塞 M"那一类——channel 收发未就绪、`sync.Mutex`/`sync.WaitGroup`/`sync.Cond` 等待、`time.Sleep`、网络 I/O 走 netpoller——goroutine 自己调用 `gopark` 让出,M 转去找下一个可运行的 G。
3. **同步阻塞(系统调用/CGO)**:上面"系统调用时 P 与 M 解绑"那一类,M 本身陷入阻塞,运行时把 P 转交出去让别的 M 继续调度。
4. **抢占**:运行时的后台监控线程 **sysmon**(不需要绑定 P,独立运行,大约每 20 微秒到 10 毫秒轮询一次)会遍历所有 P,检查各自正在运行的 G 已经连续跑了多久,一旦发现某个 G **运行超过 10ms**,就会标记它需要被抢占——Go 1.14 之前只能设置一个标志位,等这个 G 自己下次执行到函数调用的栈检查点时才会真正让出(纯计算死循环没有函数调用,所以抢不动);Go 1.14 起换成**向目标 G 所在的 M 发送 `SIGURG` 信号**,M 收到信号后在信号处理函数里保存当前 G 的执行现场、把状态改成可抢占、再调用调度器切到别的 G——这一步不依赖 G 主动配合,可以在任意执行点打断,彻底解决了纯计算死循环、CGO 调用等场景抢不动的问题。sysmon 除了负责抢占,还顺带做两件相关的事:回收长时间处于系统调用状态的 P(前面"系统调用时 P 与 M 解绑"一段提到的转交动作,实际的检测者正是 sysmon)、以及在到点时触发 GC。
5. **正常结束**:G 的函数体返回,调度器直接切到下一个可运行的 G。

**一个容易漏掉的细节:调度器不会无限偏向本地队列,以防全局队列饿死**。P 的本地队列是无锁的、优先被消费,但如果调度器每次都优先查本地队列、只有本地空了才看全局队列,理论上如果每个 P 的本地队列总能维持"不空"的状态(不断有新 G 补充进来),全局队列里的 G 就可能长期排不上号。为此调度器并不是"本地队列不空就绝对不看全局队列",而是**每处理大约 61 次调度,就会强制去全局队列取一次**,不管本地队列是否还有任务——这个"隔 N 次看一眼全局队列"的策略,和上面「select」一节"多个 case 就绪时随机选而不是死板按顺序"是同一类思路:纯粹按局部最优贪心(永远先查本地)会在全局层面制造出饥饿,加一条兜底规则,用很小的常数开销换取"不会有谁被无限期忽略"的保证。

对照 C++:`std::thread` 是 1:1 内核线程,调度归 OS,切换要进内核;Go 是 **M:N**(M 个 G 跑在 N 个线程上),大部分调度在用户态完成,切换成本低得多。

## 五、sync 包:传统锁与同步原语

不是所有场景都适合 channel。共享计数器、保护一小段临界区,用锁更直接、更快——这也提醒一件事:CSP 哲学是 Go 并发设计的主导思想,但不是教条,`sync` 包同样是一等公民,用在 channel 不合适的地方。

```go
var mu sync.Mutex
mu.Lock()
count++
mu.Unlock()          // 常配 defer mu.Unlock()
```

| 原语 | 用途 | 对照 C++ |
|------|------|---------|
| `sync.Mutex` | 互斥锁 | `std::mutex` |
| `sync.RWMutex` | 读写锁,多读单写 | `std::shared_mutex` |
| `sync.WaitGroup` | 等一组 goroutine 完成 | 无直接对应(手动 join) |
| `sync.Once` | 某代码只执行一次(懒初始化) | `std::call_once` |
| `sync/atomic` | 原子操作(Add/Load/Store/CAS) | `std::atomic` |
| `sync.Map` | 并发安全 map,读多写少优化 | 无(concurrent_map 类) |
| `sync.Pool` | 临时对象池,减少分配/GC 压力 | 对象池 |

WaitGroup 惯用法:

```go
var wg sync.WaitGroup
for i := 0; i < 10; i++ {
    wg.Add(1)
    go func(id int) {
        defer wg.Done()
        work(id)
    }(i)                  // 注意: 把 i 作为参数传进去(Go1.22 前循环变量复用坑)
}
wg.Wait()                 // 阻塞到计数归零
```

> Go 1.22 起 `for` 循环变量每轮独立,老代码里"闭包捕获循环变量"的经典 bug 大多消失;但显式传参仍是清晰的好习惯。

`sync.Mutex` 零值即可用(不用初始化),**不可拷贝**(拷了就是两把锁,`go vet` 会警告)。所以含 Mutex 的 struct 通常用指针传递。

可运行示例:100 个 goroutine 各自 +1 一千次,`Mutex` 与 `atomic.Int64` 都得到确定的 100000。若把 `mu.Lock/Unlock` 去掉、改成裸 `count++`,`go run -race` 会报 `DATA RACE`,结果也会因**丢更新**小于 100000:

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
)

func main() {
	const goroutines, per = 100, 1000
	want := int64(goroutines * per)

	// 1) sync.Mutex 保护普通计数器
	var mu sync.Mutex
	var muCount int64
	var wg sync.WaitGroup
	for i := 0; i < goroutines; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			for j := 0; j < per; j++ {
				mu.Lock()
				muCount++
				mu.Unlock()
			}
		}()
	}
	wg.Wait()

	// 2) sync/atomic 原子加
	var atCount atomic.Int64
	for i := 0; i < goroutines; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			for j := 0; j < per; j++ {
				atCount.Add(1)
			}
		}()
	}
	wg.Wait()

	fmt.Println("want  :", want)
	fmt.Println("mutex :", muCount, muCount == want)
	fmt.Println("atomic:", atCount.Load(), atCount.Load() == want)
	// want  : 100000
	// mutex : 100000 true
	// atomic: 100000 true
}
```

`sync.Mutex` 本身很小(概念上是一个状态字 + 一个信号量,共 8 字节),加锁分两条路径:无竞争时靠一次原子 CAS 直接拿到锁(fast path,几乎零开销);抢不到才会短暂自旋几次,还拿不到就通过运行时的信号量把 goroutine 挂起(park),解锁时唤醒——挂起的 goroutine 会被调度器摘下,不占用 M,和普通 channel 阻塞是同一套"挂起-唤醒"机制。这与 C++ `std::mutex` 通常直接包一层内核 futex 等待不同:Go 的锁是运行时调度框架内的一部分,阻塞的是 goroutine 而不是线程本身,这与前面 GMP 一节"阻塞一个 goroutine 不阻塞 OS 线程"的原则是一致的——不管是 channel 收发阻塞还是 mutex 抢锁失败,底层都复用同一套"挂起 G、腾出 M 去跑别的 G"的机制。细节随版本演进,以运行时源码 `sync/mutex.go` 为准。

**为什么"一个状态字 + 一个信号量,共 8 字节"能表达这么多状态:锁状态被压缩进一个 `int32` 的不同位**。`sync.Mutex` 的字段只有 `state int32` 和 `sema uint32`——所有的锁状态全挤在这一个 32 位整数里,用位运算切出四个独立的信息:第 0 位(`mutexLocked`)表示锁有没有被占用;第 1 位(`mutexWoken`)表示已经有一个等待者被唤醒、正在尝试抢锁,用来告诉正在解锁的 goroutine "不用再唤醒别人了,已经有一个在路上";第 2 位(`mutexStarving`)表示这把锁当前是不是处于下面要讲的饥饿模式;剩下的高 29 位统一记录当前有多少个 goroutine 在排队等这把锁(`waiterCount`)。实测(用 `unsafe.Sizeof` 和 `%+v` 直接看内部字段,`fmt` 对未导出字段也能打印其值):

```go
package main

import (
	"fmt"
	"sync"
	"unsafe"
)

func main() {
	var mu sync.Mutex
	fmt.Println("sizeof(sync.Mutex):", unsafe.Sizeof(mu), "bytes") // 8: state int32 + sema uint32
	fmt.Printf("unlocked: %+v\n", mu)
	mu.Lock()
	fmt.Printf("locked  : %+v\n", mu) // state 的第0位(mutexLocked)从 0 变成 1
	mu.Unlock()
	fmt.Printf("unlocked again: %+v\n", mu)
	// sizeof(sync.Mutex): 8 bytes
	// unlocked: {_:{} mu:{state:0 sema:0}}
	// locked  : {_:{} mu:{state:1 sema:0}}
	// unlocked again: {_:{} mu:{state:0 sema:0}}
	// (本机 Go 1.26 把 noCopy 标记和内部状态各拆成了一层, 最内层
	//  仍然是 state int32 + sema uint32 这两个字段, 概念不变)
}
```

**为什么要把多个状态压进同一个字段,而不是四个独立的 bool/int 字段**:如果状态分散在多个字段里,"检查锁是否空闲、检查有没有人已经被唤醒、增加等待者计数"这几件事就没法在一次原子操作里完成——要么退化成"锁一把锁来保护另一把锁"的荒谬递归,要么每个字段各自原子操作、但字段之间的组合状态在读的间隙可能被别的 goroutine 改掉(比如你先读到"未加锁"、正准备 CAS,期间别的 goroutine 已经把等待者计数改了,而你的判断依据的是过时的组合状态)。把所有状态压进一个 `int32`,一次 CAS 就能原子地"检查当前完整状态 + 计算目标状态 + 写回",不存在多字段之间不一致的窗口——这是并发数据结构里常见的手法:用尽可能少的机器字表达状态,把多个条件的组合判断也变成单次原子操作能覆盖的范围。

**正常模式与饥饿模式:为什么单纯的"CAS 抢锁 + 自旋"会有公平性问题,以及 1ms 这条判断线**。前面 fast path 描述的"CAS 抢锁失败就自旋几次,再不行就挂起排队"是 `sync.Mutex` 的**正常模式**(默认状态)。正常模式为了吞吐量做了一个明确的取舍:被唤醒的等待者(从等待队列头部拿到信号量的那个 goroutine)醒来后**并不会直接拿到锁**,而是要和此刻新到达的、正占着 CPU 运行的 goroutine 一起竞争这把锁——新来的 goroutine 因为已经在 CPU 上跑,不需要经历"被唤醒、重新被调度上 CPU"这几步开销,大概率会抢赢。这个设计在大多数场景下是对的:极大提升了整体吞吐(避免了每次解锁都强制上下文切换到等待队列头部的开销),但极端情况下会有隐患——如果新来的 goroutine 源源不断,队列头部那个等待者可能一直抢不到锁,理论上可以无限期地"饿死"。

Go 从 1.9 起加了**饥饿模式**当兜底:一旦某个等待者从入队到被唤醒的等待时间**超过 1ms**,它会把 `state` 的 `mutexStarving` 位置 1,切换到饥饿模式。饥饿模式下规则完全反过来——解锁时锁的所有权**直接移交**给等待队列最前面的那个等待者(不经过 CAS 竞争这一步),新来的 goroutine 不会自旋、也不会尝试抢锁,而是老老实实排到队尾,严格 FIFO。切回正常模式的条件有两个,满足任一个就切回:一是刚拿到锁的这个等待者发现自己其实是队列里**最后一个**,说明积压已经清空,没必要再维持饥饿模式的额外开销;二是它这次等待的时间其实**小于 1ms**(说明拥堵已经缓解)。这个"用等待时长触发、用队列是否清空或等待时长恢复正常来解除"的双模式设计,本质上是在"正常情况下的高吞吐"和"极端情况下的有界等待时间"之间找一个平衡点:绝大部分时间用正常模式换吞吐,一旦出现真实的饥饿迹象(哪怕只是一个 goroutine 等太久),就临时牺牲一点吞吐换取公平性,问题解除后再切回去——不是在两个目标里选一个,而是让系统自己根据实测的等待时长在两者之间动态切换。**这也是为什么 `sync.Mutex` 故意不支持重入**(可重入会让"当前持有者是谁、还要不要再次通过同一 goroutine 的请求"这件事变得复杂,与饥饿模式这种"公平交给队列顺序"的模型天然冲突,而且很难在这套状态位设计里干净地加入"持有者身份"和"重入计数"而不破坏原子性),官方推荐的做法是把需要重入的核心逻辑抽成不加锁的内部函数,由外部统一加锁调用。

**收集多个并发 goroutine 的执行结果**:上面 WaitGroup 的例子只是"等待完成",实际场景经常还要**收集每个 goroutine 的返回值**,并且要能把结果和是哪个任务对应上。三种常见做法,取舍点各不相同:

1. **预分配 slice + 按索引写**:开工前按任务数 `make([]T, len(tasks))`,把索引 `i` 传给每个 goroutine,goroutine 算完直接写 `results[i] = v`。这是**并发安全且无锁**的——每个 goroutine 写的是 slice 里独立的一个元素、互不重叠,数据竞争的前提"至少一个在写同一块内存"根本不成立;`WaitGroup.Wait()` 返回后直接按顺序遍历 `results` 就是有序的结果,不需要额外排序。这是三种方式里代价最低的一种,前提是任务数在开工前就已知。
2. **channel 传结果 + 任务 ID**:每个 goroutine 把 `(任务 ID, 结果, error)` 封装成一个小结构体发到 channel,主 goroutine 收完再按 ID 归位。这种方式天然支持"任务数量不确定、边生产边消费"的场景,但代价是**结果到达顺序不确定**,必须显式带上 ID 才能对应回去,并且要处理好 channel 何时关闭(通常配一个 `WaitGroup`:所有生产者 `Done` 后,由专门的一个 goroutine `Wait()` 完再 `close`,避免主 goroutine 读空 channel 死等,或者过早关闭引发向已关闭 channel 发送的 panic)。
3. **`golang.org/x/sync/errgroup`**:官方扩展包,把 `WaitGroup` +"第一个错误"+ `context` 取消揉在了一起。`errgroup.WithContext` 返回的 `ctx` 会在任意一个 `g.Go(...)` 里的函数返回非 nil error 时自动被取消,`g.Wait()` 返回的是第一个发生的 error——不需要自己再手写一套"一个任务失败就取消其余任务"的逻辑。

第 3 种在"一组任务互相依赖成败"(比如并发拉取多个接口,只要一个失败就没必要等其他的)时最省心,原因是它把"WaitGroup 的等待"和"失败时取消同伴"两件事在语义上合并成了一件事,不像第 1、2 种那样还要自己额外接一层 `context.WithCancel` 才能做到同样效果。可运行示例:5 个任务里第 4 个(索引 3)人为失败,`errgroup` 自动取消其余任务的 `ctx`,耗时更长的那个任务(索引 4)会在自己的 `ctx.Done()` 上提前退出,而不是傻等到自己的耗时结束:

```go
package main

import (
	"context"
	"fmt"
	"time"

	"golang.org/x/sync/errgroup"
)

func fetch(ctx context.Context, id int, fail bool) (int, error) {
	select {
	case <-time.After(time.Duration(id) * time.Millisecond):
	case <-ctx.Done():
		return 0, ctx.Err() // 被同伴的失败提前取消
	}
	if fail {
		return 0, fmt.Errorf("task %d failed", id)
	}
	return id * id, nil
}

func main() {
	g, ctx := errgroup.WithContext(context.Background())
	results := make([]int, 5) // 预分配 + 按索引写, 天然并发安全

	for i := 0; i < 5; i++ {
		i := i
		g.Go(func() error {
			fail := i == 3                  // 第 3 个任务(耗时 15ms)人为失败
			r, err := fetch(ctx, i*5, fail) // i=4 耗时 20ms, 会被提前取消
			if err != nil {
				return err
			}
			results[i] = r
			return nil
		})
	}

	err := g.Wait()
	fmt.Println("results:", results)
	fmt.Println("err    :", err)
	// results: [0 25 100 0 0]  —— 索引3失败未写入, 索引4被提前取消未写入
	// err    : task 15 failed
}
```

**`sync.Map`:为什么读多写少场景比"`map` + `Mutex`"快,靠的是 `read`/`dirty` 两个字典的读写分离**。上面表格里 `sync.Map` 只列了一句"读多写少优化",实际实现是一套精心设计的双 map 结构:内部维护一个只读的 `read`(用 `atomic.Pointer` 包起来,读取全程无锁)和一个加锁保护的 `dirty`(包含所有数据,含新插入的 key),外加一个 `misses` 计数器。

- **读(Load)走 fast path**:先原子读 `read`,命中直接返回,**全程不加锁**。如果 `read` 里没有,但 `read.amended`(标记 `dirty` 里有 `read` 没有的新数据)为 `true`,才加锁去查 `dirty`,并把 `misses` 加一——这条 slow path 才会碰锁。
- **晋升机制**:当 `misses` 累计到等于 `len(dirty)` 时,说明穿透 `read` 直接查 `dirty` 已经发生了足够多次,不如把 `dirty` **整体提升**成新的 `read`(一次指针赋值,O(1)),再把 `dirty` 清空——后续的读又重新回到无锁 fast path。
- **写(Store)**:如果 key 已经在 `read` 里(且没被彻底删除),直接用 **CAS** 无锁更新对应的值指针;只有写**新 key** 才需要加锁,写进 `dirty`。
- **删除是两阶段的逻辑删除**:先把 `read` 里对应 entry 的指针 CAS 成 `nil`(表示"逻辑上删了,但 `dirty` 里可能还留着"),只有在后续**重建** `dirty` 时才会把这些 `nil` 项转成 `expunged`(彻底删除、`dirty` 里保证没有这个 key)。区分 `nil`/`expunged` 两种状态的价值在于:重建 `dirty` 时只需要把 `read` 里"未被删除"的 entry 拷过去,已经是 `expunged` 的可以直接跳过,不用再次判断它是否已经在旧 `dirty` 出现过。

**为什么这套设计在读多写少场景下天然比"`map` + `Mutex`"快**:普通 `map` 配一把 `Mutex`,**每一次**读或写都要抢同一把锁——即使 99% 的操作都是读,读和读之间、读和写之间照样要互斥排队,锁本身成为瓶颈。`sync.Map` 把这两件事拆开了:只要访问的 key 已经在 `read` 里,读操作连锁都不用碰,多个 goroutine 可以真正**并行**读,不存在互斥排队;只有写新 key、或者读 miss 之后不得不查 `dirty` 时,才会退化成加锁路径。读多写少的场景里绝大多数操作都能落在无锁的 `read` 上,平均下来自然比"每次都要抢锁"的 `map+Mutex` 快。反过来,**写多或者频繁插入新 key 的场景,`sync.Map` 反而可能比 `map+Mutex` 更慢**:每次插入新 key 都要经过加锁的 `dirty` 路径;更麻烦的是晋升机制——`dirty` 提升为 `read` 之后会被清空,下一次再插入新 key 时,必须先把 `read` 里所有未删除的 entry **整体拷贝**一份新的 `dirty`(O(N) 遍历),持续的新 key 插入会反复触发这个 O(N) 拷贝,造成性能抖动。这也是为什么官方明确建议 `sync.Map` 只用于"读多写少"或者"多个 goroutine 操作各自不相交的 key 集合"这两类场景,而不是当成 `map+Mutex` 的无脑替代品。

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	var m sync.Map
	var wg sync.WaitGroup
	for i := 0; i < 100; i++ {
		wg.Add(1)
		go func(i int) {
			defer wg.Done()
			m.Store(i, i*i) // 新 key 首次写入: 加锁写 dirty
		}(i)
	}
	wg.Wait()

	var rwg sync.WaitGroup // 大量并发读, 命中 read 后走无锁 fast path
	ok := make([]bool, 100)
	for i := 0; i < 100; i++ {
		rwg.Add(1)
		go func(i int) {
			defer rwg.Done()
			v, found := m.Load(i)
			ok[i] = found && v.(int) == i*i
		}(i)
	}
	rwg.Wait()

	all := true
	for _, b := range ok {
		if !b {
			all = false
		}
	}
	fmt.Println("all 100 loaded correctly:", all)

	m.Delete(0) // 逻辑删除: read 里先标 nil
	_, found := m.Load(0)
	fmt.Println("after delete, key 0 found:", found)

	count := 0
	m.Range(func(k, v any) bool { count++; return true })
	fmt.Println("remaining count:", count)
	// all 100 loaded correctly: true
	// after delete, key 0 found: false
	// remaining count: 99
}
```

## 六、Go 内存模型与 happens-before

多核下,没有同步的并发读写没有顺序保证(编译器/CPU 会重排、缓存不可见)。Go 内存模型用 **happens-before** 定义可见性:若事件 A happens-before B,则 A 的写对 B 可见。建立 happens-before 的手段:

- channel:一次**发送** happens-before 对应的**接收完成**;channel 的**关闭** happens-before 接收到零值。
- `Mutex`:第 n 次 `Unlock` happens-before 第 n+1 次 `Lock`。
- `WaitGroup`:`Wait` 返回前,所有 `Done` 之前的写可见。
- `Once`:`Do` 里的初始化 happens-before 任何 `Do` 返回。
- `atomic`:提供顺序保证(Go 1.19 起 `sync/atomic` 有明确的类型化 API `atomic.Int64` 等)。

**没有这些同步,就不能假设一个 goroutine 的写另一个能看到。** 这和 C++ 的 `std::memory_order` 是同一类问题,Go 把它简化成"用 channel/锁,不要裸共享"。

## 七、context:取消、超时、传值

`context.Context` 是跨 goroutine/跨 API 传递**取消信号、截止时间、请求域值**的标准方式,几乎所有阻塞型标准库/框架 API 第一个参数都是它。

```go
ctx, cancel := context.WithTimeout(context.Background(), 3*time.Second)
defer cancel()                        // 必须调 cancel 释放资源

select {
case res := <-doAsync(ctx):
    use(res)
case <-ctx.Done():                    // 超时或被取消
    fmt.Println("取消原因:", ctx.Err()) // context.DeadlineExceeded / Canceled
}
```

`ctx.Done()` 返回一个在取消时被关闭的 channel,配合 `select` 用。取消信号会沿 context 树向下传播,一处 cancel,所有派生 context 都收到——用于"请求结束了,把它启动的所有下游 goroutine 一起停掉"。`context.WithValue` 传请求域数据(如 trace id),但别拿它传函数参数。

可运行示例:一次 `cancel()` 广播给 3 个 worker,它们各自的 `ctx.Done()` 同时就绪并退出。用 `WaitGroup` 确定性收敛,断言退出计数与 `ctx.Err()`:

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

func main() {
	ctx, cancel := context.WithCancel(context.Background())
	var wg sync.WaitGroup
	const n = 3
	stopped := make(chan int, n)

	for id := 0; id < n; id++ {
		wg.Add(1)
		go func(id int) {
			defer wg.Done()
			for {
				select {
				case <-ctx.Done(): // 收到取消信号, 退出
					stopped <- id
					return
				default:
					time.Sleep(time.Millisecond) // 模拟干活
				}
			}
		}(id)
	}

	time.Sleep(20 * time.Millisecond)
	cancel() // 广播取消: 所有 worker 的 ctx.Done() 一起就绪
	wg.Wait()
	close(stopped)

	fmt.Println("ctx.Err():", ctx.Err())
	fmt.Println("stopped  :", len(stopped))
	// ctx.Err(): context canceled
	// stopped  : 3
}
```

**级联取消是怎么实现的:一棵树 + 每个节点自己的 `Done` channel**。`context.WithCancel`/`WithTimeout`/`WithDeadline` 返回的都是 `*cancelCtx`(`WithTimeout`/`WithDeadline` 只是在 `cancelCtx` 基础上多挂了一个 `time.AfterFunc` 定时器,到点自动调用取消),每个 `cancelCtx` 内部维护一个 `done chan struct{}`(懒创建,第一次调用 `Done()` 才真正 `make`)和一个 `children map[canceler]struct{}` 记录"我派生出的、同样可取消的子 context 都有谁"。调用 `cancel()` 时做两件事:关闭自己的 `done` channel(这一步让所有正在 `select` 监听 `ctx.Done()` 的 goroutine 立刻收到信号),然后**遍历 `children`,递归调用每个子 context 的取消逻辑**,子 context 又会关闭自己的 `done`、再递归到它自己的子节点——这就是"一处 cancel,所有派生 context 都收到"的具体实现:取消信号沿着这棵树自顶向下逐层传播,而不是有一个全局的"取消通知"机制去广播给所有 goroutine。这也解释了为什么 `defer cancel()` 是**必须**的习惯,不只是"最佳实践"层面的建议:创建子 context 时,子节点会把自己注册进父节点的 `children` 里,如果父 context 长期存活(比如挂在一个全局变量上)而你从来不调用为某次请求创建的子 context 的 `cancel()`,这个子节点就会一直挂在父节点的 `children` 表里得不到清理,伴随它的定时器(`WithTimeout` 场景)也不会被释放——这是一种和 goroutine 泄漏同源的资源泄漏,只是泄漏的是 context 树节点和定时器,而不是 goroutine 本身。

### Context.Value:为什么不该拿它传可选参数

`context.WithValue(parent, key, val)` 每次调用都返回一个全新的 `valueCtx`,内部只有三个字段:**指向父 context 的引用、这次存的 key、这次存的 val**——不是很多人以为的"一个并发安全的 map"。多次 `WithValue` 叠加,形成的是一条**单向链表**(每个节点指向上一个),而不是一棵支持随机访问的树。`ctx.Value(key)` 的查找过程是:先比较当前节点的 key 是否匹配,不匹配就顺着父引用往上一层一层找,直到命中或者走到链表顶端的 `Background()`/`TODO()`(返回 nil)——这是一次**线性遍历**,时间复杂度 O(链长)。

**为什么 key 必须用自定义的、未导出的类型,而不是 `string`**:`valueCtx` 存 key 时用的类型是 `interface{}`,两个 `interface{}` 判等的规则是**动态类型和值都要相等**。如果两个不同的包都用 `string` 类型的字面量当 key(比如都用 `"userID"`),它们的动态类型相同(都是 `string`)、值也相同,会被认为是同一个 key——后写入的会**遮蔽**先写入的,且这个过程不会报错或警告,查找方拿到的是最近一次写入的值,不知道自己本该读的是另一个包塞进来的、语义完全不同的东西。用一个包私有的自定义类型当 key(比如 `type traceIDKey struct{}`)从根本上排除了这种可能——不同包定义的类型即便名字凑巧相同,类型本身也是不同的(类型标识里带着包路径),`interface{}` 比较类型这一步就会判定不相等,天然形成命名空间隔离。实测(用 string 做 key 的碰撞 vs 自定义类型):

```go
package main

import (
	"context"
	"fmt"
)

type traceIDKey struct{} // 自定义未导出类型, 天然避免跨包 key 冲突

func main() {
	ctx := context.Background()
	ctx = context.WithValue(ctx, "userID", "A") // 反面示例: 用 string 当 key
	ctx = context.WithValue(ctx, "userID", "B") // 恰好又用了同样的字符串 key
	fmt.Println("string key 冲突后取到:", ctx.Value("userID")) // 只拿到 B, A 被静默遮蔽

	ctx2 := context.WithValue(context.Background(), traceIDKey{}, "trace-123")
	fmt.Println("自定义类型 key:", ctx2.Value(traceIDKey{}))

	// WithValue 派生的子 context 自己不能被 cancel, 但如果父节点是可取消的,
	// 取消信号依然会通过 done channel 传导到子节点(见上文级联取消机制)
	parent, cancel := context.WithCancel(context.Background())
	child := context.WithValue(parent, traceIDKey{}, "trace-456")
	cancel()
	<-child.Done()
	fmt.Println("child.Err():", child.Err())
	// string key 冲突后取到: B
	// 自定义类型 key: trace-123
	// child.Err(): context canceled
}
```

**为什么不推荐用它传可选参数,只应该传"跨 API 边界的请求范围数据"**:`Context.Value` 看起来很方便——不用改函数签名就能往调用链深处塞数据,但这恰恰是它该被谨慎使用的原因。如果一个函数确实需要某个参数才能正确工作(数据库连接、订单 ID、业务开关),把它塞进 `Context` 会让函数签名撒谎——签名上看不出这个函数依赖什么,调用方无法在编译期被提醒"这里少传了什么",只有运行到 `ctx.Value(key)` 返回 nil 时才会在运行时炸出空指针或者用错默认值,这类 bug 又难查又违反 Go "依赖关系应该在签名里显式可见"的一般准则。`Context.Value` 真正该装的是那些"和这次请求本身绑定、贯穿整条调用链、但业务逻辑不必感知具体值"的数据——最典型的是 trace ID:业务代码不需要知道 trace ID 是什么、不需要对它做任何逻辑判断,只是在打日志、发下游 RPC 时顺手带上,这种"路过性"的数据用 `Context.Value` 传递不会破坏调用链上每个函数的可读性;但订单 ID、金额这些直接参与业务逻辑判断的数据,该出现在函数签名里就不要让它借道 `Context` 溜过去。另外,`Context.Value` 存的数据应当被当成**只读**——`valueCtx` 本身没有提供修改已有节点的方法,如果存的是指针或其他可变类型,某个下游 goroutine 却偷偷改了它指向的数据,会悄无声息地污染同一条链路上其他并行读取者看到的内容,这类"数据被谁改的"的问题在并发场景下极难排查,所以哪怕不去改 `Context` 本身的绑定,也不该改它引用的底层数据。

## 八、常见并发模式

**Worker Pool(固定数量 worker 消费任务)**:

```go
jobs := make(chan int, 100)
results := make(chan int, 100)
var wg sync.WaitGroup
for w := 0; w < 4; w++ {              // 4 个 worker
    wg.Add(1)
    go func() {
        defer wg.Done()
        for j := range jobs {         // 自动随 jobs 关闭而退出
            results <- j * j
        }
    }()
}
for i := 1; i <= 20; i++ { jobs <- i }
close(jobs)                            // 关闭 → worker 循环结束
go func() { wg.Wait(); close(results) }()
for r := range results { fmt.Println(r) }
```

**协程池(goroutine pool)本质上就是上面这种固定 worker 数的 Worker Pool,但它要解决的问题和"线程池"并不完全一样**。在 C++/Java 里,线程池的首要目的往往是**避免反复创建/销毁线程的开销**——线程本身很贵,复用是省钱的关键手段。但 Go 里创建、销毁一个 goroutine 的开销小到可以忽略(前面「goroutine:极轻量的协程」一节量化过),所以协程池的核心目的**不是省创建开销,而是限制最大并发数**:如果对每个到来的任务都 `go` 一个新的 goroutine、不加节制,遇到突发流量时会有大量 goroutine 同时运行,可能瞬间打爆下游资源(比如把数据库连接池占满)、或者让内存和 GC 压力骤增(呼应前面「goroutine 数量真的没有上限吗」一节提到的内存和调度开销)。用一个容量固定的任务 channel + 固定数量的 worker,天然把"同时在跑的任务数"钳制在 worker 数量上,这才是协程池存在的意义。

worker 数量怎么定,取决于任务是 CPU 密集还是 IO 密集:**CPU 密集型**任务(纯计算,几乎不阻塞)超过 `runtime.NumCPU()` 个 worker 就没有意义——多出来的 worker 抢的是同样有限的 CPU 时间片,只会增加调度开销而不会提高吞吐;**IO 密集型**任务(网络请求、磁盘 I/O 等,大部分时间在等待)则可以设置远大于 CPU 核数的 worker(比如核数的 5~10 倍甚至更高),因为等待 I/O 时 goroutine 会被 `gopark` 挂起、不占用 M(前面「GMP 调度模型」一节详细展开过这个机制),多开一些 worker 能让 CPU 在等待窗口里去处理别的任务。具体数字没有放之四海而皆准的公式,生产环境通常是压测调出来的。

优雅关闭协程池要保证"已提交的任务都跑完,同时不再接受新任务"——上面代码里的顺序不是随意的:先 `close(jobs)` 阻止新任务进入(此时如果代码里还有地方往 `jobs` 发送,会直接 panic,提交入口需要提前做好状态判断),`range jobs` 会在 channel 排空后自然退出循环,再用 `wg.Wait()` 确认所有 worker 都执行完当前任务、`defer wg.Done()` 触发之后,才 `close(results)`。这个顺序保证了"关闭"和"消费完剩余任务"不会互相踩踏。

**Pipeline(阶段串联,每阶段一个/多个 goroutine,用 channel 连接)**:

```
gen() ──chan──▶ square() ──chan──▶ print()
```

**Fan-out / Fan-in**:fan-out = 多个 goroutine 从同一个 channel 读(分摊活);fan-in = 把多个 channel 合并成一个。

```go
// fan-in: 合并多个输入 channel
func merge(cs ...<-chan int) <-chan int {
    out := make(chan int)
    var wg sync.WaitGroup
    for _, c := range cs {
        wg.Add(1)
        go func(c <-chan int) {
            defer wg.Done()
            for v := range c { out <- v }
        }(c)
    }
    go func() { wg.Wait(); close(out) }()
    return out
}
```

这三种模式都是同一个思想的具体化:用 channel 把"数据的所有权在哪个阶段"表达成显式的管道结构,而不是让多个 goroutine 共享一堆状态、靠隐式约定协调——这正是本章第二节 CSP 哲学在实际工程中的落地形态。

## 九、data race 与 -race 检测器

**数据竞争(data race)**:两个 goroutine 并发访问同一内存,至少一个是写,且无同步。行为未定义——可能读到撕裂值、可能崩溃。Go 不会自动帮你消除竞争(除了 map 会主动崩溃报错,见[第07章](07-复合数据结构.md))。

Go 内置竞争检测器,编译时加 `-race`:

```bash
go run -race main.go
go test -race ./...
```

它在运行时插桩每次内存访问,发现无同步的并发读写就打印详细报告(哪两个 goroutine、哪一行、调用栈)。**性能开销大(慢几倍、内存涨),只在测试/CI 用,不上生产**。这是 Go 并发调试最有用的工具,写并发代码务必用它跑一遍测试。

```
WARNING: DATA RACE
Write at 0x00c000... by goroutine 7:
  main.main.func1() main.go:12
Previous read at 0x00c000... by goroutine 6:
  main.main.func2() main.go:15
```

## 十、Go 内存分配机制与垃圾回收(GC)

前面讨论的都是"并发怎么协调",但 goroutine 之所以能开得起、GC 停顿之所以能压得低,底子上依赖 Go 运行时自己的内存分配器和垃圾回收器——这两者不是并发原语,却是并发能被大规模使用的地基,这里单独展开。

**内存分配:三级缓存 + 按大小分级**。Go 的分配器思路借鉴自 TCMalloc,核心是"按对象大小分级、每级用不同策略",而不是所有分配都走同一条路径:

- **微小对象(<16 字节,且不含指针)**:走 `mcache` 里的 Tiny 分配器,多个微小对象可以共享同一个内存槽位,省下每个对象单独记账的开销。
- **小对象(16 字节~32KB)**:优先从 **P 私有**的线程缓存 `mcache` 分配——`mcache` 是每个 P 独占的,分配时不需要加锁,这是绝大多数对象分配都会走的快路径;`mcache` 里对应规格的 span 用完了,再向全局的 `mcentral` 申请一批。
- **大对象(>32KB)**:直接从管理整个堆的 `mheap` 分配,不经过 `mcache`/`mcentral`。

**为什么要分三级,而不是所有分配都直接找 mheap**:如果每次分配都要访问全局的堆管理结构,多核并发分配时对 `mheap` 的锁竞争会成为瓶颈——这和前面 GMP 一节"P 本地队列避免全局锁竞争"是同一个设计思路的重复应用。`mcache` 绑定在 P 上、无锁访问,把绝大多数(体积小、频率高)的分配都挡在了这一层,只有本地缓存不够用时才触达有锁的 `mcentral`,真正的大对象才会碰到 `mheap`——分配路径上锁竞争的概率,和对象出现的频率恰好反向排列:越常见的分配越不需要锁。

**垃圾回收:三色标记 + 混合写屏障**。Go 的 GC 是并发标记清除,大致分四个阶段:

1. **标记准备(STW)**:短暂 stop-the-world,打开写屏障,为标记做准备。
2. **并发标记**:GC 与用户 goroutine **同时**运行,从根对象(全局变量、各 goroutine 栈上的指针等)出发,用三色标记法遍历对象图——白色(未访问)、灰色(已访问但引用的对象未扫描完)、黑色(已访问且引用对象已扫描完)三种颜色向前推进,直到不再有灰色对象,剩下的白色就是垃圾。
3. **标记终止(STW)**:再次短暂 stop-the-world,关闭写屏障,完成标记收尾。
4. **并发清理**:与用户 goroutine 并发执行,回收所有仍是白色(不可达)对象的内存,Go 1.12 起这一步也做到了并发,进一步压低 GC 对程序的影响。

**为什么并发标记不会因为用户代码同时在改指针而出错,靠的正是"混合写屏障"**:并发标记阶段用户 goroutine 仍在正常运行,随时可能修改对象间的引用关系(比如把一个已经被标记为黑色的对象,改成指向一个还没被标记的白色对象)——如果不做任何干预,这个新指向的对象可能永远不会被扫描到,造成"本该存活的对象被误回收"这种比内存泄漏更严重的正确性问题。写屏障的作用就是在这类指针赋值发生的瞬间拦截一下,把新引用到的对象重新标记为需要扫描的灰色,从而保证"标记开始时可达的对象,标记结束时一定被认为存活"这一不变式不被并发的用户代码破坏。这也是标记准备/标记终止阶段仍然需要 STW 的原因:开启/关闭写屏障这个动作本身需要一个所有 goroutine 都暂停的时间点来保证一致性;但写屏障只在指针赋值时做一点点额外记账,不需要遍历整个堆,这两次 STW 才能被压缩到极短——这正是 Go 的 GC 停顿从早期的几百毫秒级,演进到如今通常在几十微秒到毫秒级的关键改造点。

## 十一、内存分配优化实践

理解了分配器和 GC 怎么工作,内存优化的方向就不是玄学,而是"减少落到堆上的分配次数和大小",围绕这个目标有几类具体手段:

**预分配容量,避免扩容期间的重复分配与拷贝**:`make([]int, 0, 100)` 比不带容量的写法更省——slice 扩容涉及重新分配一块更大内存、把旧数据整体拷过去,如果能提前估算好容量,这些中间态的分配和拷贝可以完全省掉。

**用 `sync.Pool` 复用临时对象,但要理解它的两级结构和生命周期**:`sync.Pool` 内部是"每个 P 一个私有对象槽位 + 一个共享对象链表"的两级结构——`Get()` 优先拿本 P 的私有对象(无锁,快),拿不到就去偷其他 P 共享链表里的对象(和 GMP 的 work-stealing 是同一个思路),还拿不到才调用用户提供的 `New` 函数新建。它特别适合"频繁创建、生命周期极短"的临时对象(比如处理 HTTP 请求时用的缓冲区),但**不适合需要持久管理状态的对象**(比如数据库连接):Pool 里的对象会在 GC 发生时被无通知地清空,它只是"减少分配次数"的优化手段,不是一个可控的生命周期管理工具。

**结构体字段顺序影响内存对齐,进而影响结构体总大小**:Go 编译器会在编译期自动做内存对齐,如果字段大小不一、排列不合理,编译器会在字段之间插入空白字节填充,让每个字段的起始地址满足对齐要求。把字段按大小从大到小排列(或者把大小相同的字段放在一起),能让编译器插入的填充字节最少。实测差异:

```go
package main

import (
	"fmt"
	"unsafe"
)

// 字段顺序: bool, int64, bool —— 两个 bool 被 int64 隔开, 各自都要单独凑齐对齐
type Bad struct {
	A bool
	B int64
	C bool
}

// 按大小从大到小排列: int64, bool, bool —— 两个 bool 可以挤进同一个对齐槽
type Good struct {
	B int64
	A bool
	C bool
}

func main() {
	fmt.Println("Bad  size:", unsafe.Sizeof(Bad{}))
	fmt.Println("Good size:", unsafe.Sizeof(Good{}))
	// Bad  size: 24
	// Good size: 16
}
```

同一组字段仅仅调整声明顺序,大小就从 24 字节降到 16 字节——批量创建大量该类型实例的场景下(比如一个百万级 slice 装的都是这个结构体),差异会被放大到可观的内存量级。

**减少不必要的指针,尤其是在高频分配的类型里**:含指针字段的结构体会增加 GC 扫描的负担——标记阶段要沿着每个指针字段往下追,指针越多、层级越深,单次扫描的工作量越大;而且前面「逃逸分析实操」一节已经说明,指针语义本身也更容易触发变量逃逸到堆上(取地址、通过指针跨函数传递都是常见的逃逸诱因)。对小结构体,优先考虑值传递而不是指针传递,既避开了逃逸,也减轻了 GC 扫描压力。

**用 `strings.Builder` 代替 `+`/`+=` 拼接字符串**:Go 的字符串不可变,`s1 + s2` 每次都会分配一块新内存把两段内容拷过去,循环拼接 n 次就是 n 次分配;`strings.Builder` 内部用可增长的 `[]byte` 缓冲区攒结果,只在最后一次性转换成 `string`,把 n 次分配压缩到接近 1 次(配合预估好的 `Grow(n)` 效果更好)。

**用 pprof 定位真正的热点,而不是凭直觉优化**:上述手段都是"知道瓶颈在哪之后"的具体招数,实际排查内存问题应该先用 `go tool pprof` 的 heap profile 找到分配次数/分配总量最高的调用路径,再针对性应用这些手段——盲目地把所有 slice 都预分配、所有对象都塞进 Pool,收益往往远不如先测量再优化。

## 十二、内存泄漏的常见场景

**"Go 有 GC,为什么还会内存泄漏"这个问题本身建立在一个误解上**:GC 只能回收**不可达**的对象,它解决的是"忘了用完之后主动释放"这个问题,但完全解决不了"对象仍然被某个活跃的引用链持有,但业务逻辑上早就不再需要它"这个问题——这不是 GC 的缺陷,而是 GC 的定义决定的边界:可达性分析回答的是"这块内存还有没有指针指向它",不是"这块内存还有没有用"。以下几种场景都落在这个边界之内,GC 对它们无能为力:

**goroutine 泄漏**:goroutine 永久阻塞在一个不会再就绪的 channel 操作、一把不会再释放的锁、或者陷入没有退出条件的循环时,这个 goroutine(连同它的栈、它持有的所有堆对象引用)会一直存在——它是"活跃"的,只是永远不会再往前推进;GC 对它做可达性分析时,它的栈仍然指向那些对象,一切都被判定为可达,不会被回收。用一个确定性的例子验证:向一个没有接收方的无缓冲 channel 发送数据,goroutine 会永远卡在发送语句上:

```go
package main

import (
	"fmt"
	"runtime"
	"time"
)

// leaky 启动一个 goroutine 向 ch 发送数据,
// 但没有人接收 —— 这个 goroutine 会永远阻塞在 ch <- 1,
// 它仍是"活跃"的, 只是被永久阻塞, GC 不会回收它。
func leaky(ch chan<- int) {
	go func() {
		ch <- 1 // 永远没有接收方, 永久阻塞在这里
	}()
}

func main() {
	runtime.GC()
	time.Sleep(10 * time.Millisecond)
	base := runtime.NumGoroutine()

	const n = 50
	for i := 0; i < n; i++ {
		leaky(make(chan int)) // 每次传入一个新的、没有接收方的 channel
	}
	time.Sleep(50 * time.Millisecond) // 给这些 goroutine 时间真正启动并阻塞在发送上

	after := runtime.NumGoroutine()
	fmt.Println("base goroutines:", base)
	fmt.Println("after leak      :", after)
	fmt.Println("leaked at least :", after-base >= n)
	// base goroutines: 1
	// after leak      : 51
	// leaked at least : true
}
```

这 50 个 goroutine 会一直占着内存,直到进程退出——没有任何机制能唤醒它们。避免的方法呼应前面「context:取消、超时、传值」一节:给可能阻塞的操作配合 `ctx.Done()`/`time.After` 兜底,或者确保 channel 的发送方和接收方数量、生命周期能对得上。

**未正确释放的系统资源**:文件句柄、网络连接、数据库连接这些是操作系统资源,不是 Go 堆内存——包装它们的 Go 对象(比如 `*os.File`)本身会正常被 GC 回收,但如果没有显式调用 `Close()`,底层的文件描述符/socket 不会随之释放,而这类资源在系统层面通常有配额(单进程可打开的文件描述符数),攒得多了程序会直接因为"打开文件过多"报错崩溃——这和堆内存泄漏是两种不同层面的资源耗尽。`defer file.Close()` 这种写法能生效,是因为它把释放和获取绑在同一个函数作用域内,不依赖 GC 的时机。

**长生命周期对象持有短生命周期数据**:最常见的是没有淘汰策略的全局缓存/`map`——每次往里面塞新数据从不删旧数据,这块内存的引用链一直挂在全局变量上,天然可达,GC 永远不会碰它,增长没有上限。修复思路通常是给缓存加过期时间或者 LRU 淘汰,而不是指望 GC 帮忙清理。

**子切片长期引用大数组的底层存储**:Go 的 slice 是对底层数组的一个视图(指针+长度+容量),`sub := big[100:110]` 这种切片操作不会拷贝数据,`sub` 内部仍然指向 `big` 的底层数组。如果 `big` 本身很大(比如一次性读入的一整个大文件),而 `sub` 又被长期保存下来(比如存进了某个全局结构),即使代码里已经完全不需要 `big` 剩下的元素,只要 `sub` 还活着,整个底层数组就不会被回收——这是"可达性"和"实际需要"脱节最隐蔽的一种情况。规避方式是需要长期保留一小段数据时,显式 `copy` 出一份独立内存,而不是直接切片持有原数组的引用。

**`sync.Pool` 使用不当也可能短时间内撑爆内存**:`sync.Pool` 里的对象最终会在 GC 时被清理掉,这不假,但"最终会被清理"和"当下不会占用内存"是两回事——如果在一次并发高峰期往 Pool 里塞了大量占用巨大内存的对象且不加限制,在下一次 GC 真正发生之前,这些对象会实实在在地占着内存,某种意义上是"迟早会好,但撑不到那个时候"的泄漏。

避免这几类问题没有单一银弹,但检测手段是共通的:`pprof` 的 heap profile 能看到当前堆上存活对象按类型/调用栈的分布,持续增长且不回落的类型往往就是嫌疑对象;goroutine 泄漏专门看 `runtime.NumGoroutine()` 或 `pprof` 的 goroutine profile 是否持续增长;第三方的 `go-leak` 等工具则专门针对测试场景检测残留 goroutine。

## 小结

- **用法层面**:`go f(x,y)` 启动 goroutine,不等它跑完;channel 用 `make`/`<-`/`close`/`range` 收发和同步;`select` 同时等待多个 channel,配 `default` 做非阻塞、配 `time.After` 做超时;`sync.Mutex`/`WaitGroup`/`atomic` 处理共享状态;`context` 传取消/超时;worker pool、pipeline、fan-in/out 是常见骨架;写并发代码要用 `-race` 跑一遍。
- **设计取舍**:goroutine 是 2KB 起步、用户态调度的协程,便宜到几十万个可行,靠的是"小栈"和"运行时集成调度器"两者共同作用,少一个都不够;GMP 三元组把"并行度"(P,数量=GOMAXPROCS)和"线程数"(M,可按需超过 P)解耦,系统调用阻塞时 P 可以转交别的 M,并行度不因单次阻塞下降;网络 I/O 靠 netpoller 把同步写法转成事件驱动;无缓冲 channel 的"会合"语义是它定义本身的推论,天然提供 happens-before;`select` 多个 case 就绪时随机选择,是防止程序依赖不该依赖的书写顺序,与 map 遍历顺序随机化同源;`sync.Mutex` 阻塞的是 goroutine 而非线程,与 channel 共用同一套挂起-唤醒机制;正确性由 happens-before 保证,没有同步就不能假设写操作对另一个 goroutine 可见。
