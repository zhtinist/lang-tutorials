错误处理与资源管理:异常与垃圾回收

C++ 用异常做错误传播,用 RAII(析构函数)做资源释放,用手动 delete/智能指针管内存。Java 把这三件事拆成:异常体系、try-with-resources(近似 RAII)、以及自动垃圾回收(GC)。

一、try/catch/finally 基本写法

抛出并捕获一个异常(除以 0 会抛 ArithmeticException):

public class QuickTry {
    public static void main(String[] args) {
        try {
            int x = 10 / 0;          // 抛出 ArithmeticException
            System.out.println("不会执行到这里: " + x);
        } catch (ArithmeticException e) {
            System.out.println("捕获异常: " + e.getMessage());
        } finally {
            System.out.println("finally 总会执行");
        }
        System.out.println("程序继续往下跑");
    }
}
// 捕获异常: / by zero
// finally 总会执行
// 程序继续往下跑

要点:try 包住可能出错的代码;catch (类型 变量) 按类型匹配来接住异常;finally 里的代码不管有没有异常都会跑一遍(常用来做扫尾清理)。异常发生后,try 块里从出错点开始的代码不会再执行(上例里 x 那行的 println 不会跑),直接跳到匹配的 catch。

关闭一次资源(try-with-resources):C 里打开文件要记得 fclose,Java 里只要资源实现了 AutoCloseable,写 try (...) 就能保证用完自动关闭,不用手写 finally { close(); }:

public class QuickTWR {
    // 一个最简单的可关闭资源:实现 AutoCloseable 即可
    static class SimpleResource implements AutoCloseable {
        SimpleResource() { System.out.println("打开资源"); }
        void use() { System.out.println("使用资源"); }
        @Override public void close() { System.out.println("关闭资源"); }
    }

    public static void main(String[] args) {
        try (SimpleResource r = new SimpleResource()) {
            r.use();
        }
        System.out.println("try 块结束后 close() 已经被自动调用");
    }
}
// 打开资源
// 使用资源
// 关闭资源
// try 块结束后 close() 已经被自动调用

try (SimpleResource r = new SimpleResource()) 括号里声明的资源,在 try 块(不管正常结束还是抛异常)结束时,close() 都会被自动调用一次——这是 Java 里最接近 C++ RAII/析构函数的写法。

还有几个问题需要搞清楚:异常抛出后 JVM 到底怎么找到该由哪个 catch 接住?finally 为什么”总会执行”?try-with-resources 关闭多个资源时顺序是怎样的、如果 close() 本身也抛异常怎么办?下面依次展开。

二、异常体系:受检 vs 非受检

Java 异常分两大类,写代码时的实际区别是:受检异常编译器强制你处理,非受检异常不强制。

import java.io.*;

public class QuickChecked {
    // 受检异常:方法签名必须写 throws,否则编译不过
    static void mightFail(boolean fail) throws IOException {
        if (fail) throw new IOException("模拟IO失败");
        System.out.println("读取成功");
    }

    // 非受检异常:不需要 throws 声明
    static int divide(int a, int b) {
        return a / b; // b=0 时抛 ArithmeticException,编译器不会强制处理
    }

    public static void main(String[] args) {
        try {
            mightFail(true);
        } catch (IOException e) {
            System.out.println("捕获受检异常: " + e.getMessage());
        }

        try {
            divide(1, 0);
        } catch (ArithmeticException e) {
            System.out.println("捕获非受检异常: " + e.getMessage());
        }
    }
}
// 捕获受检异常: 模拟IO失败
// 捕获非受检异常: / by zero

如果 mightFail 声明了 throws IOException,调用它的代码要么用 try/catch 接住,要么自己也在方法签名上写 throws IOException 往外抛——否则编译器直接报错。divide 抛的 ArithmeticException 没有这个约束,你可以选择捕获,也可以不管,编译器不拦。

一切可抛出对象继承自 Throwable。它有两条主线:

                Throwable
               /         \
           Error        Exception
        (JVM 层严重故障)   /       \
     OutOfMemoryError  RuntimeException  其他(受检异常)
     StackOverflowError  (非受检)          IOException
                          NullPointerException  SQLException
                          IllegalArgumentException ...
类别 是否受检 语义 C++ 类比
Error 否 JVM 层面不可恢复(栈溢出、堆耗尽),不该 catch 近似 std::bad_alloc 之类系统级
RuntimeException 否 编程错误(空指针、越界、非法参数),应靠代码避免 逻辑错误,类似 assert 该拦住的
受检 Exception 是 可预期的外部失败(IO、网络),编译器强制处理 C++ 无对应,已废弃的 throw() 规格是反例

受检 vs 非受检是 Java 独有的编译期约束:受检异常必须在方法签名 throws 声明,或就地 try/catch,否则编译不过。C++ 早期的动态异常规格(throw(...))因难用被废弃,Java 保留了但也饱受争议。

上面的树只画了几个最常见的代表,实际接触到的远不止这些,按三个类别再补全一份常见清单:

类别 常见类型 触发场景
Error OutOfMemoryError、StackOverflowError、NoClassDefFoundError(运行时找不到类定义)、VirtualMachineError JVM 内存/资源耗尽、类加载失败、虚拟机内部故障
受检 Exception IOException、FileNotFoundException、SQLException、ClassNotFoundException(按字符串加载不存在的类)、InterruptedException(线程被中断) 文件/网络/数据库等外部资源失败,线程协作被打断
RuntimeException NullPointerException、ArrayIndexOutOfBoundsException/IndexOutOfBoundsException、ClassCastException(强制类型转换失败)、IllegalArgumentException、NumberFormatException(字符串转数字格式错误)、ArithmeticException 空指针解引用、越界访问、非法强转、参数校验失败、数字解析失败、非法算术运算(如整数除零) 
import java.io.*;
public class Checked {
    // 受检:必须声明 throws,否则编译错误
    static String readFirst(String path) throws IOException {
        try (BufferedReader r = new BufferedReader(new FileReader(path))) {
            return r.readLine();
        }
    }
    // 非受检:无需声明,编译器不拦
    static int div(int a, int b) { return a / b; } // b=0 抛 ArithmeticException
}

为什么要单独设计一个 Error 类,而不是让程序直接崩溃

Error 和 Exception 都继承自同一个 Throwable,这不是随意的类层级安排:即便 Error 代表的问题(栈溢出、堆耗尽、JVM 内部故障)本质上”无法恢复”、“不该被业务代码捕获处理”,Java 仍然把它包装成一个可携带信息的对象,而不是让 JVM 直接静默终止进程——原因是统一的可抛出对象体系带来统一的诊断能力:无论程序死于业务逻辑错误还是死于系统级故障,最终都会沿着同一套栈展开机制(下一节详述)向上传播,都能打印出一致格式的堆栈轨迹(哪个类、哪一行、调用链是什么),都能被最外层统一记录日志。如果 Error 不纳入这套体系,JVM 遇到栈溢出、内存耗尽时就只能用一种完全独立的、不可编程的方式终止(比如直接打印一条 C 层面的崩溃信息然后退出),运维和开发者就失去了通过熟悉的 Java 异常处理机制(哪怕只是 catch (Throwable t) { log(t); } 这种兜底记录)去捕捉”程序到底死于什么”的手段。语法上你确实可以写 catch (Error e) 甚至 catch (Throwable t),但这只应该用来做日志记录或资源清理这类兜底动作,而不应该期望程序在捕获后还能继续正常工作——Error 携带的信息是给人看的诊断线索,不是给程序逻辑判断走向的信号。

为什么要区分受检异常与非受检异常,而不是像 C++/Python 那样只有一种异常

这是两种不同的错误处理哲学在编译器强制力上的直接体现。Java 对受检异常选择编译期 fail-fast:一个方法只要声明可能抛出 IOException,所有调用者要么显式处理、要么继续往外声明,编译器在你写下调用语句的那一刻就逼你面对”这里可能失败”这个事实——好处是像文件/网络这类注定会在某些环境下失败的操作,不会被开发者无意间遗忘处理,坏处是大量样板 try/catch/throws 声明,并且有开发者为了让代码编译通过而写空的 catch 块吞掉异常,反而制造了虚假的健壮性。C++、Python 这类语言选择运行期发现:异常不出现在方法签名里,编译器完全不检查,代码更精简,但一个可能失败的调用如果没人记得包一层 try,问题会被推迟到程序真正跑到那一行、真正失败的那一刻才暴露——可能是生产环境上线很久之后。Java 的取舍是用编译期的啰嗦换运行期的可预测性,只对”外部环境失败,程序逻辑无法避免”(IO、网络、数据库)这类异常做强制检查,而把”编程错误,应该靠写对代码来避免”(空指针、数组越界、非法参数)排除在强制检查之外——这正是上面表格里 RuntimeException 那一行”应靠代码避免”的含义:检查这类错误不该是运行时的事,而是开发阶段该被测试和代码审查堵住的事,编译器再插手意义不大。

把受检异常包装成非受检异常向外抛

实践中经常出现:底层 API(如反射、序列化)签名上必须声明受检异常,但调用它的这一层业务逻辑其实认为这个异常”不可能发生”或”发生了也没法在这一层恢复”,硬要一路 throws 声明下去会污染一长串调用链的方法签名。常见做法是在这一层把受检异常包装成一个非受检异常再抛出,同时用异常链保留根因(呼应第五节的 cause):

static void loadConfig(String name) {
    try {
        Class.forName(name);                 // 声明 throws ClassNotFoundException(受检)
    } catch (ClassNotFoundException e) {
        throw new IllegalStateException("配置类缺失: " + name, e);  // 转成非受检,附带根因
    }
}

好处是调用方的方法签名不再被迫层层声明 throws;代价是调用方如果确实想针对这个具体失败做特殊处理,需要多一步 instanceof/getCause() 判断,不像受检异常那样在签名上直接可见——这是一种有意的取舍:把”这里几乎不会失败,失败了也没法优雅恢复”的场景,从编译器强制处理降级为可选处理。

三、try/catch/finally 与栈展开

finally 块不管 try 里是正常返回还是抛了异常,都会执行一遍——上一节 QuickTry 已经演示过:即使 10 / 0 抛出了异常,finally 里的 println 照样跑。这让它很适合放”不管成不成功都要做”的收尾动作,比如打日志、释放非 AutoCloseable 的资源。

抛出异常时,JVM 从当前方法开始查其 异常表(exception table)——javac 为每个 try 块生成一条 [起始PC, 结束PC, 处理器PC, 捕获类型] 记录。若当前帧无匹配处理器,该帧被弹出(栈展开,stack unwinding),沿调用链回溯,直到找到匹配的 catch 或到达线程栈底(此时线程终止并打印栈轨迹)。

finally 无论正常还是异常都执行。字节码层面,编译器会把 finally 的代码复制到每条正常/异常出口路径上(或用异常表 + athrow 兜底),这是它”必然执行”的实现方式。

public class Finally {
    static int tricky() {
        try {
            return 1;          // 先算出返回值 1 压栈
        } finally {
            return 2;          // finally 的 return 覆盖它 -> 实际返回 2(反模式!)
        }
    }
    public static void main(String[] args) {
        System.out.println(tricky()); // 2
    }
}

陷阱:finally 里 return 或抛异常会吞掉 try 中的返回值/异常。切勿在 finally 里 return。

四、try-with-resources:Java 的 RAII

上一节 QuickTWR 已经展示了最基本的用法:资源类实现 AutoCloseable,写在 try (...) 括号里,close() 就会在 try 块结束时自动调用——不管块里是正常跑完还是中途抛了异常。

C++ 靠对象离开作用域时析构函数确定性释放资源(RAII)。Java 对象的回收时机不确定(GC 说了算),所以不能靠 finalize 关文件。JDK7 引入 try-with-resources:任何实现 AutoCloseable(close())的对象,在 try 块结束时保证按声明的逆序调用 close()——这是 Java 最接近 RAII 的确定性资源管理。

import java.io.*;
public class TWR implements AutoCloseable {
    private final String name;
    TWR(String name) { this.name = name; System.out.println("open " + name); }
    @Override public void close() { System.out.println("close " + name); }

    public static void main(String[] args) {
        // 逆序关闭:先 close b,再 close a(类似 C++ 局部对象逆序析构)
        try (TWR a = new TWR("A"); TWR b = new TWR("B")) {
            System.out.println("body");
            throw new RuntimeException("boom");
        } catch (RuntimeException e) {
            System.out.println("caught: " + e.getMessage());
            // close 抛出的异常会作为“被抑制异常”挂在主异常上:
            for (Throwable s : e.getSuppressed()) System.out.println("suppressed: " + s);
        }
    }
    // 输出:open A / open B / body / close B / close A / caught: boom
}

区别于 C++:close() 的调用点由编译器插桩在 try 出口,而对象内存本身仍由 GC 稍后回收。即”资源(fd/句柄)确定性释放”与”内存非确定性回收”是分离的两件事。

上面的 close() 不抛异常,所以 getSuppressed() 是空的。当 try 体和 close() 都抛异常时,才看得到”被抑制异常”机制:主异常是 try 体抛的,两个 close() 的异常按逆序挂到主异常上:

public class Suppressed implements AutoCloseable {
    private final String name;
    Suppressed(String name){ this.name = name; }
    @Override public void close() {
        System.out.println("close " + name);
        throw new RuntimeException("close-fail-" + name);   // close() 自己也抛
    }
    public static void main(String[] args) {
        try (Suppressed a = new Suppressed("A"); Suppressed b = new Suppressed("B")) {
            throw new RuntimeException("body-fail");         // 主异常
        } catch (RuntimeException e) {
            System.out.println("primary   : " + e.getMessage());
            for (Throwable s : e.getSuppressed())            // close 抛的异常挂在这里
                System.out.println("suppressed: " + s.getMessage());
        }
    }
}
// close B                   <- 逆序关闭
// close A
// primary   : body-fail     <- try 体的异常胜出为主异常
// suppressed: close-fail-B  <- close 的异常被"抑制",逆序附加
// suppressed: close-fail-A

五、多重捕获与异常链

一个 catch 用 | 分隔多个类型,就能用同一段处理逻辑接住不同种类的异常,不用写重复代码:

public class QuickMultiCatch {
    static void parse(String s) {
        if (s == null) s.length();   // 对 null 调方法,直接触发 NullPointerException
        Integer.parseInt(s);         // 格式不对时抛 NumberFormatException
    }

    public static void main(String[] args) {
        String[] inputs = { null, "abc" };
        for (String s : inputs) {
            try {
                parse(s);
            } catch (NumberFormatException | NullPointerException e) {
                // 一个 catch 同时处理两种类型
                System.out.println("解析失败: " + e.getClass().getSimpleName());
            }
        }
    }
}
// 解析失败: NullPointerException
// 解析失败: NumberFormatException
public class MultiCatch {
    static void handle(String s) {
        try {
            Integer.parseInt(s);
        } catch (NumberFormatException | NullPointerException e) {
            // 多重捕获:一个 catch 处理多种类型,e 是隐式 final,类型为共同父类
            // 异常链:保留“根因(cause)”,便于定位原始故障
            throw new IllegalStateException("处理失败: " + s, e);
        }
    }
    public static void main(String[] args) {
        try { handle(null); }
        catch (IllegalStateException e) {
            System.out.println(e.getMessage());
            System.out.println("根因: " + e.getCause());
            // 根因: java.lang.NumberFormatException: Cannot parse null string
            // 注:现代 JDK 里 Integer.parseInt(null) 内部已显式判空并直接抛
            // NumberFormatException("Cannot parse null string"),而不是 NPE——
            // 这里 catch 两种类型仍然有意义:换一种解析方式(比如先手动取 s.length()),
            // 空指针路径就会走 NullPointerException 分支。
        }
    }
}

异常链(initCause / 带 cause 的构造器)让你在转译异常时不丢原始堆栈,打印时会出现 Caused by: 段落。

六、IO 流:确定性资源管理的典型场景

前面几节讲的 AutoCloseable、栈展开、被抑制异常,在真实代码里几乎都是围着”一个流用完必须关”这件事转的——文件、socket 是最常见的、必须显式关闭的非内存资源(呼应「运行模型」“内存交给 GC,句柄仍需显式关”这句话)。这一节把 Java IO 的类型体系过一遍,顺便再巩固一次 try-with-resources。

字节流与字符流:为什么要分两套类型体系

C 用一套 FILE* + fread/fwrite 处理任何数据源,不区分”这堆字节是不是文本”。Java 把 IO 类型体系从根上一分为二:

  • 字节流:InputStream/OutputStream 及其子类,以字节(8 bit)为单位,面向任意二进制数据(图片、视频、序列化对象)。
  • 字符流:Reader/Writer 及其子类,以字符为单位,内部自动处理字节到字符的编码转换。

为什么不能只用字节流,非要多一套字符流:字节和字符不是同一个东西——同一个中文字符,UTF-8 编码是 3 字节,GBK 编码是 2 字节,UTF-16 是 2 字节;如果只有字节流,任何”读一行文本”这种操作都得由调用者手动指定编码、手动拼字节、手动判断多字节字符有没有被从中间切断(读缓冲区边界恰好切在一个多字节字符中间,是乱码的经典来源)。Java 把”字节 ↔︎ 字符”这层编码转换封装进 Reader/Writer(通过 InputStreamReader/OutputStreamWriter 这两个桥接类完成),之后面向 Reader 编程时,readLine()/read() 返回的都已经是正确解码过的 char,不用操心一个字符是几字节、边界会不会被切断。代价是多了一套并行的类型体系(每个字节流概念上都有一个对应的字符流版本),换来的是”处理文本”和”处理二进制”两件事各自类型安全、互不误用——不会有人不小心把一张 JPEG 当 UTF-8 文本硬解码。

节点流与处理流:装饰器模式

FileInputStream 这类节点流直接包一个真实的数据源(文件、socket、内存数组);BufferedInputStream、DataInputStream、ObjectInputStream 这类处理流(包装流)不直接连数据源,而是包住另一个流、在它之上叠加功能:

new BufferedReader(new InputStreamReader(new FileInputStream("a.txt"), StandardCharsets.UTF_8))

这一行从内到外:FileInputStream 打开文件拿到字节流 → InputStreamReader 按 UTF-8 把字节解码成字符流 → BufferedReader 在字符流外面再包一层缓冲,提供 readLine()。这正是装饰器模式——每一层只加一种能力,不改变被包装对象的接口(都实现同一个 Reader/InputStream 抽象),层层叠加,是「面向对象与类型系统」“组合优于继承”一节的具体体现:Java 不需要为”带缓冲的、按行读的、UTF-8 解码的文件流”专门写一个类,而是用几个单一职责的类组合出来。

用 try-with-resources 正确读写文件

import java.io.*;
import java.nio.charset.StandardCharsets;

public class IoDemo {
    public static void main(String[] args) throws IOException {
        try (BufferedReader br = new BufferedReader(
                new InputStreamReader(new FileInputStream("input.txt"), StandardCharsets.UTF_8));
             BufferedWriter bw = new BufferedWriter(
                new OutputStreamWriter(new FileOutputStream("output.txt"), StandardCharsets.UTF_8))) {
            String line;
            while ((line = br.readLine()) != null) {
                bw.write(line);
                bw.newLine();
            }
        }
    }
}

多个资源用分号隔开写在同一个 try (...) 里,关闭顺序仍是声明的逆序(先关 bw 再关 br)——和第四节 TWR 例子的规则完全一致。

flush 与 close 的关系

BufferedWriter/BufferedOutputStream 内部攒了一块缓冲区,write() 调用不一定立刻触达底层文件——flush() 强制把缓冲区内容推到底层,close() 内部会先 flush() 再释放底层资源(文件描述符)。忘记 flush 又不走 try-with-resources 的话,缓冲区里的数据可能因程序异常退出而丢失,这也是 try-with-resources 优先于手写 finally { close(); } 的原因之一——不用记着关闭顺序和 flush 时机,编译器插桩全部处理好。

NIO 简述

java.nio 提供 Channel + Buffer 的另一套模型,支持非阻塞 IO 和更高效的大文件/网络吞吐,Files.copy()、FileChannel.transferTo() 这类 API 常用来做大文件复制(可利用零拷贝)。这套模型与传统 java.io 流是并行的两条路,细节不在本章展开。

七、垃圾回收(GC)

C 和 C++ 里,内存归你自己管:malloc/free,new/delete,忘了 free 就是泄漏,多 free 一次就是崩溃。Java 里没有 delete——你 new 出来的对象,什么时候释放、被谁释放,完全交给一个后台机制:垃圾回收器(Garbage Collector,GC)。它会在合适的时候扫一遍堆,把”没人再用得到”的对象内存收回来。代价是:你不知道确切的回收时刻,而且回收本身可能让程序短暂卡顿(即”停顿”/STW)。理解 GC 的原理,才能在出问题时看懂日志、调对参数。

GC 全程自动运行,你能直接调用的 API 不多,主要是 WeakReference/SoftReference/Cleaner/System.gc() 这几个——它们仍然遵循”先怎么用、再底层”的顺序;而”分代假设”“收集器怎么演进”这类纯概念内容,直接进底层讲。

八、分代假设与堆布局

这部分是纯理解性内容——GC 自己运行,你不需要写代码触发它,但看懂堆是怎么分区的,才能看懂后面”收集器怎么选”“调优参数改哪个”。

GC 建立在弱分代假设(weak generational hypothesis)上:绝大多数对象朝生夕死;活得久的对象很少指向年轻对象。于是把堆分代管理:

                Java 堆
 +---------------------------------------------------+
 | 新生代 Young Gen                                  |
 |  +----------+  +----------+  +----------+         |
 |  |  Eden    |  | Survivor |  | Survivor |         |
 |  | (新对象) |  |   S0     |  |   S1     |         |
 |  +----------+  +----------+  +----------+         |
 +---------------------------------------------------+
 | 老年代 Old Gen (Tenured)  长寿对象               |
 +---------------------------------------------------+
   (元空间 Metaspace 在本地内存,存类元数据,不在堆内)
  • 新对象在 Eden 分配(指针碰撞,极快,类似栈顶推进)。
  • Eden 满触发 Minor GC:存活对象复制到某个 Survivor,年龄 +1;每熬过一次 Minor GC 年龄增长,超过阈值(默认 15,-XX:MaxTenuringThreshold)晋升到老年代。两个 Survivor 轮流做”复制目标”,始终有一个为空(复制算法,避免碎片)。
  • 老年代满触发 Major GC(老年代回收);Full GC 通常指整堆 + 元空间回收,最慢,应尽量避免。(注:“Major GC”是分代式收集器的经典术语;G1/ZGC 等现代收集器说法不同——G1 分 young / mixed / full,其中 Full GC 是它退化时的兜底全堆回收。)
GC 类型 回收范围 触发 停顿
Minor GC 新生代 Eden 满 短
Major GC 老年代 老年代满 长
Full GC 整堆 + 元空间 老年代/元空间不足、System.gc() 最长

三种基础回收算法，以及为什么新生代老年代各用一种

上面提到”两个 Survivor 轮流做复制目标”，背后是复制算法；老年代满了触发的 Major GC，用的是另一套算法。把三种基础算法摆在一起对比，能看清楚”分代收集”这个策略到底是怎么落地成具体算法选择的：

算法 做法 优点 缺点 用在哪
标记-清除 Mark-Sweep 标记所有存活对象，清除未标记的 不需要移动对象，存活对象多时开销低 产生内存碎片；标记、清除各扫一遍堆，两次开销 老年代（存活率高，移动代价大）
复制 Copying 存活对象整体复制到另一块空间，原空间整体清空 只扫一遍，顺带完成整理，没有碎片 需要一块等大的备用空间，存活对象一多复制开销反超 新生代（弱分代假设下存活率低，复制成本小）
标记-整理 Mark-Compact 标记存活对象后，将其移动到内存一端紧凑排列，再清理边界外空间 没有碎片，不需要双倍空间 移动对象本身有开销（要同步更新所有指向它的引用） 老年代（在”不能有双倍空间”和”不能有碎片”之间的折中）

为什么新生代用复制、老年代用标记-整理/标记-清除：这正是弱分代假设的直接推论——新生代里对象”朝生夕死”，一次 Minor GC 通常只有少量对象存活，复制算法的成本正比于存活对象数量而非堆的总大小，存活率低时复制几乎是免费的整理；老年代反过来，对象存活率高，如果还用复制算法，大部分堆内容都要被复制一遍，而且复制算法天生需要预留一半空间当”备用区”，在老年代这种大空间上双倍浪费不可接受，所以老年代选择直接在原地清理（标记-清除）或原地紧凑（标记-整理）——具体选哪个，是”清除快但留碎片”与”整理慢但不留碎片”之间的权衡，不同收集器给出了不同答案（下一节详细展开）。

分代收集算法（Generational Collection）不是与前三者并列的”第四种算法”，而是”把堆分区、每个区选最适合它的算法”这个策略本身——它是上面三种算法在”弱分代假设”这个前提下的组合应用，Eden/Survivor/老年代的布局就是这个策略的具体落地。

九、可达性分析与 GC Roots

Java 不用引用计数(无法处理循环引用),而用可达性分析(reachability analysis):从一组 GC Roots 出发遍历引用图,凡不可达的对象即可回收。

GC Roots 包括:

  • 各线程栈帧局部变量表中的引用(正在执行的方法引用的对象);
  • 静态字段引用的对象;
  • 常量池引用、JNI 全局引用;
  • 同步锁持有的对象等。
GC Roots
  | 线程栈局部变量  ---> A ---> B      (A、B 可达,存活)
  | 静态字段        ---> C
                          C <---> D    (C、D 互相引用)
                                E ---> F  (E、F 互相引用但无 Root 可达 => 都回收)

注意最后一组:E、F 循环引用,引用计数法会误判为存活,而可达性分析正确判定它们为垃圾。这正是 Java 不用引用计数的原因。

十、收集器演进与 STW 权衡

STW(Stop-The-World):GC 的某些阶段必须暂停所有应用线程(到达”安全点 safepoint”),以获得一致的堆快照。收集器的进化史,本质是不断缩短 STW的历史。

收集器 特点 STW 适用
Serial 单线程,简单 全程 STW,较长 小堆、客户端
Parallel(吞吐优先) 多线程并行回收 STW 但并行 批处理,重吞吐
CMS(JDK9 弃用、JDK14 已移除) 并发标记清除,低停顿先驱 部分并发 老年代低延迟(有碎片问题)
G1(JDK9+ 默认) Region 分区、可预测停顿目标 短 STW,大部分并发 大堆通用
ZGC 染色指针 + 读屏障 停顿 <1ms,与堆大小无关 超大堆、低延迟
Shenandoah 并发压缩 停顿极短 低延迟

权衡的核心是吞吐量 vs 延迟:Parallel 追求单位时间处理最多工作(适合后台批处理);ZGC/Shenandoah 牺牲一点吞吐换取几乎无感的停顿(适合交互/在线服务)。没有”最好”,只有”最匹配场景”。

选择:-XX:+UseG1GC、-XX:+UseZGC、-XX:+UseParallelGC。

三个容易混淆的术语

  • 吞吐量(Throughput) = 用户代码运行时间 / (用户代码运行时间 + GC 时间)——衡量单位时间内”干正事”的比例,Parallel 系列收集器直接以此为优化目标。
  • 并发(Concurrent) = GC 线程与用户线程同时运行,互不阻塞——CMS/G1/ZGC 的标记阶段大多是并发的。
  • 并行(Parallel) = 多条 GC 线程同时工作,但用户线程仍处于 STW 暂停——Parallel、ParNew 都是”多线程并行,但用户线程等着”。三者并不互斥:G1 的一次回收里,某些阶段并行执行(多条 GC 线程一起标记),某些阶段又是并发执行(与用户线程同时跑)。

表里没列出的 ParNew:是 Serial 的多线程版本(同样是复制算法),它存在的唯一理由是它是当年唯一能与 CMS 配合工作的新生代收集器——CMS 只负责老年代,新生代仍需要单独选一个收集器搭配,ParNew 就是为了配合 CMS 而生的”新生代搭子”。现在 CMS 已在 JDK14 移除,ParNew 也随之失去了存在的意义。

CMS 的四个阶段,能看出”低停顿”具体是怎么换来的:初始标记(STW,只标记与 GC Roots 直接关联的对象,速度快)→ 并发标记(与用户线程一起跑,标记所有可达对象,耗时最长但不停顿)→ 重新标记(STW,修正并发标记期间因用户线程继续跑而产生的变动,通常比初始标记稍长)→ 并发清除(与用户线程一起跑,清理未标记对象)。两次 STW 都被压缩到”只做增量修正”的小范围,大头的标记、清除都放到并发阶段——这是它作为”低停顿先驱”的核心思路,代价是标记-清除算法带来的碎片,以及老年代空间在并发清理过程中被用户线程写满导致的 Concurrent Mode Failure(此时会退化成一次 Serial Old 的完整 STW 回收,停顿反而比不用 CMS 更长)。

G1 的四个阶段与 CMS 结构相似但多了一步:初始标记(STW)→ 并发标记(与用户线程并发)→ 最终标记(STW,处理并发标记期间的引用变动)→ 筛选回收(STW,但因为堆被划成了大量 Region,G1 会挑”回收收益最高”的一批 Region 优先处理,配合复制算法顺带完成整理,避免了 CMS 的碎片问题)。G1 相对 CMS 最本质的区别就是Region 化的堆布局:不再是连续的新生代/老年代,而是切成大量固定大小的小块,每块可以独立扮演 Eden/Survivor/老年代的角色,GC 时按每个 Region 的”垃圾占比/回收耗时”算一笔性价比账,优先回收最划算的那些——这让”停顿时间”从”整个老年代多大就要停多久”变成了一个可以通过 -XX:MaxGCPauseMillis 软性控制的目标。

JDK 默认收集器的演进,能看出社区对”延迟优先于吞吐”这件事态度的变化:JDK8 默认是 Parallel Scavenge(新生代)+ Parallel Old(老年代)组合,以吞吐量优先;JDK9 起默认改为 G1;ZGC/Shenandoah 转正后仍需要显式指定才会启用,还没有成为任何 LTS 版本的默认值。

十一、finalize 弃用与 Cleaner

释放资源永远优先用你已经会的 try-with-resources/显式 close()——它是确定性的,用完立刻执行。Cleaner 只是”万一你忘了调用 close()“的兜底网,不该当成主要手段:

import java.lang.ref.Cleaner;

public class QuickCleaner implements AutoCloseable {
    private static final Cleaner CLEANER = Cleaner.create();
    private final Cleaner.Cleanable cleanable;

    QuickCleaner() {
        // 注册一个"忘记 close 时的兜底清理动作"
        cleanable = CLEANER.register(this, () -> System.out.println("兜底清理被触发"));
    }

    @Override
    public void close() {
        System.out.println("显式 close() 被调用"); // 首选路径:确定性、立即执行
        cleanable.clean();                          // 手动触发清理,之后兜底动作不会再重复执行
    }

    public static void main(String[] args) {
        try (QuickCleaner r = new QuickCleaner()) {
            System.out.println("使用资源");
        }
        // 因为 try-with-resources 已经调用了 close(),兜底的 Cleaner 动作只打印一次
    }
}
// 使用资源
// 显式 close() 被调用
// 兜底清理被触发

close() 里主动调用 cleanable.clean(),清理动作立刻执行一次;如果你忘了写 try-with-resources、这个对象最终变得不可达,GC 之后 Cleaner 内部的后台线程也会自动跑一次同样的动作——但那是”最后一道保险”,不该是你依赖的主路径。

C++ 的析构函数确定性执行。Java 的 Object.finalize() 曾想扮演这个角色,但它执行时机不确定、可能永不执行、拖慢 GC、还能复活对象,已在 JDK9 标记 @Deprecated,JDK18 起进一步废弃。

替代方案:java.lang.ref.Cleaner,注册一个清理动作,当对象变得幻象可达时由后台线程执行。但它仍非确定性——关键资源永远用 try-with-resources 显式释放,Cleaner 只作最后兜底。

import java.lang.ref.Cleaner;
public class CleanerDemo implements AutoCloseable {
    private static final Cleaner CLEANER = Cleaner.create();
    // 清理动作必须是静态/独立类,绝不能持有外层对象引用,否则对象永不可回收
    static class State implements Runnable {
        public void run() { System.out.println("释放本地资源(兜底)"); }
    }
    private final Cleaner.Cleanable cleanable;
    CleanerDemo() { cleanable = CLEANER.register(this, new State()); }
    @Override public void close() { cleanable.clean(); } // 显式路径:确定性释放
}

十二、引用强度:强/软/弱/虚

平时写的 Object o = new Object() 都是强引用——只要它可达,GC 绝不会碰它。如果你想要”这个对象我还想用,但内存紧张时可以先牺牲它”这种效果,把它包一层 WeakReference:

import java.lang.ref.WeakReference;

public class QuickWeakRef {
    public static void main(String[] args) {
        Object obj = new Object();
        WeakReference<Object> weak = new WeakReference<>(obj); // 包一层弱引用
        System.out.println("get() 之前: " + (weak.get() != null)); // true —— 还有强引用 obj

        obj = null;      // 去掉唯一的强引用
        System.gc();      // 建议 JVM 做一次垃圾回收(不保证立即执行)
        System.out.println("get() 之后: " + weak.get()); // 很可能是 null
    }
}
// get() 之前: true
// get() 之后: null

weak.get() 拿到的是被引用的对象,或者 null(已被回收)。只要 obj 这个强引用还在,weak.get() 就一直有效;把 obj 置空、并且再没有别的强引用指着它之后,GC 就有权回收它,weak.get() 随之变成 null。

java.lang.ref 提供四种引用强度,决定对象在 GC 眼中的”生存权”:

强度 类 GC 行为 典型用途
强引用 普通 Object o = ... 可达就绝不回收 默认
软引用 SoftReference 内存不足时才回收 内存敏感缓存
弱引用 WeakReference 下次 GC 即回收 WeakHashMap、规范化映射
虚引用 PhantomReference 永远取不到对象,仅作回收通知 替代 finalize 做清理

软引用:内存敏感的缓存

软引用的语义是”内存不紧张就留着,紧张了就先牺牲它”——这天然适合做缓存:缓存命中能提升性能,但缓存本身不是不能丢的东西,内存告急时应该优先让路给业务逻辑,而不是把 OOM 留给用户。下面这个例子先确认内存充足时软引用活得好好的,再故意撑爆堆逼近 OOM,观察软引用先于 OutOfMemoryError 被清空:

import java.lang.ref.SoftReference;
import java.util.ArrayList;
import java.util.List;

public class SoftCache {
    public static void main(String[] args) {
        SoftReference<byte[]> cache = new SoftReference<>(new byte[1024 * 1024]); // 模拟1MB缓存数据
        System.out.println("刚创建: " + (cache.get() != null));

        System.gc(); // 内存充足时的常规 GC 几乎不会动软引用
        System.out.println("正常 GC 后(内存充足): " + (cache.get() != null));

        try {
            List<byte[]> hog = new ArrayList<>();
            while (true) hog.add(new byte[4 * 1024 * 1024]); // 疯狂吃内存,逼近 OOM
        } catch (OutOfMemoryError e) {
            System.out.println("触发 OOM 时软引用已被回收: " + (cache.get() == null));
        }
    }
}
// 用 java -Xmx64m SoftCache 运行:
// 刚创建: true
// 正常 GC 后(内存充足): true
// 触发 OOM 时软引用已被回收: true

JVM 保证:在抛出 OutOfMemoryError 之前,一定会先清空所有软引用再重试分配——这是软引用”内存不足时才回收”里”不足”的准确含义:不是某个百分比阈值,而是”已经到了不清掉你就要 OOM”的最后关头。所以软引用缓存永远不会导致 OOM(它会在 OOM 前被牺牲掉),但也意味着一旦被回收,缓存是整体清空,不是按 LRU 之类的策略挑着清——如果需要更精细的淘汰策略,应该用 Guava Cache/Caffeine 这类显式管理容量的缓存,而不是依赖软引用。

import java.lang.ref.*;
public class Refs {
    public static void main(String[] args) {
        ReferenceQueue<byte[]> queue = new ReferenceQueue<>();
        byte[] data = new byte[1024];
        // 弱引用 + 引用队列:对象被回收后,ref 会被入队,可据此感知回收
        WeakReference<byte[]> weak = new WeakReference<>(data, queue);
        data = null;          // 去掉唯一强引用
        System.gc();          // 建议 GC(不保证立即执行)
        System.out.println("回收后 get(): " + weak.get()); // 很可能是 null
        Reference<?> polled = queue.poll();                 // 已回收的引用被入队
        System.out.println("入队: " + (polled == weak));
    }
}

ReferenceQueue 是配套机制:当被引用对象被回收,对应的 Reference 对象被 JVM 放入队列,你的清理线程 poll 到后执行善后(Cleaner 内部正是这么实现的)。

虚引用:只用来”感知”回收,拿不到对象本体

弱引用/软引用的 get() 好歹还能在对象没被回收前拿到实例;虚引用从创建那一刻起 get() 就永远返回 null——它唯一的作用是在关联对象被判定可回收后,把自己放进 ReferenceQueue,让你的代码”事后”知道”这个对象已经没了”,从而触发一次清理动作,这才是”虚引用”这个名字的含义:

import java.lang.ref.PhantomReference;
import java.lang.ref.ReferenceQueue;

public class PhantomDemo {
    public static void main(String[] args) throws InterruptedException {
        ReferenceQueue<Object> queue = new ReferenceQueue<>();
        Object target = new Object();
        PhantomReference<Object> phantom = new PhantomReference<>(target, queue);

        System.out.println("phantom.get() 永远是 null: " + (phantom.get() == null));

        target = null;             // 去掉唯一强引用
        System.gc();
        Thread.sleep(200);         // 给 Reference Handler 线程一点时间入队

        System.out.println("对象被回收后虚引用已入队: " + (queue.poll() == phantom));
    }
}
// phantom.get() 永远是 null: true
// 对象被回收后虚引用已入队: true

典型用途是清理堆外资源:DirectByteBuffer 背后的堆外内存不受 GC 直接管理,JDK 内部用类似虚引用的机制在 Java 对象本体被回收的同时,顺带触发堆外内存的释放——虚引用负责”知道该清理了”,真正的清理动作(调用 native 方法释放内存)由你注册的清理逻辑完成,这正是前面「finalize 弃用与 Cleaner」一节里 cleanable.clean() 兜底路径的底层原理。

弱引用最常见的落地是 WeakHashMap:key 只被弱引用持有,一旦外部再无强引用,GC 后条目自动消失——天然适合做规范化缓存,避免”只加不删”的泄漏:

import java.util.*;
public class WeakMap {
    static void seed(Map<Object,String> m) {          // key 只存活在这个栈帧里
        m.put(new Object(), "v");
        m.put(new Object(), "v");
    }
    public static void main(String[] args) throws Exception {
        Map<Object,String> weak = new WeakHashMap<>();
        seed(weak);
        System.out.println("before GC  weak.size = " + weak.size());
        System.gc();
        Thread.sleep(100);
        System.out.println("after  GC  weak.size = " + weak.size());
    }
}
// before GC  weak.size = 2
// after  GC  weak.size = 0    <- key 无强引用,GC 回收后条目被清除
// (注意:若把 key 留在 main 的局部变量里,它会成为 GC Root 而不被回收)

十三、Java 里内存泄漏长什么样

有 GC 不代表没内存泄漏。泄漏 = 对象逻辑上没用了,但仍从 GC Roots 可达,GC 因而不回收。常见形态:

  • 长生命周期集合只加不删:static Map/缓存不断 put,键值永远可达。用 WeakHashMap 或设容量上限(如 Guava/Caffeine 缓存)。
  • 监听器/回调未注销:观察者注册后忘记 removeListener,被主题对象一直引用。
  • ThreadLocal 未 remove:线程池线程长期存活,ThreadLocal 的 value 随线程一直可达。用完必须 remove()。
  • 内部类隐式持有外部实例:非静态内部类/匿名类持有 Outer.this,若其生命周期比外部对象长,外部对象无法回收(Cleaner 那节的告诫同源)。

为什么弱引用没能彻底防住 ThreadLocal 泄漏

ThreadLocal 的值实际存在每个线程自带的 ThreadLocalMap 里,这个 Map 的 Entry 设计得很巧:Entry extends WeakReference<ThreadLocal<?>>——key(ThreadLocal 实例本身)是弱引用,value(你塞进去的业务对象)是强引用。这样设计的意图很明确:如果外部已经没有任何强引用指向这个 ThreadLocal 对象了(比如它是某个方法的局部变量,方法已经返回),GC 就能把 key 回收掉,不会因为”线程还活着”就让这个 ThreadLocal 对象也跟着永远不能回收——这正是上一节「引用强度」里弱引用”下次 GC 即回收”这个特性的一次典型工程应用。下面用一个简化版复现这个结构:

import java.lang.ref.WeakReference;

public class ThreadLocalPattern {
    static class Entry extends WeakReference<Object> { // 模拟 Entry extends WeakReference<ThreadLocal<?>>
        Object value; // 强引用,不会因为 key 被回收而自动清空
        Entry(Object key, Object value) { super(key); this.value = value; }
    }
    public static void main(String[] args) {
        Object threadLocalKey = new Object();      // 模拟一个 ThreadLocal 实例
        byte[] bigValue = new byte[1024 * 1024];   // 模拟塞进去的 1MB 业务对象
        Entry entry = new Entry(threadLocalKey, bigValue);

        threadLocalKey = null;  // 用户忘了持有 ThreadLocal 引用
        System.gc();

        System.out.println("key 被回收了吗: " + (entry.get() == null));
        System.out.println("value 还在吗: " + (entry.value != null));
    }
}
// key 被回收了吗: true
// value 还在吗: true

问题恰恰出在这里:key 没了强引用会被 GC 清掉,但 value 依然被 Entry 强引用着——只要这个 Entry 还挂在线程的 ThreadLocalMap 数组里,value 就一直占着内存。而 ThreadLocalMap 只有在下一次这个线程自己调用 ThreadLocal 的 get()/set()/remove() 时,才会顺便清理掉那些 key 已经是 null 的”stale entry”——如果线程是线程池里的长期存活线程,恰好又不再访问这个 ThreadLocal,这次清理可能永远不会自然发生。这就是弱引用设计”防住了一半”的真实含义:它防住了”ThreadLocal 对象本身”的泄漏,但防不住”塞进去的 value”的泄漏——后者仍然需要你在用完之后显式调用 remove(),这是它和软/弱/虚引用自动化回收最大的不同:自动化机制只覆盖了 key,value 的生命周期必须靠你自己管。

十四、常见 OOM 与调优参数

OutOfMemoryError 是 Error,细分为不同信息:

错误信息 含义 方向
Java heap space 堆放不下 增大 -Xmx 或查泄漏(堆转储分析)
GC overhead limit exceeded 花 98%+ 时间 GC 却回收很少 通常是泄漏或堆太小
Metaspace 类元数据超限(动态生成大量类) -XX:MaxMetaspaceSize,查类加载器泄漏
unable to create new native thread 线程数超系统/内存限制 减少线程、调 -Xss
Direct buffer memory 堆外直接内存耗尽 -XX:MaxDirectMemorySize

常用参数:

-Xms512m -Xmx4g                  # 初始/最大堆(生产建议两者相等,避免动态扩容抖动)
-Xss1m                           # 每线程栈大小
-XX:MaxMetaspaceSize=256m        # 元空间上限
-XX:+UseG1GC -XX:MaxGCPauseMillis=200  # 用 G1 并设停顿目标
-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/tmp/dump.hprof  # OOM 时导出堆快照
-Xlog:gc*                        # 打印 GC 日志(JDK9+ 统一日志),用于分析

诊断流程:-Xlog:gc* 看 GC 频率与停顿 → OOM 时拿 .hprof → 用 MAT/VisualVM 分析支配树(dominator tree)找出谁在撑着大对象不放。

小结

  • 用法层面:try/catch 按类型接住异常,finally 保证总执行;try-with-resources 让实现了 AutoCloseable 的资源用完自动 close();catch (A | B e) 一次接住多种类型;受检异常必须在方法签名写 throws 或就地捕获,非受检异常没有这个约束;GC 自动运行不用你操心,但 WeakReference/SoftReference/Cleaner 是你能主动用的几个相关 API,资源释放仍优先用显式 close(),Cleaner 只当兜底。
  • 底层层面:异常靠方法自带的异常表定位处理器,找不到就逐帧栈展开;finally 靠编译期代码复制实现”必然执行”;try-with-resources 按声明逆序调用 close(),close() 抛出的异常会作为 suppressed 挂在主异常上;异常链靠 cause 保留根因。Error 纳入统一的 Throwable 体系是为了让系统级故障也能走同一套可诊断的栈轨迹;受检/非受检的区分是编译期 fail-fast 与运行期发现两种哲学的取舍,底层 API 的受检异常常被包装成非受检异常向外抛、并用 cause 保留根因。IO 流按字节/字符分两套类型体系是为了让”处理文本”与”处理二进制”各自类型安全,处理流通过装饰器模式在节点流外层叠加缓冲/编码等能力。GC 不用引用计数(处理不了循环引用),靠可达性分析从 GC Roots 出发判活;堆按弱分代假设分 Eden/Survivor/老年代,新生代用复制算法、老年代用标记-清除/标记-整理,分代收集本质是”每个区选最适合它的算法”这个策略;Minor/Major/Full GC 回收范围递增;收集器从 Serial 到 G1/ZGC 的演进史就是压缩 STW 停顿的历史,G1 靠 Region 化堆布局把停顿时间变成可调目标,CMS 的四阶段并发标记-清除是这条路上的先驱但有碎片和 Concurrent Mode Failure 的代价;finalize 已弃用,Cleaner + PhantomReference/ReferenceQueue 是它的替代机制;软引用在 OOM 前才被清空、适合内存敏感缓存,弱引用下次 GC 即回收、ThreadLocalMap.Entry 用它做 key 正是为了不让 ThreadLocal 对象本身泄漏,但 value 仍需显式 remove();内存泄漏在 Java 里表现为”逻辑上没用但仍可达”。掌握这些,你就能像管理 C++ 内存那样,自信地驾驭 JVM 的堆。
