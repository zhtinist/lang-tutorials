运行模型：javac、字节码、JVM 与 JIT

C/C++ 的编译链路是单段式的：gcc/clang 把 .c 源码直接编成目标 CPU 架构的机器码，链接后得到一个绑定特定 OS/架构的可执行文件。Java 是两段式的：javac 先把源码编译成平台无关的中间表示（字节码），再由 JVM 在目标机器上把字节码变成实际执行的指令。本章讲清这条链路的每一环，以及为什么要多插入字节码这一层——这是理解后续内存模型、调用栈、并发一切内容的地基。

一、编译与运行的最小流程

Java 程序的最小骨架：一个 class，里面一个 main 方法，程序从 main 开始跑。

// Hello.java
public class Hello {
    public static void main(String[] args) {
        System.out.println("Hello, Java");
    }
}

几条直接能上手的规则：

  • 文件名必须和 public class 的名字完全一致：这个类叫 Hello，文件就必须叫 Hello.java。
  • 编译：javac Hello.java —— 产出一个 Hello.class 文件。
  • 运行：java Hello —— 注意是类名 Hello，不带 .class 后缀，也不是文件名。
javac Hello.java
java Hello

输出：

Hello, Java

再写一个带变量和运算的，巩固”编译 → 运行”这套流程：

// Add.java
public class Add {
    public static void main(String[] args) {
        int a = 3;
        int b = 4;
        int sum = a + b;
        System.out.println(sum);
    }
}
javac Add.java
java Add

输出：

7

javac 编译、java 运行，IDE 也只是替你自动执行这两步。这两步背后是什么,是本章要拆开讲的内容。

二、从源码到字节码：javac 产出什么

// Hello.java
public class Hello {
    public static void main(String[] args) {
        int sum = 0;
        for (int i = 0; i < 10; i++) {
            sum += i;
        }
        System.out.println(sum);
    }
}

编译：

javac Hello.java     # 产出 Hello.class

javac 与 gcc 的本质区别：gcc 的输出面向真实 CPU，指令集是 x86-64 / ARM64；javac 的输出面向一台假想的栈式虚拟机，指令集就是”字节码”（bytecode）。字节码不假设寄存器数量、不假设字长、不假设字节序——它只面向 JVM 规范定义的抽象机器。这就是”一次编写，到处运行”的技术根基：.class 文件在 Windows/Linux/macOS、x86/ARM 上是逐字节相同的。

.class 文件是一个有严格格式的二进制容器（魔数 0xCAFEBABE 开头），里面包含：

区段 内容 C/C++ 类比
常量池 constant pool 字符串、类名、方法名、字面量的符号引用 类似 .rodata + 符号表，但更结构化
字段表 类的字段声明 struct 成员布局信息
方法表 每个方法的字节码 + 元数据 函数体，但带完整类型签名
属性表 行号表、局部变量表、注解等 调试信息（类似 DWARF），但内置

为什么要多插入字节码这一层，而不是像 gcc 一样直接编译到机器码：这是”可移植性”与”极致性能”之间一次明确的取舍。直接编译到机器码（AOT，Ahead-Of-Time）能让编译器在编译期看到完整的目标 CPU 特性，做深入的静态优化，程序启动即以峰值速度运行，但产物与目标 CPU 架构、操作系统、ABI 强绑定——挪到另一种 CPU 就要重新编译，这是 C/C++ “一次编写，各平台分别编译”模型的代价。Java 把”翻译成具体机器指令”这一步推迟到运行时，编译器只需要面向一台抽象的栈式虚拟机，产出的 .class 文件在任何装了 JVM 的机器上逐字节相同，换来”一次编写，到处运行”；代价是运行时必须多做一轮翻译（解释或 JIT 编译），程序启动阶段无法立刻达到原生代码的速度。第三节的 JIT 和第五节的 GraalVM AOT 会看到这套取舍具体如何被弥补或反向选择。

关键点：.class 保留了完整的类型与符号信息。C 程序 strip 之后几乎只剩机器码，符号丢失；而 .class 天然携带类名、方法签名、字段类型——这是反射、动态加载、运行时类型检查得以存在的物质基础。

下面这段代码就靠这些留存的信息，在运行时读出方法的精确签名——这在 strip 过的 C 二进制上是做不到的：

import java.lang.reflect.Method;

Class<?> c = java.util.ArrayList.class;
System.out.println("class = " + c.getName());
Method m = c.getMethod("add", Object.class);
System.out.println("method = " + m.getName());
System.out.println("returns = " + m.getReturnType().getName());
System.out.println("params = " + m.getParameterCount());
// 输出：
// class = java.util.ArrayList
// method = add
// returns = boolean
// params = 1

用 javap 看字节码

javap 是 JDK 自带的反汇编器，相当于 Java 世界的 objdump -d：

javap -c Hello.class

main 方法的字节码大致如下（注释我加的）：

0:  iconst_0        // 把常量 0 压入操作数栈
1:  istore_1        // 弹出栈顶存入局部变量表 slot 1（即 sum）
2:  iconst_0        // 常量 0 入栈
3:  istore_2        // 存入 slot 2（即 i）
4:  iload_2         // 加载 i 入栈
5:  bipush 10       // 常量 10 入栈
7:  if_icmpge 20    // 若 i >= 10 跳到偏移 20（退出循环）
10: iload_1         // 加载 sum
11: iload_2         // 加载 i
12: iadd            // 栈顶两值相加，结果留在栈上
13: istore_1        // 存回 sum
14: iinc 2, 1       // 直接对 slot 2（i）自增 1，不经过操作数栈
17: goto 4          // 回到循环判断
20: getstatic ...   // 取 System.out
23: iload_1
24: invokevirtual println
27: return

注意 iconst/istore/iload/iadd 这些指令没有寄存器操作数。JVM 是栈式机器：运算的输入输出都在”操作数栈”上流转，而不是像 x86 那样 add eax, ebx 指名寄存器。i 前缀表示操作 int 类型，还有 l(long)、f(float)、d(double)、a(引用 address)。iinc 是少见的能直接改局部变量表的指令。

每个方法在字节码里都声明了它需要多大的操作数栈（stack=）和多少个局部变量 slot（locals=）。这些是编译期就算好的固定值，JVM 据此分配栈帧——见「函数与调用栈」。

三、类加载：把 .class 装进 JVM

C 程序启动时，加载器（loader）把 ELF 段映射进内存，重定位、绑定动态库符号，一次性搞定。Java 的类加载是惰性的、按需的、运行期的，分三个阶段。

为什么类加载要设计成懒加载：一个典型 Java 程序在编译期依赖成百上千个类（JDK 核心类库 + 第三方库），如果启动时像 C 静态链接那样把全部依赖一次性加载解析完毕，启动时间会随依赖图规模线性增长，而其中大多数类在这次运行里根本用不到（一个分支从未走到的异常处理类、一个从未触发的功能模块）。懒加载把加载/链接/初始化的开销分摊到”第一次真正用到该类”的那一刻，未被触碰的类完全零开销，这是”启动快”这一目标下的直接工程选择。它还有一个次生好处：类可以来自还不存在的地方（网络、动态生成的字节码、插件在运行时才提供的实现），只要在真正使用前能找到字节流即可——这在”必须在链接期见到全部符号”的静态链接模型下是做不到的。

1. 加载 Loading

根据类的全限定名找到 .class 字节流（从文件系统、jar、网络、甚至运行时生成），解析成方法区/元空间里的一个内部数据结构，并在堆上创建一个代表该类的 java.lang.Class 对象。这一步类似 dlopen 打开一个库，但粒度是单个类。

2. 链接 Linking（三小步）

  • 验证 Verification：检查字节码是否合法、类型是否安全、栈是否会溢出/下溢。C/C++ 没有对应物——它信任编译器产出的机器码；JVM 因为可能加载来路不明的字节码，必须做这层安全校验。
  • 准备 Preparation：为静态字段分配空间并置零值（int→0，引用→null）。注意此时不执行用户赋值。
  • 解析 Resolution：把常量池里的符号引用（“类 A 的方法 foo”）替换为直接引用（内存地址/偏移）。这相当于 C 的链接期符号解析，但发生在运行时，且可以延迟到第一次使用时才做。

3. 初始化 Initialization

执行静态初始化块和静态字段的赋值（即 <clinit> 方法）。触发时机：首次 new、访问静态字段/方法、反射等。JVM 保证 <clinit> 在多线程下只执行一次（带锁），这也是”静态单例 + 类加载”惯用法线程安全的原因。

下面这段代码验证了”惰性 + 只一次”：Config 的静态初始化直到第一次主动使用才发生，且再次访问不会重复执行：

static class Config {
    static { System.out.println("  [Config <clinit> runs]"); }
    static final int READY = compute();
    static int compute() { System.out.println("  [compute() runs]"); return 42; }
}
public static void main(String[] a) {
    System.out.println("main start");
    System.out.println("before touching Config");
    int v = Config.READY;   // 第一次主动使用 -> 触发 <clinit>
    System.out.println("Config.READY = " + v);
    int v2 = Config.READY;  // 再次访问 -> <clinit> 不会重复执行
    System.out.println("Config.READY = " + v2);
}
// 输出：
// main start
// before touching Config
//   [Config <clinit> runs]
//   [compute() runs]
// Config.READY = 42
// Config.READY = 42

注意 [Config <clinit> runs] 出现在 before touching Config 之后——类加载确实推迟到了用到它的那一刻。

完整生命周期:触发初始化的场景与类的卸载

上面演示的是”首次主动使用”触发 <clinit>，完整列出来 JVM 规范定义的主动使用场景其实有好几种：虚拟机启动时初始化含 main 方法的主类；首次 new 一个类的实例；首次访问某个类的静态字段或调用静态方法（不包括编译期就能确定的 final 常量——它在编译期就被直接内联进了调用方的常量池，不会触发被引用类的初始化）；首次通过反射（Class.forName 默认参数即触发）访问某个类；初始化一个类时，如果它的父类还没初始化，先递归初始化父类。除此之外的”被动引用”（比如通过子类引用父类的静态字段、定义数组但不实例化、引用上面说的编译期常量）都不会触发初始化——这是”懒加载”原则贯彻到底的体现，也是”类加载惰性”这一设计目标在细节上的具体落地。

链接阶段的准备（Preparation）也有一个例外需要注意：普通静态字段在这一步只拿到零值，但被 static final 修饰、且值在编译期就能确定的常量，会在编译时直接被内联进引用它的类自己的常量池，准备阶段根本不会为它单独分配内存、也不需要等目标类初始化完成——这正是”一个类的 static final int 常量值被修改后，没重新编译的调用方代码仍然用旧值”这个经典陷阱的成因：调用方拿到的从来就不是”运行时读一次”的值，而是编译期就已经拷贝进自己常量池的字面量。

类同样会被卸载：当同时满足三个条件——该类的所有实例都已被回收、加载它的类加载器本身已被回收、且它的 java.lang.Class 对象在任何地方都没有引用（无法再通过反射访问）——方法区里的类元数据才会被 GC 回收。Bootstrap ClassLoader 加载的核心类实际上永远不会被卸载，因为 Bootstrap ClassLoader 本身的生命周期等同于整个 JVM 进程；能被卸载的通常只是自定义类加载器加载的类（常见于容器/插件热部署场景，卸载失败正是”类加载器泄漏”的根源）。注意类的卸载回收的是方法区里的元数据，与堆里对象实例的垃圾回收是两回事——一个类被卸载不代表它曾经创建过的所有实例都跟着消失，那些实例仍由堆的可达性分析单独判断（见「错误处理与资源管理」）。

双亲委派模型 Parent Delegation

JVM 里有多个类加载器，形成层级：

        Bootstrap ClassLoader   (C++ 实现，加载 java.* 核心类)
              ▲  委派
        Platform ClassLoader    (JDK 平台模块)
              ▲  委派
        Application ClassLoader (你的 classpath)
              ▲  委派
        自定义 ClassLoader

加载一个类时，子加载器先向上委派给父加载器尝试，父加载不了才自己加载。好处：核心类（如 java.lang.String）永远由 Bootstrap 加载，你没法用一个伪造的 java.lang.String 顶替系统类——这是一种安全与一致性保证。C/C++ 里若两个 .so 各自带同名符号，行为取决于链接顺序，容易出问题；双亲委派从机制上避免了核心类被”劫持”。

类的唯一性：全限定名 + 类加载器

JVM 判断两个类”是不是同一个类”，不只看类名，而是全限定名 + 加载它的类加载器共同决定。哪怕字节码完全相同，只要被两个不同的类加载器分别 defineClass，JVM 就认为这是两个互不相干的类型——instanceof 判断为 false，互相强转会抛 ClassCastException。下面用两个自定义类加载器分别加载同一份 .class 字节码验证这一点（先单独编译一个最简单的 Sample.java 得到 Sample.class，再运行下面的加载器）：

// Sample.java —— 先 javac 编译好，下面的加载器直接读它的字节码
public class Sample {}
import java.io.*;
import java.nio.file.*;

// 自定义类加载器：重写 loadClass()（而不是通常建议的 findClass()），
// 对指定类名"跳过向上委派"，直接自己加载字节流——这是打破双亲委派最直接的手段。
class BreakingLoader extends ClassLoader {
    private final String targetClassName;
    BreakingLoader(String targetClassName) {
        super(null); // 不设 parent，模拟"完全不委派"的极端情形
        this.targetClassName = targetClassName;
    }
    @Override
    protected Class<?> loadClass(String name, boolean resolve) throws ClassNotFoundException {
        if (!name.equals(targetClassName)) {
            return ClassLoader.getSystemClassLoader().loadClass(name);
        }
        try {
            byte[] bytes = Files.readAllBytes(Paths.get("Sample.class"));
            Class<?> c = defineClass(name, bytes, 0, bytes.length);
            if (resolve) resolveClass(c);
            return c;
        } catch (IOException e) {
            throw new ClassNotFoundException(name, e);
        }
    }
}

public class BreakDelegation {
    public static void main(String[] args) throws Exception {
        BreakingLoader loader1 = new BreakingLoader("Sample");
        BreakingLoader loader2 = new BreakingLoader("Sample");
        Class<?> c1 = loader1.loadClass("Sample");
        Class<?> c2 = loader2.loadClass("Sample");

        System.out.println("c1 == c2 ? " + (c1 == c2));
        Object o1 = c1.getDeclaredConstructor().newInstance();
        Object o2 = c2.getDeclaredConstructor().newInstance();
        System.out.println("o1.getClass() == o2.getClass() ? " + (o1.getClass() == o2.getClass()));
    }
}
// c1 == c2 ? false
// o1.getClass() == o2.getClass() ? false
// （强行互相 cast 会抛 ClassCastException：Cannot cast Sample to Sample）

这不是 bug，是双亲委派要保护的核心性质本身：类加载器 + 全限定名共同构成类型的身份证。也正因为如此，双亲委派把”核心类库只能由 Bootstrap 加载”变成了一个可强制的约束——用户即便自定义了一个同名的 java.lang.String，双亲委派会先把加载请求委托给 Bootstrap，最终生效的还是 JDK 自带的那个；伪造版本就算真被加载出来，也和系统里其它地方用到的 String 不是同一个类型，互不兼容，自然起不到”顶替”的作用。

如何打破双亲委派

双亲委派不是语言强制的规则，而是 ClassLoader.loadClass() 默认实现里的一种约定——只要重写这个方法，就可以不走”先问父亲”这条路。三种常见方式：

  1. 自定义类加载器重写 loadClass()：上面的 demo 就是最直接的方式——不调用 super.loadClass()，自己决定要不要委派、从哪里读字节码。JDK 官方推荐的常规做法通常只重写 findClass()（父加载器失败后才会被调用），这样仍保留双亲委派”先问父亲”的顺序；像上面这样直接重写 loadClass() 本身，才是真正意义上的”打破”。

  2. SPI 机制 + 线程上下文类加载器：典型矛盾场景是 JDBC——java.sql.DriverManager 由 Bootstrap 加载，但具体的数据库驱动实现（比如 com.mysql.cj.jdbc.Driver）在应用的 classpath 下，由 Application ClassLoader 加载。按标准双亲委派，Bootstrap 加载的 DriverManager 没法反向委派给”儿子”Application ClassLoader 去加载驱动类。JDK 的解法是给每个线程挂一个线程上下文类加载器（Thread Context ClassLoader），默认就是 Application ClassLoader；DriverManager 内部通过 Thread.currentThread().getContextClassLoader() 拿到它，反向”借用”子加载器加载驱动——这是一种从顶层向下层反向查找的变通。java.util.ServiceLoader（Java SPI 机制的核心）用的也是同一套上下文类加载器，解决”接口定义在核心库、具体实现在应用层”的加载问题。

  3. Tomcat 的类加载器隔离：同一个 Tomcat 里部署多个 Web 应用，各自可能依赖同一个类库的不同版本。如果严格走双亲委派，所有类最终都会委派到同一个 Application ClassLoader，不同版本的同名类会互相冲突。Tomcat 的解法是给每个 Web 应用配一个独立的 WebappClassLoader，并且反转默认查找顺序：优先加载自己 WEB-INF/classes 和 WEB-INF/lib 下的类，找不到才向上委派给公共父加载器——这样每个应用的类互相隔离，同名不同版本的库可以在同一个 Tomcat 进程里共存。这是”打破双亲委派”在生产环境里最常见的落地案例。

四、执行：解释 + JIT 混合模式

拿到字节码后，JVM 怎么执行？两种手段并用（HotSpot 的默认”混合模式”）：

解释执行

JVM 内置一个字节码解释器，逐条读取字节码、查表、执行对应的 C++ 逻辑。启动快（不用等编译），但每条指令都有解释开销，比原生机器码慢一到两个数量级。

热点探测 + JIT 编译

HotSpot 这个名字就来自它的策略：探测热点代码（Hot Spot）。JVM 为每个方法维护计数器（方法调用次数 + 循环回边次数），一旦超过阈值，就认定它”热”，交给 JIT（Just-In-Time）编译器把这段字节码在运行时编译成本地机器码，之后直接执行机器码。

HotSpot 有两个 JIT 编译器（分层编译 Tiered Compilation 会协同使用）：

编译器 定位 特点
C1（Client） 快速编译 优化少，编译快，先顶上
C2（Server） 深度优化 激进优化，编译慢，用于最热的代码

典型路径：解释执行 → C1 编译（带性能计数）→ C2 重编译最热部分。

为什么需要 JIT，而不是纯解释或纯 AOT 二选一：三种方案各自卡在一个极端。纯解释器启动零延迟（不用等编译），但每条字节码都要经过”取指-查表-分派”的开销，长期运行的代码也一直慢；纯 AOT（如 gcc）能提前做深度优化，但编译期看不到运行时才知道的信息（这次运行里某个虚方法调用点实际上只被一个实现类命中、某个循环实际迭代了几十亿次值得激进展开），只能基于静态假设做保守优化。JIT 把两者的优点拼在一起：先用解释执行（或最快的 C1）立刻跑起来，避免启动等待；同时用计数器持续观察运行时行为,一旦某段代码被证实”热”，才投入编译期成本更高、优化更激进的 C2,用实际观测到的分支概率、类型信息做静态编译器不敢做的投机优化。分层编译（Tiered Compilation）正是”启动延迟”与”峰值吞吐”这对矛盾的调和方案：C1 编译快、优化保守，负责让代码尽早摆脱解释执行的慢速；C2 编译慢、优化激进，只对少数真正的热点方法投入，避免把编译时间浪费在只跑一次的代码上。赌错的投机优化可以去优化（deoptimization）退回解释执行重新收集信息，这是”运行时信息可能过时或不全”这一代价的兜底机制。

这就是 Java “越跑越快”、且有时能逼近甚至局部超过 C 的原因：JIT 掌握运行时信息——实际走哪个分支、某个虚方法实际只调用了一个实现类、某个循环边界是多少。它能据此做静态编译器做不到的投机优化（speculative optimization），赌错了再”去优化”（deoptimization）退回解释执行。而 gcc 编译时对运行时一无所知，只能保守。

几个关键 JIT 优化（对内存行为影响很大）

  • 方法内联 Inlining：把被调方法体直接嵌入调用处，消除调用开销，还打开了后续优化的视野。等价于 C 的 inline，但 JIT 是运行时基于热度自动决定的。
  • 逃逸分析 Escape Analysis：分析一个对象的引用是否”逃逸”出当前方法（是否被返回、被存入堆上其它对象、被其它线程看到）。若不逃逸，JVM 可以做：
    • 标量替换（Scalar Replacement）：把本该在堆上 new 的对象拆散成它的各个字段，当作普通局部变量直接放进栈帧 slot 甚至寄存器。注意这不是”把整个对象搬到栈上”，而是对象作为一个整体根本不再存在——因此既没有堆分配、也无需 GC 回收。（HotSpot 并没有真正的”整对象栈上分配”，能省掉堆分配的机制就是标量替换。）

这一点对你理解 Java 内存很重要：Java 语言层面”对象一律在堆上”，但 HotSpot 实现层面，逃逸分析可能让短命的、不逃逸的对象根本不进堆。这弥合了 Java 与 C（栈上放 struct）的部分性能差距。详见「变量与内存模型」。

五、运行时内存区域

一个运行中的 JVM 把内存划成几块（JVM 规范定义，HotSpot 实现）：

┌───────────────────────────────────────────────────────┐
│                         JVM 进程                         │
│                                                         │
│  所有线程共享 ↓                                          │
│  ┌─────────────────────┐   ┌───────────────────────┐   │
│  │        堆 Heap        │   │  方法区 / 元空间         │   │
│  │  所有对象、数组       │   │  类元数据、方法字节码    │   │
│  │  GC 主战场            │   │  运行时常量池           │   │
│  │  (new 出来的都在这)   │   │  (元空间在本地内存)      │   │
│  └─────────────────────┘   └───────────────────────┘   │
│                                                         │
│  每个线程私有 ↓                                          │
│  ┌───────────┐ ┌───────────┐ ┌──────────┐ ┌──────────┐ │
│  │ JVM 栈     │ │ PC 寄存器  │ │本地方法栈 │ │ ...      │ │
│  │ 一堆栈帧   │ │ 当前指令   │ │JNI 用     │ │每线程一份 │ │
│  └───────────┘ └───────────┘ └──────────┘ └──────────┘ │
└───────────────────────────────────────────────────────┘
区域 谁的 存什么 C/C++ 类比
堆 Heap 共享 所有对象、数组实例 malloc 的堆，但由 GC 自动回收
方法区/元空间 Metaspace 共享 类结构、方法字节码、运行时常量池、静态字段的元信息（字段的值存放在堆上的 Class 镜像对象里，不在元空间） 代码段 + 只读数据段（但可运行时增长）
JVM 栈 每线程 栈帧（局部变量表、操作数栈） 线程调用栈，逻辑一致
PC 寄存器 每线程 当前执行到的字节码地址 程序计数器 PC/RIP
本地方法栈 每线程 执行 native（JNI）方法时的栈 C 侧的原生栈

上表是运行时数据怎么摆放；调用这些 native 方法靠的是另外两个组件——本地方法接口（Native Method Interface，即 JNI）：当某个方法被 native 关键字标记，执行引擎不会去解释/编译它的字节码（它压根没有字节码体），而是通过 JNI 这层接口跳转到本地实现；本地方法库（Native Method Library）：存放这些 native 方法真正的实现（.so/.dll），比如 java.io.FileInputStream 的读文件操作、线程的创建与调度，最终都要通过本地方法库调用操作系统提供的系统调用完成——Java 语言本身不能直接碰触操作系统内核资源，这是它跨平台设计必然的代价，native 接口 + 本地方法库正是补上这块”必须和具体 OS 打交道”的缺口。至此，类加载器（本节”类加载”）、运行时数据区（上表）、执行引擎（解释器 + JIT，上一节）、本地方法接口、本地方法库——JVM 规范定义的五大组成部分，在本章里都各自有了对应的落地位置。

堆内部怎么切：TLAB、Survivor 比例、大对象、字符串常量池

上表把堆看作一整块”对象存放地”，实际实现里 HotSpot 对堆做了更细的切分，这些细节在「错误处理与资源管理」的 GC 章节会被反复用到，这里先建立静态认识：

  • 默认堆大小：不显式指定 -Xmx/-Xms 时，HotSpot 会按物理内存的比例给出默认值——初始堆大小约为物理内存的 1/64，最大堆大小约为物理内存的 1/4（具体比例随 JDK 版本和平台略有调整）。生产环境几乎总是显式设置这两个参数，不依赖默认值，原因见下一节。
  • TLAB（Thread Local Allocation Buffer）：Eden 区会划出一小部分（默认约占 Eden 的 1%），给每个线程私有独占的一小块”本地分配缓冲区”。新对象优先在自己线程的 TLAB 里通过指针碰撞分配，不需要加锁；只有 TLAB 用满了才去竞争整个 Eden 的分配锁。这是”多线程同时 new 对象”避免锁竞争的关键优化，也是”对象分配很快”这个印象背后的具体机制。
  • Eden : Survivor0 : Survivor1 默认比例是 8 : 1 : 1（-XX:SurvivorRatio=8）：这个比例基于”大多数对象活不过一次 Minor GC”的弱分代假设——留给存活对象的 Survivor 空间不需要很大，把更多空间留给 Eden 能让 Minor GC 触发得更少。
  • 大对象直接进老年代：超过 -XX:PretenureSizeThreshold 阈值的对象（典型场景是大数组），会跳过新生代，直接分配进老年代——避免大对象在 Eden/Survivor 之间来回复制的开销，也避免新生代因为塞不下大对象而被迫提前触发 Minor GC。
  • 字符串常量池（String Pool）：JDK7 起从永久代移入堆，用于存放 String.intern() 之后的字符串，保证内容相同的字符串字面量在池里只有一份拷贝，避免重复对象——"a" + "b" 这种编译期能确定的字面量拼接会自动进池，但 new String("ab") 不会。
  • 直接内存（Direct Memory）：ByteBuffer.allocateDirect() 分配的是堆外内存，不受 -Xmx 限制、不被 GC 直接管理，靠虚引用/Cleaner 机制在关联的 Java 对象被回收时顺带释放（「错误处理与资源管理」有虚引用的完整例子）。-XX:MaxDirectMemorySize 专门限制它的上限，和堆内存是两套独立的记账体系。

几点与 C 的对照： - 元空间在本地内存（native memory），不在 GC 堆里（这是 JDK8 起的设计，取代了旧的”永久代 PermGen”）。 - 堆的回收是自动的：没有 free/delete，GC 判定不可达就回收。你几乎从不手动管理堆生命周期——这是与 C 最大的心智差异，也是「错误处理与资源管理」里 try-with-resources 只针对”非内存资源”（文件/socket）的原因：内存交给 GC，句柄仍需显式关。 - 栈的语义几乎和 C 一样：每次方法调用压一个栈帧，返回时弹出；栈太深触发 StackOverflowError（对应 C 的栈溢出，但 JVM 会抛异常而非直接段错误）。

六、AOT：GraalVM native-image

Java 也能像 C 一样提前编译（Ahead-Of-Time）成原生可执行文件。GraalVM 的 native-image 在构建期做闭包分析，把用到的类、方法、乃至一个精简的运行时（含 GC）静态编译打包成一个独立可执行文件：

native-image Hello        # 产出一个原生可执行文件 hello
./hello                   # 无需 JVM，毫秒级启动

代价与取舍： - 优点：启动极快、内存占用小、无需分发 JVM——适合 CLI 工具、Serverless/函数计算冷启动。这时它和 C 的分发模型很像：一个原生二进制。 - 代价：构建期必须知道全部会用到的类，因此反射、动态代理、运行时生成类需要额外配置；失去了 JIT 的运行时投机优化，峰值吞吐可能不如长时间预热后的 C2。

所以对照记忆： - javac → 字节码，跨平台，靠 JVM + JIT 运行时优化（长跑服务的主流）。 - native-image → 原生码，绑定平台，构建期定死（快启动短命进程的选择）。 - gcc/clang → 原生码，绑定平台，编译期定死（C/C++ 的唯一路径）。

七、JVM 常见参数速查

上面几节分别解释了堆分代、元空间、类加载的原理，这里把对应的启动参数集中列一张速查表——java 命令后面这些 -X/-XX 前缀的参数，就是把前几节讲的”概念”变成”可调的旋钮”。

类别 参数 作用
堆内存 -Xms<size> 初始堆大小
堆内存 -Xmx<size> 最大堆大小（生产建议与 -Xms 设为相同值，避免运行时动态扩容触发额外停顿）
堆内存 -Xmn<size> 新生代大小（直接指定，优先级高于 -XX:NewRatio）
堆内存 -XX:NewRatio=<n> 老年代/新生代比例，默认 2（老年代占约 2/3）
堆内存 -XX:SurvivorRatio=<n> Eden/单个 Survivor 比例，默认 8
栈 -Xss<size> 每线程 JVM 栈大小，调小可以在总内存有限时开更多线程，调大是应对 StackOverflowError（深递归）的直接手段
方法区 -XX:MetaspaceSize=<size> 元空间触发 Full GC 的初始阈值（不是硬上限），用量超过它会先触发一次 GC 尝试回收类元数据，之后 JVM 按情况动态调大阈值
方法区 -XX:MaxMetaspaceSize=<size> 元空间硬上限，超过才真正 OOM；不设置默认几乎不受限（仅受本机内存约束）
方法区（已废弃） -XX:PermSize / -XX:MaxPermSize JDK7 及以前的永久代参数，JDK8 起永久代被元空间取代，这两个参数不再生效
GC 选择 -XX:+UseSerialGC / -XX:+UseParallelGC / -XX:+UseG1GC / -XX:+UseZGC 选择收集器，见「错误处理与资源管理·收集器演进」
GC 调优 -XX:MaxGCPauseMillis=<ms> G1/ZGC 的目标停顿时间（软目标，不是硬保证）
GC 调优 -XX:ParallelGCThreads=<n> 并行 GC 阶段的线程数，默认等于 CPU 核心数
GC 调优 -XX:MaxTenuringThreshold=<n> 对象在 Survivor 里熬过几次 Minor GC 才晋升老年代，默认 15
诊断 -Xlog:gc* 打印 GC 日志（JDK9+ 统一日志框架），调优第一步永远是先看日志
诊断 -verbose:class 打印类加载信息，排查”这个类到底是谁加载的”“为什么被加载了两次”这类双亲委派相关问题
诊断 -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=<path> OOM 时自动导出堆快照，配合 MAT/VisualVM 找内存泄漏

为什么 -Xms 和 -Xmx 生产环境要设成相等：堆从初始大小扩容到最大大小的过程，本身需要向操作系统申请新内存、重新计算分代边界，这个动作会触发一次额外停顿；如果堆大小在运行中反复震荡（先长大，GC 后又收缩），等于在正常的 GC 停顿之外又叠加了一层扩缩容开销。固定为同一个值，相当于启动时就把”以后要用的内存”一次性占住，用空间换稳定性——这也是为什么高并发、对延迟敏感的场景（比如秒杀），调优的第一步永远是先把 -Xms/-Xmx 锁死为同一个值，再谈其它参数；同理，-Xmn 通常会调大到 -Xms 的 1/2 到 2/3，因为这类场景会产生大量生命周期极短的临时对象，让它们尽量在新生代里用复制算法回收掉，避免过早晋升到老年代拖慢 Major GC。

-XX:MetaspaceSize 和 -Xmx 的区别值得单独强调：它不是”最大值”而是”第一次触发 Full GC 去回收类元数据的阈值”——元空间用量到达这个值，JVM 会先尝试一次 Full GC 卸载不再使用的类，回收不够再动态调大这个阈值，如此反复；真正的硬上限是 -XX:MaxMetaspaceSize。这也是”类加载了很多但没配 MaxMetaspaceSize“的服务在长期运行后本地内存被元空间无限吃掉的常见原因（典型场景：大量动态生成类的框架，字节码增强库不断产生新类而对应的类加载器又没有被回收，即前面提到的”类加载器泄漏”）。

小结

  • 流程：javac 文件名.java 编译（类名须与文件名一致）→ java 类名（不带后缀）运行；IDE 只是自动执行这两步。
  • javac 产出平台无关字节码而非机器码，代价是运行时需要 JVM 这台栈式虚拟机再翻译一遍，换来的是同一份 .class 到处运行；这是可移植性与 AOT 峰值性能之间的取舍。
  • 类加载是运行时、惰性、分层（双亲委派）的——懒加载把开销分摊到真正用到某个类的那一刻，避免为用不到的类付出启动成本；双亲委派保证核心类不会被伪造版本顶替，且类的唯一性由”全限定名 + 类加载器”共同决定。
  • 双亲委派可以被打破：自定义类加载器重写 loadClass()、SPI 机制借助线程上下文类加载器反向查找、Tomcat 给每个 Web 应用配独立 WebappClassLoader 并反转查找顺序，三种方式服务于三种不同的实际诉求。
  • HotSpot 先解释、探测热点后 JIT（C1 快编译顶上、C2 深度优化最热代码），分层编译正是”启动延迟”与”峰值吞吐”这对矛盾的调和；逃逸分析能对不逃逸对象做标量替换（拆成标量放栈帧/寄存器，而非整体栈上分配）。
  • 运行时内存分共享的堆/元空间与每线程的 JVM 栈/PC/本地栈；堆由 GC 自动回收；堆内部还有 TLAB、Survivor 8:1:1 比例、大对象直接进老年代、字符串常量池等更细的分区，都是弱分代假设的具体落地。
  • JVM 参数把”概念”变成”旋钮”：-Xms/-Xmx 生产建议锁死为同一个值避免动态扩容停顿，-XX:MetaspaceSize 是触发 Full GC 的阈值而非硬上限，二者的区别是排查内存问题时最容易搞混的一点。
  • 需要 C 式的快启动原生二进制时，用 GraalVM native-image 做 AOT，代价是牺牲运行时动态性与峰值优化。
