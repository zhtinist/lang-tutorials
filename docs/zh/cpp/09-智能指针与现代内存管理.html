智能指针与现代内存管理

本章覆盖现代 C++ 内存管理的核心知识点:三种智能指针(unique_ptr/shared_ptr/weak_ptr)的用法与适用场景、make_unique/make_shared、循环引用问题、自定义删除器、RAII 思想,以及 new/delete 与 malloc/free 的区别。现代 C++ 代码里几乎不应该出现裸 new/delete。

一、unique_ptr:独占所有权

std::unique_ptr 是最轻量的智能指针,同一时刻只能有一个 unique_ptr 拥有资源,不可拷贝、只能移动(所有权转移),没有引用计数开销,几乎等价于裸指针的性能。

#include <iostream>
#include <memory>

struct Widget {
    int id;
    Widget(int id) : id(id) { std::cout << "构造 Widget " << id << "\n"; }
    ~Widget() { std::cout << "析构 Widget " << id << "\n"; }
};

std::unique_ptr<Widget> makeWidget(int id) {
    return std::make_unique<Widget>(id);  // make_unique(C++14):异常安全,且比 new + 构造 unique_ptr 更简洁
}

int main() {
    auto w1 = makeWidget(1);
    std::cout << "w1->id=" << w1->id << "\n";

    auto w2 = std::move(w1);        // unique_ptr 不可拷贝,只能移动(所有权转移)
    std::cout << "w1 is " << (w1 ? "valid" : "null") << "\n"; // null,所有权已转移
    std::cout << "w2->id=" << w2->id << "\n";

    {
        auto w3 = std::make_unique<Widget>(3);
    } // 离开作用域,w3 自动析构 —— RAII
}
构造 Widget 1
w1->id=1
w1 is null
w2->id=1
构造 Widget 3
析构 Widget 3
析构 Widget 1

适用场景:资源只有唯一所有者的绝大多数情况——函数内创建、返回给调用者;类的成员,表示”我独占这个资源”;工厂函数的返回值。应作为默认首选的智能指针。

二、shared_ptr 与 weak_ptr:共享所有权

std::shared_ptr 通过引用计数支持多个所有者共享同一个对象,计数归零时自动释放。std::weak_ptr 不参与计数,只”观察”对象是否还存活,用来打破循环引用。

#include <iostream>
#include <memory>

struct Node {
    int id;
    Node(int id) : id(id) { std::cout << "构造 Node " << id << "\n"; }
    ~Node() { std::cout << "析构 Node " << id << "\n"; }
};

int main() {
    auto a = std::make_shared<Node>(1);   // make_shared:一次分配同时容纳对象和控制块,比 shared_ptr(new T) 更高效
    std::cout << "use_count(a)=" << a.use_count() << "\n"; // 1

    {
        auto b = a;                          // 拷贝 shared_ptr,引用计数 +1
        std::cout << "use_count(a)=" << a.use_count() << "\n"; // 2
    } // b 离开作用域,引用计数 -1

    std::cout << "use_count(a) after scope=" << a.use_count() << "\n"; // 1

    std::weak_ptr<Node> weakRef = a;   // weak_ptr 不增加引用计数,只是“观察”
    std::cout << "use_count via weak still=" << a.use_count() << "\n"; // 1

    if (auto locked = weakRef.lock()) { // lock() 尝试提升为 shared_ptr,对象存活则成功
        std::cout << "locked id=" << locked->id << "\n";
    }

    a.reset();                           // 显式释放
    std::cout << "expired=" << weakRef.expired() << "\n"; // 1(true),对象已销毁
}
构造 Node 1
use_count(a)=1
use_count(a)=2
use_count(a) after scope=1
use_count via weak still=1
locked id=1
析构 Node 1
expired=1

make_shared 比 std::shared_ptr<T>(new T(...)) 更推荐:后者要分配两次(对象一次、控制块一次),前者一次分配同时放下对象和控制块,更快且异常安全性更好。适用场景:多个地方需要共同拥有、生命周期不确定谁最后释放的资源(比如观察者模式里的观察者列表、图/树结构中共享的节点)。

三、循环引用问题与 weak_ptr 解决方案

如果两个对象互相持有对方的 shared_ptr,会形成引用环,双方引用计数永远不会归零,导致内存泄漏:

#include <iostream>
#include <memory>

struct Node {
    int id;
    std::shared_ptr<Node> next;   // 两边都用 shared_ptr 会形成循环引用
    Node(int id) : id(id) { std::cout << "构造 Node " << id << "\n"; }
    ~Node() { std::cout << "析构 Node " << id << "\n"; }
};

void demoLeak() {
    auto a = std::make_shared<Node>(1);
    auto b = std::make_shared<Node>(2);
    a->next = b;    // a 持有 b 的 shared_ptr
    b->next = a;      // b 也持有 a 的 shared_ptr —— 循环引用!
    std::cout << "use_count(a)=" << a.use_count() << " use_count(b)=" << b.use_count() << "\n"; // 都是 2
} // a, b 局部变量析构,但各自引用计数只减到 1(对方还拿着),对象永远不会被析构 —— 内存泄漏
构造 Node 1
构造 Node 2
use_count(a)=2 use_count(b)=2
(demoLeak 结束,但没有看到 Node 的析构输出 —— 说明发生了内存泄漏)

解决方案是把其中一个方向的引用(通常是”反向指针”、“父指针”这类逻辑上不应该拥有所有权的一边)改成 weak_ptr:

struct NodeFixed {
    int id;
    std::shared_ptr<NodeFixed> next;
    std::weak_ptr<NodeFixed> prev;    // 用 weak_ptr 打破环,不增加引用计数
    NodeFixed(int id) : id(id) { std::cout << "构造 NodeFixed " << id << "\n"; }
    ~NodeFixed() { std::cout << "析构 NodeFixed " << id << "\n"; }
};

void demoFixed() {
    auto a = std::make_shared<NodeFixed>(1);
    auto b = std::make_shared<NodeFixed>(2);
    a->next = b;
    b->prev = a;      // weak_ptr,不增加 a 的引用计数
    std::cout << "use_count(a)=" << a.use_count() << " use_count(b)=" << b.use_count() << "\n"; // a=1, b=2
} // 离开作用域后正常释放
构造 NodeFixed 1
构造 NodeFixed 2
use_count(a)=1 use_count(b)=2
析构 NodeFixed 1
析构 NodeFixed 2
(demoFixed 结束,两个 NodeFixed 都被正确析构)

判断原则:两个对象的”拥有”关系如果是双向的,至少要有一个方向不算作真正的所有权(只是引用/观察),就应该用 weak_ptr。典型场景:双向链表/树的父指针、观察者模式里被观察者持有观察者列表、缓存里指向”拥有者”的反向指针。

四、自定义删除器

智能指针默认用 delete/delete[] 释放资源,但很多资源(C API 返回的句柄、文件指针、系统对象)需要专门的释放函数,这时可以提供自定义删除器:

#include <iostream>
#include <memory>
#include <cstdio>

struct FileCloser {
    void operator()(FILE* f) const {
        if (f) {
            std::cout << "关闭文件\n";
            std::fclose(f);
        }
    }
};

int main() {
    // unique_ptr 的删除器类型是模板参数的一部分
    std::unique_ptr<FILE, FileCloser> file(std::fopen("/tmp/cpp_tutorial_test.txt", "w"));
    if (file) {
        std::fputs("hello\n", file.get());
    }
    // 离开作用域自动调用 FileCloser::operator(),而不是默认的 delete

    // shared_ptr 的删除器是运行期存储的(类型擦除),可以直接传 lambda
    std::shared_ptr<int> arr(new int[5], [](int* p) {
        std::cout << "自定义删除数组\n";
        delete[] p;
    });
}
自定义删除数组
关闭文件

unique_ptr<T, Deleter> 的删除器类型是模板参数,不同删除器 = 不同类型;shared_ptr<T> 的删除器在构造时传入、类型被擦除,同一个 shared_ptr<T> 类型可以持有带不同删除器的对象。

五、RAII 思想

RAII(Resource Acquisition Is Initialization,资源获取即初始化)是 C++ 资源管理的核心哲学:把资源的生命周期绑定到一个对象的生命周期上——构造函数里获取资源,析构函数里释放资源。由于 C++ 保证局部对象在离开作用域时(无论是正常返回还是异常导致的栈展开)一定会调用析构函数,资源就一定会被释放,不需要 try/finally 这类语法来保证清理。

#include <iostream>
#include <stdexcept>

class FileGuard {              // RAII:构造时获取资源,析构时自动释放,保证异常安全
public:
    FileGuard(const std::string& name) : name_(name) {
        std::cout << "打开资源: " << name_ << "\n";
    }
    ~FileGuard() {
        std::cout << "释放资源: " << name_ << "\n";
    }
private:
    std::string name_;
};

void mayThrow(bool doThrow) {
    FileGuard guard("data.txt");    // 资源获取即初始化
    if (doThrow) {
        throw std::runtime_error("出错了");
    }
    std::cout << "正常使用资源\n";
} // 无论正常返回还是异常抛出,guard 的析构函数都会被调用,资源不会泄漏

int main() {
    try {
        mayThrow(false);
        mayThrow(true);
    } catch (const std::exception& e) {
        std::cout << "捕获异常: " << e.what() << "\n";
    }
}
打开资源: data.txt
正常使用资源
释放资源: data.txt
打开资源: data.txt
释放资源: data.txt
捕获异常: 出错了

智能指针、std::lock_guard、标准库容器本身都是 RAII 的具体实现——这是理解”为什么现代 C++ 几乎不需要手写 try/finally 式清理代码”的关键。

六、new/delete 与 malloc/free 对比

#include <iostream>
#include <cstdlib>

struct Point {
    int x, y;
    Point() : x(0), y(0) { std::cout << "Point 构造函数被调用\n"; }
};

int main() {
    // malloc/free:只分配/释放原始内存,不调用构造/析构函数
    Point* p1 = (Point*)std::malloc(sizeof(Point));
    std::cout << "malloc 之后 x=" << p1->x << " (未初始化,值不确定)\n";
    std::free(p1);

    // new/delete:分配内存 + 调用构造函数;delete 调用析构函数 + 释放内存
    Point* p2 = new Point();        // 会打印 "Point 构造函数被调用"
    std::cout << "new 之后 x=" << p2->x << "\n"; // 保证是 0,因为构造函数初始化了
    delete p2;

    // new[]/delete[] 用于数组
    int* arr = new int[5]{1,2,3,4,5};
    std::cout << arr[4] << "\n";
    delete[] arr;
}

必须记住的配对规则:new 配 delete,new[] 配 delete[],malloc 配 free——混用(比如 new 分配的对象用 free 释放,或 new[] 分配的数组用 delete 而非 delete[] 释放)是未定义行为。现代 C++ 代码应优先用智能指针 + 容器,把裸 new/delete/malloc/free 限制在极少数手写底层数据结构或与 C API 交互的场景。
