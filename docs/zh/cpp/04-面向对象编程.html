面向对象编程

本章覆盖 C++ 面向对象的核心机制:类定义与访问控制、各种构造函数(含继承构造)、析构函数、this 指针、静态成员、friend、继承(单继承/多继承/虚继承)、多态的底层实现(vtable/vptr)、抽象类、override/final,以及重载与重写的辨析、深拷贝与浅拷贝、单例模式的实现演进。

一、类的定义与访问控制

#include <iostream>
#include <string>

class Person {
public:                              // 外部可访问
    Person(std::string name, int age) : name_(name), age_(age) {} // 构造函数,成员初始化列表

    void introduce() const {          // const 成员函数:承诺不修改成员变量
        std::cout << "我是 " << name_ << ",今年 " << age_ << " 岁\n";
    }
    void birthday() { ++age_; }

private:                              // 只有类自己(及友元)能访问
    std::string name_;
    int age_;

protected:                             // 自己和子类能访问,外部不能访问
    int secretLevel_ = 0;
};

int main() {
    Person p("Alice", 30);
    p.introduce();
    p.birthday();
    p.introduce();
    // p.name_ = "x";  // 编译错误:name_ 是 private
}
我是 Alice,今年 30 岁
我是 Alice,今年 31 岁

直接访问 private 成员会在编译期报错:

error: 'x' is a private member of 'P'

      ^
note: declared private here

class 默认成员是 private,继承默认是 private;struct 默认成员是 public,继承默认是 public——这是二者在语言层面唯一的区别,其余能力完全相同。

二、构造函数:默认 / 拷贝 / 移动 / 委托

#include <iostream>
#include <utility>

class Buffer {
public:
    Buffer() : Buffer(16) { std::cout << "默认构造(委托)\n"; }          // 委托构造:调用同类另一个构造函数
    explicit Buffer(int size) : size_(size), data_(new int[size]) {     // 普通构造函数
        std::cout << "普通构造 size=" << size_ << "\n";
    }
    Buffer(const Buffer& other) : size_(other.size_), data_(new int[other.size_]) { // 拷贝构造
        for (int i = 0; i < size_; ++i) data_[i] = other.data_[i];
        std::cout << "拷贝构造\n";
    }
    Buffer(Buffer&& other) noexcept : size_(other.size_), data_(other.data_) {       // 移动构造
        other.data_ = nullptr;
        other.size_ = 0;
        std::cout << "移动构造\n";
    }
    ~Buffer() {
        std::cout << "析构 size=" << size_ << "\n";
        delete[] data_;
    }

private:
    int size_;
    int* data_;
};

int main() {
    Buffer a;                          // 默认构造(内部委托到 Buffer(16))
    Buffer b(32);                       // 普通构造
    Buffer c = b;                        // 拷贝构造
    Buffer d = std::move(b);              // 移动构造,b 被“掏空”(data_ 置空,size_ 置 0)
}

默认构造(委托)
普通构造 size=32
拷贝构造
移动构造
析构 size=32
析构 size=32
析构 size=0
析构 size=16

要点:

  • 委托构造函数(C++11):一个构造函数的初始化列表里可以调用同一个类的另一个构造函数(Buffer() : Buffer(16) {}),避免重复初始化逻辑。
  • 拷贝构造函数 T(const T&):用已有对象初始化新对象,深拷贝资源。
  • 移动构造函数 T(T&&) noexcept(C++11):“窃取”临时对象/std::move 标记对象的资源,避免深拷贝;应标注 noexcept,否则 std::vector 等容器扩容时出于异常安全考虑会退回使用拷贝而非移动。
  • explicit 修饰单参数构造函数可以阻止隐式类型转换,详见第 5 章。

拷贝构造函数的参数为什么必须是 const T&,不能按值传递:如果按值传递,调用拷贝构造函数本身就需要先拷贝一次实参来构造这个形参——而构造这个形参又要再调用一次拷贝构造函数,无限递归,编译器会直接拒绝这种声明。用 const 引用则一次性解决两个问题:不产生任何额外拷贝;同时能绑定非 const 左值、const 左值、以及临时对象(右值),且向调用方承诺不会修改源对象。

编译器什么时候不生成默认构造函数:只要类里手动定义了任意一个构造函数(哪怕只是一个参数化构造函数),编译器就不再自动合成无参默认构造函数;如果仍然需要一个无参版本,必须显式写 ClassName() = default;。

继承构造函数(C++11):派生类如果只是想直接复用基类的构造函数集合,不需要逐个手写转发,可以用 using 声明一次性引入:

class Base {
public:
    Base(int x) : x_(x) {}
protected:
    int x_;
};

class Derived : public Base {
public:
    using Base::Base;   // 继承构造函数:Derived(int) 直接复用 Base(int) 的实现
};

Derived d(42);   // 等价于隐式定义了 Derived(int x) : Base(x) {}

这只是省去了手写透传构造函数的模板代码,派生类新增的成员如果需要额外初始化,仍要另外处理(继承来的构造函数不会初始化派生类自己新增的非静态成员,只会走它们的默认初始化)。

三、析构函数

析构函数(~ClassName())在对象生命周期结束时自动调用,负责释放资源(见上例);基类析构函数如果可能被多态删除(通过基类指针 delete),必须声明为 virtual,否则只会调用基类析构函数,派生类的资源被泄漏(第 5 章会展开对象生命周期管理的细节)。

构造函数为什么不能是虚函数:虚函数调用依赖对象已经就绪的 vptr(见第六节),而 vptr 本身正是在构造函数执行过程中才被设置起来的——构造函数的职责是”把对象建出来”,虚函数机制的前提是”对象已经存在”,两者在时序上互相矛盾,语言干脆禁止构造函数声明为 virtual。析构函数则相反,越是可能被多态删除的基类,越应该把析构函数声明为虚。

在构造函数或析构函数体内调用虚函数会怎样:语法上可以通过编译,但不会表现出多态。构造期间,对象的动态类型还停留在”当前正在执行构造函数的这一层”,vptr 指向的是当前类的 vtable,而不是最终派生类的 vtable,所以调用到的永远是当前类自己的版本;析构期间同理,一旦派生类的析构函数已经执行完毕、开始执行基类析构函数,vptr 又会退回指向基类的 vtable。这不是”没实现好”,而是刻意的设计——对象在构造/析构的这一层完成之前,其派生类那部分状态要么还没初始化、要么已经析构完毕,允许多态调用到一个状态不完整的派生类版本反而更危险。

析构函数里能不能抛异常:能通过编译,但极度危险,实践中应当避免。如果这次析构恰好发生在另一个异常引发的栈展开(stack unwinding)过程中,析构函数内部再抛出第二个异常会导致 C++ 运行时无法决定该传播哪一个异常,直接调用 std::terminate 终止整个程序,不会被任何上层 catch 捕获。因此析构函数内部涉及的所有操作(包括调用可能抛异常的函数)都应该用 try/catch 吞掉,绝不允许异常穿出析构函数边界。

四、this 指针、静态成员、friend

#include <iostream>

class Counter {
public:
    Counter() { ++count_; }                  // 每构造一个对象,静态成员 +1
    ~Counter() { --count_; }

    Counter& setValue(int v) {                 // 返回 *this 引用,支持链式调用
        value_ = v;
        return *this;                           // this 是指向当前对象的指针,*this 是对象本身
    }
    Counter& add(int v) {
        value_ += v;
        return *this;
    }
    int value() const { return value_; }

    static int count() { return count_; }      // 静态成员函数:不依赖具体对象,只能访问静态成员

    friend void dump(const Counter& c);          // 友元函数声明:能访问 private 成员

private:
    int value_ = 0;
    static int count_;                            // 静态成员变量声明:所有对象共享一份
};

int Counter::count_ = 0;                           // 静态成员变量的定义(在类外分配存储,必须写一次)

void dump(const Counter& c) {
    std::cout << "value_=" << c.value_ << "\n";     // friend 可以访问 private 成员
}

int main() {
    Counter a, b;
    std::cout << "count=" << Counter::count() << "\n"; // 2

    a.setValue(10).add(5).add(1);                       // 链式调用,依赖 *this 的引用返回
    std::cout << "a.value=" << a.value() << "\n";        // 16
    dump(a);
}
count=2
a.value=16
value_=16

要点:

  • this 在非静态成员函数内隐式存在,类型是 ClassName*(const 成员函数内是 const ClassName*)。
  • 静态成员变量属于类而非某个对象,必须在类外定义一次分配存储(C++17 起可以用 inline static 在类内直接定义,免去类外这一行)。
  • friend 打破封装边界,让指定的外部函数或类访问 private/protected 成员,应谨慎使用(过多 friend 会削弱封装性)。

this 本质上只是编译器隐式传给每个非静态成员函数的第一个参数——调用 obj.func(x),编译器实际生成的代码等价于 func(&obj, x),this 就是这个隐含的对象地址实参,不是存储在对象内部的字段,也没有任何特殊运行时机制。类型上要区分两种情况:普通成员函数里 this 的类型是 ClassName* const——指针本身不可变(不能让 this 指向别的对象),但指向的对象可以修改;const 成员函数里 this 的类型是 const ClassName* const——指针和指向的对象都不可变,这也是 const 成员函数不能修改非 mutable 成员的根本原因。this 的存储位置取决于调用约定:x64/ARM 平台通常通过寄存器传递,只有函数体内需要真正取 this 的地址时,编译器才会把它溢出到栈上。

静态成员函数为什么没有 this,也不能访问非静态成员:静态成员函数属于类本身而非任何具体对象,调用形式是 ClassName::staticFunc(),不依赖任何对象实例,编译器自然无法为它准备一个对象地址;没有对象地址,也就无法定位任何一个具体对象的非静态成员在内存中的偏移位置,这两条限制是同一个原因的两个表现。

为什么不能直接用 this 构造一个 shared_ptr:this 是裸指针,不携带任何生命周期信息。如果在类内部写 std::shared_ptr<T>(this),会创建一个和外部已有的 shared_ptr 完全独立的新控制块,两个控制块各自认为自己是唯一所有者,最终对同一个对象各自触发一次析构,造成双重释放。正确做法是让类继承 std::enable_shared_from_this<T>,再调用 shared_from_this() 获取共享同一控制块的 shared_ptr(第 9 章展开)。

五、继承:单继承 / 多继承 / 虚继承与菱形问题

#include <iostream>

class Animal {
public:
    Animal(std::string name) : name_(name) {}
    virtual ~Animal() { std::cout << "~Animal " << name_ << "\n"; } // 基类析构应为 virtual
    virtual std::string sound() const { return "..."; }              // 虚函数,可被派生类覆盖
    void describe() const { std::cout << name_ << " says " << sound() << "\n"; }
protected:
    std::string name_;
};

class Dog : public Animal {             // 单继承,public 继承
public:
    Dog(std::string name) : Animal(name) {}
    std::string sound() const override { return "Woof"; } // override 显式声明覆盖基类虚函数
};

class Flyable {
public:
    virtual void fly() const { std::cout << "flying...\n"; }
    virtual ~Flyable() = default;
};

class FlyingDog : public Dog, public Flyable {  // 多继承:同时继承 Dog 和 Flyable
public:
    FlyingDog(std::string name) : Dog(name) {}
};

int main() {
    Dog d("Rex");
    d.describe();                       // Rex says Woof

    Animal* ap = &d;                     // 基类指针指向派生类对象
    ap->describe();                      // 仍输出 Woof —— 多态:sound() 走的是 Dog::sound

    FlyingDog fd("Buddy");
    fd.describe();
    fd.fly();
}
Rex says Woof
Rex says Woof
Buddy says Woof
flying...
~Animal Buddy
~Animal Rex

菱形继承问题:如果 Left、Right 都非虚继承自同一个 Base,Diamond : Left, Right 会在内存里包含两份 Base 子对象,访问共同基类的成员产生二义性:

class Base { public: int value = 1; };
class Left : public Base {};
class Right : public Base {};
class Diamond : public Left, public Right {}; // 非虚继承:Diamond 里有两份 Base 子对象

int main() { Diamond d; std::cout << d.value << "\n"; } // 编译错误:二义性
error: non-static member 'value' found in multiple base-class subobjects of type 'Base':
    class Diamond -> Left -> Base
    class Diamond -> Right -> Base

解决方法是虚继承(virtual public Base),让 Left、Right 共享同一份 Base 子对象:

class Base { public: int value = 1; };
class Left : virtual public Base {};    // 虚继承:Left 和 Right 共享同一份 Base 子对象
class Right : virtual public Base {};
class Diamond : public Left, public Right {};

int main() {
    Diamond d;
    d.value = 99;               // 不再二义:只有一份 Base 子对象
    std::cout << d.value << "\n";
    std::cout << "sizeof(Diamond)=" << sizeof(Diamond) << "\n"; // 因虚基类指针变大
}
99
sizeof(Diamond)=24

虚继承的代价是每个虚继承分支都要多存一个指向共享基类子对象的指针(虚基类表指针),对象体积变大,构造顺序也更复杂(最终派生类负责初始化虚基类)。实践中应尽量用组合替代多继承,菱形继承是 C++ 里公认的复杂度重灾区,能不用就不用。

为什么虚基类必须由最终派生类直接初始化:普通继承下,每一层派生类的构造函数只负责初始化自己直接基类的那一份子对象,层层转发。但虚继承下 Base 全局只有一份共享子对象,如果 Left 和 Right 的构造函数都各自尝试初始化它,就会出现同一块内存被初始化两次的冲突。C++ 标准的规定是:虚基类必须由最终派生类的构造函数直接负责初始化,中间层(Left、Right)构造函数初始化列表里对 Base 的初始化请求会被编译器直接忽略。这意味着即使 Base 隔着两层继承关系,Diamond 的构造函数也必须显式调用 Base 的构造函数,不能指望 Left/Right 代劳:

class Base {
public:
    Base(int v) : value(v) {}
    int value;
};
class Left : virtual public Base {
public:
    Left() : Base(0) {}       // 虚继承下这里对 Base 的初始化会被忽略
};
class Right : virtual public Base {
public:
    Right() : Base(0) {}      // 同样被忽略
};
class Diamond : public Left, public Right {
public:
    Diamond() : Base(99), Left(), Right() {}  // 真正生效的是这里的 Base(99)
};

Diamond 构造出来后 value 是 99,而不是 Left/Right 各自尝试设置的 0——只有最终派生类构造函数里显式给出的初始化实参才会生效。

六、多态与虚函数机制:vtable / vptr

一个类只要声明了至少一个 virtual 函数,编译器就会给每个对象隐式插入一个指针(vptr),指向该类的虚函数表(vtable,每个类一张,不是每个对象一张):

#include <iostream>

struct NoVirtual {
    int x;
};

struct WithVirtual {
    int x;
    virtual void foo() {}
};

int main() {
    std::cout << "sizeof(NoVirtual)=" << sizeof(NoVirtual) << "\n";     // 4:只有一个 int
    std::cout << "sizeof(WithVirtual)=" << sizeof(WithVirtual) << "\n"; // 16:多了 8 字节的隐藏 vptr(含对齐)
}
sizeof(NoVirtual)=4
sizeof(WithVirtual)=16

调用虚函数(ap->describe() 内部的 sound())时,编译器生成的代码是”先通过对象的 vptr 找到该类的 vtable,再按固定偏移取出函数指针并调用”——这就是”运行时多态”的实现原理:调用哪个函数体,取决于对象实际类型的 vtable,而不是指针/引用的静态类型。这也是虚函数调用比普通函数调用多一次间接寻址、无法内联的原因。

多继承下 vtable 怎么处理:第五节 FlyingDog : public Dog, public Flyable 这类多继承对象,通常需要多个 vptr——每一条独立的继承链各自对应一份 vptr 和一张 vtable。通过 Dog* 调用虚函数走的是 Dog 这条链的 vptr,通过 Flyable* 调用走的是 Flyable 那条链的 vptr,编译器在做基类指针转换(比如 FlyingDog* 转 Flyable*)时会自动调整指针数值,使其指向正确的子对象起始位置,这也是多继承下裸指针数值转换前后可能不同的原因。

七、纯虚函数与抽象类、override/final

#include <iostream>
#include <memory>

class Shape {
public:
    virtual ~Shape() = default;
    virtual double area() const = 0;    // 纯虚函数,没有函数体(=0),使 Shape 成为抽象类
    void report() const { std::cout << "面积: " << area() << "\n"; }
};

class Circle final : public Shape {     // final 修饰类:禁止再被继承
    double r_;
public:
    explicit Circle(double r) : r_(r) {}
    double area() const override final { return 3.14159 * r_ * r_; } // final 修饰函数:禁止子类再覆盖
};

class Square : public Shape {
    double s_;
public:
    explicit Square(double s) : s_(s) {}
    double area() const override { return s_ * s_; }
};

int main() {
    // Shape s;                     // 编译错误:不能实例化抽象类

    std::unique_ptr<Shape> shapes[] = {
        std::make_unique<Circle>(2.0),
        std::make_unique<Square>(3.0),
    };
    for (auto& s : shapes) s->report(); // 多态调用:运行时根据实际类型走 vtable 派发
}
面积: 12.5664
面积: 9

含有纯虚函数(= 0)的类是抽象类,不能直接实例化:

error: variable type 'Shape' is an abstract class
    Shape s;
note: unimplemented pure virtual method 'area' in 'Shape'

override 显式声明”这是对基类虚函数的覆盖”,编译器会核对签名是否真的匹配基类虚函数,拼写错误或签名不一致会在编译期报错而不是悄悄变成一个新的、不参与多态的普通函数——应对所有覆盖基类虚函数的地方都加上。final 可以修饰虚函数(禁止子类再覆盖)或修饰类(禁止被继承),违反规则会编译报错:

class A { public: virtual void f() final {} };
class B : public A { public: void f() override {} }; // 试图覆盖 final 函数
error: declaration of 'f' overrides a 'final' function
    void f() override {}
         ^
note: overridden virtual function is here

纯虚函数能否有函数体:能。= 0 只表示”派生类必须重写它才能实例化”,不表示”基类完全不能提供实现”。基类可以在类外给纯虚函数补一份默认实现,派生类通过 Base::f() 显式调用它,把这份实现当作自己重写逻辑的一部分来复用——常见于析构函数:纯虚析构函数可以让类变成抽象类且仍然必须提供函数体,因为析构链路要求每一层都能被正常调用到。

final 在 C++11 之前怎么实现、为什么现在不用了:C++11 前没有 final 关键字,只能靠一套 hack:利用虚继承规则——虚基类必须由最终派生类直接初始化(第五节)。做法是定义一个构造函数为 private 的辅助类,让目标类虚继承这个辅助类并声明为其友元,目标类自己能构造(作为友元可访问 private 构造函数),但如果有人试图再继承目标类,新的最终派生类需要直接调用辅助类的私有构造函数,却因为不是友元而访问不到,编译失败。这套方案依赖复杂的继承和访问控制组合,可读性和维护成本都很差,final 出现之后完全没有必要再用,仅作历史了解。

final 除了防止继承,还有什么实际收益:编译器确认一个类是 final,或者某个虚函数被标记 final 之后,能够确定不会再有派生类重写它,从而做去虚拟化(devirtualization)——把原本需要经过 vptr 间接跳转的虚函数调用,在编译期直接确定调用目标,改写成普通的直接调用,甚至进一步内联。热路径上频繁调用的小虚函数标注 final 能带来实测可见的性能提升,这也是”组合优于继承”之外,final 值得主动使用的一个工程理由。

八、重载与重写的区别

重载(Overload)发生在同一作用域内(同一个类,或同一个命名空间),多个函数同名但参数列表不同(类型、个数、顺序任一不同即可),编译器在编译期根据实参类型直接决定调用哪个版本,属于静态绑定。不能仅凭返回值类型区分重载——调用点编译器只能看到传入的实参,看不到调用方打算怎么处理返回值(甚至可能根本不使用),无法据此消歧。

重写(Override)要求同时满足三个条件:存在继承关系、基类函数声明为 virtual、派生类函数签名(函数名、参数列表、const 修饰)与基类完全一致。满足这三点后,通过基类指针或引用调用该函数,运行时依据对象的实际类型通过 vtable 决定调用哪个版本,属于动态绑定(见第六节)。

容易被混淆的第三种情况是隐藏(hiding):派生类定义了和基类同名的函数,但只要基类该函数不是 virtual,或者参数列表不同,就不构成重写,而是把基类的同名函数遮蔽掉了。通过派生类对象或指针调用只能看到派生类版本,基类版本被藏起来(仍可通过 Base::func() 显式调用)。这是实际开发中常见的坑——很多人以为派生类定义了同名函数就自动构成重写,实际上没有 virtual、或者签名对不上,就完全没有多态这回事,通过基类指针调用永远只会调到基类版本。这正是 C++11 引入 override 关键字的原因:写在派生类函数声明后,让编译器检查签名是否真的匹配基类的虚函数,一旦函数名拼错或参数类型写错,编译器直接报错,而不是悄悄退化成一次隐藏。

维度 重载 重写 隐藏
作用域 同一类或同一命名空间 存在继承关系的基类与派生类之间 存在继承关系的基类与派生类之间
触发条件 函数名相同,参数列表不同 基类函数为 virtual,派生类签名完全一致 基类函数非 virtual,或签名不一致
绑定时机 编译期(静态绑定) 运行期(动态绑定,通过 vtable) 编译期(静态绑定,按静态类型查名)
能否靠返回值区分 不能 不适用(要求返回值一致,协变返回类型是唯一例外) 不适用

重写的返回类型必须严格一致,唯一的例外是协变返回类型(covariant return type):如果基类虚函数返回 Base*,派生类重写时允许返回 Derived*(Derived 是 Base 的子类)。重载和重写是不同维度的概念,可以同时存在于一个类里——某个重载版本恰好是从基类继承来的虚函数被重写了,互不冲突。

九、深拷贝与浅拷贝

编译器在没有自定义拷贝构造函数和拷贝赋值运算符时,会自动生成执行浅拷贝的版本——逐个成员按值复制(memberwise copy)。对 int、double 这类值类型成员没有问题,但对指针成员,复制的是地址本身:拷贝之后两个对象的指针成员指向同一块堆内存,而这两个对象的生命周期是独立的、析构顺序不受控制,这就埋下了三类具体问题:

  • 双重释放:两个对象各自析构时都对同一块内存执行 delete,第二次 delete 是未定义行为,实践中通常直接崩溃。
  • 悬垂指针:先析构的那个对象释放了内存后,另一个对象的指针成员就变成了指向已释放内存的悬垂指针。
  • 意外的相互影响:通过一个对象修改了共享内存的内容,另一个对象读到的数据也随之改变,即便调用方完全没有操作过第二个对象。

下面这段代码用 -fsanitize=address 实测复现了浅拷贝导致的双重释放:

class ShallowBuffer {
public:
    ShallowBuffer(const char* s) {
        len_ = strlen(s) + 1;
        data_ = new char[len_];
        memcpy(data_, s, len_);
    }
    ~ShallowBuffer() { delete[] data_; }
    // 未自定义拷贝构造/赋值运算符 -> 编译器生成浅拷贝,只复制指针值
private:
    char* data_;
    size_t len_;
};

void triggerDoubleFree() {
    ShallowBuffer a("hello");
    ShallowBuffer b = a;   // 浅拷贝:b.data_ 和 a.data_ 指向同一块堆内存
}   // 作用域结束时,a、b 的析构函数都会对同一个指针执行 delete[] -> 双重释放

深拷贝为指针成员重新分配一块独立内存,并复制原内存的内容,拷贝之后两个对象各自持有独立的堆内存。正确实现深拷贝需要同时手写拷贝构造函数、拷贝赋值运算符、析构函数三者——这就是 C++ 里的 Rule of Three:只要析构函数里有 delete,就必须同时手写拷贝构造和拷贝赋值,反之亦然:

class DeepBuffer {
public:
    DeepBuffer(const char* s) {
        len_ = strlen(s) + 1;
        data_ = new char[len_];
        memcpy(data_, s, len_);
    }
    DeepBuffer(const DeepBuffer& other) : len_(other.len_) {
        data_ = new char[len_];
        memcpy(data_, other.data_, len_);
    }
    DeepBuffer& operator=(const DeepBuffer& other) {
        if (this == &other) return *this;   // 防止自赋值先释放后读取
        delete[] data_;
        len_ = other.len_;
        data_ = new char[len_];
        memcpy(data_, other.data_, len_);
        return *this;
    }
    ~DeepBuffer() { delete[] data_; }
private:
    char* data_;
    size_t len_;
};

判断标准很直接:只要类里有裸指针且这个指针指向的内存是这个类自己 new 出来的,就必须写深拷贝;等价地说,只要析构函数里有 delete,就一定要配套写拷贝构造函数和拷贝赋值运算符。STL 容器是值语义,push_back 一个自定义对象会触发它的拷贝构造函数——如果这个类持有裸指针却没实现深拷贝,容器内部的副本和外部原对象共享同一块内存,一旦容器扩容触发旧元素析构、释放这块内存,容器里”新”的那份对象的指针就变成悬垂指针。

移动语义(第二节)是介于浅拷贝和共享、深拷贝之间的第三种选择——既不共享资源,也不复制资源,而是直接”偷”走源对象的指针,再把源对象自己的指针置空,开销从深拷贝的 O(n) 降到 O(1)。现代 C++ 更实用的替代方案是直接用 unique_ptr/shared_ptr 管理动态分配的资源,从根本上避免手写深拷贝——unique_ptr 直接禁止拷贝,彻底杜绝共享问题;shared_ptr 用引用计数管理共享生命周期,最后一个引用销毁时才真正释放(第 9 章详细展开)。写时复制(COW)曾是另一种折中方案——拷贝时先共享内存,只有某一方真正要修改数据、且发现引用计数大于 1 时才现场深拷贝一份,但多线程下维护引用计数需要原子操作,开销可观,C++11 后标准库已放弃 COW,std::string 的拷贝就是普通深拷贝。

十、单例模式的实现

单例模式要保证一个类只有一个实例并提供全局访问点:构造函数私有化,显式删除拷贝构造和拷贝赋值(防止绕过访问点复制出第二个实例),再通过一个静态方法返回唯一实例。四种实现方式是逐步演进的,每一步都是为了修掉上一版本的一个具体缺陷。

饿汉式在程序启动阶段就创建好实例(静态成员变量,main 执行前完成初始化)。天然线程安全,但如果单例本身很重、且可能根本用不到,就浪费了启动时间;更麻烦的是多个饿汉式单例之间的初始化顺序未定义(Static Initialization Order Fiasco),如果单例 A 依赖单例 B,而 B 恰好还没初始化完,就会出问题。

懒汉式延迟到第一次调用 getInstance() 时才创建,解决了饿汉式浪费资源的问题,但多线程环境下两个线程可能同时判断出实例为空,各自创建了一个实例,线程不安全。

双检锁(DCLP)在懒汉式基础上加锁:第一次不加锁的检查避免每次调用都要经历加锁开销,加锁后的第二次检查避免多个线程排队等锁时重复创建。但在 C++11 之前,instance = new Singleton() 语义上分”分配内存、调用构造函数、赋值给指针”三步,编译器或 CPU 可能把顺序重排成”分配内存、赋值指针、调用构造函数”,导致另一个线程在构造函数还没执行完时就看到非空指针并直接返回未构造完成的对象。

Magic Static(C++11 起推荐)利用函数内局部 static 变量,标准明确规定其初始化过程必须是线程安全的:

class Singleton {
public:
    static Singleton& getInstance() {
        static Singleton instance;   // C++11 保证:多线程首次并发调用时只有一个真正执行构造
        return instance;
    }
    Singleton(const Singleton&) = delete;
    Singleton& operator=(const Singleton&) = delete;
private:
    Singleton() = default;
};

这个方案没有手动锁、没有裸指针管理、没有内存泄漏风险(程序结束时局部 static 对象自动析构),线程安全完全交给编译器,是目前公认的最优解。

单例模式的取舍:单例本质上是一种全局状态,会带来单元测试困难(全局状态难以在测试用例间隔离重置)、隐藏依赖关系(调用方代码里看不出自己依赖了它)等副作用,能用依赖注入替代时通常优先选依赖注入。真正适合单例的场景是那些天然全局唯一、生命周期贯穿整个程序的对象:日志器、全局配置管理器、线程池、连接池。
