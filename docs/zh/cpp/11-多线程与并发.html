多线程与并发

C++11 之前标准库没有线程支持，大家各自用 pthread/Windows API，非常不统一。 C++11 引入了 <thread>、<mutex>、<condition_variable>、<atomic>、<future> 这一整套跨平台并发库， 这是很多”学过 C++ 语法但没写过并发代码”的人最容易在面试/实战中翻车的地方——本章尽量讲全。

一、std::thread：创建和管理线程

#include <thread>
#include <iostream>
using namespace std;

void worker(int id) {
    cout << "thread " << id << " running\n";
}

int main() {
    thread t1(worker, 1);
    thread t2(worker, 2);
    t1.join();   // 阻塞等待线程结束（必须 join 或 detach，否则析构时程序会 terminate）
    t2.join();
    return 0;
}
join()：阻塞当前线程，直到目标线程执行完毕，然后回收其资源。
detach()：把线程"放生"，让它在后台独立运行，不再需要 join；线程对象析构后，
          底层线程仍然继续跑，直到自己结束（要小心：不能再访问已经销毁的局部变量）。

⚠️ 一个 std::thread 对象在被销毁之前，必须调用过 join() 或 detach() 中的一个，
   否则析构函数会调用 std::terminate() 直接崩溃程序——这是新手最容易踩的坑。

编译多线程程序需要加 -pthread（Linux/macOS）：g++ -std=c++20 -pthread main.cpp。

二、数据竞争与 std::mutex

#include <mutex>
#include <thread>
using namespace std;

int counter_unsafe = 0;
void increment_unsafe() {
    for (int i = 0; i < 100000; i++) counter_unsafe++;  // 多线程同时读写，数据竞争(data race)
}

mutex m;
int counter_safe = 0;
void increment_safe() {
    for (int i = 0; i < 100000; i++) {
        lock_guard<mutex> lg(m);  // 构造时加锁，析构时自动解锁（RAII思想）
        counter_safe++;
    }
}

int main() {
    thread u1(increment_unsafe), u2(increment_unsafe);
    u1.join(); u2.join();
    cout << "unsafe (期望200000): " << counter_unsafe << endl;  // 实测: 108308（不确定，每次跑都可能不同）

    thread s1(increment_safe), s2(increment_safe);
    s1.join(); s2.join();
    cout << "mutex保护 (期望200000): " << counter_safe << endl; // 实测: 200000，稳定正确
}

实测结果（两个线程各自增加 counter 十万次）：不加锁的版本实测输出 108308（应为 200000）—— counter++ 不是原子操作（读取、加一、写回三步），两个线程的操作交错执行导致部分自增丢失。 加了 lock_guard 之后稳定得到正确的 200000。

lock_guard<mutex>：最简单的 RAII 锁封装，构造时 lock()，析构时 unlock()，不能中途手动解锁/重新加锁。
unique_lock<mutex>：比 lock_guard 更灵活，支持中途 unlock()/lock()、配合 condition_variable 使用、
                    延迟加锁(std::defer_lock)——但比 lock_guard 多一点点开销。
scoped_lock（C++17）：可以同时锁多个 mutex，内部用死锁避免算法保证不会因为加锁顺序不同而死锁
                     （见下面第四节）。

三、std::atomic：无锁原子操作

#include <atomic>

atomic<int> counter_atomic{0};
void increment_atomic() {
    for (int i = 0; i < 100000; i++) counter_atomic++;  // 原子自增，硬件指令级保证不会交错
}
// 两个线程各跑 increment_atomic 后，counter_atomic 稳定等于 200000
atomic<T> 对基本类型的自增/自减/比较交换(CAS)等操作提供硬件级别的原子性保证，
不需要 mutex 也能避免数据竞争，通常比 mutex 更快（没有线程阻塞/唤醒的开销），
但只适合"单个变量的简单操作"；如果要保护一段包含多个变量的复合逻辑，还是需要 mutex。

compare_exchange_weak/strong 是实现无锁数据结构的核心原语（CAS：
"如果当前值等于期望值，就换成新值，返回是否成功"），本章不展开，
可以理解为很多无锁队列/无锁栈底层都是围绕它做文章。

四、多个锁与死锁

死锁的经典场景：线程A按"先锁m1再锁m2"的顺序加锁，线程B按"先锁m2再锁m1"的顺序加锁，
两个线程各自锁住一个，都在等待对方释放另一个——永远卡住。

避免死锁的方法：
  1. 约定全局统一的加锁顺序（所有线程都先锁m1再锁m2）——最简单但依赖人为约定，容易出错
  2. 用 std::scoped_lock（或 C++11 的 std::lock）一次性锁多个 mutex，
     内部使用死锁避免算法（尝试加锁+回退重试），不管你传入的顺序是什么都不会死锁
mutex m1, m2;

void task_a() {
    scoped_lock lock(m1, m2);  // 顺序 m1, m2
}
void task_b() {
    scoped_lock lock(m2, m1);  // 顺序 m2, m1 —— 如果用两个 lock_guard 分别加锁，这里就会死锁
}
// 用 scoped_lock 后两个函数并发执行 1000 次都不会死锁（已验证）

五、std::condition_variable：线程间等待/通知

#include <condition_variable>
#include <queue>
using namespace std;

mutex mtx;
condition_variable cv;
queue<int> q;
bool finished = false;

void producer() {
    for (int i = 0; i < 5; i++) {
        { lock_guard<mutex> lg(mtx); q.push(i); }
        cv.notify_one();  // 唤醒一个正在 wait 的线程
    }
    { lock_guard<mutex> lg(mtx); finished = true; }
    cv.notify_all();      // 唤醒所有等待的线程（通知"结束"这种事件用 notify_all）
}

void consumer() {
    while (true) {
        unique_lock<mutex> ul(mtx);
        // wait 的第二个参数是"谓词"：只有它返回 true 才真正醒来继续往下执行；
        // 否则即使被 notify 唤醒，发现谓词仍是 false 也会自动重新进入等待——这叫"防止虚假唤醒"
        cv.wait(ul, [] { return !q.empty() || finished; });
        while (!q.empty()) {
            cout << "consumed " << q.front() << endl;
            q.pop();
        }
        if (finished) break;
    }
}
// 输出：consumed 0 1 2 3 4（生产者-消费者模型的标准写法）
为什么 wait() 必须传 unique_lock 而不能是 lock_guard：
  wait() 内部逻辑是"释放锁 -> 挂起等待通知 -> 被唤醒后重新加锁 -> 返回"，
  这个"释放/重新加锁"的操作需要锁对象支持中途 unlock()/lock()，lock_guard 不支持，只有 unique_lock 支持。

六、std::async / std::future / std::promise

#include <future>
using namespace std;

int add(int a, int b) {
    this_thread::sleep_for(chrono::milliseconds(10));
    return a + b;
}

int main() {
    // async：提交一个任务到后台执行，立即返回一个 future 句柄
    future<int> fut = async(launch::async, add, 3, 4);
    cout << "主线程可以先做别的事...\n";
    cout << "结果: " << fut.get() << endl;  // get() 阻塞直到结果就绪，只能调用一次

    // promise/future：更底层的手动传递结果的方式
    promise<int> prom;
    future<int> f2 = prom.get_future();
    thread producer_thread([&prom] { prom.set_value(42); });  // 子线程算完后手动 set_value
    cout << "promise/future结果: " << f2.get() << endl;         // 主线程阻塞等待
    producer_thread.join();
}
std::async 的两种启动策略：
  launch::async    —— 立即在新线程里异步执行
  launch::deferred —— 延迟执行，直到调用 fut.get()/wait() 时才在当前线程同步执行
  不传策略（默认）—— 由标准库自行决定用哪种，不同实现可能不一样，通常建议显式指定 launch::async

future/promise 的价值：把"线程间传递一个结果"这件事标准化，
不需要自己手写"共享变量+mutex+条件变量"这一整套模板代码。

七、std::call_once：保证只初始化一次

once_flag flag;
void init_once() {
    call_once(flag, [] { cout << "只会打印一次\n"; });
}
// 就算 3 个线程同时调用 init_once()，"只会打印一次"也只会真正执行一次
// 这是"线程安全的单例模式"最标准的实现方式（比双检锁 DCLP 更简单也更不容易写错）

八、thread_local：线程本地存储

thread_local int tls_counter = 0;  // 每个线程各自拥有一份独立的拷贝，互不影响

void increment_tls() {
    for (int i = 0; i < 5; i++) tls_counter++;
    cout << "线程 " << this_thread::get_id() << " 的 tls_counter=" << tls_counter << endl;
}
// 两个子线程各自跑完后各自输出 5，主线程的 tls_counter 仍然是 0（完全独立，没有互相影响）

常见用途：每个线程独立维护一个”错误码”、一个内存池/随机数生成器实例，避免加锁开销。

九、内存序简介（进阶，了解即可）

atomic 操作默认用 memory_order_seq_cst（顺序一致性），是最强也最直观的内存序——
所有线程看到的原子操作顺序都一致，符合直觉，但性能开销也最大。

C++11 还提供了更弱的内存序（memory_order_relaxed / acquire / release 等）用于极致性能优化场景，
允许编译器/CPU 对指令重排提供更大自由度——这部分内容理解门槛较高，
绝大多数业务代码不需要手动指定内存序，默认的 seq_cst 已经够用，
只有写高性能无锁数据结构库的场景才需要深入研究。

十、多线程 vs 多进程 vs 协程

维度 多线程 多进程 协程（如 C++20 coroutine）
内存空间 共享同一进程地址空间 各自独立地址空间 共享（本质是同一线程内的协作式调度）
切换开销 中等（内核调度） 大（涉及地址空间切换） 极小（用户态切换，不进内核）
通信方式 共享内存 + 锁/原子操作 IPC（管道/共享内存/socket等） 直接函数调用/共享变量
崩溃隔离 一个线程崩溃，整个进程都崩 进程间隔离，一个崩溃不影响其他 同线程内，隔离性同线程
典型场景 CPU密集型并行计算、共享状态的并发任务 需要强隔离性、独立崩溃恢复的服务 高并发I/O（网络请求），避免线程切换开销
