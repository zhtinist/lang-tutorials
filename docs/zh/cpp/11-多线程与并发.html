多线程与并发

C++11 之前标准库没有线程支持，大家各自用 pthread/Windows API，非常不统一。 C++11 引入了 <thread>、<mutex>、<condition_variable>、<atomic>、<future> 这一整套跨平台并发库， 这是很多”学过 C++ 语法但没写过并发代码”的人最容易在面试/实战中翻车的地方——本章尽量讲全。

一、std::thread：创建和管理线程

#include <thread>
#include <iostream>
using namespace std;

void worker(int id) {
    cout << "thread " << id << " running\n";
}

int main() {
    thread t1(worker, 1);
    thread t2(worker, 2);
    t1.join();   // 阻塞等待线程结束（必须 join 或 detach，否则析构时程序会 terminate）
    t2.join();
    return 0;
}
join()：阻塞当前线程，直到目标线程执行完毕，然后回收其资源。
detach()：把线程"放生"，让它在后台独立运行，不再需要 join；线程对象析构后，
          底层线程仍然继续跑，直到自己结束（要小心：不能再访问已经销毁的局部变量）。

⚠️ 一个 std::thread 对象在被销毁之前，必须调用过 join() 或 detach() 中的一个，
   否则析构函数会调用 std::terminate() 直接崩溃程序——这是新手最容易踩的坑。

编译多线程程序需要加 -pthread（Linux/macOS）：g++ -std=c++20 -pthread main.cpp。

二、数据竞争与 std::mutex

#include <mutex>
#include <thread>
using namespace std;

int counter_unsafe = 0;
void increment_unsafe() {
    for (int i = 0; i < 100000; i++) counter_unsafe++;  // 多线程同时读写，数据竞争(data race)
}

mutex m;
int counter_safe = 0;
void increment_safe() {
    for (int i = 0; i < 100000; i++) {
        lock_guard<mutex> lg(m);  // 构造时加锁，析构时自动解锁（RAII思想）
        counter_safe++;
    }
}

int main() {
    thread u1(increment_unsafe), u2(increment_unsafe);
    u1.join(); u2.join();
    cout << "unsafe (期望200000): " << counter_unsafe << endl;  // 实测: 108308（不确定，每次跑都可能不同）

    thread s1(increment_safe), s2(increment_safe);
    s1.join(); s2.join();
    cout << "mutex保护 (期望200000): " << counter_safe << endl; // 实测: 200000，稳定正确
}

实测结果（两个线程各自增加 counter 十万次）：不加锁的版本实测输出 108308（应为 200000）—— counter++ 不是原子操作（读取、加一、写回三步），两个线程的操作交错执行导致部分自增丢失。 加了 lock_guard 之后稳定得到正确的 200000。

lock_guard<mutex>：最简单的 RAII 锁封装，构造时 lock()，析构时 unlock()，不能中途手动解锁/重新加锁。
unique_lock<mutex>：比 lock_guard 更灵活，支持中途 unlock()/lock()、配合 condition_variable 使用、
                    延迟加锁(std::defer_lock)——但比 lock_guard 多一点点开销。
scoped_lock（C++17）：可以同时锁多个 mutex，内部用死锁避免算法保证不会因为加锁顺序不同而死锁
                     （见下面第四节）。

三、std::atomic：无锁原子操作

#include <atomic>

atomic<int> counter_atomic{0};
void increment_atomic() {
    for (int i = 0; i < 100000; i++) counter_atomic++;  // 原子自增，硬件指令级保证不会交错
}
// 两个线程各跑 increment_atomic 后，counter_atomic 稳定等于 200000
atomic<T> 对基本类型的自增/自减/比较交换(CAS)等操作提供硬件级别的原子性保证，
不需要 mutex 也能避免数据竞争，通常比 mutex 更快（没有线程阻塞/唤醒的开销），
但只适合"单个变量的简单操作"；如果要保护一段包含多个变量的复合逻辑，还是需要 mutex。

compare_exchange_weak/strong 是实现无锁数据结构的核心原语（CAS：
"如果当前值等于期望值，就换成新值，返回是否成功"），本章不展开，
可以理解为很多无锁队列/无锁栈底层都是围绕它做文章。

四、多个锁与死锁

死锁的经典场景：线程A按"先锁m1再锁m2"的顺序加锁，线程B按"先锁m2再锁m1"的顺序加锁，
两个线程各自锁住一个，都在等待对方释放另一个——永远卡住。

避免死锁的方法：
  1. 约定全局统一的加锁顺序（所有线程都先锁m1再锁m2）——最简单但依赖人为约定，容易出错
  2. 用 std::scoped_lock（或 C++11 的 std::lock）一次性锁多个 mutex，
     内部使用死锁避免算法（尝试加锁+回退重试），不管你传入的顺序是什么都不会死锁
mutex m1, m2;

void task_a() {
    scoped_lock lock(m1, m2);  // 顺序 m1, m2
}
void task_b() {
    scoped_lock lock(m2, m1);  // 顺序 m2, m1 —— 如果用两个 lock_guard 分别加锁，这里就会死锁
}
// 用 scoped_lock 后两个函数并发执行 1000 次都不会死锁（已验证）

五、std::condition_variable：线程间等待/通知

#include <condition_variable>
#include <queue>
using namespace std;

mutex mtx;
condition_variable cv;
queue<int> q;
bool finished = false;

void producer() {
    for (int i = 0; i < 5; i++) {
        { lock_guard<mutex> lg(mtx); q.push(i); }
        cv.notify_one();  // 唤醒一个正在 wait 的线程
    }
    { lock_guard<mutex> lg(mtx); finished = true; }
    cv.notify_all();      // 唤醒所有等待的线程（通知"结束"这种事件用 notify_all）
}

void consumer() {
    while (true) {
        unique_lock<mutex> ul(mtx);
        // wait 的第二个参数是"谓词"：只有它返回 true 才真正醒来继续往下执行；
        // 否则即使被 notify 唤醒，发现谓词仍是 false 也会自动重新进入等待——这叫"防止虚假唤醒"
        cv.wait(ul, [] { return !q.empty() || finished; });
        while (!q.empty()) {
            cout << "consumed " << q.front() << endl;
            q.pop();
        }
        if (finished) break;
    }
}
// 输出：consumed 0 1 2 3 4（生产者-消费者模型的标准写法）
为什么 wait() 必须传 unique_lock 而不能是 lock_guard：
  wait() 内部逻辑是"释放锁 -> 挂起等待通知 -> 被唤醒后重新加锁 -> 返回"，
  这个"释放/重新加锁"的操作需要锁对象支持中途 unlock()/lock()，lock_guard 不支持，只有 unique_lock 支持。

六、std::async / std::future / std::promise

#include <future>
using namespace std;

int add(int a, int b) {
    this_thread::sleep_for(chrono::milliseconds(10));
    return a + b;
}

int main() {
    // async：提交一个任务到后台执行，立即返回一个 future 句柄
    future<int> fut = async(launch::async, add, 3, 4);
    cout << "主线程可以先做别的事...\n";
    cout << "结果: " << fut.get() << endl;  // get() 阻塞直到结果就绪，只能调用一次

    // promise/future：更底层的手动传递结果的方式
    promise<int> prom;
    future<int> f2 = prom.get_future();
    thread producer_thread([&prom] { prom.set_value(42); });  // 子线程算完后手动 set_value
    cout << "promise/future结果: " << f2.get() << endl;         // 主线程阻塞等待
    producer_thread.join();
}
std::async 的两种启动策略：
  launch::async    —— 立即在新线程里异步执行
  launch::deferred —— 延迟执行，直到调用 fut.get()/wait() 时才在当前线程同步执行
  不传策略（默认）—— 由标准库自行决定用哪种，不同实现可能不一样，通常建议显式指定 launch::async

future/promise 的价值：把"线程间传递一个结果"这件事标准化，
不需要自己手写"共享变量+mutex+条件变量"这一整套模板代码。

七、std::call_once：保证只初始化一次

once_flag flag;
void init_once() {
    call_once(flag, [] { cout << "只会打印一次\n"; });
}
// 就算 3 个线程同时调用 init_once()，"只会打印一次"也只会真正执行一次
// 这是"线程安全的单例模式"最标准的实现方式（比双检锁 DCLP 更简单也更不容易写错）

八、thread_local：线程本地存储

thread_local int tls_counter = 0;  // 每个线程各自拥有一份独立的拷贝，互不影响

void increment_tls() {
    for (int i = 0; i < 5; i++) tls_counter++;
    cout << "线程 " << this_thread::get_id() << " 的 tls_counter=" << tls_counter << endl;
}
// 两个子线程各自跑完后各自输出 5，主线程的 tls_counter 仍然是 0（完全独立，没有互相影响）

常见用途：每个线程独立维护一个”错误码”、一个内存池/随机数生成器实例，避免加锁开销。

九、内存序简介（进阶，了解即可）

atomic 操作默认用 memory_order_seq_cst（顺序一致性），是最强也最直观的内存序——
所有线程看到的原子操作顺序都一致，符合直觉，但性能开销也最大。

C++11 还提供了更弱的内存序（memory_order_relaxed / acquire / release 等）用于极致性能优化场景，
允许编译器/CPU 对指令重排提供更大自由度——这部分内容理解门槛较高，
绝大多数业务代码不需要手动指定内存序，默认的 seq_cst 已经够用，
只有写高性能无锁数据结构库的场景才需要深入研究。

十、多线程 vs 多进程 vs 协程

维度 多线程 多进程 协程（如 C++20 coroutine）
内存空间 共享同一进程地址空间 各自独立地址空间 共享（本质是同一线程内的协作式调度）
切换开销 中等（内核调度） 大（涉及地址空间切换） 极小（用户态切换，不进内核）
通信方式 共享内存 + 锁/原子操作 IPC（管道/共享内存/socket等） 直接函数调用/共享变量
崩溃隔离 一个线程崩溃，整个进程都崩 进程间隔离，一个崩溃不影响其他 同线程内，隔离性同线程
典型场景 CPU密集型并行计算、共享状态的并发任务 需要强隔离性、独立崩溃恢复的服务 高并发I/O（网络请求），避免线程切换开销

十一、锁的两种实现思路：自旋锁 vs 互斥锁

std::mutex 加锁失败时具体怎么处理，标准没有规定，但主流实现（glibc 的 pthread_mutex、Linux 下依赖的 futex）选择的是”让线程睡眠，把 CPU 让给别人”——这只是众多加锁策略里的一种，另一种思路是自旋（busy-wait）：加锁失败就原地空转重试，不发生线程切换。

C++ 标准库没有提供现成的自旋锁类型，只给了 std::atomic_flag 这个原语，需要自己搭：

#include <atomic>

class SpinLock {
    std::atomic_flag flag_ = ATOMIC_FLAG_INIT;
public:
    void lock() {
        while (flag_.test_and_set(std::memory_order_acquire)) {
            // 拿不到锁，原地空转重试，不放弃 CPU
        }
    }
    void unlock() {
        flag_.clear(std::memory_order_release);
    }
};
// 4 个线程各自 lock/unlock 十万次保护同一个 counter++，实测 counter 稳定等于 400000
test_and_set 是一条硬件保证的原子指令：把标志位从 0 改成 1 并返回旧值。
旧值是 1 说明锁被占着，当前线程在 while 里不断重试；旧值是 0 说明抢到了锁。
整个过程没有系统调用、没有线程状态切换——失败的代价就是纯粹的 CPU 空转。

对比 mutex 加锁失败时的路径（Linux 下走 futex 系统调用）：
把线程放进等待队列、挂起，CPU 转去调度其他可运行的线程；解锁时再通过系统调用唤醒等待者。
一次完整的用户态/内核态切换（保存寄存器现场、重新被调度上 CPU）通常落在 1~10 微秒量级。

该用自旋锁还是互斥锁，取决于临界区能”关多久”——本质是一个简单的不等式：临界区的执行时间，相比两次上下文切换的开销，谁更大。

场景 临界区时长 推荐 理由
极短的原子级操作（如自增计数器） 几十纳秒级 自旋锁 忙等的浪费远小于一次上下文切换
包含 I/O、复杂计算、可能阻塞的调用 几十微秒以上 互斥锁 自旋这段时间足够调度很多别的工作，继续空转纯属浪费
经验拐点 10~20 微秒左右 视情况 这个量级正好接近上下文切换本身的开销，谁划算取决于具体硬件和负载

单核 CPU 上自旋锁是个陷阱：单核系统任意时刻只有一个执行流在跑。如果线程 A 持有锁、线程 B 自旋等待，B 会一直占着这唯一的核心空转，A 根本没有机会被重新调度上 CPU 去执行完临界区、释放锁——这基本等价于死锁，除非内核可抢占、能强制把 B 换下去。这也是为什么自旋锁只在多核环境、且预期锁很快会被释放的场景下才有意义，单核环境下应该无条件选互斥锁。

活锁与退避：多个线程同时自旋抢同一把锁，可能出现”大家都在抢、谁也抢不到”的惊群效应——每次锁一释放，所有自旋线程几乎同时尝试抢占，互相干扰缓存行，反而拖慢了真正拿到锁的那个线程。常见解法是失败后加入随机退避（等待一个随机时间再重试，打散竞争时机）、票据锁（ticket lock）保证先来后到的公平顺序、MCS 锁让每个等待线程只在自己私有的缓存行上自旋（减少多个线程反复争抢同一条共享缓存行带来的总线流量）。

自适应自旋：更精细的实现不会非此即彼，而是先自旋一小段时间（经验上约为一次上下文切换开销的 1.5~2 倍），若这段时间内还没拿到锁，再退化为真正的睡眠等待——短暂持有的锁享受自旋的低延迟，长时间持有的锁又不会让等待线程无谓空转。Java 的 synchronized 和 Linux 内核自身的 mutex_lock 都采用了类似策略。

C++20 给 atomic_flag 增加了 wait()/notify_one()/notify_all()，可以在拿不到锁时避免纯粹的忙等，由标准库实现决定用更高效的方式阻塞：

void lock() {
    while (flag_.test_and_set(std::memory_order_acquire)) {
        flag_.wait(true, std::memory_order_relaxed); // 拿不到锁时不必一直空转
    }
}
void unlock() {
    flag_.clear(std::memory_order_release);
    flag_.notify_one();
}

（本机 Apple Clang + -std=c++20 编译运行验证：4 线程各自增 10 万次，counter 稳定等于 400000，两种写法结果一致。）生产环境如果确实需要自旋锁，通常直接用平台提供的实现（如 POSIX 的 pthread_spinlock_t），而不是手写。

读写锁是建立在这两者之上的更高层抽象：允许多个读者并发持锁、写者独占，解决的是”读多写少”场景下互斥锁把所有读操作都串行化的浪费。std::shared_mutex（C++17）提供了 lock_shared()/unlock_shared()（读者用）和 lock()/unlock()（写者用）两套接口；多数标准库实现里它是基于互斥锁/条件变量搭建的，不是自旋型实现——想要”读者多、临界区短、优先自旋”的读写锁，仍然需要自己实现或依赖第三方库。

十二、单线程高并发的另一条路：I/O 多路复用

前面几节的并发模型都是”一个任务对应一个线程”，线程数随并发连接数线性增长；网络服务器面对成千上万个连接时，另一条路是单线程/少量线程 + I/O 多路复用：一个线程同时监视一大堆文件描述符，等待其中任意一个进入就绪状态（可读/可写/异常）再去处理它，避免了”一个连接一个线程”的内存和调度开销。Linux 下这条路径有三代实现：select → poll → epoll。

维度 select poll epoll
内核数据结构 位图 fd_set struct pollfd 数组 红黑树（管理注册的 fd）+ 就绪链表
fd 数量限制 默认 1024（受编译期常量 FD_SETSIZE 限制） 无硬性上限（受 ulimit -n 约束） 无硬性上限
每次调用的开销 用户态构造整个 fd_set 并整体拷贝进内核，内核遍历所有注册 fd 逐个检查 拷贝整个 pollfd 数组进内核，同样遍历所有 fd epoll_ctl 只在注册/取消监视时调用一次；epoll_wait 不需要每次都重新传入完整 fd 集合
时间复杂度 O(n)，n 是监视的 fd 总数 O(n) O(k)，k 是当前就绪的连接数，与监视的 fd 总数无关
触发模式 仅水平触发（LT） 仅水平触发（LT） 支持水平触发（LT，默认）和边缘触发（ET）
跨平台性 是，POSIX 标准 是，POSIX 标准 否，Linux 专有（macOS 对应 kqueue，Windows 对应 IOCP）

为什么 epoll 能做到 O(活跃连接数) 而不是 O(总连接数)：select/poll 的模型是”每次调用都重新告诉内核我关心哪些 fd”，内核每次都要把整个集合拷进来、逐个检查一遍状态——一万个连接里哪怕只有十个真正活跃，也要做一万次检查。epoll 把”注册关心哪些 fd”和”查询就绪状态”这两件事解耦：epoll_ctl 把 fd 挂进内核维护的一棵红黑树（选红黑树是因为增删查都要频繁发生，需要稳定的 O(log n)）；fd 真正就绪时，内核通过设备驱动的回调机制主动把它加入一条独立的就绪链表；epoll_wait 只需要把这条就绪链表的内容拷给用户态，开销天然只跟”当前有多少就绪”成正比，和”总共注册了多少”无关。

水平触发（LT）与边缘触发（ET）：LT 是 select/poll 唯一支持、也是 epoll 的默认模式——只要一个 fd 处于就绪状态（比如读缓冲区还有数据没读完），每次调用都会重新通知，不管上一次有没有处理完，编程模型简单，但处理不及时会反复被通知。ET 是 epoll 独有模式——只在 fd 就绪状态发生跳变的那一刻通知一次（从”无数据”变成”有数据”的瞬间），之后即便数据没读完也不会再通知，直到下一次新的跳变。

LT: fd 只要有数据就一直通知
    ─●───●───●───●───●─→  （每次 epoll_wait 都返回这个 fd，直到数据被读完）

ET: 只在状态跳变的瞬间通知一次
    ─●───────────────────→  （只在"从无到有"这一下通知，之后必须自己一次读干净）

ET 模式下必须一次性把数据处理完：配合非阻塞 I/O，用循环反复 read() 直到返回 EAGAIN（缓冲区已读空）才停止；如果只读了一部分就跳出循环、以为”下次还会通知我”，实际上不会有新通知，导致数据滞留、连接卡死。ET 能减少 epoll_wait 被调用和返回的次数，在连接数巨大的场景下降低系统调用总数，代价是编程复杂度更高，必须严格保证”非阻塞 I/O + 循环读到 EAGAIN”这个模式。

实践选择：连接数不多（几十到几百量级）、或者需要跨平台，用 select/poll 足够，没必要为理论上的性能优势引入平台耦合（epoll 是 Linux 专有，macOS 要换成 kqueue，Windows 换成 IOCP）；Linux 平台、高并发长连接场景（网络服务器、反向代理）用 epoll，O(活跃连接数) 相比 O(总连接数) 的优势会随连接规模扩大越来越明显。选定 epoll 后默认用 LT 模式即可——它相比 select/poll 的核心优势（O(k) 而不是 O(n)）在 LT 下已经成立；ET 只是在此基础上进一步压缩系统调用次数，不是使用 epoll 的必要条件，除非确认非阻塞 I/O 循环读的写法已经处理正确，否则不必为了 ET 承担额外的复杂度和隐蔽 bug 风险。

I/O 多路复用和本章前面的线程模型不是互斥的两条路，而是常常结合使用：一个进程内跑少量线程（通常对应 CPU 核数），每个线程各自跑一个 epoll 事件循环，用多路复用解决”单线程如何同时应对海量连接”，用少量线程解决”如何利用多核”——这正是 Nginx、Redis 等高性能服务器的经典架构。
