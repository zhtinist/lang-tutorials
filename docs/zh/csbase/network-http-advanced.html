HTTP进阶、安全与缓存

覆盖 HTTP 协议版本演进（1.0 → 1.1 → 2.0）、多 TCP 连接与队头阻塞、HTTPS 的加密与证书验证原理、强缓存与协商缓存、Cookie 与 Session、DNS 查询过程，最后用”从输入 URL 到页面展示”这道综合题把整条链路串起来。

一、HTTP/1.0 与 HTTP/1.1 的区别

方面 HTTP/1.0 HTTP/1.1
默认连接方式 短连接（每次请求后关闭） 长连接（默认开启，标准化持久连接）
Host 头 不支持 必须携带（支持虚拟主机）
分块传输 不支持 支持 Transfer-Encoding: chunked
缓存机制 只有 Expires、Last-Modified 新增 Cache-Control、ETag
范围请求 不支持 支持 Range 头 + 206 状态码
状态码数量 基础集合 扩展到 40 余个

连接管理：HTTP/1.0 下每个 HTTP 请求都要重新经历一次完整的三次握手和四次挥手，开销很大。HTTP/1.1 默认启用持久连接（可通过 Connection: keep-alive 显式声明,配合 timeout=30 之类的参数控制存活时间）,一条 TCP 连接可以承载多个先后发出的请求,省掉了重复握手的成本。

Host 头：HTTP/1.0 的请求里不携带目标域名信息,意味着一个 IP 地址只能对应一个网站。HTTP/1.1 强制要求携带 Host 字段,同一台物理机/同一个 IP 之上可以用虚拟主机技术承载多个不同域名的站点,这是共享托管和云计算基础设施能够发展起来的前提之一。

分块传输编码：HTTP/1.0 要求响应体大小必须通过 Content-Length 提前告知,这对内容长度无法预先确定的动态内容（比如持续生成的日志流）不友好。HTTP/1.1 引入 Transfer-Encoding: chunked，允许服务器把响应体拆成多个块边生成边发送,不需要提前知道总长度。

缓存机制演进：HTTP/1.0 的强缓存靠 Expires（绝对时间戳，依赖客户端本地时钟)，协商缓存靠 Last-Modified / If-Modified-Since。HTTP/1.1 引入了 Cache-Control（用相对时间表示,如 max-age=3600，不受客户端时钟不同步影响)和 ETag / If-None-Match（用内容指纹做验证，比基于时间的验证更精确）,详见后面”强缓存与协商缓存”一节。

管道化（Pipelining）与队头阻塞：HTTP/1.1 理论上允许在同一个连接上不等前一个请求的响应返回就发出下一个请求（管道化）,但绝大多数浏览器默认并不启用这项特性,因为一旦某个请求处理得慢,会阻塞排在它后面的所有响应——这是应用层的队头阻塞问题,后面会详细展开。

范围请求：HTTP/1.1 支持客户端通过 Range: bytes=0-499 只请求资源的一部分,服务器以 206 Partial Content 响应,是断点续传、视频拖动进度条这类功能的基础。

状态码扩展：HTTP/1.1 相比 HTTP/1.0 补充了大量更精细的状态码,比如 100 Continue（客户端在发送大请求体前先确认服务器愿意处理）、409 Conflict（资源状态冲突）、410 Gone（资源永久删除，语义比 404 更明确）。

二、HTTP/2.0 的改进

HTTP/2.0 没有改动 HTTP 的方法、状态码这些应用层语义,改的是报文的传输格式和连接的使用方式,核心目标是解决 HTTP/1.1 遗留的队头阻塞和头部冗余问题。

二进制分帧（Binary Framing）：HTTP/1.1 是纯文本协议,解析效率低且容易出现歧义（比如换行符处理）。HTTP/2 把所有传输的信息拆分成更小的二进制帧,每个帧带有类型（HEADERS、DATA、PRIORITY 等）、长度、所属的流 ID,解析速度更快,也是实现后面几项改进的基础。

多路复用（Multiplexing）：这是最核心的改进。HTTP/1.1 的持久连接虽然复用了 TCP 连接,但同一连接上的请求本质上还是要串行处理——排在前面的请求响应慢,会卡住后面的请求,这就是应用层队头阻塞。HTTP/2 给每个请求/响应分配一个流 ID,不同流的二进制帧可以在同一条 TCP 连接上交错发送、乱序到达,接收端根据流 ID 重新拼装——多个请求真正做到了并行处理，不再相互阻塞。

头部压缩（HPACK）：HTTP/1.1 每次请求都要带上完整的头部信息,而很多字段（User-Agent、Cookie 等）在同一个客户端的多次请求里是重复的,尤其在移动网络下这部分冗余流量的浪费很明显。HPACK 算法用三个手段压缩头部：一份预定义的静态字典（收录 61 个常见 HTTP 头字段）；一份动态字典（把本次连接里出现过的自定义字段缓存下来,后续引用直接用索引代替完整字段）；再加上基于字符出现频率的哈夫曼编码。综合下来头部体积能减少 50%~90%。

流优先级（Stream Prioritization）：HTTP/1.1 里资源的加载顺序完全由发起请求的顺序决定,浏览器没法明确告诉服务器”这个资源更重要,先给我”。HTTP/2 允许客户端构建一棵优先级树,通过权重和依赖关系描述资源之间的重要性（比如 JS 依赖 CSS 先加载完),服务器据此决定带宽分配和发送顺序,让首屏内容优先呈现。

服务器推送（Server Push）：HTTP/1.1 下,浏览器必须先解析完 HTML 才能发现它依赖的 CSS、JS 等资源,再逐个发起新请求,这中间的等待造成了额外的往返延迟。HTTP/2 允许服务器在客户端明确请求 HTML 之前,主动把它预判会用到的关联资源一起推送过去；如果客户端本地已经有缓存不需要这些资源,可以用 RST_STREAM 帧拒绝。

关于队头阻塞需要澄清一个层次：HTTP/1.1 的队头阻塞发生在应用层——服务器必须按请求顺序依次返回响应；HTTP/2 用多路复用解决了应用层的队头阻塞,但它仍然跑在单条 TCP 连接上,一旦这条 TCP 连接发生丢包,TCP 协议本身要求所有流的数据都必须等这个丢的包重传完成才能继续处理,这是传输层的队头阻塞,HTTP/2 本身解决不了,这也是 HTTP/3 改用 QUIC（基于 UDP）的直接动机。

三、HTTP 为什么使用多个 TCP 连接

HTTP/1.1 环境下,浏览器为同一个域名维护一个连接池,通常同时打开 6~8 条 TCP 连接（具体数字因浏览器而异)，而不是一个域名只用一条连接。

为什么需要多条连接：单条 HTTP/1.1 连接内部请求必须串行处理——排队的队头阻塞问题前面提过。把并发请求分散到多条独立连接上,是 HTTP/1.1 时代绕开这个限制的实际做法：页面里的 JS、CSS、图片等资源被分配到不同连接上并行获取,各连接互不影响,谁先处理完谁的响应就先回来,不需要严格保持和请求发出时相同的顺序。

每条连接各自独立地经历建连开销：每条 TCP 连接都要单独完成一次三次握手；如果是 HTTPS,每条连接还要各自单独做一次 TLS 握手,这会额外增加 1~2 个 RTT 的延迟。也就是说,多开连接虽然缓解了队头阻塞,但代价是握手开销随连接数线性增加,而且每条新连接都要从 TCP 慢启动的低速率状态重新爬升,初始阶段传输效率并不高。

域名分片（Domain Sharding）：早期为了进一步突破单域名连接数上限,有的网站会把静态资源放到多个子域名下（如 static1.example.com、static2.example.com），让浏览器对每个域名都各开一批连接,变相提高并发度。这个技巧在 HTTP/2 普及之后基本被放弃,因为多路复用已经能在一条连接内解决并发问题,域名分片反而会导致连接数过多、TLS 握手次数增加,得不偿失。

HTTP/2 的解法：多路复用让同一域名下的所有请求共享一条 TCP 连接就能并发处理,不再需要开多条连接规避队头阻塞,同时配合 HPACK 头部压缩和流优先级,整体连接利用率比 HTTP/1.1 的”开多条连接硬扛”要高效得多。

HTTP/3 的进一步改进：HTTP/2 虽然解决了应用层队头阻塞,但底层仍然是一条 TCP 连接,一旦发生丢包,所有流都要一起等待重传（传输层队头阻塞）。HTTP/3 基于 QUIC协议（构建在 UDP 之上）,在传输层原生实现了多路复用,不同流之间真正独立,一个流丢包不会连累其他流；QUIC 内建集成了 TLS 1.3,支持 0-RTT 建连,进一步压缩了握手延迟。

四、HTTPS 与 HTTP 的区别

维度 HTTP HTTPS
加密 明文传输,无加密 通过 SSL/TLS 加密（AES、ChaCha20 等算法）
默认端口 80 443
证书 不需要 需要 CA 签发的数字证书
完整性校验 无 有（基于哈希算法如 SHA-256）
身份认证 无法验证服务器身份 通过证书验证服务器身份，防止中间人伪装

HTTP 报文（包括头部、Cookie、请求体）在网络中以明文形式传输,任何处于传输路径上的中间节点都能读取甚至篡改内容,这是中间人攻击（MITM）的温床。HTTPS 的做法是在 HTTP 和 TCP 之间插入一层 SSL/TLS,所有 HTTP 内容在交给 TCP 之前先经过加密,同时通过证书机制验证”对方服务器真的是它声称的那个域名”,而不是攻击者伪装的。

因为多了一次 TLS 握手,HTTPS 建立连接会比纯 HTTP 多消耗 1~2 个 RTT 的延迟（TLS 1.3 优化到 1-RTT，支持会话复用时可以做到 0-RTT）。现代浏览器和协议规范已经把 HTTPS 当作事实上的强制要求：HTTP/2 规范本身并不强制要求加密,但主流浏览器只对 HTTPS 站点启用 HTTP/2；HTTP/3 则在协议层面直接要求集成 TLS 1.3,不再存在”HTTP/3 明文”这种形态。

五、HTTPS 的工作原理（TLS 握手全流程）

HTTPS 的安全性建立在一次 TLS 握手协商出的会话密钥之上，握手完成后所有 HTTP 数据都用这个会话密钥做对称加密传输。整个握手过程融合了非对称加密（用于安全地交换密钥）和对称加密（用于高效加密实际业务数据）两种手段,各取所长。

握手完整流程分为 8 步：

1. Client Hello：客户端发起连接,携带自己支持的 TLS 版本列表、支持的加密套件（cipher suite）列表,以及一个客户端随机数（Client Random）。

2. Server Hello：服务器从客户端提供的候选中,选定一个双方都支持的 TLS 版本和加密套件,同时生成并返回自己的一个随机数（Server Random）。

3. 证书下发：服务器把自己的数字证书发送给客户端。证书里包含服务器的公钥、证书对应的域名、有效期,以及签发该证书的 CA（Certificate Authority）信息。

4. 证书验证：客户端（通常由浏览器完成）校验这份证书的合法性,具体检查三件事：证书是否由客户端信任的 CA 签发（沿着证书链逐级向上验证,直到某个根 CA 是浏览器/操作系统内置信任的);证书是否在有效期内;证书里记录的域名是否和当前访问的域名一致。任何一项不通过,浏览器就会给出”连接不安全”的警告。

5. 密钥交换（生成预主密钥）：验证通过后,客户端生成一个随机数,称为预主密钥（Pre-Master Secret）,用服务器证书里的公钥对它加密,发送给服务器。因为这一步使用的是非对称加密,只有持有对应私钥的服务器才能解密出这个预主密钥,即使这段密文被中间人截获也无法还原——这正是非对称加密在这一步存在的意义:公钥加密、私钥解密,保护密钥交换过程本身的安全。

6. 会话密钥生成：服务器用自己的私钥解密出预主密钥后,双方（客户端和服务器）分别用相同的算法,把”客户端随机数 + 服务器随机数 + 预主密钥”这三个值一起运算,各自独立推导出同一把会话密钥（Session Key）。因为算法和三个输入值双方都一致,不需要再传输这把密钥本身,规避了密钥在网络上明文传递的风险。

7. Change Cipher Spec：双方各自发出信号,通知对方”从这条消息之后,我们要切换到刚才协商出来的加密算法和会话密钥进行通信了”。

8. Finished：双方各自发送一条用会话密钥加密过的验证消息,互相确认握手过程中交换的信息没有被篡改、握手成功完成。至此 TLS 握手结束,后续的 HTTP 请求和响应都用这把会话密钥做对称加密传输。

为什么握手阶段用非对称加密、正式传输阶段用对称加密：非对称加密的公钥和私钥分离,能在双方事先没有共享密钥的情况下,安全地完成密钥交换（只有私钥持有者能解密),但它的加解密计算开销很大,不适合用来加密大批量的业务数据。对称加密加解密速度快得多,但要求通信双方提前持有同一把密钥,而这把密钥没法直接明文传输。HTTPS 的方案就是先用非对称加密”，只做一件事——安全地协商出一把对称密钥（会话密钥）,之后所有实际的 HTTP 数据传输都改用这把对称密钥加密,兼顾了安全性（密钥交换阶段无法被窃取）和效率（大批量数据传输走对称加密，速度快）。

六、强缓存与协商缓存

浏览器缓存分为两级判断：先看强缓存是否命中，命中就直接用本地副本，完全不发请求；没命中再走协商缓存，向服务器发一次验证请求，由服务器判断资源是否变化。

请求资源
   |
   v
检查强缓存(Cache-Control / Expires) 是否仍在有效期内
   |
   +-- 是 --> 直接使用本地缓存(状态码 200 from cache),不发请求
   |
   +-- 否 --> 发送验证请求(带 If-None-Match / If-Modified-Since)
                 |
                 v
           服务器比对 ETag / Last-Modified
                 |
                 +-- 未变化 --> 返回 304 Not Modified,浏览器使用本地缓存
                 |
                 +-- 已变化 --> 返回 200 + 新资源内容

强缓存

Cache-Control（HTTP/1.1 引入）：用相对时间描述缓存有效期,常见指令包括 max-age=3600（缓存 3600 秒内有效）、public（允许包括代理服务器在内的任何缓存层缓存该资源）、private（只允许浏览器本地缓存,不允许代理缓存）、no-cache（不使用强缓存,每次都要走协商缓存验证）、no-store（完全不缓存,每次都重新请求完整资源）。

Expires（HTTP/1.0 引入）：用绝对时间戳描述过期时间,如 Expires: Thu, 27 Feb 2025 17:52:00 GMT。缺点很明显——它依赖客户端本地系统时钟,如果客户端时间和服务器时间没有同步,缓存有效期的判断就会出错。

两者同时出现时,Cache-Control 优先级更高,Expires 只在不支持 Cache-Control 的老旧客户端上起兜底作用。

协商缓存

Last-Modified / If-Modified-Since：服务器首次响应时用 Last-Modified 字段告知资源最后修改时间；浏览器再次请求同一资源时,带上 If-Modified-Since 字段回传这个时间戳；服务器比对资源实际的修改时间和这个时间戳,如果没有更新就返回 304 Not Modified（不携带资源体，浏览器继续用本地缓存),如果已更新就返回 200 加上最新内容。这个方案的局限在于时间戳只精确到秒,如果资源在 1 秒内被多次修改,这种验证方式就会误判为”没有变化”。

ETag / If-None-Match：服务器首次响应时用 ETag 字段返回资源内容的一个哈希指纹（如 ETag: "d3f4e5"）；浏览器再次请求时通过 If-None-Match 字段带上这个指纹；服务器重新计算当前内容的哈希值并比对,不一致就返回 200 + 新内容,一致就返回 304。因为判断依据是内容本身而不是修改时间,不存在秒级精度的问题,即使文件在极短时间内被改了又改回原样,只要最终内容哈希一致，ETag 也能正确识别为”未变化”。

两者同时存在时,ETag 的优先级高于 Last-Modified，因为它判断得更精确，代价是服务器需要额外计算哈希值，开销比直接比较时间戳略高。

实践建议

带哈希文件名的静态资源（如 app.a3f5c2.js）适合用强缓存加很长的 max-age，因为内容一旦变化文件名本身就会变，天然避免了缓存陈旧的问题；没有文件名哈希的动态或经常更新的资源，适合用协商缓存并优先依赖 ETag；对实时性要求高、每次都要拿到最新数据的接口，直接用 no-cache 或很短的 max-age。

七、Cookie 与 Session

Cookie 是服务器通过响应头 Set-Cookie 下发、存储在浏览器端的一小段文本数据，之后浏览器会在同源的每次请求里自动通过 Cookie 请求头带回给服务器。

Session 是服务器端维护的会话上下文，数据实际存放在服务器内存或数据库里，每个用户对应一份独立的 Session 数据，通过一个唯一的 Session ID 来标识。

维度 Cookie Session
存储位置 浏览器端 服务器端
数据类型 只能是字符串 可以是任意复杂对象
安全性 较低（存储在客户端，可被用户查看甚至篡改） 较高（数据始终留在服务端）
对请求的影响 增大每次请求的头部体积 占用服务器内存/存储资源
典型防护 HttpOnly（禁止 JS 读取）、SameSite（限制跨站携带） 需要防范 Session 固定攻击等

工作流程

Cookie 单独使用时的流程很直接：服务器在响应里写 Set-Cookie: username=htzhu; Path=/; HttpOnly，浏览器保存这份数据，此后每次向同源地址发请求都会自动附上 Cookie: username=htzhu。

Session 通常并不是脱离 Cookie 独立工作的，而是”Session 数据放服务端、Session ID 靠 Cookie 传递”这样一个组合：服务器首次识别到一个新会话时，生成一个 Session ID（比如 JSESSIONID=abc123），通过 Set-Cookie 下发给浏览器；浏览器后续请求自动带上这个 ID，服务器凭这个 ID 去查找对应的 Session 数据，找回这个用户此前的登录状态、购物车内容等信息。

安全性对比

Cookie 存放在客户端，面临两类主要风险：XSS 攻击可以通过注入脚本读取页面里能访问到的 Cookie（用 HttpOnly 属性可以禁止 JavaScript 读取 Cookie，缓解这个问题）；CSRF 攻击利用浏览器自动携带 Cookie 的特性，诱导用户在不知情的情况下向目标网站发出请求（用 SameSite 属性限制 Cookie 只在同站请求或特定跨站场景下携带，可以缓解）。

Session 因为敏感数据始终留在服务端、传递给客户端的只有一个不透明的 ID，安全性相对更高，但需要防范 Session 固定攻击（攻击者提前设定好一个 Session ID 诱导受害者使用，登录后攻击者用同一个 ID 就能冒充受害者身份）等针对 Session 机制本身的攻击手法。

与 Token/JWT 的关系

不依赖 Cookie 的替代方案包括把 Session ID 直接编码进 URL 里（安全性较差，容易泄露在日志和浏览器历史中），以及使用 JWT（JSON Web Token）——JWT 直接把用户身份和会话数据编码进 Token 本身（并做签名防篡改），服务端不需要额外存储任何 Session 数据，天然契合无状态的 RESTful API 设计。分布式系统里常见两种演进路径：一是把 Session 数据集中存储到 Redis 等共享存储中，让多台应用服务器共享同一份会话状态；二是干脆放弃服务端 Session，完全依赖 JWT 这种自包含的 Token 方案。

八、DNS 查询过程

DNS（Domain Name System）把人类可读的域名解析成 IP 地址，整个过程按由近及远、逐级查找的顺序进行。

完整查询步骤

第一步，检查本地缓存：依次检查浏览器自身的 DNS 缓存、操作系统级别的 DNS 缓存、以及本地 hosts 文件（macOS/Linux 是 /etc/hosts，Windows 是 C:\Windows\System32\drivers\etc\hosts）。命中任意一级就直接拿到 IP，后面的步骤全部跳过。

第二步，向本地 DNS 服务器（通常是 ISP 提供或用户手动配置的）发起递归查询：如果本地缓存没有命中，浏览器把查询请求交给本地 DNS 服务器，本地 DNS 服务器如果自己缓存里有记录就直接返回；没有的话由它继续下面的迭代查询过程。

第三步，查询根域名服务器：本地 DNS 服务器向全球十几组根 DNS 服务器之一发起查询，根服务器不知道具体域名对应的 IP，但知道该顶级域名（如 .com）对应的顶级域服务器地址，把这个地址返回给本地 DNS 服务器。

第四步，查询顶级域名服务器（TLD Server）：本地 DNS 服务器拿着根服务器给的地址，继续向顶级域服务器查询，顶级域服务器返回目标域名对应的权威 DNS 服务器（Authoritative Name Server）地址。

第五步，查询权威域名服务器：本地 DNS 服务器向这个权威服务器发起查询，权威服务器上存放着该域名具体的解析记录，直接返回对应的 IP 地址。

第六步，结果返回与缓存：本地 DNS 服务器把查到的结果按 TTL（Time To Live，记录有效期，比如 3600 秒）缓存下来，同时把 IP 地址返回给最初发起请求的客户端，客户端也会缓存这个结果，供之后一段时间内复用。

递归查询与迭代查询

这两个术语描述的是查询过程中不同环节的行为方式：客户端到本地 DNS 服务器这一段是”递归”——客户端只发一次请求，剩下所有查询工作全部交给本地 DNS 服务器代劳，客户端只等最终结果。本地 DNS 服务器向根服务器、顶级域服务器、权威服务器逐级查询这一段是”迭代”——每一级服务器都只返回”你应该去问谁”，而不是替本地 DNS 服务器把全部查询都做完，本地 DNS 服务器需要自己拿着上一级给的地址，逐级往下问。

缓存的意义

各级 DNS 服务器（包括本地 DNS、甚至部分递归查询链路上的中间节点）都会缓存查询结果，TTL 到期前重复查询同一域名不需要再走完整的根 → 顶级域 → 权威服务器这条链路，大大减少了全球 DNS 系统的查询压力，也让常用域名的解析速度非常快。

常见 DNS 记录类型

记录类型 含义
A 域名对应的 IPv4 地址
AAAA 域名对应的 IPv6 地址
CNAME 域名别名，指向另一个域名
MX 该域名对应的邮件服务器地址

九、从输入 URL 到页面展示的完整流程

这是把前面所有网络知识串联起来的综合应用题，完整链路可以分成三大阶段：网络连接建立、请求响应交换、浏览器渲染。

      |
      v

      v
[2] DNS 查询 —— 域名解析为 IP 地址
      |
      v
[3] 建立 TCP 连接 —— 三次握手

      v
[4] TLS 握手(仅 HTTPS) —— 协商密钥、验证证书

第一步，URL 解析：浏览器把输入的 URL 字符串拆解成协议（HTTP 或 HTTPS）、主机名（如 www.example.com）、端口号（未显式指定时 HTTP 默认 80、HTTPS 默认 443）、路径（如 /index.html）等组成部分。

第二步，DNS 查询：按上一节描述的顺序——本地 hosts 文件、浏览器/系统缓存、本地 DNS 服务器递归查询（根服务器 → 顶级域服务器 → 权威服务器）——最终拿到目标主机名对应的 IP 地址。

第三步，建立 TCP 连接：浏览器向拿到的 IP 地址、目标端口发起三次握手——发 SYN 报文，收到服务器的 SYN-ACK，再回一个 ACK，连接进入 ESTABLISHED 状态（详见第一个文件的三次握手一节）。

第四步，TLS 握手（仅当协议是 HTTPS 时才有这一步）：客户端发 Client Hello，服务器回 Server Hello 并带上数字证书，客户端验证证书链、域名、有效期，验证通过后用证书公钥加密一个预主密钥发给服务器，双方各自推导出会话密钥，随后的通信全部用这把对称密钥加密（详见本文件第五节 HTTPS 工作原理）。

第五步，发送 HTTP 请求：浏览器组装并发出一个完整的 HTTP 请求报文，包含请求行（如 GET /index.html HTTP/1.1）、请求头（Host、User-Agent、Accept、Cookie 等字段）、以及请求体（GET 通常为空，POST 携带表单或 JSON 数据）。

第六步，服务器接收并处理请求：以常见的 Java Web 容器（如 Tomcat）为例，服务器接收到 HTTP 请求后，根据配置（如 web.xml 里的 URL 映射规则）找到应该处理这个路径的 Servlet；如果该 Servlet 还没有被实例化，容器通过反射创建实例并调用其 init() 方法完成初始化；随后调用 service() 方法，service() 根据请求方法（GET/POST 等）分发给对应的 doGet()/doPost() 方法执行具体业务逻辑，处理过程中通常会涉及查询数据库、调用其他服务等操作，最终把处理结果写入响应对象。

第七步，服务器返回 HTTP 响应：处理完成后，服务器组装响应报文返回给浏览器，包含状态行（如 HTTP/1.1 200 OK）、响应头（Content-Type、Content-Length 等字段）、响应体（通常是 HTML 文档，也可能是 JSON 等其他格式的数据）。

第八步，浏览器解析渲染页面：这一步本身又分为若干子阶段——浏览器从上到下解析收到的 HTML，构建出 DOM（文档对象模型）树；解析 HTML 中引用的 CSS（包括外链、内联、<style> 标签），构建出 CSSOM（CSS 对象模型）树；解析并执行页面中的 JavaScript，脚本执行过程中可能会修改 DOM 或 CSSOM 的内容（这也是 <script> 标签的位置会影响页面渲染时机的原因）；把 DOM 树和 CSSOM 树合并，计算出每个可见节点最终应该呈现的样式，构建出渲染树（Render Tree，不包含 display:none 等不可见的节点）；基于渲染树进行布局计算（Layout / Reflow），确定每个元素在页面上的精确位置和尺寸；最后把计算好的内容绘制（Paint）到屏幕上，用户才真正看到页面内容。

这套流程把网络层（DNS、TCP、TLS、HTTP）和渲染层（DOM、CSSOM、渲染树、布局、绘制）完整衔接了起来：前半段是”如何把请求送到服务器、把响应带回来”，后半段是”浏览器怎么把拿到的这段响应体变成用户能看到的画面”，两段合在一起才是这道题的完整答案。
