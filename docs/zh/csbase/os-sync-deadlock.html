操作系统同步互斥与死锁

多个进程或线程并发执行时，一旦涉及共享资源，就会出现两类问题：一是”谁先谁后”的协作顺序问题（同步），二是”同一时刻只能一个用”的独占访问问题（互斥）。处理不好，轻则数据错乱，重则所有相关进程永远卡住不动——也就是死锁。这一篇把同步互斥的实现手段，从最原始的软件算法到操作系统提供的信号量、管程，再到死锁的成因、预防和银行家算法，逐一讲清楚。

一、线程同步的方式有哪些

线程的实现方式分内核级和用户级两类（参见”进程和线程的区别”），同步手段也因此分成两组。

内核级线程（KLT）的同步方式，特点是需要操作系统介入，竞争失败的线程会被移出调度队列进入阻塞：

  • 互斥锁（Mutex）：通过系统调用（如 pthread_mutex_lock）获取锁，确保同一时间只有一个线程进入临界区，竞争失败的线程被阻塞。Linux 用 futex 做了优化——先在用户态自旋一小段时间，实在拿不到锁才真正陷入内核阻塞，减少不必要的上下文切换。适用场景是长临界区，比如文件操作，用忙等待反而浪费 CPU。
  • 信号量（Semaphore）：计数信号量管理资源池，例如数据库连接池——池子里有几个连接就允许几个线程同时拿；二进制信号量等价于互斥锁，但支持跨进程（System V 信号量）。
  • 条件变量（Condition Variable）：必须搭配互斥锁使用，wait() 释放锁并阻塞，signal() 唤醒等待线程。典型场景是生产者-消费者模型：缓冲区满了生产者等待，缓冲区空了消费者等待，谁的条件满足了就被对方唤醒。
  • 读写锁（Read-Write Lock）：读锁共享（多个线程可同时持有），写锁独占。适合读多写少的场景，比如配置文件——多个线程同时读取配置没问题，但更新配置时必须独占。
  • 自旋锁（Spinlock）：线程循环检测锁状态（类似 while (lock == BUSY);），不主动让出 CPU。适用于多核环境下的短临界区，比如 Linux 内核处理中断时的临界区保护——因为临界区执行得很快，忙等的开销比切换线程的开销还小。风险是如果临界区变长，长时间自旋会白白浪费 CPU，需要配合抢占式调度。

用户级线程（ULT）的同步方式，特点是尽量不触发内核态切换：

  • 原子操作（Atomic）：通过 CPU 指令（如 CAS、LL/SC）直接操作内存，不需要锁。适合无锁计数器、标志位更新这类简单操作（如 atomic.AddInt32），复杂逻辑仍然需要锁。
  • 协程同步原语：如 Go 的 channel，通过通信传递数据所有权来代替共享内存，依赖调度器做协作式（非抢占式）切换，没有锁竞争，适合高并发 I/O 密集型任务（网络服务器）。
  • 轻量级锁：先在用户态尝试自旋，失败后再升级为内核锁，例如 Java 的锁膨胀机制（偏向锁→轻量级锁→重量级锁），目的是减少内核切换次数，兼顾性能与公平性。
  • 非阻塞数据结构：基于原子操作实现的无锁队列、无锁栈，比如 Java 的 ConcurrentLinkedQueue。
  • 协作式调度同步：用户态调度器主动让出 CPU（如协程 yield），通过事件循环协调任务。缺点是依赖开发者手动控制切换时机，容易因为忘记让出而引发死锁。

几个常见追问：

Go 的 Goroutine 如何避免内核级同步的开销？ 用 channel 通信替代锁，协程切换完全在用户态由调度器管理，只有在真正需要系统调用时才进入内核态。

自旋锁在什么场景下会失效？如何优化？ 单核环境下自旋等于纯粹浪费 CPU（因为持锁线程根本没有机会被调度执行来释放锁）；临界区一长，自旋时间跟着变长同样不划算。优化方式是设置最大自旋次数，超过后转为阻塞锁，或者做自适应自旋——根据历史等待时间动态预测这次该不该继续自旋。

自旋锁在内核线程和用户线程中使用有何差异？ 内核态可以直接禁用中断来保证原子性、防止死锁，并且支持多核并发自旋；用户态没有这个特权，只能依赖原子指令或 futex，单核环境下需要主动调用 sched_yield 让出 CPU。

二、常见的锁有哪些类型

三种最典型的锁：

  • 互斥锁（Mutex Lock）：保证同一时间只有一个线程能访问共享资源，一个线程拿到锁后其他线程必须等锁释放。常与条件变量配合实现条件同步，适用于需要独占访问的场景，如修改全局变量、维护共享数据结构。
  • 读写锁（Read-Write Lock）：拆成共享的读锁和独占的写锁——读锁可以被多个线程同时持有，写锁只能被一个线程持有。适合读多写少的场景，如缓存系统、数据库。
  • 自旋锁（Spin Lock）：锁被占用时不阻塞，而是循环检测（忙等待），以此避免线程切换的开销。适用于锁占用时间极短的场景，比如内核里的临界区保护。

信号量、锁、条件变量三者的关系是一个常见的追问点：

  • 信号量是最通用的同步机制，靠计数器控制资源访问，几乎任何同步问题（包括锁）都可以用信号量搭建出来。互斥锁本质上就是信号量的一个特例——一个只能取 0 或 1 的二进制信号量。
  • 锁是更高层次的抽象，专门用来保护临界区。互斥锁虽然和信号量相关，但作为一个具体实现，它本身属于锁的范畴。读写锁、自旋锁也是锁的类型，但它们不是信号量的特例：读写锁允许多个读操作并发但写操作排他，自旋锁是获取失败时忙等而不是阻塞——这两种行为都超出了”一个计数器”能表达的语义。
  • 条件变量通常和互斥锁一起使用，用于线程间的通信：允许线程在某个条件不满足时等待，等其他线程发出通知再醒来。条件变量本身不是信号量，但可以和信号量结合实现更复杂的同步逻辑。

为什么要用锁和条件变量而不是直接裸用信号量？ 两个原因。一是抽象层次——锁和条件变量提供了更高层次的抽象，代码更易读易写易维护；信号量更底层，需要开发者手动管理计数器，容易出错。二是功能专门化——锁专门保护临界区，条件变量专门做线程间通信，两者组合能更清晰地表达同步逻辑；而信号量虽然功能强大，想用它单独实现同样的效果往往要写更多代码，还更容易踩中死锁或资源争用的坑。

三、进程的同步与互斥及其实现方法

同步（又称直接相互制约关系，“程序-程序”模式）：多个协作进程按一定顺序执行，在工作中相互等待或通信，体现的是协作关系。互斥（又称间接相互制约关系，“程序-资源-程序”模式）：一个进程访问临界资源时，其他进程必须等它退出临界区才能访问，体现的是竞争关系。

先明确两个概念：临界资源是同一时刻只能由一个进程使用的资源，既包括打印机、磁带机、绘图仪这类物理设备，也包括消息队列、共享变量、文件这类软件资源；临界区是程序中访问临界资源的那部分代码。临界区前面通常有一段检查代码（进入区），后面有一段释放代码（退出区），其余代码称为剩余区。

同步与互斥的实现都必须遵循四条设计准则：

  1. 空闲让进：临界区空闲时，请求进入的进程应立即被允许进入，不能让临界资源闲置。
  2. 忙则等待：已有进程在临界区内时，其他请求进入的进程必须在外面等待，确保互斥访问。
  3. 有限等待：对请求访问临界资源的进程，必须保证它能在有限时间内进入临界区，否则会陷入”无限等待”，即便最终等到资源也失去了意义。
  4. 让权等待：进程如果暂时无法进入临界区，应该立即释放处理器，避免陷入”忙等”浪费 CPU。

软件实现方法

以下四种方法只考虑两个进程之间的互斥，是理解”为什么需要硬件/操作系统支持”的铺垫：

① 单标志法：设一个共享变量 turn（0 或 1），表示进入临界区的权限归谁：

// 进程 P0
while (TRUE) {
    while (turn != 0);   // 进入区：turn=1 说明轮到 P1，P0 阻塞在这里
    临界区;
    turn = 1;             // 退出区：把权限让给 P1
    剩余区;
}
// 进程 P1
while (TRUE) {
    while (turn != 1);
    临界区;
    turn = 0;
    剩余区;
}

问题：强制要求两个进程轮流进入，如果 P0 还没准备好进临界区，P1 明明想进也进不去（临界区空闲却不让进），违背了”空闲让进”。

② 双标志先检查法：改用数组 flag[2]，进程进入前先检查对方标志位，对方不忙就把自己标志位置 TRUE：

while (TRUE) {
    while (flag[j]);   // 检查对方是否在用
    flag[i] = TRUE;    // 标记自己进入
    临界区;
    flag[i] = FALSE;
    剩余区;
}

问题：检查 flag[j] 和设置 flag[i] 之间存在时间差，两个进程可能都检查到对方标志位为 FALSE，然后同时把自己的标志位置 TRUE 并同时进入临界区，违背”忙则等待”。

③ 双标志后检查法：调整顺序，先设置自己的标志位再检查对方：

while (TRUE) {
    flag[i] = TRUE;    // 先声明自己要进
    while (flag[j]);
    临界区;
    flag[i] = FALSE;
    剩余区;
}

这样避免了两个进程同时进入，但又引出新问题：如果两个进程都先把自己的 flag 置 TRUE，然后互相发现对方也想进，就会都卡在 while (flag[j]) 里退不出来，违背”有限等待”和”空闲让进”。

④ Peterson 算法：结合标志位和谦让变量 turn，既表明”我想进”，又主动谦让：

while (TRUE) {
    flag[i] = TRUE;              // 先表示希望进入
    turn = j;                    // 再谦让，把先机让给对方
    while (flag[j] && turn == j); // 对方也想进且轮到对方时，自己等待
    临界区;
    flag[i] = FALSE;
    剩余区;
}

Peterson 算法满足互斥、空闲让进、有限等待三个条件，但不满足”让权等待”（不能进临界区时依然在忙等，没有主动释放处理器），并且只能处理两个进程之间的互斥，不符合多进程的实际需求。这说明纯软件手段本身有局限，必须靠硬件或操作系统层面的机制补齐。

硬件实现方法

  • 关中断方法：进入临界区前关中断（暂停进程调度，让当前进程独占处理机），退出后再开中断。能同时满足空闲让进、忙则等待、有限等待，但不适用于多处理器环境——即使把当前核心的中断关了，其他核心上的进程照样能跑，无法阻止它们同时进入临界区。
  • 硬件指令方法：TSL（Test-and-Set-Lock）通过一条硬件指令完成”读取并设置”的原子操作；Swap（又称 exchange）指令通过硬件原子地交换两个变量的值。两者都利用了指令级的原子性来规避软件方法里”检查”和”设置”之间的时间差问题。

高级同步机制

  • 信号量（Semaphore）：一种关联临界资源的数据结构，不同的值表示资源的不同状态，支持 P()（申请资源，不够则阻塞等待）和 V()（释放资源，有等待者则唤醒一个）两种原子操作。按用途和取值范围可分为二进制信号量和计数信号量，按实现机制可分为整型信号量和记录型信号量。
  • 管程（Monitor）：为了集中管理分散在各个进程里的临界区、防止进程违反同步规则而引入的软件模块，由公共变量及其访问函数组成。进程对共享资源的请求、释放等操作必须统一通过管程完成，管程会根据资源状态决定接受或拒绝，确保每次只有一个进程能进入临界区。管程带有面向对象的思想——把共享数据结构和对它的操作、以及同步细节都封装在一个对象里，调用者不需要关心内部的同步逻辑。
  • 屏障（Barrier）：确保多个进程或线程在某个点之前都不会继续往下执行——先到的进程会一直等待，直到所有进程都到达屏障后才一起放行。适合并行计算、多阶段任务这类需要”集合点”的场景。
  • 条件变量（Condition Variable）：本质是一个抽象对象，内部维护一个等待队列，用于在多个进程/线程之间传递状态信息，专门适合”等待某条件成立”的场景，通常与互斥锁一起使用以避免竞态条件。

进程本身由程序段、数据段、进程控制块（PCB）三部分组成。程序未运行时，程序段和数据段是磁盘上的静态文件；运行时操作系统把它们加载进内存形成进程的地址空间，进程就是这个动态执行过程——多个进程完全可以对应同一段静态的程序代码（比如同一个可执行文件启动了多个实例）。

四、死锁的定义与预防

死锁是指多个进程或线程在执行过程中，因为竞争资源而造成的一种互相等待的僵局，导致所有相关进程都无法继续向前推进。产生死锁必须同时满足四个必要条件：

  1. 互斥条件：资源一次只能被一个进程占用（资源本身是独占的，不能共享）。
  2. 请求和保持条件：进程已经持有至少一个资源，同时又在请求其他资源。
  3. 不可抢占条件：进程已经获得的资源不能被其他进程或系统强行剥夺，只能由持有者自己主动释放。
  4. 循环等待条件：存在一个进程-资源的循环等待链，比如进程 A 等进程 B 持有的资源，进程 B 又在等进程 A 持有的资源。

一个具体的死锁场景：进程 1 持有打印机、请求扫描仪，进程 2 持有扫描仪、请求打印机——两者互相持有对方需要的资源，又都不肯放手，形成循环等待，从此都卡死不动。

死锁预防的思路是从根本上破坏四个必要条件之一，让死锁根本没有发生的可能：

  • 破坏互斥条件：允许资源被多个进程共享。例：只读文件可以被多个进程同时打开访问，不需要互斥。
  • 破坏请求和保持条件：要求进程请求资源前必须先释放已持有的资源，或者干脆采用”一次性分配”策略——进程开始执行前必须一次性申请到运行期间需要的全部资源。
  • 破坏不可抢占条件：允许系统强制抢占进程已持有的资源。例：当某进程请求资源失败时，系统可以抢占它已经拿到的资源分给别人。
  • 破坏循环等待条件：给资源统一编号，要求进程只能按编号递增的顺序申请资源，这样就不可能出现”A 等 B、B 又等 A”这种环。

死锁的完整处理策略分为四类：

  1. 死锁预防（Deadlock Prevention）：如上所述，通过破坏必要条件从根源上避免死锁，代价是限制了资源分配的灵活性。
  2. 死锁避免（Deadlock Avoidance）：不限制资源分配方式，而是在每次分配前动态检查系统会不会进入不安全状态，最经典的是银行家算法（见下文）。优点是不需要事先限制资源分配方式，缺点是需要预先知道每个进程的最大资源需求，且计算开销较大。
  3. 死锁检测（Deadlock Detection）：不做任何限制，允许死锁真的发生，然后定期检查系统状态是否已经死锁。常用资源分配图检测环路，或用定期检测算法模拟资源分配过程来判断。优点是不限制资源分配，缺点是检测本身消耗系统资源，且检测到死锁后还需要进一步处理。
  4. 死锁解除（Deadlock Recovery）：检测到死锁后采取恢复措施，常见做法是终止进程（选择一个或多个死锁进程强制终止，释放其资源）或资源抢占（强制回收死锁进程持有的资源分给别人）。选择终止或抢占哪个进程时，通常会综合考虑进程优先级、已运行时间、资源占用情况，以最小化对系统整体的影响。

五、死锁产生的深层原因与真实场景

除了四个必要条件这个理论刻画，死锁在实践中往往可以归结为四类具体原因：

  • 资源竞争：多个进程争用数量有限的资源，这是死锁的物质基础。
  • 推进顺序不当：进程之间的执行顺序安排不合理，导致互相等待。
  • 资源分配策略问题：系统缺乏有效的死锁预防或避免机制。
  • 程序设计缺陷：开发者在写代码时没有考虑资源获取的先后顺序。

几个真实世界里死锁高发的场景：

数据库系统：事务 A 锁定了第 1 行、请求锁第 2 行；事务 B 锁定了第 2 行、请求锁第 1 行——两个事务互相等待对方释放锁，形成死锁。解决方案通常是两阶段锁定协议，或者由数据库引擎的死锁检测器发现环路后主动回滚其中一个事务。

操作系统资源管理：进程 1 持有打印机、请求扫描仪；进程 2 持有扫描仪、请求打印机。解决方案是对资源做有序分配——规定所有进程必须先申请打印机再申请扫描仪，杜绝反向申请的可能。

多线程编程：线程 A 按 lock(m1) → lock(m2) 的顺序加锁，线程 B 按 lock(m2) → lock(m1) 的顺序加锁——如果 A 刚拿到 m1、B 刚拿到 m2，两者就会互相等待对方释放。解决方案是建立锁的层次结构，规定所有代码路径必须按照同一个固定顺序获取多把锁。

分布式系统：多个节点互相等待对方的响应或释放的资源，本质和单机死锁一样，只是资源分布在了不同节点上，检测和恢复的难度更高。

死锁常和另外两个概念混淆，值得专门辨析一下：

  • 死锁：进程被阻塞，彻底不做任何事，永远卡住。
  • 活锁：进程仍在运行、状态在变化，但始终没有实质性进展——类比两个人在走廊相向而行，同时向同一侧让路，结果还是撞上，反复调整却谁都过不去。
  • 饥饿：进程长期得不到所需资源，但理论上有获得资源、继续推进的可能（比如低优先级进程在优先级调度下一直被插队，但不是完全没有机会）。

实际开发中预防死锁常用的手段：锁顺序——所有线程按相同顺序获取多把锁；锁超时——尝试获取锁时设置超时时间，超时就放弃并回退；锁粒度——尽量缩小锁保护的范围，减少持锁时间和锁的数量；无锁编程——用原子操作或无锁数据结构规避锁本身；层级锁——显式定义锁的获取层级，强制自上而下获取。

六、银行家算法

银行家算法由 Dijkstra 提出，是一种用于动态资源分配的死锁避免算法（注意区分于死锁预防）。核心思想：每次有进程申请资源，系统都要实时判断”如果批准这次申请，系统是否还能找到一种让所有进程都顺利跑完的分配顺序”；只有在分配后系统仍处于安全状态时才批准，否则拒绝或者让进程继续等待。这个类比来自银行放贷——银行只有在确认放贷后仍有能力应对所有储户提款需求时才会放款。

算法依赖四个数据结构：

  • Available[m]：系统当前每种资源的可用数量，随分配和回收动态变化。
  • Max[n][m]：n 个进程各自对 m 类资源的最大需求量，进程运行前必须提前声明。
  • Allocation[n][m]：每个进程当前已经占有的各类资源数量。
  • Need[n][m]：每个进程完成任务还需要的资源数量，Need[i][j] = Max[i][j] - Allocation[i][j]。

处理一次资源请求 Request_i 的步骤（进程 Pi 申请资源）：

  1. 若 Request_i[j] ≤ Need[i][j]，进入下一步；否则说明申请量超过了当初声明的最大需求，直接判定请求失败。
  2. 若 Request_i[j] ≤ Available[j]，进入下一步；否则说明系统当前没有足够的空闲资源，Pi 必须等待。
  3. 系统先试探性分配资源，更新三个数据结构：
Available[j]      = Available[j] - Request_i[j];
Allocation[i][j]  = Allocation[i][j] + Request_i[j];
Need[i][j]        = Need[i][j] - Request_i[j];
  1. 调用安全性算法检查试探性分配之后系统是否仍处于安全状态。如果安全，这次分配就正式生效；如果不安全，撤销刚才的试探性分配，恢复原状态，让 Pi 继续等待。

安全性检查算法：

  1. 初始化两个向量：Work[m] = Available[m]（可用于维持进程运行的资源量）；Finish[n] 全部置为 FALSE（表示尚未确认某进程能顺利跑完）。
  2. 在所有 Finish[i] == FALSE 的进程里，找一个满足 Need[i][j] ≤ Work[j] 的进程 Pi（即当前剩余资源足够它跑完）。找不到就跳到第 4 步。
  3. 假设 Pi 能顺利运行完毕并释放它占有的全部资源：Work[j] = Work[j] + Allocation[i][j]，把 Finish[i] 置为 TRUE，回到第 2 步继续找下一个满足条件的进程。
  4. 如果最终所有进程的 Finish[i] 都为 TRUE，说明存在一个安全序列，系统处于安全状态，允许本次分配；只要有一个进程始终找不到满足条件的机会，系统就处于不安全状态，本次分配不能批准。

优缺点：优点是能严格避免死锁、保证系统安全，资源利用率也比”一次性分配所有资源”这类死锁预防策略更高。缺点也很实际：需要进程预先声明最大资源需求，现实场景里这个需求量往往难以准确预估或动态调整；每次请求都要跑一遍安全性检查，遍历所有进程，时间复杂度为 O(n²)，计算开销不小；而且它假设资源可以被安全地”暂不分配、让进程等待”，因此不适用于不可抢占资源（比如打印机这类独占设备一旦占用就无法中途插队检查）。
