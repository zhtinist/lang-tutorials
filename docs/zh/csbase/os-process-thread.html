操作系统基础与中断异常

操作系统是硬件和应用程序之间的一层系统软件，管理 CPU、内存、外存、I/O 设备等有限资源，同时向上给应用程序提供统一的服务接口。这一篇从操作系统的基本特征讲起，过渡到进程线程的划分、进程间通信、几种调度算法及其应用场景，再到用户态/内核态的权限分层，最后讲清楚中断和异常这一对”CPU 获取控制权的唯一方式”。

一、操作系统基础

操作系统（Operating System）是介于硬件资源和应用程序之间的系统软件，控制和管理整个计算机系统的硬件和软件资源，调度计算机的工作与资源分配，进而为用户和其他软件提供服务——操作系统是计算机系统中最基本的系统软件。一个有助于理解的问题是：如果没有操作系统，你手里的 PC 还能做什么？答案是几乎什么都做不了，因为所有硬件访问都要经过它。

操作系统的四大特征：

  • 并发：并发指两个或多个事件在同一时间间隔内发生，计算机系统中同时存在多个运行中的程序，具有处理和调度多个程序同时执行的能力。要注意并发和并行的区别——并发指同一时间间隔，并行指同一时刻；单核 CPU 上多个进程”同时”运行，本质是并发（时间片轮流），只有多核才能实现真正的并行。
  • 共享：系统中的资源可以供内存中多个并发执行的进程共同使用，分两种情况——互斥共享：一段时间内只允许一个进程访问该资源，这种资源称为临界资源（例如打印机，两个进程不能同时往打印机送数据）；同时访问：一段时间内允许多个进程”同时”访问，这里的”同时”通常是宏观上的，微观上仍是交替进行（例如多个进程读同一个只读文件）。
  • 虚拟：把一个物理上的实体转化为若干逻辑上的对应物，比如一个物理 CPU 通过分时被虚拟成多个逻辑 CPU 供多个进程”独占”使用。
  • 异步：进程的执行并不是一贯到底的，而是以不可预知的速度向前推进——同一个进程在两次运行之间，走到哪一步、花了多久是不确定的。

操作系统的四大功能：

  1. 资源分配与回收：计算机重要的硬件资源无非 CPU、内存、硬盘、I/O 设备，这些资源总是有限的，管理问题最终归结为分配和回收两件事。分配体现在：多个进程同时请求 CPU 时该给谁（进程调度）？内存不够了怎么办？A 进程非法访问了 B 进程的内存地址怎么办？内存的内碎片、外碎片问题如何处理？回收则要考虑内存回收后如何合并等问题。
  2. 为应用程序提供服务：操作系统把硬件操作封装起来，提供统一接口（系统调用）供开发者调用。如果没有操作系统，应用程序要直接面对硬件，除了编程困难，使用不当还可能直接损坏硬件。
  3. 应用程序管理：控制进程的整个生命周期——进程开始时的环境配置和资源分配、进程结束后的资源回收、进程调度等。
  4. 内核四项能力：进程调度能力（管理进程、线程，决定谁使用 CPU）；内存管理能力（决定内存的分配和回收）；硬件通信能力（管理硬件，为进程和硬件之间提供通信）；系统调用能力（应用程序请求更高权限的服务时，通过系统调用作为用户程序和操作系统之间的接口）。

操作系统的双重角色：一是管理者——分为 CPU 管理、内存管理、外存管理、IO 管理，以及维护自身的健壮性（鲁棒性，即使被粗鲁地对待也能正常运行）和安全性；二是魔术师——让每个进程都觉得自己独占了 CPU 和整片物理内存，而实际上每个进程只是在某个时间段内占用 CPU，也只占用了实际内存中很小的一部分。

用户程序与操作系统的关系是相互调用的：从操作系统的角度看，计算机启动后第一个运行的软件就是操作系统，之后所有进程都运行在它之上，使用它提供的服务，同时被它监控，进程结束后资源也由它回收；从进程的角度看，进程调用操作系统提供的服务来实现自己的功能。

二、进程和线程的区别

进程（Process）是计算机中一个执行的程序实例，每个进程对应一个运行中的程序，是操作系统资源分配的最小单位——在没有引入线程概念的操作系统中，同时也是调度的最小单位。线程（Threads）是比进程更小的概念，也称”轻量级进程”（Light Weight Process，LWP），是对进程的进一步细分：一个进程可以同时拥有多个线程，靠多线程实现程序的并发执行，而不必依赖多进程。

两者的对比：

维度 进程 线程
调度单位 引入内核级线程后不再是调度最小单位 是调度的最小单位
资源分配 始终是资源分配的最小单位 只拥有少量资源（来自所属进程）
并发性 多进程间可并发执行 一个进程内多线程也能并发执行
独立性 进程间默认不共享全局变量，拥有独立地址空间 线程间只有少数资源不共享（如线程的栈区）
系统开销 进程通信、进程切换开销大 线程通信、线程切换开销小
多处理机 单个进程只能运行在一个处理机上 内核级线程可以充分利用多处理机
协同工作 进程之间互不影响 用户级线程阻塞会拖累整个进程的执行

进程有四个主要特点：

  1. 动态性：从创建到消亡是动态的，具有生命周期。
  2. 并发性：多个进程并发执行时表现出三个特性——间断性（协同完成同一任务的进程需要同步，进而导致暂停）；失去封闭性（并发进程共享系统资源，任意进程都可能改变某资源的状态从而影响其他进程）；不可再现性（相同的初始条件下，并发执行的结果可能不同）。失去封闭性导致了不可再现性，这是理解这三点关系的关键。
  3. 独立性：进程能独立运行，是资源分配的最小单位，各进程获得的资源独立于其他进程。
  4. 异步性：进程以不可预知的速度向前推进——这是进程并发性带来的直接后果（进程的并发性导致了进程的异步性）。但通过同步与互斥机制，可以在异步性的前提下依然得到确定、可再现的结果。

在没有引入线程概念时，进程有两个特点：① 是资源所有权的最小单位，拥有对内存、I/O 通道、I/O 设备等资源的控制权和所有权；② 是调度/执行的最小单位，是可以被内核调度的独立实体。线程可以看作是在”调度/执行”这一属性上对进程的进一步细分——引入线程前，进程是调度的最小单位；引入由内核支持的内核级线程后，线程才成为调度的最小单位。

线程的实现方式分两类：

  • 用户级线程（ULT）：线程的管理完全由应用程序实现，在用户空间完成，操作系统感知不到线程的存在。这种方式下，系统调度的最小单位依然是进程，线程的调度由其所在进程自行实现。
  • 内核级线程（KLT）：需要操作系统内核支持，创建、阻塞、撤销和切换都在内核空间完成，内核通过 TCB（线程控制块）来感知和控制线程。这种方式下，线程才是系统调度的最小单位。

引入线程带来四点优势：

  1. 进一步提高并发性：单处理机系统中，线程模型能把同一进程内的 CPU 计算和 I/O 访问分离开并发执行；多处理机系统中，每个内核级线程都能占用一个处理机，充分发挥多处理机的优势。
  2. 共享地址空间与可用数据：同一进程内的线程可以直接共享数据而不需要经过内核，速度上有很大优势。
  3. 更轻量级：很多操作系统中，创建一个线程比创建一个进程快 10~100 倍，线程的切换和撤销也远比进程快。
  4. 更好的交互性：线程能提高图形界面程序的交互性，避免程序整体”卡死”——比如一个耗时的计算任务放在后台线程执行，主线程仍能响应用户点击。

三、进程间通信方式

进程间通信主要有五种方式：

  1. 信号量机制（Semaphore）：进程通过 P/V 操作控制信号量，用于解决同步和互斥问题，适合需要同步的场景，比如避免竞争条件和死锁。信号量本身是一种同步通信机制，支持两种原子操作：P()（等待，申请资源不够则阻塞）和 V()（信号，释放资源并唤醒等待者）。
  2. 共享存储机制（Shared Memory）：允许多个进程直接访问同一块内存区域，是效率最高的进程间通信方式之一。又可细分为两种：共享数据结构——进程间共享同一数据结构，需要编程人员自己处理同步互斥问题，传输效率较低；共享存储区——操作系统在内存中开辟一块共享区域供多个进程读写，传输效率高。进程要存取共享存储区时，会把自己的虚地址空间映射到该区域，并向操作系统提出申请。
  3. 消息传递机制（Message Passing）：依赖操作系统内核支持，通过消息队列或信箱传递数据，消息以数据块形式传输，支持不同类型数据，适用于无关进程之间的通信。实现上需要分别实现 Send 和 Receive 两个原语，又分两种方式：直接通信——发送进程直接把消息发送给接收进程，挂载到接收进程的消息队列上；间接通信——操作系统额外创建一片空间存储各种消息，类似一个”信箱”，发送和接收进程都依赖这个中间实体，因此也称”信箱通信模式”，在计算机网络中被广泛运用。
  4. 管道通信机制（Pipeline）：适合简单数据传输，分两类。匿名管道：使用一种共享文件（“pipe 文件”）实现，连接一个读进程和一个写进程，写进程以字节流形式把数据送入管道，读进程从管道读出，是半双工通信（数据单向流动），适用于父子进程或兄弟进程之间，在 UNIX/Linux 中用 pipe() 系统调用创建。命名管道（Named Pipe/FIFO）：具有文件名，可以在无关进程之间使用，用 mkfifo() 系统调用创建。
  5. 套接字机制（Socket）：一种网络通信机制，可以在不同主机上的进程之间通信，适合分布式系统。通信方式可以是面向连接的（TCP）也可以是无连接的（UDP）。

操作系统要实现管道机制，需要提供三种支撑：同步机制、互斥机制、通信双方确定对方存在的机制。由此管道具备以下特点：

  1. 同步性：写进程写入一定量数据后进入阻塞，等读进程读出后被唤醒；读进程把数据读完后也进入阻塞，等写进程写完后被唤醒。
  2. 互斥性：一个进程正在读/写管道时，其他想读/写的进程必须等待。
  3. 存在确认：通信双方需要先确定对方存在，否则会陷入阻塞。
  4. 固定缓冲区：管道是一个固定大小的缓冲区（比如 4KB），在内核中实现，大小不受磁盘容量影响。
  5. 借助文件系统实现：管道本质是一个共享文件，读进程把管道视为输入文件，写进程视为输出文件，因此可以复用文件系统的机制来实现。
  6. 一次性读取：数据一旦被读取就会被抛弃，不能重复读。
  7. 半双工：某一时刻数据只能单向传输，如果要实现全双工（双向同时传输），需要用两个管道。

当多个进程读写同一个管道时可能出现读写错乱，常见解决方案：① 只允许一个管道对应多个写进程和一个读进程；② 允许多个写进程和多个读进程，但系统让各个读进程轮流从管道中读取数据。

四、进程调度算法

进程调度算法解决的是”多个就绪进程排队等 CPU，该先给谁”的问题，常见的有七种：

1. 先来先服务（FCFS, First-Come First-Served）：也叫 FIFO，进程按到达顺序进入就绪队列，CPU 依次执行，非抢占式——一旦进程开始执行就要跑到完成才释放 CPU。适用于批处理系统、任务执行时间差异不大的场景。优点是实现简单、公平性较高；缺点是长作业会阻塞短作业（即”饥饿”现象），平均等待时间长，不适合交互式系统，也没有考虑不同进程的紧急程度差异，天然偏向处理器密集型和长进程。

举个具体例子：三个进程 P1（执行时间 20ms）、P2（执行时间 3ms）、P3（执行时间 3ms）依次到达，FCFS 下 P2 和 P3 分别要等 20ms 和 23ms 才能开始执行，即使它们本身只需要 3ms 就能跑完——这就是长作业”堵车”导致后面短作业陪等的典型场景，业内称为 convoy 效应（车队效应）。

2. 短进程优先（SPF/SRT）：SPF（Shortest Process First，非抢占式）——在就绪队列中选预估处理器使用时间最短的进程执行（作业调度里对应称短作业优先 SJF）；SRT（Shortest Remaining Time，抢占式）——选剩余运行时间最短的进程执行，如果运行过程中来了一个需要时间更短的进程，会立即抢占 CPU，当前进程状态由执行态退回就绪态。适用于批处理系统、短作业较多的场景。SPF 的优点是：如果调度时刻待调度进程都同时可运行（或几乎同时到达），SPF 的平均等待时间和平均周转时间是最优的；缺点是需要预估进程的运行时间，可能估算不准，或者进程”谎报”运行时间骗取优先执行，长作业也可能被”饿死”。SRT 在 SPF 基础上进一步优化了平均等待时间，但需要频繁计算剩余时间，开销更大。

沿用上面的例子：如果换成 SPF/SRT，P2、P3 会先于 P1 执行，三个进程的平均等待时间明显缩短——这正是”短作业优先”这一策略的价值所在，但代价是必须提前知道（或预估）每个进程要跑多久。

3. 优先级调度算法（PSA, Priority Scheduling Algorithm）：每个进程分配一个优先级，CPU 执行优先级最高的进程，可以是抢占式也可以是非抢占式。优先级又可分为静态优先级（调度之初就确定，运行期间不变）和动态优先级（运行过程中动态调整）。适用于实时系统或需要区分任务重要性的场景，比如操作系统内核任务通常给予比普通用户进程更高的优先级。优点是灵活，缺点是低优先级进程可能被饿死，动态调整优先级还会增加开销。

4. 高响应比优先（HRRN, Highest Response Ratio Next）：综合等待时间和运行时间来调度，响应比 = (等待时间 + 运行时间) / 运行时间。随着等待时间增加，响应比会变大，优先级也随之提高，这样短作业本来响应比就高（运行时间是分母），而长作业等得越久响应比也会慢慢追上来，不至于被无限期饿死。适用于批处理系统、任务执行时间差异较大的场景，兼顾了公平性和效率，代价是每次调度都要计算响应比，开销较大。

5. 时间片轮转（RR, Round Robin）：仅用于进程调度。每个进程分配一个时间片（比如 10ms），系统按 FCFS 维护就绪队列，时间片用完就把当前进程放回队尾，调度下一个进程。这样每个进程都能公平地使用处理器，也保证了响应时间。适用于分时操作系统、交互式系统（如桌面操作系统）。优点是公平性高；缺点是时间片设得过大就退化成 FCFS，设得过小又会因为频繁切换增加系统开销。

6. 多级队列调度（Multilevel Queue Scheduling）：仅用于进程调度。把就绪队列拆成多个，按类型或优先级把进程分配到不同队列，每个队列可以采用不同的调度算法（比如批处理队列用 FCFS，交互队列用 RR），队列之间也有优先级高低。在多处理器系统中，还可以给每个处理器指定一个就绪队列，便于把需要协作的一组线程/进程分配到同一队列同时获得资源。适用于任务类型多样的混合系统（既有批处理又有交互任务）；缺点是低优先级队列的进程可能被饿死。

7. 多级反馈队列调度（Multilevel Feedback Queue Scheduling）：仅用于进程调度，也是现代通用操作系统（Linux、Windows）实际使用的调度思路。把就绪队列分成多个子队列，依次分配递减的优先级，第一个队列优先级最高；同时高优先级队列的时间片更小，低优先级队列的时间片更大（避免低优先级任务被频繁打断切换）。新进程创建后先进入第一个队列末尾，按 FCFS 调度；如果一个时间片内没跑完，就降级到下一个队列，如此反复，直到降到最低优先级队列后不再降级，改用时间片轮转调度。调度顺序上，只有第 1 到 i-1 级队列都没有就绪进程时，才会调度第 i 级队列；如果正在运行第 i 级队列的进程时，第一级队列突然来了新进程，会立刻发生抢占式调度，被抢占的进程重新放回第 i 级队列末尾。适用于通用操作系统；优点是能较好满足各类进程的需求（很多现代操作系统的调度算法都是 MLFQ 的变体），缺点是实现复杂、开销较大。

五、调度算法的分类体系、性能指标与应用场景

上面七种算法可以按目标场景归成四类：批处理调度（FCFS、SJF、HRRN，注重吞吐量）、交互式调度（RR、优先级调度，注重响应时间）、实时调度（EDF、RMS，满足时间约束）、混合调度（MLFQ，自适应多种负载）。

评价一个调度算法好坏，通常看五个指标：周转时间（从提交到完成的总时间）、响应时间（从提交到首次得到响应的时间）、吞吐量（单位时间完成的进程数）、公平性（各进程获得 CPU 时间的均衡程度）、CPU 利用率（CPU 忙碌时间占比）。

各算法的横向对比：

调度算法 抢占性 公平性 响应时间 吞吐量 实现复杂度 主要特点
FCFS（先来先服务） 非抢占 高 差 中 低 简单公平；可能产生 convoy 效应；对长作业有利
SJF（短作业优先） 非抢占 低 好 高 中 最小化平均等待时间；可能饿死长作业；需预知执行时间
SRTF（最短剩余时间优先） 抢占 低 很好 高 高 SJF 的抢占式版本；响应时间优秀；实现复杂度高
RR（时间片轮转） 抢占 高 好 中 中 公平性好；时间片大小影响性能；适合交互式系统
优先级调度 可选 低 好 高 中 支持优先级区分；可能饿死低优先级；可配置抢占性
MLFQ（多级反馈队列） 抢占 中 很好 高 高 自适应调度；平衡响应和吞吐；防止饿死机制
CFS（完全公平调度） 抢占 很高 很好 高 很高 红黑树管理进程；基于 vruntime；高度公平

各算法的典型应用场景：

  • FCFS：批处理系统、简单嵌入式系统、教学演示、负载极轻的服务器。
  • SJF/SRTF：已知作业长度的批处理任务、科学计算调度、编译服务器等需要最小化平均等待时间的场景。
  • RR：分时操作系统、交互式系统（桌面、服务器）、需要公平性的多用户环境。
  • 优先级调度：实时系统、关键任务系统、有明确优先级区分的应用、操作系统内核任务调度。
  • MLFQ：现代通用操作系统（Windows、部分 macOS 版本）、混合型工作负载（交互式+批处理并存）。
  • CFS：Linux 桌面和服务器系统、需要高度公平性的环境、虚拟化平台、多核系统。CFS 用红黑树管理所有可运行进程，按每个进程的 vruntime（虚拟运行时间，累计获得 CPU 时间的加权值）排序，每次调度总是选 vruntime 最小的进程运行，天然地把 CPU 时间摊得很均匀。

几个高频追问：

什么是 convoy 效应？如何避免？ 一个长进程堵住了后面一串短进程的执行，导致短进程平均等待时间飙升，根源在于 FCFS 对长进程更”友好”、对短进程不利。解决办法是换用抢占式调度（RR、SRTF），或者给单个进程设置最大执行时间限制，防止一个任务长期霸占 CPU。

MLFQ 如何防止进程被饿死？ 三个机制：优先级提升——低优先级进程等待足够长时间后提升回高优先级队列；时间片调整——低优先级队列给更大的时间片，保证一旦轮到就能获得足够多的 CPU 时间；周期重置——定期把所有进程重新放回最高优先级队列，重置整个调度历史。

实时调度中 EDF 和 RMS 的区别？ EDF（最早截止时间优先，Earliest Deadline First）：动态优先级，谁的绝对截止时间最早就先调度谁，理论上 CPU 利用率可以达到 100%；RMS（速率单调调度，Rate Monotonic Scheduling）：静态优先级，任务周期越短优先级越高，可调度性有一个固定上限——CPU 利用率不超过约 69% 时才能保证所有任务都能按时完成。RMS 适合周期固定的任务集，EDF 适合周期动态变化的场景。

六、作业调度、内存调度、进程调度的区别

这三者是操作系统调度体系的三个不同层级，分别对应”进入系统、内存驻留、CPU 执行”三个阶段：

1. 作业调度（高级调度 / 长程调度）：从外存的后备队列中挑选作业调入内存，并为其创建进程，也称长程调度或接纳调度。调度频率很低（几分钟到几小时一次），控制的是系统的并发度（内存中同时存在的进程数量），决策因素包括作业类型、资源需求、优先级。调度目标是平衡系统负载、提高吞吐量、满足不同用户需求、合理利用资源。具体例子：把 CPU 密集型作业和 IO 密集型作业混合调度，避免同类资源的争抢。

2. 内存调度（中级调度 / 交换调度）：内存紧张时，把部分进程暂时换出到外存（交换区），等内存有空闲或进程可以运行时再换回来。调度频率适中（秒级到分钟级），通过”交换”（Swapping）实现，用于解决内存资源竞争。这里涉及两种状态：就绪状态（进程在内存中，等待 CPU）和就绪挂起状态（进程被换出到外存，但本身处于可运行状态）。触发条件包括内存不足、进程长时间阻塞、系统负载调整需求。

3. 进程调度（低级调度 / 短程调度）：从就绪队列中挑一个进程分配 CPU 时间片执行，也称短程调度或 CPU 调度。调度频率极高（毫秒级），要求调度开销必须很小，实现进程间的快速切换，一般由调度器（Dispatcher）实现。调度目标是最大化 CPU 利用率、最小化响应时间、保证公平性、满足实时性要求，具体算法就是上面讲的 FCFS、SJF、优先级调度、RR、MLFQ 等。

三者协同工作：作业调度决定”哪些程序能进内存变成进程”，内存调度决定”进程暂时是否留在内存里”，进程调度决定”内存里的进程谁先用 CPU”。

作业调度在现代操作系统中还存在吗？ 答案是仍然存在，只是形式发生了变化。传统形式是批处理系统里用户提交作业、系统按队列处理（如早期大型机系统）；现代演变形式则转移到了更高层级——云计算和集群调度工具（Kubernetes、YARN、Slurm）承担了传统作业调度的角色，桌面/移动系统里”用户启动一个应用”本质上也是一种隐式的作业调度，还结合了应用沙箱和资源限制。现代作业调度的特征是即时性更强（用户期望立即响应而非排队）、交互性更强（图形界面、实时反馈）、和虚拟化容器化结合更紧密、策略更多样（公平调度、优先级、资源预留、抢占）。这个变化的根本原因是硬件性能大幅提升、资源不再极度稀缺，计算模式从批处理转向了交互式，但在大数据处理、科学计算等领域，传统意义上的作业调度依然活跃。

三者的具体适用场景：

  • 作业调度：批处理系统（银行交易批处理、科学计算任务队列、数据仓库 ETL 作业、报表生成）、大型服务器环境（高性能计算集群、云计算资源调度、Hadoop/Spark 这类分布式计算框架、Slurm/PBS 这类作业管理系统）——共同点是需要控制并发作业数、管理作业间依赖、做资源预留和优先级管理。
  • 内存调度：内存资源紧张的环境（移动设备多任务、嵌入式系统、虚拟机内存超分配）、工作集管理（数据库缓冲池、Web 缓存、文件系统页面缓存、垃圾回收器的内存整理）、虚拟内存系统（页面交换、工作集修剪、内存压缩）。
  • 进程调度：通用操作系统（Windows 的多级反馈队列、Linux 的 CFS、macOS 的 Grand Central Dispatch）、实时系统（VxWorks、QNX 这类嵌入式实时操作系统，工业控制、航天、医疗设备）、特殊需求系统（交互式系统要快速响应、服务器系统要高吞吐、多媒体系统要保证带宽、移动设备要节能）、多核系统（负载均衡、缓存亲和性、NUMA 优化）。

七、处理机的两种状态

处理机（CPU）在操作系统中主要运行在两种状态：核心态（Kernel Mode）和用户态（User Mode）。核心态又称特权态、管态、系统态，拥有最高特权级别，可以执行所有指令，包括特权指令（如开关中断、修改页表、直接 I/O 操作），能访问整个物理内存地址空间（包括内核空间和用户空间），可以直接操作所有硬件资源（设备控制器、中断控制器、时钟）。用户态又称普通态、目态，特权级别受到严格限制，只能执行非特权指令——一旦尝试执行特权指令会触发保护异常，所有硬件操作都必须通过操作系统提供的接口间接完成。

这两种状态的分离靠硬件机制实现，包括模式位、内存保护单元、特权指令检查等。从用户态切换到核心态有三种途径：系统调用（应用程序主动请求内核服务）、中断（外部设备请求服务）、异常（程序错误或特殊条件触发）；从核心态返回用户态则通过中断返回指令或进程上下文切换完成。

一个具体的切换例子：用户态程序调用 read()、write()、fork() 等库函数时，这些函数内部会触发特殊的软中断指令或快速系统调用指令，导致 CPU 从用户态切换到核心态，由内核代为执行真正的特权操作，执行完毕后再切回用户态继续跑用户代码。

模式切换的开销分两部分：直接开销来自硬件操作本身——保存和恢复用户态上下文需要操作数十个寄存器，切换栈指针到内核栈，更新 CPU 模式位和控制寄存器，刷新 TLB 或切换地址空间 ID；间接开销往往更显著——TLB 失效导致后续内存访问需要重新走一遍页表遍历，用户态和内核态数据混合污染缓存导致命中率下降，分支预测失效造成流水线被清空，现代 CPU 的推测执行也会被打断。这也是为什么频繁的系统调用、频繁的用户态/内核态切换会明显拖慢程序性能。

八、用户态和内核态

用户态是 CPU 运行用户程序的一种模式，权限较低，不能直接访问硬件资源，需要通过系统调用（System Call）请求内核态的服务。内核态是 CPU 运行操作系统内核的一种模式，拥有最高权限，可以直接访问硬件资源，负责管理进程调度、内存管理、设备驱动等核心功能。

具体来说，当在用户空间执行应用程序自己的代码时，CPU 处于用户模式，只能运行部分指令、只能访问用户空间这部分内存，应用程序的代码和数据也保存在用户空间。当用户程序调用系统 API（即发生系统调用）时，会暂停用户程序的执行，转而执行内核代码、访问内核空间，这时 CPU 切换到内核模式，可以运行全部指令、访问全部内存空间，对硬件有完全的访问权限。

需要强调一点：内核态通常不会直接运行用户程序（即便内核态理论上可以访问用户空间），而是通过系统调用机制安全地与用户空间交互。当用户程序需要执行特权操作时，它通过系统调用请求操作系统服务，这个请求触发从用户态到内核态的切换，CPU 执行操作系统提供的服务代码完成请求的操作，执行完再切回用户态继续跑用户程序。这种设计确保了系统的安全性与稳定性，同时实现了用户程序和内核的隔离——用户程序即使写错了代码，也很难直接搞崩整个系统内核。

从系统分层的角度看，操作系统位于用户层和硬件层之间，向上提供服务、向下管理资源，是计算机系统各类软硬件资源的管理者。进程间的切换无法直接靠硬件实现，因此需要操作系统这一层系统软件来对处理器和硬件资源做抽象改造——这一层系统软件本身就是一组运行在内核态的程序模块。

硬件层面的实现依据是 CPU 中的程序状态字寄存器（PSW）：其中有一个二进制位，可以用 1 表示”内核态”、0 表示”用户态”（也可以反过来约定），CPU 每执行一条特权指令前都会检查这个位，据此决定是否允许执行。

九、什么是中断和异常

中断和异常都是 CPU 响应特殊事件的机制，会打断当前的执行流程，统称为中断向量（Interrupt Vector）机制。两者的核心区别在于事件来源：

  • 中断（Interrupt）：来自 CPU 外部的异步事件，比如 I/O 设备请求、时钟信号，与 CPU 当前正在执行的指令无关、随时可能发生。中断具有三个特性：异步性（与当前执行指令无关）、可屏蔽性（可以通过中断屏蔽位暂时禁止某些中断）、可嵌套性（高优先级中断可以打断低优先级中断的处理）。中断又分两类：硬件中断——可屏蔽中断（INTR，可以通过 CLI 一类指令屏蔽）和非屏蔽中断（NMI，即使关中断也一定会被响应，比如内存奇偶校验错误这类必须立即处理的严重事件）；软件中断——由 INT 指令主动触发，比如 Linux 早期用 int 0x80 实现系统调用。
  • 异常（Exception）：由 CPU 内部执行指令时检测到的同步事件，与当前执行的指令直接相关。特性是同步性（特定指令执行必然产生）、不可屏蔽（无法通过软件屏蔽）、精确性（可以精确定位到出错的指令）。异常又分三类：故障（Fault）——可恢复的错误，比如缺页异常、除零异常；陷阱（Trap）——有意产生的异常，比如断点调试、系统调用；终止（Abort）——严重到无法恢复的错误，比如硬件故障。

两者都会触发 CPU 从用户态切换到内核态，执行对应的处理程序。也正因如此，异常和中断机制是操作系统获得 CPU 控制权的唯一方式——没有这套机制，操作系统内核就没有办法在用户程序运行的过程中插进来做调度、做资源管理。

具体的中断/异常处理机制上，一个典型例子是除零异常：CPU 执行除法指令时检测到除数为零，会触发一个故障类异常，交由异常处理程序处理——处理程序可能记录出错的指令地址（EIP），然后终止相关进程或者向进程发送 SIGFPE 信号。另一个例子是缺页异常：进程访问了一个尚未加载到物理内存的页面，CPU 检测到后触发缺页异常，这是一种可恢复的故障——操作系统会从磁盘把对应页面调入内存，然后重新执行刚才触发异常的那条指令（注意：这里断点记录的是当前指令本身，而不是下一条指令，因为这条指令根本没有执行成功）。

关于中断处理为什么要分”上半部”和”下半部”是一个常见追问：上半部（硬中断处理）要求快速响应，只做最必要的操作（比如把数据从设备寄存器搬到内存缓冲区），下半部（软中断/任务队列）负责处理真正耗时的操作，这样能减少中断被屏蔽的时间，提高系统整体的响应性——如果所有处理逻辑都堆在硬中断里做，会导致中断屏蔽期间其他中断长时间得不到响应。

中断和异常处理时，CPU 至少要保存程序计数器（PC）、处理器状态字（PSW）、以及一些关键寄存器；具体到 x86 架构会保存 EFLAGS、CS、EIP，ARM 架构则保存 CPSR 和返回地址。

页错误（缺页异常）究竟算中断还是异常？答案是异常（故障类），因为它是同步的——访问一个无效页面时会立即触发，和当前执行的指令直接相关，而且必须处理完（把页面调入内存）才能让程序继续往下走，这几点完全符合异常”同步、与指令相关”的定义，而不具备中断”外部、异步、随时可能发生”的特点。

十、中断和异常的分类细节与响应处理流程

在处理一条指令时，CPU 会在指令执行结束的那一刻判断是否存在内部异常或外部中断请求。一旦存在，就要进入异常/中断响应过程，核心任务是保存断点和程序状态、识别异常事件或中断源、转入对应的服务程序处理。

内部异常（Exception），也称内部中断或软件中断，是 CPU 执行当前指令产生的、与该指令密切相关的同步事件，进一步细分为三类：

  • 故障（Fault）：通常由指令执行本身引起，如未定义指令、越权指令、段故障、缺页故障、除数为零、浮点溢出、整数溢出等。对于可恢复的故障（如缺页故障），操作系统可以做页面调度来修复问题，然后回到发生故障的那条指令继续执行——注意此时的断点是当前指令本身，而不是下一条指令，因为当前指令并没有真正执行完。对于不可恢复的故障（如未定义指令、越权指令），操作系统只能终止当前进程。
  • 自陷（Trap）：是一种事先安排好的异常事件，通过程序里显式调用自陷指令触发，用于在用户态主动调用操作系统内核程序（比如系统调用、条件陷阱指令）。自陷异常和函数调用有点像，但不存在程序断点——自陷指令不会在用户栈上保存返回地址，执行时会有条件或无条件地转去调用内核程序，执行完后返回自陷指令的下一条指令（这一点与故障不同）。
  • 终止（Abort）：指使 CPU 无法继续执行的硬件故障，和具体指令无关，比如机器校验错、总线错误，或者异常处理过程中再次发生异常导致的”双错”。发生时当前程序无法继续执行，只能由操作系统终止，并由异常处理程序尝试重启系统。

外部中断（Interrupt）来自 CPU 外部，与具体指令无关，是随机事件——外部设备（如鼠标、键盘）向 CPU 发出中断请求，提供了外设与 CPU 交流的机制，也是重要的 I/O 方式之一。CPU 会在当前指令执行完毕后响应中断，转到对应的中断处理程序，处理完后返回到发生中断那条指令的下一条（因为被中断的指令本身已经执行完毕，这一点和处理故障时的断点位置不同）。外部中断还可以按三个维度再分类：

  • 按是否可被屏蔽：分为可屏蔽中断（关中断状态下不会被响应，属于硬件中断）和非屏蔽中断（即使关中断也会被响应，属于硬件中断）。
  • 按能否直接提供中断服务地址：分为向量中断（中断事件能直接提供中断服务程序入口地址）和非向量中断（不能直接提供，需要额外查询确定入口地址）。
  • 按处理过程能否被打断：分为单重中断（CPU 执行中断服务程序时不能被其他中断请求打断）和多重中断（执行中断服务程序时可以去响应更高优先级的中断请求，又称”中断嵌套”）。

处理流程上，异常与中断基本一致：发生中断事件时，CPU 在当前指令结束时进入中断周期做中断响应，响应过程中引出中断服务程序，再由中断服务程序执行后续的中断处理（也有例外，比如产生故障异常的那条指令本身没有执行完，但必须立即响应）。具体拆成两个阶段：

中断响应（这一阶段由硬件自动完成）：

  1. 关中断：防止处理当前中断时又冒出新的中断请求，破坏正在保存的断点、程序状态字、现场信息。
  2. 保存断点和程序状态字：断点是程序的返回地址，程序状态字包含各种状态信息，两者分别保存在 PC 和 PSW 寄存器中，CPU 会把这两个寄存器内容压栈，供后续恢复被中断进程时使用。
  3. 引出中断服务程序：CPU 识别具体的中断源，据此找到对应的中断服务程序。

中断处理（CPU 控制权已经交给操作系统）：

  1. 保护现场：保存一些通用寄存器的信息，防止接下来执行中断处理程序时把这些寄存器内容覆盖掉。
  2. 执行中断处理程序：具体的中断服务逻辑。
  3. 恢复现场：恢复保存的通用寄存器信息，重新开中断，恢复 PC 和 PSW，让被中断的进程完全恢复到原来的状态继续执行。

值得一提的是，不同计算机体系或教材对”中断”和”异常”的划分并不统一：MIPS 体系把内部异常和外部中断都统称为”异常”；X86 体系则把两者都称为”中断”，并把来自 CPU 内部的称为”内部中断”或”软件中断”，来自外部的称为”外部中断”或”硬件中断”。还有教材把内部异常里的故障和自陷归为”程序性异常”（即软件中断），把终止和外部中断归为”硬件中断”。这些命名差异不影响底层机制本身，遇到不同资料交叉引用时留意术语口径即可。

十一、中断处理的具体过程

中断是计算机系统中由硬件或软件触发的一种异步事件处理机制，它打断 CPU 当前正在执行的程序，转而执行预先定义好的中断处理程序，处理完毕后再恢复原程序的执行。整个过程可以拆成四个阶段：中断请求、中断响应、中断处理、中断返回，涉及中断控制器、中断向量表、程序状态字、现场保护与恢复等关键组件。中断机制是实现 CPU 与外部设备并行工作、提高系统效率、及时处理紧急事件的基础。

具体展开这四个阶段：

整个过程始于中断源的产生——可以是外部硬件设备（键盘敲击、网络包到达、定时器超时），也可以是内部软件条件（除零错误、页故障、系统调用请求）。当中断事件发生时，中断控制器接收并仲裁可能同时发生的多个中断请求，根据优先级决定哪个中断先被服务，然后向 CPU 发出中断请求信号。

CPU 在每条指令执行结束时都会检查是否有待处理的中断请求。如果中断是被允许的、且当前优先级允许响应，就进入中断响应周期：先完成当前指令的执行，再保存关键的处理器状态——包括程序计数器（指向下一条要执行的指令）和程序状态字（包含条件码、中断允许位等标志）；接着根据中断类型从中断向量表中查出对应中断处理程序的入口地址，同时自动关闭中断允许位（防止新的中断打断当前的响应过程）。

随后 CPU 跳转到中断服务程序开始执行，进入中断处理阶段：处理程序首先保存被中断程序的完整现场，再根据中断的具体原因执行对应的处理逻辑，处理过程中可能需要和设备控制器交互来清除中断源（比如告诉网卡”这个包我已经收到了，可以清空缓冲区”）。

处理完成后，中断服务程序恢复之前保存的现场，执行中断返回指令——恢复此前保存的程序状态字和程序计数器，CPU 由此返回被中断的程序继续执行，整个过程对原程序透明，仿佛从未被打断过。

中断机制的精妙之处在于：通过硬件自动化的状态保存与恢复，加上分层的中断优先级管理，实现了 CPU 计算与 I/O 操作的高度重叠，大幅提高了系统吞吐率和响应实时性。

从更底层的角度看，中断可以分成四类：硬中断（来自硬件设备，即 IRQ）、软中断（由 INT 指令触发）、异常（执行指令时出错，如除零、缺页）、不可屏蔽中断（NMI）（必须立即处理，无法通过软件屏蔽）。

几个常见追问：

中断和轮询的区别？ 中断是事件驱动的——设备准备好后主动通知 CPU，CPU 利用率高、响应及时；轮询是 CPU 定期主动检查设备状态，实现简单但会浪费 CPU 周期去反复查询”好了没”。现代系统通常两者混合使用：高频、紧急的事件用中断，低频、不那么紧急的场景用轮询（比如某些高速网卡在流量很大时会主动切换成轮询模式，减少频繁中断带来的开销，这也是 NAPI 一类机制的设计动机）。

中断嵌套如何处理？ 进入中断处理时会自动或手动关中断（CLI），处理完关键代码后再重新开中断（STI）；中断控制器负责管理各中断源之间的优先级——可以是固定优先级（比如 IRQ0 > IRQ1 > …），也可以是循环优先级；非屏蔽中断（NMI）可以打断包括其他中断处理过程在内的任何中断。

什么是中断描述符表（IDT）？ 这是 x86 架构下的中断向量表，包含 256 个条目，每个条目 8 字节，记录了对应中断处理程序的入口地址和权限级别，通过 LIDT 指令加载。IDT 里包含不同类型的门描述符：任务门、中断门、陷阱门，分别对应不同的中断/异常响应方式。
