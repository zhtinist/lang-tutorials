计算机网络基础与TCP详解

覆盖传输层 TCP/UDP 的核心区别、HTTP 协议的请求方法/状态码/头部字段，以及 TCP 连接管理与可靠性机制的全部细节：三次握手、四次挥手、TIME_WAIT、可靠传输、拥塞控制、Keepalive。

一、TCP 和 UDP 的区别

TCP（Transmission Control Protocol）是面向连接的可靠传输协议，UDP（User Datagram Protocol）是无连接的不可靠传输协议，两者都工作在传输层，但设计目标完全相反：TCP 用额外的开销换正确性，UDP 用放弃保证换速度。

维度 TCP UDP
连接方式 三次握手建立连接，四次挥手释放连接 无连接，直接发送数据报
可靠性 通过确认应答、超时重传、校验和确保可靠 不保证送达，可能丢包
传输顺序 序列号保证数据按序到达 不保证顺序，乱序也不会重排
传输速度 较慢（握手、确认、重传都有开销） 快（没有额外的控制逻辑）
头部开销 最小 20 字节（无选项时） 固定 8 字节
流量控制 支持（滑动窗口） 不支持
拥塞控制 支持（慢启动、拥塞避免等算法） 不支持
数据边界 面向字节流，没有消息边界 面向报文，一次 send 对应一次 recv
典型应用 HTTP、文件传输、邮件（SMTP） DNS 查询、视频会议、在线游戏、直播

为什么某些场景故意选 UDP：DNS 查询是一问一答的小数据包，用不着连接维护的开销；视频会议、直播这类实时流媒体，丢一帧不如卡一下——TCP 的重传反而会让画面延迟累积得更严重，这类场景对”实时”的需求高于对”完整”的需求，UDP 更合适。反过来，文件传输、网页加载对数据完整性要求高，宁可慢一点也不能少字节，选 TCP。

需要可靠性又想要 UDP 速度的场景（比如 HTTP/3），做法是在 UDP 之上用应用层协议（QUIC）自己实现确认、重传、拥塞控制，而不是依赖 TCP。

二、HTTP 请求方法

HTTP/1.1 定义了 8 种方法，此外 PATCH 是 RFC 5789（2010 年）后补充的扩展方法。

方法 语义 安全性 幂等性 典型场景
GET 请求指定资源，参数放在 URL 中 安全 幂等 查询数据、加载页面
POST 提交数据，数据放在请求体中 不安全 不幂等 表单提交、创建订单
PUT 全量更新资源，客户端提供完整数据 不安全 幂等 覆盖式更新用户信息
DELETE 删除指定资源 不安全 幂等 删除文章/用户
HEAD 与 GET 相同但只返回响应头，无响应体 安全 幂等 检查资源是否存在、验证链接有效性
OPTIONS 查询服务器支持的方法，或做跨域预检 安全 幂等 CORS 预检请求
TRACE 回显服务器收到的请求内容，用于调试 不安全 幂等 调试（生产环境通常禁用）
CONNECT 建立到目标服务器的隧道 不安全 幂等 HTTPS 代理隧道
PATCH 局部更新资源，只提交需要修改的字段 不安全 不幂等 修改用户昵称等单一字段

这里”安全”（safe）和”幂等”（idempotent）是两个独立的概念，不要混淆：

  • 安全指方法本身不会改变服务器上的资源状态，纯粹是只读操作。GET、HEAD、OPTIONS、TRACE 是安全的。
  • 幂等指同一个请求执行一次和执行 N 次，服务器最终状态是一样的。GET 幂等好理解（查询不会变结果）；DELETE 也是幂等的——删除一个已经不存在的资源，和删除一次的效果相同（都是”资源不存在”），所以重复调用不会产生额外副作用；PUT 幂等是因为它总是用相同的完整数据覆盖资源，写十次结果和写一次一样。POST 和 PATCH 不幂等：连续两次 POST 创建订单接口，会创建出两个订单。

TRACE 因为会把请求内容原样回显，可能被用来配合 XSS 窃取 Cookie（Cross-Site Tracing 攻击），实践中服务器和代理通常直接禁用它。

版本演进上，HTTP/1.0 只定义了 GET、POST、HEAD 三种方法；HTTP/1.1 补齐到 8 种；HTTP/2 和 HTTP/3 沿用 HTTP/1.1 的方法集合，没有新增方法，它们改进的是底层传输机制而非语义层。

三、GET 和 POST 的区别

GET 和POST 都是”请求方法”，但在实践中承担的角色差异很大，核心还是刚才那张方法表里的两行，这里展开对比：

维度 GET POST
参数位置 拼接在 URL 上（?name=value&...） 放在请求体里
长度限制 受浏览器/服务器 URL 长度限制（约 2~8KB，取决于实现） 理论上无限制，受服务器配置限制
可见性 参数出现在地址栏、浏览器历史、服务器日志中 不出现在地址栏，但仍是明文（除非 HTTPS）
缓存 可被浏览器和代理缓存 默认不缓存
幂等性 幂等 不幂等
安全性（safe） 安全，不修改服务器状态 不安全，可能修改状态
编码 只能是 ASCII，非 ASCII 字符需要 URL 编码 支持多种编码（multipart/form-data、application/json 等）

几个容易被忽视的点：

GET 参数出现在 URL 里意味着它会被写进浏览器历史记录、服务器访问日志、代理缓存，所以绝不能用 GET 传密码、Token 等敏感信息——即使走 HTTPS，URL 本身在这些留存点也是明文的。POST 把参数放进请求体，不会出现在地址栏和日志里，但这不等于”安全”，请求体内容在没有 HTTPS 的情况下依然是明文，能被抓包工具直接看到。真正的机密性保护来自 HTTPS 加密，跟用 GET 还是 POST 无关。

幂等性决定了重试策略：浏览器对 GET 请求可以放心地自动重试或做预加载，因为重复执行不会有副作用；对 POST 请求浏览器会弹出”是否重新提交表单”的确认，因为重复提交可能意味着下单两次。

在 RESTful API 设计里，GET 对应读操作、POST 对应创建操作、PUT 对应更新、DELETE 对应删除，这套约定就是建立在 HTTP 方法本身的语义（安全性、幂等性）之上的。

四、HTTP 状态码

状态码按首位数字分为 5 类，语义上代表请求处理的不同阶段和结果。

1xx 信息类

状态码 名称 含义
100 Continue 服务器已收到请求头，客户端可以继续发送请求体
101 Switching Protocols 协议切换成功，如从 HTTP 升级到 WebSocket

2xx 成功类

状态码 名称 含义
200 OK 请求已被正确处理，响应体携带结果
201 Created 请求成功且创建了新资源（典型于 POST）
202 Accepted 请求已接受但尚未处理完成（异步任务）
203 Non-Authoritative Information 返回的信息来自缓存副本而非源服务器
204 No Content 处理成功但没有内容返回（典型于 DELETE）
205 Reset Content 要求客户端重置当前文档视图（如清空表单）
206 Partial Content 返回了资源的一部分（配合 Range 请求，用于断点续传）

3xx 重定向类

状态码 名称 含义
300 Multiple Choices 资源存在多个可选表示，需要客户端选择
301 Moved Permanently 资源永久重定向到新地址，浏览器会缓存该跳转
302 Found 资源临时重定向到新地址，不缓存
303 See Other 强制客户端用 GET 方法访问另一个 URI（常见于 POST 后跳转）
304 Not Modified 资源未修改，客户端可直接使用本地缓存
305 Use Proxy 必须通过指定代理访问资源（已被现代浏览器弃用）
306 Unused 保留但已废弃，被 307/308 取代
307 Temporary Redirect 临时重定向，且要求保持原请求方法（区别于 302）

4xx 客户端错误类

状态码 名称 含义
400 Bad Request 请求存在语法或参数错误
401 Unauthorized 未提供有效身份凭证，需要认证
402 Payment Required 保留状态码，用于需要付费的场景（如部分支付网关）
403 Forbidden 已认证但无权访问该资源
404 Not Found 服务器找不到请求的资源
405 Method Not Allowed 该资源不支持请求所用的 HTTP 方法
406 Not Acceptable 服务器无法提供符合 Accept 头要求的内容格式
407 Proxy Authentication Required 需要先通过代理服务器的身份验证
408 Request Timeout 服务器等待客户端发送请求的时间过长
409 Conflict 请求与服务器当前状态冲突（如并发编辑版本冲突）
410 Gone 资源曾经存在但已被永久删除
411 Length Required 请求缺少必需的 Content-Length 头
412 Precondition Failed 请求头中的前置条件未满足（如 If-Match 校验失败）
413 Payload Too Large 请求体超过服务器允许的大小限制
414 URI Too Long 请求的 URL 超出服务器限制
415 Unsupported Media Type 服务器不支持请求携带的数据格式
416 Range Not Satisfiable 请求的范围超出了资源实际大小
417 Expectation Failed 服务器无法满足请求头中 Expect 字段的要求

5xx 服务器错误类

状态码 名称 含义
500 Internal Server Error 服务器内部错误，无法完成请求（代码异常、数据库崩溃等）
501 Not Implemented 服务器不支持实现请求所需的功能
502 Bad Gateway 网关/代理从上游服务器收到了无效响应
503 Service Unavailable 服务器过载或正在维护，暂时无法处理请求
504 Gateway Timeout 网关/代理等待上游服务器响应超时
505 HTTP Version Not Supported 服务器不支持请求所使用的 HTTP 协议版本

304 和 404 容易混淆：304 表示”资源没变，请继续用你本地那份”，这是缓存机制的一部分（配合协商缓存使用，见 network-http-advanced.md）；404 表示”资源根本不存在”，两者语义完全不同。502 和 504 都发生在有反向代理/网关的架构里：502 是上游返回了一个网关看不懂或无效的响应（比如后端进程崩溃、连接被拒绝），504 是网关压根没在超时时间内等到上游的响应（后端处理太慢）。

五、HTTP 头部字段

头部字段按作用范围分为四类。

请求字段

字段 作用
Host 指定目标域名和端口，HTTP/1.1 必需字段，用于同一 IP 上区分多个虚拟主机
User-Agent 标识客户端类型（浏览器、操作系统），服务器可据此返回适配内容
Accept 声明客户端可接受的响应内容类型（MIME 类型），如 application/json
Authorization 携带身份认证凭证，如 Bearer <token>
Cookie 携带此前服务器通过 Set-Cookie 下发的会话信息

响应字段

字段 作用
Server 标识服务器软件及版本，生产环境通常隐藏以减少信息泄露
Set-Cookie 让客户端存储 Cookie，可附加 HttpOnly（禁止 JS 读取）、Secure（仅 HTTPS 下发送）等属性
Location 重定向的目标地址，配合 3xx 状态码使用
WWW-Authenticate 告知客户端应使用的认证方式，配合 401 状态码使用

通用字段

字段 作用
Cache-Control 控制缓存行为，如 max-age=3600 表示缓存 1 小时有效
Connection 管理 TCP 连接的复用方式，HTTP/1.1 默认 keep-alive
Date 报文生成的日期时间（GMT 格式）

实体字段

字段 作用
Content-Type 声明消息体的媒体类型，如 text/html、application/json
Content-Length 消息体的字节数，用于判断响应是否接收完整
Content-Encoding 消息体的压缩编码方式，如 gzip、deflate
Last-Modified 资源最后一次修改的时间，配合协商缓存使用

这四类字段的划分逻辑是：请求字段只出现在请求报文里、描述客户端自身特性；响应字段只出现在响应报文里、描述服务端特性；通用字段两边都能用、控制传输层面的行为（连接管理、缓存策略）；实体字段描述的是消息体本身的元信息（类型、大小、编码），不管这个消息体是出现在请求还是响应中。

六、TCP 三次握手

三次握手的目的是在正式传输数据之前，让客户端和服务器互相确认”我能发、你能收，你能发、我能收”，同时同步双方的初始序列号（ISN，Initial Sequence Number）。

客户端(Client)                                服务器(Server)
    |                                              |
    |   CLOSED                              LISTEN |
    |                                              |
    |------ 第一次握手: SYN=1, seq=x ------------->|
    |   SYN-SENT                                   |
    |                                     SYN-RCVD  |
    |<---- 第二次握手: SYN=1,ACK=1, ------------- --|
    |            seq=y, ack=x+1                    |
    |                                               |
    |------ 第三次握手: ACK=1, -------------------->|
    |            seq=x+1, ack=y+1                  |
    |   ESTABLISHED                    ESTABLISHED  |
    |                                               |

第一次握手：客户端随机生成一个初始序列号 x，将 SYN 标志位置为 1，发送 SYN 报文（不携带数据，但会消耗一个序号），自身状态从 CLOSED 变为 SYN-SENT。

第二次握手：服务器收到 SYN 报文后，随机生成自己的初始序列号 y，将 SYN 和 ACK 标志位都置为 1，确认号（ack）设为 x + 1（表示”你的 x 号字节我已确认收到，下次请从 x+1 开始发”），发送这个 SYN-ACK 报文，自身状态从 LISTEN 变为 SYN-RCVD。

第三次握手：客户端收到 SYN-ACK 后，序号设为 x + 1，确认号设为 y + 1，将 ACK 标志位置为 1，发送这个 ACK 报文（此时可以顺带携带业务数据），自身状态从 SYN-SENT 变为 ESTABLISHED。服务器收到这个 ACK 后，状态从 SYN-RCVD 变为 ESTABLISHED。至此双方都确认连接建立完成，可以开始正常的数据传输。

端点 初始状态 第 1 次握手后 第 2 次握手后 第 3 次握手后
客户端 CLOSED SYN-SENT SYN-SENT ESTABLISHED
服务器 LISTEN LISTEN SYN-RCVD ESTABLISHED

为什么必须是三次，不能是两次或四次

两次握手不够：如果只握手两次（客户端发 SYN，服务器回 SYN-ACK 就直接认为连接建立），会有一个经典问题——已经失效的历史连接请求可能造成服务器资源浪费。设想这样一个场景：客户端发出第一个 SYN 报文，但因为网络拥塞被卡在某个中间节点，迟迟到不了服务器；客户端等待超时后，重新发送了第二个 SYN，这次正常完成两次握手、数据传完、连接正常释放。过了一段时间，那个滞留在网络里的第一个”旧” SYN 终于姗姗来迟到达了服务器。如果只需要两次握手就能建立连接，服务器会误以为这是一个新的连接请求，回复 SYN-ACK 并进入等待客户端发数据的状态——但客户端根本不知道这个连接的存在，永远不会给它发数据，服务器就会白白占用资源空等下去。三次握手加了这一步验证：服务器发出 SYN-ACK 后，必须等到客户端的第三次 ACK 才真正建立连接；对于这个迟到的旧连接，客户端收到服务器的 SYN-ACK 后会因为不认识这个连接而直接丢弃或回复 RST，服务器等不到第三次 ACK，超时后自行放弃这个半连接，不会产生资源浪费。

三次握手同步了双方的初始序列号：TCP 是全双工的，两个方向的数据流各自独立编号，因此双方都需要各自生成并让对方确认自己的 ISN。第一次握手客户端把 x 告诉服务器，第二次握手服务器确认 x 的同时把自己的 y 告诉客户端，第三次握手客户端确认 y——正好三次握手就能让双方都完成”我的 ISN 你收到了”的双向确认，这是保证后续数据按序号正确排列、去重的前提。

四次握手是多余的：三次握手已经完成了双向的”发送/接收能力确认”外加”双向 ISN 同步”，这两件事三次交互就能覆盖，第四次握手不会带来额外的可靠性收益，只会多引入一个 RTT 的建连延迟，没有必要。

七、TCP 四次挥手

挥手比握手多一次，本质原因是 TCP 连接是全双工的，两个方向的关闭是独立的——挥手不是”同时关闭两个方向”，而是”先关一个方向，再关另一个方向”，中间服务器那侧可能还有数据没发完。

客户端(Client)                                服务器(Server)
    |   ESTABLISHED                    ESTABLISHED  |
    |                                               |
    |------ 第一次挥手: FIN=1, seq=u -------------->|
    |   FIN-WAIT-1                                  |
    |                                    CLOSE-WAIT  |
    |<---- 第二次挥手: ACK=1, ---------------------  |
    |            seq=v, ack=u+1                    |
    |   FIN-WAIT-2                                  |
    |            (服务器可能仍在发送剩余数据)         |
    |                                               |
    |<---- 第三次挥手: FIN=1,ACK=1, ----------------|
    |            seq=w, ack=u+1                    |
    |   TIME-WAIT                          LAST-ACK  |
    |                                               |
    |------ 第四次挥手: ACK=1, -------------------->|
    |            seq=u+1, ack=w+1                  |
    |   (等待 2MSL)                          CLOSED  |
    |                                               |
    |   CLOSED                                      |

第一次挥手：客户端（主动关闭方）数据发送完毕，发送 FIN=1、seq=u 的报文段，表示”我这边没有数据要发了”，自身状态从 ESTABLISHED 变为 FIN-WAIT-1。这个状态下客户端仍然可以接收服务器发来的数据。

第二次挥手：服务器收到 FIN 后，立即回复一个 ACK=1、seq=v、ack=u+1 的确认报文，自身状态从 ESTABLISHED 变为 CLOSE-WAIT。客户端收到这个 ACK 后，状态从 FIN-WAIT-1 变为 FIN-WAIT-2。此时，客户端到服务器方向的连接已经关闭，但服务器到客户端方向可能还有数据没发完。

第三次挥手：服务器把自己剩余的数据发送完毕后，才发送 FIN=1、ACK=1、seq=w、ack=u+1 的报文段，表示”我这边现在也发完了”，自身状态从 CLOSE-WAIT 变为 LAST-ACK。

第四次挥手：客户端收到服务器的 FIN 后，回复 ACK=1、seq=u+1、ack=w+1 的确认报文，自身状态从 FIN-WAIT-2 变为 TIME-WAIT，并等待 2MSL（Maximum Segment Lifetime，报文最大生存时间）后才真正进入 CLOSED。服务器收到这个最终的 ACK 后，直接进入 CLOSED 状态。

为什么是四次而不是三次

第二次挥手（服务器对客户端 FIN 的 ACK）和第三次挥手（服务器自己的 FIN）没法合并成一次，原因是服务器收到客户端的 FIN 时，往往还有数据没发送完——它必须先应答对方”你的关闭请求我收到了”（第二次挥手），但不能立刻宣布自己也关闭（那意味着第三次挥手要等所有数据发完才能发出）。这中间的时间差，正是 CLOSE-WAIT 状态存在的意义。如果强行把 ACK 和 FIN 合并成一次挥手，服务器就必须在收到对方 FIN 的瞬间同时确定自己也没有数据要发了，这在实际场景里往往做不到，所以 TCP 挥手天然是四次而非三次（除非服务器凑巧在收到 FIN 时也刚好没有数据要发，此时 ACK 和 FIN 可以捎带在一起发送，退化成三次挥手，但这是特例不是常规流程）。

第四次挥手也是必须的：如果没有这最后的 ACK，服务器发出 FIN 后无法知道对方是否收到，一旦这个 FIN 丢失且没有重传确认机制，服务器会永远停留在 LAST-ACK 状态，无法正常释放连接。

八、TIME_WAIT 状态

TIME_WAIT 是主动关闭连接的一方，在完成四次挥手的最后一步（发出最终 ACK）之后所停留的状态，会持续 2MSL 的时长（Linux 默认对应 60 秒左右）才真正转为 CLOSED。

作用

确保最后一个 ACK 能可靠送达：如果这个最终 ACK 在网络中丢失，被动关闭方（服务器）会因为收不到确认而重传它的 FIN 报文。如果客户端发完 ACK 立刻退出、不保留任何状态，就无法响应这个重传的 FIN，服务器就会一直等不到确认、长期滞留在 LAST-ACK。TIME_WAIT 期间客户端仍然”在场”，能够重新应答收到的重传 FIN，重新发一次 ACK。

清除网络中滞留的旧数据包：网络里可能还有这条连接之前发出、尚未到达或者被路由延误的数据包。2MSL 的等待时间足以让这些滞留包因为超过其最大生存时间而被网络丢弃，避免它们在这条连接关闭之后，被一个使用相同四元组（源 IP、源端口、目的 IP、目的端口）的新连接误收，造成数据错乱。

给内核充分的时间清理连接资源：包括端口、缓冲区、连接跟踪表项等，等 TIME_WAIT 结束后才彻底释放。

为什么是 2 倍 MSL 而不是 1 倍

第一个 MSL 保证客户端发出的最后那个 ACK 有充分时间到达服务器；第二个 MSL 用来覆盖”如果那个 ACK 丢了、服务器重传 FIN”这种情况——重传的 FIN 也需要一个 MSL 的时间抵达客户端。两个 MSL 加起来，覆盖了”最坏情况下一来一回都要重试一次”的时间窗口。

如果没有 TIME_WAIT 会怎样

主动关闭方一发完最后的 ACK 就立刻释放连接、复用端口，可能导致两个问题：一是服务器那边的 FIN 万一丢失需要重传时，客户端已经不认识这个连接了，服务器可能长期卡在 LAST-ACK 无法正常关闭；二是如果本地端口很快被一个新连接复用，网络中滞留的旧连接数据包可能会被新连接错误地当作自己的数据接收，造成数据污染。

TIME_WAIT 过多的危害及应对

一台机器的可用临时端口大约只有 2.8 万个左右（默认范围通常是 32768~60999），如果某台服务器频繁发起大量短连接且都是主动关闭方，会在短时间内堆积大量 TIME_WAIT 状态占用端口，导致新连接无法分配到可用端口而创建失败；同时每个 TIME_WAIT 连接都占用一定的内核内存，数量过多也会拖累系统整体性能。

常见的解决办法：

# 内核参数调整
net.ipv4.tcp_tw_reuse = 1            # 允许将处于 TIME_WAIT 的端口重新用于新连接
net.ipv4.tcp_max_tw_buckets = 262144 # 提高 TIME_WAIT 数量上限
net.ipv4.tcp_fin_timeout = 60        # 控制 FIN_WAIT_2 的超时时间
  • 应用层用 SO_REUSEADDR 选项让新的 socket 可以绑定处于 TIME_WAIT 的地址端口。
  • 尽量使用长连接（连接池）代替频繁的短连接，从源头减少挥手次数。
  • 用负载均衡把连接压力分散到多台服务器实例上。

Linux 默认 2MSL 约 60 秒，Windows 默认更长（约 240 秒），不同操作系统的取值不完全一致，但原理相同。

九、TCP 如何保证可靠传输

TCP 的”可靠”体现在保证数据不丢失、不重复、按序到达、且没有传输错误。这是靠多个机制协同实现的：

序列号（Sequence Number）：TCP 把应用层交下来的数据看作一串连续的字节流，给每个字节编上逻辑序号；建立连接时双方各自协商出一个初始序列号（ISN），此后每个报文段的头部都携带”该报文段第一个字节的序号”。有了序列号，接收方就能把乱序到达的报文段重新排序、识别出哪些字节缺失（触发重传）、也能识别重复到达的报文段并丢弃。

确认应答（ACK）：接收方每收到数据就回一个带确认号的 ACK，确认号表示”这个序号之前的所有字节我都收到了”，这是一种累积确认机制。发送方靠这个确认号判断哪些数据已经安全送达，还没被确认的数据就留在重传队列里。

超时重传（Timeout Retransmission）：发送每个报文段时都会启动一个重传计时器（RTO，Retransmission Timeout），如果在计时器到期前收到了对应的 ACK 就撤销计时器；如果计时器超时仍未收到确认，就判定该报文段丢失并重新发送。RTO 的具体数值不是固定的，是基于对网络往返时延（RTT）的动态测量计算出来的。

快速重传（Fast Retransmit）：接收方一旦收到了序号不连续、比期望值大的失序报文段，会立即回复一个重复的 ACK（确认号仍是它期望收到的那个缺失字节）。发送方一旦连续收到 3 个或以上相同的重复 ACK，就直接重传对应报文段，不用等超时计时器走完，缩短了恢复时间。

校验和（Checksum）：TCP 报文段的头部和数据部分会一起计算出一个校验和字段。接收方收到后重新计算一遍并比对，如果结果不一致就说明传输过程中出现了比特错误，直接丢弃该报文段（等同于没收到,依赖发送方的超时重传机制来补救）。

连接管理：三次握手确保双方在真正传数据之前，已经确认彼此的收发能力正常并同步好了初始序列号；四次挥手确保双方各自的数据都发送完毕才断开连接。这为可靠传输提供了一个”双方状态已知”的前提。

流量控制（滑动窗口）：接收方通过报文段头部的窗口字段（接收窗口 rwnd）告诉发送方自己还有多少缓冲空间，发送方据此调整发送速率，避免把接收方的缓冲区冲爆导致丢包。

拥塞控制：发送方还要考虑整个网络路径的承载能力，通过维护一个拥塞窗口（cwnd）动态调整发送速率，详见下一节。

这几类机制的分工可以这样理解：可靠传输本身（序列号、ACK、重传、校验和）处理的是”已经发生的错误”，是端到端的事后补救；流量控制处理的是接收端来不及处理的问题，是发送方和接收方之间点对点的事前预防；拥塞控制处理的是整个网络路径承载力的问题，是发送方对网络全局状况的事前自适应。三者相互支撑：流量控制和拥塞控制通过减少丢包，减轻了重传机制的负担；而重传机制依赖的信号（ACK、重复 ACK、超时）本身就是拥塞控制算法据以调整窗口的输入。

十、拥塞控制

拥塞控制是发送方根据对网络拥塞状况的估计，动态调整自己发送速率的一套机制，核心变量是拥塞窗口 cwnd。它和流量控制经常被放在一起比较，但控制的对象完全不同：

维度 拥塞控制 流量控制
防止对象 压垮网络（路由器、链路） 压垮接收方的缓冲区
控制变量 拥塞窗口 cwnd 接收窗口 rwnd
判断依据 丢包、时延增大等网络反馈信号 接收方主动上报的剩余缓冲空间

实际发送方一次能发出去的数据量，取两者中更小的那个：

实际发送窗口 = min(cwnd, rwnd)

拥塞控制包含四个经典阶段（合称拥塞控制算法）：

慢启动（Slow Start）：连接刚建立，或者发生了超时重传（判定为严重拥塞）之后，cwnd 从一个较小值开始（通常是 1~10 个 MSS），此后每收到一个 ACK 就把 cwnd 增加 1 个 MSS——效果是每经过一个 RTT，cwnd 大约翻一倍,呈指数增长。这个阶段持续到 cwnd 达到 ssthresh（慢启动门限）为止。

拥塞避免（Congestion Avoidance）：一旦 cwnd 达到 ssthresh，算法从指数增长切换为线性增长——每经过一个 RTT，cwnd 只增加 1 个 MSS，而不是翻倍。这个阶段的目的是在窗口已经比较大、接近网络容量上限时更谨慎地试探，避免猛增导致拥塞。这个阶段持续到检测到丢包为止。

快重传（Fast Retransmit）：接收方一旦收到失序报文段就立刻发重复 ACK，发送方连续收到 3 个或以上重复 ACK 时，不必等待超时计时器,直接重传丢失的报文段——这通常意味着只是单个报文段丢失，而不是严重的网络拥塞。

快恢复（Fast Recovery）：执行完快重传之后，发送方把 ssthresh 设为当前 cwnd 的一半，同时把 cwnd 也直接降到这个新 ssthresh 附近（而不是像超时那样退回到很小的初始值重新慢启动），然后按拥塞避免的线性规则继续增长。这样处理的好处是,网络其实还有相当的承载能力时,不需要把发送速率打回原形,能更快恢复到较高的吞吐量。

这四个阶段的衔接逻辑：慢启动指数增长到 ssthresh → 切换到拥塞避免线性增长 → 检测到丢包（重复 ACK 触发快重传 + 快恢复，或超时触发重新慢启动）→ 循环。

现代 Linux 系统默认使用的拥塞控制算法是 CUBIC（基于三次方程曲线调整窗口增长速度,更适应高带宽高延迟网络）；Google 提出的 BBR 算法则是另一条路线,不依赖丢包作为拥塞信号,而是直接建模带宽和往返时延来决定发送速率,在丢包率较高但带宽充足的网络里（如移动网络）比传统基于丢包的算法表现更好。

十一、TCP Keepalive 与 HTTP Keep-Alive

这两个名字很像的机制，工作在完全不同的协议层，目的也不同。

维度 TCP Keepalive HTTP Keep-Alive
所属层次 传输层（TCP协议本身） 应用层（HTTP协议特性）
目的 探测长期空闲的连接对端是否还存活 让一个 TCP 连接承载多个 HTTP 请求/响应，避免反复握手
管理方 操作系统内核 HTTP 客户端和服务器程序
触发时机 连接长时间（通常是几小时量级）没有数据交互 一次 HTTP 请求/响应完成之后
控制方式 内核参数、socket 选项（如 SO_KEEPALIVE） HTTP Connection 请求头、服务器配置
传输内容 空的探测包（纯 ACK 段） 真实的 HTTP 请求和响应数据

TCP Keepalive 对应用程序完全透明：当一条连接闲置超过设定阈值,内核会自动发出探测包,如果对端仍然存活会回应 ACK；如果连续几次探测都得不到回应,内核判定对端已经不可达,关闭这条连接并释放资源。它解决的问题是”这条连接看起来还开着,但对面到底还在不在”。

HTTP Keep-Alive 是应用层主动决定”这次响应发完了,先别关 TCP 连接,留着给下一个请求用”，通过 Connection: keep-alive 头声明。它省掉的是每次请求都重新走一遍三次握手（以及 HTTPS 下的 TLS 握手）的开销，这个连接通常在几秒到几分钟的量级后就会被主动关闭（由服务器的超时配置决定）,时间尺度远比 TCP Keepalive 短。

两者是分层配合的关系：HTTP Keep-Alive 负责应用层面”连接复用”的日常调度，时间尺度短；TCP Keepalive 是传输层的兜底保险，只在连接真的长时间空闲、又没有走正常关闭流程时才会介入探测，时间尺度长得多——正常情况下 HTTP 层的超时机制会先于 TCP Keepalive 生效，把连接关掉。
