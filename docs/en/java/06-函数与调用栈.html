Functions and the Call Stack: The Truth About Methods and Parameter Passing

In C++ you have global functions, member functions, static member functions, function pointers, reference parameters, std::move… Java narrows all of this down to a single concept: the method. A method always belongs to some class; there is no function floating free outside a class. But narrowing doesn’t mean simple — the stack frame layout, the dispatch mechanism, and the iron rule of pass-by-value only behind a method call are the underlying truths this chapter pries open.

1. Method Definition and Overloading

A Java method must be written inside some class, composed of return-type methodName(parameter-list) { method-body }:

public class MethodDemo {
    static int add(int a, int b) {
        return a + b;
    }

    static void greet(String name) {
        System.out.println("Hello, " + name);
    }

    public static void main(String[] args) {
        int sum = add(3, 4);
        System.out.println(sum);     // 7
        greet("Ada");                 // Hello, Ada
    }
}
  • If there’s no return value, write void; the method body may have no return, or may use a value-less return; to exit early.
  • Calling a method is just methodName(actual-args...), the same as C.
  • The above all use static methods (which belong to the class itself and can be called without first new-ing an object); an ordinary instance method requires an object first, then object.methodName(...), which is detailed in Object-Oriented Programming and the Type System.

A single class can have multiple methods with the same name but different parameter lists; this is called overloading, and at the call site the compiler automatically selects the matching one based on the argument types:

public class Greeter {
    static void say(String name) { System.out.println("Hi, " + name); }
    static void say(int times)   { System.out.println("repeat " + times + " times"); }

    public static void main(String[] args) {
        say("Ada");   // Hi, Ada          -- selects say(String)
        say(3);       // repeat 3 times   -- selects say(int)
    }
}

A method signature = method name + parameter type list (not including the return type, the same as C++). Overloading is resolved at compile time based on the static types of the arguments, just like C++ overload resolution, but Java has no default parameters, so you can only emulate them with multiple overloads or varargs.

public class Overload {
    static void f(int x)    { System.out.println("int: " + x); }
    static void f(long x)   { System.out.println("long: " + x); }
    static void f(Object x) { System.out.println("Object: " + x); }

    public static void main(String[] args) {
        f(1);        // int: an exact match is always preferred
        f(1L);       // long
        f("hi");     // Object
        // Overload resolution order: exact match → widening → boxing → varargs
        byte b = 5;
        f(b);        // int: byte is widened to int, rather than boxed to Object
    }
}

Key point: overload resolution happens at compile time, and javac directly binds the call site to a specific signature. The runtime actual type of an object has no effect whatsoever on overloading — this is a completely different matter from overriding, discussed below.

The point that “overloading looks at the static type” is the easiest to confuse with overriding. Look at this example: the same object, with a different declared type, selects a different overload:

public class OverloadStatic {
    static void f(Object o) { System.out.println("Object"); }
    static void f(String s) { System.out.println("String"); }

    public static void main(String[] args) {
        Object x = "hi";        // the runtime actual type is String
        f(x);                   // Object —— only looks at x's static type, Object
        f("hi");                // String —— the literal's static type is String
        f((Object) "hi");       // Object —— the cast changes the static type
    }
}

x clearly holds a String at runtime, but f(x) still selects f(Object) — because overloading is fixed at compile time by the variable’s declared type, and the runtime actual type does not participate. This is exactly the opposite of overriding (override, which follows the runtime actual type via the vtable): one is looked up by static type and fixed at compile time, the other by dynamic type and decided at runtime.

2. Java Has Only Pass-by-Value

In C++ you can explicitly distinguish pass-by-value, pass-by-pointer, and pass-by-reference. Java has only one: pass-by-value. The whole controversy stems from “what value is passed for a reference type”.

The answer: what is passed is a copy of the reference value (the reference, which you can think of as the object’s address). Not the object itself, and not a C++-style “reference alias”.

  • Primitive types: the 4/8 bytes of numeric value are copied.
  • Reference types: that “reference value pointing to the heap object” is copied (with pointer compression enabled by default on HotSpot 64-bit, this is usually a 4-byte oop).

The copy and the original variable point to the same heap object, so you can change the object’s contents; but reassigning the copy leaves the original variable untouched.

Why Java kept only this single mechanism of pass-by-value, rather than also offering reference/pointer parameters like C++: this is a trade-off between “parameter-passing rules that are singular and predictable” and “expressiveness at the call site”. In C++, the same function signature void f(T x) / void f(T& x) / void f(T* x) has completely different passing semantics, and when reading the call site f(a) you simply cannot tell whether a will be modified in place without looking at the function declaration — a common readability burden in C++, to be papered over with naming conventions or documentation. Java’s design is: parameter passing always has exactly one rule — copy the bits in the caller’s variable — and this rule treats primitives and reference types alike, fully unified with the a = b assignment rule in Variables and the Memory Model, so you don’t have to learn a separate set of semantics for parameter passing. The price is giving up the ability to “modify the caller’s reference itself in place” (i.e., what the swap example below proves — the inability to genuinely swap two references); to get that effect you can only switch to a different expression: carry the mutable state through fields/arrays of a shared object, or return a new value. This is the same design philosophy behind “Java has no pointer arithmetic, no default parameters”: exchange fewer but fully consistent rules for the property that any call site can infer the actual effect of parameter passing without inspecting the signature’s details.

The swap Counterexample: Proving You Can’t Change the Caller’s Reference

public class Swap {
    static class Box { int v; Box(int v) { this.v = v; } }

    // an attempt to swap two references — doomed to fail
    static void swap(Box a, Box b) {
        Box t = a; a = b; b = t;   // only swaps the copies a and b
    }

    // able to change the object's contents — succeeds
    static void fill(Box x) {
        x.v = 999;                 // writes the heap field through the copied reference
    }

    public static void main(String[] args) {
        Box p = new Box(1), q = new Box(2);
        swap(p, q);
        System.out.println(p.v + " " + q.v); // 1 2: the caller's references didn't change
        fill(p);
        System.out.println(p.v);             // 999: the object's contents were changed
    }
}

Memory diagram (when swap reaches b = t;):

   main frame                    swap frame
 +----------+                 +----------+
 |  p ------|----+       +----|  a ------|--> points back to Box(2)
 |  q ------|--+ |       |    |  b ------|--> points back to Box(1)
 +----------+  | |       |    |  t ------|--> Box(1)
               | |       |    +----------+
               | +-------|-----------+
               |         |           |
               v         |           v
        heap: Box(1) <---+    heap: Box(2)
             v=999            v=2

p and q in main point to the same thing from start to finish; what swap swaps is a and b in its own frame. After the method returns, the swap frame, along with a, b, and t, is popped off the stack and destroyed.

Want a real swap in Java? You can only return new values, pass in a mutable container (array/holder object), or use fields. There is no C++ Box*& or Box&.

Comparison table:

Scenario C++ Java
Passing a primitive Value/reference/pointer optional Value only (copy the number)
Passing an object Value (deep/shallow copy constructor)/reference/pointer Value only (copy the reference value, not the object)
Changing object contents affects the caller Reference/pointer can Can (sharing the same heap object)
Changing the pointing affects the caller Reference/pointer can Impossible

3. Stack Frame Structure

On every method call, the JVM pushes a frame onto the current thread’s Java Virtual Machine stack. This is the same as C++’s call-stack concept, but the structure is explicitly mandated by the JVM specification:

Thread stack (high address at the bottom, illustration grows downward)
 +--------------------------------------+
 | Frame A (main)                       |
 |  Local Variable Table                |  <- similar to C++ locals + parameter area
 |  Operand Stack                       |  <- the work area for bytecode computation (C++ uses registers/an implicit stack)
 |  Frame data: return address, reference to the constant pool |
 +--------------------------------------+
 | Frame B (the method called by A)     |  <- top of stack, the currently active frame
 |  ...                                 |
 +--------------------------------------+
  • Local Variable Table: an array-like structure, numbered by slot. long/double occupy 2 slots, everything else occupies 1. Slot 0 of an instance method is this. The method’s maximum number of local variables is computed at compile time and written into the Code attribute’s locals.
  • Operand Stack: the JVM is a stack-based virtual machine (unlike x86’s register machine). iadd pops two ints off the operand stack, adds them, and pushes the result back. The maximum depth is also determined at compile time (stack).
  • Frame data: the return address (the caller’s next instruction), a reference to the exception table, and so on.

Use javap to see the truth:

// Frame.java
public class Frame {
    static int add(int a, int b) { int c = a + b; return c; }
}
$ javac Frame.java && javap -c -v Frame.class
static int add(int, int);
  Code:
   stack=2, locals=3, args_size=2   // operand stack depth 2, local variable table 3 slots (a, b, c)
     0: iload_0        // push slot0 (a) onto the operand stack
     1: iload_1        // push slot1 (b)
     2: iadd           // pop two, add, push back
     3: istore_2       // pop and store into slot2 (c)
     4: iload_2        // push c again
     5: ireturn        // pop as the return value

The return value is passed through the operand stack: the callee’s ireturn pops the top of the stack, and the JVM pushes it onto the caller’s frame’s operand stack. Parameter passing is the reverse: the caller pushes the actual arguments onto its own operand stack, and the invoke* instruction consumes them and fills them into the low slots of the new frame’s local variable table.

4. Method Dispatch: Static Binding vs Dynamic Binding

In C++ non-virtual functions are statically bound, and virtual functions go through the vtable. Java’s counterpart is more regular, embodied by four bytecode instructions:

Instruction Purpose Binding time
invokestatic Static methods Static (compile time)
invokespecial Constructors, private, super. calls Static
invokevirtual Ordinary instance methods Dynamic (look up the vtable at runtime)
invokeinterface Interface methods Dynamic (look up the itable)
invokedynamic lambdas, method references, dynamic languages Fixed after the first link at runtime

Static Binding

static, private, and final methods, as well as overload resolution, are all fixed at compile time. Although a final method uses invokevirtual, the JIT can devirtualize and inline it, because it can never be overridden.

Dynamic Binding and the vtable

An ordinary instance method call compiles to invokevirtual. At runtime the JVM uses the type pointer (klass pointer) in the object header to find the actual class’s method metadata, and retrieves the target method’s entry from its virtual method table (vtable) at a fixed index. This is almost identical to C++’s vptr → vtable mechanism, differing in:

  • C++: the object stores a vptr, and the vtable lives in the read-only data segment.
  • HotSpot: the klass pointer in the object header (mark word + klass pointer) points to an InstanceKlass in the Metaspace, with the vtable immediately following it.
object (heap)         InstanceKlass (Metaspace)
+-------------+       +------------------+
| mark word   |       | ... metadata ... |
| klass ptr --|------>| vtable[0] -> ...  |
+-------------+       | vtable[1] -> Dog.speak
| instance fields |   | vtable[2] -> ...  |
+-------------+       +------------------+
public class Dispatch {
    static class Animal { void speak() { System.out.println("..."); } }
    static class Dog extends Animal { @Override void speak() { System.out.println("Woof"); } }

    public static void main(String[] args) {
        Animal a = new Dog();
        a.speak();   // invokevirtual: static type Animal, at runtime finds Dog's vtable slot -> "Woof"
    }
}

invokeinterface is slightly slower: an interface method’s vtable index in an implementing class is not fixed, so it requires looking up the itable (interface method table) or a search, and the JIT optimizes it with an inline cache.

Why overloading goes through compile-time static dispatch and overriding goes through runtime dynamic dispatch, rather than unifying them into one mechanism: it’s because the two solve problems at completely different levels, and unifying them would please neither side. Overloading solves “which piece of code should a single method name execute under different parameter types” — the answer to this question depends only on information visible at the call site (the static types of the arguments), and there’s enough data to decide it at compile time, with no reason to defer it to runtime; compile-time resolution also brings a direct benefit: lower call overhead (invokestatic/invokespecial need no table lookup), and the behavior is fully determined at compile time, so it won’t jump to an “unexpected” overload version because the runtime object’s actual type differs (recall the earlier example where f(x) always selects f(Object)). Overriding solves a completely different problem — “for the same piece of calling code, facing a concrete subclass implementation that may vary at runtime, which version should be called” — and the essence of this problem is polymorphism: when writing the call, the caller often knows only the declared type (such as Animal), and the true target method can only be known at runtime from the object’s actual type (Dog), so it must use invokevirtual to look up the vtable and decide dynamically. Lumping these two problems together — e.g., letting overloading also resolve by runtime type — would turn “which overload to call”, an operation that should be cheaply determined at compile time, into a runtime query of the arguments’ true types on every call, and would render the compile-time safety net of static type checking meaningless. Only by designing them separately can “which method body a parameter type selects” and “which subclass implementation gets executed” each be solved in the most cost-effective way.

5. Recursion and StackOverflowError

A recursive method simply calls itself in its own body, written exactly as in C:

public class Factorial {
    static long fact(int n) {
        if (n <= 1) return 1;
        return n * fact(n - 1);
    }
    public static void main(String[] args) {
        System.out.println(fact(5));   // 120
    }
}

Each level of recursion pushes a frame. Java’s stack capacity is set by -Xss (default about 512KB~1MB, platform-dependent). When the stack is exhausted it throws StackOverflowError (note it’s an Error, not an Exception, see Chapter 9). The JVM does not do tail-call optimization (TCO); even tail recursion still eats the stack — an important difference from many functional languages and some C++ compilers.

public class Recur {
    static long depth = 0;
    static void dive() { depth++; dive(); }   // no termination, deliberately blows the stack
    public static void main(String[] args) {
        try { dive(); }
        catch (StackOverflowError e) {
            System.out.println("stack blew up at depth approx: " + depth); // the larger each frame, the fewer levels
        }
    }
}

Deep recursion should be rewritten as iteration + an explicit Deque simulating a stack, moving the frame data from the thread stack onto the heap.

6. Variadic Parameters (varargs)

Adding ... after a parameter type lets you pass any number of arguments at the call site (including 0), and inside the method it’s used as an array:

public class Varargs {
    static int sum(int... xs) {          // compiled as int[] xs
        int s = 0; for (int x : xs) s += x; return s;
    }
    public static void main(String[] args) {
        System.out.println(sum(1, 2, 3)); // the compiler generates new int[]{1,2,3}
        System.out.println(sum());        // passes an empty array new int[]{}, not null
        int[] arr = {4, 5};
        System.out.println(sum(arr));     // passes the array directly, without wrapping another layer
    }
}

T... is just T[] in bytecode. At the call site the compiler automatically packs the scattered arguments into a heap array — so every call may incur an array allocation. When overloading + varargs are involved, the fixed-parameter version takes precedence over the varargs version (varargs is the last tier of resolution).

7. Lambdas and Method References: the Stage for invokedynamic

A lambda is a “method body with no name”, written as (parameters) -> expression or code block, commonly used as a “transferable behavior” passed to another method:

import java.util.function.IntBinaryOperator;
public class LambdaBasic {
    public static void main(String[] args) {
        IntBinaryOperator add = (a, b) -> a + b;
        System.out.println(add.applyAsInt(3, 4));   // 7
    }
}

A method reference is shorthand for a lambda; Class::methodName passes an existing method directly as a behavior, e.g., System.out::println.

A C++ lambda generates an anonymous closure class (with operator()) at compile time. Java does not generate a .class for each lambda at compile time; instead it uses invokedynamic to defer the implementation to runtime.

import java.util.function.IntBinaryOperator;
public class Lambda {
    public static void main(String[] args) {
        IntBinaryOperator add = (a, b) -> a + b;   // compiled into an invokedynamic call site
        System.out.println(add.applyAsInt(3, 4));
    }
}

javap -c shows an invokedynamic #N, 0 with a bootstrap method LambdaMetafactory.metafactory. The mechanism:

  1. The lambda body itself is compiled by javac into a private static/instance method in the host class (such as lambda$main$0).
  2. The first time execution reaches that invokedynamic, the JVM calls the bootstrap method, and LambdaMetafactory dynamically generates at runtime a class implementing IntBinaryOperator, whose abstract method delegates to that private method.
  3. The generated implementation is bound to that call site’s CallSite, and subsequent calls hit it directly, at nearly zero overhead.

Benefit: it avoids the bloat of “one class file per lambda” and leaves the generation strategy to the runtime (a better implementation can be swapped in the future without changing the bytecode). Method references (String::length, System.out::println, ArrayList::new) go through exactly the same mechanism, except the target method points directly to an existing method rather than a synthetic one.

On the capture front: a local variable captured by a lambda must be effectively final. Because what’s captured is a copy of the variable’s value (a copy of the reference value for a reference type), stored as a constructor argument when the instance is generated — this is close to C++’s [=] by-value capture semantics, whereas Java does not allow [&]-style by-reference capture of a local variable (a local variable lives on the stack and expires when the method returns, so capturing a reference would dangle).

An intuitive runnable verification: in a loop, each iteration stores i into a new cur (each iteration a new, effectively-final variable), and each lambda captures its own copy of the value:

import java.util.*;
import java.util.function.Supplier;
public class Capture {
    public static void main(String[] args) {
        List<Supplier<Integer>> fns = new ArrayList<>();
        for (int i = 0; i < 3; i++) {
            int cur = i;              // a new, effectively-final variable each iteration
            fns.add(() -> cur);       // captures cur's value at that moment
        }
        for (var f : fns) System.out.print(f.get() + " ");  // 0 1 2
        System.out.println();
    }
}

The three lambdas print 0 1 2 respectively, because each captures a copy of cur’s value at creation time, not a shared single variable. This contrasts with JavaScript, where var closures all capture the same final i (often printing 3 3 3) — Java, by “capturing a value copy + effectively final”, roots out this class of shared-mutable-state pitfalls at the source.

Summary

  • A method always belongs to some class; there are no free-floating functions. Parameter passing is always pass-by-value — for a reference type, what’s passed is a copy of the reference value. This unified rule buys the property that any call site can judge the effect of parameter passing without inspecting the signature, at the price of being unable to modify the caller’s reference itself in place.
  • Overloading is resolved at compile time by static type, overriding at runtime by dynamic type via the vtable — the two solve problems at different levels (the former is “which piece of code to select”, the latter is “which implementation a polymorphic call invokes”), and lumping them together would drag an overhead that could have been fixed at compile time out to runtime.
  • A stack frame is composed of the local variable table + operand stack + frame data; invokestatic/special are statically bound, invokevirtual/interface go through the vtable/itable for dynamic dispatch, and invokedynamic carries the runtime generation of lambdas.
  • The JVM does not do tail-call optimization, so deep recursion will StackOverflowError.
