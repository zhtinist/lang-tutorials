Data Types and Memory Layout

This chapter follows on from the two-camp division in “Variables and the Memory Model”, spelling out how much space each type takes in memory and what it looks like, contrasting with C throughout.

1. The 8 Primitive Types: Fixed-Width, Cross-Platform, No unsigned

Literals and suffixes are similar to C: 10L (long), 3.14f (float), 0x1F (hexadecimal), 0b1010 (binary), 017 (octal, leading 0). Java 7+ allows underscore separators to improve readability:

long   creditCard = 1234_5678_9012_3456L;
int    million     = 1_000_000;
int    bytes       = 0b1101_0010;
double pi          = 3.141_592_653;

C’s integer widths are implementation-defined: int may be 16/32/64 bits, and long differs across platforms (LP64 vs LLP64); you have to rely on <stdint.h>’s int32_t to be certain. Java writes the widths into the language specification, consistent across all platforms:

Type Bit width Range Approximate C equivalent Default value
byte 8 -128 ~ 127 int8_t 0
short 16 -32768 ~ 32767 int16_t 0
int 32 ±2.1e9 int32_t 0
long 64 ±9.2e18 int64_t 0L
float 32 IEEE754 single precision float 0.0f
double 64 IEEE754 double precision double 0.0d
char 16 UTF-16 code unit 0~65535 none (wchar_t is not a reliable match) ''
boolean unspecified true/false none (C uses int/_Bool) false

Three Java features you must remember:

  1. No unsigned. All integer types are signed (char is the only unsigned 16-bit quantity, but semantically it is a character, not a number). When you need unsigned arithmetic, use a wider type or static methods such as Integer.toUnsignedLong, Integer.divideUnsigned. For logical right shift use >>> (see “Basic Syntax”).
  2. char is a 16-bit UTF-16 code unit, not C’s 8-bit char. A single char cannot hold every Unicode character (supplementary-plane characters need two chars, i.e. a surrogate pair). To handle the semantics of “one character,” use the int code point APIs. String encoding is covered later.
  3. The size of boolean is unspecified. The JVM spec does not define how many bits a boolean occupies; in HotSpot a single boolean variable is usually treated as an int, and each element of a boolean[] array occupies 1 byte. Don’t count on bit packing (for a bitmap, use long + bitwise operations, or BitSet).

Floating point follows IEEE754: there are Double.NaN and Double.POSITIVE_INFINITY; 0.0/0.0 yields NaN and 1.0/0.0 yields Infinity (unlike integer division by zero, which throws an exception). The pitfall that NaN != NaN is true is the same as in C.

2. Wrapper Classes, Autoboxing, and the Integer Cache

Every primitive type has a corresponding wrapper class—it wraps the value into an object on the heap so it can be placed into containers that only accept objects (generic collections can’t hold int, only Integer; see “Composite Data Structures”):

Primitive Wrapper class
int Integer
long Long
double Double
char Character
boolean Boolean
… (byte/short/float likewise)

Autoboxing / unboxing: the compiler automatically converts between primitive types and wrapper classes.

Integer boxed = 42;          // autoboxing: the compiler inserts Integer.valueOf(42)
int prim = boxed;            // auto-unboxing: the compiler inserts boxed.intValue()
List<Integer> list = new ArrayList<>();
list.add(7);                 // boxing: int 7 -> an Integer object placed on the heap
int v = list.get(0);         // unboxing

The cost (note for the performance-sensitive): boxing must new an object on the heap, with a reference pointing to it—far more expensive than an int on the stack, and it creates GC pressure. For intensive numeric computation, don’t use List<Integer>; use int[] or IntStream (see “Standard Library Algorithms”).

The Integer Cache [-128, 127] and the == Trap

Integer.valueOf(int) returns the same cached object for values from -128 to 127 (the upper bound can be tuned with -XX:AutoBoxCacheMax); outside that range a new object is created each time. Hence:

Integer a = 127, b = 127;
System.out.println(a == b);      // true  —— cache hit, same object
Integer c = 128, d = 128;
System.out.println(c == d);      // false —— each newly created, different objects
System.out.println(c.equals(d)); // true  —— compares values, correct

Combined with the == semantics from Chapter 3: == compares references, and the cache makes small integers happen to share objects, so it is true, while large integers are not. Conclusion: to compare wrapper-class values, always use equals or first unbox into primitives to compare. Unboxing also carries an NPE risk: Integer x = null; int y = x; throws NPE at runtime.

Another subtle auto-unboxing trap hides in the ternary expression: when the two branches have different wrapper types, the compiler unboxes both sides and then performs binary numeric promotion, and finally reboxes—the result type may not be what you expect.

public class Ternary {
    public static void main(String[] args) {
        Object x = true ? Integer.valueOf(1) : Double.valueOf(2);
        System.out.println(x);                            // 1.0   —— not 1!
        System.out.println(x.getClass().getSimpleName()); // Double
    }
}

true clearly selects Integer.valueOf(1), but because the other branch is Double, the entire ternary expression is promoted to double: Integer is first unboxed to int → promoted to double 1.0 → then reboxed to Double. This is a product of the JLS ternary-expression typing rules combined with auto-boxing/unboxing; C’s ?: only has arithmetic promotion, without this boxing layer.

More Boxing Pitfalls: Cross-Wrapper-Type equals, Using a Wrapper as a Lock

equals judges equality by both type and value; different wrapper classes are not equal even if their numeric values are equal—this is often tripped over when looking up a Map<String, Long> with an Integer, or when comparing across types:

System.out.println(Long.valueOf(1).equals(Integer.valueOf(1)));  // false: different types, even though both values are 1

The reason is straightforward: Long.equals internally first checks the type with instanceof Long; Integer is not an instance of Long, so it short-circuits and returns false directly, never reaching the value-comparison step—equals performs no implicit numeric promotion (unlike the implicit widening among arithmetic operators).

Another, more subtle trap is using a wrapper class as a synchronization lock object:

Integer lock = 1000;      // outside the [-128,127] cache range, a newly created Integer object
synchronized (lock) { /* ... */ }

It looks no different from locking on any object, but wrapper classes are types annotated as “value-based classes” (modern javac emits an [identity] attempt to synchronize on an instance of a value-based class warning for this)—the language spec only guarantees the stability of their value semantics, not the stability of their identity (whether they are the same object): within the same numeric range ([-128,127]) different variables may share the same cached object, while outside the range each is newly created. If code writes Integer lock1 = 1000; and Integer lock2 = 1000; in two places yet mistakenly assumes they are “the same lock,” since both are outside the cache range and are different objects, synchronized actually locks two unrelated objects and provides no mutual exclusion—this is a concurrency hazard produced when the object identity of reference types (the == semantics of Chapter 3) is quietly polluted by the wrapper class cache’s “looks like a value type” behavior. For locking, use a dedicated object with a well-defined lifetime (such as new Object() or the business object itself), not any wrapper type or string literal that might be cached/shared.

3. Object Memory Layout (HotSpot)

This is the part C programmers care about most: what does a Java object actually look like on the heap? In HotSpot, an object consists of three parts:

┌────────────────────────────────────────────────┐
│ Object Header                                    │
│  ┌──────────────────────────────────────────┐  │
│  │ Mark Word   (usually 8 bytes on 64-bit JVM)│  │  hash code, GC generational age,
│  │                                            │  │  lock state / biased-lock pointer, etc.
│  ├──────────────────────────────────────────┤  │
│  │ Klass pointer (to class metadata in the   │  │  4 bytes when compressed oops is on
│  │  method area / metaspace)                  │  │  ≈ one of the roles of C++'s vptr
│  └──────────────────────────────────────────┘  │
│  [ if an array, also a length field (4 bytes) ] │
├────────────────────────────────────────────────┤
│ Instance Data                                    │  each field laid out by type,
│  int / long / reference ...                      │  HotSpot reorders to save padding
├────────────────────────────────────────────────┤
│ Padding                                          │  padded to a multiple of 8 bytes
└────────────────────────────────────────────────┘

Compared with C++: C++’s struct/class has no Mark Word; when there are virtual functions, there is a vptr pointing to the vtable. Java’s Klass pointer takes on the duty of “finding the class metadata and method table” (virtual method dispatch is covered in “Functions and the Call Stack”), while the Mark Word is something C++ has nothing of—it carries the object hash, GC age, and the built-in lock (synchronized) state.

Why does the Mark Word cram the hash code, GC age, and lock state—three unrelated things—into the same word: because these things are almost never needed simultaneously during an object’s lifetime, and splitting them into three separate fields would make every object carry a few wasted bytes needlessly. Since the number of objects in Java is often in the tens of millions to billions, an extra 8 bytes per object means tens to hundreds of MB of overall overhead. The Mark Word’s solution is to reuse the same bits on demand, distinguishing the current meaning by low-bit flags: a newly created object is by default in the no-lock or biased-lock state, at which point the high bits may not yet be used; only when hashCode() is called does the JVM write the hash value into this region and mark it “computed”; once synchronized contention occurs, the same region is reinterpreted as a pointer to a lock record on the thread stack, “inflating” step by step with the degree of contention from biased lock → lightweight lock → heavyweight lock, and each inflation switches the encoding format within this same word. GC also needs to record a generational-age counter here to decide when an object is promoted from the young generation to the old generation (see the generational hypothesis in “Error Handling and Resource Management”). This is time multiplexing (the same memory carries different information at different stages) rather than space multiplexing, trading state-machine-style encoding complexity for a smaller fixed overhead per object—this kind of space-sensitive bit-packing design corresponds in C to handwritten bitfields or packing multiple flag bits into a uint64_t and parsing them yourself; Java builds this logic into the object model, and business code sees none of it.

Alignment exists just as in C’s struct: HotSpot by default aligns objects on an 8-byte boundary, padding at the end. There may also be padding between fields. The difference is: in C, field order strictly follows declaration order (unless pragma pack), whereas HotSpot reorders fields on its own to minimize padding (placing wide types first, grouping references together for easy GC scanning); you cannot assume declaration order equals memory order.

An empty object (no fields) under 64-bit + compressed oops is usually 16 bytes (8 Mark + 4 Klass + 4 padding).

Compressed Oops (CompressedOops)

As mentioned earlier in Chapter 3: under 64-bit, a reference should be 8 bytes, which takes too much space and hurts the cache. HotSpot by default enables Compressed Ordinary Object Pointers for heaps smaller than 32GB: it encodes references as 32 bits, and on access restores the real address by left-shifting 3 bits according to the 8-byte object alignment.

Why 4 bytes can address an address space that should require 8 bytes: the key lies in the “alignment” fact mentioned in the previous paragraph—since the starting address of every object on the heap is guaranteed to be a multiple of 8 bytes (due to the alignment requirement), the lowest 3 bits of the real address are always 0, and storing these 3 bits is pure waste. Compressed oops simply don’t store those 3 bits, storing only the result of right-shifting the address by 3 bits; this way the 2^32 encoded values a 32-bit unsigned number can represent each correspond to an 8-byte-aligned real address, so the effective addressing range is 2^32 × 8 = 32GB, rather than the 4GB a 32-bit address can directly represent. The cost is a left-shift conversion on each dereference (essentially free for modern CPUs—one shift instruction), in exchange for reference fields and Klass pointers being generally halved, making objects smaller and improving cache hit rates—the smaller the objects, the more of them a CPU cache line of the same size can hold, so GC scanning and field access are both faster. Once the heap exceeds 32GB, the compressed encoding space is insufficient, and the JVM automatically falls back to 8-byte raw pointers (this is the direct reason for the tuning wisdom of “don’t set the heap to just over 32GB”: crossing the 32GB threshold not only fails to give you more but actually widens all pointers). This is a pure HotSpot implementation detail; there is no corresponding concept in C (C pointers are just raw addresses, with no such encoding layer).

4. Arrays Are Objects

int[] a = new int[5];      // allocate an array of length 5, elements default to 0
System.out.println(a.length);   // 5, length is a built-in field, not a method call
a[0] = 10;
System.out.println(a[0]);       // 10

Out-of-bounds access throws an exception, rather than silently corrupting memory as in C:

a[10] = 1;                 // ArrayIndexOutOfBoundsException

Java arrays are objects on the heap, not C’s “a stretch of raw contiguous memory + a base address.” Memory layout: an array object = object header (including an extra length field) + a contiguous element region + padding.

int[5] on the heap:
┌──────────┬────────┬──────────────────────────────┐
│ header    │ length=5│ [0][1][2][3][4]  contiguous int elements │
└──────────┴────────┴──────────────────────────────┘

Key comparisons: - Elements are stored contiguously; the element region of an int[] is 5 contiguous ints—this is the same as C, and cache-friendly. - Bounds-checked: every a[i] access has the JVM verify 0 <= i < length, throwing an exception on out-of-bounds rather than undefined behavior. The JIT can often prove that in-loop indices are safe and thereby eliminate bounds checks, so hot loops don’t have the overhead you might imagine. - Reference arrays store references: the element region of a String[] / Object[] is a row of references, each pointing to a real object on the heap (possibly null)—not inlined objects. This differs from C’s struct T arr[] (value inlining) and is more like T* arr[] (an array of pointers). Java currently has no contiguous object array with value inlining (Project Valhalla’s value classes may provide this in the future). - Multidimensional arrays are “arrays of arrays”: int[][] is an array whose elements are “int[] references,” rows can be of unequal length (jagged arrays), and the memory is not guaranteed to be contiguous overall. C’s int m[3][4] is a truly contiguous row-major block—this is an important difference; when pursuing locality in numeric computation, people often switch to a one-dimensional int[] with manual indexing.

5. String: Immutable + Constant Pool + intern

String s = "abc";
System.out.println(s.length());        // 3
System.out.println(s.charAt(0));        // a
System.out.println(s.substring(1));     // bc
System.out.println(s.concat("d"));      // abcd (returns a new string, s itself unchanged)

String is a reference type and an immutable object. Internally (Compact Strings in JDK9+) it uses a byte[] to store characters plus a coder marking the encoding (Latin-1 or UTF-16)—as long as the code points of all characters in the whole string are ≤ 0xFF (representable in Latin-1, including Latin extensions and common Western accented letters), each character takes 1 byte; once any character with a code point > 0xFF appears (Chinese, emoji, etc.), the whole string switches to UTF-16, 2 bytes per character. It is not \0-terminated; the length is an explicit field.

What Immutability Means

Any “modifying” method returns a new object, leaving the original string untouched:

String s = "abc";
s.concat("d");            // returns a new string "abcd", but it's not received, so s is still "abc"
s = s.toUpperCase();      // "ABC" is a new object, s is redirected to it, the old "abc" awaits collection

The benefits of immutability: it can be safely shared (no synchronization needed across threads), its hash can be cached, and it can be safely used as a Map key. The cost: concatenation produces many intermediate objects—so use StringBuilder.

The String Constant Pool and intern

String literals ("hello" in source) are placed by the JVM into a string constant pool (driven by the runtime constant pool, located in the heap). Identical literals share the same object:

String a = "hi";
String b = "hi";
System.out.println(a == b);          // true! the same object in the pool

String c = new String("hi");         // new forces a separate new object on the heap
System.out.println(a == c);          // false! different objects
System.out.println(a == c.intern()); // true! intern() returns the canonical object in the pool

Memory diagram:

Constant pool (in heap)     Regular heap
[ "hi" object P ]◀──a        [ "hi" object Q ]◀── c (newly created)
       ▲────── b
c.intern() looks up the pool and returns P; hence a == c.intern() is true
  • == being true for literals is only because they share the pool object—don’t rely on it; to compare content always use equals (echoing Chapter 3).
  • intern() registers/looks up a string in the pool and returns the canonical instance. Large numbers of duplicate strings can save memory this way, but overuse bloats the pool—use with caution.
  • Constant concatenation determinable at compile time ("a" + "b") is folded by javac directly into the "ab" literal and entered into the pool.

The following runnable example makes the difference between “compile-time folding” and “runtime concatenation” crystal clear:

public class Folding {
    public static void main(String[] args) {
        String s           = "ab";
        String compileTime = "a" + "b";   // two literals, folded by javac into "ab" in the pool
        String c           = "a";         // a non-final local variable
        String runtime     = c + "b";     // concatenated at runtime via StringConcatFactory, a new object
        System.out.println(s == compileTime);      // true  —— the same pool object
        System.out.println(s == runtime);          // false —— newly created at runtime
        System.out.println(s == runtime.intern()); // true  —— intern retrieves the canonical object from the pool
    }
}

As long as everything participating in the concatenation is a compile-time constant (a literal or a final constant), the result is folded into one literal at compile time and enters the constant pool; as long as there is one variable only known at runtime (like the non-final c above), the concatenation happens at runtime and produces a new object on the heap.

StringBuilder: A Mutable Buffer

When you need to concatenate frequently or build strings in a loop, use StringBuilder (not thread-safe, for single-threaded use; the thread-safe version is StringBuffer):

StringBuilder sb = new StringBuilder();
for (int i = 0; i < 100; i++) {
    sb.append(i).append(',');   // modifies the internal char/byte buffer in place, without building intermediate Strings
}
String result = sb.toString();  // generate the String once at the end

Internally it maintains a resizable byte array (like a manually realloc’d buffer in C), append appends in place, and it only grows when capacity runs out (usually doubling). The compiler automatically optimizes concatenations like "a" + b + "c": JDK 9+ (JEP 280) compiles them by default into invokedynamic + StringConcatFactory (visible with javap -c; only JDK 8 and earlier use explicit StringBuilder). But each += in a loop is a separate concatenation per iteration, each producing an intermediate String, accumulating to O(n²), so for loop concatenation be sure to manually reuse a single StringBuilder.

StringBuffer: The Thread-Safe Historical Version

The relationship between StringBuffer and StringBuilder is like that of Vector/ArrayList and Hashtable/HashMap in the “Collections Framework”—StringBuffer, present since JDK 1.0, adds synchronized on all mutating methods (append/insert/delete/…); StringBuilder was only introduced in JDK 5, dropping synchronization with an identical API, meant for scenarios known not to be shared across threads. Both inherit the same abstract base class AbstractStringBuilder (internally also a resizable byte[] value + a coder encoding marker, homologous to String’s internal representation), differing only in whether the methods carry the synchronized keyword:

Dimension String StringBuffer StringBuilder
Mutability Immutable, modification produces a new object Mutable, modifies the internal array in place Mutable, modifies the internal array in place
Thread safety Safe (naturally guaranteed by immutability) Safe (method-level synchronized) Not safe
Performance Lowest (frequent concatenation produces many intermediate objects) Medium (synchronization has overhead) Highest (no synchronization overhead)
Typical scenario String constants, scenarios rarely modified A mutable string buffer shared across multiple threads Concatenating/building strings within a single thread (the vast majority of cases)

Why you should use StringBuilder rather than StringBuffer most of the time: a StringBuilder/StringBuffer instance is almost always a local variable inside a method—from new to the finishing toString(), it usually does not outlive the current method (or the current object’s construction), and is never held by multiple threads simultaneously, so StringBuffer’s layer of synchronization at the vast majority of call sites is paying for a contention that will never happen. Only when you actually publish a reference to the same mutable string buffer for shared read/write across multiple threads do you need StringBuffer’s synchronization semantics (and even then, in most scenarios concatenating the result with an immutable String and sharing only at the boundary is simpler and safer than sharing a mutable buffer).

Converting between String and StringBuffer/StringBuilder:

String str = "kamanotes";
StringBuffer viaCtor = new StringBuffer(str);      // way one: pass directly into the constructor
StringBuffer viaAppend = new StringBuffer();
viaAppend.append(str);                             // way two: build an empty one first, then append

String back1 = viaCtor.toString();                 // StringBuffer -> String: toString()
String back2 = new String(viaAppend);              // StringBuffer -> String: an overloaded String constructor
kamanotes kamanotes

Summary

  • The 8 primitive types are fixed-width, cross-platform, with no unsigned; char is a 16-bit UTF-16 code unit; the size of boolean is unspecified.
  • Wrapper classes box values into heap objects; Integer caches [-128,127], causing == to be true for small values and false for large ones—compare values with equals.
  • A HotSpot object = object header (Mark Word + Klass pointer) + instance fields + padding; the Mark Word reuses the same bits on demand to carry the hash, GC age, and lock state, trading encoding complexity for a smaller fixed overhead per object; fields are reordered; compressed oops exploits the fact that “objects are 8-byte aligned, so the low 3 bits of the address are always 0” to squeeze references down to 4 bytes (heaps < 32GB).
  • Arrays are objects on the heap: they have a length field and bounds checks; elements are contiguous, but reference arrays store references, and multidimensional arrays are arrays of arrays (not guaranteed contiguous overall).
  • String is immutable, internally a byte[] + encoding marker with no \0; literals share the constant pool, intern() retrieves the canonical instance; use StringBuilder for frequent concatenation.
  • Boxing pitfalls go beyond ==: cross-wrapper-type equals (e.g. Long vs Integer) is always false, and using a wrapper class outside the cache range as a lock object plants a concurrency hazard due to “looks like value semantics, actually reference identity.”
  • StringBuffer and StringBuilder have identical APIs and homologous internals (AbstractStringBuilder); the only difference is that the former has method-level synchronized; local-variable scenarios almost never need this synchronization, so prefer StringBuilder.
