Runtime Model: javac, Bytecode, the JVM, and JIT

The compilation pipeline of C/C++ is single-stage: gcc/clang compiles .c source directly into machine code for the target CPU architecture, and after linking you get an executable bound to a specific OS/architecture. Java is two-stage: javac first compiles source into a platform-independent intermediate representation (bytecode), and then the JVM turns that bytecode into instructions actually executed on the target machine. This chapter clarifies every link in this chain, and why the extra bytecode layer is inserted — this is the foundation for understanding everything that follows: the memory model, the call stack, concurrency.

1. The Minimal Compile-and-Run Flow

The minimal skeleton of a Java program: one class containing one main method; the program starts running from main.

// Hello.java
public class Hello {
    public static void main(String[] args) {
        System.out.println("Hello, Java");
    }
}

A few rules you can put to use right away:

  • The file name must exactly match the name of the public class: this class is called Hello, so the file must be called Hello.java.
  • Compile: javac Hello.java — produces a Hello.class file.
  • Run: java Hello — note it’s the class name Hello, without the .class suffix, and not the file name.
javac Hello.java
java Hello

Output:

Hello, Java

Let’s write another one with a variable and some arithmetic to reinforce the “compile → run” flow:

// Add.java
public class Add {
    public static void main(String[] args) {
        int a = 3;
        int b = 4;
        int sum = a + b;
        System.out.println(sum);
    }
}
javac Add.java
java Add

Output:

7

javac compiles, java runs; the IDE merely automates these two steps for you. What lies behind these two steps is what this chapter sets out to unpack.

2. From Source to Bytecode: What javac Produces

// Hello.java
public class Hello {
    public static void main(String[] args) {
        int sum = 0;
        for (int i = 0; i < 10; i++) {
            sum += i;
        }
        System.out.println(sum);
    }
}

Compile:

javac Hello.java     # produces Hello.class

The essential difference between javac and gcc: gcc’s output targets a real CPU, with an instruction set of x86-64 / ARM64; javac’s output targets a hypothetical stack-based virtual machine, whose instruction set is “bytecode.” Bytecode assumes no particular number of registers, no word size, no byte order — it targets only the abstract machine defined by the JVM specification. This is the technical foundation of “write once, run anywhere”: the .class file is byte-for-byte identical across Windows/Linux/macOS and x86/ARM.

The .class file is a binary container with a strict format (beginning with the magic number 0xCAFEBABE), containing:

Section Contents C/C++ analogy
constant pool symbolic references to strings, class names, method names, and literals similar to .rodata + symbol table, but more structured
field table the class’s field declarations struct member layout info
method table each method’s bytecode + metadata function bodies, but with full type signatures
attribute table line number table, local variable table, annotations, etc. debug info (like DWARF), but built in

Why insert an extra bytecode layer, rather than compiling straight to machine code like gcc: this is a deliberate trade-off between “portability” and “peak performance.” Compiling directly to machine code (AOT, Ahead-Of-Time) lets the compiler see the full set of target CPU features at compile time and perform deep static optimization, so the program runs at peak speed from startup — but the artifact is tightly bound to the target CPU architecture, operating system, and ABI. Moving it to a different CPU means recompiling; this is the cost of the C/C++ model of “write once, compile separately per platform.” Java defers the “translate into concrete machine instructions” step to run time; the compiler only needs to target an abstract stack-based virtual machine, and the resulting .class file is byte-for-byte identical on any machine with a JVM, buying “write once, run anywhere.” The cost is an extra round of translation at run time (interpretation or JIT compilation), so the program cannot immediately reach native-code speed during the startup phase. Section 4’s JIT and Section 6’s GraalVM AOT will show how this trade-off is specifically compensated for, or chosen in reverse.

Key point: .class retains complete type and symbolic information. After a C program is stripped, almost nothing but machine code remains and symbols are lost; whereas .class inherently carries class names, method signatures, and field types — this is the material basis for reflection, dynamic loading, and runtime type checking to exist.

The following code relies on this retained information to read a method’s exact signature at run time — something you cannot do on a stripped C binary:

import java.lang.reflect.Method;

Class<?> c = java.util.ArrayList.class;
System.out.println("class = " + c.getName());
Method m = c.getMethod("add", Object.class);
System.out.println("method = " + m.getName());
System.out.println("returns = " + m.getReturnType().getName());
System.out.println("params = " + m.getParameterCount());
// Output:
// class = java.util.ArrayList
// method = add
// returns = boolean
// params = 1

Viewing Bytecode with javap

javap is the disassembler bundled with the JDK, the equivalent of objdump -d in the Java world:

javap -c Hello.class

The main method’s bytecode looks roughly like this (the comments are mine):

0:  iconst_0        // push constant 0 onto the operand stack
1:  istore_1        // pop the top of stack into local variable table slot 1 (i.e. sum)
2:  iconst_0        // push constant 0
3:  istore_2        // store into slot 2 (i.e. i)
4:  iload_2         // load i onto the stack
5:  bipush 10       // push constant 10
7:  if_icmpge 20    // if i >= 10, jump to offset 20 (exit the loop)
10: iload_1         // load sum
11: iload_2         // load i
12: iadd            // add the top two values, leaving the result on the stack
13: istore_1        // store back into sum
14: iinc 2, 1       // increment slot 2 (i) by 1 directly, without going through the operand stack
17: goto 4          // back to the loop condition
20: getstatic ...   // fetch System.out
23: iload_1
24: invokevirtual println
27: return

Note that instructions like iconst/istore/iload/iadd have no register operands. The JVM is a stack machine: the inputs and outputs of operations flow through the “operand stack,” rather than naming registers as x86 does with add eax, ebx. The i prefix indicates operating on the int type; there are also l (long), f (float), d (double), and a (reference, address). iinc is one of the rare instructions that can modify the local variable table directly.

Each method declares in its bytecode how large an operand stack it needs (stack=) and how many local variable slots (locals=). These are fixed values computed at compile time, and the JVM allocates the stack frame accordingly — see “Functions and the Call Stack”.

3. Class Loading: Getting the .class into the JVM

When a C program starts, the loader maps the ELF segments into memory, does relocation, and binds dynamic library symbols, all in one shot. Java’s class loading is lazy, on-demand, and happens at run time, in three phases.

Why class loading is designed to be lazy: a typical Java program depends on hundreds or thousands of classes at compile time (the JDK core library + third-party libraries). If, at startup, it loaded and resolved all dependencies at once like C static linking, startup time would grow linearly with the size of the dependency graph — yet most of those classes are never used in a given run (an exception-handling class for a branch never taken, a feature module never triggered). Lazy loading spreads the cost of loading/linking/initialization out to the moment “this class is actually used for the first time”; untouched classes cost exactly nothing. This is a direct engineering choice under the “fast startup” goal. It has a secondary benefit too: classes can come from places that don’t even exist yet (the network, dynamically generated bytecode, an implementation a plugin only supplies at run time) — all that’s required is that the byte stream can be found before it’s actually used. This is impossible under a static linking model that “must see all symbols at link time.”

3.1 Loading

Locate the .class byte stream by the class’s fully qualified name (from the file system, a jar, the network, or even generated at run time), parse it into an internal data structure in the method area / metaspace, and create on the heap a java.lang.Class object representing this class. This step is similar to dlopen opening a library, but at the granularity of a single class.

3.2 Linking (three sub-steps)

  • Verification: check that the bytecode is legal, that types are safe, and that the stack will not overflow/underflow. C/C++ has no counterpart — it trusts the machine code its compiler produces; the JVM, because it may load bytecode of unknown origin, must perform this layer of safety checking.
  • Preparation: allocate space for static fields and set them to zero values (int→0, reference→null). Note that user-supplied assignments are not executed at this point.
  • Resolution: replace the symbolic references in the constant pool (“method foo of class A”) with direct references (memory addresses/offsets). This is equivalent to C’s link-time symbol resolution, but happens at run time, and can be deferred until first use.

3.3 Initialization

Execute the static initializer blocks and the assignments of static fields (i.e. the <clinit> method). Trigger points: first new, accessing a static field/method, reflection, etc. The JVM guarantees that <clinit> runs exactly once even under multiple threads (with a lock), which is why the “static singleton + class loading” idiom is thread-safe.

The following code verifies “lazy + exactly once”: the static initialization of Config does not happen until it is actively used for the first time, and a subsequent access does not repeat it:

static class Config {
    static { System.out.println("  [Config <clinit> runs]"); }
    static final int READY = compute();
    static int compute() { System.out.println("  [compute() runs]"); return 42; }
}
public static void main(String[] a) {
    System.out.println("main start");
    System.out.println("before touching Config");
    int v = Config.READY;   // first active use -> triggers <clinit>
    System.out.println("Config.READY = " + v);
    int v2 = Config.READY;  // access again -> <clinit> does not run again
    System.out.println("Config.READY = " + v2);
}
// Output:
// main start
// before touching Config
//   [Config <clinit> runs]
//   [compute() runs]
// Config.READY = 42
// Config.READY = 42

Note that [Config <clinit> runs] appears after before touching Config — class loading really is deferred to the moment the class is used.

The Full Lifecycle: Scenarios That Trigger Initialization, and Class Unloading

The demo above showed “first active use” triggering <clinit>; to list them out fully, the JVM specification actually defines several active use scenarios: initializing the main class containing main when the virtual machine starts; the first new of an instance of a class; the first access to a class’s static field or call to a static method (excluding final constants determinable at compile time — those are inlined directly into the caller’s constant pool at compile time, and do not trigger initialization of the referenced class); the first reflective access to a class (Class.forName triggers it with its default arguments); and, when initializing a class, if its superclass is not yet initialized, recursively initializing the superclass first. Any other “passive reference” (e.g. referencing a superclass static field through a subclass, declaring an array without instantiating it, referencing the compile-time constants just mentioned) does not trigger initialization — this is the “lazy loading” principle carried through to the end, and the concrete landing at the level of detail of the “lazy class loading” design goal.

The Preparation step of linking also has an exception worth noting: an ordinary static field only receives its zero value at this step, but a constant modified with static final whose value is determinable at compile time is inlined directly into the constant pool of the class that references it at compile time; the Preparation step allocates no memory for it separately at all, nor does it need to wait for the target class to finish initializing. This is precisely the cause of the classic pitfall that “after a class’s static final int constant value is modified, caller code that hasn’t been recompiled still uses the old value”: what the caller obtained was never a “read once at run time” value, but a literal already copied into its own constant pool at compile time.

Classes are likewise unloaded: only when three conditions are met simultaneously — all instances of the class have been reclaimed, the class loader that loaded it has itself been reclaimed, and its java.lang.Class object is not referenced anywhere (no longer reachable via reflection) — will the class metadata in the method area be reclaimed by GC. The core classes loaded by the Bootstrap ClassLoader are in practice never unloaded, because the lifetime of the Bootstrap ClassLoader itself equals that of the entire JVM process; what can be unloaded is usually only classes loaded by custom class loaders (common in container/plugin hot-deployment scenarios, and a failure to unload is precisely the root of “class loader leaks”). Note that class unloading reclaims the metadata in the method area, which is a different matter from the garbage collection of object instances on the heap — a class being unloaded does not mean all the instances it once created disappear with it; those instances are still judged separately by the heap’s reachability analysis (see “Error Handling and Resource Management”).

The Parent Delegation Model

There are multiple class loaders in the JVM, forming a hierarchy:

        Bootstrap ClassLoader   (C++ implementation, loads the java.* core classes)
              ▲  delegates
        Platform ClassLoader    (JDK platform modules)
              ▲  delegates
        Application ClassLoader (your classpath)
              ▲  delegates
        Custom ClassLoader

When loading a class, a child loader first delegates upward to its parent to try; only if the parent cannot load it does the child load it itself. The benefit: core classes (such as java.lang.String) are always loaded by Bootstrap, and you cannot substitute a forged java.lang.String for the system class — this is a guarantee of security and consistency. In C/C++, if two .so files each carry a symbol of the same name, the behavior depends on link order and is prone to problems; parent delegation avoids the “hijacking” of core classes by mechanism.

Class Uniqueness: Fully Qualified Name + Class Loader

When the JVM decides whether two classes “are the same class,” it looks not only at the class name but at the fully qualified name + the class loader that loaded it, together. Even if the bytecode is completely identical, as long as it is defineClassed separately by two different class loaders, the JVM regards them as two unrelated types — instanceof evaluates to false, and casting between them throws ClassCastException. The following uses two custom class loaders to load the same .class bytecode separately to verify this (first compile a minimal Sample.java on its own to get Sample.class, then run the loaders below):

// Sample.java —— compile with javac first; the loaders below read its bytecode directly
public class Sample {}
import java.io.*;
import java.nio.file.*;

// Custom class loader: override loadClass() (rather than the usually recommended findClass()),
// "skip upward delegation" for the specified class name and load the byte stream ourselves ——
// this is the most direct means of breaking parent delegation.
class BreakingLoader extends ClassLoader {
    private final String targetClassName;
    BreakingLoader(String targetClassName) {
        super(null); // no parent, to simulate the extreme case of "no delegation at all"
        this.targetClassName = targetClassName;
    }
    @Override
    protected Class<?> loadClass(String name, boolean resolve) throws ClassNotFoundException {
        if (!name.equals(targetClassName)) {
            return ClassLoader.getSystemClassLoader().loadClass(name);
        }
        try {
            byte[] bytes = Files.readAllBytes(Paths.get("Sample.class"));
            Class<?> c = defineClass(name, bytes, 0, bytes.length);
            if (resolve) resolveClass(c);
            return c;
        } catch (IOException e) {
            throw new ClassNotFoundException(name, e);
        }
    }
}

public class BreakDelegation {
    public static void main(String[] args) throws Exception {
        BreakingLoader loader1 = new BreakingLoader("Sample");
        BreakingLoader loader2 = new BreakingLoader("Sample");
        Class<?> c1 = loader1.loadClass("Sample");
        Class<?> c2 = loader2.loadClass("Sample");

        System.out.println("c1 == c2 ? " + (c1 == c2));
        Object o1 = c1.getDeclaredConstructor().newInstance();
        Object o2 = c2.getDeclaredConstructor().newInstance();
        System.out.println("o1.getClass() == o2.getClass() ? " + (o1.getClass() == o2.getClass()));
    }
}
// c1 == c2 ? false
// o1.getClass() == o2.getClass() ? false
// (forcibly casting between them throws ClassCastException: Cannot cast Sample to Sample)

This is not a bug; it is the very core property that parent delegation exists to protect: the class loader + fully qualified name together constitute a type’s identity card. Precisely because of this, parent delegation turns “core class libraries can only be loaded by Bootstrap” into an enforceable constraint — even if a user defines a java.lang.String of the same name, parent delegation first delegates the load request to Bootstrap, and the one that ultimately takes effect is still the one that ships with the JDK; even if the forged version really were loaded, it would not be the same type as the String used everywhere else in the system, they would be incompatible, and so it would naturally fail to serve as a “replacement.”

How to Break Parent Delegation

Parent delegation is not a rule enforced by the language, but a convention in the default implementation of ClassLoader.loadClass() — as long as you override this method, you can avoid the “ask the parent first” path. Three common approaches:

  1. A custom class loader overriding loadClass(): the demo above is the most direct way — don’t call super.loadClass(), and decide for yourself whether to delegate and where to read the bytecode from. The JDK’s officially recommended conventional practice is usually to override only findClass() (which is called only after the parent loader fails), thereby preserving the “ask the parent first” order of parent delegation; overriding loadClass() itself directly, as above, is the true “breaking.”

  2. The SPI mechanism + the thread context class loader: the classic conflict scenario is JDBC — java.sql.DriverManager is loaded by Bootstrap, but the concrete database driver implementation (e.g. com.mysql.cj.jdbc.Driver) is on the application’s classpath, loaded by the Application ClassLoader. Under standard parent delegation, the DriverManager loaded by Bootstrap cannot delegate in reverse to its “child” the Application ClassLoader to load the driver class. The JDK’s solution is to attach to each thread a thread context class loader, which by default is the Application ClassLoader; DriverManager internally obtains it via Thread.currentThread().getContextClassLoader() and “borrows” the child loader in reverse to load the driver — a workaround of reverse lookup from the top layer down to a lower layer. java.util.ServiceLoader (the core of the Java SPI mechanism) uses the same context-class-loader machinery to solve the loading problem of “the interface is defined in the core library, the concrete implementation is at the application layer.”

  3. Tomcat’s class loader isolation: multiple web applications deployed in the same Tomcat may each depend on different versions of the same class library. Under strict parent delegation, all classes would ultimately delegate to the same Application ClassLoader, and same-named classes of different versions would conflict with one another. Tomcat’s solution is to give each web application its own independent WebappClassLoader, and to reverse the default lookup order: prefer loading classes under its own WEB-INF/classes and WEB-INF/lib, and only delegate upward to the common parent loader if not found — this way each application’s classes are isolated from one another, and same-named libraries of different versions can coexist in a single Tomcat process. This is the most common production landing of “breaking parent delegation.”

4. Execution: The Mixed Mode of Interpretation + JIT

Once it has the bytecode, how does the JVM execute it? Two techniques are used together (HotSpot’s default “mixed mode”):

Interpreted Execution

The JVM has a built-in bytecode interpreter that reads bytecode one instruction at a time, looks it up in a table, and executes the corresponding C++ logic. It starts fast (no need to wait for compilation), but each instruction carries interpretation overhead, one or two orders of magnitude slower than native machine code.

Hot-Spot Detection + JIT Compilation

The name HotSpot comes from its strategy: detecting hot code (Hot Spot). The JVM maintains counters for each method (number of method invocations + number of loop back-edges); once a threshold is exceeded, it deems the method “hot” and hands that bytecode to the JIT (Just-In-Time) compiler to compile at run time into native machine code, after which the machine code is executed directly.

HotSpot has two JIT compilers (Tiered Compilation uses them cooperatively):

Compiler Role Characteristics
C1 (Client) fast compilation few optimizations, compiles fast, steps in first
C2 (Server) deep optimization aggressive optimizations, compiles slowly, used for the hottest code

Typical path: interpreted execution → C1 compilation (with performance counters) → C2 recompilation of the hottest parts.

Why JIT is needed, rather than picking one of pure interpretation or pure AOT: all three schemes are each stuck at an extreme. A pure interpreter has zero startup latency (no waiting for compilation), but every bytecode goes through the “fetch-lookup-dispatch” overhead, and even long-running code stays slow forever; pure AOT (like gcc) can do deep optimization ahead of time, but the compiler cannot see information only known at run time (that in this run a certain virtual-method call site is in fact hit by only one implementing class, or that a certain loop actually iterates billions of times and is worth aggressive unrolling), and can only optimize conservatively based on static assumptions. JIT stitches the advantages of both together: it runs immediately via interpretation (or the fastest C1) to avoid startup waiting; meanwhile it uses counters to continuously observe run-time behavior, and only once a piece of code is proven “hot” does it invest the higher compilation cost of the more aggressive C2, using the actually-observed branch probabilities and type information to do the speculative optimizations a static compiler wouldn’t dare. Tiered Compilation is precisely the reconciliation of the conflict between “startup latency” and “peak throughput”: C1 compiles fast and optimizes conservatively, responsible for getting code out of slow interpretation as early as possible; C2 compiles slowly and optimizes aggressively, invested only in the few genuine hot methods, avoiding wasting compile time on code that runs only once. A speculative optimization that bet wrong can deoptimize back to interpreted execution to re-collect information — this is the fallback mechanism for the cost that “run-time information may be stale or incomplete.”

This is why Java “gets faster as it runs,” and can sometimes approach or even locally surpass C: the JIT possesses run-time information — which branch is actually taken, that a certain virtual method is actually called by only one implementing class, what a certain loop’s bound is. It can accordingly do the speculative optimizations a static compiler cannot; if it bets wrong, it “deoptimizes” back to interpreted execution. Whereas gcc, at compile time, knows nothing about run time and can only be conservative.

A Few Key JIT Optimizations (with Big Effects on Memory Behavior)

  • Inlining: embed the callee’s method body directly at the call site, eliminating call overhead and further opening up the horizon for subsequent optimizations. Equivalent to C’s inline, but the JIT decides it automatically at run time based on hotness.
  • Escape Analysis: analyze whether a reference to an object “escapes” the current method (whether it is returned, stored into another object on the heap, or seen by another thread). If it does not escape, the JVM can do:
    • Scalar Replacement: break apart an object that would have been newed on the heap into its individual fields, treating them as ordinary local variables placed directly into stack frame slots or even registers. Note this is not “moving the whole object onto the stack”; rather, the object as a whole no longer exists at all — so there is neither a heap allocation nor a need for GC to reclaim it. (HotSpot does not actually have real “whole-object stack allocation”; the mechanism that eliminates heap allocation is scalar replacement.)

This point is important for your understanding of Java memory: at the Java language level “objects are all on the heap,” but at the HotSpot implementation level, escape analysis may keep short-lived, non-escaping objects out of the heap entirely. This closes part of the performance gap between Java and C (which puts structs on the stack). See “Variables and the Memory Model”.

5. Runtime Memory Regions

A running JVM divides memory into several regions (defined by the JVM specification, implemented by HotSpot):

┌───────────────────────────────────────────────────────┐
│                       JVM process                       │
│                                                         │
│  Shared by all threads ↓                                │
│  ┌─────────────────────┐   ┌───────────────────────┐   │
│  │        Heap          │   │ Method Area / Metaspace│   │
│  │  all objects, arrays │   │ class metadata,        │   │
│  │  the main GC arena   │   │ method bytecode        │   │
│  │  (everything new'ed) │   │ runtime constant pool  │   │
│  │                      │   │ (metaspace in native mem)│ │
│  └─────────────────────┘   └───────────────────────┘   │
│                                                         │
│  Private to each thread ↓                               │
│  ┌───────────┐ ┌───────────┐ ┌──────────┐ ┌──────────┐ │
│  │ JVM stack  │ │ PC register│ │native    │ │ ...      │ │
│  │ a pile of  │ │ current    │ │method    │ │one per   │ │
│  │ stack frames│ │ instruction│ │stack(JNI)│ │thread    │ │
│  └───────────┘ └───────────┘ └──────────┘ └──────────┘ │
└───────────────────────────────────────────────────────┘
Region Whose Stores C/C++ analogy
Heap shared all object and array instances the malloc heap, but reclaimed automatically by GC
Method Area / Metaspace shared class structures, method bytecode, the runtime constant pool, and the metadata of static fields (the field values are stored in the Class mirror object on the heap, not in metaspace) code segment + read-only data segment (but can grow at run time)
JVM stack per-thread stack frames (local variable table, operand stack) the thread call stack; logically the same
PC register per-thread the address of the bytecode currently being executed the program counter PC/RIP
Native method stack per-thread the stack when executing native (JNI) methods the native stack on the C side

The table above is how runtime data is laid out; calling these native methods relies on two other components. The Native Method Interface (i.e. JNI): when a method is marked with the native keyword, the execution engine does not interpret/compile its bytecode (it has no bytecode body at all), but jumps through the JNI layer to the native implementation. The Native Method Library: stores the actual implementations of these native methods (.so/.dll) — for example, the file-reading operation of java.io.FileInputStream, and thread creation and scheduling, ultimately have to be completed by calling into the system calls provided by the operating system through the native method library. The Java language itself cannot directly touch operating-system kernel resources; this is an inevitable cost of its cross-platform design, and the native interface + native method library are precisely what fill this “must deal with the specific OS” gap. At this point, the class loader (this section’s “class loading”), the runtime data areas (the table above), the execution engine (interpreter + JIT, the previous section), the native method interface, and the native method library — the five major components defined by the JVM specification — all have their corresponding landing places in this chapter.

How the Heap Is Subdivided Internally: TLAB, the Survivor Ratio, Large Objects, the String Constant Pool

The table above treats the heap as a single monolithic “object storehouse”; in the actual implementation HotSpot subdivides the heap more finely, and these details are used repeatedly in the GC chapter of “Error Handling and Resource Management”. Here we first establish a static understanding:

  • Default heap size: when -Xmx/-Xms are not specified explicitly, HotSpot gives default values as a fraction of physical memory — the initial heap size is about 1/64 of physical memory, and the maximum heap size is about 1/4 of physical memory (the exact ratios vary slightly by JDK version and platform). Production environments almost always set these two parameters explicitly rather than relying on defaults; the reason is in the next section.
  • TLAB (Thread Local Allocation Buffer): the Eden region carves out a small portion (by default about 1% of Eden) as a small “thread-local allocation buffer” owned exclusively and privately by each thread. New objects are allocated first in the thread’s own TLAB via pointer bumping, without needing a lock; only when the TLAB is full does the thread go and contend for the allocation lock over the whole of Eden. This is the key optimization by which “multiple threads newing objects at once” avoids lock contention, and the concrete mechanism behind the impression that “object allocation is very fast.”
  • The default Eden : Survivor0 : Survivor1 ratio is 8 : 1 : 1 (-XX:SurvivorRatio=8): this ratio is based on the weak generational hypothesis that “most objects don’t survive a single Minor GC” — the Survivor space left for surviving objects need not be large, and leaving more space for Eden makes Minor GC trigger less often.
  • Large objects go straight to the old generation: objects exceeding the -XX:PretenureSizeThreshold threshold (the typical scenario being large arrays) skip the young generation and are allocated directly into the old generation — avoiding the cost of copying a large object back and forth between Eden/Survivor, and avoiding forcing a premature Minor GC because the young generation can’t fit the large object.
  • The String Constant Pool (String Pool): since JDK 7 it was moved from the permanent generation into the heap, used to hold strings after String.intern(), ensuring that string literals with identical contents have only one copy in the pool, avoiding duplicate objects — literal concatenations determinable at compile time such as "a" + "b" are automatically interned, but new String("ab") is not.
  • Direct Memory: what ByteBuffer.allocateDirect() allocates is off-heap memory, not subject to -Xmx, not directly managed by GC, and freed via the phantom-reference/Cleaner mechanism as a side effect when the associated Java object is reclaimed (“Error Handling and Resource Management” has a full example of phantom references). -XX:MaxDirectMemorySize specifically caps its upper bound, and is a separate accounting system from heap memory.

A few comparisons with C: - Metaspace is in native memory, not in the GC heap (this is the design since JDK 8, replacing the old “permanent generation, PermGen”). - Heap reclamation is automatic: there is no free/delete; GC reclaims what it judges unreachable. You almost never manage the heap lifecycle manually — this is the biggest mental difference from C, and the reason why in “Error Handling and Resource Management” try-with-resources targets only “non-memory resources” (files/sockets): memory is left to GC, but handles still need to be closed explicitly. - The semantics of the stack are almost the same as C’s: each method call pushes a stack frame, popped on return; if the stack gets too deep it triggers StackOverflowError (corresponding to C’s stack overflow, but the JVM throws an exception rather than segfaulting directly).

6. AOT: GraalVM native-image

Java can also, like C, be Ahead-Of-Time compiled into a native executable. GraalVM’s native-image performs closure analysis at build time, statically compiling and packaging the classes and methods used, and even a slimmed-down runtime (including a GC), into a single standalone executable:

native-image Hello        # produces a native executable, hello
./hello                   # no JVM needed, millisecond startup

Costs and trade-offs: - Advantages: extremely fast startup, small memory footprint, no need to ship a JVM — suitable for CLI tools and Serverless/function-computing cold starts. Here it is much like C’s distribution model: a single native binary. - Costs: at build time all classes that will be used must be known, so reflection, dynamic proxies, and runtime class generation need extra configuration; and it loses JIT’s run-time speculative optimizations, so peak throughput may be inferior to C2 after a long warm-up.

So, for comparative memory: - javac → bytecode, cross-platform, runs via JVM + JIT run-time optimization (the mainstream for long-running services). - native-image → native code, platform-bound, fixed at build time (the choice for fast-startup, short-lived processes). - gcc/clang → native code, platform-bound, fixed at compile time (C/C++’s only path).

7. A Quick Reference of Common JVM Parameters

The sections above separately explained the principles of heap generations, metaspace, and class loading; here we gather the corresponding startup parameters into one quick-reference table — those -X/-XX-prefixed parameters after the java command are exactly what turn the “concepts” of the previous sections into “tunable knobs.”

Category Parameter Effect
Heap memory -Xms<size> initial heap size
Heap memory -Xmx<size> maximum heap size (production recommendation: set equal to -Xms to avoid the extra pause of dynamic resizing at run time)
Heap memory -Xmn<size> young generation size (set directly; takes priority over -XX:NewRatio)
Heap memory -XX:NewRatio=<n> old-gen/young-gen ratio, default 2 (old gen occupies about 2/3)
Heap memory -XX:SurvivorRatio=<n> Eden/single-Survivor ratio, default 8
Stack -Xss<size> per-thread JVM stack size; shrinking it lets you spawn more threads when total memory is limited, enlarging it is the direct means of dealing with StackOverflowError (deep recursion)
Method area -XX:MetaspaceSize=<size> the initial threshold at which metaspace triggers a Full GC (not a hard cap); when usage exceeds it, a GC is first triggered to try to reclaim class metadata, after which the JVM dynamically raises the threshold as appropriate
Method area -XX:MaxMetaspaceSize=<size> the hard cap on metaspace; only exceeding it truly OOMs; unset, it is by default almost unbounded (constrained only by native memory)
Method area (deprecated) -XX:PermSize / -XX:MaxPermSize the permanent-generation parameters of JDK 7 and earlier; since JDK 8 the permanent generation is replaced by metaspace and these parameters no longer take effect
GC selection -XX:+UseSerialGC / -XX:+UseParallelGC / -XX:+UseG1GC / -XX:+UseZGC select the collector, see “Error Handling and Resource Management · The Evolution of Collectors”
GC tuning -XX:MaxGCPauseMillis=<ms> the target pause time for G1/ZGC (a soft goal, not a hard guarantee)
GC tuning -XX:ParallelGCThreads=<n> the number of threads in the parallel GC phase, default equal to the number of CPU cores
GC tuning -XX:MaxTenuringThreshold=<n> how many Minor GCs an object survives in Survivor before being promoted to the old generation, default 15
Diagnostics -Xlog:gc* print GC logs (JDK 9+ unified logging framework); the first step in tuning is always to look at the logs first
Diagnostics -verbose:class print class-loading information, to investigate parent-delegation-related questions like “who exactly loaded this class” or “why was it loaded twice”
Diagnostics -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=<path> automatically export a heap snapshot on OOM, to find memory leaks with MAT/VisualVM

Why -Xms and -Xmx should be set equal in production: the process of the heap growing from its initial size to its maximum size itself requires requesting new memory from the operating system and recomputing generation boundaries, and this action triggers an extra pause; if the heap size keeps oscillating during the run (growing, then shrinking after GC), you are stacking a layer of resize overhead on top of the normal GC pauses. Fixing them to the same value is equivalent to grabbing “the memory you’ll use later” all at once at startup, trading space for stability — which is also why, in high-concurrency, latency-sensitive scenarios (like flash sales), the first step of tuning is always to lock -Xms/-Xmx to the same value before talking about other parameters; by the same token, -Xmn is usually enlarged to between 1/2 and 2/3 of -Xms, because such scenarios produce a large number of extremely short-lived temporary objects, and you want them reclaimed by the copying algorithm within the young generation as much as possible, to avoid premature promotion to the old generation slowing down Major GC.

The difference between -XX:MetaspaceSize and -Xmx is worth emphasizing on its own: it is not a “maximum” but “the threshold for the first Full GC that reclaims class metadata” — when metaspace usage reaches this value, the JVM first attempts a Full GC to unload no-longer-used classes; if reclamation is insufficient it dynamically raises this threshold, and so on repeatedly; the true hard cap is -XX:MaxMetaspaceSize. This is also the common cause of a service that “loads many classes but hasn’t configured MaxMetaspaceSize” having its native memory endlessly eaten by metaspace after long running (the typical scenario: frameworks that generate lots of classes dynamically, where a bytecode-enhancement library keeps producing new classes while the corresponding class loaders are not reclaimed — the aforementioned “class loader leak”).

Summary

  • Flow: javac filename.java compiles (the class name must match the file name) → java classname (no suffix) runs; the IDE just automates these two steps.
  • javac produces platform-independent bytecode rather than machine code; the cost is that at run time the JVM, this stack-based virtual machine, must translate it once more, and what you buy is that the same .class runs anywhere; this is the trade-off between portability and AOT peak performance.
  • Class loading is run-time, lazy, and layered (parent delegation) — lazy loading spreads the cost out to the moment a class is actually used, avoiding paying the startup cost for classes never used; parent delegation ensures core classes won’t be replaced by forged versions, and a class’s uniqueness is determined jointly by “fully qualified name + class loader.”
  • Parent delegation can be broken: a custom class loader overriding loadClass(), the SPI mechanism doing reverse lookup via the thread context class loader, and Tomcat giving each web application an independent WebappClassLoader and reversing the lookup order — three approaches serving three different practical needs.
  • HotSpot interprets first, then JITs after detecting hot spots (C1 steps in with fast compilation, C2 deeply optimizes the hottest code); Tiered Compilation is precisely the reconciliation of the conflict between “startup latency” and “peak throughput”; escape analysis can perform scalar replacement on non-escaping objects (breaking them into scalars placed into stack frames/registers, rather than whole-object stack allocation).
  • Runtime memory divides into the shared heap/metaspace and the per-thread JVM stack/PC/native stack; the heap is reclaimed automatically by GC; internally the heap also has TLAB, the 8:1:1 Survivor ratio, large objects going straight to the old generation, the string constant pool, and other finer partitions — all concrete landings of the weak generational hypothesis.
  • JVM parameters turn “concepts” into “knobs”: production advice is to lock -Xms/-Xmx to the same value to avoid dynamic-resize pauses, and -XX:MetaspaceSize is the threshold that triggers a Full GC rather than a hard cap — the difference between the two is the easiest thing to confuse when investigating memory problems.
  • When you need a C-style fast-startup native binary, use GraalVM native-image for AOT; the cost is sacrificing run-time dynamism and peak optimization.
