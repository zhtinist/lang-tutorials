Variables and the Memory Model: What Really Happens in a = b

Most of the “weird bugs” a C/C++ programmer hits after switching to Java stem from a misunderstanding of what actually happens in memory during assignment, comparison, and parameter passing. This chapter thoroughly clarifies stack frames, the heap, and the two camps of variables.

1. Basic Syntax of Declaration and Assignment

In Java, declaring a variable is type name = value;, almost the same as C:

public class VarDemo {
    public static void main(String[] args) {
        // Primitive types: the variable holds the value directly
        int age = 20;
        double price = 9.9;

        // Reference types: the variable holds "a reference pointing to an object"
        String name = "Ada";              // a String object
        int[] nums = new int[]{1, 2, 3};  // an array object

        System.out.println(age);    // 20
        System.out.println(price);  // 9.9
        System.out.println(name);   // Ada
        System.out.println(nums[0]);// 1

        // Assignment: copy the value/reference on the right of = into the variable on the left
        int age2 = age;      // what's copied is the numeric value
        age2 = 99;
        System.out.println(age);     // 20, unaffected

        int[] nums2 = nums;  // what's copied is the "reference"
        nums2[0] = 100;
        System.out.println(nums[0]); // 100! both variables point to the same array
    }
}

Changing age2 does not affect age, but changing nums2[0] also changes nums[0]. This is neither coincidence nor a bug, but the core mechanism this chapter is about to explain thoroughly.

Let’s put the core conclusion up front, then argue it point by point:

Java variables come in two camps: primitive-type variables hold the “value” directly; reference-type variables hold a “reference value” — a JVM-managed pointer that points to an object on the heap. a = b is always “copy the bits inside b into a”: for primitive types this copies the value itself, for reference types it copies that pointer (from then on the two variables point to the same heap object).

2. The Two Camps

Camp Members What the variable stores Where the data is
Primitive types byte short int long float double char boolean the value itself (bits) where the variable is (a stack frame slot, or inlined in an object field)
Reference types classes, interfaces, arrays, String, wrapper classes, enums… the reference value (≈ pointer) the object the reference points to is on the heap

Put in C terms: - A primitive-type variable ≈ int a;; the memory of a directly is that integer. - A reference-type variable ≈ Foo* p;; the memory of p holds an address, and the real Foo is on the heap (allocated by new). But you cannot do arithmetic on this “pointer,” cannot dereference it to take an address, cannot cast it to an integer — it is a JVM-managed, constrained pointer.

HotSpot implementation detail: a reference on a 64-bit JVM usually occupies 8 bytes, but with compressed pointers (CompressedOops) enabled it is squeezed to 4 bytes (using a 35-bit addressable encoding, effective by default for heaps < 32GB). See “Data Types”. The language specification does not prescribe the concrete representation of a reference, only its semantics.

Why divide into two camps, rather than “everything is an object” like Python/Smalltalk: this is a trade-off between performance and consistency. The “everything is an object” model is conceptually cleaner — any value has a uniform method-call interface, and containers can hold anything indiscriminately — but the cost is that every integer, every boolean, must be an object on the heap, and even a loop variable i++ goes through an object allocation (or at least a boxing operation and a cache lookup) and an indirect reference dereference, whereas a register-level integer addition by the CPU takes just one clock cycle. Java’s trade-off is: pull the eight most frequent, fixed-size types that semantically just “are a value” (byte/short/int/long/float/double/char/boolean) out of the object system, store them directly as values in stack frame slots or object fields, without going through indirect reference addressing, without occupying the extra space of an object header (see the object-header overhead in “Data Types”), able to be mapped by the JIT directly into registers to participate in operations. The cost is that primitive types lose the uniformity of “everything is an object” — they cannot be put into generic containers that require Object (List<int> is illegal), and must be boxed into wrapper types like Integer to be brought into the object system, which gives rise to the boxing overhead and wrapper-class caching discussed in “Data Types”. This is “sparing 99% of high-frequency operations the object overhead” in exchange for “an extra type system that requires manual boxing/unboxing,” rather than making all values uniform but all slow.

3. Local Variable Table Slots: Where Variables Live

Each method call pushes a stack frame onto the current thread’s JVM stack; the frame contains a local variable table, composed of a number of slots (the count is fixed at compile time, see the javap in “Runtime Model”).

  • A slot is 32 bits. int/float/reference each occupy 1 slot; long/double occupy 2 consecutive slots.
  • Both method parameters and locals declared inside the method live in this table.

For a primitive-type local variable, the slot holds that value. For a reference-type local variable, the slot holds that reference (pointing into the heap). The object body is never in the slot, always on the heap (except with escape analysis, see the end of the chapter).

4. a = b: The Core of the Core

4.1 Primitive Types: Copy the Value

int b = 100;
int a = b;   // copy b's bits (100) into a's slot
a = 200;     // only changes a's own slot, b unaffected
// at this moment a=200, b=100

Memory diagram (stack frame local variable table):

 before assignment    after a = b          after a = 200
┌──────────┐       ┌──────────┐        ┌──────────┐
│ b │ 100  │       │ b │ 100  │        │ b │ 100  │
├──────────┤       ├──────────┤        ├──────────┤
│ a │  ??  │       │ a │ 100  │←copy   │ a │ 200  │
└──────────┘       └──────────┘        └──────────┘
     Two independent slots, unaffecting each other. Equivalent to C's int a=b;

This is exactly the same as C, no surprises.

4.2 Reference Types: Copy the Reference (what’s copied is the pointer, not the object!)

int[] b = new int[]{1, 2, 3};  // build an array object on the heap; b holds the reference to it
int[] a = b;                    // copy the "reference value"! a and b point to the same array
a[0] = 99;                      // modify the heap object through a
System.out.println(b[0]);       // prints 99! because b points to the same object

This is the intuition a C programmer most needs to build: int[] a = b; does not copy the array, but copies that pointer. It is equivalent to C’s int* a = b; (a shallow pointer copy), and not a memcpy.

Memory diagram:

      stack frame local var table          Heap
   ┌────────────────┐         ┌───────────────────────┐
   │ b │  ref ●──────┼────────▶│ int[3] object          │
   ├────────────────┤    ┌───▶│ [0]=99 [1]=2 [2]=3     │
   │ a │  ref ●──────┼────┘    │ (a[0]=99 changes here) │
   └────────────────┘         └───────────────────────┘
      a and b are two pointers to the same heap object (aliasing)

Compared with the primitive-type diagram, the difference is clear at a glance:

   Object a = b  (reference type)      int a = b  (primitive type)
   ┌───────┐                          ┌───────┐
   │ b │●──┼──┐                       │ b │100│
   ├───────┤  │   heap                ├───────┤
   │ a │●──┼──┴──▶[ object ]           │ a │100│ ← independent copy
   └───────┘  two pointers share one   └───────┘  two independent values
              object

Commit one sentence to memory: primitive-type assignment clones the “data,” reference-type assignment clones the “pointer.” The latter produces aliasing — modifying the object through either variable is visible to the other. This is exactly the same behavior as two pointers in C pointing to the same malloced memory.

4.3 What If You Want a Real Copy

Java does not deep-copy automatically (there is no C++ copy constructor triggered on assignment). To get an independent copy you must do it explicitly:

int[] a = b.clone();               // shallow copy of the array, yields a new object
int[] a2 = Arrays.copyOf(b, b.length);
List<T> copy = new ArrayList<>(src);  // the collection's copy constructor

Note these are mostly shallow copies: the container/array itself is new, but if it holds references inside, the element references still share the same batch of objects. A deep copy requires you to copy layer by layer.

Let’s measure this “shallow” — a 2D array clone() only copies the outer references, the inner arrays are still shared:

int[][] grid = {{1, 2}, {3, 4}};
int[][] copy = grid.clone();   // clone() is a shallow copy: only copies the outer references
copy[0][0] = 99;               // penetrates into the shared inner array
System.out.println(grid[0][0]);          // 99  <- the original object was changed too!
System.out.println(copy[0] == grid[0]);  // true -- the inner is the same array object

// A real deep copy must copy the inner arrays one by one
int[][] deep = new int[grid.length][];
for (int i = 0; i < grid.length; i++) deep[i] = grid[i].clone();
deep[1][0] = -1;
System.out.println(grid[1][0]);          // 3   <- this time the original object is safe

5. == vs equals

Once you understand the two camps, this classic pitfall follows naturally.

==: Compares “the bits in the variable”

  • Primitive types: compares the value. 3 == 3 → true. Intuitive.
  • Reference types: compares the reference — i.e. “is it the same heap object” (whether the addresses are the same), not the content.
String x = new String("hi");
String y = new String("hi");
System.out.println(x == y);        // false! two different heap objects, two different pointers
System.out.println(x.equals(y));   // true! compares content

Memory diagram:

 ┌───────┐        heap
 │ x │●──┼──▶[ String "hi" object① ]
 ├───────┤
 │ y │●──┼──▶[ String "hi" object② ]   x==y compares ● vs ●, different targets→false
 └───────┘                             x.equals(y) compares char by char→true

equals: Compares “content” (semantic equality)

equals is a method defined on Object, and can be overridden. The default implementation (Object.equals) is just == (compares references); but String, wrapper classes, collections, etc. override it to compare logical content instead. So: - To compare string/object content, always use equals. - Use == only when you really want to ask “is it the same object,” or to compare primitive types, or to compare against null.

Literals also have a “string constant pool” detail: the same literal reuses the same object in the pool, whereas new String(...) forces a new object — this happens to illuminate the difference between == (compares references) and equals (compares content) crystal-clearly:

String p = "hi";
String q = "hi";              // same literal -> same object in the pool
String n = new String("hi");  // new forces creation of a new heap object
System.out.println(p == q);         // true  -- both point to that object in the pool
System.out.println(p == n);         // false -- n is another object
System.out.println(p == n.intern());// true  -- intern() returns the one in the pool
System.out.println(p.equals(n));    // true  -- content is always equal

Paired with equals is hashCode: the contract is “if equals is equal, then hashCode must be equal,” otherwise putting them into a HashMap/HashSet goes wrong. See “Composite Data Structures”. In C++ you provide operator== and hash for unordered_map — it’s the same thing.

A Counterintuitive Trap: Wrapper-Class Caching

Integer a = 100, b = 100;
System.out.println(a == b);   // true  —— 100 is in the cache range
Integer c = 200, d = 200;
System.out.println(c == d);   // false —— 200 exceeds the cache, they are two objects

Integer has an object cache for [-128, 127]; when boxing, it reuses the same object, so == happens to be true; beyond that a new object is created and == is false. This precisely shows that == compares references. To compare the values of wrapper classes, always use equals or unbox first. Details in “Data Types”.

6. null

null is the “null reference” of reference types, equivalent to C’s null pointer nullptr — the variable points to no object.

String s = null;         // s's slot holds the "null reference" value
s.length();              // NullPointerException! "dereferencing" a null reference

The difference from C: dereferencing a null pointer in C is undefined behavior (most likely a segfault), while in Java it deterministically throws NullPointerException (NPE), which can be caught and carries a stack trace (Helpful NPE / JEP 358: introduced in JDK 14 but off by default, on by default since JDK 15, able to indicate which variable was null). Primitive types cannot be null (they hold a value, not a reference); int x = null; is a compile error. This is also why unboxing a wrapper-class Integer into an int throws NPE if it is null.

7. final Variable Semantics

final is often used to parallel C++’s const, but the distinction must be precise: final constrains “whether the variable’s slot can be assigned again,” not whether the object it points to can be changed.

final int x = 10;
// x = 20;                 // compile error: cannot reassign

final int[] arr = {1, 2, 3};
arr[0] = 99;               // legal! changes the content of the heap object, doesn't touch the reference arr
// arr = new int[5];       // compile error: cannot make arr point to another object

Understand it via the memory diagram: final locks down the slot on the left (cannot change what it points to), but cannot lock the content of the object in the heap on the right.

 final int[] arr ●═══▶[ 1, 2, 3 ]   ═══ means this reference is locked and can't be re-pointed
                        ↑ but the object content can still change: arr[0]=99 ok
  • To make “the object immutable too,” you must rely on the object’s own design (e.g. String is inherently immutable, or use an immutable collection List.copyOf(...)). This is similar to the C++ distinction of const int* p (can’t change the pointed-to content) vs int* const p (can’t change the target): Java’s final provides only the latter half — it locks the target, not the content.
  • final fields: must be assigned exactly once before construction completes, immutable afterward; there is a multi-thread visibility guarantee (after construction completes, other threads can see the correct final field values).
  • final local variables / parameters: often used for capture by a lambda (a lambda can only capture “effectively final” local variables, see “Functions and the Call Stack”).

Why final locks only the reference, not the content, rather than offering deep freezing like some languages: the root cause still lies in the unified rule a = b — assignment always copies “the bits in the variable,” and all final can constrain is whether these bits can be overwritten afterward; it governs the storage location that is the variable, not the content of the heap memory that location points to. Whether the content of a heap object can change depends on whether the class’s own defined methods expose “mutators” (e.g. an array exposes arr[i]=, an ArrayList exposes add, whereas String simply provides no mutation methods at all) — this is each type’s own contract, and there is no unified way at the language level to “freeze” an object graph of arbitrary shape (an object may recursively reference other mutable objects through its fields, deep freezing would require recursively traversing and copying the whole graph, and would have to cope with cyclic references). Limiting final to the single semantics of “lock the storage location” — uniform, cheap, and statically verifiable — buys the ability for the compiler to perform definite assignment analysis and the safe-publication guarantee for multiple threads consistently on any type, without having to separately define what “deep immutable” means for each type. When you genuinely need deep immutability, leave it to the concrete type’s own implementation (String is immutable, record combined with immutable collections, List.copyOf) — that is more reliable than forcing a generic but semantically vague “deep freeze” at the language level.

8. Putting Them into Object Fields

The above discusses local variables (in stack frame slots). An object’s fields follow the same two-camp rule, only their storage location is inside the object on the heap:

class Node {
    int value;      // primitive-type field: the value is inlined directly in the Node object's memory
    Node next;      // reference field: holds a reference pointing to another Node on the heap (or null)
}

Memory diagram (a Node object on the heap):

The Node object on the heap
┌─────────────────────────┐
│ [object header mark+klass]│  ← see the object layout in Chapter 4
│ value : 42              │  ← int value inlined
│ next  : ref ●───────────┼──▶ another Node object (or null)
└─────────────────────────┘

This is exactly what a linked list/tree looks like in Java: structurally isomorphic to C’s struct Node { int value; struct Node* next; };, the only differences being that next is a managed reference, the object is on the GC heap, and you don’t free it.

9. Escape Analysis: Language Semantics vs HotSpot Implementation

The language specification says “objects are all on the heap.” But in HotSpot, the JIT’s escape analysis (see “Runtime Model”), if it proves that a newed object won’t escape the current method, may do scalar replacement: break the object into several primitive values placed directly into stack frame slots or even registers, never entering the heap and needing no GC.

int distance() {
    var p = new Point(3, 4);   // p does not escape this method
    return p.x * p.x + p.y * p.y;
    // After HotSpot optimization: there may be no new at all; x, y become two on-stack local variables
}

So the precise statement is: - At the semantic level: reference-type objects are logically on the heap, assignment copies the reference, and aliasing holds. - At the implementation level: non-escaping objects may be scalar-replaced (broken into primitive values placed into stack frame slots/registers, rather than moving the whole object onto the stack), approaching the efficiency of C’s “struct on the stack” — but this is semantically transparent to the code you write; you need not, and cannot, control it directly.

This explains why creating lots of short-lived small objects in Java is often not as slow as you’d imagine.

10. Heap vs Stack: Five Dimensions Often Asked in Interviews

The previous sections have thoroughly explained the stack frame local variable table (slots) and heap objects separately; here we put the two head-to-head, comparing along the five dimensions most often asked about, and along the way answer “why their characteristics look the way they do.”

Dimension Stack (JVM stack / per-thread) Heap (Heap / globally shared)
Stores what stack frames: local variable table (slots), operand stack, return address objects and arrays newed
Ownership thread-private, each thread has its own independent stack thread-shared, all threads see the same heap
Lifecycle pushed on method call, popped and destroyed on return, deterministic an object lives until it becomes unreachable, judged by GC, non-deterministic (see “Error Handling and Resource Management”)
Allocation/reclamation speed extremely fast: pushing is essentially moving a stack-top pointer slower: the allocator must find a free block, GC periodically scans and reclaims
Space size small and fixed (-Xss, default about 512KB~1MB/thread) large and dynamically adjustable (-Xms/-Xmx)
Thread safety inherently safe, stack frames are invisible to other threads needs synchronization mechanisms (synchronized/volatile, see “Concurrency Model”) to ensure safe multi-thread access
Error on exhaustion StackOverflowError (see the recursion-exhausts-the-stack in “Functions and the Call Stack”) OutOfMemoryError: Java heap space (see “Error Handling and Resource Management”)

Why stack allocation is an order of magnitude faster than heap allocation: the stack’s lifecycle rules are extremely regular — last-in-first-out, a method call pushes a frame, a return pops a frame, the order determined entirely by the call relationships, with no need to consider “when is this block of memory freed” or “is anyone still using it.” This strict ordering degenerates allocation into a pointer bump operation: move the stack-top pointer down (or up, depending on the implementation) by a fixed offset and the allocation is done, and reclamation is even free — move the stack-top pointer back and that block of memory automatically “ceases to exist,” with no traversal, no marking, no extra bookkeeping needed. The heap is otherwise: an object’s lifetime is determined by a complex graph of reference relationships, at any moment some objects live long and some live short, the order utterly without pattern, and the allocator must find a suitable spot among a pile of free blocks of varying sizes (a free-list lookup or pointer bumping within a TLAB, see “Runtime Model”), and reclamation must rely on reachability analysis scanning the entire reference graph before it can judge who can be collected — this whole set of bookkeeping the stack needs none of, only because its lifecycle pattern (strictly nested call/return) is inherently far simpler than the heap’s lifecycle pattern (arbitrary object-graph lifetimes).

Why the stack is inherently thread-safe while the heap needs extra synchronization: a stack frame’s lifecycle is strictly bound to “the method call the current thread is executing” — each thread has its own independent JVM stack, and thread A’s stack frames are forever invisible to thread B, so two threads cannot possibly read/write the same stack-frame local variable at the same time; thread safety is a direct corollary of this “privacy,” needing no extra design. The heap, on the other hand, is an address space shared by all threads: any object newed by any thread, any reference held by any thread, could in theory be passed to another thread to hold — sharing means the possibility of concurrent access always exists, which is why Java needs the whole apparatus of synchronized/volatile/atomic classes to cope with the multi-thread visibility and contention issues of data on the heap. This also explains why local variables (on the stack) never need locking, whereas object fields (on the heap), once shared across threads, may need it.

Why one is smallish and fixed while the other is largish and adjustable: the stack’s size needs to be reserved at the very moment “a thread is created” (one stack per thread), and the number of threads is often tens to thousands; if each thread’s stack were opened very large, the total overhead would balloon linearly with the thread count, so the stack size is designed as a smallish default value (-Xss), enough to be usable, and enlarging it is usually only to accommodate deeper recursion; the heap is a single global instance, needing to be planned just once for the total object volume of the whole program, so it can and should naturally be opened larger, and left room for dynamic expansion (between -Xms and -Xmx) to adapt to run-time variation in the number of objects.

Summary

  1. The two camps of variables: primitive types hold the value, reference types hold the pointer (reference value); the division into camps is a trade-off between performance (avoiding object/boxing overhead for high-frequency operations) and consistency.
  2. a = b always copies “the bits in the variable”: for primitive types it’s a value copy (an independent copy), for reference types it’s a pointer copy (producing aliasing, sharing the same heap object). To get a copy you must explicitly clone/copy-construct, and the default is a shallow copy.
  3. == compares bits (for reference types, whether they are the same object), equals compares content — to compare object content, always use equals.
  4. null is the null reference; dereferencing it deterministically throws NPE (not UB); primitive types cannot be null.
  5. final locks only “what the variable points to,” not “the object content”: because it constrains the bit pattern that is the storage location, not the content of the heap memory that location points to; deep immutability is left to the type itself to implement (String, immutable collections), buying a semantics that is uniform and statically verifiable across any type.
  6. Object fields likewise follow the two-camp rule, only they live inside the heap object; linked lists/trees are isomorphic to C’s struct, only the reference is managed and reclaimed by GC.
  7. HotSpot escape analysis may perform scalar replacement on non-escaping objects (breaking them into scalars placed into stack frames/registers, rather than whole-object stack allocation), but this is semantically transparent.
  8. Stack allocation is fast, inherently thread-safe, small and fixed; heap allocation is slow, needs extra synchronization, large and adjustable — the root of all of it lies in the fact that the stack’s lifecycle is strictly nested (last-in-first-out, thread-private), while the heap’s lifecycle is determined by an arbitrary reference-relationship graph; stack exhaustion throws StackOverflowError, heap exhaustion throws OutOfMemoryError.
