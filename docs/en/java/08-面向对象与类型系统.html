Object Orientation and the Type System

This is the most OOP-concept-dense chapter in the book, touching on a dozen-odd topics: classes, inheritance, polymorphism, generics, records, sealed types, enums, and lambdas — what an object actually lays out on the heap, how virtual methods get dispatched, and what’s left of generics at runtime.

1. The Basic Shape of a Class: definition, inheritance, generics, lambdas

Procedural vs. Object-Oriented: a paradigm trade-off

C is a procedural language: a program is organized as a series of functions (procedures), and the data (struct) and the functions that operate on that data are two separate things — a struct Point is just data, distance(Point a, Point b) is defined separately somewhere else, and the struct itself has no idea which functions are operating on it. Java is object-oriented: it bundles the data and the methods that operate on it into the same type definition, so Point itself “knows” what can be done to it.

Why bundle data and functions together instead of keeping them separate as C does: the problem with the procedural approach is that once a struct is defined, functions that operate on it can pop up anywhere in the codebase; adding a new function requires no sign-off from whoever defined the struct and adheres to no contract — what the data “can do” is scattered across the whole program, and there is no single place that can answer “exactly which operations does this type support?” Object orientation puts methods and data inside the same class body, which first gives “what this type can do” a single, enumerable location (the class definition itself); second, a method accessing a field no longer has to receive it as an explicit parameter (this is bound implicitly, see below), so the call site reads more like natural language (“point.distance(other)” rather than “distance(point, other)”); and finally — most importantly — only by binding data and methods together can you even talk about encapsulation (whether the data can be modified directly from outside is decided by the class itself), inheritance (a subtype reuses the supertype’s data + methods), and polymorphism (the same method call gives different implementations for different types) — all three presuppose that “a method belongs to a type”, and in the procedural world there is no “belongs to” relationship to speak of.

The cost is equally direct: object orientation saddles every object with extra runtime structure (the object header, see below) and a layer of indirection (method lookup), unlike the procedural style where “data is just data, functions are just functions” with no hidden dispatch mechanism at all. C’s choice is “if you want a behavior, explicitly pass the data and call the function yourself”; Java’s choice is “the type carries its behavior, and at call time the runtime decides which piece of code to run” — which is exactly the root reason the dynamic dispatch (polymorphism) mechanism dissected later in this chapter exists.

Java is not a purely object-oriented language: the 8 primitive types (int/boolean/…) are not objects, have no methods, and cannot be inherited from (“Variables and the Memory Model” discussed how this is a trade-off between performance and consistency); this differs from Smalltalk’s “everything is an object”, but it doesn’t stop Java’s type system from being organized around objects overall.

The biggest difference between Java’s class and C’s struct: a class can hold functions directly (called “methods”), an object created with new always lives on the heap, and the variable stores a reference pointing to it (for details see “Variables and the Memory Model”).

class Point {
    int x, y;                          // fields (member variables)
    Point(int x, int y) {              // constructor: same name as the class, no return type
        this.x = x;                    // this refers to the current object, distinguishing field from parameter
        this.y = y;
    }
    int sum() {                        // method
        return x + y;
    }
}

public class PointBasics {
    public static void main(String[] args) {
        Point p = new Point(3, 4);     // new an instance
        System.out.println(p.sum());  // call a method: 7
        System.out.println(p.x);      // access a field directly: 3
    }
}
7
3

class Point { ... } is just a “blueprint”; new Point(3, 4) is what actually builds an object on the heap, and p holds a reference to that object. The same blueprint can new countless objects, and their fields don’t affect one another.

The simplest inheritance and interface

extends means “inherit a class” (single inheritance, you can write only one), and implements means “implement one or more interfaces”:

interface Greeter {
    String greet();                    // interface method: signature only, no implementation
}

class Animal {
    String name = "animal";
    String speak() {
        return name + " makes a sound";
    }
}

class Dog extends Animal implements Greeter {
    Dog() { name = "dog"; }
    @Override public String greet() { return "woof from " + name; }
}

public class InheritBasics {
    public static void main(String[] args) {
        Dog d = new Dog();
        System.out.println(d.speak());   // inherited method: dog makes a sound
        System.out.println(d.greet());   // interface-implementing method: woof from dog
    }
}
dog makes a sound
woof from dog

Dog both inherits Animal’s fields and methods (inheritance) and must write out the greet() that Greeter promises (implementing the interface) — @Override is a marker for the compiler and the reader, meaning “this overrides a method of the superclass/interface”; if you misspell the method name, the compiler reports an error immediately.

The simplest generic: Box<T>

The <T> after the class name means “this class can hold any type, and what it actually holds is decided by the user”:

class Box<T> {
    T value;
    Box(T value) { this.value = value; }
    T get() { return value; }
}

public class BoxBasics {
    public static void main(String[] args) {
        Box<String> b = new Box<>("hello");
        System.out.println(b.get());       // hello

        Box<Integer> n = new Box<>(42);
        System.out.println(n.get());       // 42
    }
}
hello
42

Box<String> and Box<Integer> are the same piece of code, with T replaced by a concrete type at the point of use; the compiler is responsible for checking that the types are right, and you don’t need to write a separate Box for each type.

The simplest lambda

Runnable is an interface with a single method run() (such interfaces are called “functional interfaces”); the lambda () -> ... simply writes an implementation for that method directly, without defining a class specifically for it:

public class LambdaBasics {
    public static void main(String[] args) {
        Runnable r = () -> System.out.println("running!");
        r.run();                          // call it just like an ordinary method
    }
}
running!

Java objects are uniformly allocated on the heap, and an object begins with a hidden “object header”, part of which points to the class-descriptor structure it belongs to (called klass in HotSpot) — this pointer plays much the same role as the vptr in C++: it determines which piece of code to jump to when calling a virtual method. The variable itself does not store the object, only this reference (for the details of value/reference semantics see “Variables and the Memory Model”; for the exact byte layout of the object header see “Data Types”).

With this model in mind, the sections below pry each topic apart one by one: initialization order, encapsulation, inheritance, polymorphism (vtable), abstract class vs. interface, Object, generic erasure, record, sealed, enum, inner classes and lambdas.

2. Initialization Order

A constructor can delegate to another constructor of the same class with this(...), or explicitly call a superclass constructor with super(...) (if you write neither, the compiler automatically inserts a no-arg super()):

class Person {
    String name;
    int age;
    Person(String name) { this(name, 0); }          // this(...): delegate to another constructor of this class
    Person(String name, int age) { this.name = name; this.age = age; }
}
class Student extends Person {
    String school;
    Student(String name, int age, String school) {
        super(name, age);                            // super(...): call the superclass constructor
        this.school = school;
    }
}
public class ConstructorBasics {
    public static void main(String[] args) {
        Student s = new Student("Ann", 20, "MIT");
        System.out.println(s.name + " " + s.age + " " + s.school);  // Ann 20 MIT

        Person p = new Person("Bob");                // goes through the this(...) delegation, age defaults to 0
        System.out.println(p.name + " " + p.age);     // Bob 0
    }
}
Ann 20 MIT
Bob 0

All instance methods of a Java class are “virtual” by default (except private/static/final). When you new an object, the JVM executes in a fixed order:

1. On first use of the class: static fields default to zero values → static initializer blocks + static field assignments (in source order, once only)
2. Instance creation: allocate heap memory, all instance fields set to zero values
3. Superclass instance initialization (recursively: superclass fields → superclass instance blocks → superclass constructor body)
4. This class's instance field default values → instance initializer blocks + field assignments (in source order)
5. This class's constructor body
class Base {
    String x = init("Base.x");        // ③
    Base() { System.out.println("Base()"); }
    static String s = init("Base.s");  // ① at class-loading time
    static String init(String m){ System.out.println(m); return null; }
}
class Derived extends Base {
    String y = Base.init("Derived.y"); // ④
    Derived() { super(); System.out.println("Derived()"); } // super() is implicitly first
}
// new Derived() prints: Base.s (first time) → Base.x → Base() → Derived.y → Derived()
Base.s
Base.x
Base()
Derived.y
Derived()

Compare C++: members are constructed in the initializer list in declaration order, and the base class before the derived class — Java’s order is similar, but there is no initializer-list syntax, and static initialization is lazy (triggered only on the first active use of the class, and the class loader guarantees it runs exactly once in a thread-safe manner).

The first line of a constructor must be this(...) or super(...); if you write neither, the compiler inserts a no-arg super(). Calling a virtual method during construction is dangerous: if a superclass constructor calls a method overridden by the subclass, the subclass’s fields are not yet initialized at that point (still zero values), so you read an uninitialized state. C++ binds a virtual call during construction statically to the current class’s version; Java binds it dynamically to the subclass’s version, which is more dangerous.

See the pitfall in the flesh: the superclass constructor calls the virtual method size(), which dispatches to the subclass version, but at that moment the subclass field value is still a zero value:

public class CtorVirtual {
    static class Base {
        Base() { System.out.println("Base ctor sees size = " + size()); } // virtual call
        int size() { return 0; }
    }
    static class Derived extends Base {
        int value = 42;                 // initialized only after super()
        @Override int size() { return value; }
    }
    public static void main(String[] args) {
        Derived d = new Derived();
        System.out.println("after ctor  size = " + d.size());
    }
}
Base ctor sees size = 0    <- dynamically dispatched to Derived.size(), but value is not yet assigned (zero value)
after ctor  size = 42      <- only after construction completes is it 42

3. Encapsulation

Access modifiers control “who can access this field/method”; the most common usage is to make a field private and expose only getters/setters:

class Account {
    private double balance;   // cannot be accessed directly from outside

    Account(double initial) { balance = initial; }

    public double getBalance() {     // can only be read through a method
        return balance;
    }
    public void deposit(double amount) {
        if (amount > 0) balance += amount;  // take the chance to validate
    }
}

public class EncapBasics {
    public static void main(String[] args) {
        Account a = new Account(100);
        a.deposit(50);
        System.out.println(a.getBalance());  // 150.0
        // a.balance = -999;    // compile error: balance is private, inaccessible from outside
    }
}
150.0

Access modifiers from narrow to wide: private < package-level (the default, no keyword) < protected < public. Note that Java’s protected also allows same-package access, giving it wider semantics than C++’s. There is no friend. The module system (JPMS) can encapsulate an entire package at a coarser granularity.

4. Inheritance: single inheritance + multiple interfaces

A class can extends only one superclass, but can implements any number of interfaces, separated by commas:

abstract class AbstractBase {
    void base() { System.out.println("base"); }
}
class Service extends AbstractBase implements Runnable, AutoCloseable {
    @Override public void run() { System.out.println("running"); }
    @Override public void close() { System.out.println("closed"); }
}
public class ServiceCheck {
    public static void main(String[] args) {
        Service s = new Service();
        s.base();
        s.run();
        s.close();
    }
}
base
running
closed

A Java class can only inherit singly (avoiding the complexity of C++’s diamond inheritance and virtual inheritance), but it can implement any number of interfaces.

Interfaces used to be allowed only abstract methods; since JDK 8 they can have default methods (with an implementation) and static methods, and since JDK 9 they can have private methods. This brings the ability to “inherit implementations multiply”, but fields are still only constants (public static final), so there is no stateful diamond problem. If two interfaces have default methods with the same signature, the subclass must explicitly override to resolve the conflict, otherwise it’s a compile error:

interface A2 { default String who() { return "A"; } }
interface B2 { default String who() { return "B"; } }
class C2 implements A2, B2 { }   // compile error
error: types A2 and B2 are incompatible
  class C2 inherits unrelated defaults for who() from types A2 and B2

Use InterfaceName.super.methodName() to explicitly indicate which interface’s default implementation to use, resolving the conflict:

interface A { default String who() { return "A"; } }
interface B { default String who() { return "B"; } }
class C implements A, B {
    @Override public String who() { return A.super.who() + B.super.who(); } // explicitly resolve the conflict
}
AB

Why “favor composition over inheritance”

Inheritance is white-box reuse: what the subclass gets is not just the superclass’s public interface but direct exposure to the superclass’s implementation details — the subclass’s behavior changes as the superclass’s internal implementation changes, and even if the superclass only alters an internal detail it never promised in its contract, it can silently throw the subclass’s overriding method out of alignment (the classic “fragile base class problem”). Combined with the fact that Java only allows single inheritance, once a type needs to reuse two unrelated capabilities, the inheritance hierarchy cannot express it, and you can only fall back to interface default methods (see above). A subclass also never inherits the superclass’s constructors, nor can it directly access the superclass’s private members (only indirectly through the public/protected methods the superclass exposes) — these two points further show that what inheritance passes down is a “type hierarchy”, not “free access to implementation details”.

Composition — having a class hold an instance of another class as a field and reuse functionality by calling its public methods — is black-box reuse: the internal implementation of the composed object is completely invisible, and the only coupling surface is its public interface. This brings three benefits inheritance cannot give: first, coupling is weaker, the internal implementation can be changed freely, and as long as the interface stays the same the outside notices nothing; second, it is more flexible, the composition relationship can be swapped dynamically at runtime (point the field at another implementation), whereas an inheritance relationship is fixed at compile time; third, it is easier to unit-test, the composed dependency can be replaced with an interface + mock, without pulling in the whole superclass chain the way inheritance does.

// Inheritance version: strong coupling, Logger's implementation details (format, target) are welded into Service's type hierarchy
class Logger { void log(String m) { System.out.println("[LOG] " + m); } }
class ServiceByInherit extends Logger {
    void doWork() { log("working"); }
}

// Composition version: Service depends only on the methods Logger exposes, and the internal implementation can be swapped at any time
class ServiceByCompose {
    private final Logger logger;                 // held, not inherited
    ServiceByCompose(Logger logger) { this.logger = logger; }
    void doWork() { logger.log("working"); }
}
[LOG] working
[LOG] working

This isn’t to say inheritance has no place — for expressing a strict “is-a” hierarchy (Circle is-a Shape) or when you need polymorphism to dispatch uniformly, inheritance (together with interfaces) is still the most direct tool; “favor composition over inheritance” is a rule of thumb reminding you that when both can achieve reuse, prefer the one with weaker coupling, not a replacement for inheritance.

5. Polymorphism and the Virtual Method Table (vtable)

After a subclass overrides (@Override) a superclass method, even if you use a superclass-typed reference to call it, what actually runs is the subclass version — this is “dynamic dispatch”:

class Bird {
    String sound() { return "..."; }
}
class Duck extends Bird {
    @Override String sound() { return "quack"; }
}

public class PolyBasics {
    public static void main(String[] args) {
        Bird b = new Duck();          // a supertype reference pointing to a subclass object
        System.out.println(b.sound()); // quack —— dispatched at runtime by the actual object type, not the declared reference type
    }
}
quack

Java instance methods are dynamically dispatched by default. HotSpot’s implementation is highly similar to C++’s vtable:

Each class has a klass structure in the method area (Metaspace), containing a vtable:
  Klass(Animal)          Klass(Dog extends Animal)
  vtable:                vtable:
   [0] Object.method...    [0] Object.method... (inherited)
   [k] Animal::speak ─┐    [k] Dog::speak    ← override, same slot
                      │
object header's klass ptr ─┘ points to its own Klass
calling a.speak():
   1. take a's object-header klass ptr
   2. fetch the method address from the fixed vtable slot
   3. call   —— almost identical to C++

Differences:

  • Interface methods cannot use a fixed vtable slot (when one class implements multiple interfaces, the slots cannot be unified), so a separate itable (interface method table) + runtime lookup is used, slightly slower than the vtable. The JIT optimizes with an inline cache: it remembers the actual type of the last call, and in the monomorphic case there is nearly zero overhead.
  • Java’s final/private/static methods are statically bound (invokespecial/invokestatic), with no virtual dispatch.
  • The JIT also does devirtualization: if it can prove a call site has only one implementation (CHA, class hierarchy analysis), it inlines directly, and de-optimizes at STW if a new subclass is later loaded. C++ needs a manual final or link-time optimization to get a similar effect.

At the bytecode level there are four call instructions: invokevirtual (virtual), invokeinterface (interface), invokespecial (constructor/private/super), invokestatic (static), plus invokedynamic (lambdas, string concatenation). See “Methods and the Call Stack” for details.

Fields don’t participate in polymorphism: only methods are dynamically dispatched

The dynamic dispatch above holds only for methods; field access is statically bound — determined by the reference’s declared type, regardless of the object’s actual type. This is the point most likely to trip you up in an interview, because intuitively fields and methods both “seem to belong to the object”:

class Base { int x = 1; int getX() { return x; } }
class Derived extends Base {
    int x = 2;                     // a field with the same name as the superclass's; not an override but "hiding", each stored independently
    @Override int getX() { return x; }
}
public class FieldNoPoly {
    public static void main(String[] args) {
        Derived d = new Derived();
        Base b = d;                              // the same object, two references of different declared types
        System.out.println(b.x + " " + d.x);     // 1 2  —— fields fetched by the reference's declared type
        System.out.println(b.getX() + " " + d.getX()); // 2 2 —— methods go through the vtable by the object's actual type
    }
}
1 2
2 2

b.x and d.x clearly point to the same object, yet they fetch two different values — because a subclass field with the same name does not “override” the superclass field but carves out its own separate storage in the object’s memory, hiding the superclass field’s name, and which copy you access is decided entirely statically at compile time by the reference’s declared type, without consulting the vtable. This is in sharp contrast to methods: getX() always goes to Derived::getX whether called through b or d. The mnemonic is “for fields look at the left at compile time, for methods look at the right at runtime” (corresponding to the more common phrase “compile-time looks left, runtime looks right”, which refers specifically to methods): the b in b.x has declared type Base, which decides you get Base’s x; while b.getX() must, at runtime, consult the vtable of the object b actually points to (Derived).

Why fields can’t also be dynamically dispatched: a method call can be made into one layer of indirection (look up the vtable, then jump), because the method itself is just a code address, and the lookup cost can be amortized by JIT inline caches and the like; a field is different — field access has to land on “which offset in the object’s memory”, and this offset must be fixed at compile time so that a simple “read a fixed offset” bytecode instruction (getfield) can be generated, without having to look up the type first on every field read to decide which offset to fetch from. If fields were also dynamically dispatched, it would mean that every field read would first require an indirect lookup like a virtual method call, and for the highest-frequency operation of “reading an integer field” the overhead would be wildly disproportionate. So Java chose to weld field offsets in at compile time (deciding which class’s layout to look in by the declared type), reserving the privilege of “deciding which implementation to use at runtime” for methods only.

This also explains why upcasting (upcast, assigning a subclass reference to a superclass reference, such as Base b = d;, done automatically without an explicit cast) and downcasting (downcast, (Derived) b, requiring an explicit cast and potentially throwing ClassCastException) only affect “which members the compiler can see”, not the object itself: a cast merely changes the “declared type through which you view the same object”; the object’s layout on the heap and its actual type never change. instanceof (see the pattern-matching switch in “Control Flow”) is the means to query this “actual type” at runtime, often used before a downcast to judge whether the cast is safe.

6. Abstract Class vs. Interface

An abstract class can mix “abstract methods” (no method body, the subclass must implement) with “concrete methods” (with an implementation, inherited and used directly); before Java 8 an interface could only have abstract methods:

abstract class Shape {
    abstract double area();          // abstract method, no body
    void describe() {                // concrete method, can have an implementation
        System.out.println("area = " + area());
    }
}
class Circle extends Shape {
    double r;
    Circle(double r) { this.r = r; }
    @Override double area() { return Math.PI * r * r; }
}

interface Movable {
    void move();                     // abstract method
}
class Car implements Movable {
    @Override public void move() { System.out.println("car moves"); }
}

public class AbstractVsInterfaceBasics {
    public static void main(String[] args) {
        new Circle(2).describe();
        new Car().move();
    }
}

Instance fields May have (with state) Only public static final constants
Constructor Yes No

Semantics “what it is” (is-a) “what it can do” (can-do, capability)

Rule of thumb: use an abstract class to express a type hierarchy with shared state; use an interface to express a capability/contract that needs to be combined multiply. In the JDK, AbstractList is an abstract-class skeleton and List is an interface.

Why an abstract method cannot be private/static/final

abstract class Bad {
    private abstract void f();   // compile error: illegal combination of modifiers
}
error: illegal combination of modifiers: abstract and private

This isn’t an arbitrary syntax restriction; all three modifiers directly contradict “an abstract method must be overridden by a subclass” from their own semantics: a private method is invisible to the subclass, so the subclass can’t even “see” this method, let alone override it; a static method relies on static binding (invokestatic) and does not participate in the dynamic dispatch this chapter keeps emphasizing, whereas the sole purpose of an abstract method’s existence is “leave a slot whose concrete implementation is decided by dynamic dispatch”; a final method explicitly forbids being overridden, directly opposing “an abstract method must be overridden”. The compiler rejecting all three is the consistency that the concept of “abstract” must obey when it lands in the type system — if allowed, the promise of the abstract keyword (left for the subclass to implement) would be negated at the same time by another modifier on the same method declaration.

Multiple inheritance of interfaces: extends can take multiple parent interfaces

A class’s extends can take only one superclass, but an interface’s extends can take multiple parent interfaces — this is the only place where interfaces and classes are asymmetric, because interfaces have no field state and there is no diamond data conflict as in class multiple inheritance:

interface Flyable { void fly(); }
interface Swimmable { void swim(); }
interface Amphibious extends Flyable, Swimmable { }   // an interface can inherit multiple interfaces

class Duck2 implements Amphibious {
    @Override public void fly() { System.out.println("flying"); }
    @Override public void swim() { System.out.println("swimming"); }
}

7. Object’s Methods and the equals/hashCode Contract

Every class implicitly inherits Object. The three most commonly overridden methods are equals (judging “value equality”), hashCode (working with HashMap/HashSet), and toString (the text you see when printing):

import java.util.Objects;

class Point2 {
    int x, y;
    Point2(int x, int y) { this.x = x; this.y = y; }

    @Override public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof Point2 p)) return false;
        return x == p.x && y == p.y;
    }
    @Override public int hashCode() { return Objects.hash(x, y); }
    @Override public String toString() { return "Point2(" + x + ", " + y + ")"; }
}

public class EqualsBasics {
    public static void main(String[] args) {
        Point2 a = new Point2(1, 2);
        Point2 b = new Point2(1, 2);
        System.out.println(a.equals(b));   // true
        System.out.println(a == b);        // false —— different objects
        System.out.println(a);             // Point2(1, 2) —— toString is called
    }
}
true
false
Point2(1, 2)

== always compares references (whether it’s the same object); to compare “whether the contents are equal”, you must override equals. System.out.println(a) automatically calls a.toString().

Object is analogous to but stronger than C++ — C++ has no unified root. Key methods: equals, hashCode, toString, getClass, clone, wait/notify (see Concurrency), finalize (deprecated, see GC).

The equals/hashCode contract (violating it causes collections to misbehave)

  1. a.equals(b) is true ⟹ a.hashCode() == b.hashCode() (equal implies same hash).
  2. The converse is not required (equal hashes need not be equal, i.e. collisions are allowed).
  3. equals must be reflexive, symmetric, transitive, consistent, and non-null.

Overriding only equals without hashCode, then putting the object into a HashMap/HashSet, will cause it to be lost by landing in the wrong bucket (see “The Collections Framework”). The default Object.equals is reference equality (==), and the default hashCode is an identity hash — often mistakenly described as “derived from the object’s address”, but that doesn’t hold up (the hash would change after GC moves the object); modern HotSpot (the default in JDK8+) uses a thread-local xorshift pseudo-random number to generate it, computed lazily on the first call, stored into the object header’s mark word, and unchanged thereafter (see “Data Types”).

final class Point {
    final int x, y;
    Point(int x, int y){ this.x=x; this.y=y; }
    @Override public boolean equals(Object o){
        if (this == o) return true;
        if (!(o instanceof Point p)) return false; // pattern-matching instanceof
        return x == p.x && y == p.y;
    }
    @Override public int hashCode(){ return Objects.hash(x, y); }
}

You can auto-generate these with a record (below).

The cost of violating the contract can be seen directly: override only equals, not hashCode, and equal objects scatter into different buckets, so a HashSet can no longer find them back:

import java.util.*;
public class HashContract {
    // overrode equals but not hashCode —— violates the contract
    static class Bad {
        final int id; Bad(int id){ this.id = id; }
        @Override public boolean equals(Object o){ return o instanceof Bad b && b.id == id; }
    }
    // both overridden —— correct
    static class Good {
        final int id; Good(int id){ this.id = id; }
        @Override public boolean equals(Object o){ return o instanceof Good g && g.id == id; }
        @Override public int hashCode(){ return Integer.hashCode(id); }
    }
    public static void main(String[] args) {
        System.out.println("Bad  equal? " + new Bad(1).equals(new Bad(1)));
        Set<Bad> bad = new HashSet<>(); bad.add(new Bad(1));
        System.out.println("Bad  contains equal obj? " + bad.contains(new Bad(1)));

        Set<Good> good = new HashSet<>(); good.add(new Good(1));
        System.out.println("Good contains equal obj? " + good.contains(new Good(1)));
    }
}
Bad  equal? true                 <- the two Bad(1) are equal
Bad  contains equal obj? false   <- but the default hashCode differs, they scatter to different buckets, not found!
Good contains equal obj? true    <- only after overriding correctly can it be found back

getClass() or instanceof in equals: the trade-off of symmetry

The examples above all use instanceof to check the type, but there is another common style, obj.getClass() != this.getClass(). The two are not a matter of picking one at random, but different stances on “whether a subclass counts as equal”, and picking the wrong one violates the symmetry in the equals contract (a.equals(b) and b.equals(a) must give the same result):

class Point { int x;
    Point(int x){ this.x = x; }
    @Override public boolean equals(Object o){
        if (!(o instanceof Point p)) return false;   // with instanceof: a subclass can also be equal
        return x == p.x;
    }
}
class ColorPoint extends Point {
    String color;
    ColorPoint(int x, String color){ super(x); this.color = color; }
    // does not override equals, inherits Point's directly: compares only x, not color
}
public class EqualsSymmetry {
    public static void main(String[] args) {
        Point p = new Point(1);
        ColorPoint cp = new ColorPoint(1, "red");
        System.out.println(p.equals(cp));   // true —— instanceof considers ColorPoint to be a kind of Point
        System.out.println(cp.equals(p));   // true —— symmetric, both sides agree
    }
}
true
true

Replacing instanceof with getClass() != o.getClass() makes “comparing a superclass object with a subclass object” always false (because the Class objects differ), which does preserve symmetry, but at the cost that the superclass’s equals can never again consider any subclass instance equal to itself — if the business semantics are “as long as the coordinates are the same it counts as equal, and color is just extra information”, the getClass() version is actually more counterintuitive than the instanceof version. What is truly dangerous is mixing them: the superclass uses instanceof, and the subclass overrides equals to add an extra field comparison (for instance requiring ColorPoint to have both x and color equal), which produces p.equals(cp) being true (the superclass can’t see color, compares only x) while cp.equals(p) is false (the subclass requires color to be equal too, and p has no color) — the same pair of equals calls gives different results when swapped, directly violating the contract. Rule of thumb: either design classes participating in equals comparison to be final (eliminating the possibility of subclassing, as a record inherently is), or use getClass() for equality throughout an inheritance hierarchy (giving up the “superclass and subclass can be equal” semantics but preserving symmetry).

8. Generics and Type Erasure (the fundamental divide from C++ templates)

You declare a generic class with class ClassName<T> (the Box<T> above already showed this); a generic method writes <T> before the return type, and the type parameter is inferred automatically from the argument passed at call time:

public class GenericMethodBasics {
    static <T> T firstOf(T[] arr) {     // generic method: the type parameter goes before the return type
        return arr[0];
    }
    public static void main(String[] args) {
        String[] names = {"Ann", "Bob"};
        System.out.println(firstOf(names));   // Ann

        Integer[] nums = {10, 20};
        System.out.println(firstOf(nums));    // 10
    }
}
Ann
10

This is the most “counterintuitive” part of Java’s type system, and where it differs most from C++, so below we lay out what actually happens at runtime.

Erasure: no generic information at runtime

Java generics are a compile-time feature. After compilation the type parameter is “erased”: List<String> and List<Integer> are both the same List class at runtime (the raw type List, with T erased to Object, or erased to the upper bound if bounded). The compiler inserts casts where needed and does static type checking.

List<String> ls = new ArrayList<>();
ls.add("hi");
String s = ls.get(0);   // the compiler inserts a (String) cast
// at runtime: ls.getClass() == ArrayList.class, exactly the same as List<Integer>

Compare C++: templates are monomorphized, vector<int> and vector<string> compile to two independent copies of code, each with its own type at runtime — a zero-cost abstraction but with code bloat. Java has only one copy of code, no bloat, but loses the type at runtime, which gives rise to a series of restrictions.

Why Java chose erasure instead of monomorphizing separate code for each concrete type as C++ does: the fundamental reason is backward compatibility with a bytecode ecosystem that had existed for years. Generics were only added in JDK 5 (2004), and before that the Collection, List and other interfaces had already been used as raw types for nearly a decade; huge numbers of already-compiled .class files running in production (and third-party-published jar packages) were full of List with no type parameters. If Java, like C++ templates, generated a separate copy of bytecode for each concrete type, List<String> and raw List would become two runtime-incompatible classes, and newly compiled generic code could not be passed directly to old methods written against raw types, nor called by old code — this would instantly break the binary compatibility of all published libraries, and old and new code could not mix. The erasure approach does the opposite: List<String> compiles to an ordinary List, exactly the same as List bytecode compiled before JDK 5, with the compiler merely inserting extra type checks and casts at compile time. This way a new piece of genericized code can seamlessly call old code written against raw types, and vice versa — this is called “migration compatibility”, an explicit goal of the Java team when designing generics; what is sacrificed is runtime type information (leading to a series of restrictions such as being unable to new T[], and instanceof being unable to carry a type parameter), in exchange for a decade’s worth of accumulated bytecode assets continuing to work without recompilation. This is a design driven by historical baggage rather than a pure technical optimum — had Java shipped with generics from day one, it most likely would not have chosen this path.

At runtime the two generic instances are the same Class object; the raw type exposes even more clearly that “there is no more type checking at runtime”:

import java.util.*;
public class Erasure {
    public static void main(String[] args) {
        List<String>  ls = new ArrayList<>();
        List<Integer> li = new ArrayList<>();
        System.out.println(ls.getClass());                 // both erased to ArrayList
        System.out.println(li.getClass());
        System.out.println("same Class object? " + (ls.getClass() == li.getClass()));
        // the type parameter is not kept at runtime, the line below can store it, exposed only when fetched and used:
        List raw = li;                 // raw type
        raw.add("oops");               // no ClassCastException here (only a compile warning)
        System.out.println("li now holds: " + li.get(0));  // even though it's declared List<Integer>
    }
}
class java.util.ArrayList
class java.util.ArrayList
same Class object? true
li now holds: oops

At compile time there is an unchecked warning at raw.add("oops"), but it does not prevent compilation or cause a runtime error.

The four major restrictions brought by erasure

// 1. Cannot new T[] (the runtime type can't be determined, and covariant arrays would miss the check)
// T[] arr = new T[10];              // compile error
T[] arr = (T[]) new Object[10];       // workaround: cast, with an unchecked warning

// 2. Cannot new T() (don't know which class to construct)
// T t = new T();                     // compile error, need to pass a Supplier<T> or Class<T>

// 3. instanceof cannot carry a type parameter (no such information at runtime)
// if (x instanceof List<String>)     // compile error
if (x instanceof List<?>) { }         // can only use a wildcard

// 4. static fields cannot use a type parameter; cannot catch a generic exception

Erasure also makes “seemingly different” overloads clash at compile time

class Overloads {
    void foo(List<String> a) { }
    void foo(List<Integer> b) { }   // compile error: after erasure the two methods have the same signature
}
error: name clash: foo(List<Integer>) and foo(List<String>) have the same erasure

List<String> and List<Integer> are different types in the source, yet the compiler rejects them outright — because after erasure both methods’ bytecode signatures are foo(List), and while overload resolution (see “Methods and the Call Stack”) happens at compile time on the pre-erasure types the compiler sees, the methods themselves must be generated into the class file, and they need different bytecode signatures to coexist; since the two are completely identical after erasure, the JVM level has no way to tell which one to call, so the compiler just blocks the error up front rather than having the runtime guess with some hidden mechanism. This is the direct projection, in the specific scenario of overload resolution, of erasure’s fundamental restriction that “only one copy of type information survives at runtime”.

Bridge methods

Erasure would break covariant returns and generic overriding, so the compiler generates a bridge method to bridge the gap:

class Node<T> { T get(){...} void set(T t){...} }
class StrNode extends Node<String> {
    @Override String get(){...}        // the one you wrote
    // the compiler also secretly generates: Object get(){ return get(); }  ← bridge, matches the superclass's erased signature Object get()
}

Otherwise the superclass Node after erasure is Object get(), the subclass’s String get() has a different signature, and virtual dispatch wouldn’t line up. The bridge method is visible with javap -v, marked ACC_BRIDGE ACC_SYNTHETIC — in practice you can indeed see two gets in StrNode.class: one ()Ljava/lang/String; (the one you wrote), and one ()Ljava/lang/Object; with the ACC_BRIDGE, ACC_SYNTHETIC flags (generated by the compiler).

Wildcards: the PECS principle

Generics are invariant: List<String> is not List<Object> (the opposite of array covariance, and safer). To relax this, use a wildcard:

  • ? extends T: upper bound, producer (you can only read out T, not write in, because you don’t know the exact subtype).
  • ? super T: lower bound, consumer (you can only write in T, and reading out only gives Object).
  • Mnemonic PECS: Producer-Extends, Consumer-Super.
// read from src, write to dst: src is the producer so use extends, dst is the consumer so use super
static <T> void copy(List<? super T> dst, List<? extends T> src){
    for (T t : src) dst.add(t);
}

C++20 concepts / old-style SFINAE solve a similar “constrain the type parameter” problem, but the mechanism is completely different (compile-time duck typing vs. nominal subtyping + erasure).

9. record: an Immutable Data Carrier

A record declares its fields in one line, and the compiler auto-generates the constructor, accessors (named exactly after the fields, with no get prefix), and equals/hashCode/toString:

record Point3(int x, int y) { }

public class RecordBasics {
    public static void main(String[] args) {
        Point3 p = new Point3(3, 4);
        System.out.println(p.x());      // 3   —— accessor, not called getX()
        System.out.println(p.y());      // 4
        System.out.println(p);          // Point3[x=3, y=4] —— auto-generated toString
    }
}
3
4
Point3[x=3, y=4]
record Point(int x, int y) { }
// auto-generates: private final fields, an all-args constructor, accessors x()/y(), equals/hashCode/toString

A record is implicitly final, its fields are final, and semantically it is a “transparent data aggregate”. Think of it as C++’s aggregate struct + an auto-generated operator==. You can add a compact constructor to validate:

record Range(int lo, int hi) {
    Range {   // compact constructor, auto-assigns after validation
        if (lo > hi) throw new IllegalArgumentException();
    }
}
Range r = new Range(1, 5);
System.out.println(r);           // Range[lo=1, hi=5]
new Range(5, 1);                 // throws IllegalArgumentException —— the validation in the compact constructor takes effect

10. sealed: Sealed Types (controlled inheritance)

sealed interface ... permits ... explicitly lists “who can implement it”; classes not on the list cannot implement it:

sealed interface Vehicle permits Car2, Bike { }
record Car2(int wheels) implements Vehicle { }
record Bike() implements Vehicle { }

public class SealedBasics {
    public static void main(String[] args) {
        Vehicle v = new Car2(4);
        System.out.println(v);   // Car2[wheels=4]
    }
}
Car2[wheels=4]

Restricting who can inherit/implement, combined with pattern matching, enables exhaustiveness checking:

sealed interface Shape permits Circle, Square { }
record Circle(double r) implements Shape { }
record Square(double s) implements Shape { }

double area(Shape sh) {
    return switch (sh) {          // the compiler knows there are only two, no default needed
        case Circle c -> Math.PI * c.r() * c.r();
        case Square s -> s.s() * s.s();
    };
}
System.out.println(area(new Circle(2)));  // 12.566370614359172
System.out.println(area(new Square(3)));  // 9.0

This is similar to expressing a closed sum type in C++ with std::variant + std::visit. sealed lets the compiler verify the switch is exhaustive — miss covering one subtype and the switch expression fails to compile, rather than leaving a hole that only surfaces at runtime.

11. enum: a Full-Fledged Class

The simplest enum just lists a series of constant names, like C’s enum but safer — it cannot be mixed with integers, and both switch and == work directly on it:

enum Day { MON, TUE, WED, THU, FRI, SAT, SUN }

public class EnumBasics {
    public static void main(String[] args) {
        Day d = Day.MON;
        System.out.println(d);            // MON
        System.out.println(d == Day.MON); // true —— enum constants can be compared directly with ==

        for (Day day : Day.values()) {    // iterate over all constants
            System.out.print(day + " ");
        }
        System.out.println();
    }
}

true
MON TUE WED THU FRI SAT SUN

A Java enum is not a C/C++ integer constant, but is compiled into a class extending java.lang.Enum, with each enum constant being a singleton object (guaranteed by the JVM). It can have fields, methods, constructors, and even a separate method body per constant (constant-specific behavior):

enum Planet {
    EARTH(5.97e24, 6.37e6), MARS(6.42e23, 3.39e6);  // calls the constructor
    private final double mass, radius;
    Planet(double m, double r){ mass=m; radius=r; }
    double gravity(){ return 6.67e-11 * mass / (radius*radius); }
}
for (Planet p : Planet.values()) {
    System.out.println(p + " gravity = " + p.gravity());
}
EARTH gravity = 9.813440652193735
MARS gravity = 3.726159709713629

Because they are singletons, enums can be safely compared with ==, and are the best way to implement the singleton pattern; EnumMap/EnumSet use the ordinal as a bitmap/array, making them extremely efficient.

12. Inner Classes, Anonymous Classes, Lambdas, and Variable Capture

A functional interface (an interface with a single abstract method, such as the built-in Runnable) can be assigned directly with a lambda, without writing a dedicated implementation class:

Runnable r = () -> System.out.println("running!");
r.run();

Kinds of inner classes

  • Static nested class (static class): no reference to an outer instance, equivalent to a top-level class placed inside.
  • Member inner class: holds a hidden outer this reference and can access the outer instance’s fields — this is also a source of memory leaks (the inner-class instance staying alive drags the outer instance along).
  • Local class / anonymous class: defined inside a method.

Captured variables must be effectively final

A local variable captured by an anonymous class/lambda must be final or effectively final (never assigned again after initialization):

int base = 10;                 // effectively final
Runnable r = () -> System.out.println(base + 1);
// base = 20;                  // if uncommented, the line above fails to compile

Why? A local variable lives in a stack frame, which is destroyed after the method returns; whereas a lambda/anonymous-class object lives on the heap and may live longer. Java’s approach is to copy the value of the captured variable into the lambda object (primitives copy the value, reference types copy the reference value), requiring it to be unchanging so that the semantics of “the original variable on the stack” and “the copy on the heap” stay consistent, avoiding the confusion of the two being out of sync.

Compare C++ lambdas: you explicitly choose [=] to capture by value or [&] to capture by reference; by reference you can capture a mutable variable, but once the stack variable goes out of scope it becomes a dangling reference (UB) — the responsibility is on you. Java uses effectively final to seal off this pitfall at the language level (only by value, and the value doesn’t change). Capturing an instance field is different: the lambda captures this, accesses the field through it, and the field is mutable.

The underpinnings of lambdas: invokedynamic

A lambda is not syntactic sugar for an anonymous class. javac generates an invokedynamic instruction, and on first execution LambdaMetafactory dynamically generates a class at runtime that implements the functional interface. The benefit: a lambda with no captures can reuse the same instance (stateless), avoiding the bloat of one class file per site as with anonymous classes. Method references (String::length) work the same way.

13. Reflection: Runtime Type Introspection

The preceding sections on generic erasure leave a question: ArrayList<String>’s Class object at runtime is exactly the same as the raw type’s, so how is “what type information can still be queried at runtime” itself accomplished? The answer is reflection — not generic information, but the structural information inherent to every class (which fields, methods, and constructors it has, and the annotations on the class), which was never erased; reflection is the mechanism for reading out this structural information at runtime and invoking it dynamically.

The Class object: the entry point to reflection

For every loaded class, the JVM maintains a unique Class object in the method area (Metaspace) describing it — this is exactly the API-level mirror, in Java, of that metadata pointed to by the “klass pointer in the object header” from the start of this chapter. There are three ways to obtain a class’s Class object:

Class<?> c1 = String.class;                    // type known at compile time: the literal
Class<?> c2 = "hi".getClass();                 // looked up from an object instance
Class<?> c3 = Class.forName("java.lang.String"); // dynamically loaded by string name at runtime

Class.forName is the most crucial of the three: the class name can come from a config file, an annotation, a command-line argument — only it can, without knowing the concrete class name at compile time at all, let the program decide at runtime which class to use, which is the root of reflection’s “dynamism”.

Dynamically creating objects, reading/writing fields, and invoking methods via reflection

import java.lang.reflect.*;

class User {
    private String name;
    private User() {}                          // private constructor and private field, normally inaccessible from outside
    private User(String name) { this.name = name; }
    private String greet() { return "hi, " + name; }
}

public class ReflectDemo {
    public static void main(String[] args) throws Exception {
        Class<?> clazz = Class.forName(User.class.getName());

        // bypass private, obtain the private constructor and call it
        Constructor<?> ctor = clazz.getDeclaredConstructor(String.class);
        ctor.setAccessible(true);                // breaks encapsulation: normal code wouldn't compile here
        Object user = ctor.newInstance("Ann");

        // bypass private, read and write the private field
        Field nameField = clazz.getDeclaredField("name");
        nameField.setAccessible(true);
        System.out.println("read private field: " + nameField.get(user));
        nameField.set(user, "Bob");

        // bypass private, dynamically call the private method (the method name is given as a string, which can come from a config file)
        Method greet = clazz.getDeclaredMethod("greet");
        greet.setAccessible(true);
        System.out.println(greet.invoke(user));
    }
}
read private field: Ann
hi, Bob

The getDeclaredXxx family of methods can obtain all members declared by this class, including private ones (the getXxx versions without Declared return only public members, including inherited ones); setAccessible(true) turns off Java’s language-level access checks — this line is the literal embodiment of reflection “breaking encapsulation”: the private modifier was a contract the compiler enforced for you, and after this reflective call line, that contract is null and void at runtime.

Why reflection exists: the framework doesn’t know your type but must operate on it

Spring’s dependency injection is the most typical example: when the container starts up, which classes in the business code are to be managed, which dependencies each class’s constructor needs, which field is annotated @Autowired — this information simply doesn’t exist when Spring is compiled; it all comes from the business code you write later. The framework’s code can’t possibly import your classes ahead of time or new your objects; it can only, at runtime: scan a class-name string → Class.forName to load it → use reflection to read its constructor parameter types and the annotations on its fields → decide what to inject → use reflection to call the constructor/setter to stuff in the dependencies. This is a fundamental contradiction between generality and specificity: the framework must, without knowing at all what classes the user will define, still be able to create, wire, and invoke these classes — a static-typed method call cannot do this (the method name and parameter types must be welded in at compile time), and only reflection, by downgrading “which method to call” from a compile-time syntactic structure to a runtime string lookup and dynamic dispatch, can achieve this decoupling where “framework code and business code don’t know each other yet can work together”. Similarly, MyBatis relies on reflection to set each column of a query result set into a POJO’s fields reflectively, JSON libraries (Jackson/Gson) rely on reflection to walk the fields for serialization/deserialization, and JUnit relies on reflection to discover and call methods annotated @Test — the common feature of these frameworks is that the set of concrete types they must handle is open and unknown when the framework itself is compiled, and only reflection can work under this openness.

The cost: performance, type safety, encapsulation

Reflection is not free flexibility; three costs correspond to three typical negative scenarios:

  • Performance overhead: Method.invoke() is slower than a direct call, for two reasons — first, arguments need to be boxed into an Object[] to pass, and the return value needs unboxing, so primitives go through an unnecessary objectification; second, a reflective call goes through a layer of access-permission checking and method lookup (a modern JVM will, after many calls, “inflate” a high-frequency reflective call into a dynamically generated bytecode delegate, i.e. the MethodAccessor switches from NativeMethodAccessor to GeneratedMethodAccessor, closing most of the gap, but the first call and low-frequency calls are still noticeably slower than invokevirtual). Dense call paths (hot loops) should avoid reflection.
  • Weakened type safety: a reflective call turns the method name and parameter types, which should be checked at compile time, into a string and an Object[] validated only at runtime — misspell the method name or mismatch parameter types, and the compiler is completely unaware, only throwing NoSuchMethodException/IllegalArgumentException when it runs to that invoke() line. This is yet another instance of the “static type checking vs. runtime flexibility” trade-off that recurs throughout this chapter (of the same origin as generic erasure and the instanceof check).
  • Breaking encapsulation: setAccessible(true) can bypass private, which means the assumption that “access permissions are the designer’s contract” doesn’t hold in the face of reflection — this is both the reason it can implement mechanisms like dependency injection and a source of security risk (the strong encapsulation of the JDK 9+ module system is precisely meant to re-plug this hole at module boundaries, with packages not opened rejecting deep cross-module reflection by default).

Rule of thumb: for problems in business code that can be solved with interfaces/polymorphism, don’t solve them with reflection — reflection should be reserved for frameworks and general-purpose tooling code that genuinely need to “handle compile-time-unknown types”.

The relationship with generic erasure

Reflection and generic erasure seem contradictory (one says “type information can still be queried at runtime”, the other says “type information is erased at runtime”), but they are actually complementary: what reflection can query is the structure of the class itself (which fields and methods ArrayList has), while what erasure discards is the type parameter (the String in ArrayList<String>) — list.getClass() can only ever tell you this is an ArrayList, and there is no method in the reflection API that lets you ask “what was this ArrayList instance originally instantiated with, a String?”, because that information was already erased at compile time; reflection queries the metadata that genuinely exists at runtime, and information that already didn’t exist before erasure cannot be conjured out of thin air by reflection either.

Summary

  • Objects uniformly live on the heap, and the klass pointer in the object header is analogous to C++’s vptr; the initialization order is “superclass static → superclass instance → superclass constructor → this class’s instance → this class’s constructor”, and calling a virtual method during construction runs into the pitfall of subclass fields not yet being initialized.
  • protected has wider semantics than C++’s, allowing same-package access; single inheritance + multiple interfaces avoids the complexity of C++’s diamond inheritance, and interface default methods bring “multiple inheritance of implementations” but with no stateful diamond problem, and conflicts must be resolved by explicit override.
  • Polymorphism is implemented via the vtable (class methods) + itable (interface methods), and the JIT optimizes with inline caches and devirtualization; overriding is dispatched at runtime by the dynamic type, which is a different thing from overloading resolved statically at compile time (see “Methods and the Call Stack”).
  • equals/hashCode must be overridden in pairs; otherwise violating the contract will cause equal objects to be “unfindable” in a HashMap/HashSet by scattering into the wrong bucket.
  • Generics do type checking at compile time and are erased to raw types at runtime — this is for backward compatibility with a decade’s worth of bytecode assets accumulated before generics appeared (migration compatibility), at the cost of restrictions such as being unable to new T[]/new T() and instanceof being unable to carry a type parameter, and the compiler also generates bridge methods to bridge the signature mismatch caused by erasure.
  • record/sealed/enum are all syntactic sugar where the compiler generates large amounts of boilerplate, and an enum constant is essentially a singleton object; a lambda capturing a local variable requires it to be effectively final (value-copy semantics), and under the hood relies on invokedynamic + LambdaMetafactory to generate the implementation class at runtime, rather than being syntactic sugar for an anonymous class.
  • Object orientation binds data and methods together, in exchange for a unified carrier for the three things encapsulation/inheritance/polymorphism, at the cost of one extra layer of indirection per object; inheritance is white-box reuse and composition is black-box reuse, and when both can satisfy the reuse need, prefer the more weakly coupled composition. Polymorphism dynamically dispatches only methods, while field access is statically bound by the declared type (hiding, not overriding).
  • Reflection reads a class’s structural information (Class/Field/Method/Constructor) at runtime and invokes it dynamically, and is the core mechanism by which frameworks like Spring/MyBatis handle “compile-time-unknown types”, at the cost of slower calls, type checking pushed to runtime, and being able to bypass private to break encapsulation.
