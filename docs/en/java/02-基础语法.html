Basic Syntax: A Comparison with C/C++

Java’s surface syntax deliberately hews close to the C family—{} to delimit blocks, ; to end statements, the way if/for/while are written, the arithmetic and logical operators—and this was an explicit design goal of Gosling’s team: let C/C++ programmers get by with almost no need to relearn the notation, so their attention can go straight to the semantic differences. This chapter therefore does not rehearse these commonplaces one by one; it covers only the places where Java genuinely parts ways with C/C++ in syntax and language structure, and the design trade-off behind each divergence.

First, here is a snippet that shows the common notation, to establish an overall impression:

public class Basics {
    public static void main(String[] args) {
        int age = 20;
        double price = 9.9;
        String name = "Ada";
        boolean ok = true;

        int sum = age + 5;
        System.out.println(sum);                              // 25
        System.out.println("name=" + name + ", age=" + age);  // name=Ada, age=20

        if (age >= 18) {
            System.out.println("adult");
        } else {
            System.out.println("minor");
        }

        for (int i = 0; i < 3; i++) {
            System.out.println("i=" + i);   // i=0  i=1  i=2
        }
    }
}

Comments use // and /* */, the same as C. Below we discuss the structural differences item by item.

1. Everything lives inside a class; the program entry point

C allows free functions and global variables; Java has no free functions and no global variables—all code must hang off a class (or interface / enum / record).

public class App {
    public static void main(String[] args) {
        System.out.println("Hello");
    }
}

Why it is designed this way: Java’s object model inherits the “pure object-orientation” philosophy of the Smalltalk lineage, deliberately leaving no escape hatch for either free functions or mutable global state. This is not merely an aesthetic choice—mutable global state is the hardest thing to reason about in a multithreaded program (any thread may read or write it at any moment, which causes trouble for static analysis, concurrency correctness, and the later security-sandbox model). Forcing all code to belong to some class amounts to forcing it to belong to a definite namespace and access-control boundary. One of Java’s early design goals was to safely load and run untrusted code from the network (the applet model), and a language with no globally writable state is clearly easier to make safe in that way.

Compared with C’s int main(int argc, char** argv): - main returns void: the JVM launcher uses reflection to look up the entry point by the fixed signature public static void main(String[]); it cares only about “can it be found and invoked,” not about any business return value—the process exit code is a separate, independent channel, and to set it you explicitly call System.exit(int). Decoupling “function return value” from “process exit status” lets the entry-point signature stay uniform across all programs, without having to invent a variety of main signatures for “what value this program wants to return.” - The parameter is String[] args, without the program name: C’s argv[0] is the program name, a historical legacy of how the exec family of system calls passes arguments (the program needs to know the name it was invoked under, e.g. a busybox-style multiplexed binary). The JVM already knows which class to run, so it does not need to stuff this information into the user-visible argument array; args therefore contains only the real invocation arguments, and the array carries its own length, so no separate argc is needed. - Must be static: the JVM must be able to call the entry point after it has loaded the class but before it has created any instance; a static method does not depend on the existence of an instance, which is the direct corollary of the “class first, instance later” lifecycle order (an instance method’s invocation logically requires an object first).

Starting with JDK 21, a streamlined entry-point form that omits the class wrapper was offered as a preview, and it became a final feature in JDK 25 (JEP 512)—but this is only syntactic sugar for teaching/scripting scenarios; the load-reflect-invoke machinery behind public static void main(String[]) is unchanged, and serious projects still use the classic form as the norm.

2. Packages and imports: no preprocessor

C/C++ use #include to do textual pasting: the declarations in a header file are copied verbatim into every source file that references it at compile time, and #define macros do pure text substitution. The cost of this mechanism is significant—the same declaration is re-parsed in every compilation unit, macro expansion does not obey scope rules (globally in effect, redefinable at will), #ifdef makes the same source effectively a different program under different compile conditions, and forgetting an include guard causes repeated inclusion.

Java replaces this whole mechanism with packages + imports:

package com.example;

import java.util.List;          // import a single class
import java.util.*;             // import a whole package (not recursive into sub-packages)
import static java.lang.Math.*; // static import

public class Demo { /* ... */ }

import does no textual insertion whatsoever; it only tells the compiler “which fully qualified name a given simple name corresponds to.” The actual type resolution happens at compile time by looking up the symbol table, and at run time by the class loader loading .class files on demand (see Runtime Model).

Why header files and forward declarations can be dispensed with: the root cause is that a .class file is itself self-describing—it contains the complete method signatures, field types, constant pool, and other metadata, so the compiler or class loader can read a class’s complete contract straight from this binary, without maintaining a separate hand-written .h declaration, as C++ does, to “pre-announce” what the implementation contains. This is also why classes can reference each other and form circular dependencies—the compiler resolves symbols on a per-class basis and does not require the strict textual order of “you must have already seen the declaration before you use it,” whereas C++’s single-pass compilation model must see the declaration before use. This is the natural result of two entirely different compilation-and-linking models: C++ compiles to object files and then a linker stitches symbols together; Java compiles to bytecode carrying complete metadata and then the class loader resolves symbols on demand at run time.

Dropping macros also brings a benefit that is often underrated: no macros means no whole class of macro bugs—macros ignore scope and the type system, and a form like #define MAX(a,b) ((a)>(b)?(a):(b)) evaluates its arguments repeatedly when they have side effects, whereas Java replaces “function macros” with ordinary methods (which get inlined by the JIT, see Runtime Model) that obey the normal rules of scope, type checking, and evaluation order. Constants use static final, and platform differences are handled by runtime checks or build tools, rather than by compile-time conditional expansion into “source code that is actually different.”

3. Strong static typing; var local inference

int count = 10;
double ratio = 0.5;
String name = "Ada";
long big = 9_000_000_000L;   // beyond int range, requires the L suffix

Like C++, Java is strongly and statically typed: every variable’s type is fixed at compile time, and a type mismatch is a compile error—this is so that the JIT/AOT can determine method dispatch and memory layout at compile time rather than run time, and so type errors surface during development rather than in the user’s hands.

The var introduced in JDK 10 does local-variable type inference, semantically corresponding to C++11’s auto:

var count = 10;                        // inferred as int
var list = new ArrayList<String>();    // inferred as ArrayList<String>

Why Java added this only in its 10th release, and only for local variables: after generics (Java 5), type declarations often became very long (Map<String, List<Integer>> m = new HashMap<>();) and were pure visual noise; var is compile-time syntactic sugar aimed at this specific pain point—the type is still fixed at compile time, var does not change the fact that Java is a statically typed language, the bytecode contains the concrete type, it is completely equivalent to writing the type name by hand, and there is zero runtime difference. It is deliberately restricted to local variables “inside a method, and with a mandatory initializer expression” because field types and method signatures are part of the public contract (both documentation for callers and part of the binary interface), and using var would deprive readers/callers of a direct way to inspect the contract; a local variable, by contrast, is purely an implementation detail, and inferring it away affects no one’s understanding of the external contract. This is a carefully considered boundary, not an arbitrary restriction.

4. Operators

The vast majority of operators are the same as C: arithmetic + - * / %, relational == != < > <= >=, logical && || !, bitwise & | ^ ~ << >>, compound assignment, and increment/decrement—the notation carries over directly. What is genuinely worth digging into are the few divergences below, each corresponding to a specific design trade-off:

The if condition must be a boolean, and does not accept an integer: in C, “nonzero is true,” and the classic bug of mistyping == as = in if (a = b) compiles precisely because the value of the assignment expression (b) can be implicitly converted to the “truth value” the condition needs. Java requires the condition to be a boolean, and int cannot be implicitly converted to boolean, so this kind of typo simply fails to compile in Java—using the type system to root out, at the language level, a whole class of bugs that every C programmer has been burned by, at the cost of sacrificing the flexibility of “using an integer as a truth value” (e.g. you can no longer write if (count) to test for nonzero).

Unsigned right shift >>> is separate from arithmetic right shift >>: Java deliberately does not design unsigned integer types (there are only the signed types byte/short/int/long), in exchange for simpler, unambiguous overflow and sign-extension rules—it need not handle, as C does, implementation-defined behavior such as “which side gets promoted to which in a mixed signed/unsigned operation.” But even without unsigned types, there is still a real need to “treat the top bit as a pure bit rather than a sign bit” (bit manipulation, hashing, simulating unsigned arithmetic), and >>> is the escape hatch opened specifically for this: >> fills with the sign bit (arithmetic right shift), >>> fills with 0 (logical right shift). In C, whether the sign bit is filled depends on whether the type itself is unsigned; Java makes this choice explicit with two operators.

Integer division by zero throws an exception rather than being undefined behavior: the C standard defines integer division by zero as undefined behavior, allowing different hardware platforms to handle it differently (some trigger a CPU exception directly, some return garbage). The JVM, as a cross-hardware managed runtime, must guarantee that the same bytecode behaves identically on any platform, so it defines “divide by zero” as deterministically throwing ArithmeticException, which can be handled by catch. This is the direct dividing line between the two design philosophies of “a language specification guaranteeing portable, deterministic behavior” and “staying close to the hardware and allowing platform differences.” Floating-point division by zero, on the other hand, follows the semantics of IEEE-754 itself, yielding Infinity/NaN without throwing—because the IEEE-754 standard defines these values itself, so the JVM need not provide an extra fallback.

Shift counts are taken modulo the bit width: for int shifts the shift amount is implicitly & 31, and for long it is & 63, so 1 << 32 results in 1, not 0. This is likewise an example of “eliminating platform-dependent undefined behavior”—in C, a shift amount exceeding the type’s bit width is undefined behavior, whereas Java explicitly specifies the modulo rule, and the result is the same on any platform.

+ is the only “overloaded” operator: as long as one operand is a String, + becomes concatenation, handled specially by the compiler (internally often converted to StringBuilder.append, see Data Types). This is the only escape hatch opened deliberately—Java does not support user-defined operator overloading at the language level (the reasoning is in Section 8), but string concatenation is frequent enough to be worth an exception.

Testing these in practice:

System.out.println(1 << 32);        // 1  (32 & 31 == 0, i.e. 1<<0)
System.out.println(-8 >> 1);        // -4   arithmetic right shift, fills the sign bit
System.out.println(-8 >>> 28);      // 15   logical right shift, fills with 0

try { int x = 1 / 0; }
catch (ArithmeticException e) { System.out.println(e.getMessage()); } // / by zero
System.out.println(1.0 / 0);        // Infinity (IEEE-754 semantics, no exception thrown)

System.out.println("sum=" + 1 + 2); // sum=12 (evaluated left to right; once it becomes a string it concatenates all the way)
System.out.println(1 + 2 + "=sum"); // 3=sum (still ordinary addition until the string is reached)

5. Strings: an immutable class, not a character array

String s = "hello";
int n = s.length();               // an O(1) field, not a strlen-style scan for \0
boolean same = s.equals("hello"); // compare content with equals, not ==
String up = s.toUpperCase();      // returns a new string; s itself is unchanged

String is a class, not a char* and not a char[], and it is immutable—any “modifying” method returns a new object, and the original object’s content never changes:

String s = "hello";
String up = s.toUpperCase();
System.out.println(s);         // hello   the original string is unchanged
System.out.println(s == up);   // false   up is a different object

Why it is designed to be immutable: this is not an arbitrary choice but one that serves three goals at once: 1. Safe sharing without defensive copies: multiple references can safely point to the same String object without worrying that some code has quietly altered its content—this matters especially for strings that are frequently passed around as HashMap keys, class names, file paths, and network addresses; if strings were mutable, there would in principle be a time-of-check-to-time-of-use vulnerability where “it is one value when validated and has been changed to another when used.” 2. Safe caching of the hash value: an immutable object’s hash value is computed once and is valid forever; String.hashCode() caches the result internally, greatly lowering the cost of using a string as a HashMap key. 3. Lock-free thread safety: an immutable object is inherently thread-safe, and multiple threads reading the same String need no synchronization whatsoever.

The cost is clear: frequent concatenation keeps producing new objects, and concatenating with + inside a loop is O(n²). This is the direct price of immutability, and the remedy is the mutable StringBuilder (internally a growable char/byte array, akin to a manually managed buffer; details in Data Types).

6. Console IO

System.out.println("a whole line with a newline");
System.out.printf("%d and %.2f%n", 10, 3.14159);  // printf-like; %n is a platform-independent newline

Scanner sc = new Scanner(System.in);
int x = sc.nextInt();

System.out/System.err/System.in are objects wrapping stdout/stderr/stdin respectively. printf-style formatting does runtime type checking in Java—a format specifier that does not match the actual argument type throws an exception, rather than, as with C’s printf, being undefined behavior when the argument type does not match the specifier (this is precisely the root of a whole class of historical “format string attack” vulnerabilities in C: an attacker-crafted format string can make printf interpret data on the stack as the wrong type, causing information disclosure or even arbitrary writes). Java replaces “type mismatch is UB” with “throw an exception on type-check failure,” consistent with its handling of divide-by-zero, shifting, and so on above: if you can fail deterministically, do not leave nondeterministic behavior.

7. Comments and Javadoc

/**
 * Javadoc documentation comment
 * @param n the input count
 * @return the computed result
 */
public int compute(int n) { return n * 2; }

Tags such as @param/@return/@throws are a language-level convention understood by both the compiler and the toolchain; the javadoc tool generates HTML API documentation from them, and IDEs display hover tooltips based on them. C/C++ have no such language-built-in documentation layer; tools like Doxygen are external conventions, and the compiler itself does not understand the structure of these comments. Making the documentation format part of the language ecosystem’s shared consensus buys a highly uniform API-documentation style across the whole ecosystem.

8. Structural differences from C++, and the trade-offs behind them

Dimension C++ Java
Inheritance Multiple inheritance Single class inheritance + multiple interface implementation
Pointers Explicit pointer syntax */&/-> No explicit pointer syntax; references are managed pointers
Memory release delete/free, manual GC, automatic reclamation
Operator overloading Supported Not supported (only + for string concatenation is the exception)
Free functions Supported None; everything is in a class
Arrays Contiguous stack/heap memory, no bounds checking Objects carrying length, with bounds checking
Header files Required None; no preprocessor/macros
Default parameters Supported Not supported; use method overloading instead
Destruction RAII deterministic destruction No deterministic destruction; use try-with-resources
const Widely applicable modifier final (much narrower semantics)

Explaining the trade-offs item by item, rather than stopping at listing differences:

  • Single inheritance + multiple interfaces, rather than multiple inheritance: C++’s multiple inheritance runs into the diamond-inheritance problem—when the same base class is inherited twice via two paths, whether the base members are shared or held separately requires extra mechanisms such as virtual inheritance to disambiguate, with complex, error-prone rules. Java’s solution is to split “inheriting an implementation” from “inheriting a type contract”: a class can inherit only from a single class (avoiding the implementation-level diamond problem), but it can implement any number of interfaces (pure contract, with no state by default; a new but much narrower conflict-resolution rule was introduced only after default methods were allowed in JDK 8). This is the classic trade-off of “sacrificing some expressiveness for simplicity of rules.”
  • No operator overloading: C++ allows almost any operator to be overloaded, which brings expressiveness (e.g. multiplying matrices directly with *) but is also a long-criticized source of complexity—a + b may silently call a custom function that is expensive and has side effects, and you cannot tell from the notation itself what is happening when reading the code. Java chooses the predictability of “a method call is always a method call”: a.equals(b) and bigInt.add(other) are both written as explicit methods, at the cost of verbosity, in exchange for the certainty of “you know roughly what will happen from the notation you see.”
  • No deterministic destruction; try-with-resources instead of RAII: C++’s destructor is called deterministically when a scope exits, which relies on an object’s lifetime being statically determinable. Java’s GC, in order to do generational collection, potentially move objects, and collect concurrently across threads, leaves the termination time of an object’s lifetime to the runtime to decide, so it is no longer deterministic—the finalize() mechanism has therefore been deprecated. But non-memory resources such as file handles and network connections still need deterministic closing, and Java uses try-with-resources (see Error Handling and Resource Management) to reimplement the core value of RAII—“close on scope exit”—without relying on deterministic destruction.
  • Arrays are always bounds-checked: out-of-bounds array access in C is undefined behavior, a major source of memory-safety problems. A Java array is, at the language level, a heap object carrying a length field, and every subscript access does a bounds check, throwing ArrayIndexOutOfBoundsException on an out-of-bounds access rather than reading or writing memory that does not belong to the array. The cost is an extra comparison per access, and the JIT can usually eliminate redundant checks that are provably safe within a loop, pushing the runtime cost close to zero.

Summary

  • Syntactic notation: {}, ;, if/for/while, and the arithmetic and logical operators are the same as C and carry over directly; var (JDK 10+) provides local type inference but does not change the essence of static typing.
  • Everything is in a class: no free functions and no global variables, stemming from the pure-object-oriented design and the historical goal of a security sandbox; main must be static as a direct result of the loading order “the class exists before the instance.”
  • No preprocessor: .class files self-describe complete signatures, making import merely name resolution rather than textual insertion, dispensing with header files, forward declarations, and macros, and thereby avoiding the whole class of bugs macros bring.
  • The few operator divergences (if needs a boolean, >>>, divide-by-zero throwing an exception, shift-count modulo) are all backed by the same principle: if you can report an error deterministically, leave no undefined behavior.
  • String immutability is a design serving three goals jointly—safe sharing, hash caching, and lock-free concurrency—at the cost of needing StringBuilder for concatenation.
  • The structural differences from C++ (single inheritance with multiple interfaces, no operator overloading, no deterministic destruction, mandatory array bounds checking) are each a concrete trade-off between “simplicity/safety” and “expressiveness/peak performance,” not arbitrary omissions.
