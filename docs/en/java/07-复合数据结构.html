Internal Implementation of the Collections Framework

In C++ you reach for std::vector, std::list, std::unordered_map, std::map. Java’s collections framework (Java Collections Framework, JCF) maps onto these one-for-one conceptually, but the internal implementation details, memory layout, resize strategies, and iterator semantics all deserve to be pried open one by one: what each container actually lays out on the heap, whether it copies values or references, and where the complexity comes from.

For the basics of “reference vs value”, see Variables and the Memory Model; for object header layout, see Data Types and Memory Layout.

1. Arrays: the Bedrock of Everything

An array stores a group of same-typed elements. You declare it with type[], create it with new type[length], and once the length is fixed it can never change:

int[] a = new int[4];       // 4 ints, all initialized to 0
a[0] = 100;
a[3] = 400;
System.out.println(a[0]);      // 100
System.out.println(a.length);  // 4 (note: it's a field, no parentheses — not a.length())

String[] s = new String[3]; // 3 reference slots, all initialized to null
s[0] = "hi";
System.out.println(s[1]);      // null (not yet assigned)

Out-of-bounds access throws an exception immediately; it does not silently read or write other memory the way C does:

int[] b = new int[2];
System.out.println(b[5]); // throws ArrayIndexOutOfBoundsException, program terminates (unless you catch it)

You can also supply all elements directly at declaration time:

int[] c = {1, 2, 3};        // length automatically fixed at 3

Java arrays are genuine objects, allocated on the heap; they are not just a chunk of raw memory plus pointer arithmetic as in C.

int[] a = new int[4];        // heap allocation: object header + length field + 4 contiguous ints
String[] s = new String[3];  // heap: 3 contiguous "reference slots", initialized to null

The Array Covariance Trap

Java array covariance means String[] IS-A Object[]. This passes at compile time, but at runtime every write must perform a type check:

Object[] arr = new String[3];
arr[0] = "ok";           // fine
arr[1] = Integer.valueOf(1); // compiles! throws ArrayStoreException at runtime

C++ templates are invariant: vector<string> and vector<Object> have nothing to do with each other. This Java array design is historical baggage (from before generics existed, so that Arrays.sort(Object[]) could work), and the price is a runtime store check. Generic collections (discussed below) are invariant.

Bounds-Check Cost and Its Elimination

Every a[i] inserts a 0 <= i < a.length check. The JIT has Range Check Elimination: in provably safe loops like for (int i=0;i<a.length;i++), C2 hoists the check out of the loop or deletes it entirely, bringing performance close to C. So there is a cost at the specification level, but at the implementation level it is frequently optimized away.

3. ArrayList vs LinkedList

ArrayList is the most commonly used “list”, supporting indexed access, appending, and removal:

List<String> list = new ArrayList<>();
list.add("a");
list.add("b");
list.add("c");
System.out.println(list.get(1));   // b
list.remove("b");                  // remove by value (there's also an overload remove(int) that removes by index)
System.out.println(list);          // [a, c]
System.out.println(list.size());   // 2

LinkedList is used essentially the same way as ArrayList (both implement the List interface), and additionally provides two-ended operations like addFirst/addLast:

LinkedList<String> linked = new LinkedList<>();
linked.add("x");
linked.addFirst("w");
System.out.println(linked);        // [w, x]

Beginners can just reach for ArrayList mindlessly at first; the following explains why.

ArrayList: Dynamic Array

Internally it is simply an Object[] elementData + an int size:

// simplified JDK source structure
transient Object[] elementData; // the array that actually stores the elements
private int size;               // logical size (<= elementData.length capacity)

Memory diagram:

ArrayList object (heap)      elementData array (heap)
┌───────────────┐          ┌────┬────┬────┬────┬────┬────┐
│ elementData ──┼────────▶ │ e0 │ e1 │ e2 │null│null│null│
│ size = 3      │          └────┴────┴────┴────┴────┴────┘
└───────────────┘           capacity = 6, size = 3

Note that it stores references (Object[]); the objects themselves are scattered all over the heap — unlike C++ vector<Point>, which inlines the Point values contiguously. So when you traverse a Java ArrayList<Point>, it’s “contiguous array → jump one by one to scattered heap locations”, and its cache locality is worse than a value-semantics C++ vector. To store primitives contiguously, you have to use a native int[] or a third-party primitive collection.

Resize: default capacity is 10; when full it grows by 1.5× (newCap = oldCap + (oldCap >> 1)), and Arrays.copyOf allocates a new array and copies the references (a shallow copy — it only copies pointer values, not the objects themselves).

size=10 is full, adding the 11th element:
new capacity = 10 + 5 = 15, allocate Object[15], copy 10 references over, old array awaits GC

Contrast with C++ std::vector, which commonly grows by 2× (libstdc++ uses 2x, MSVC uses 1.5x). Amortized O(1) append.

Why 1.5× rather than 2×: both guarantee amortized O(1) append complexity — as long as you grow by a fixed ratio (rather than a fixed increment) each time, the total copy cost is a geometric series, and amortized over each add it’s constant. The real difference lies in two things: wasted space and reuse of old memory. The larger the multiplier, the fewer resizes (lower total copy cost), but the larger the upper bound on space wasted after each resize — 2× growth wastes close to 50% of capacity in the worst case (when growth stops right after a resize), while 1.5× has an upper bound of about 33%. For Java, whose memory footprint is already more “bloated” than C++ value-semantics containers (recall the earlier discussion of ArrayList<Point> elements scattered across the heap), this is a more conservative choice. Another frequently cited reason is the potential for reusing old memory: if the growth multiplier is strictly less than the golden ratio (1+√5)/2 ≈ 1.618, then in theory the memory freed by the first few old arrays could possibly be reused by some later resize (this is a potential benefit arising from the mathematical property, on some allocators, that “the sum of a geometric growth sequence is less than the current demand”; whether it actually kicks in depends on the specific allocator implementation). 1.5 falls just under this threshold, and is an empirically well-balanced value between “as few resizes as possible” and “as small a peak waste as possible” — not an arbitrary choice.

Using reflection to peek at the true length of the underlying elementData array, you can directly observe this 1.5× growth curve (capacity is an internal implementation detail, so reflection needs --add-opens):

import java.lang.reflect.*;
import java.util.*;
public class GrowDemo {
    static int cap(ArrayList<?> list) throws Exception {
        Field f = ArrayList.class.getDeclaredField("elementData");
        f.setAccessible(true);
        return ((Object[]) f.get(list)).length;
    }
    public static void main(String[] args) throws Exception {
        ArrayList<Integer> list = new ArrayList<>();
        System.out.println("initial capacity = " + cap(list));
        int last = -1;
        for (int i = 0; i < 40; i++) {
            list.add(i);
            int c = cap(list);
            if (c != last) { System.out.println("size=" + list.size() + " -> capacity=" + c); last = c; }
        }
    }
}
// Run: java --add-opens java.base/java.util=ALL-UNNAMED GrowDemo.java
// initial capacity = 0     <- empty constructor lazily allocates; first add builds a length-10 array
// size=1  -> capacity=10
// size=11 -> capacity=15   <- 10 + (10>>1) = 15
// size=16 -> capacity=22   <- 15 + (15>>1) = 22
// size=23 -> capacity=33
// size=34 -> capacity=49

Source Evolution of the Resize Implementation: JDK 8 → JDK 9+ (including local JDK 25)

The 1.5× growth curve above underwent a refactoring of its underlying call chain between JDK 8 and the current JDK (25 locally). The numeric results are unchanged, but the implementation approach is worth understanding:

  • JDK 8: add(E e) → ensureCapacityInternal() → calculateCapacity() → ensureExplicitCapacity() → grow(). Inside grow(), the formula is hard-coded and assigned directly to the field:

    int newCapacity = oldCapacity + (oldCapacity >> 1);

  • JDK 9 and later (local JDK 25 uses this set too): the call chain is simplified to add(E e) → a private overload add(E e, Object[] elementData, int s) → grow(), passing elementData and size in as parameters instead of repeatedly reading fields inside the method. The capacity calculation is extracted into the shared utility class ArraysSupport:

    int newCapacity = ArraysSupport.newLength(oldCapacity,
            minCapacity - oldCapacity, /* minimum growth, the minimum needed */
            oldCapacity >> 1);         /* preferred growth, how much we'd prefer to grow */

    ArraysSupport.newLength is a shared utility method introduced in JDK 9, reused by ArrayList, HashMap, ArrayDeque, and other collection classes, so that each of them avoids reimplementing the same “minimum needed, preferred growth” boundary-handling logic; swapping field access for parameter passing also gives the JIT more room for escape analysis and inlining. This is a purely internal refactoring: the computed value of newCapacity and the 1.5× curve itself did not change — run the reflection code above once on JDK 8 and once on JDK 25 and the printed capacity sequences are identical.

When you construct with an initial capacity, new ArrayList<>(3), there is an easily overlooked edge case: inserting the 4th element triggers a resize, at which point minCapacity=4, oldCapacity=3, and oldCapacity>>1 is only 1, so taking “the larger of the two” gives a new capacity of 3+1=4, not the intuitive 3*1.5→4 (the numbers happen to coincide, but the derivation path differs). Only once capacity has grown large enough that oldCapacity>>1 (the preferred increment) consistently exceeds minCapacity-oldCapacity (the minimum increment) will you see a stable “exactly 1.5×” curve; the first few resizes at small capacity look more like “just a little more each time” linear growth, so don’t hastily extrapolate the ratio formula from small-scale tests.

ArrayList vs Vector

Vector is an older implementation than ArrayList (a JDK 1.0 legacy). Both are based on an Object[] dynamic array; the differences center on:

Dimension ArrayList Vector
Thread safety No Yes — every public method is synchronized
Growth multiplier 1.5× (oldCapacity + oldCapacity>>1) 2× (newCapacity = oldCapacity * 2)
Traversal Iterator / enhanced for Iterator + legacy Enumeration (elements())
Status Preferred Not recommended

Vector’s synchronized locks the entire object, so at any moment only one thread can enter any public method; even two threads merely reading must take turns exclusively. ArrayList doesn’t carry this overhead and is clearly faster in single-threaded scenarios. If you genuinely need thread safety in a multithreaded setting, use Collections.synchronizedList() or CopyOnWriteArrayList (see “Which Collections Are Thread-Safe” below) rather than Vector’s method-level whole-table lock — this is also the direct reason for “don’t use Vector in new code”.

LinkedList: Doubly Linked List

private static class Node<E> {
    E item;
    Node<E> next;
    Node<E> prev;
}

Each node is an independent heap object: 16-byte object header + 3 references (item/next/prev, each 4 bytes with compressed pointers) ≈ 32 bytes/node, a huge overhead to store a single element. Memory diagram:

first ─▶┌────┬────┬────┐   ┌────┬────┬────┐   ┌────┬────┬────┐◀─ last
        │prev│item│next┼──▶│prev│item│next┼──▶│prev│item│next│
        │null│ e0 │  ●─┘   │ ●  │ e1 │ ●─┘   │ ●  │ e2 │null│
        └────┴────┴────┘◀──┴────┴────┴────┘◀──┴────┴────┴────┘

Corresponds to C++ std::list. Nodes are scattered across the heap, so traversal is cache-unfriendly. get(i) is O(n) (walking from the nearest end). In practice ArrayList is almost always better; even with frequent head insertion, ArrayDeque is faster than LinkedList. LinkedList’s only advantage is O(1) removal when you hold a node reference, but the collection API generally never hands you a node.

ArrayList vs a Plain Array: How to Choose

Combining this with the array memory layout analysis in section 1, the trade-off between arrays and ArrayList can be summed up in one sentence: a fixed element count and a pursuit of extreme performance (especially for primitives) → use an array; an uncertain count and a need for the collection API → use ArrayList.

Dimension Plain array ArrayList
Length Fixed after creation; growing requires manually rebuilding the whole thing with Arrays.copyOf Auto-resizes (1.5×); size() always reflects the current element count
Element types stored Both primitives and reference types; primitives are inlined contiguously (see the memory diagram in section 1) Only reference types; primitives like int are auto-boxed into Integer, and elements are scattered across the heap (see the earlier ArrayList<Point> discussion)
API Only [] and .length; insertion/removal require hand-written shifting add/remove/contains/indexOf, etc., ready out of the box
Generic constraints Covariant but without compile-time enforcement of element type (Object[] o = new String[3] only reports ArrayStoreException at runtime, see section 1) ArrayList<String> welds the type in at compile time; no such runtime surprises
Typical scenarios Numeric computation, image/audio buffers, and other high-volume primitive scenarios The vast majority of “a group of objects” scenarios in business code

If the scenario is “store a huge pile of int/long and still grow dynamically”, the boxing overhead of ArrayList<Integer> may become a bottleneck; in that case, prefer hand-writing a dynamic array backed by int[], or bring in a third-party library that offers IntArrayList such as Eclipse Collections / fastutil (already mentioned in section 1), rather than being forced to pick between just “array” and “ArrayList”.

4. HashMap: the Main Event

HashMap stores “key -> value” mappings: put writes, get looks up by key, containsKey checks whether a key exists; traverse with entrySet() to get key-value pairs:

Map<String, Integer> scores = new HashMap<>();
scores.put("Alice", 90);
scores.put("Bob", 85);
System.out.println(scores.get("Alice"));           // 90
System.out.println(scores.containsKey("Carol"));   // false
for (Map.Entry<String, Integer> e : scores.entrySet()) {
    System.out.println(e.getKey() + " -> " + e.getValue());
}

Note: HashMap does not guarantee iteration order (the next section shows the actual print order differing from the insertion order); if you want a fixed order, see LinkedHashMap/TreeMap in the next section.

Corresponds to C++ std::unordered_map, but the implementation details differ greatly.

Structure: Bucket Array + Linked List / Red-Black Tree

transient Node<K,V>[] table;  // bucket array, length is always a power of 2
static class Node<K,V> {
    final int hash;   // the cached, perturbed hash
    final K key;
    V value;
    Node<K,V> next;   // linked-list pointer (chaining to resolve collisions)
}

Memory diagram (chaining on collision):

table (Node[16])
┌────┐
│ 0  │──▶ null
│ 1  │──▶ [h,k1,v1] ──▶ [h,k9,v9] ──▶ null   (bucket 1 has two colliding keys)
│ 2  │──▶ null
│... │
│ 5  │──▶ [h,k5,v5] ──▶ null

The Two General Solutions to Hash Collisions, and Why HashMap Chose Chaining

For any hash table implementation, as long as the bucket array has finite length, collisions are unavoidable, and there are only two general lines of attack:

  • Open Addressing: all elements live in the array itself; on collision, some probe sequence finds the next empty slot — linear probing (checking i+1, i+2, ... in turn, prone to “clustering”), quadratic probing (checking i±1², i±2², ..., easing clustering but potentially not probing all cells), double hashing (a second hash function determines the probe step, giving a more even distribution).
  • Separate Chaining: each bucket hangs an independent data structure (usually a linked list), stringing together all elements that land in that bucket — this is exactly HashMap’s choice, and the origin of the Node<K,V>.next chaining structure earlier in this section.

Why HashMap chose chaining rather than open addressing:

  1. Complexity of deletion: with open addressing, you cannot simply null out a deleted element, or you’d truncate subsequent probe sequences; you typically have to write a “deleted” tombstone marker, which both occupies a slot and complicates the lookup logic. With chaining, deletion is just ordinary linked-list removal, unhooking a node in O(1).
  2. Tolerance for load factor: with open addressing, all elements crowd into the same array, and once the load factor approaches 1 the probe sequences grow sharply, so you must strictly keep it at a low load factor (well below 1) to preserve performance, making it more sensitive to space waste. Chaining allows a load factor greater than 1 (in the extreme it degenerates into one big linked list — merely slow, not completely broken the way open addressing becomes), and HashMap’s default load factor of 0.75 is more relaxed as a result.
  3. Demands on hash function uniformity: with open addressing, once the hash function distributes unevenly, probe sequences overlap heavily and cause chain-reaction clustering. With chaining, even a mediocre hash function only lengthens the linked list within a single bucket, so the blast radius is more controllable.
  4. Resize pressure: with open addressing, resizing changes the semantics of the probe sequences wholesale, so you almost must reinsert every element. With chaining, resizing (rehash below) can redistribute bucket by bucket, and JDK 8 even manages to avoid recomputing the hash by checking a single bit.

On top of chaining, HashMap layers another optimization — treeifying when a chain’s length exceeds a threshold (see below), an enhancement that only arrived in JDK 8; the choice of chaining itself has been unchanged from JDK 1.0 to today.

The Hash Perturbation Function

The bucket index = hash & (n-1) (n is a power of 2, equivalent to modulo but faster). If you used key.hashCode() directly, the high bits wouldn’t participate (because & (n-1) keeps only the low bits), so keys with different high bits but identical low bits would collide. The perturbation XORs the top 16 bits down into the low bits:

static final int hash(Object key) {
    int h;
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
}

Treeify When Collisions Intensify

When a single bucket’s chain reaches length ≥ 8 and the table length is ≥ 64, the chain converts into a red-black tree, dropping that bucket’s worst-case lookup from O(n) to O(log n). When the tree node count falls back to ≤ 6, it degenerates back into a chain (the 6/8 hysteresis interval avoids frequent conversions).

chain length >= 8 and table.length >= 64:
bucket ──▶ chain ─treeify─▶ red-black tree (TreeNode)
if table hasn't reached 64 yet, resize in preference to treeifying

Why JDK 8 specifically introduced the red-black tree for this instead of keeping chains all the way: under a normal random distribution, a HashMap bucket can almost never accumulate 8 elements — the Poisson distribution tells us that at a load factor of 0.75, the probability of a single bucket reaching 8 elements is negligibly low, and chains are never a problem in normal use. What really drove this change is a class of denial-of-service attack that maliciously constructs hash collisions: if an attacker can control the keys placed into a HashMap (a typical scenario is a web server putting HTTP request parameter names into a HashMap during parsing), they can carefully craft a batch of strings whose hashCode() results deliberately land in the same bucket, degrading an operation you expected to be O(1) into an O(n) chain traversal — such attacks (the “Hash DoS” disclosed in 2011) once let a handful of malformed requests peg the CPU of web frameworks across many languages. With chains alone, even a hash perturbation function that already XORs high bits into low bits cannot prevent deliberately constructed collisions. JDK 8’s approach sets a ceiling on this worst case: once a bucket’s chain length hits a threshold “almost never reached under a normal distribution, but easily reached under attack” (8), it converts to a red-black tree, bounding the worst-case complexity at O(log n) instead of O(n). This is a “leave the normal path unchanged, only harden the worst case” design: the average scenario is still ordinary chained buckets (simple to implement, small constant factor), and only when it genuinely degrades to a pathological distribution does it bear the red-black tree’s higher implementation complexity and maintenance cost (larger nodes, insertion/deletion must maintain balance). This also explains why the threshold for reverting to a chain is set at 6 rather than 8 — to avoid repeatedly flipping the structure back and forth when the element count jitters between 7 and 8; the 6/8 gap is a hysteresis design meant to absorb this jitter.

Load Factor and Resize (rehash)

  • Load factor 0.75: when size > capacity * 0.75, resize to double. 0.75 is a space/time compromise (via Poisson-distribution analysis, balancing collision probability against wasted memory).
  • Resize rehash: allocate a new bucket array twice the size and rehash every element. Because capacity is a power of 2 and doubles, an element’s new position is only one of two possibilities: original position or original position + old capacity. JDK 8 exploits this property to avoid recomputing the hash — it only looks at whether the hash & oldCap bit is 0 or 1, splitting the old chain into two chains (lo/hi) and placing them at the two positions in the new table. O(n) but with a small constant.
old table.length=16, growing to 32:
a bucket's chain is split into two by (hash & 16) → bucket j and bucket j+16

JDK 7’s resize trigger condition has one hidden restriction more than JDK 8’s: JDK 7’s addEntry() checks (size >= threshold) && (null != table[bucketIndex]) — not only must the total element count exceed the threshold, but the specific bucket this insertion happens to land in must already be non-empty (i.e., an actual hash collision occurred) to trigger the resize; JDK 8 simplifies this to only size > threshold, no longer caring which bucket this insertion lands in. This is an easily overlooked historical detail, but it doesn’t affect the broad conclusion that both use “load factor 0.75, double past the threshold”.

The Full Flow of the put Method

The preceding points (bucket structure, perturbation function, treeify, resize) are each a corner of the puzzle; stringing them together into the full flow of putVal (JDK 8+) gives exactly the five steps “compute hash → locate bucket → handle collision → insert or update → check resize”:

// simplified putVal, keeping the core branches, omitting generics wildcards and such
final V putVal(int hash, K key, V value, boolean onlyIfAbsent, boolean evict) {
    Node<K,V>[] tab; Node<K,V> p; int n, i;
    // ① the bucket array is not yet initialized (first put) — resize() to build the table first
    if ((tab = table) == null || (n = tab.length) == 0)
        n = (tab = resize()).length;
    // ② locate the bucket with (n-1) & hash; bucket empty, drop in the new node directly — the fastest path
    if ((p = tab[i = (n - 1) & hash]) == null)
        tab[i] = newNode(hash, key, value, null);
    else {
        // ③ bucket non-empty, handle collision: first check whether the bucket's first node is the same key
        Node<K,V> e; K k;
        if (p.hash == hash && ((k = p.key) == key || (key != null && key.equals(k))))
            e = p; // hit, record the node to be updated
        else if (p instanceof TreeNode) // already treeified, do a red-black-tree insertion
            e = ((TreeNode<K,V>) p).putTreeVal(this, tab, hash, key, value);
        else {
            // ordinary chain: traverse to the tail; if found, record e; if not, tail-insert a new node
            for (int binCount = 0; ; ++binCount) {
                if ((e = p.next) == null) {
                    p.next = newNode(hash, key, value, null);
                    // chain length reached the threshold (8), attempt treeify (internally also checks whether table length >= 64)
                    if (binCount >= TREEIFY_THRESHOLD - 1)
                        treeifyBin(tab, hash);
                    break;
                }
                if (e.hash == hash && ((k = e.key) == key || (key != null && key.equals(k))))
                    break; // found the same-key node, break out
                p = e;
            }
        }
        // ④ key already exists: onlyIfAbsent decides whether to overwrite value, return the old value
        if (e != null) {
            V oldValue = e.value;
            if (!onlyIfAbsent || oldValue == null) e.value = value;
            afterNodeAccess(e); // hook method; LinkedHashMap uses it to maintain access order (LRU)
            return oldValue;
        }
    }
    ++modCount; // structural-modification count +1; fail-fast iterators rely on it to detect concurrent modification
    // ⑤ a new node was inserted; resize if size exceeds the threshold
    if (++size > threshold) resize();
    afterNodeInsertion(evict); // hook method; LinkedHashMap's LRU eviction logic hangs here
    return null;
}

A few points that often come up:

  • The onlyIfAbsent parameter: put() passes false (overwrite if present), putIfAbsent() passes true (don’t overwrite if present, return the old value) — both share the same putVal, differing only by this one boolean.
  • The afterNodeAccess/afterNodeInsertion hooks: empty implementations in HashMap, specifically left for LinkedHashMap to override, used to maintain the insertion-order/access-order doubly linked list (section 5) and implement LRU cache eviction — a textbook template-method pattern in the design, where HashMap defines the skeleton and subclasses fill in the details.
  • Which happens first, treeify or resize: when inserting a new node lengthens a chain, treeify is checked first, and if treeify internally finds table.length < 64 it resizes in preference to actually building a tree (to avoid mass-building red-black trees on a small table and wasting space); whereas the overall resize check after insertion completes (step ⑤) is a separate matter, checking whether the whole table’s size exceeds the threshold, unrelated to any single bucket’s chain length.

The Key Contract: equals/hashCode

HashMap locates in two steps: first find the bucket by hash, then compare within the bucket one by one with equals. So a custom key must correctly override both equals and hashCode, or equal objects scattered into different buckets can’t be found again. See the equals/hashCode contract in “Object-Oriented Programming and the Type System”. Same in C++: unordered_map needs a std::hash specialization + operator==.

Why It Is Not Thread-Safe: Down to Each Specific Bad Thing

“Not thread-safe” is not an empty phrase; under concurrency HashMap concretely runs into these kinds of problems:

1. JDK 7: resize infinite loop (a classic interview question). JDK 7’s transfer() uses head insertion to move old-chain elements into the new array, and does so “traversing the old chain while inserting new nodes at the head of the new bucket”. If thread A is suspended halfway through a resize while thread B is also resizing concurrently, the two alternately advancing the next pointer can twist a link that was originally a → b into a ring a → b → a after the two threads each disagree about “the next node”. Afterwards, any thread that then get()s that bucket traverses next forever without reaching null, pegging the CPU and freezing the program.

normal relocation:  a -> b -> null
after concurrent interleaving it may become:  a -> b -> a -> b -> ... (a ring, traversal never terminates)

2. JDK 8: data overwrite (lost update). JDK 8 changed transfer() to tail insertion, no longer producing a ring — the official release note explicitly cites fixing this infinite loop; but this does not equal thread safety. The most direct example is two threads simultaneously executing step ② of putVal() on the same empty bucket (tab[i] == null, drop in the new node directly) — this “check bucket empty + write new node” combination is not atomic, both threads read “the bucket is empty”, both perform the write, and the later write directly overwrites the earlier write’s reference, so the earlier put is entirely lost and size increased only once.

3. Lost size count. ++size is itself a three-step “read-increment-write-back”; executed concurrently by multiple threads it’s a classic race: two threads both read size=10, both compute 11 and write it back, so two puts only make size become 11 instead of 12. The following code reliably reproduces a “lost update” (switching HashMap to a get+put read-modify-write pattern; it doesn’t rely on any specific internal race, it only needs to demonstrate that “a non-atomic read-write combination loses updates under concurrency”):

import java.util.*;
import java.util.concurrent.*;

public class LostUpdateDemo {
    public static void main(String[] args) throws Exception {
        Map<String, Integer> map = new HashMap<>(); // not thread-safe
        map.put("counter", 0);
        int threads = 8, loopsPerThread = 2000;
        ExecutorService pool = Executors.newFixedThreadPool(threads);
        CountDownLatch latch = new CountDownLatch(threads);
        for (int t = 0; t < threads; t++) {
            pool.submit(() -> {
                for (int i = 0; i < loopsPerThread; i++) {
                    int cur = map.get("counter");   // read
                    map.put("counter", cur + 1);    // modify then write back; the read-write is not atomic
                }
                latch.countDown();
            });
        }
        latch.await();
        pool.shutdown();
        System.out.println("expected = " + (threads * loopsPerThread));
        System.out.println("actual   = " + map.get("counter"));
    }
}
// expected = 16000
// actual   = 2866   <- the actual output differs every run, but is reliably less than expected, proving lost updates

4. modCount is not volatile, so fail-fast is unreliable too. modCount is just a plain int field; when one thread structurally modifies the Map, another thread’s iterator won’t necessarily “see” the change immediately (a visibility problem), so ConcurrentModificationException is “best-effort” rather than guaranteed to fire — this is also the fundamental reason section 8 stresses that “fail-fast is not concurrency protection”.

Summarizing from the three core lenses of concurrent programming: put()’s “check bucket empty + write” and ++size both break atomicity; the modCount/table references are not marked volatile, breaking visibility; JDK 7’s head-insertion relocation additionally involves ordering under instruction reordering. Stack all three together and you have the entire content behind the statement “HashMap is not thread-safe”.

How ConcurrentHashMap Solves Thread Safety

ConcurrentHashMap uses two completely different approaches in JDK 7 and JDK 8:

JDK 7: segment locks (Segment). The whole ConcurrentHashMap is split into several Segments, each of which extends ReentrantLock and internally is itself an independent little HashEntry[] hash table. A write operation locks only its own Segment; different Segments can be written concurrently. The upper bound on concurrency is the number of Segments (default 16). Read operations mostly don’t lock, relying on volatile for visibility.

ConcurrentHashMap (JDK7)
┌─────────┬─────────┬─────────┬─────┐
│Segment0 │Segment1 │Segment2 │ ... │  <- each Segment carries its own ReentrantLock
│(small hash)│(small hash)│(small hash)│     │     and its own HashEntry[]
└─────────┴─────────┴─────────┴─────┘

JDK 8: drop Segment, switch to CAS + synchronized (locking the bucket head node). The structure reverts to the same single Node[] table as HashMap (likewise supporting chain-to-red-black-tree conversion), and concurrency control descends to the “bucket” granularity, finer than Segment:

  • When the target bucket is empty, use CAS (compareAndSwapObject) to try dropping in the head node directly; on success it’s done, no lock needed; on failure (meaning another thread got there first) it spins and retries.
  • When the target bucket is already non-empty (another thread is occupying it, or there’s already a chain/tree), apply synchronized to that bucket’s head node, mutually excluding only at this one bucket’s granularity, without affecting concurrent writes to other buckets.
  • During resize, a volatile sizeCtl/migration-state marker coordinates multiple threads in a “sharded relocation”: each thread claims a range of buckets to migrate, marks that range “done” with CAS when finished, and other threads can come “help” migrate ranges not yet done, rather than having only one thread resize alone while the others idle.
ConcurrentHashMap (JDK8)
Node[] table (same structure as HashMap)
bucket empty  → CAS drop in directly (lock-free)
bucket non-empty → synchronized (that bucket's head node) → chain/red-black-tree insertion

The theoretical concurrency rises from “the number of Segments” to “the array length”, and since JDK 6 synchronized supports lock upgrading (biased lock → lightweight lock → heavyweight lock), so in low-contention scenarios it performs on par with ReentrantLock yet more lightly — this is the direct reason JDK 8 abandoned segment locking.

Why ConcurrentHashMap disallows a null key/value: get(key) returning null has two possible meanings — “this key doesn’t exist” or “this key exists but its value is null”. Single-threaded, you can call containsKey() once more to disambiguate; but in a concurrent setting containsKey() and get() are two separate calls, and another thread may insert/remove in between, so the result you looked up is already out of sync, and null brings an unremovable ambiguity. Hashtable likewise forbids null; HashMap single-threaded has no such ambiguity problem, so it relaxes the restriction.

How to Choose Among HashMap / Hashtable / HashSet / ConcurrentHashMap

HashMap Hashtable HashSet ConcurrentHashMap
Thread safety No Yes (whole-table synchronized) No Yes (CAS + bucket-level synchronized)
null key/value Both allowed Neither allowed One null element allowed Neither allowed
Underlying structure Array + chain/red-black tree Array + chain (no treeify) Wraps a HashMap internally, elements as keys Array + chain/red-black tree
Initial capacity 16, power of 2 11, resize 2n+1 Same as HashMap Customizable, also power of 2
Iterator fail-fast Iterator Legacy Enumeration + fail-fast Iterator fail-fast Iterator Weakly consistent iterator, does not throw ConcurrentModificationException
Use case Single-threaded / already self-synchronized key-value storage Basically abandoned, only for maintaining old code Single-threaded deduplication, membership testing High-concurrency counters, caches, shared state

Hashtable’s default capacity is a prime number, 11 (rather than a power of 2), meant to reduce collisions in concert with its own hash distribution strategy, but the price is that after resizing to 2n+1 it must recompute the hash of every element — unlike HashMap/ConcurrentHashMap, whose capacity is always a power of 2 and can use bit operations instead of modulo and exploit the “the new position differs by only one bit” property during resize to skip recomputing hashes. This is also one of the reasons Hashtable clearly lags in performance, not merely a matter of “it added locks”.

Which Collections Are Thread-Safe

Besides ConcurrentHashMap, the java.util.concurrent package together with a few legacy classes forms the full picture of Java’s thread-safe collections:

Collection/utility Belongs to Thread-safe implementation approach
Vector List Method-level synchronized (legacy, not recommended)
Hashtable Map Method-level synchronized (legacy, not recommended)
Collections.synchronizedList/Map/Set(...) Wrapper Wraps a lock around the passed-in collection; every method call synchronizes the whole collection, coarse granularity
ConcurrentHashMap Map See above, CAS + bucket-level synchronized
CopyOnWriteArrayList List Copy-on-write of the entire array (writes are heavy, reads are entirely lock-free), suited to “read-heavy, write-almost-never” scenarios, e.g., listener lists
ConcurrentLinkedQueue Queue Lock-free (CAS) non-blocking queue
The BlockingQueue family (ArrayBlockingQueue/LinkedBlockingQueue, etc.) Queue Internally uses locks + condition variables, supports “block and wait when the queue is full/empty”, the standard tool for the producer-consumer pattern

Selection principle: prefer the purpose-built concurrent collections in the java.util.concurrent package (ConcurrentHashMap, CopyOnWriteArrayList, the various BlockingQueues), which are optimized with fine-grained locking or lock-free algorithms for concurrent scenarios; you’ll only see Vector/Hashtable in legacy code; Collections.synchronizedXxx() is a stopgap of “wrapping a shell around a ready-made non-thread-safe collection”, coarse-grained and mediocre in performance, and compound operations (e.g., “check contains then insert”) still require the caller to lock the wrapped collection themselves for overall synchronization.

5. LinkedHashMap / TreeMap

LinkedHashMap and TreeMap have put/get just like HashMap; the only difference is iteration order:

Map<String, Integer> linked = new LinkedHashMap<>();
linked.put("banana", 1);
linked.put("apple", 2);
System.out.println(linked.get("apple")); // 2
System.out.println(linked);              // {banana=1, apple=2}

Map<String, Integer> tree = new TreeMap<>();
tree.put("banana", 1);
tree.put("apple", 2);
System.out.println(tree);                // {apple=2, banana=1}

How to choose among the three Maps: don’t care about order → HashMap (fastest); want to iterate in insertion order → LinkedHashMap; want to iterate sorted by key → TreeMap.

LinkedHashMap

On top of HashMap’s Node, it adds a before/after doubly linked chain to maintain insertion order (or access order with accessOrder=true, enabling an LRU cache). Hash lookup is still O(1), with the extra cost of maintaining one linked list threading through all nodes.

HashMap's bucket structure + one doubly linked chain threading through all nodes (recording order)
head ──▶ node ──▶ node ──▶ node ──▶ tail

TreeMap

Based on a red-black tree (self-balancing BST), corresponding to C++ std::map. Sorted by key (natural order or a Comparator). All operations are O(log n), and it provides ordered views like firstKey/lastKey/floorKey/ceilingKey/subMap. Keys must be comparable (Comparable or pass a Comparator), see Standard Library Algorithms.

The Distribution of Red-Black Trees Across Java Collections

An easy point to confuse with “HashMap will treeify” is: only TreeMap/TreeSet use the red-black tree as their sole core structure, where every lookup, insertion, and deletion happens on the whole tree, naturally maintaining global ordering; whereas the red-black tree in HashMap/HashSet/LinkedHashMap/LinkedHashSet/ConcurrentHashMap is merely a local degeneration structure inside a single bucket when collisions are severe (the treeify conditions in section 4: chain length ≥ 8 and table length ≥ 64). Between buckets it’s still hash distribution, and the whole Map does not thereby gain any global sorting ability — HashMap’s iteration order is still the “seemingly random” bucket order and won’t become sorted just because some bucket internally is a tree.

Compared with the AVL tree that pursues absolute balance, the red-black tree allows the looser balance of “the longest path is no more than twice the shortest path” (guaranteed by the rules “equal number of black nodes, no two red nodes adjacent”), needing fewer rotations on insertion/deletion and thus lower maintenance cost, while lookup complexity remains steady at O(log n) — this is an engineering trade-off of “giving up ultimate balance in exchange for lower overall maintenance cost”. TreeMap benefits from it directly, while HashMap’s treeify uses it as a “safety net for the worst case”; the two motivations are not the same.

The iteration-order comparison of the three Maps is clear at a glance: HashMap is determined by bucket position (unspecified, looks “random”), LinkedHashMap preserves insertion order, TreeMap is sorted by key:

import java.util.*;
public class MapOrder {
    static void fill(Map<String,Integer> m) {
        for (String k : new String[]{"banana","apple","cherry","date"}) m.put(k, k.length());
    }
    public static void main(String[] args) {
        Map<String,Integer> hash = new HashMap<>();
        Map<String,Integer> linked = new LinkedHashMap<>();
        Map<String,Integer> tree = new TreeMap<>();
        fill(hash); fill(linked); fill(tree);
        System.out.println("HashMap:       " + hash.keySet());
        System.out.println("LinkedHashMap: " + linked.keySet());
        System.out.println("TreeMap:       " + tree.keySet());
    }
}
// HashMap:       [banana, date, apple, cherry]   <- bucket order, unspecified (never rely on it)
// LinkedHashMap: [banana, apple, cherry, date]   <- insertion order
// TreeMap:       [apple, banana, cherry, date]   <- lexicographic order

6. HashSet / ArrayDeque

HashSet is a collection that “stores only keys, no values”: add adds, contains checks whether an element exists, and duplicate elements are automatically ignored:

Set<String> set = new HashSet<>();
set.add("a");
set.add("b");
set.add("a");                          // duplicate, ignored
System.out.println(set.size());        // 2
System.out.println(set.contains("a"));  // true

ArrayDeque is a double-ended queue: use it as a stack with push/pop (last-in-first-out), or as a queue with offer/poll (first-in-first-out):

ArrayDeque<Integer> stack = new ArrayDeque<>();
stack.push(1);
stack.push(2);
System.out.println(stack.pop());    // 2 —— last-in-first-out

ArrayDeque<Integer> queue = new ArrayDeque<>();
queue.offer(1);
queue.offer(2);
System.out.println(queue.poll());   // 1 —— first-in-first-out
  • HashSet: internally just a HashMap, with the element as the key and the value a shared dummy Object. So everything about HashSet equals the keySet of a HashMap. Corresponds to C++ unordered_set.
  • LinkedHashSet: internally a LinkedHashMap, preserving insertion order.
  • TreeSet: internally a TreeMap, sorted, corresponds to std::set.
  • ArrayDeque: a double-ended queue implemented with a circular array; the two indices head/tail move around a ring buffer, and it doubles on resize. As either a stack or a queue it’s faster than Stack (obsolete, inherits from Vector, carries synchronization) and LinkedList. The preferred stack/queue implementation. It disallows null (null denotes an empty slot).
ArrayDeque circular array:
┌───┬───┬───┬───┬───┬───┐
│ e │ e │   │   │ e │ e │   head=4, tail=2 (wrapped around)
└───┴───┴───┴───┴───┴───┘

7. Generic Collections and the Impact of Type Erasure

When declaring a collection, angle brackets <type> specify “what it can hold”; the compiler blocks type errors for you at compile time, and you don’t need a cast when retrieving:

ArrayList<String> names = new ArrayList<>();
names.add("Alice");
// names.add(42);       // compile error: type mismatch, caught by the compiler before you even run Java
String first = names.get(0); // no cast needed
System.out.println(first);   // Alice

Contrast: without angle brackets (the old-style ArrayList names = new ArrayList();), get(0) returns an Object that you must cast manually, and it may blow up only at runtime — which is why nowadays you always write the type inside the angle brackets in Java.

ArrayList<String> at runtime is just ArrayList, with an internal Object[]; the generic type is only checked at compile time, with casts inserted automatically. This is why you can’t new T[], and why a collection always stores references (primitives are auto-boxed). For the details of the erasure mechanism, see Generics and Type Erasure.

Consequence: each element of an ArrayList<Integer> is an Integer object on the heap + a reference in the array, so the memory and boxing/unboxing overhead is far greater than C++ vector<int>. For performance-sensitive scenarios use native arrays or third-party primitive collections (Eclipse Collections, fastutil).

8. Iterators and fail-fast

Using the enhanced for loop to traverse a collection is the most common idiom; underneath, the compiler is actually calling Iterator for you:

List<String> list = new ArrayList<>(List.of("a", "b", "c"));
for (String x : list) {
    System.out.println(x);
}

There’s a hard rule: during traversal, do not call the collection’s add/remove directly to modify it (regardless of whether it’s the element you intend to remove), or it will very likely throw an exception. To remove elements during traversal, use removeIf, or explicitly obtain the Iterator and call its own remove(). The “underlying comparison with C” below explains why.

The collection internally maintains modCount (the structural-modification count). When an iterator is created it records expectedModCount, and validates it on every next(); if the collection is modified via a non-iterator route in the meantime, it throws ConcurrentModificationException.

List<Integer> list = new ArrayList<>(List.of(1, 2, 3));
for (Integer x : list) {      // enhanced for uses Iterator underneath
    if (x == 2) list.remove(x); // structural modification → modCount changes → the next next() throws
}
// Correct approach: use iterator.remove() or list.removeIf(x -> x == 2)

Running it for real, you can see the exception really does get thrown, while removeIf is safe and unscathed:

import java.util.*;
public class FailFast {
    public static void main(String[] args) {
        List<Integer> list = new ArrayList<>(List.of(1, 2, 3, 4));
        try {
            for (Integer x : list) {          // enhanced for uses Iterator underneath
                if (x == 2) list.remove(x);   // structural modification, modCount changes
            }
        } catch (ConcurrentModificationException e) {
            System.out.println("caught: " + e.getClass().getSimpleName());
        }
        list.removeIf(x -> x == 2);           // correct: goes through the iterator internally, doesn't throw CME
        System.out.println("after removeIf: " + list);
    }
}
// caught: ConcurrentModificationException
// after removeIf: [1, 3, 4]

fail-fast is best-effort error detection (not guaranteed to fire), not concurrency protection; for genuine concurrency use CopyOnWriteArrayList/ConcurrentHashMap (weakly consistent iterators that don’t throw this exception). The C++ STL counterpart is “iterator invalidation” — but in the STL that’s UB, whereas Java proactively throws an exception to help you catch it early.

Summary

  • An array is a heap object carrying a length field; out-of-bounds throws an exception rather than being UB, but covariance leaves the trap of a runtime store check.
  • ArrayList is a resizable array of references, growing by 1.5× — a trade-off value between the number of resizes and peak memory waste; LinkedList is a doubly linked list (high per-node overhead, cache-unfriendly traversal), with markedly different complexity, and in practice ArrayList/ArrayDeque are almost always the better choice.
  • HashMap is a bucket array + chain/red-black tree, sustaining amortized O(1) via hash perturbation, resizing at a 0.75 load factor, and JDK 8’s rehash optimization; the treeify introduced in JDK 8 specifically targets maliciously constructed hash-collision attacks, bounding the worst-case complexity from O(n) to O(log n), and almost never triggers under a normal distribution.
  • LinkedHashMap/TreeMap maintain order with a doubly linked chain and a red-black tree respectively; HashSet/TreeSet/LinkedHashSet are essentially shells over the corresponding Maps; the red-black tree is a global structure only in TreeMap/TreeSet, and merely a local degeneration of a single bucket in the HashMap family.
  • HashMap’s thread-unsafety shows up as flaws at all three levels: atomicity (check-bucket-empty + write, ++size), visibility (modCount/table not volatile), and ordering (JDK 7 head-insertion concurrent resize forming a ring); ConcurrentHashMap uses CAS + bucket-level synchronized (JDK 8, replacing JDK 7’s Segment segment locks) to push concurrency control down to the single bucket, and, with coordinated resizing, solves these problems.
  • Generics are erased at runtime, so all primitives in a collection are boxed; iterators do fail-fast detection via modCount, which is best-effort rather than concurrency protection.
