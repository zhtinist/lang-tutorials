Common Third-Party Libraries

Dependency management has long been a pain point in C/C++: hand-written Makefile/CMake, header files plus static/dynamic libraries, and only recently a unified approach with vcpkg/Conan. The Java ecosystem unified dependency distribution long ago with Maven/Gradle + a central repository. This chapter covers build tools, the coordinate mechanism, and what specific problem each mainstream library solves and at what cost.

1. Build and Dependency Management

Coordinates and Repositories

Write a single line in a config file saying “which library, which version I want to use,” and the build tool automatically goes to the repository, downloads the corresponding jar package, and places it into the project—no need, as in C/C++, to download source or prebuilt libraries from official sites yourself and manually configure include/lib paths.

Each library is uniquely identified by its GAV coordinates: groupId:artifactId:version. Analogous to “namespace + library name + version” in C++, but here it is a globally unified namespace (Maven Central).

com.google.guava : guava : 33.0.0-jre
     |               |         |
   groupId       artifactId  version

Maven (pom.xml, XML, convention over configuration):

<dependencies>
    <dependency>
        <groupId>com.google.guava</groupId>
        <artifactId>guava</artifactId>
        <version>33.0.0-jre</version>
    </dependency>
</dependencies>

Gradle (build.gradle, Groovy/Kotlin DSL, more flexible, fast incremental builds):

dependencies {
    implementation 'com.google.guava:guava:33.0.0-jre'
    testImplementation 'org.junit.jupiter:junit-jupiter:5.10.0'
}

The build tool downloads jars from the repository into a local cache (Maven’s ~/.m2/repository); the default repository is Maven Central, and a private server (Nexus/Artifactory) can be added.

Transitive Dependencies and scope

The key mechanism: transitive dependencies. You depend on A, A depends on B, and the build tool automatically fetches B—no need to declare it explicitly. Analogous to C++ if it had fully automatic header-file + library dependency resolution.

Your project ──> Jackson-databind ──> Jackson-core
                                  └──> Jackson-annotations   (fetched fully automatically)

Dependency conflicts: when different libraries depend on different versions of the same library, Maven arbitrates using “nearest path wins + first-declared wins,” while Gradle takes the highest version by default. You can view the dependency tree with mvn dependency:tree / gradle dependencies and exclude with <exclusions>.

scope/configuration determines in which phase a dependency is visible:

Maven scope Gradle configuration Meaning
compile (default) implementation/api needed at both compile and run time
provided compileOnly needed at compile time, provided at runtime by the container (e.g. Servlet API)
runtime runtimeOnly needed only at runtime (e.g. JDBC drivers)
test testImplementation needed only for testing

implementation vs api (Gradle): implementation does not transitively expose the dependency to downstream consumers (encapsulation, analogous to PIMPL hiding the implementation), while api does expose it. Sensible use of implementation reduces the recompilation scope and avoids dependency leakage.

2. Ecosystem Positioning

General Utilities: Guava, Apache Commons

  • Guava (Google): Preconditions argument validation, immutable collections ImmutableList, Multimap/BiMap/Cache (local cache), Splitter/Joiner, and the concurrent ListenableFuture. Highly engineered, the first choice for modern projects.
  • Apache Commons: commons-lang3 (StringUtils, ObjectUtils), commons-collections4, commons-io. Long-established, relied upon by many legacy projects. Newer JDK versions have built in quite a few equivalents (like String.strip, Files.readString); use as needed.

JSON: Jackson, Gson

Serializing/deserializing objects to and from JSON, reading and writing fields via reflection.

// Jackson: the most full-featured, Spring's default, supports three modes—streaming/tree/data binding
ObjectMapper mapper = new ObjectMapper();
String json = mapper.writeValueAsString(person);        // object -> JSON
Person p = mapper.readValue(json, Person.class);        // JSON -> object

// Gson (Google): a more concise API, fewer dependencies, for lightweight scenarios
Gson gson = new Gson();
String j = gson.toJson(person);
Person p2 = gson.fromJson(j, Person.class);

Selection: for Spring projects use Jackson directly (already integrated); for standalone small tools use Gson.

Enterprise Framework: Spring / Spring Boot

The de facto standard for Java backends. The core is the IoC container + DI + AOP.

The specific problem dependency injection (DI) solves: when one class needs to use the functionality of another, the most direct approach is to new the dependency internally—OrderService writes new AlipayClient() inside. The cost of writing it this way is not obvious in small projects but gradually surfaces as a project grows: 1. Cannot replace the implementation: when testing OrderService you want to use a fake payment client (mock) that doesn’t actually make network requests, but AlipayClient is already hard-coded inside OrderService, with no seam to insert a substitute implementation, so you can only test alongside the real network call (slow, unstable, possibly incurring real charges). 2. Dependency relationships must be threaded through by hand: if AlipayClient itself depends on an HttpConfig, then to construct it correctly OrderService must know how the whole chain is assembled—when the dependency graph gets even a little deeper, the hand-written new code in main degenerates into a big block of “who is created first, and passed to whom” boilerplate, and any change to a downstream constructor signature forces every hand-assembled spot along the call chain to change too. 3. Lifecycle and scope management: whether the same AlipayClient instance should exist only once in the whole application (singleton) or one per request—hand-written new has no single place to decide and record this, making it easy to end up with “what should be reused isn’t, what should be isolated isn’t.”

What a DI container does is quite plain: it moves the bookkeeping of “who creates the objects, in what order, how many are created, and when they are destroyed” out of business code and manages it centrally in the container, so a business class only declares what types of dependencies it needs (usually through constructor parameters), not caring which concrete implementation the dependency is or how it is built:

@Service                              // declared as a container-managed Bean
public class OrderService {
    private final PayClient payClient;
    // constructor injection: at startup the container finds a PayClient-type Bean and passes it in
    public OrderService(PayClient payClient) { this.payClient = payClient; }
}

The direct benefits this brings correspond to the three costs above: for testing, just pass a hand-written or Mockito-generated fake PayClient into the same constructor, without changing a single line of OrderService’s code; no matter how deep the dependency chain, the container scans, resolves, and injects in order uniformly at startup (including detecting circular dependencies and reporting errors), and business code always faces only the “I need an X” layer; whether singleton or multi-instance, and when to initialize/destroy, are managed uniformly by the container per configuration, no longer scattered among hand-written news. Why this is worth a framework rather than writing your own factory function: once a hand-written factory needs to support “find an implementation by interface,” “handle construction order,” “detect circular dependencies,” “distinguish singleton and multi-instance scopes,” and “switch implementations by environment/toggle,” what you write is essentially a feature-incomplete homemade DI container—rather than reinventing it and having to maintain this whole mechanism yourself, better to use a ready-made, full-featured container proven across many projects.

AOP (Aspect-Oriented Programming): extracts cross-cutting concerns (transactions, logging, permissions) out of business code and weaves them in declaratively.

@Transactional                        // the method is automatically wrapped in a transaction: begin -> execute -> commit/rollback
public void placeOrder() { /* pure business, no transaction boilerplate */ }

Underneath it relies on dynamic proxies: Spring generates a proxy object for the Bean, and a method call first passes through the proxy (executing the aspect logic) and then forwards. Two implementations: - JDK dynamic proxy: when the target implements an interface, use java.lang.reflect.Proxy to generate a proxy class for the interface at runtime. - CGLIB: when there is no interface, generate a subclass of the target class at runtime (bytecode enhancement) overriding the methods. Therefore proxied methods cannot be final (they can’t be overridden).

This mechanism relies on reflection (reading type information and invoking methods at runtime)—C++ has no built-in reflection; Java implements it via .class metadata + the Class/Method APIs, at the cost of runtime overhead and difficulty of static optimization (Spring’s slow startup partly stems from this; GraalVM native images are a mitigation for this point).

ORM: Hibernate / JPA

  • JPA: a specification (interfaces) defining the annotations and APIs for object-relational mapping.
  • Hibernate: the most mainstream implementation of JPA.
@Entity                               // mapped to a database table
public class User {
    @Id @GeneratedValue Long id;      // primary key, auto-increment
    @Column(nullable = false) String name;
}
// operate on objects with EntityManager/Repository, and the framework translates to SQL

The specific problem ORM solves is the impedance mismatch between the “object model” and the “relational model”: in the object world, data exists as a graph structure with inheritance, associations, and collection fields (a User references a set of Orders, an Order in turn references Products); in a relational database, data is flat tables associated by foreign keys. Hand-written JDBC converting directly between these two models means every query repeats four kinds of boilerplate: concatenating SQL strings (a misspelled column/table name won’t be caught at compile time, only exposed at runtime), pulling each column out of the ResultSet and manually stuffing it into object fields, managing the opening/closing of connections and transactions plus exception handling, and having to guard against SQL injection yourself whenever there is string concatenation. This work has to be repeated for every table and every query, and most of it is mechanical field shuffling, not business logic.

Hibernate/JPA automates this mechanical conversion: annotate the class with its mapping to the table (@Entity/@Id/@Column), read and write fields via reflection at runtime, automatically generate parameterized SQL, and automatically convert the result set back into objects. It also incidentally does two things hand-written JDBC won’t do automatically: dirty checking—the EntityManager remembers an entity’s original state when it was read from the database, and at transaction commit automatically compares, generating an UPDATE only for the fields actually modified, with no need to manually judge “which columns did I change this time”; and a session-level cache—repeatedly querying the same entity by ID within the same transaction/session won’t repeatedly hit the database. If you had to reimplement these abilities in hand-written JDBC, you would essentially be building a simplified version of an ORM.

The costs are equally real and should not be dodged: the auto-generated SQL is opaque, and complex queries easily trigger the N+1 query inadvertently (querying a list and then accessing the association field of each element one by one; if the association is lazy-loaded, this becomes 1 list query + N association queries rather than a single JOIN); accessing an unloaded field of an object after it has left the session throws LazyInitializationException; and object-relational mapping itself is not always intuitive when handling inheritance hierarchies and complex many-to-many relationships. Choosing an ORM is essentially trading “control over execution details” for “development efficiency and less boilerplate,” and for complex report-style queries many teams still choose to write SQL directly or use a more lightweight SQL-mapping tool (such as MyBatis).

Testing: JUnit5 + Mockito

// JUnit5: a unit testing framework
class CalcTest {
    @Test
    void add() {
        assertEquals(3, new Calc().add(1, 2));
    }
    @ParameterizedTest
    @ValueSource(ints = {1, 2, 3})
    void positive(int n) { assertTrue(n > 0); }
}

// Mockito: mock dependencies to isolate the unit under test
UserRepo repo = mock(UserRepo.class);
when(repo.findById(1L)).thenReturn(new User());   // stubbing: specify the mock's behavior
UserService svc = new UserService(repo);
svc.load(1L);
verify(repo).findById(1L);                        // verify the interaction occurred

Mockito’s ability to “isolate the unit under test” hinges precisely on the constructor injection from the DI section above—UserService’s dependency is declared via a constructor parameter rather than an internal new, so the test code has a seam to insert a fake UserRepo; if UserService internally news a real UserRepo, the unit test cannot avoid incidentally testing database access—this is exactly the concrete benefit DI brings to “testability.”

Compile-Time Enhancement: Lombok

Uses annotations to generate bytecode at compile time, eliminating boilerplate such as getters/setters/constructors/toString.

@Data                                 // generates getters/setters/equals/hashCode/toString
@AllArgsConstructor
public class Point {
    private int x;
    private int y;
    // no methods in the source, but the compiled bytecode has them all
}

Principle: Lombok is an annotation processor that hooks into the javac compilation pipeline and modifies the AST (abstract syntax tree) at compile time to inject methods. It is not runtime reflection, so there is zero runtime overhead. Cost: the IDE needs a plugin to recognize the generated methods; it depends on javac internal APIs, so major JDK version upgrades occasionally bring compatibility issues.

Logging: SLF4J + Logback

SLF4J is a logging facade (i.e. a layer of unified interface standing at the very front—your code depends only on this interface, and the caller is unaware of which concrete logging implementation sits behind it), while Logback/Log4j2 are the implementations. Code depends only on the facade, binding the concrete implementation at runtime—analogous to “programming to interfaces,” so you can swap implementations without changing code.

private static final Logger log = LoggerFactory.getLogger(MyClass.class);
log.info("user {} logged in", userId);   // the {} placeholder concatenates lazily, not building the string when the level isn't enabled, saving overhead
log.error("failed", exception);

A config file (logback.xml) controls the level, output format, and rolling policy, with no code changes needed.

The underlying mechanism of “the facade depends on an interface, binding the implementation at runtime” is the JDK’s built-in SPI (Service Provider Interface): java.util.ServiceLoader. SLF4J relies precisely on it to discover and bind implementations like Logback at runtime. Below is a demonstration of this mechanism in pure JDK—no third-party library needed.

The caller depends only on the interface Greeter; implementation classes are registered via config files under META-INF/services/, discovered at runtime by ServiceLoader, with neither new nor import appearing in the caller’s code:

// spi/Greeter.java —— the "facade": the caller depends only on it
package spi;
public interface Greeter { String greet(String name); }

// spi/EnglishGreeter.java —— one implementation
package spi;
public class EnglishGreeter implements Greeter {
    public String greet(String name) { return "Hello, " + name; }
}

// spi/FrenchGreeter.java —— another implementation
package spi;
public class FrenchGreeter implements Greeter {
    public String greet(String name) { return "Bonjour, " + name; }
}

// spi/Main.java —— the caller: discovers implementations at runtime, references no implementation class
package spi;
import java.util.ServiceLoader;
public class Main {
    public static void main(String[] args) {
        ServiceLoader<Greeter> loader = ServiceLoader.load(Greeter.class);
        for (Greeter g : loader) {   // discovered at runtime, the caller does not new/import concrete implementations
            System.out.println(g.getClass().getSimpleName() + " -> " + g.greet("Ada"));
        }
    }
}

The registration file (plain text, one full implementation-class name per line), placed under META-INF/services/ on the classpath, with filename = the full interface name:

file: META-INF/services/spi.Greeter
spi.EnglishGreeter
spi.FrenchGreeter

Compile and run (the out directory contains both the classes and META-INF/services):

javac -d out spi/*.java
java -cp out spi.Main
# EnglishGreeter -> Hello, Ada
# FrenchGreeter -> Bonjour, Ada

Adding a new implementation only requires adding a class + one line to the registration file, with zero changes to the caller—this is exactly the JDK-native support for “programming to interfaces + pluggable implementations,” and also the common foundation of JDBC drivers, SLF4J bindings, java.nio.file.spi, and more.

High-Performance Networking: Netty

An asynchronous, event-driven networking framework based on Java NIO (multiplexing with epoll/kqueue), using the Reactor pattern + a small number of threads to handle massive numbers of connections. RPC frameworks (gRPC-Java, Dubbo) and messaging middleware often use it underneath.

The problem Netty aims to solve shares the same root as virtual threads (see “Concurrency Models”)—“one thread per network connection” cannot hold up on thread-stack memory and context switching when connections reach tens of thousands—but it offers a different route: virtual threads let blocking-style code be transparently unmounted/mounted at runtime; Netty, at the programming-model level, directly refuses to let a thread block on a single connection, instead using a small number of threads to poll massive numbers of connections through the OS’s multiplexing mechanism (epoll/kqueue, a single system call querying which of a large batch of connections are ready), so only ready connections are processed, and the processing itself is non-blocking. Both routes are essentially “covering a large number of waiting connections with a small number of execution units,” the difference being that virtual threads preserve the synchronous programming style, while Netty is an explicit event-driven callback style.

  • EventLoop: one thread bound to one selector, polling multiplexed channel events—analogous to a hand-written epoll event loop in C, but encapsulated as a pipeline.
  • ChannelPipeline: a chain of handlers that inbound/outbound data passes through in turn (codec, business processing), similar to a chain of responsibility.
  • Pooled ByteBuf (off-heap memory + reference counting), reducing GC and copies—close to manually managing buffers in C, but you must remember to release manually to prevent leaks.

Applicability: self-built high-concurrency long-connection services. For ordinary HTTP services, Spring Boot (with its embedded Tomcat/Netty) suffices; there’s no need to write Netty directly.

3. Packaging: jar and fat-jar

  • Ordinary jar: contains only this project’s classes + resources, without dependencies. To run it you must list all dependency jars on the classpath manually—analogous to compiling to .o without linking the libraries.
  • fat-jar / uber-jar: packs all transitive dependencies into one executable jar, and java -jar app.jar runs directly. Spring Boot uses spring-boot-maven-plugin; ordinary projects use maven-shade-plugin or Gradle’s shadow plugin.
mvn package                       # produces target/app.jar
java -jar target/app.jar          # a fat-jar runs directly
java -cp "app.jar:libs/*" Main    # an ordinary jar needs the classpath specified

When multiple dependencies in a fat-jar contain resources of the same name (like their respective META-INF/services), conflicts arise, and the shade plugin’s transformers are responsible for merging them.

4. JNI: The Cost of Calling C

Java code itself runs inside the JVM’s managed environment (automatic garbage collection, memory safety) and cannot directly call compiled C functions. JNI (Java Native Interface) is the official bridge: it lets a Java method call a piece of native code written in C/C++ and compiled into a .so/.dll (for reusing an existing native library, or doing CPU-intensive computation). But crossing this bridge is costly and is usually a last resort:

public class NativeLib {
    static { System.loadLibrary("mylib"); }   // load libmylib.so/.dll
    public native int compute(int[] data);    // a native method, implemented on the C side
}

Sources of cost: - Call overhead: each crossing of the JNI boundary has a fixed cost (argument marshalling, state switching), unsuitable for high-frequency fine-grained calls. - Object marshalling: Java objects/arrays are on the managed heap, and access from the C side needs GetArrayElements and the like, which may trigger a copy or pin the object, hindering GC from moving/compacting it. - Safety: a crash in native code (segfault) directly takes down the entire JVM, losing the JVM’s memory-safety guarantee. - Portability: a native library must be compiled for each platform, breaking Java’s “write once, run anywhere.”

The JDK is pushing the FFM API (Foreign Function & Memory, JEP 454, officially in JDK 22) as a modern replacement for JNI, declaring native calls and off-heap memory in pure Java with no C glue code needed, at lower cost and with more safety. New projects should consider it first.

The reflection mechanism behind dependency injection and proxies can be combined with the type information in 08-Object Orientation and the Type System; for the class loading and runtime model of fat-jars, see 01-The Runtime Model.

Summary

  • Usage level (how to choose, how to write): declare dependencies with GAV coordinates, and the build tool fetches them automatically (including transitive dependencies), with scope controlling the visible phase; for JSON choose Jackson (complete ecosystem) or Gson (lightweight); Spring declares Beans and transaction boundaries via annotations; JPA/Hibernate maps tables to annotated classes; testing uses JUnit5 + Mockito to isolate dependencies; Lombok uses annotations to save boilerplate; logging is written against the SLF4J interface, swapping the implementation via a config file; packaging into a fat-jar runs directly with one command; JNI/FFM is used only when you must reuse a native library or squeeze out extreme performance.
  • Principle level (why it’s designed this way, what problem it solves): the DI container moves “how objects are created, how many are created, and how the dependency order is resolved” out of business code for central management, directly yielding testability (injecting mocks to replace real dependencies) and freeing you from manually changing construction code everywhere when the dependency graph changes—writing equivalent functionality by hand is essentially reinventing an incomplete container; Spring AOP relies on dynamic proxies (JDK Proxy or a CGLIB subclass) to wrap a layer around the method call, and like DI relies on reflection to read/write fields and discover types at runtime; ORM solves the impedance mismatch between the object graph and relational tables, automatically generating SQL and doing dirty checking and session caching, at the cost of opaque generated SQL and easily stepping on N+1 queries and lazy-loading traps; Lombok is an annotation processor that modifies the AST at compile time with zero runtime overhead; the pluggable mechanism of the SLF4J facade and JDBC drivers is at bottom the JDK-native SPI/ServiceLoader; Netty and virtual threads solve the same class of “connections/requests far exceeding the thread-count ceiling” problem, addressing it via event-driven and user-space scheduling routes respectively; a fat-jar merely merges multiple jars’ classes and resources into one package, with the class-loading model unchanged; the cost of JNI comes from the argument marshalling and GC interaction when crossing the boundary between the “managed heap” and “raw memory.”
