Control Flow

Java’s branch and loop syntax is highly similar to C (if/for/while/switch can be copied over directly); this chapter focuses on the points of difference and the mechanisms at the bytecode level: the three forms of switch and their bytecode implementations, the iterator behind the enhanced for, pattern matching, and text blocks.

1. if

Basically the same as C, with one hard difference: the condition must be a boolean (see “Basic Syntax”). The “nonzero is true” style of if (n) does not compile in Java; you must write if (n != 0). The benefit is that it eradicates the classic bug of mistakenly writing an assignment as if (a = b) — in if (a = b), if a = b is not of boolean type it is a compile error outright.

At the bytecode level, if is just a conditional comparison instruction (if_icmpge, ifnull, ifeq, etc.) plus a jump, the same as what we saw in Chapter 1, no surprises.

2. switch: Three Forms + Bytecode

switch has three ways to write it in total: traditional switch, the -> expression switch, and the pattern-matching switch — each solving a more specific problem than the last.

2.1 Traditional switch: The Fall-Through Trap Persists

Exactly like C: not writing break falls through to the next case.

int day = 3;
switch (day) {
    case 1:
    case 2:
    case 3:
        System.out.println("first half of the workweek");
        break;                       // omit it and you fall through, the same pitfall as C
    case 6:
    case 7:
        System.out.println("weekend");
        break;
    default:
        System.out.println("other");
}

Types supported by traditional switch: integers (and wrapper classes unboxable to int), char, enum, and String (C does not support switching on strings). String’s switch is lowered by the compiler into a two-level decision of “locate first by hashCode, then confirm by equals.”

2.2 Expression switch (->, JDK 14+): No Fall-Through, Can Return a Value

The new syntax uses ->, does not fall through, needs no break, and can also be evaluated as an expression:

int day = 3;
String kind = switch (day) {
    case 1, 2, 3, 4, 5 -> "workday";       // multiple labels juxtaposed by commas
    case 6, 7          -> "weekend";
    default            -> "invalid";
};                                          // note that as an expression, there's a semicolon at the end

// When multiple statements are needed, use a block + yield to return a value
int score = switch (grade) {
    case 'A' -> 100;
    case 'B' -> { int base = 80; yield base + 5; }  // yield hands out the block's value
    default  -> 0;
};

Key points: - A -> branch jumps out automatically once executed, no fall-through, syntactically eliminating the bug of forgetting to write break. - As an expression, the compiler requires exhausting all possibilities (covering all enum values for an enum, or providing a default), otherwise it is a compile error — safer than C. - A multi-statement branch uses a {} block and yield to hand out a value (return here would return the whole method, don’t confuse the two).

Why introduce the expression switch specifically (JEP 361, made official in JDK 14): traditional switch has two long-criticized problems. First, fall-through by default — break is a means of “preventing fall-through” rather than “entering the next branch,” semantically counterintuitive, and every case missing a break is a real bug; such mistakes recur in production code, so common they became a standard rule in static-analysis tools. Second, a traditional switch is only a statement, unable to be used as an expression to directly produce a value — to branch on some value to compute a result, you must first declare a variable, assign it in each case, and remember to break on every path, an amount of boilerplate out of proportion to the logical complexity, and easy to miss a branch and forget to assign. The expression switch solves both problems at once: the -> syntax makes each branch not fall through by default (to fall through you must explicitly use a block and the old syntax), while the whole switch can be used directly as an expression assigned to a variable or used as a return value, and the compiler further enforces exhaustiveness checking, plugging omissions like “forgot to write some branch.” This is not syntactic-sugar prettification, but downgrading the common need of “branch evaluation” from “statement + manual assignment + break discipline” into a built-in, structurally error-preventing expression.

2.3 Pattern-Matching switch (JDK 21+): Dispatch by Type

switch can match on type and bind a variable, and combined with sealed types can do exhaustiveness checking:

Object obj = ...;
String desc = switch (obj) {
    case Integer i when i > 0 -> "positive integer " + i;   // when is the guard condition
    case Integer i            -> "non-positive integer " + i;
    case String s             -> "string of length " + s.length();
    case null                 -> "null value";              // can match null explicitly
    default                   -> "other type";
};

This is equivalent to gathering a string of if (obj instanceof Integer i) ... else if (obj instanceof String s) ... into a structured form, a product of Java moving toward “algebraic data types + pattern matching.” A completely different level from C’s switch.

Below is a full runnable version; describe dispatches over several actual types:

public class PatternSwitch {
    static String describe(Object obj) {
        return switch (obj) {
            case Integer i when i > 0 -> "positive integer " + i;
            case Integer i            -> "non-positive integer " + i;
            case String s             -> "string of length " + s.length();
            case null                 -> "null value";
            default                   -> "other type";
        };
    }
    public static void main(String[] args) {
        System.out.println(describe(42));     // positive integer 42
        System.out.println(describe(-3));     // non-positive integer -3
        System.out.println(describe("hello")); // string of length 5
        System.out.println(describe(null));   // null value
        System.out.println(describe(3.14));   // other type
    }
}

Note that the order of cases matters: the guarded Integer i when i > 0 must come before the unguarded Integer i; if you put the unguarded one first, it would eat all Integers first, and the compiler would report an error outright because the later case is “already covered by the earlier one and unreachable.”

Why introduce the pattern-matching switch that dispatches by type (JEP 441, made official in JDK 21): before this, the extremely common need of “dispatching by runtime type” could only be written as a string of if (obj instanceof Integer) { Integer i = (Integer) obj; ... } else if (obj instanceof String) { String s = (String) obj; ... }. This code has two layers of duplicated labor: first judge the type, then manually cast once more — instanceof has already confirmed the type at run time, and the cast is logically redundant information repetition, purely boilerplate caused by the language’s lack of expressiveness; moreover, this string of if-else has no compiler to check for you “whether all possible types are covered,” and a missed branch only surfaces at run time as an unhandled default path. The pattern-matching switch integrates “type judgment + variable binding + optional value matching” into one structure, and combined with sealed types (see “Object-Orientation and the Type System”) also lets the compiler do exhaustiveness checking — if you write a case for every implementing class of a sealed interface, exhaustiveness is verified by the compiler, no hand-written default fallback needed, and adding an implementing class and forgetting to handle it fails at compile time outright rather than silently slipping through at run time. This is essentially Java moving toward the mature mechanism of “algebraic data types + pattern matching” in functional languages, to solve the “branch by structure/type” kind of problem that previously could only be hand-written as a verbose and unsafe instanceof+cast chain.

2.4 Bytecode: tableswitch vs lookupswitch

switch has two instructions in bytecode, chosen automatically by the compiler according to the distribution of case values — this is why switch is often faster than an equivalent if-else chain:

Instruction Applies to Mechanism Complexity
tableswitch case values contiguous or near-contiguous use the value as a jump-table index to jump directly O(1)
lookupswitch case values sparse store sorted (value, offset) pairs, binary search O(log n)

tableswitch is like the jump table a C compiler generates for dense cases: it compiles case 1/2/3 into a contiguous offset table, and at run time target = table[value - low bound], done in one addressing, without comparing one by one. lookupswitch is for sparse values like case 1/100/10000, storing sorted key-value pairs for binary search. You can observe it with javap -c:

javap -c YourClass     // you'll see tableswitch { ... } or lookupswitch { ... }

Contiguous small-integer cases → tableswitch (fastest); sparse → lookupswitch. This hints: in performance-sensitive scenarios, keeping case values as contiguous as possible favors generating a jump table.

Below we compare the two instructions with a real example. dense has contiguous cases (0~3), sparse has sparse cases (1/100/10000):

public class SwitchByteCode {
    static int dense(int x) {   // case 0,1,2,3 contiguous
        switch (x) {
            case 0: return 10;  case 1: return 11;
            case 2: return 12;  case 3: return 13;
            default: return -1;
        }
    }
    static int sparse(int x) {  // case 1,100,10000 sparse
        switch (x) {
            case 1: return 10;  case 100: return 11;
            case 10000: return 12;
            default: return -1;
        }
    }
    public static void main(String[] args) {}
}

The key output of javac SwitchByteCode.java && javap -c SwitchByteCode.class (measured):

static int dense(int);
     0: iload_0
     1: tableswitch   { // 0 to 3
                   0: 32
                   1: 35
                   2: 38
                   3: 41
             default: 44
        }

static int sparse(int);
     0: iload_0
     1: lookupswitch  { // 3
                   1: 36
                 100: 39
               10000: 42
             default: 45
        }

dense compiles into tableswitch — a contiguous offset table for 0..3, jumping directly by index at run time; sparse compiles into lookupswitch — sorted key-value pairs for binary search. Same switch, but the distribution of case values decides which instruction is used.

3. Loops

for / while / do-while, all three, are semantically identical to C, so no need to belabor them:

for (int i = 0; i < n; i++) { ... }
while (cond) { ... }
do { ... } while (cond);   // executes at least once

Java also has an enhanced for (for-each) that C lacks, specifically for “iterating over each element of a thing” without managing the index yourself:

int[] arr = {1, 2, 3};
for (int x : arr) { ... }              // iterate an array

List<String> list = List.of("a","b");
for (String s : list) { ... }          // iterate a collection

The bytecode of for/while/do-while is just a loop test + a goto back-edge (see the goto 4 in Chapter 1). The back-edge count is precisely one of the bases on which HotSpot decides a “hot loop” and triggers the JIT.

The underlying mechanism of the enhanced for depends on what is iterated: - Arrays: the compiler lowers it into an ordinary indexed for loop (controlled by length, accessed by index), with no iterator object, zero extra overhead. - Collections implementing Iterable: the compiler lowers it into calling iterator() to get an iterator and looping over hasNext()/next(). Equivalent expansion:

// for (String s : list) {...} actually compiles into ↓
for (Iterator<String> it = list.iterator(); it.hasNext(); ) {
    String s = it.next();
    ...
}

Compared with C++’s range-based for (for (auto& x : container) relying on begin()/end()), it corresponds almost one-to-one: Java relies on Iterable.iterator() + the Iterator interface. Note that when iterating a collection with the enhanced for, you cannot add to or remove from that collection inside the loop body, otherwise the iterator detects the structural change and throws ConcurrentModificationException (to remove, use the iterator’s own remove() or use removeIf). Collections and iterators are detailed in “Composite Data Structures”.

4. Labeled break / continue

Java has no goto (it is a reserved word but unused), but it provides labeled break/continue to break out of / continue an outer loop, covering the common scenario in C of using goto to break out of nested loops:

outer:
for (int i = 0; i < n; i++) {
    for (int j = 0; j < m; j++) {
        if (matrix[i][j] == target) {
            found = true;
            break outer;        // break out of both outer loops directly
        }
        if (skip) continue outer;  // go directly to the outer loop's next iteration
    }
}

break outer ends the entire loop the label refers to, continue outer jumps to that loop’s next iteration. More structured and readable than C’s flag variables or goto. At the bytecode level it is still a goto to the corresponding offset.

5. The Ternary Operator

int max = (a > b) ? a : b;

Same as C. Note that in Java the two branches of a ternary expression must have compatible types (type promotion / boxing is applied); e.g. cond ? 1 : 2.0 is a double overall. Mixing wrapper classes with primitive types may trigger auto-unboxing leading to an unexpected NPE, so beware.

6. instanceof Pattern Matching

Traditional instanceof judges the type and then still requires a manual cast; pattern matching (JDK 16+) does it in one step and binds a variable:

// Traditional style
if (obj instanceof String) {
    String s = (String) obj;    // still have to cast again
    System.out.println(s.length());
}

// Pattern-matching style
if (obj instanceof String s) {  // if the check succeeds, obj is bound to s (already of String type)
    System.out.println(s.length());
}

// You can keep using the bound variable within the same condition
if (obj instanceof String s && s.length() > 3) { ... }

The scope of s is “wherever it can be determined to definitely be a String” (flow-sensitive scoping). This, Chapter 8’s type system, and this chapter’s pattern-matching switch are the same direction of language evolution. It is equivalent to making C++’s if (auto* p = dynamic_cast<String*>(obj)) more convenient.

7. Text Blocks (Text Block, JDK 15+)

A multi-line string literal, saving you from hand-writing \n and concatenation, similar to the heredoc of other languages:

String json = """
        {
          "name": "Ada",
          "age": 36
        }
        """;                    // wrapped in triple quotes; the indentation baseline is determined at compile time and common leading whitespace stripped

Key points: - It is still an ordinary String (immutable, interned into the constant pool), only the way it’s written is different; at run time it is no different from an ordinary string. - The compiler takes the indentation of the closing """ as the baseline and strips the common leading whitespace of each line, making it convenient to align indentation in your code without polluting the content. - Well suited for embedding JSON / SQL / HTML. Compared with C where you can only concatenate a bunch of adjacent "..." or use line-ending \, text blocks are much cleaner.

Summary

  • The if condition must be a boolean, eliminating if(a=b)-type mistakes.
  • The three forms of switch each solve a more specific problem than the last: traditional switch (has fall-through, a legacy burden from C-style default fall-through), the -> expression switch (eliminates the forgot-to-break bug, and can also serve as an expression with enforced exhaustiveness checking), and the pattern-matching switch (replaces the verbose and unsafe instanceof+cast chain with compiler-verified exhaustiveness); String/enum can both be switched on.
  • The bytecode tableswitch (contiguous values → jump table, O(1)) vs lookupswitch (sparse values → binary search, O(log n)), chosen automatically by the compiler, viewable with javap -c, is why switch is sometimes faster than an equivalent if-else chain.
  • Enhanced for: arrays are lowered into an indexed loop, collections rely on Iterable.iterator(); modifying the collection during iteration throws ConcurrentModificationException.
  • Labeled break/continue replaces cross-level goto.
