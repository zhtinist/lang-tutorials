# 内存管理与 I/O 设备

操作系统对内存的管理经历了从"一个进程独占全部内存"到"分页支撑的虚拟内存"的演进，核心动机始终是同一个：物理内存有限，而进程数量和进程需要的地址空间不断增长。I/O 这一侧的问题则相反——CPU 和外部设备的速度差了几个数量级，如何让 CPU 不被"等设备"拖慢，催生了从轮询到中断、DMA、通道，再到多路复用和异步 I/O 的一整套机制。这一篇把内存管理（连续分配、分段分页、虚拟内存、页面置换）和 I/O 管理（控制方式、I/O 模型、磁盘调度、设备管理）串起来讲，并且补两个常考的"其他"知识点（编译链接、软硬链接）和两个计算机组成原理的基础问题（CPU/GPU、冯·诺依曼与哈佛体系结构）。

## 一、内存的连续分配方式

连续分配要求一个进程在内存中占用**一段连续的物理地址空间**——即地址范围是 `[start, start + size - 1)` 这样一段整体。这是内存管理最早期的方式，理解它的局限性，才能理解为什么后来会发展出分页这种非连续管理机制。

**三种连续分配方式**：

- **单一连续分配**：内存只分两部分——操作系统占一块，用户程序占剩下的全部。同一时刻只能有一个用户进程在内存中运行。优点是没有内存管理的复杂性，也不存在碎片问题；缺点是 CPU 利用率极低，多任务无从谈起，早已被淘汰，仅在早期单任务系统或极简嵌入式场景出现。
- **固定分区分配**：内存启动时被预先划分成若干个大小固定的分区（可以等大小，也可以不等大小），每个分区只能装下一个进程。问题在于**内部碎片**——进程通常比分区小，分区里剩下的空间既装不下别的进程，又不能物理上让当前进程用，白白浪费。
- **动态分区分配**：不预先划分分区，进程到达时才按需分配一块恰好够用的连续内存。分配算法有四种：
  - **首次适应（First Fit）**：空闲块按地址顺序排成链表，从头开始找，第一个大小够用的就分配。实现简单，但链表前部容易被切割得越来越碎。
  - **最佳适应（Best Fit）**：遍历所有空闲块，选择大小最接近请求量的那个分配。表面上最节省空间，但恰恰会留下大量比请求量略大一点、几乎无法再利用的小碎片。
  - **最坏适应（Worst Fit）**：反过来，每次都选**最大**的空闲块分配，让剩下的部分尽量大、还能再用。缺点是大块空间很快被用光，之后遇到大请求就没地方分了。
  - **邻近适应（Next Fit）**：像首次适应，但不是每次都从链表头开始找，而是从上次分配结束的位置继续往下找。避免了链表头部被反复扫描和切割，但容易导致内存后半部分被过度使用，前后碎片不均衡。

动态分区虽然比固定分区灵活，但分配、回收次数一多，空闲内存还是会被切成大量不连续的小块，也就是**外部碎片**——碎片总量可能足够，但没有一块连续到能满足新请求。

**连续分配为什么被淘汰**：本质问题是"要求连续"这个约束本身——无论用哪种分配算法，只要坚持进程必须占用连续物理地址，外部碎片就无法根治，内存利用率也上不去。分页机制把这个约束直接去掉——**逻辑上连续，物理上可以不连续**——从根源上解决了这个问题，这也是内存管理从连续分配走向分段分页的直接动因。

## 二、内存分段与分页

分段和分页是两种**非连续**内存管理方式，都要求引入地址映射机制（段表 / 页表），但划分依据完全不同。

**分段（Segmentation）**：按程序的逻辑功能模块划分——代码段、数据段、堆栈段各自成一段，每段长度可以不同。段表记录每个段的**段基址**和**段长**。地址是二维的（段号 + 段内偏移），地址转换要做两次越界检查：先看段号是否超过段表长度，再看段内偏移是否超过该段的段长，任何一步越界都会触发中断。分段对用户不透明——程序员需要显式组织和引用段（比如汇编里的 `.text`、`.data`），换来的好处是能做**段级共享和保护**（例如代码段设为只读，多个进程共享同一份代码段的物理内存，只需各自的段表项都指向相同的段基址和段长）。代价是可变长度的段容易导致**外部碎片**，且难以在此基础上实现虚拟内存。

**分页（Paging）**：把物理内存和逻辑地址空间都切成大小固定的块——物理内存里的块叫**页框（Frame）**，逻辑地址空间里的块叫**页面（Page）**，两者大小相等（常见 4KB）。页表记录逻辑页号到物理页框号的映射，这个映射过程对用户完全透明。地址是一维的（页号 + 页内偏移），转换时只需一次越界检查（页号是否超过页表长度）——页内偏移不需要检查，因为它严格小于页面大小，不存在越界的可能。分页的代价是**内部碎片**（进程大小不是页大小的整数倍，最后一页会有浪费），好处是消除了外部碎片，而且为虚拟内存的实现打下了基础。

两者的差异可以归纳成一张表：

| 维度 | 分段 | 分页 |
|------|------|------|
| 管理单元 | 可变长度段（按逻辑模块划分） | 固定大小页（页框与页面大小相等） |
| 用户可见性 | 不透明，需要程序员显式管理 | 透明，操作系统统一管理 |
| 地址结构 | 二维地址（段号 + 段内偏移） | 一维地址（页号 + 页内偏移） |
| 碎片类型 | 外部碎片 | 内部碎片 |
| 共享与保护 | 段级（如整个代码段只读） | 页级（每页有读/写/执行权限位） |
| 硬件开销 | 段表 + 段长检查 | 页表 + TLB（快表）+ MMU |
| 典型应用 | 早期系统（如 x86 实模式） | 现代操作系统（Linux、Windows） |

**保护机制**上两者思路一致，都靠**界地址保护**（越界检查）和**存取控制保护**（读/写/执行权限检查）。**共享机制**上，分段共享要求不同进程的段表项指向同一个物理基址和段长；分页共享则要求不同进程的页表项映射到同一个物理页框。

现代操作系统（Linux、Windows）以分页作为核心内存管理机制；部分架构（如 x86）出于向后兼容，同时保留了分段功能，但实践中通常把所有段的基址设为 0、段长设为最大，实质上把分段"降级"为不发挥作用的摆设，真正干活的是分页。32 位系统里，通过二级页表把一个虚拟地址转换成物理地址，大致流程是：虚拟地址拆成"页目录索引 + 页表索引 + 页内偏移"三部分，先用页目录索引在页目录表里找到对应的页表，再用页表索引在这个页表里找到页框号，最后页框号拼上页内偏移得到物理地址：

```text
虚拟地址: [ 页目录索引 | 页表索引 | 页内偏移 ]
                |            |           |
                v            v           |
           页目录表 ---> 页表 ---> 页框号  |
                                    |     |
                                    v     v
                             物理地址 = 页框号 + 页内偏移
```

## 三、虚拟内存的概念与作用

虚拟内存是操作系统提供的一种**从逻辑上扩充内存**的技术，建立在分页（或分段）机制之上，核心是两个功能：**请求调入**和**内存置换**。它给每个进程一个独立、连续的虚拟地址空间，让每个进程都误以为自己独占了整个内存，实际上物理内存和磁盘空间被结合起来共同支撑这个假象。

**请求调入**：进程运行时并不需要一次性把所有页面都装进物理内存，只装入当前用得到的部分；当访问到还没调入的页面时，操作系统再把它从磁盘读进来。

**内存置换**：当请求调入发生、但物理内存已经装满时，操作系统要选一批暂时用不上的页面换出到磁盘，腾出空间给当前需要的页面——选哪些页面换出，就是页面置换算法要解决的问题（下一节详细展开）。

请求分页存储管理方式，就是在普通分页管理的基础上，叠加了请求调入和内存置换这两个功能。

**硬件支持**主要有三块：

- **请求页表机制**：在普通页表的基础上增加**状态位**（该页是否已调入内存）、**访问字段**（配合置换算法记录访问情况）、**修改位**（该页调入后是否被写过）、**外存地址**（该页在磁盘上的位置）四个字段。其中状态位和外存地址是必须有的，修改位和访问字段则要看具体置换/写回策略是否需要。
- **缺页中断机构**：CPU 访问的页不在内存中时触发缺页中断。和普通中断不同，缺页中断是在指令的**执行周期内**触发的——CPU 会立即中止当前指令的执行，跳转到操作系统的缺页处理程序，等所需页面调入内存、页表更新完毕后，再回来重新执行这条指令。
- **地址变换机构**：负责把虚拟地址转换为物理地址，具体由页表和 TLB（快表，缓存最近用过的页表项）配合完成。

**优缺点**：优点是提高内存利用率（不常用的数据换出到磁盘，腾出物理内存）、简化编程（内存管理对程序员透明）、支持多任务（每个进程有独立地址空间）；缺点是频繁的缺页中断和页表查找带来性能开销，且实现本身增加了操作系统的复杂度。

**页框分配策略**分三种：

1. **固定分配局部置换**：给每个进程分配固定数量的页框，置换只在该进程自己的页框范围内进行。
2. **可变分配局部置换**：置换依然只在进程自己的页框内进行（互不干扰），但分配的页框数量会根据进程的运行情况动态增减。
3. **可变分配全局置换**：系统维护一个全局空闲页框队列，谁缺页就从队列里分一个给谁；队列空了，就从整个系统的内存空间里选一个页面换出。

注意**不存在"固定分配全局置换"**这种组合——全局置换意味着任何进程都可能被抢走页框，进程持有的页框数（驻留集）必然会变化，这与"固定分配"矛盾。

实际系统中，Linux 采用纯分页机制管理虚拟内存；Windows 采用分段与分页结合的方式（即"请求段页式存储管理"），以支持更大的地址空间和更细粒度的保护。

## 四、页面置换算法

页面置换算法解决的问题是：物理内存已满、又发生缺页时，选哪个页面换出到磁盘。目标是让缺页率尽量低。六种常见算法：

**1. 最佳置换算法（OPT, Optimal）**：每次都淘汰"未来最长时间不会再被访问"的页面。这是理论上缺页率最低的算法，但需要预知未来的访问序列，现实中无法实现，只用作衡量其他算法优劣的性能上限参考。

**2. 先进先出（FIFO, First In First Out）**：淘汰最早进入内存的页面，用队列实现。实现简单、开销低，但完全不考虑页面是否还会被用到，性能较差，还会出现**Belady 异常**——增加物理页框数，缺页率反而可能上升（详见下一节的演示）。

**3. 最近最久未使用（LRU, Least Recently Used）**：淘汰最长时间没有被访问的页面，基于**时间局部性**（最近被访问过的页面，很可能很快再被访问）。可以用双向链表（软件）或计数器（硬件）实现，命中率接近 OPT，但需要维护访问时间戳或调整链表顺序，开销较高。

**4. 最不常用（LFU, Least Frequently Used）**：淘汰**访问次数**最少的页面。和 LRU 的区别在于关注点不同——LRU 看"上一次用的时间"，LFU 看"一段时间内用了多少次"。适合访问模式稳定的场景，但对突发访问不敏感，可能误淘汰刚开始变得常用的页面。

**5. 时钟置换算法（Clock，又叫二次机会算法）**：把当前在物理页框中的所有页面连成一个**循环队列**，每个页面带一个**访问位**，被访问到就置 1。发生缺页时，指针从当前位置开始扫描：访问位为 0 就换出该页；访问位为 1 就先把它置 0（给它"第二次机会"），指针前进一位，继续找。指针无论页框满没满，都会按顺序持续移动。一次换出最多绕循环队列两圈。实现简单，命中率接近 LRU，但访问位只有 0/1 两态，判断不如 LRU 精细。

**6. 改进的时钟算法**：在时钟算法基础上，再引入**修改位**，把页面按（访问位, 修改位）分成四个优先级淘汰：

| 优先级 | 访问位 | 修改位 | 含义 |
|--------|--------|--------|------|
| 最高 | 0 | 0 | 最近未访问、未修改——直接丢弃即可，代价最小 |
| 次高 | 0 | 1 | 最近未访问但被修改过——需要写回磁盘才能丢弃 |
| 次低 | 1 | 0 | 最近访问过、未修改 |
| 最低 | 1 | 1 | 最近访问过且被修改过——最不该被换出 |

每次查找失败都会把扫描过的页面访问位清 0，一次换出最多绕循环队列四圈。这样能优先淘汰"不用写回磁盘"的页面，减少 I/O 开销，代价是实现更复杂。

六种算法的对比：

| 算法 | 优点 | 缺点 | 适用场景 |
|------|------|------|----------|
| OPT | 理论最优，缺页率最低 | 无法实现，需预知未来访问序列 | 理论分析、性能上限参考 |
| FIFO | 实现简单，开销低 | 可能出现 Belady 异常，未利用局部性 | 对性能要求不高的简单系统 |
| LRU | 基于局部性原理，性能接近 OPT | 实现复杂，开销较高 | 对性能要求高的通用系统 |
| LFU | 适合访问频率差异明显的场景 | 对突发访问不敏感 | 访问模式稳定的系统 |
| Clock | 实现简单，性能接近 LRU | 访问位是二值的，判断较粗糙 | 需要平衡性能与复杂度的系统 |
| 改进 Clock | 兼顾访问位和修改位，减少 I/O | 实现更复杂 | 对 I/O 性能要求高的系统 |

| 13 | 2 | {2,3,0} | 命中 | - |
| 14 | 1 | {2,0,1} | 缺页 | 3 此后不再出现 |
| 15 | 2 | {2,0,1} | 命中 | - |
| 16 | 0 | {2,0,1} | 命中 | - |
| 17 | 1 | {2,0,1} | 命中 | - |
| 18 | 7 | {0,1,7} | 缺页 | 2 此后不再出现 |
| 19 | 0 | {0,1,7} | 命中 | - |
| 20 | 1 | {0,1,7} | 命中 | - |

OPT 总缺页次数：**9**，是这条序列在 3 个页框下能达到的理论最优值。三者对比：**FIFO(15) > LRU(12) > OPT(9)**，直观印证了"越能利用局部性，缺页率越低"。

**Belady 异常的具体例子**：用另一条经典序列 `1 2 3 4 1 2 5 1 2 3 4 5` 对比 FIFO 在 3 个页框和 4 个页框下的表现：

| 页框数 | 逐步结果（F=缺页, H=命中） | 总缺页次数 |
|--------|------------------------------|------------|
| 3 | F F F F F F F H H F F H | 9 |
| 4 | F F F F H H F F F F F F | 10 |

页框从 3 增加到 4，FIFO 的缺页次数反而从 9 上升到 10——这就是 Belady 异常。原因是 FIFO 只按"进入时间"排队，不考虑页面近期是否还会被用到，增加页框数改变了整个置换发生的时机，可能恰好把马上要用的页面挤出去。LRU、OPT、LFU 这类基于"栈算法"（拥有 n 个页框时的驻留集，一定是拥有 n+1 个页框时驻留集的子集）性质的算法不会出现这种异常。

**Clock 算法的执行片段**：用序列 `1 2 3 4 1 2`，3 个页框，演示指针和访问位的变化：

| 步骤 | 访问页面 | 结果 | 扫描过程 | 帧内容(引用位) | 指针位置 |
|------|----------|------|----------|-----------------|----------|
| 1 | 1 | 缺页 | 帧0空闲，直接放入 | 1(1) _ _ | 1 |
| 2 | 2 | 缺页 | 帧1空闲，直接放入 | 1(1) 2(1) _ | 2 |
| 3 | 3 | 缺页 | 帧2空闲，直接放入 | 1(1) 2(1) 3(1) | 0（绕回） |
| 4 | 2 | 命中 | 页2在帧1，引用位已是1 | 1(1) 2(1) 3(1) | 0（不变，命中不移动指针） |
| 5 | 4 | 缺页 | 指针查帧0(1,ref=1)→给二次机会,ref置0,指针→1；查帧1(2,ref=1)→二次机会,ref置0,指针→2；查帧2(3,ref=1)→二次机会,ref置0,指针→0；绕回后再查帧0(1,ref=0)→淘汰1 | 4(1) 2(0) 3(0) | 1 |

这个例子展示了 Clock 算法"给过一次机会、访问位清零，绕一圈后再淘汰"的核心机制——它本质上是 LRU 的一种低成本近似。

## 六、I/O 控制方式

I/O 控制方式描述的是 CPU 与外部设备之间数据交换的管理机制。四种方式代表了"CPU 从高度参与到几乎不参与"的一条演进路线，演进动力是两个矛盾：**CPU 速度远高于 I/O 设备速度**，以及**CPU 应该专注计算、不该被 I/O 管理拖累**。

**1. 程序直接控制方式（轮询 Polling）**：CPU 通过程序主动、持续地检查设备状态寄存器，设备就绪后由 CPU 亲自执行数据传输，整个过程完全由 CPU 指令完成。实现最简单，不需要额外硬件，但 CPU 长时间忙等待，利用率极低，也无法让设备和 CPU 并行工作。只适合简单、低速设备。

**2. 中断驱动方式**：CPU 启动 I/O 操作后转去做别的事情，设备完成操作后向 CPU 发送**中断信号**。处理流程是：设备控制器发出中断请求（IRQ）→ CPU 执行完当前指令后响应中断 → 保存当前程序上下文（PC、寄存器等）→ 跳转到中断服务程序（ISR）→ ISR 处理 I/O → 恢复上下文，返回原程序继续执行。相比轮询，CPU 利用率明显提高，能实现设备并行操作，代价是每次中断都有上下文保存/恢复的开销，适合中低速设备。

**3. DMA 方式（Direct Memory Access，直接内存访问）**：由专门的 DMA 控制器接管数据传输本身，CPU 只需要初始化 DMA（设置源地址、目标地址、数据量），之后 DMA 控制器直接在设备和内存之间搬运数据，完全不需要 CPU 逐字节参与；传输全部完成后，DMA 再向 CPU 发一次中断通知。传输方式又分三种：**周期窃取**（DMA 只在 CPU 不占用总线的空当传输）、**块传输**（一次性传输整块数据）、**透明传输**（CPU 完全无感知）。DMA 大幅减少了 CPU 干预，适合高速、大批量的数据传输，代价是需要额外的 DMA 控制器硬件，且可能引发总线竞争。

**4. 通道控制方式（Channel）**：通道是一个拥有自己指令系统的**专用 I/O 处理器**，CPU 只需要向通道发出一条"启动通道程序"的命令，之后由通道自己独立执行整个 I/O 过程，一个通道还能连接多个设备形成一个 I/O 子系统。通道类型分三种：**字节多路通道**（分时服务多个低速设备）、**选择通道**（独占方式服务单个高速设备）、**数组多路通道**（结合前两者优点）。这种方式下 CPU 几乎被完全解放，通道能并行处理多个 I/O 请求，代价是硬件成本高，多见于大型机和服务器。

四种方式的演进本质是把"数据搬运"这件事逐步从 CPU 身上剥离出去，转交给更专用、更并行的硬件去做，CPU 因此能腾出手来专注于计算任务。

## 七、I/O 模型

I/O 模型描述应用程序和内核在数据读写过程中如何交互，核心是两个阶段的处理策略：**等待数据就绪阶段**（数据从网络/磁盘到达内核缓冲区）和**数据拷贝阶段**（数据从内核缓冲区拷贝到用户空间）。常见的五种模型只有一种是真正的异步 I/O，其余四种即使不阻塞在"等待"阶段，也都在"拷贝"阶段需要进程参与，因此都属于同步 I/O。

**1. 阻塞 I/O（Blocking I/O）**：进程发起 I/O 调用后，一直等到整个操作（等待+拷贝）完成才返回，是 socket 读写默认的行为。实现最简单，但一个线程同一时间只能处理一个连接，并发性能差。

```text
用户进程                       内核
  | recvfrom()                   |
  |------------------------------>|  等待数据到达(进程阻塞)
  |                               |  ......数据到达......
  |                               |  拷贝数据到用户缓冲区
  |<------------------------------|
  | 处理数据                       |
```

适用场景：简单的客户端程序、低并发教学示例、批处理脚本、不追求高并发的工具程序。

**2. 非阻塞 I/O（Non-blocking I/O）**：每次调用立即返回，要么拿到数据，要么返回 `EAGAIN`/`EWOULDBLOCK` 表示数据还没就绪，进程需要自己不断轮询检查状态。

```text
用户进程                              内核
  | recvfrom() -> EWOULDBLOCK          |
  | recvfrom() -> EWOULDBLOCK          |  轮询，数据未就绪
  | recvfrom() -> EWOULDBLOCK          |
  | ......                             |
  | recvfrom() -> 数据就绪              |
  |------------------------------------>|  拷贝数据(此阶段仍阻塞)
  |<-------------------------------------|
```

不阻塞在等待阶段，但持续轮询会让 CPU 占用率飙升。适用场景：需要快速响应的 GUI 程序、连接数不大的简单游戏服务器、需要和其他计算任务交织执行的 I/O、实时控制系统。

**3. I/O 多路复用（I/O Multiplexing）**：用 `select`/`poll`/`epoll`（Linux）等系统调用，让单个线程同时监控多个文件描述符，只有当其中至少一个就绪时才返回，然后再对就绪的 fd 执行实际的读写。

```text
用户进程                       内核
  | select / epoll_wait          |
  |------------------------------>|  同时监控多个fd，等待任一就绪
  |<-------------------------------|  返回就绪的fd列表
  | recvfrom(就绪的fd)             |
  |------------------------------>|  拷贝数据(此阶段阻塞)
  |<-------------------------------|
```

本质上仍是同步 I/O（拷贝阶段仍要等待），但一个线程能同时管理成千上万个连接，是目前应用最广泛的模型。适用场景：高并发网络服务器（Nginx、Redis）、即时通讯、实时数据推送、代理与负载均衡、WebSocket 服务器。

**4. 信号驱动 I/O（Signal-driven I/O）**：进程先注册一个 `SIGIO` 信号处理函数，然后继续执行其他任务而不阻塞；内核在数据就绪时发送 `SIGIO` 信号，进程在信号处理函数里再调用 `recvfrom` 完成数据拷贝（这一步仍会阻塞）。

```text
用户进程                          内核
  | 注册SIGIO信号处理函数              |
  | 继续执行其他任务(不阻塞)             |  后台等待数据
  |                                  |  ......数据就绪，发送SIGIO信号......
  | 信号处理函数被触发                  |
  | recvfrom()拷贝数据(此步阻塞)        |
  |<----------------------------------|
```

不常用，因为信号处理逻辑比较复杂、容易和其他信号处理产生冲突。适用场景：UDP 服务器（如 DNS）、嵌入式系统、特殊设备驱动、对延迟敏感的监控系统。

**5. 异步 I/O（Asynchronous I/O）**：进程发起 I/O 请求后立即返回，**等待数据和拷贝数据这两个阶段都完全由内核完成**，内核处理完毕后主动通知（回调或信号）进程，进程全程不参与、不阻塞。对应 POSIX 的 `aio_read`/`aio_write` 接口，以及 Linux 的 `io_uring`。

```text
用户进程                           内核
  | aio_read()发起请求                |
  | 继续执行其他任务(完全不阻塞)          |  等待数据 + 拷贝数据(全部由内核完成)
  |                                  |  ......全部完成......
  |<----------------------------------|  通知完成(回调/信号)
  | 直接使用数据                       |
```

这是五种模型里唯一真正的异步 I/O。适用场景：高性能文件服务器、数据库管理系统、Windows 平台的 IOCP 高性能服务器、大数据处理、视频流处理。

**Reactor 与 Proactor**：Reactor 模式基于 I/O 多路复用，通知应用"现在可以开始读写了"；Proactor 模式基于异步 I/O，通知应用"操作已经全部完成了"——两者的区别正好对应"谁来做拷贝这一步"。

## 八、epoll 为什么比 select/poll 高效

`select`、`poll`、`epoll` 都是 I/O 多路复用的具体实现，性能差异集中体现在如何管理"一大堆 fd"这件事上。

**select 的问题**：每次调用都要把整个 `fd_set` 从用户空间拷贝进内核，内核**线性遍历所有 fd**（O(n) 时间复杂度）找出就绪的，返回后用户态还要再遍历一遍找出到底哪些就绪了；并且 `fd_set` 大小通常被编译期常量限制在 1024 个描述符；每次调用还要重新设置一遍要监控的 fd 集合。

**poll 的改进**：用 `pollfd` 数组代替固定大小的 `fd_set`，摆脱了 1024 个连接的硬限制，但本质问题没变——依然需要线性遍历所有 fd（O(n)），依然需要整体拷贝 `pollfd` 数组。

**epoll 的高效设计**：

- **红黑树管理 fd**：`epoll_ctl` 增删改监控的 fd，时间复杂度 O(log n)，不需要每次调用都重新传入整个 fd 集合。
- **就绪链表**：内核通过**回调机制**在 fd 就绪时把它加入一个单独的就绪链表，`epoll_wait` 只需要返回这个就绪链表的内容，不需要遍历全部被监控的 fd。
- **内核态与用户态共享内存**：避免了 `select`/`poll` 那种每次调用都整体拷贝描述符集合的开销。

三者的性能对比：

| 特性 | select | poll | epoll(LT) | epoll(ET) |
|------|--------|------|-----------|-----------|
| 时间复杂度 | O(n) | O(n) | O(1) | O(1) |
| 连接数限制 | 1024 | 无 | 无 | 无 |
| 内存拷贝 | 每次调用都拷贝 | 每次调用都拷贝 | 内核用户共享 | 内核用户共享 |
| 触发方式 | 水平触发 | 水平触发 | 水平触发 | 边缘触发 |
| 编程复杂度 | 简单 | 简单 | 中等 | 复杂 |

**epoll 的核心三个系统调用**：`epoll_create` 创建一个 epoll 实例（返回专用的 epoll fd）；`epoll_ctl` 向这个实例添加/修改/删除要监控的 fd 及其关心的事件；`epoll_wait` 阻塞等待事件发生，只返回就绪的 fd 列表。

**水平触发（LT）与边缘触发（ET）**：LT 是默认模式，只要 fd 处于可读/可写状态就会一直触发通知，可以分多次读完数据，编程简单、不容易漏处理，但可能有冗余通知；ET 只在 fd 状态**发生变化的那一刻**触发一次通知，因此必须在一次通知里把数据一次性读/写完，否则这次没读完的数据不会再有单独通知——这就要求 ET 模式必须配合**非阻塞 I/O**，否则读到一半阻塞住会导致其它 fd 被饿死。ET 性能更好，但编程复杂度也更高。

**epoll 的局限性**：只在 Linux 上可用（Windows 用 IOCP）；不支持普通磁盘文件（普通文件始终被认为"就绪"，没有实际意义）；连接数很少时，`epoll_ctl`/`epoll_wait` 本身的调用开销未必比 `select`/`poll` 划算。

**惊群效应**（多个进程/线程等待同一个 fd，事件发生时全部被唤醒，但只有一个能真正处理）可以通过 Linux 4.5+ 提供的 `EPOLLEXCLUSIVE` 标志（只唤醒一个等待者）、`SO_REUSEPORT`（内核级别的连接负载均衡）、或应用层用互斥锁/单线程 accept 来解决。

## 九、磁盘调度算法

磁盘一次访问的总耗时由三部分组成：**寻道时间**（磁头移动到目标柱面，约 5~15ms）、**旋转延迟**（等待目标扇区转到磁头下方，约 4~8ms）、**传输时间**（真正读写数据，相对很短）。磁盘调度算法优化的是**寻道时间**，因为它是三者中的主要瓶颈——通过合理安排一批 I/O 请求的服务顺序，减少磁头来回移动的总距离。

下面用一个经典例子演示各算法：磁盘有 200 个柱面（编号 0~199），当前磁头位于柱面 **53**，待处理的请求队列依次是：

```text
请求队列: 98 183 37 122 14 124 65 67
磁头初始位置: 53
柱面范围: 0 ~ 199
```

（以下演示假设磁头当前正朝柱面号增大的方向移动。）

**1. 先来先服务（FCFS）**：完全按请求到达的顺序服务，不做任何优化。

```
53 → 98 → 183 → 37 → 122 → 14 → 124 → 65 → 67
```

| 移动段 | 距离 |
|--------|------|
| 53→98 | 45 |
| 98→183 | 85 |
| 183→37 | 146 |
| 37→122 | 85 |
| 122→14 | 108 |
| 14→124 | 110 |
| 124→65 | 59 |
| 65→67 | 2 |

总寻道距离 = 640，平均寻道距离 = 80.0。公平性最好、实现最简单，但磁头来回震荡（"抖动"），性能是几种算法里最差的。

**2. 最短寻道时间优先（SSTF）**：每次都选离当前磁头位置最近的请求服务，贪心策略。

```
53 → 65 → 67 → 37 → 14 → 98 → 122 → 124 → 183
```

| 移动段 | 距离 |
|--------|------|
| 53→65 | 12 |
| 65→67 | 2 |
| 67→37 | 30 |
| 37→14 | 23 |
| 14→98 | 84 |
| 98→122 | 24 |
| 122→124 | 2 |
| 124→183 | 59 |

总寻道距离 = 236，平均寻道距离 = 29.5，比 FCFS 好得多。缺点是可能"饥饿"——如果中间区域请求源源不断，边缘的请求（比如这里的 183）可能长时间轮不到。

**3. 扫描算法（SCAN，电梯算法）**：磁头朝一个方向移动，服务沿途所有请求，一直走到磁盘物理端点才反向，行为很像电梯。

```
53 → 65 → 67 → 98 → 122 → 124 → 183 → 199(端点) → 37 → 14 → 0(端点)
```

总寻道距离 = (199-53) + (199-0) = 146 + 199 = **345**，平均 43.125。没有饥饿问题，但磁头即使沿途已经没有请求了，也必须先走到物理端点才能反向，边缘请求的等待时间会偏长。

**4. 循环扫描算法（C-SCAN）**：磁头单向移动服务请求，到端点后**不服务任何请求、径直跳回起点**，再重新单向扫描，只朝一个方向服务。

```
53 → 65 → 67 → 98 → 122 → 124 → 183 → 199(端点) --跳回--> 0(端点) → 14 → 37
```

总寻道距离 = 146 + 199（快速跳回）+ 37 = **382**，平均 47.75。所有请求的响应时间更均匀（不会有的等很久有的等很短），代价是总寻道距离比 SCAN 更大。

**5. LOOK 算法**：SCAN 的改进版——磁头不必开到物理端点，走到**当前方向上最后一个请求**就反向，省掉了"跑到空端点"这一段浪费。

```
53 → 65 → 67 → 98 → 122 → 124 → 183(最远请求，反向) → 37 → 14
```

总寻道距离 = (183-53) + (183-14) = 130 + 169 = **299**，平均 37.375，比 SCAN 更省。

**6. C-LOOK 算法**：C-SCAN 的改进版——跳回时不必跳到物理端点 0，而是直接跳到**另一方向上最小的那个请求**。

```
53 → 65 → 67 → 98 → 122 → 124 → 183(最远请求) --跳回--> 14(最小请求) → 37
```

总寻道距离 = (183-53) + (183-14) + (37-14) = 130 + 169 + 23 = **322**，平均 40.25。

六种算法在这条请求序列下的对比：

| 算法 | 总寻道距离 | 平均寻道距离 | 特点 |
|------|------------|--------------|------|
| FCFS | 640 | 80.0 | 最公平最简单，性能最差 |
| SSTF | 236 | 29.5 | 局部最优，可能饥饿 |
| SCAN | 345 | 43.125 | 无饥饿，边缘等待较久 |
| C-SCAN | 382 | 47.75 | 响应时间最均匀，寻道距离最大 |
| LOOK | 299 | 37.375 | 比 SCAN 更省，不跑空程 |
| C-LOOK | 322 | 40.25 | 比 C-SCAN 更省，响应仍较均匀 |

除了这六种，还有两种面向"减少磁臂粘着"（某个方向请求持续涌入导致另一方向请求迟迟得不到服务）的变体：**N 步扫描（N-Step-SCAN）**把请求队列拆成 N 个子队列，每个子队列各自跑一遍 SCAN；**FSCAN**只用两个队列——一个是当前正在服务的队列（按 SCAN 执行），新来的请求全部进入另一个队列等下一轮，避免新请求无限期插队打断当前扫描。

现代存储设备对调度算法的影响：**SSD** 没有机械寻道，寻道时间几乎为零，传统寻道优化算法的意义大幅降低，Linux 对 SSD 通常直接用 `noop` 调度器（或干脆不调度，交给设备内部处理），转而关注并发队列深度和垃圾回收调度；**RAID 阵列**则需要跨多个物理磁盘做调度和负载均衡。适用场景归纳：FCFS 适合负载很轻的系统或 SSD；SSTF 适合中等负载、需要快速响应的交互式系统；SCAN/LOOK 适合负载较重的多用户系统（文件服务器、数据库服务器）；C-SCAN/C-LOOK 适合要求响应时间更均匀的实时系统和多媒体服务器。

## 十、设备管理

设备管理负责计算机外部设备的分配、驱动、缓冲和故障处理，核心目标是把纷繁的硬件差异封装成统一、稳定的接口。

**设备分配策略**分三种：**独占分配**（打印机这类设备一次只给一个进程用）、**共享分配**（磁盘这类设备允许多个进程并发访问）、**虚拟分配**（通过 **SPOOLing** 技术把一台独占设备伪装成可共享设备，比如打印任务先假脱机到磁盘队列，再由后台依次真正送到打印机，这样多个进程都能"随时"提交打印任务而不必互相等待）。设备调度算法就是前面讲过的 FCFS、SSTF、SCAN/C-SCAN 等（磁盘场景用得最多）。

**设备驱动与硬件抽象**：驱动程序把千差万别的硬件细节隐藏起来，向上提供 `read`/`write`/`ioctl` 这类统一接口。按访问方式分三种驱动模型：**字符设备**（键盘、鼠标，流式访问，通常不支持随机访问）、**块设备**（磁盘、SSD、USB，按固定大小的块访问，支持随机访问，有缓冲区缓存）、**网络设备**（网卡，以报文为单位传输）。

**缓冲管理**目的是抹平 CPU 和 I/O 设备之间的速度差。四种缓冲策略：**单缓冲**（一个缓冲区交替使用，简单但并行度差）、**双缓冲**（两个缓冲区轮流填充和消费，读写可以重叠进行，提高并行度）、**循环缓冲**（多个缓冲区组成环形队列，适合连续的流式数据）、**缓冲池**（系统级共享缓冲区，多个进程/设备共同使用，减少各自单独开缓冲区的浪费）。

**中断处理机制**：中断分**硬件中断**（设备产生）、**软件中断**（程序主动触发）、**异常**（执行过程中出错，如缺页）三类。处理流程是：设备发出中断请求（IRQ）→ CPU 保存现场并识别中断源 → 执行中断服务程序（ISR）→ 恢复现场，继续执行原来的程序。处理关键代码段时可以临时**屏蔽中断**，避免关键操作被打断导致状态不一致。

**错误检测与恢复**：错误分**临时错误**（可以通过重试恢复，比如网络丢包重传）和**永久错误**（需要人工介入，比如硬件损坏）。具体机制包括内存/磁盘的 **ECC 校验**、网络设备的**重传机制**、磁盘的**坏块管理**、以及设备的**热插拔支持**。

**设备虚拟化**：目的是提高设备利用率和使用灵活性。除了前面提到的 SPOOLing，还有**设备透传**（虚拟机直接访问物理设备，几乎没有虚拟化开销）和**完全软件模拟的虚拟设备**（比如虚拟网卡）。

字符设备与块设备的核心区别：字符设备是流式访问、没有固定大小、通常不支持随机访问（键盘、鼠标、串口）；块设备是块式访问、有固定块大小、支持随机访问、通常带缓冲区缓存（磁盘、SSD、USB 存储）。**DMA（直接内存访问）**允许设备直接和内存交换数据而不经过 CPU 逐字节搬运，减轻 CPU 负担、提高大数据传输效率，也是零拷贝技术的硬件基础——传统方式数据要经过"设备 → 内核缓冲区 → 用户缓冲区"两次拷贝，零拷贝技术借助 DMA 让数据直接从设备搬到用户缓冲区（或者内核缓冲区之间转移，不再经过 CPU 参与的一次内存拷贝），减少了不必要的数据搬运。

## 十一、程序编译与链接

一份高级语言源代码要变成可执行程序，要经过**预处理、编译、汇编、链接**四个阶段。

**1. 预处理（Preprocessing）**：处理源码里以 `#` 开头的指令——展开 `#include` 头文件、执行 `#define` 宏替换、处理 `#ifdef` 等条件编译指令，输出一份不再包含预处理指令的纯源码文件。

**2. 编译（Compilation）**：把预处理后的源码翻译成目标机器的汇编代码，内部又分几个子步骤——**词法分析**把源码拆解成一个个 token（关键字、标识符、常量等）；**语法分析**把 token 序列组织成抽象语法树（AST）；**语义分析**做类型检查和作用域检查；**代码优化**对中间代码做优化；**代码生成**最终产出目标平台的汇编代码。

**3. 汇编（Assembly）**：把汇编代码翻译成真正的机器指令，生成**目标文件**（`.o` 或 `.obj`），目标文件里包含代码段、数据段、符号表、重定位信息。

**4. 链接（Linking）**：把多个目标文件和需要的库文件组合成最终的可执行文件——**符号解析**把函数调用、全局变量引用和它们实际的定义关联起来；**地址分配**给各个段分配运行时的内存地址；**重定位**根据分配好的地址，修正目标文件里那些原本只是"占位"的相对/绝对地址引用；**库链接**把用到的静态库或动态库接进来。

一个多文件 C++ 项目的完整命令流程：

```bash
# 1. 预处理（生成 main.i 和 math_utils.i）
g++ -E main.cpp -o main.i
g++ -E math_utils.cpp -o math_utils.i

# 2. 编译为汇编代码（生成 main.s 和 math_utils.s）
g++ -S main.cpp -o main.s
g++ -S math_utils.cpp -o math_utils.s

# 3. 汇编为目标文件（生成 main.o 和 math_utils.o）
g++ -c main.cpp -o main.o
g++ -c math_utils.cpp -o math_utils.o

# 4. 链接为可执行文件（生成 main）
g++ main.o math_utils.o -o main

# 或者一步完成（编译器内部自动跑完上述四步）
g++ main.cpp math_utils.cpp -o main
```

**静态链接 vs 动态链接**：静态链接把库代码直接复制进最终的可执行文件，文件体积大，但运行时不依赖任何外部库文件（用 `-static` 选项）；动态链接的可执行文件只保存对库的引用，实际的库代码在程序运行时才由动态链接器加载进来，节省磁盘和内存空间，库更新时也不需要重新编译整个程序，代价是运行环境必须有对应版本的动态库。

**重定位**是链接过程里绕不开的一步：链接器把多个目标文件里相同类型的段合并到一起时，各个符号原来在自己目标文件里的地址就不再有效了，需要统一调整成合并后的实际地址——这个过程记录在重定位表里，分为链接时重定位（生成可执行文件时就确定所有地址）和加载时重定位（可执行文件里保留一部分不确定地址，等程序被加载进内存时才最终确定，这也是位置无关代码 PIC 和动态库能被加载到不同地址的基础）。

编译和解释的区别：编译是一次性把源代码整体翻译成机器码后再执行，执行效率高；解释是逐行翻译逐行执行，调试方便但效率较低；即时编译（JIT）则是运行时把热点代码编译成机器码，兼顾了两者的优点（如 JVM、V8）。

## 十二、硬链接与软链接

硬链接和软链接（符号链接）都是 Linux 文件系统里"给同一份数据起别名"的机制，但实现原理完全不同。

**硬链接（Hard Link）**：本质是让一个新的目录项直接指向已有文件的 **inode**，和原文件共享同一个 inode（也就共享同一份数据块），inode 里的引用计数 `i_links_count` 会递增。因为 inode 是同一个，硬链接和原文件地位完全平等，没有"谁是本体、谁是别名"的区别；只有当 `i_links_count` 减到 0 时（所有硬链接和原文件都被删除），inode 和数据块才会真正被释放。

**软链接（Soft Link / 符号链接）**：是一个独立的文件，拥有自己的 inode，类型标记为符号链接（`S_IFLNK`），它的数据块里存的不是真实数据，而是**目标文件的路径字符串**；文件大小就等于这个路径字符串的长度。

两者的差异可以归纳如下：

| 维度 | 硬链接 | 软链接 |
|------|--------|--------|
| inode | 与原文件共享同一个 inode | 拥有独立的 inode |
| 跨文件系统 | 不支持（inode 号只在同一文件系统内唯一） | 支持 |
| 删除原文件 | 硬链接仍可访问数据，直到引用计数为 0 | 软链接成为悬空链接，无法再访问 |
| 链接对象 | 只能链接文件，不能链接目录 | 可以链接文件和目录 |
| 存储内容 | 目录项直接指向 inode | 数据块里存储目标路径字符串 |

Linux 命令层面的验证：

```bash
# 创建原始文件
echo "hello" > original.txt
ls -li original.txt
# 123456 -rw-r--r-- 1 user group 6 Jan 1 10:00 original.txt
# ↑ inode: 123456, 链接数: 1

# 创建硬链接：inode 相同，链接数变为 2
ln original.txt hard_link.txt
ls -li original.txt hard_link.txt
# 123456 -rw-r--r-- 2 user group 6 Jan 1 10:00 hard_link.txt
# 123456 -rw-r--r-- 2 user group 6 Jan 1 10:00 original.txt

# 创建软链接：inode 不同，是独立文件
ln -s original.txt soft_link.txt
ls -li soft_link.txt
# 789012 lrwxrwxrwx 1 user group 12 Jan 1 10:00 soft_link.txt -> original.txt

# 删除原始文件后
rm original.txt
cat hard_link.txt     # 仍能正常读取，因为 inode 和数据块还在
cat soft_link.txt     # 报错：目标文件不存在，软链接已"悬空"
```

**为什么硬链接不能跨文件系统**：inode 号的编号空间是每个文件系统各自独立分配的，不同文件系统完全可能出现相同的 inode 号，跨文件系统直接引用 inode 号会产生歧义，因此硬链接被限制在同一文件系统内。软链接因为存的是路径字符串（本质是"再走一遍路径查找"），不涉及 inode 号的直接引用，所以可以跨文件系统。

**为什么大多数系统禁止给目录创建硬链接**：目录如果可以随意建立硬链接，很容易构造出目录自己指向自己的祖先目录这种**目录环**，会让依赖"目录结构是一棵树"这个假设的程序（比如递归遍历文件树的程序）陷入死循环；相比之下，文件的硬链接不会有这个问题，因为所有硬链接都是平级的，不存在层级关系。

典型应用场景：**软件版本管理**（`java -> java-11` 这类符号链接方便切换版本）、**快捷方式**（常用目录的快速访问入口）、**路径重定向**（把旧路径无痛指向新位置）、**配置文件统一管理**（多个位置的配置都链接到同一份实际配置）。

## 十三、CPU 与 GPU 的区别

CPU（Central Processing Unit，中央处理器）和 GPU（Graphics Processing Unit，图形处理器）都是"处理器"，但设计目标完全不同——一个为**复杂的通用逻辑控制**优化，一个为**大规模简单并行计算**优化。

**CPU 的构成与功能**：CPU 主要由**运算器**和**控制器**两部分构成（从硬件实现角度也可以说成"数据通路"和"控制部件"，两种划分角度不同但不矛盾）。CPU 的五大功能中，前四项由控制器完成，最后一项由运算器完成：

1. **指令控制**：保证指令按程序预定的顺序执行，同时也保证单条指令内部"取指→分析→执行"这三步的顺序执行。
2. **操作控制**：产生完成一条指令所需要的各种操作信号，发送给对应的执行部件。
3. **时序控制**：对每个操作信号进行精确定时——什么时候产生、持续多久。
4. **中断控制**：及时响应内部异常（如缺页）和外部中断请求（如键盘输入）。
5. **数据加工**：对数据做算术运算、逻辑运算，或者在部件之间传送数据。

**GPU 的构成与功能**：GPU 主要由大量**流处理器**和**显存**构成，核心特点是拥有成千上万个相对简单的核心，可以同时处理海量数据——比如图像处理里，每个像素的计算天然是独立的，GPU 可以把这些像素分给成千上万个核心并行处理。GPU 最初为**图形渲染**而生（把 3D 模型转换为 2D 图像，处理光照、阴影、纹理），现代 GPU 借助其强大的并行计算能力，被广泛用于**通用计算**（GPGPU），例如深度学习训练、科学模拟、密码学计算。GPU 专注于高吞吐量，处理大批量简单重复的运算效率极高，但处理复杂分支逻辑和单线程任务的效率不如 CPU。

两者的核心差异可以概括为：CPU 少量核心、每个核心都很强，擅长处理复杂逻辑和任务调度；GPU 大量核心、每个核心相对简单，擅长同一套逻辑在海量数据上并行重复执行。在实际系统里两者是协作关系——CPU 负责整体的逻辑控制和任务调度，把适合大规模并行的子任务甩给 GPU 去跑（比如深度学习训练里，CPU 负责数据预处理和调度，GPU 负责矩阵运算）。

## 十四、冯·诺依曼体系结构与哈佛体系结构

这两种体系结构的根本分歧在于：**指令和数据是否共用同一个存储器**。

**冯·诺依曼体系结构**：由数学家冯·诺依曼在 1945 年研究 EDVAC 时提出，核心思想是"**存储程序**"——程序和数据以同等地位一起放进同一个存储器，CPU 靠指令周期的不同阶段（取指周期 vs 执行周期）来区分当前正在处理的到底是指令还是数据。主要特点：

1. 采用存储程序方式工作：程序预先存入存储器，计算机运行时从程序首地址取出第一条指令并执行，此后依次执行后续指令直到程序结束。
2. 硬件系统由**运算器、存储器、控制器、输入设备、输出设备**五大部件组成。
3. 指令和数据都存放在同一个存储器里，按地址访问，两者在存储器里的表现形式（二进制）没有区别。
4. 指令由**操作码**（表示做什么操作）和**地址码**（表示操作数在存储器里的位置）组成。

**哈佛体系结构**：核心特点是把**指令存储器和数据存储器物理上分开**，各自配一套独立的地址总线和数据总线。主要特点：

1. 指令和数据分别存放在两个独立的存储器里，各走各的总线。
2. 因为总线独立，CPU 可以在同一个时钟周期内**同时**读取一条指令和一个数据，并行度高于冯·诺依曼结构。
3. 需要两套独立的存储器和总线，硬件设计复杂度、成本都更高。

两种结构的对比：

| 维度 | 冯·诺依曼体系结构 | 哈佛体系结构 |
|------|-------------------|--------------|
| 存储器 | 指令和数据共用一个存储器 | 指令和数据分开存储 |
| 总线 | 一套地址/数据总线 | 指令、数据各一套独立总线 |
| 并行度 | 同一时刻只能取指令或取数据 | 可同时取指令和数据 |
| 硬件复杂度 | 较低 | 较高 |
| 典型应用 | 通用计算机（PC、服务器） | 早期单片机、部分 DSP 芯片 |

现代通用计算机（PC、服务器）基本都基于冯·诺依曼体系结构设计，由**主机**（CPU + 主存储器）和**外部设备**（I/O 设备）两大部分组成；哈佛体系结构更多见于对指令/数据吞吐有极致要求的嵌入式场景，比如部分单片机和数字信号处理器（DSP）会同时取指令和数据以提升执行效率。需要注意的是，不少现代处理器（包括很多 CPU 的一级缓存设计）在**缓存层面**采用指令缓存和数据缓存分离的哈佛式结构，但对上层的主存储器而言仍然是统一编址的冯·诺依曼结构——这种"外层冯·诺依曼、内层哈佛"的混合设计，兼顾了通用性和缓存访问的并行效率。
