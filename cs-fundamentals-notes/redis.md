# Redis 核心机制

Redis 面试的考点集中在两条主线:一是"数据怎么存"——五种基础结构加上底层编码、内存淘汰与过期策略、RDB/AOF 持久化;二是"高并发下会出什么问题、怎么防"——缓存穿透/击穿/雪崩、分布式锁、布隆过滤器、主从同步。本篇按这个顺序展开,重点讲清楚穿透、击穿、雪崩三个最容易混淆的概念。

## 一、Redis 数据结构

**五种基础结构**

| 结构 | 底层实现 | 典型场景 | 命令示例 |
|------|----------|----------|----------|
| String | SDS(简单动态字符串),记录长度实现 O(1) 取长度,预留空间减少频繁扩容 | 缓存单个对象/JSON、计数器、分布式锁 | `SET user:1:name "tom"`<br>`INCR article:1001:view_count` |
| Hash | 数据量小时用 ziplist(压缩列表)紧凑存储,数据量大或字段多时转为哈希表 | 存对象的多个字段(用户信息、商品信息),可以只更新某个字段而不用整体重写 | `HSET user:1 name "tom" age 20`<br>`HGET user:1 name` |
| List | quicklist(链表 + 压缩列表的结合),兼顾双端操作效率和存储紧凑性 | 消息队列、最新动态、时间线 | `LPUSH order:queue 1001`<br>`RPOP order:queue` |
| Set | 元素为整数时用 intset,否则用哈希表 | 去重、标签、共同好友(交集)、黑名单 | `SADD tag:java user:1`<br>`SISMEMBER tag:java user:2` |
| ZSet(有序集合) | 跳表(按 score 排序、支持范围查询) + 哈希表(按元素名 O(1) 查 score) | 排行榜、延迟队列、范围查询类需求 | `ZADD rank:game 100 user:1`<br>`ZREVRANGE rank:game 0 2 WITHSCORES` |

ZSet 用跳表而不是红黑树的原因:跳表实现范围查询(`ZRANGEBYSCORE`)只需要在链表层顺序遍历,代码复杂度远低于红黑树的中序遍历,且跳表的多层索引结构天然支持按 rank 定位,工程实现更简单。

**扩展结构**

- **Bitmap**:本质是对 String 做按位操作,常用来做签到、每日活跃标记、在线状态——一个 bit 代表一个状态位,极致省内存。
- **HyperLogLog**:用固定且很小的内存(约 12KB)近似统计海量数据的基数(去重计数),代价是存在小比例误差,典型场景是网页 UV 统计。
- **Geospatial(GEO)**:建立在有序集合之上,用 score 编码经纬度,支持"附近的人""附近门店"这类地理位置查询。
- **Stream**:5.0 引入的消息流结构,相比 List 多了消费位点(offset)、消费者组、消息确认(ACK)机制,适合需要"消息不丢失、支持多消费者分组消费"的场景,如订单流、日志流水。

```
XADD stream:order * orderId 1001 status created
XREAD COUNT 1 STREAMS stream:order 0
```

选型口诀:单值缓存和计数器用 String;对象的部分字段读写用 Hash;需要双端操作的队列用 List;要去重或做集合运算用 Set;要排序或做范围查询用 ZSet;海量数据只关心基数用 HyperLogLog;需要消费组和位点管理用 Stream。

## 二、内存淘汰策略

当 `maxmemory` 配置的内存上限被触及时,Redis 按配置的淘汰策略决定丢弃哪些数据,一共 8 种:

| 策略 | 作用范围 | 淘汰依据 |
|------|----------|----------|
| noeviction | 不淘汰 | 内存满后直接报错,写请求失败(默认策略,慎用) |
| volatile-lru | 仅设置了过期时间的 key | 最近最少使用 |
| allkeys-lru | 所有 key | 最近最少使用,纯缓存场景最常用的策略之一 |
| volatile-lfu | 仅设置了过期时间的 key | 最不经常使用(访问频率) |
| allkeys-lfu | 所有 key | 最不经常使用,适合热点分布相对稳定的场景 |
| volatile-random | 仅设置了过期时间的 key | 随机淘汰 |
| allkeys-random | 所有 key | 随机淘汰 |
| volatile-ttl | 仅设置了过期时间的 key | 优先淘汰剩余存活时间(TTL)更短的 key |

**LRU 与 LFU 的区别**:LRU(Least Recently Used)看"最近有没有被访问",只要最近访问过就不容易被淘汰,哪怕访问频率很低;LFU(Least Frequently Used)看"访问频率高不高",即使刚被访问过,但历史累计频率低,依然可能被淘汰。业务里如果存在"曾经很热但已经过气"的数据,LFU 比 LRU 更能准确识别真正的热点。Redis 出于性能考虑,两者都是近似实现(采样估算),不是严格精确的算法。

**volatile-\* 与 allkeys-\* 的取舍**:如果实例里大部分 key 都没设置 TTL,用 volatile 系列策略在内存满时可能无 key 可淘汰,照样会导致写入失败;纯缓存场景(所有数据都可以重新计算或重新查库)通常直接用 allkeys-lru 或 allkeys-lfu,不必区分是否有 TTL。

## 三、过期策略

内存淘汰策略解决"内存满了怎么办",过期策略解决"设置了 TTL 的 key 到期后什么时候真正被删除"——这是两套独立的机制,容易被混着问。Redis 采用**惰性删除 + 定期删除**的组合,刻意不用定时删除。

- **惰性删除**:只有在访问某个 key 时才检查它是否过期,过期就立即删除并返回空。优点是不需要额外扫描,对 CPU 友好;缺点是如果一个过期 key 一直没被访问,会一直占着内存不被回收。
- **定期删除**:后台线程周期性地从设置了 TTL 的 key 中抽样检查,发现过期就删除,并且有执行时间片限制,避免长时间占用主线程影响正常请求。优点是能持续回收内存,不完全依赖惰性删除的"被动触发";缺点是抽样式检查不保证实时性,过期 key 可能会短暂残留。
- **定时删除(未采用)**:理论上可以为每个 key 单独维护一个定时器,到期立刻删除,但这需要为海量 key 维护海量定时器,调度开销和内存开销都难以接受,与 Redis 单线程高性能的设计目标冲突,所以没有采用。

Redis 内部维护一个专门的"过期字典"记录带 TTL 的 key,过期判断和删除都以主节点为准,再通过 `DEL` 命令的方式同步给从节点,保证主从数据一致。常用命令:`EXPIRE`/`PEXPIRE`/`EXPIREAT` 设置过期时间,`TTL`/`PTTL` 查看剩余时间,`PERSIST` 取消过期时间,`SET key value EX seconds` 设置值的同时带上过期时间,`KEEPTTL` 选项在覆盖写入时保留原有 TTL。

## 四、持久化机制:RDB 与 AOF

**RDB(快照)**

某一时刻把整个内存数据集写成一个二进制快照文件(默认 `dump.rdb`)。

- 触发方式:配置规则自动触发(如 `save 900 1` 表示 900 秒内有至少 1 次写操作就触发),或手动执行 `SAVE`(同步阻塞主线程,生产环境基本不用)/`BGSAVE`(fork 子进程后台生成,主线程继续对外服务)。
- 优点:文件体积小,恢复速度快,适合做全量备份和数据迁移。
- 缺点:两次快照之间的数据如果发生宕机会丢失;fork 子进程瞬间会有内存和 CPU 开销,大内存实例上可能造成短暂卡顿。

**AOF(追加日志)**

把每一条修改数据的写命令追加写入日志文件,重启时重放这些命令来恢复数据。刷盘策略由 `appendfsync` 控制:

| 策略 | 行为 | 特点 |
|------|------|------|
| always | 每条写命令立即刷盘 | 最安全,性能开销最大 |
| everysec | 每秒刷盘一次(生产常用) | 性能和安全的折中,最多丢 1 秒数据 |
| no | 由操作系统决定何时刷盘 | 性能最好,风险最高 |

AOF 的优点是数据丢失窗口比 RDB 小,文件内容是可读的命令流;缺点是文件通常比 RDB 大,重放命令恢复的速度也比直接加载 RDB 慢。

**AOF 重写**:`BGREWRITEAOF` 会把历史命令合并压缩——比如对同一个 key 执行了 100 次 `INCR`,重写后直接变成一条 `SET key 100`,大幅缩减文件体积,而不是逐条保留历史命令。

**混合持久化**:AOF 重写时,前半部分按 RDB 的二进制快照格式写入全量数据,后半部分继续追加增量的 AOF 命令。重启恢复时先加载 RDB 部分(快),再重放后面的增量命令(新),兼顾了 RDB 的恢复速度和 AOF 的数据完整性。

**如何选择**:纯缓存、数据可从数据库重建的场景可以关闭持久化换性能;对数据丢失敏感的场景至少开 `AOF everysec`;兼顾恢复速度和数据安全,用 RDB + AOF 混合持久化。注意:两者都开启时,Redis 重启默认优先用 AOF 恢复,因为它的数据完整性更高。

## 五、缓存穿透、击穿、雪崩

这三个概念的相同点是"最终都会导致大量请求打到数据库",但触发条件和解法完全不同,是高频面试题,必须能一句话分清楚区别。

| 维度 | 缓存穿透 | 缓存击穿 | 缓存雪崩 |
|------|----------|----------|----------|
| 核心特征 | 查询的数据**根本不存在**,缓存和数据库都没有 | **单个热点 key** 恰好过期,大量并发同时回源重建 | **大量 key** 同一时间失效,或 Redis **整体不可用** |
| 典型触发场景 | 恶意攻击、参数错误、爬虫扫描不存在的 ID | 秒杀商品、热搜词条,该 key 的 TTL 到点 | 批量导入时设置了相同 TTL、缓存节点宕机 |
| 数据库压力来源 | 每次相同的无效请求都穿过缓存直达数据库 | 短时间内大量相同 key 的请求集中冲向数据库 | 大范围、不同 key 的请求同时绕过缓存层 |

**缓存穿透的解法**

1. **参数校验**:在业务入口拦截明显非法的请求(负数 ID、格式错误的主键),从源头减少无意义查询。
2. **缓存空值**:数据库查不到时,把这个"空结果"也存进 Redis,设置一个较短的 TTL(比如 2 分钟)。下次同样的请求直接在缓存层返回空,不再打到数据库。实现简单,代价是要额外占用一些缓存空间,且短期内如果数据库真的插入了这条数据,会有短暂的不一致。
3. **布隆过滤器**:提前把数据库中所有可能存在的 key 放进布隆过滤器,请求先过一遍过滤器——判定"一定不存在"就直接拒绝,连 Redis 都不用查;只有过滤器判定"可能存在"才继续走缓存和数据库。适合 key 集合巨大、且不存在查询占比很高的场景,缺点是有一定误判率,需要提前规划好容量。

**缓存击穿的解法**

1. **互斥锁/分布式锁**:缓存失效的瞬间,只放一个线程去查数据库并重建缓存,其他线程等待或短暂重试。优点是强保护数据库,不会有多个线程同时打库;代价是等待的线程会有一定延迟。
2. **热点 key 永不过期**:对极少数已知的热点数据不设置物理 TTL,而是在逻辑上快到期前由后台线程异步刷新,业务侧感知不到失效。
3. **逻辑过期**:缓存值里额外带一个"逻辑过期时间"字段而不是用 Redis 自身的 TTL。请求读到已经逻辑过期的数据时,先照常返回这个旧值(保证不阻塞),同时另起一个线程异步重建缓存。这种方式优先保可用性和响应速度,代价是短时间内返回的是稍微过时的数据。
4. **热点预热**:活动开始前、流量高峰前提前把预计会成为热点的数据加载进缓存,避免第一波流量就撞上缓存未命中。

方案怎么选:要求强一致、能接受少量线程等待,用互斥锁;要求任何时候都快速响应、能接受短暂脏读,用逻辑过期。

**缓存雪崩的解法**

1. **过期时间打散**:给 TTL 增加一个随机偏移量(比如基础 30 分钟 + 随机 0~5 分钟),避免大批 key 在同一时刻集中失效。
2. **Redis 高可用**:用主从 + 哨兵或 Redis Cluster,单个节点故障不会导致整个缓存层不可用。
3. **多级缓存**:本地缓存(如进程内的 Caffeine)+ Redis + 数据库分层,Redis 故障时本地缓存还能扛住一部分热点流量。
4. **限流、降级、熔断**:缓存层异常时,主动限制打到数据库的流量,必要时对非核心功能降级,保护数据库不被瞬间打垮。
5. **数据预热和错峰刷新**:大批量缓存数据分批、错开时间刷新,而不是一次性统一设置相同的过期时间。

**一句话区分三者**:穿透是"数据不存在";击穿是"一个热点数据的过期时机不对";雪崩是"一大片数据或者整个缓存层同时失效"。穿透用布隆过滤器/缓存空值防,击穿用互斥锁/逻辑过期防,雪崩用打散 TTL + 高可用防。

## 六、Redis 分布式锁

分布式锁解决的是"多个进程/多台机器之间竞争同一把锁"的问题,不同于单机内的 `synchronized`,必须依赖一个所有节点都能访问到的中间存储,Redis 凭借单线程命令的原子性成为常见选择。

**加锁**

```
SET lockKey requestId NX PX 30000
```

- `NX`:只有键不存在时才设置成功,保证同一时刻只有一个客户端能拿到锁。
- `PX 30000`:设置 30 秒过期时间,防止持有锁的客户端崩溃后锁永远得不到释放。
- `requestId`:客户端生成的唯一标识(UUID 或线程标识),用来标记"这把锁是谁加的"。

**释放锁必须先判断归属再删除**,不能直接 `DEL`。用 Lua 脚本保证"比较 + 删除"是原子操作:

```lua
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end
```

如果直接 `DEL` 而不做比对,可能出现这种情况:客户端 A 加锁后业务执行超时,锁自动过期,客户端 B 趁机拿到锁;这时 A 执行完业务才去 `DEL`,会把 B 的锁误删。用 Lua 脚本先 `GET` 比对 `requestId` 相等才 `DEL`,就避免了误删别人的锁。

**业务执行时间不可预估的场景**:如果提前设置的 TTL 覆盖不了实际业务耗时,可以用类似 Redisson 的**看门狗(watchdog)机制**——后台线程定期检测锁是否还被持有,如果业务还没跑完就自动给锁续期,业务真正结束后才真正释放锁,避免了"TTL 设置多长"这个两难问题(太短会提前释放导致锁失效,太长会在客户端崩溃后让锁长期占用、故障恢复变慢)。

**常见错误写法**

1. `SETNX` 和 `EXPIRE` 分成两条命令执行——如果客户端在两条命令之间崩溃,锁会没有过期时间,变成永久锁,必须用 `SET key value NX PX ms` 一条命令原子完成。
2. TTL 设置不合理——过短导致业务没执行完锁就提前释放,过长导致持锁者故障后其他客户端要等很久才能拿到锁。
3. 获取锁失败后疯狂自旋重试——会造成 CPU 空转和大量无效请求,应该配合指数退避或者设置获取超时后快速失败。

**局限性**:单实例的 Redis 分布式锁不能保证绝对安全,尤其在主从异步复制场景下——如果客户端在主节点加锁成功,但这个写命令还没同步到从节点主节点就宕机了,故障转移后新主节点上并没有这把锁,另一个客户端可能重新加锁成功,导致同一时刻出现两个"持锁者"。对锁的安全性要求非常高的场景,需要考虑更严格的方案(如 Redlock 算法,通过向多数派独立的 Redis 实例申请锁来降低单点异步复制带来的风险),但也要权衡它带来的额外复杂度和网络开销是否必要。

## 七、布隆过滤器

布隆过滤器是一种用极小内存判断"某个元素是否存在"的概率型数据结构,由一个**位数组**(初始全 0,长度 m)和 **k 个不同的哈希函数**组成。

**写入**:对元素做 k 次哈希计算,得到 k 个位置,把位数组里这些位置全部置为 1。

**查询**:同样做 k 次哈希计算,检查这 k 个位置——

- 只要有一个位置是 0,说明这个元素**一定不存在**(可以直接拦截,不必再查 Redis 或数据库);
- 如果 k 个位置全部是 1,说明这个元素**可能存在**(需要继续查缓存/数据库确认)。

**为什么会误判、但不会漏判**:不同元素的哈希结果可能落在同一批位置上,多个元素叠加写入后,某个原本没插入过的元素也可能凑巧让它对应的 k 个位置全部变成 1,这就是误判(假阳性)。但只要某个位置是 0,就一定说明从未有任何元素让它置 1,所以判定"不存在"是绝对准确的,不会出现漏判(假阴性)。

**优缺点**

- 优点:内存占用极小(即使是海量 key 也只需要几 MB 到几十 MB),插入和查询都是 O(k) 的位运算,速度极快,适合放在请求入口做第一道拦截。
- 缺点:存在误判率(可以通过增大位数组和哈希函数个数降低,但无法降到 0);标准布隆过滤器不支持删除——因为一个 bit 可能被多个元素共用,直接把某个元素对应的位置清零可能误伤了其他元素。

**在 Redis 中的使用方式**

1. 通过 `RedisBloom` 模块提供的专用命令:

```
BF.RESERVE user:id:bf 0.01 1000000   -- 创建过滤器,误判率 0.01,预计装 100 万元素
BF.ADD user:id:bf 1001               -- 添加元素
BF.EXISTS user:id:bf 1001            -- 查询元素是否可能存在
```

2. 也可以基于原生 Bitmap 自己实现位数组和哈希函数逻辑,不依赖额外模块。

**典型场景**:防止缓存穿透——请求先过布隆过滤器,判定不存在就直接拒绝,避免恶意或无效请求持续打到 Redis 和数据库。使用前需要根据预计元素数量和可接受的误判率提前规划容量,并且要把数据库里已有的全部 key 一次性导入过滤器,后续新增数据时同步写入,否则会出现"数据库里已经有、过滤器却说不存在"的问题。

## 八、Redis 主从同步

主从复制是 Redis 高可用的基础,主节点负责写,从节点分担读流量,同时是哨兵故障转移和集群容灾的前提。

**建立复制连接**:从节点连上主节点后,依次执行三步——发送 `PING` 确认链路可用,发送 `REPLCONF` 上报自己的监听端口和能力,发送 `PSYNC` 请求正式开始同步数据。

**全量同步**(首次复制,或无法进行增量同步时触发):

```
从节点: PSYNC ? -1                        (没有历史复制上下文)
主节点: 执行 BGSAVE 生成 RDB 快照
主节点: 将 RDB 文件发送给从节点
从节点: 清空自己的旧数据,加载收到的 RDB
主节点: 把生成/发送 RDB 期间产生的新写命令暂存进复制缓冲区
主节点: RDB 加载完成后,把缓冲区里攒的增量命令补发给从节点
```

**增量同步**(短暂断线重连场景):从节点记录自己同步到的 `offset`,主节点用 `repl_backlog_buffer`(复制积压缓冲区)维护一段最近的写命令历史。重连时从节点带着 `master_replid + offset` 发起 `PSYNC`:如果 backlog 里还留着断线期间缺失的那部分命令,主节点直接补发这部分增量;如果 backlog 已经被覆盖冲掉,或者 `replid` 对不上(比如主节点重启过),就退化成全量同步。

**两个关键状态**:`master_replid` 标识当前这条复制流的身份,`offset` 是复制数据流的位置指针,两者共同决定增量同步能否成功衔接。

**日常命令传播**:首次同步完成后,主节点会把后续所有写命令异步持续传播给从节点,从节点周期性地向主节点回报自己的同步进度(ACK)。

**问题与注意事项**

- 全量同步开销大:需要 fork 子进程、生成 RDB、传输文件,大实例场景下对主节点的 CPU、内存、网络都有明显影响,应该尽量让从节点保持稳定连接、避免频繁触发全量同步。
- `repl_backlog_buffer` 太小:网络抖动或从节点短暂下线时间稍长,缺失的命令就可能被新写入覆盖掉,导致本该走增量同步的场景被迫退化成全量同步,应根据写入量和网络状况适当调大。
- 一致性是最终一致而非强一致:主从复制是异步的,主节点写成功即返回,不等待从节点确认,所以从节点数据总会有轻微的滞后(复制延迟),故障切换时可能丢失极少量刚写入但还没同步过去的数据。
- 在主从架构基础上,生产环境通常还会引入**哨兵(Sentinel)**持续监控主从节点的健康状态,一旦发现主节点故障,由哨兵集群投票选出新的主节点并自动完成故障转移,这也是主从复制机制之上更完整的高可用方案。
